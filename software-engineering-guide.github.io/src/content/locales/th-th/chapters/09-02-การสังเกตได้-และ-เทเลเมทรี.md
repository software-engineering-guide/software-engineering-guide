# 9.2 การสังเกตได้ และเทเลเมทรี

## ภาพรวมและแรงจูงใจ

[เทเลเมทรี](https://en.wikipedia.org/wiki/Telemetry) (telemetry) คือข้อมูลที่ระบบปล่อยออกมาเกี่ยวกับพฤติกรรมของตัวเอง ได้แก่ เมตริก บันทึก (log) trace และเหตุการณ์ที่เก็บจากซอฟต์แวร์ที่กำลังทำงาน การเฝ้าติดตาม (monitoring) ตอบคำถามที่คุณรู้อยู่แล้วว่าต้องถามจากเทเลเมทรีนั้น ดิสก์เต็มหรือยัง อัตราข้อผิดพลาดเกินเกณฑ์หรือไม่ บริการยังทำงานอยู่ไหม ส่วน[ความสามารถในการสังเกตระบบ](https://en.wikipedia.org/wiki/Observability_(software)) (observability) กว้างกว่านั้น คือความสามารถในการถามคำถามใหม่เกี่ยวกับสถานะภายในของระบบจากภายนอกโดยไม่ต้องส่งโค้ดใหม่ เพื่อให้เข้าใจพฤติกรรมที่คุณไม่เคยคาดคิด เมื่อระบบเติบโตเป็นสถาปัตยกรรมแบบกระจาย [ไมโครเซอร์วิส](https://en.wikipedia.org/wiki/Microservices) และ[สถาปัตยกรรมขับเคลื่อนด้วยเหตุการณ์](https://en.wikipedia.org/wiki/Event-driven_architecture) ความล้มเหลวที่เจ็บที่สุดคือความล้มเหลวที่ไม่มีใครเห็นมาก่อน และความสามารถในการสังเกตระบบคือสิ่งที่ช่วยให้คุณแก้ไขมันได้ การเฝ้าติดตามบอกว่ามีบางอย่างผิดปกติ ความสามารถในการสังเกตระบบช่วยให้คุณค้นหาว่าทำไม

สำหรับทีมขนาดใหญ่ ความแตกต่างนี้เป็นตัวตัดสิน คุณเคยเข้าใจโมโนลิธได้ด้วยการอ่านบันทึกบนเครื่องเดียว แต่แพลตฟอร์มสมัยใหม่ครอบคลุมบริการนับร้อย หลายทีม หลายภูมิภาค และการพึ่งพาบุคคลที่สาม ซึ่งคำขอของผู้ใช้เพียงหนึ่งรายการอาจแตะส่วนประกอบหลายสิบตัว ไม่มีใครเก็บภาพทั้งระบบไว้ในหัวได้ เทเลเมทรีร่วมที่มีคุณภาพจึงกลายเป็นเนื้อเยื่อเชื่อมที่ทำให้วิศวกรทุกคนตามคำขอข้ามขอบเขตได้ เทียบอาการข้ามบริการ และให้เหตุผลเกี่ยวกับระบบที่ไม่มีใครเป็นเจ้าของทั้งหมด ถ้าไม่มี เหตุการณ์จะลากยาว การกล่าวโทษจะปลิวไปมาระหว่างทีม และสาเหตุที่แท้จริงจะซ่อนอยู่

ระบบองค์กรขนาดใหญ่และภาครัฐยกระดับเดิมพันด้วยการปฏิบัติตามกฎระเบียบ ความสามารถในการตรวจสอบ และความรับผิดชอบต่อสาธารณะ หน่วยกำกับดูแลอาจต้องการหลักฐานว่าใครเข้าถึงอะไรและเมื่อไร ทีมความมั่นคงปลอดภัยต้องใช้เทเลเมทรีตรวจจับการบุกรุก บริการที่ให้บริการประชาชนต้องแสดงได้ว่าเป็นไปตามข้อผูกพันด้านประสิทธิภาพที่ประกาศไว้ ความสามารถในการสังเกตระบบที่ดีรับใช้ทั้งหมดนี้พร้อมกัน: เป็นเครื่องมือวิศวกรรม มาตรการควบคุมความมั่นคงปลอดภัย และกลไกความรับผิดชอบในตัวเดียว การใช้มาตรฐานการติดตั้งเครื่องมือวัดแบบเปิดช่วยหลีกเลี่ยงการผูกติดกับเอเจนต์เฉพาะของผู้ให้บริการรายเดียว ซึ่งสำคัญอย่างยิ่งเมื่อระบบต้องอยู่ได้หลายทศวรรษและผ่านรอบการจัดซื้อหลายครั้ง

*ดูเพิ่มเติม:* บทที่ 9.1 (วิศวกรรมความน่าเชื่อถือของไซต์และ SLO), บทที่ 9.3 (การจัดการเหตุการณ์) และบทที่ 3.3 (ระบบแบบกระจาย)

## หลักการสำคัญ

- **ติดตั้งเครื่องมือวัดเพื่อคำถามที่ยังไม่รู้** ออกแบบเทเลเมทรีให้สืบสวนความล้มเหลวแปลกใหม่ได้ ไม่ใช่แค่แบบที่คุณคาดไว้
- **สามเสาหลัก เรื่องราวเดียว** เมตริก บันทึก และ trace เป็นมุมมองที่เสริมกัน คุณค่าของมันคูณเพิ่มเมื่อเชื่อมโยงกัน ไม่ใช่แยกเป็นไซโล
- **ทำทุกอย่างให้มีโครงสร้าง** เทเลเมทรีที่มีโครงสร้างและเครื่องอ่านได้พร้อมฟิลด์สม่ำเสมอ ดีกว่าข้อความอิสระที่มีแต่มนุษย์อ่านได้
- **เชื่อมโยงด้วยตัวระบุร่วม** ตัวระบุ trace และคำขอที่ส่งต่อทุกที่ช่วยให้คุณเย็บเหตุการณ์เดียวข้ามบริการได้
- **แจ้งเตือนที่อาการ ไม่ใช่สาเหตุ** เรียกคนเมื่อมีปัญหาที่ผู้ใช้เห็นได้ ปล่อยให้แดชบอร์ดและการสืบสวนเผยสาเหตุเบื้องหลัง
- **ทุกการเรียกเวรต้องลงมือทำได้** การแจ้งเตือนที่ไม่ต้องการการลงมือจากมนุษย์คือสัญญาณรบกวนที่กัดกร่อนความไว้วางใจและก่อให้เกิดความเหนื่อยล้า
- **ความหลากหลายของค่าสูง (high cardinality) คือฟีเจอร์** ความสามารถในการแบ่งตามผู้ใช้ คำขอ ภูมิภาค และเวอร์ชัน คือสิ่งที่ทำให้การดีบักใน production เป็นไปได้
- **เป็นเจ้าของการติดตั้งเครื่องมือวัดของคุณ** ใช้มาตรฐานเทเลเมทรีแบบเปิดที่เป็นกลางต่อผู้ให้บริการ เพื่อควบคุมข้อมูลของคุณเองและเปลี่ยน backend ได้

## ข้อแนะนำ

### สร้างบนสามเสาหลักและมากกว่านั้น

**เมตริก (Metrics)** คืออนุกรมเวลาเชิงตัวเลข เก็บถูก และเหมาะกับแดชบอร์ด แนวโน้ม และเกณฑ์การแจ้งเตือน **บันทึก (Logs)** คือบันทึกเหตุการณ์แยกรายการที่มีเวลากำกับ ละเอียดมาก และจำเป็นต่อการสืบสวนเชิงนิติวิทยาศาสตร์ **[Trace](https://en.wikipedia.org/wiki/Tracing_(software))** ติดตามคำขอเดียวขณะเคลื่อนผ่านบริการ แสดงเวลาแฝงและการพึ่งพากันบนกราฟการเรียกแบบกระจาย นอกจากนี้ลองพิจารณา **เหตุการณ์ (events)** (การเปลี่ยนสถานะที่มีความหมาย เช่น การ deploy) **โปรไฟล์ (profiles)** (โค้ดใช้ CPU และหน่วยความจำที่ไหน) และ**[การเฝ้าติดตามผู้ใช้จริง](https://en.wikipedia.org/wiki/Real_user_monitoring)** (real user monitoring) ของประสบการณ์ฝั่งไคลเอนต์จริง เสาหลักเดียวไม่เพียงพอ เป้าหมายคือการเคลื่อนไหวระหว่างกันได้อย่างลื่นไหลระหว่างการสืบสวน

### ใช้ OpenTelemetry และบันทึกแบบมีโครงสร้างเป็นมาตรฐาน

นำ [OpenTelemetry](https://en.wikipedia.org/wiki/OpenTelemetry) มาใช้เป็นมาตรฐานที่เป็นกลางต่อผู้ให้บริการสำหรับสร้างและเก็บเมตริก บันทึก และ trace มันแยกการติดตั้งเครื่องมือวัดออกจาก backend สำหรับวิเคราะห์ ทำให้คุณเปลี่ยนผู้ให้บริการได้โดยไม่ต้องติดตั้งเครื่องมือวัดใหม่ในบริการนับร้อย คุณสมบัตินี้สำคัญอย่างยิ่งสำหรับระบบองค์กรและภาครัฐที่อยู่นาน ปล่อยบันทึกเป็นระเบียนที่มีโครงสร้าง (เช่น JSON) พร้อมชื่อฟิลด์ที่สม่ำเสมอสำหรับเวลา ระดับความรุนแรง บริการ และตัวระบุ ส่งต่อตัวระบุ trace หรือการเชื่อมโยง (correlation ID) จากขอบระบบผ่านทุกการเรียกปลายทาง และใส่ไว้ในทุกบรรทัดบันทึกและ exemplar ของเมตริก เพื่อให้สามเสาหลักเชื่อมถึงกันโดยอัตโนมัติ

### ออกแบบการแจ้งเตือนให้ลงมือทำได้และมีสัญญาณรบกวนต่ำ

ปรัชญาการแจ้งเตือนของคุณเป็นตัวตัดสินว่าการเข้าเวรจะยั่งยืนหรือไม่ แจ้งเตือนเป็นหลักที่อาการที่ผู้ใช้รู้สึก โดยแสดงเป็นอัตราการใช้งบ (burn rate) ของ SLO ([วัตถุประสงค์ระดับบริการ](https://en.wikipedia.org/wiki/Service-level_objective)) เรียกคนเมื่อคุณกำลังใช้งบข้อผิดพลาด (ส่วนที่ยอมให้ขาดจากวัตถุประสงค์นั้น) เร็วพอที่จะละเมิดมัน โดยใช้การแจ้งเตือน burn rate หลายหน้าต่างเวลาเพื่อสมดุลระหว่างการตรวจจับที่เร็วกับการแจ้งเตือนผิด สงวนการเรียกเวรไว้สำหรับปัญหาที่ต้องการการลงมือจากมนุษย์ทันที และส่งที่เหลือไปที่ตั๋วหรือแดชบอร์ด ตัดการแจ้งเตือนที่ดังโดยไม่ต้องลงมือทำออกอย่างไม่ปราณี เพราะความเหนื่อยล้าจากการแจ้งเตือนเป็นสาเหตุหลักของการพลาดเหตุการณ์จริงและความหมดไฟของผู้เข้าเวร ทุกการแจ้งเตือนควรเชื่อมไปยัง runbook

### สร้างแบบจำลองสุขภาพระบบด้วยแดชบอร์ดและการเฝ้าติดตาม SLO

สร้างแดชบอร์ดรอบแบบจำลองสุขภาพที่ชัดเจน ไม่ใช่กำแพงเมตริกทุกตัวที่คุณมี กรอบเริ่มต้นที่ดีคือ "สี่สัญญาณทอง" (four golden signals): เวลาแฝง ปริมาณทราฟฟิก ข้อผิดพลาด และความอิ่มตัว (saturation) สร้างแดชบอร์ดระดับบริการที่แสดงสถานะ SLO และงบข้อผิดพลาดที่เหลือได้ในแวบเดียว บวกแดชบอร์ดระดับสูงกว่าที่สร้างแบบจำลองสุขภาพโดยรวมของระบบและเส้นทางผู้ใช้ คัดสรรอย่างตั้งใจ เพราะแดชบอร์ดที่แสดงทุกอย่างไม่สื่ออะไรเลย วางไว้ใกล้การแจ้งเตือนและ runbook เพื่อให้ผู้ตอบสนองเคลื่อนจากสัญญาณไปสู่บริบทและการลงมือได้อย่างรวดเร็ว

### เปิดทางให้ดีบักใน production ด้วย high cardinality

ปัญหา production ที่ยากที่สุดมักกระทบชิ้นแคบๆ: ลูกค้าหนึ่งราย ภูมิภาคหนึ่ง API เวอร์ชันหนึ่ง อุปกรณ์ประเภทหนึ่ง การสืบสวนต้องใช้เทเลเมทรีที่มี **high cardinality** คือความสามารถในการจัดกลุ่มและกรองด้วยฟิลด์ที่มีค่าไม่ซ้ำกันมาก เช่น ID ผู้ใช้หรือ ID คำขอ เหตุการณ์แบบกว้างที่มีแอตทริบิวต์มากมาย พกหลายมิติต่อระเบียน ช่วยให้คุณถามคำถามอะไรก็ได้ภายหลัง รักษา cardinality และความเที่ยงตรงของการสุ่มตัวอย่างให้พอแยกค่าผิดปกติได้ และเลือก trace ที่เชื่อมกับ exemplar เพื่อให้ยอดพุ่งบนเมตริกนำคุณตรงไปยังคำขอช้าที่เป็นตัวแทน

### จัดการต้นทุน การเก็บรักษา และการสุ่มตัวอย่าง

ปริมาณเทเลเมทรีโตตามระบบและอาจกลายเป็นค่าใช้จ่ายก้อนใหญ่ กำหนดนโยบายการเก็บรักษาตามประเภทข้อมูล: เก็บข้อมูลความละเอียดสูงสั้นๆ และข้อมูลสรุปรวมนานกว่า ใช้การสุ่มตัวอย่าง trace อย่างชาญฉลาด โดยเอนเอียงไปทางเก็บข้อผิดพลาดและคำขอช้า เพื่อเก็บส่วนหางที่น่าสนใจไว้โดยไม่ต้องจ่ายค่าความสำเร็จทั่วไปทุกรายการ ทบทวนค่าใช้จ่ายเทเลเมทรีเป็นประจำ เพราะต้นทุนการสังเกตระบบที่ไม่มีใครควบคุมอาจเทียบเท่ากับโครงสร้างพื้นฐานที่มันสังเกตอยู่

## ข้อดีข้อเสียและการแลกเปลี่ยน

| การตัดสินใจ | ข้อดี | ข้อเสีย |
|---|---|---|
| เหตุการณ์ที่มี high cardinality | ดีบักได้ทรงพลัง ถามได้ทุกอย่าง | ต้นทุนจัดเก็บและสืบค้นสูงขึ้น |
| การสุ่มตัวอย่างแบบเข้มข้น | ต้นทุนต่ำลง สัญญาณรบกวนน้อยลง | อาจพลาดเหตุการณ์ที่เกิดยาก |
| การแจ้งเตือนตามอาการ | เรียกเวรน้อยลงและลงมือทำได้ | ต้องมี SLO ที่ดีจึงจะได้ผล |
| มาตรฐาน OpenTelemetry | เป็นกลางต่อผู้ให้บริการ ย้ายได้ | ต้องใช้ความพยายามย้ายระบบ เครื่องมือยังพัฒนาอยู่ |
| เก็บบันทึกนาน | นิติวิทยาศาสตร์และการตรวจสอบดีขึ้น | ต้นทุนจัดเก็บ เสี่ยงความเป็นส่วนตัว |

การตัดสินใจเรื่องการสังเกตระบบสรุปลงที่ความตึงเครียดระหว่างความเที่ยงตรงกับต้นทุน การเก็บทุกอย่างที่ความละเอียดเต็มให้การมองย้อนหลังที่สมบูรณ์แบบ แต่ในระดับใหญ่แพงเกินไป ตัดแรงเกินไปก็ประหยัดเงิน แต่คุณอาจทิ้งระเบียนเดียวที่จะอธิบายเหตุขัดข้องได้ การสุ่มตัวอย่างและชั้นการเก็บรักษาคือวิธีที่ทีมที่เป็นผู้ใหญ่เดินบนเส้นนี้ โดยเก็บข้อผิดพลาดและค่าผิดปกติไว้ ขณะที่ทำให้ข้อมูลทั่วไปบางลง ข้อแลกเปลี่ยนของการแจ้งเตือนคือความไวกับสัญญาณรบกวน: แจ้งเตือนมากไปทำให้เหนื่อยล้าและพลาดเหตุการณ์ น้อยไปปล่อยให้ปัญหาลุกลาม การแจ้งเตือนตามอาการที่ขับเคลื่อนด้วย SLO แก้ปัญหานี้ได้มาก แต่ต้องมี SLO ที่มีความหมายอยู่ก่อน

## คำถามที่ควรคุยกับทีม

1. **แผนของคุณในการย้ายบริการเดิมมาใช้ OpenTelemetry คืออะไร และจะหลีกเลี่ยงการจ่ายค่าสองชุดเครื่องมือวัดในช่วงเปลี่ยนผ่านได้อย่างไร?** การติดตั้งเครื่องมือวัดที่เป็นกลางต่อผู้ให้บริการคือคุณสมบัติที่ให้คุณเปลี่ยน backend ได้โดยไม่ต้องติดตั้งใหม่ในบริการนับร้อย และสำคัญที่สุดสำหรับระบบองค์กรและภาครัฐที่อยู่นานกว่าสัญญากับผู้ให้บริการรายใดรายหนึ่ง การย้ายคือจุดที่เจตนาดีหยุดชะงัก: ระบบที่ติดตั้งเครื่องมือวัดไม่ครบทิ้งช่องว่างไว้ตรงจุดที่คำขอข้ามจากบริการใหม่ไปบริการเก่า ทำให้ trace แบบครบวงจรขาด นำรายการสำรวจมาคุย: บริการใดปล่อยข้อมูลจากเอเจนต์เฉพาะ บริการใดปล่อย OpenTelemetry และ trace context หลุดที่ขอบเขตตรงไหน ตัดสินลำดับที่ตามเส้นทางคำขอจริงไม่ใช่ผังองค์กร และจัดงบสำหรับช่วงที่คุณรันทั้งสอง collector คำตอบกำหนดว่าคุณเป็นเจ้าของเทเลเมทรีของตัวเองจริงหรือยังผูกติดกับเอเจนต์ของผู้ให้บริการรายเดียว

2. **คุณตรวจสอบความสามารถในการลงมือทำของทุกการแจ้งเตือนครั้งล่าสุดเมื่อไร และเดือนที่แล้วมีการเรียกเวรกี่ครั้งที่ไม่ต้องใช้การลงมือจากมนุษย์?** ความเหนื่อยล้าจากการแจ้งเตือนเป็นสาเหตุหลักของการพลาดเหตุการณ์จริงและความหมดไฟของผู้เข้าเวร ดังนั้นการเรียกเวรที่ไม่ต้องลงมือทำไม่ใช่สัญญาณรบกวนที่ไม่มีพิษภัย แต่กัดกร่อนการตอบสนองที่คุณพึ่งพาอย่างจริงจัง นำหลักฐานมา: ดึงการเรียกเวรของเดือนที่แล้ว ทำเครื่องหมายแต่ละรายการว่าลงมือทำหรือถูกเมิน และนับว่ากี่รายการที่เชื่อมกับ runbook สำหรับทีมใหญ่ที่ครอบคลุมหลายบริการ การแจ้งเตือนที่รบกวนจากทีมหนึ่งทำให้ผู้เข้าเวรร่วมทุกคนชาชิน ตั้งมาตรฐานว่าทุกการเรียกเวรต้องเชื่อมกับ runbook และผูกกับ burn rate ของ SLO แล้วลบส่วนที่เหลือโดยไม่ปราณี ผลของการตรวจสอบนี้ควรลดปริมาณการเรียกเวรโดยตรงและบอกว่าบริการใดไม่มี SLO ที่มีความหมายรองรับการแจ้งเตือน

3. **กลยุทธ์การสุ่มตัวอย่าง trace ของคุณคืออะไร และคุณมั่นใจแค่ไหนว่าเก็บข้อผิดพลาดและส่วนหางที่ช้าไว้?** ปริมาณเทเลเมทรีโตตามระบบ และต้นทุนการสังเกตระบบที่ไม่มีใครควบคุมอาจเทียบเท่าโครงสร้างพื้นฐานที่มันสังเกตอยู่ คุณจึงต้องสุ่มตัวอย่าง และคำถามคือคุณสุ่มอย่างชาญฉลาดหรือไม่ การตัด cardinality หรือสุ่มสุ่มสี่สุ่มห้าจะตัดระเบียนที่จำเป็นต่อการดีบักปัญหาแคบๆ ที่กระทบลูกค้าหนึ่งราย ภูมิภาคหนึ่ง หรือ API เวอร์ชันหนึ่งออกไปพอดี นำชั้นการเก็บรักษาและกฎการสุ่มตัวอย่างปัจจุบันมา: คุณเอนเอียงไปทางเก็บข้อผิดพลาดและคำขอช้าไหม ใช้ trace ที่เชื่อมกับ exemplar เพื่อให้ยอดพุ่งของเมตริกนำไปสู่คำขอช้าที่เป็นตัวแทนหรือเปล่า สำหรับระบบที่ถูกตรวจสอบและผูกกับความเป็นส่วนตัว ต้องประสานการเก็บรักษากับกฎการใช้ข้อมูลเท่าที่จำเป็น เพื่อไม่ให้สะสมข้อมูลส่วนบุคคลไว้เพื่อดีบัก คำตอบกำหนดว่าคุณใช้งบเทเลเมทรีที่ไหน และเหตุขัดข้องรุนแรงครั้งต่อไปจะอธิบายได้หรือเป็นปริศนา

4. **SLO ใดของคุณเป็นข้อผูกพันต่อเส้นทางผู้ใช้จริง และอันไหนเป็นตัวชี้วัดตัวแทนที่ไม่มีใครนอกทีมเจ้าของเชื่อ?** การแจ้งเตือนตามอาการจะได้ผลก็ต่อเมื่ออาการตรงกับสิ่งที่ผู้ใช้รู้สึกจริง การแจ้งเตือนที่ผูกกับเกณฑ์ CPU หรือเป้าหมายความพร้อมใช้งานที่คิดขึ้นมาจะเรียกคนเพราะปัญหาที่อาจไม่สำคัญ แต่เงียบต่อปัญหาที่สำคัญ สำหรับองค์กรใหญ่ SLO ยังเป็นสัญญาที่ให้ทีมอิสระใช้การหมุนเวียนเข้าเวรร่วมกันได้โดยไม่ต้องโต้เถียงเรื่องความรุนแรงใหม่ทุกครั้งที่เกิดเหตุการณ์ นำแคตตาล็อก SLO ปัจจุบัน เส้นทางผู้ใช้ที่แต่ละวัตถุประสงค์มีไว้ปกป้อง และการละเมิดของไตรมาสล่าสุดว่าลูกค้าร้องเรียนจริงหรือไม่ มาคุย ในบริบทองค์กรขนาดใหญ่และภาครัฐ ผูก SLO ที่มองเห็นได้ชัดที่สุดกับข้อผูกพันด้านประสิทธิภาพที่ประกาศไว้ซึ่งบริการต้องรับผิดชอบ เพื่อให้สัญญาณ burn rate เดียวกันที่เรียกวิศวกรเป็นหลักฐานที่คุณแสดงต่อหน่วยกำกับดูแลหรือหน่วยตรวจสอบ การพูดคุยควรเลิกใช้ตัวชี้วัดตัวแทนและเหลือรายการวัตถุประสงค์สั้นๆ ที่คนนอกวิศวกรรมจะรู้จักว่าเป็นคำสัญญาต่อผู้ใช้

5. **ใครเป็นเจ้าของธรรมาภิบาลข้อมูลเทเลเมทรี และคุณพิสูจน์ได้ไหมว่าข้อมูลส่วนบุคคลถูกปกปิดก่อนไปถึง backend การสังเกตระบบ?** เหตุการณ์ที่มี high cardinality และการเก็บบันทึกนานคือคุณสมบัติที่ทำให้ดีบักได้ และเป็นคุณสมบัติเดียวกันที่เปลี่ยนที่เก็บการสังเกตระบบให้เป็นสำเนาข้อมูลส่วนบุคคลของผู้ใช้ที่ไม่มีใครดูแล แรงดึงที่ขัดกันเป็นเรื่องจริง: วิศวกรต้องการแอตทริบิวต์ที่ละเอียดกว่าและเก็บนานกว่า ขณะที่ฝ่ายความเป็นส่วนตัวและกฎหมายต้องการการใช้ข้อมูลเท่าที่จำเป็นและอายุข้อมูลที่สั้น นำแผนผังการไหลของข้อมูลมา แสดงว่าฟิลด์ใดมีข้อมูลส่วนบุคคลหรืออ่อนไหว การปกปิดหรือการแทนด้วยโทเคน (tokenisation) เกิดที่ใดในไปป์ไลน์ และชั้นการเก็บรักษาต่อประเภทข้อมูลเป็นอย่างไร สำหรับระบบที่มีการกำกับดูแลและระบบสาธารณะ ระบุผู้รับผิดชอบ เชื่อมโยงการเก็บรักษากับฐานทางกฎหมายและกฎการใช้ข้อมูลเท่าที่จำเป็นที่คุณต้องปฏิบัติตาม และพร้อมแสดงต่อผู้ตรวจสอบว่าการเข้าถึงตัวเทเลเมทรีเองถูกบันทึกและควบคุม คำตอบตัดสินว่าแพลตฟอร์มการสังเกตระบบของคุณเป็นสินทรัพย์หรือเป็นการละเมิดถาวรที่รอวันถูกค้นพบ

6. **เมื่อเหตุการณ์ข้ามบริการของหลายทีม เทเลเมทรีของคุณให้ผู้ตอบสนองคนเดียวตามคำขอได้ตลอดเส้นทางหรือไม่ หรือเส้นทางขาดทุกขอบเขตความเป็นเจ้าของ?** คำสัญญาทั้งหมดของเทเลเมทรีที่เชื่อมโยงและส่งต่อ ID คือวิศวกรคนเดียวให้เหตุผลเกี่ยวกับระบบที่ไม่มีใครเป็นเจ้าของทั้งหมดได้ และคำสัญญานั้นพังที่ขอบเขตที่ trace context หลุดหรือที่สองทีมใช้ตัวระบุและเครื่องมือที่เข้ากันไม่ได้ ชั่งน้ำหนักแรงดึงไปทางความเป็นอิสระของแต่ละทีมในการเลือกเครื่องมือการสังเกตระบบ เทียบกับต้นทุนร่วมของระบบที่แตกเป็นเสี่ยงซึ่งการส่งต่อทุกครั้งเป็นทางตันระหว่างเหตุขัดข้อง นำไทม์ไลน์เหตุการณ์ข้ามทีมล่าสุดมา ทำเครื่องหมายจุดที่ผู้ตอบสนองหลงทาง พร้อมรายการสำรวจว่าบริการใดส่งต่อ correlation ID ร่วมและบริการใดไม่ส่ง สำหรับองค์กรขนาดใหญ่หรือแพลตฟอร์มภาครัฐที่ประกอบจากหลายผู้ให้บริการและระบบอายุยาว ตัดสินว่าจะบังคับจากส่วนกลางแค่ไหน มาตรฐาน trace context ร่วมและรูปแบบ ID ร่วม เทียบกับที่ปล่อยให้ทีมตัดสินเอง เพราะส่วนประกอบที่คุณจัดซื้อใหม่ตลอดหลายทศวรรษยังต้องทำงานร่วมกันบนคำขอเดียวกัน คำตอบบอกว่าเหตุการณ์ข้ามหลายทีมครั้งหน้าจะเป็นการสืบสวนที่ประสานงานกัน หรือการชี้นิ้วโทษกัน

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ด้วยบริการไม่กี่ตัวและไม่มีคนว่าง ให้ติดตั้ง OpenTelemetry ตั้งแต่วันแรกและส่งบันทึก JSON แบบมีโครงสร้างที่พก ID คำขอเดียวตลอดเส้นทาง การลงทุนเล็กน้อยนี้เปลี่ยน "แอปช้า" ให้เป็น trace ที่อ่านได้ และให้คุณอิสระย้ายจากแพ็กเกจฟรีไปเป็น backend แบบเสียเงินภายหลังโดยไม่ต้องติดตั้งเครื่องมือวัดใหม่ ข้ามแดชบอร์ดที่ซับซ้อนและกลไก SLO ไปก่อนจนกว่าจะมีผู้ใช้ที่คุณวัดประสบการณ์ได้จริง

**ธุรกิจขนาดเล็ก.** คุณไม่มีผู้เชี่ยวชาญด้านการสังเกตระบบและงบจำกัด ดังนั้นพึ่ง backend ที่มีผู้จัดการให้ ซึ่งรวมการติดตั้งเครื่องมือวัด การจัดเก็บ และแดชบอร์ดไว้ แทนการประกอบระบบเอง การตัดสินใจซื้อเทียบกับสร้างเอื้อให้ซื้อเกือบทุกครั้งที่นี่ ความใส่ใจอันมีน้อยของคุณควรใช้กับการแจ้งเตือนสัญญาณทองสองสามตัวที่บอกว่าบริการล่ม ไม่ใช่การรันไปป์ไลน์เทเลเมทรี ตั้งขีดจำกัดการเก็บรักษาที่เด็ดขาดเพื่อไม่ให้ต้นทุนเทเลเมทรีแซงโครงสร้างพื้นฐานที่มันเฝ้าดูอย่างเงียบๆ

**องค์กรขนาดใหญ่.** งานคือธรรมาภิบาลข้ามหลายทีม: มาตรฐาน OpenTelemetry ร่วม รูปแบบ correlation ID ร่วม และแดชบอร์ด SLO ที่คัดสรรแล้ว เพื่อให้ผู้ตอบสนองคนเดียวตามคำขอข้ามบริการนับสิบได้ จัดการเทเลเมทรีเป็นศูนย์ต้นทุนด้วยชั้นการเก็บรักษาและนโยบายการสุ่มตัวอย่าง ทำการแจ้งเตือนให้เป็นมาตรฐานบน burn rate ของ SLO เพื่อให้การเข้าเวรร่วมยั่งยืน และตัดการแจ้งเตือนรบกวนจากส่วนกลาง เพื่อไม่ให้ความเหนื่อยล้าของทีมเดียวทำให้ทุกคนชาชิน มองชั้นการติดตั้งเครื่องมือวัดเป็นโครงสร้างพื้นฐานที่เป็นกลางต่อผู้ให้บริการและอยู่นานกว่าสัญญา backend ใดๆ

**ภาครัฐ.** กฎการจัดซื้อ ความโปร่งใส และความรับผิดชอบต่อสาธารณะหล่อหลอมการออกแบบ ใช้การติดตั้งเครื่องมือวัดแบบเปิดเป็นมาตรฐาน เพื่อให้ระบบที่คาดว่าจะทำงานหลายทศวรรษผ่านการจัดซื้อใหม่ด้วยผู้ให้บริการต่างรายได้โดยไม่ถูกตัวประกันด้วยเอเจนต์เฉพาะ และกำหนดให้การย้ายได้นั้นอยู่ในสัญญา ใช้บันทึกการตรวจสอบแบบมีโครงสร้างเพื่อแสดงว่าใครเข้าถึงระเบียนใดเมื่อไร ปกปิดหรือแทนด้วยโทเคนข้อมูลส่วนบุคคลก่อนถึงที่เก็บเทเลเมทรี และประสานการเก็บรักษากับกฎหมายการใช้ข้อมูลเท่าที่จำเป็น เผยแพร่แดชบอร์ด SLO สำหรับบริการที่ให้บริการประชาชน เพื่อให้สัญญาณเดียวกับที่วิศวกรดูเป็นหลักฐานที่มองเห็นได้ของข้อผูกพันที่คุณต้องรับผิดชอบ

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสี่คนส่งมอบ backend มือถือและได้รับเสียงบ่นคลุมเครือว่า "แอปช้า" ซ้ำๆ ที่ทำซ้ำไม่ได้ ทีมเพิ่ม OpenTelemetry ให้บริการไม่กี่ตัวและเปลี่ยนเป็นบันทึก JSON แบบมีโครงสร้างพร้อม ID คำขอที่พกจากแอปผ่านทุกช่วง รายงานช้าครั้งถัดไปแก้ได้ในไม่กี่นาที: trace เดียวแสดงว่าตารางคำสั่งซื้อขาดดัชนีฐานข้อมูลใต้คิวรีเฉพาะ เพราะเลือกการติดตั้งเครื่องมือวัดแบบเปิดตั้งแต่เนิ่นๆ ภายหลังทีมจึงย้ายจากแพ็กเกจฟรีไปเป็น backend แบบเสียเงินได้โดยไม่ต้องติดตั้งเครื่องมือวัดใหม่เลย

**องค์กรขนาดใหญ่.** แพลตฟอร์มอีคอมเมิร์ซขนาดใหญ่ติดตั้ง OpenTelemetry ให้ทุกบริการ โดยส่งต่อ trace ID จากเบราว์เซอร์ของลูกค้าผ่านการชำระเงิน การจ่ายเงิน สินค้าคงคลัง และการจัดส่ง เมื่ออัตราการซื้อลดลง วิศวกรเข้าเวรเริ่มจากการแจ้งเตือน burn rate ของ SLO เปิดสัญญาณทองบนแดชบอร์ดการชำระเงิน เห็นเวลาแฝงสูงในภูมิภาคเดียว และตาม exemplar trace ไปถึงการเรียกฐานข้อมูลช้าในบริการเดียว แอตทริบิวต์ high cardinality แสดงว่าปัญหาจำกัดอยู่ที่หมวดสินค้าเดียว ซึ่งนำไปสู่การแก้ไขที่ตรงจุดในไม่กี่นาทีแทนที่จะเป็นชั่วโมง

**ภาครัฐ.** หน่วยบริการสุขภาพแห่งชาติรันแพลตฟอร์มเวชระเบียนผู้ป่วยภายใต้กฎการตรวจสอบและความเป็นส่วนตัวที่เข้มงวด บันทึกแบบมีโครงสร้างเก็บว่าใครเข้าถึงระเบียนใดเมื่อไร ป้อนทั้งการเฝ้าติดตามความมั่นคงปลอดภัยและการรายงานการปฏิบัติตามกฎระเบียบ ขณะที่ฟิลด์ที่ระบุตัวบุคคลได้ถูกปกปิดหรือแทนด้วยโทเคนในเทเลเมทรี แดชบอร์ด SLO สาธารณะแสดงความพร้อมใช้งานและเวลาแฝงของการจองนัดหมายสำหรับประชาชน ด้วยการใช้การติดตั้งเครื่องมือวัดแบบเปิดเป็นมาตรฐาน หน่วยงานหลีกเลี่ยงการผูกติดกับผู้ให้บริการเฉพาะรายตลอดระบบที่คาดว่าจะทำงานหลายทศวรรษและถูกจัดซื้อใหม่โดยผู้ให้บริการต่างรายตลอดอายุ

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ผลตอบแทนหลักของความสามารถในการสังเกตระบบคือเวลาตรวจจับและแก้ไขเหตุการณ์ที่ลดลงอย่างมาก สำหรับบริการที่ระบบล่มมีต้นทุนสูง การลดเวลาเฉลี่ยในการแก้ไขจากชั่วโมงเหลือนาทีคุ้มค่าเครื่องมือหลายเท่าในเหตุการณ์ใหญ่ครั้งเดียว การสังเกตระบบยังประหยัดเวลาวิศวกรรมที่ไม่ต้องใช้ไปกับการเดา การทำซ้ำบั๊ก และการเถียงกันว่าทีมใดผิด และช่วยย่นวงจรป้อนกลับที่ทำให้ทีมส่งมอบอย่างมั่นใจ คุณค่าด้านความมั่นคงปลอดภัยและการปฏิบัติตามกฎระเบียบก็เป็นจริงเช่นกัน: เทเลเมทรีเดียวกันรองรับการตรวจจับการบุกรุกและหลักฐานการตรวจสอบ

ต้นทุนรวมตลอดอายุการใช้งาน (TCO) รวมความพยายามติดตั้งเครื่องมือวัด ต้นทุนจัดเก็บและสืบค้นเทเลเมทรี และวินัยในการคัดสัญญาณออกจากสัญญาณรบกวน ต้นทุนเหล่านี้มองเห็นได้และเกิดซ้ำ ซึ่งล่อให้ผู้บริหารลงทุนน้อยเกินไป ต้นทุนของการไม่นำมาใช้ใหญ่กว่าแต่เห็นยากกว่า: ระบบล่มที่ยืดเยื้อ ปัญหาประสิทธิภาพที่วินิจฉัยไม่ได้ เหตุการณ์ความมั่นคงปลอดภัยที่พบช้าหรือไม่พบเลย และวิศวกรที่หมดไฟกับการแจ้งเตือนที่ทำอะไรไม่ได้ ใช้ข้อมูลเหตุการณ์จริงโน้มน้าว แสดงเวลาแก้ไขและผลกระทบทางธุรกิจของเหตุขัดข้องล่าสุด และประมาณการการลดลงที่เทเลเมทรีที่ดีขึ้นจะให้ การวางกรอบการสังเกตระบบเป็นประกันที่ช่วยเร่งการส่งมอบด้วย แทนที่จะเป็นศูนย์ต้นทุนล้วนๆ จะชนะการโต้แย้ง

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **แจ้งเตือนทุกอย่าง** การเรียกเวรทุกความผิดปกติฝึกให้ผู้ตอบสนองเมินการแจ้งเตือน เหตุการณ์จริงจึงหลุดรอดไป
- **เรียกเวรตามสาเหตุ** การแจ้งเตือนที่สาเหตุภายในแทนอาการของผู้ใช้ท่วมการเข้าเวรด้วยสัญญาณรบกวนและพลาดความล้มเหลวแปลกใหม่
- **บันทึกไม่มีโครงสร้าง** บันทึกข้อความอิสระที่สืบค้นหรือเชื่อมโยงไม่ได้บังคับให้ต้อง grep ด้วยมืออย่างช้าๆ ระหว่างเหตุการณ์
- **สามเสาหลักแยกไซโล** เมตริก บันทึก และ trace ในเครื่องมือที่ไม่เชื่อมกันและไม่มีตัวระบุร่วมทำให้ตามเหตุการณ์ตลอดเส้นทางไม่ได้
- **แดชบอร์ดบานปลาย** แดชบอร์ดนับร้อยที่ไม่ได้คัดสรรหมายความว่าไม่มีใครรู้ว่าอันไหนแสดงว่าระบบสุขภาพดี
- **cardinality ยุบ** การตัดฟิลด์ high cardinality เพื่อประหยัดต้นทุนเอาข้อมูลที่จำเป็นต่อการดีบักปัญหาแคบๆ ออกไปพอดี
- **ผูกติดผู้ให้บริการ** เอเจนต์เฉพาะทุกที่ทำให้การเปลี่ยน backend แพงเกินไปและจับข้อมูลของคุณเป็นตัวประกัน

## แบบจำลองความเป็นผู้ใหญ่

**ระดับ 1 เริ่มต้น** การสังเกตระบบเป็นแบบเฉพาะกิจและตั้งรับ การตรวจสอบเวลาทำงานพื้นฐานและบันทึกไม่มีโครงสร้างอยู่บนแต่ละเครื่อง การดีบักหมายถึงล็อกอินเข้าเซิร์ฟเวอร์เพื่อ grep และไม่มีเทเลเมทรีร่วม การแจ้งเตือนมีสัญญาณรบกวน ตามสาเหตุ และมักถูกเมิน เหตุการณ์จริงจึงโผล่ผ่านเสียงบ่นของผู้ใช้แทนที่จะเป็นสัญญาณ

**ระดับ 2 พัฒนา** แนวปฏิบัติพื้นฐานเริ่มปรากฏแต่ต่างกันไปตามทีม บางบริการส่งเมตริกและบันทึกไปที่ศูนย์กลาง มีแดชบอร์ดไม่กี่ตัวและการแจ้งเตือนตามเกณฑ์ แต่บันทึกมีโครงสร้างเพียงบางส่วนและ trace ไม่มีหรือไม่ครบ การเชื่อมโยงข้ามบริการเป็นแบบทำมือ และการที่วิศวกรตามคำขอได้ตลอดเส้นทางหรือไม่ขึ้นอยู่กับว่าทีมใดเกี่ยวข้อง

**ระดับ 3 สร้างมาตรฐาน** การติดตั้งเครื่องมือวัดถูกจัดทำเป็นเอกสารและบังคับใช้ทั้งองค์กร OpenTelemetry ข้ามบริการพร้อม trace หรือ correlation ID ที่ส่งต่อ บันทึกแบบมีโครงสร้างพร้อมชื่อฟิลด์สม่ำเสมอ การติดตามแบบกระจาย แดชบอร์ดสัญญาณทองที่คัดสรร และการแจ้งเตือนตามอาการบนพื้นฐาน SLO คือมาตรฐานที่ทุกทีมปฏิบัติตาม ทุกการเรียกเวรเชื่อมกับ runbook และผูกกับ SLO และการเข้าเวรยั่งยืนแทนที่จะเป็นต้นเหตุของความหมดไฟ

**ระดับ 4 บริหารจัดการ** ระบบการสังเกตระบบเองถูกวัดและควบคุมเทียบกับเส้นฐาน คุณติดตามความครอบคลุมการติดตั้งเครื่องมือวัดและอัตราการส่งต่อ trace context ข้ามบริการ สัดส่วนการเรียกเวรที่ลงมือทำเทียบกับที่ถูกเมิน เวลาเฉลี่ยในการตรวจจับและแก้ไข การบรรลุ SLO และการใช้งบข้อผิดพลาด และต้นทุนเทเลเมทรีต่อบริการเทียบกับงบประมาณ ช่องว่างและสัญญาณรบกวนของการแจ้งเตือนถูกลดด้วยข้อมูลไปสู่เป้าหมายที่ชัดเจน ความเที่ยงตรงของการสุ่มตัวอย่างถูกตรวจสอบเพื่อให้ระเบียนข้อผิดพลาดและส่วนหางที่ช้ารอด และการตัดสินใจ go หรือ no-go เรื่องความครอบคลุมและการเก็บรักษาทำบนหลักฐานแทนความเห็น

**ระดับ 5 ประสานทั้งระบบ** การสังเกตระบบถูกปรับปรุงอย่างต่อเนื่องและผนวกทั่วทั้งองค์กร เทเลเมทรีที่มี high cardinality และเต็มไปด้วยเหตุการณ์ช่วยให้สืบสวนเฉพาะกิจได้กับทุกชิ้นส่วน การแจ้งเตือนขับเคลื่อนด้วย burn rate ของ SLO พร้อมสัญญาณรบกวนน้อยที่สุด และการสุ่มตัวอย่างกับการเก็บรักษาปรับตามต้นทุนและความเสี่ยงที่เปลี่ยนไป เทเลเมทรีป้อนการวางแผนความจุ การตรวจจับความมั่นคงปลอดภัย และการตัดสินใจด้านผลิตภัณฑ์เป็นกิจวัตร และแพลตฟอร์มปรับสัญญาณ งบประมาณ และความครอบคลุมของตัวเองใหม่เมื่อระบบ ภาพภัยคุกคาม และภาระผูกพันตามกฎระเบียบเปลี่ยนไป

## ประเด็นชวนคุย

- จุดสมดุลที่เหมาะระหว่างความเที่ยงตรงของเทเลเมทรีกับต้นทุนสำหรับบริการสำคัญที่สุดของคุณอยู่ตรงไหน
- คุณตัดสินอย่างไรว่าอะไรสมควรเรียกเวร อะไรเป็นตั๋ว และอะไรเป็นเพียงรายการบนแดชบอร์ด
- กลยุทธ์ของคุณในการส่งต่อ correlation ID ข้ามทีมที่ไม่ได้ใช้โค้ดเบสหรือรอบการปล่อยร่วมกันคืออะไร
- คุณรักษาพลังการดีบักแบบ high cardinality ไว้อย่างไรขณะที่ปฏิบัติตามข้อกำหนดด้านความเป็นส่วนตัวและการใช้ข้อมูลเท่าที่จำเป็น
- เครื่องมือการสังเกตระบบควรถูกบังคับจากส่วนกลางหรือเลือกรายทีม และผลที่ตามมาของแต่ละทางเป็นอย่างไร
- คุณจะแสดงต่อผู้ตรวจสอบอย่างไรว่าเทเลเมทรีของคุณครบถ้วนและมีร่องรอยหากถูกแก้ไข (tamper-evident)

## ข้อสรุปสำคัญ

- การเฝ้าติดตามตรวจจับปัญหาที่รู้แล้ว ส่วนความสามารถในการสังเกตระบบให้คุณสืบสวนปัญหาที่ไม่รู้โดยไม่ต้องส่งโค้ดใหม่
- เมตริก บันทึก และ trace มีคุณค่ามากที่สุดเมื่อเชื่อมโยงกันผ่านตัวระบุร่วม ไม่ใช่แยกเป็นไซโล
- ใช้ OpenTelemetry และบันทึกแบบมีโครงสร้างเป็นมาตรฐาน เพื่อให้เป็นกลางต่อผู้ให้บริการและย้ายได้ตลอดอายุระบบที่ยาวนาน
- แจ้งเตือนที่อาการที่ผู้ใช้เห็นได้ผ่าน burn rate ของ SLO ทำให้ทุกการเรียกเวรลงมือทำได้ และตัดสัญญาณรบกวนอย่างไม่หยุดหย่อน
- คัดสรรแดชบอร์ดรอบแบบจำลองสุขภาพที่ชัดเจน เช่น สัญญาณทอง แทนที่จะแสดงทุกเมตริก
- เทเลเมทรีที่มี high cardinality และเต็มไปด้วยเหตุการณ์คือสิ่งที่ทำให้ดีบักปัญหา production ที่แคบๆ ได้
