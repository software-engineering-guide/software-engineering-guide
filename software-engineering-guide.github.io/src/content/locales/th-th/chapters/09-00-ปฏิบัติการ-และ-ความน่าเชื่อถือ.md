# 9.0 บทนำส่วนที่ 9: ปฏิบัติการ และ ความน่าเชื่อถือ

การสร้างซอฟต์แวร์เป็นเพียงครึ่งเดียวของงาน อีกครึ่งคือการดูแลให้ซอฟต์แวร์ทำงานได้ดีต่อเนื่อง และสำหรับองค์กรส่วนใหญ่ ครึ่งหลังนี้ไม่มีวันจบ ส่วนนี้ว่าด้วยการดำเนินงานระบบจริงใน production คุณจะได้นิยามว่า "น่าเชื่อถือพอ" หมายถึงอะไร แล้วออกแบบวิศวกรรมให้ไปถึงระดับนั้น คุณจะได้เรียนรู้การมองเห็นภายในระบบที่ซับซ้อนให้ชัดพอจะแก้ปัญหาที่ไม่คาดคิดได้ การรับมือเมื่อเกิดเหตุขัดข้องอย่างเป็นระบบ และการทำทั้งหมดนี้โดยไม่สิ้นเปลืองเงินหรือปล่อยคาร์บอนโดยเปล่าประโยชน์ นี่คือวินัยที่เปลี่ยนระบบที่ใช้งานได้แค่ตอนสาธิตให้เป็นบริการที่ผู้คนพึ่งพาได้เป็นปีๆ

สำหรับทีมขนาดใหญ่ เรื่องเหล่านี้ไม่ใช่งานเบื้องหลังอีกต่อไป แต่กลายเป็นระบบหนึ่งในตัวมันเอง แพลตฟอร์มสมัยใหม่ครอบคลุมบริการนับร้อย หลายทีม หลายภูมิภาค และการพึ่งพาบุคคลที่สาม ไม่มีใครเก็บภาพทั้งหมดไว้ในหัวได้ เมื่อขนาดใหญ่ขึ้น ทั้งคุณค่าของความน่าเชื่อถือและราคาของความผิดพลาดก็สูงขึ้นตาม ระบบล่มหนึ่งชั่วโมงกลายเป็นรายได้ที่หายไปและความไว้วางใจที่สึกกร่อน การแจ้งเตือนที่คลุมเครือเพียงข้อเดียวกลายเป็นการเรียกเวรนับพันครั้ง ค่าใช้จ่ายคลาวด์ที่รั่วไหลเพียงไม่กี่เปอร์เซ็นต์กลายเป็นเงินหลายล้านดอลลาร์ การปฏิบัติการในระดับนี้ต้องมีภาษากลาง [เทเลเมทรี](https://en.wikipedia.org/wiki/Telemetry) (telemetry) กลาง และโครงสร้างกลาง เพื่อให้คนจำนวนมากลงมือร่วมกันอย่างสอดคล้องบนระบบที่ไม่มีใครเป็นเจ้าของทั้งหมด

บริบทองค์กรขนาดใหญ่และภาครัฐยกระดับทุกอย่างให้เดิมพันสูงขึ้น อุตสาหกรรมที่มีการกำกับดูแลมีข้อผูกมัดด้านความพร้อมใช้งานตามกฎหมาย ข้อกำหนดการตรวจสอบ และการรายงานเหตุขัดข้องภาคบังคับ บริการที่ให้บริการประชาชนต้องพิสูจน์ได้ว่าเป็นไปตามเป้าหมายประสิทธิภาพที่ประกาศไว้ และจะหยุดให้บริการเฉยๆ ไม่ได้ งบประมาณภาครัฐใช้เงินภาษีภายใต้ข้อบังคับด้านความยั่งยืนและการลดคาร์บอนสุทธิเป็นศูนย์ที่เข้มข้นขึ้น ในบริบทเหล่านี้ ปฏิบัติการ ความน่าเชื่อถือ และ[ความสามารถในการสังเกตระบบ](https://en.wikipedia.org/wiki/Observability_(software)) (observability: การเข้าใจสถานะภายในของระบบจากผลลัพธ์ภายนอก) ไม่ใช่แค่สุขอนามัยในการปฏิบัติงาน แต่เป็นเครื่องมือของความรับผิดชอบต่อสังคม ความมั่นคงปลอดภัย และความไว้วางใจต่อสถาบัน

## บทในส่วนนี้

- **9.1 วิศวกรรมความน่าเชื่อถือของไซต์:** การนำวิศวกรรมซอฟต์แวร์มาใช้กับงานปฏิบัติการ โดยนิยามความน่าเชื่อถือด้วย SLI ([ตัวชี้วัดระดับบริการ](https://en.wikipedia.org/wiki/Service-level_indicator)), SLO ([วัตถุประสงค์ระดับบริการ](https://en.wikipedia.org/wiki/Service-level_objective)) และ SLA ([ข้อตกลงระดับบริการ](https://en.wikipedia.org/wiki/Service-level_agreement)) ใช้งบข้อผิดพลาด (error budget: ส่วนที่ยอมให้ขาดจากความน่าเชื่อถือสมบูรณ์แบบ) เพื่อสมดุลระหว่างความเร็วกับความเสถียร ลดงานซ้ำซากหรือ toil (งานปฏิบัติการด้วยมือที่ทำซ้ำและทำให้อัตโนมัติได้) อย่างไม่หยุดหย่อนด้วยระบบอัตโนมัติ และพยากรณ์ความจุเพื่อไม่ให้การเติบโตมาเซอร์ไพรส์คุณ
- **9.2 การสังเกตได้ และเทเลเมทรี:** ก้าวข้ามการเฝ้าติดตามความล้มเหลวที่รู้จักไปสู่ความสามารถในการสังเกตระบบอย่างแท้จริง ซึ่งสร้างบนเทเลเมทรีที่ระบบปล่อยออกมา (เมตริก บันทึก trace และเหตุการณ์ที่เชื่อมโยงกันด้วยตัวระบุร่วม) ใช้มาตรฐาน [OpenTelemetry](https://en.wikipedia.org/wiki/OpenTelemetry) ที่เป็นกลางต่อผู้ให้บริการ (มาตรฐานเปิดสำหรับสร้างและเก็บเทเลเมทรี) และออกแบบการแจ้งเตือนให้เรียกคนก็ต่อเมื่อเป็นปัญหาที่ลงมือแก้ได้และผู้ใช้เห็นผลจริงเท่านั้น
- **9.3 การจัดการเหตุการณ์:** การตรวจจับ ประสานงาน แก้ไข และเรียนรู้จากเหตุขัดข้อง ผ่านการหมุนเวียนเข้าเวรที่ยั่งยืน โครงสร้างการบัญชาการเหตุการณ์ที่ชัดเจน (ลำดับขั้นที่กำหนดไว้เพื่อประสานการตอบสนอง) พร้อมบทบาทและระดับความรุนแรงที่กำหนดไว้ การสื่อสารกับผู้มีส่วนได้ส่วนเสียอย่างตรงไปตรงมา และ[การทบทวนหลังเหตุการณ์](https://en.wikipedia.org/wiki/Postmortem_documentation)แบบไม่กล่าวโทษ (การทบทวนเหตุการณ์ที่มุ่งหาสาเหตุเชิงระบบ ไม่ใช่โทษรายบุคคล) ที่ผลักดันให้การแก้ไขเชิงป้องกันเสร็จสมบูรณ์
- **9.4 ต้นทุน ความยั่งยืน และซอฟต์แวร์สีเขียว:** นำความรับผิดชอบทางการเงินและสิ่งแวดล้อมมาสู่ production ผ่านการมองเห็นและปรับแต่ง FinOps (การปฏิบัติการทางการเงินสำหรับค่าใช้จ่ายคลาวด์) การออกแบบที่คำนึงถึงคาร์บอน (จัดเวลาและสถานที่ทำงานให้ตรงกับช่วงที่ไฟฟ้าสะอาดกว่า) และประหยัดพลังงาน การปรับขนาดทรัพยากรให้พอดีอย่างต่อเนื่อง และการแลกเปลี่ยนอย่างตั้งใจระหว่างต้นทุน ประสิทธิภาพ และความน่าเชื่อถือ

- **9.5 การกู้คืนจากภัยพิบัติและความต่อเนื่องทางธุรกิจ:** เตรียมพร้อมรอดผ่านวันที่เลวร้ายด้วยการกำหนดเป้าหมายเวลากู้คืน (RTO) และจุดกู้คืนข้อมูล (RPO) จากการวิเคราะห์ผลกระทบทางธุรกิจ เก็บสำรองข้อมูลที่ทดสอบแล้วและแก้ไขไม่ได้ เลือกกลยุทธ์การกู้คืนบนสเปกตรัมของต้นทุนกับความเร็ว และซ้อมการสลับระบบสำรอง เพื่อให้การกู้คืนเป็นสิ่งที่พิสูจน์แล้ว ไม่ใช่สิ่งที่ได้แต่หวัง

- **9.6 วิศวกรรมความโกลาหลและการทดสอบความทนทาน:** สร้างความมั่นใจว่าระบบทนต่อสภาวะปั่นป่วนได้ ด้วยการกำหนดสถานะปกติ ตั้งสมมติฐาน และฉีดความผิดพลาดที่สมจริงโดยควบคุมขอบเขตผลกระทบ แล้วพัฒนาจากวันซ้อมเหตุการณ์ (game day) ไปสู่การตรวจสอบความทนทานแบบอัตโนมัติอย่างต่อเนื่อง
- **9.7 การวางแผนความจุและการพยากรณ์ความต้องการ:** จัดสรรทรัพยากรคำนวณ พื้นที่เก็บข้อมูล และเครือข่ายให้ตรงกับความต้องการที่พยากรณ์ไว้ โดยเผื่อพื้นที่ว่างอย่างตั้งใจ ใช้การทดสอบโหลดและการให้เหตุผลตามทฤษฎีแถวคอย (queueing theory) เพื่อไม่ให้เวลาแฝงพุ่งสูงเมื่อใกล้เต็มขีดจำกัด และสมดุลต้นทุนกับความน่าเชื่อถือ
- **9.8 การเข้าเวรและความพร้อมปฏิบัติการ:** ออกแบบการเข้าเวรให้มนุษยธรรมและยั่งยืน ด้วยการแจ้งเตือนที่ลงมือทำได้ การยกระดับที่ชัดเจน การทบทวนความพร้อมก่อนขึ้น production และคู่มือปฏิบัติการ (runbook) เพื่อให้คนที่ดูแลบริการได้รับการเตรียมพร้อมให้ประสบความสำเร็จ ไม่ใช่หมดไฟ

## บทเหล่านี้เกี่ยวข้องกันอย่างไร

สี่บทนี้ประกอบกันเป็นวงจรปฏิบัติการที่แน่นหนา [วิศวกรรมความน่าเชื่อถือของไซต์](https://en.wikipedia.org/wiki/Site_reliability_engineering) (บทที่ 9.1) กำหนดเป้าหมาย: SLI และ SLO นิยามว่าความน่าเชื่อถือคืออะไร และงบข้อผิดพลาดตัดสินว่าเมื่อไรควรชะลอ ความสามารถในการสังเกตระบบ (บทที่ 9.2) คือวิธีวัดและปกป้องเป้าหมายเหล่านั้น เพราะการแจ้งเตือนตามอัตราการใช้งบ SLO (burn-rate) ทำงานได้ก็ต่อเมื่อเทเลเมทรีมีโครงสร้างดี และยังเป็นวิธีที่ผู้ตอบสนองใช้หา "เหตุผล" เบื้องหลังความล้มเหลวด้วย [การจัดการเหตุการณ์](https://en.wikipedia.org/wiki/Incident_management) (บทที่ 9.3) คือสิ่งที่เกิดขึ้นเมื่อคุณใช้งบข้อผิดพลาดเร็วกว่าที่วางแผน: การแจ้งเตือนจากบทที่ 9.2 ดังขึ้น โครงสร้างการบัญชาการเริ่มทำงาน และการทบทวนหลังเหตุการณ์แบบไม่กล่าวโทษที่ตามมาจะป้อนการปรับปรุงที่ยั่งยืนกลับเข้าสู่งานความน่าเชื่อถือและงานติดตั้งเครื่องมือวัด ต้นทุนและความยั่งยืน (บทที่ 9.4) ปิดวงจร โดยยืนยันให้คุณจัดสรรความน่าเชื่อถือและประสิทธิภาพให้ตรงกับ SLO ที่กำหนดในบทที่ 9.1 แทนที่จะเกินความจำเป็นทุกที่ เพื่อให้สามเหลี่ยมของต้นทุน ประสิทธิภาพ และความน่าเชื่อถือสมดุลอย่างตั้งใจ ไม่ใช่เพราะความกลัว

ความเชื่อมโยงขยายไปไกลกว่าส่วนนี้ ความเป็นเจ้าของความน่าเชื่อถือในส่วนนี้ถูกกำหนดโดยโครงสร้างทีมในบทที่ 1.2 และส่งมอบผ่านไปป์ไลน์และวิศวกรรมแพลตฟอร์มในบทที่ 8.1 และ 8.4 เพราะการ deploy ที่ปลอดภัยและบ่อยครั้งเป็นเงื่อนไขเบื้องต้นของการดำเนินงานในระดับใหญ่ วัฒนธรรมไม่กล่าวโทษที่เน้นการเรียนรู้ ซึ่งทำให้การตอบสนองเหตุการณ์เป็นไปอย่างตรงไปตรงมา เริ่มต้นในบทที่ 1.1 และรูปแบบความน่าเชื่อถือและความทนทานที่อยู่เบื้องหลังแนวปฏิบัติเหล่านี้มีรากฐานจากสถาปัตยกรรมในบทที่ 3.3 และ 3.5 สุดท้าย หลักฐานที่วินัยเหล่านี้สร้างขึ้น ตั้งแต่เทเลเมทรีที่พร้อมรับการตรวจสอบ ไปจนถึงการทบทวนหลังเหตุการณ์และการระบุต้นทุนตามเจ้าของ ป้อนตรงเข้าสู่งานบริหารความเสี่ยง การรับรอง และธรรมาภิบาลของบทที่ 10.2 และ 11.3 เมื่อดำเนินงานได้ดี ระบบในส่วนนี้คือสิ่งที่ช่วยให้องค์กรรักษาสัญญาได้นานหลังจากที่เขียนโค้ดเสร็จไปแล้ว
