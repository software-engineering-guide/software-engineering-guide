# 1.0 บทนำส่วนที่ 1: ผู้คน

ซอฟต์แวร์สร้างขึ้นโดยผู้คน และผู้คนถูกจัดระเบียบด้วยวัฒนธรรม โครงสร้าง และกระบวนการ ก่อนจะพูดถึงโค้ด [สถาปัตยกรรม](https://en.wikipedia.org/wiki/Software_architecture) หรือเครื่องมือ ส่วนนี้จึงมองไปที่ระบบของมนุษย์ที่ผลิตทุกอย่างเหล่านั้นขึ้นมา ได้แก่ คุณค่าร่วมที่ทีมยึดถือ วิธีแบ่งตัวเป็นทีมย่อย วิธีเติบโตในสายอาชีพ วิธีประสานงานในแต่ละวัน และวิธีตัดสินใจรวมถึงจดจำการตัดสินใจนั้น ทุกอย่างที่เหลือในหนังสือเล่มนี้ตั้งอยู่บนรากฐานเหล่านี้ สถาปัตยกรรมที่ยอดเยี่ยมซึ่งสร้างโดยองค์กรที่หวาดกลัว แตกเป็นเสี่ยง หรือขี้ลืม จะไม่รอดเมื่อเจอความเป็นจริง

สำหรับทีมขนาดใหญ่ รากฐานเหล่านี้ไม่ได้เกิดขึ้นเองตามสัญชาตญาณอีกต่อไป แต่กลายเป็นเรื่องของโครงสร้าง แนวปฏิบัติที่ซึมซับกันเองได้ในทีมแปดคนที่นั่งห้องเดียวกัน จะล่มสลายเมื่อต้องใช้กับแปดร้อยคนที่กระจายอยู่ทั่วโลก ดังนั้นคุณต้องทำให้วัฒนธรรมชัดเจน ออกแบบเส้นแบ่งระหว่างทีมอย่างมีจุดประสงค์ เขียนความคาดหวังด้านการเติบโตลงเป็นลายลักษณ์อักษร ย้ายการประสานงานจากการคุยกันตามทางเดินไปสู่เอกสารที่คงอยู่ได้นาน และบันทึกการตัดสินใจเพื่อให้เหตุผลยังอยู่ต่อไปแม้คนที่ตัดสินใจจะไม่อยู่แล้ว

องค์กรขนาดใหญ่และภาครัฐรู้สึกถึงแรงกดดันเหล่านี้ครบทุกด้าน พวกเขาทำงานในระดับขนาดใหญ่ ภายใต้การตรวจสอบและกำกับดูแล ในช่วงเวลายาวนาน และมีทั้งพนักงานประจำ ผู้รับจ้าง และผู้ขาย ระบบที่คุณสร้างวันนี้อาจใช้งานไปอีกสิบปี โดยมีคนดูแลที่ไม่เคยรู้จักคุณ ในบริบทแบบนี้ รากฐานในส่วนนี้ไม่ใช่ทักษะอ่อน (soft skills) หรือของที่มีก็ดี แต่เป็นกลไกของ[ความทรงจำขององค์กร](https://en.wikipedia.org/wiki/Institutional_memory) ความรับผิดชอบต่อผลงาน และ[การบริหารความเสี่ยง](https://en.wikipedia.org/wiki/Risk_management)

## บทในส่วนนี้

- **1.1 คุณค่าวิศวกรรมซอฟต์แวร์:** ความเชื่อร่วมและพฤติกรรมในชีวิตประจำวันที่เป็นตัวกำหนดว่าซอฟต์แวร์ถูกสร้างขึ้นมาอย่างไรจริงๆ โดยมี[ความปลอดภัยทางจิตใจ](https://en.wikipedia.org/wiki/Psychological_safety) การเรียนรู้แบบไม่กล่าวโทษ ความเป็นเจ้าของที่ชัดเจน วัฒนธรรมการเขียน และจังหวะการทำงานที่ยั่งยืนเป็นแกนกลาง
- **1.2 โครงสร้างทีมและการออกแบบองค์กร:** การแบ่งคนเป็นทีมมีผลต่อซอฟต์แวร์ที่สร้างได้อย่างไร ([กฎของคอนเวย์](https://en.wikipedia.org/wiki/Conway%27s_law): องค์กรผลิตระบบที่สะท้อนโครงสร้างการสื่อสารของตัวเอง) โดยใช้ทีมแบบ stream-aligned, platform, enabling และ complicated-subsystem เพื่อลด[ภาระทางปัญญา](https://en.wikipedia.org/wiki/Cognitive_load)และลดการพึ่งพากันระหว่างทีม
- **1.3 บทบาท บันไดอาชีพ และการเติบโต:** การสร้างกรอบอาชีพที่ชัดเจนและผ่านการปรับเทียบ โดยมีสายผู้ปฏิบัติงานเฉพาะด้าน (individual contributor) และสายผู้บริหารขนานกันไป เพื่อให้การกำหนดระดับ การเลื่อนตำแหน่ง การจ้างงาน และค่าตอบแทนเป็นธรรม สม่ำเสมอ และอธิบายได้เมื่อองค์กรมีขนาดใหญ่
- **1.4 วิธีการทำงาน:** ทีมประสานงาน วางแผน และส่งมอบงานในแต่ละวันอย่างไร โดยให้น้ำหนักกับหลักการมากกว่าพิธีกรรม และใช้แนวปฏิบัติแบบไม่ต้องพร้อมกัน (asynchronous) เอกสารมาก่อน และมุ่งผลลัพธ์เป็นค่าเริ่มต้น ซึ่งขยายได้ข้ามเขตเวลาและกำลังคนหลายรูปแบบ
- **1.5 การตัดสินใจและธรรมาภิบาล:** การสร้างสมดุลระหว่างความเป็นอิสระของทีมกับความสอดคล้องขององค์กร ผ่าน paved road การทบทวนที่มีขนาดเหมาะสม การคิดแบบแยกการตัดสินใจที่ย้อนกลับได้กับย้อนกลับไม่ได้ และการบริหาร[หนี้ทางเทคนิค](https://en.wikipedia.org/wiki/Technical_debt)เป็นพอร์ตโฟลิโอ
- **1.6 บันทึกการตัดสินใจ:** วิธีเขียน จัดเก็บ และรักษาบันทึกการตัดสินใจ โดยรูปแบบที่พบบ่อยที่สุดคือ[บันทึกการตัดสินใจด้านสถาปัตยกรรม](https://en.wikipedia.org/wiki/Architectural_decision) (ADR) เพื่อให้เหตุผลเบื้องหลังการเลือกยังอยู่รอดแม้พนักงานหมุนเวียนและผ่านการตรวจสอบได้ รวมถึงวิธีทำให้การตัดสินใจค้นหาเจอได้และทดสอบได้
- **1.7 มาตรฐานวิศวกรรมและข้อยกเว้น:** องค์กรเขียน เผยแพร่ บังคับใช้ และพัฒนามาตรฐานวิศวกรรมอย่างไร และจัดการกับการเบี่ยงเบนผ่านกระบวนการข้อยกเว้น (waiver) ที่มีธรรมาภิบาลและบันทึกไว้อย่างไร เพื่อให้มาตรฐานน่าเชื่อถือโดยไม่แข็งทื่อ

- **1.8 การจ้างงาน การสัมภาษณ์ และการปฐมนิเทศ:** การสร้างทีมอย่างตั้งใจผ่านการสรรหาที่ครอบคลุม การสัมภาษณ์แบบมีโครงสร้างและผ่านการปรับเทียบที่ลดอคติ และแผนปฐมนิเทศจริงจังที่ช่วยให้วิศวกรใหม่ทำงานได้ผลและรู้สึกเป็นส่วนหนึ่งอย่างรวดเร็ว แทนที่จะปล่อยให้เอาตัวรอดเอง
- **1.9 การทำงานแบบกระจายและทางไกล:** การทำงานข้ามสถานที่และเขตเวลาโดยใช้การร่วมมือแบบไม่ต้องพร้อมกัน เป็นลายลักษณ์อักษร และเอกสารมาก่อนเป็นค่าเริ่มต้น ออกแบบช่วงเวลาทับซ้อนและการส่งต่องานอย่างตั้งใจ และประเมินคนจากผลลัพธ์ ไม่ใช่จากจำนวนชั่วโมงหรือการให้คนเห็นหน้า
- **1.10 ประสิทธิผลทางวิศวกรรมและผลิตภาพของนักพัฒนา:** การวัดและปรับปรุงว่าวิศวกรทำงานได้ดีที่สุดอย่างมีประสิทธิผลเพียงใด โดยใช้กรอบหลายมิติ (SPACE และประสบการณ์ของนักพัฒนา) แทนตัวเลขเดี่ยวที่ถูกเล่นเกมได้ง่าย และขจัดแรงเสียดทานและงานซ้ำซากที่ทำให้ทีมช้าลง

- **1.11 การบริหารงานวิศวกรรม:** ฝีมือในการบริหารวิศวกร ไม่ใช่ตัวบันไดอาชีพเอง ได้แก่วงจรการคุยตัวต่อตัว (one-on-one) การให้ฟีดแบ็ก และการโค้ช การมอบหมายงาน การบริหารผลการปฏิบัติงานอย่างมีมนุษยธรรม และการถูกวัดว่าเป็นตัวคูณพลังของทีม ไม่ใช่วัดจากผลงานของตัวเอง
- **1.12 ความหลากหลาย ความเท่าเทียม การรวมกลุ่ม และความรู้สึกเป็นส่วนหนึ่ง:** การสร้างทีมที่ความแตกต่างมีอยู่จริง ได้รับการปฏิบัติอย่างเป็นธรรม ถูกรวมเข้ามาอย่างจริงจัง และทำให้รู้สึกว่าตนเป็นส่วนหนึ่ง เพราะทีมที่ครอบคลุมสร้างซอฟต์แวร์ได้ดีกว่า และเพราะมันเป็นสิ่งที่ถูกต้อง โดยมีการวัดผลอย่างซื่อสัตย์และไม่ทำแค่พอเป็นพิธี (tokenism)
- **1.13 การเป็นพี่เลี้ยง การโค้ช และการแบ่งปันความรู้:** การพัฒนาคนและกระจายความเชี่ยวชาญอย่างตั้งใจผ่านการเป็นพี่เลี้ยง การโค้ช และการสนับสนุน (sponsorship) ชุมชนผู้ปฏิบัติ การบรรยายภายใน การทำงานคู่ (pairing) และการใช้เอกสารเป็นสื่อสอน เพื่อให้ความรู้อยู่ต่อได้เกินกว่าตัวบุคคล และความเสี่ยงแบบ bus factor ต่ำ

## บทเหล่านี้เกี่ยวข้องกันอย่างไร

บทเหล่านี้ร้อยเป็นเส้นเรื่องเดียวกัน คุณค่ากำหนดว่าองค์กรใส่ใจอะไร โครงสร้างและบทบาทกำหนดว่าใครทำงานและเติบโตอย่างไร วิธีการทำงานกำกับว่าผู้คนประสานงานกันอย่างไร ธรรมาภิบาลและบันทึกการตัดสินใจรักษาเหตุผลเบื้องหลังการเลือกเหล่านั้นไว้ ความพึ่งพากันเรียงตามลำดับนี้ วัฒนธรรมการเขียนและความปลอดภัยทางจิตใจในบทที่ 1.1 เป็นเงื่อนไขเบื้องต้นของการปรับเทียบอย่างซื่อสัตย์ในบทที่ 1.3 การร่วมมือแบบเอกสารมาก่อนในบทที่ 1.4 และบันทึกการตัดสินใจที่คงทนในบทที่ 1.6 เส้นแบ่งทีมที่ออกแบบในบทที่ 1.2 คือคันโยกหลักของคุณในการขยายการประสานงานในบทที่ 1.4 ซึ่งเลือกอย่างชัดเจนที่จะลดความจำเป็นในการประสานงาน แทนที่จะเพิ่มกรอบการทำงานที่หนักขึ้น บทที่ 1.5 และ 1.6 เป็นคู่กันโดยตั้งใจ บทแรกวางปรัชญาธรรมาภิบาล บทหลังเปลี่ยนมันเป็นแนวปฏิบัติที่ทำต่อเนื่อง

อิทธิพลของส่วนนี้แผ่ไปทั่วทั้งเล่ม โครงสร้างทีมในบทที่ 1.2 หล่อหลอม[วิศวกรรมแพลตฟอร์ม](https://en.wikipedia.org/wiki/Platform_engineering)ในบทที่ 8.4 และความเป็นเจ้าของด้านความน่าเชื่อถือในบทที่ 9.1 บันทึกการตัดสินใจที่แนะนำไว้ที่นี่ปรากฏซ้ำทุกที่ที่มีการเลือกสำคัญ ตั้งแต่พื้นฐานสถาปัตยกรรมในบทที่ 3.1 ไปจนถึงการตัดสินใจสร้างเองหรือซื้อและการจัดซื้อจัดจ้างในบทที่ 10.3 และการรับประกันด้วย fitness function ของบันทึกเหล่านี้เชื่อมกับสายการส่งมอบในบทที่ 8.1 การเรียนรู้แบบไม่กล่าวโทษในบทที่ 1.1 หนุนหลัง[การจัดการเหตุการณ์](https://en.wikipedia.org/wiki/Incident_management)ในบทที่ 9.3 และการตัดสินใจที่ปกป้องได้และมีเอกสารรองรับซึ่งวางรากไว้ตลอดส่วนนี้ ก็คือสิ่งที่งานด้านความเสี่ยง การตรวจสอบ และการรับประกันในบทที่ 10.2 ต้องอาศัย วางรากฐานให้ถูก แล้วส่วนที่เหลือของหนังสือจะนำไปใช้ได้ง่ายขึ้นมาก
