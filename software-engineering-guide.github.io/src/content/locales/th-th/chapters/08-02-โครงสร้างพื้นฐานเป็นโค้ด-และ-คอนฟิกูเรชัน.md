# 8.2 โครงสร้างพื้นฐานเป็นโค้ดและคอนฟิกูเรชัน

## ภาพรวมและแรงจูงใจ

[โครงสร้างพื้นฐานเป็นโค้ด](https://en.wikipedia.org/wiki/Infrastructure_as_code) (infrastructure as code หรือ IaC) หมายถึงการกำหนดและจัดเตรียมโครงสร้างพื้นฐาน (เครือข่าย เซิร์ฟเวอร์ ฐานข้อมูล ตัวกระจายโหลด และสิทธิ์การเข้าถึง) ผ่านไฟล์นิยามที่เครื่องอ่านได้ แทนการคลิกในคอนโซลด้วยมือหรือใช้สคริปต์เฉพาะกิจ [การจัดการคอนฟิกูเรชัน](https://en.wikipedia.org/wiki/Configuration_management) (configuration management) ขยายแนวคิดเดียวกันไปยังการตั้งค่าและสถานะของระบบหลังจากที่ระบบถูกสร้างขึ้นแล้ว ทั้งสองอย่างนี้ร่วมกันเปลี่ยนโครงสร้างพื้นฐานจากของที่ปั้นด้วยมือและเปราะบาง ให้เป็นผลผลิตที่มีเวอร์ชัน รีวิวได้ และสร้างซ้ำได้ ภายใต้วินัยทางวิศวกรรมเดียวกับที่คุณใช้กับโค้ดแอปพลิเคชัน

สำหรับทีมขนาดใหญ่ IaC ไม่ใช่ความสะดวกแต่เป็นความจำเป็น เมื่อวิศวกรหลายร้อยคนต้องการสภาพแวดล้อม และทรัพยากรนับพันต้องสม่ำเสมอกันข้ามภูมิภาคและบัญชี การจัดเตรียมด้วยมือตามไม่ทันและไม่อาจถูกต้องต่อไปได้ โครงสร้างพื้นฐานที่คนตั้งค่าเองจะค่อยๆ เลื่อนไปสู่เซิร์ฟเวอร์ "สโนว์เฟลก" (snowflake) ที่ไม่ซ้ำใคร ซึ่งไม่มีใครเข้าใจครบถ้วนและสร้างขึ้นใหม่หลังความล้มเหลวอย่างเชื่อถือได้ไม่ได้ ไม่ช้าก็เร็ว การเขียนโครงสร้างพื้นฐานเป็นโค้ดทำให้มันสม่ำเสมอ ตรวจสอบย้อนหลังได้ และทิ้งได้ สภาพแวดล้อมใดๆ สร้างขึ้นใหม่ได้จากนิยามของมัน และทุกการเปลี่ยนแปลงคือ diff ที่รีวิวได้

องค์กรขนาดใหญ่และภาครัฐได้ประโยชน์อีกข้อหนึ่งที่ชี้ขาด คือธรรมาภิบาลที่บังคับใช้ได้จริง ข้อกำหนดด้านความมั่นคงปลอดภัยและการปฏิบัติตามข้อกำหนด เช่น การเข้ารหัสข้อมูลขณะจัดเก็บ การแบ่งส่วนเครือข่าย ภูมิภาคที่อนุมัติ และการติดแท็กเพื่อจัดสรรต้นทุน ฝังไว้ในโค้ดได้โดยตรงและตรวจอัตโนมัติก่อนที่จะมีอะไรถูกจัดเตรียม แทนที่จะตรวจสอบโครงสร้างพื้นฐานหลังเกิดเหตุแล้วไล่จับการละเมิด คุณกันไม่ให้โครงสร้างพื้นฐานที่ไม่ปฏิบัติตามข้อกำหนดเกิดขึ้นมาเลย การเปลี่ยนจากการตรวจจับเป็นการป้องกันนี้คือเหตุผลหลักที่ IaC กลายเป็นรากฐานของแนวปฏิบัติด้านแพลตฟอร์มสมัยใหม่

## หลักการสำคัญ

- เลือกนิยามแบบประกาศ (declarative) ที่อธิบายสถานะที่ต้องการ มากกว่าสคริปต์แบบสั่งการ (imperative) ที่อธิบายขั้นตอน
- เก็บนิยามโครงสร้างพื้นฐานทั้งหมดในระบบควบคุมเวอร์ชัน และรีวิวเหมือนโค้ดอื่นๆ
- ปฏิบัติต่อโครงสร้างพื้นฐานเป็นสิ่งที่แก้ไขไม่ได้ (immutable) คือแทนที่ ไม่ใช่แก้ไขกับที่
- ทำให้การจัดเตรียมเป็นอิดเอมโพเทนต์ (idempotent) เพื่อให้การใช้นิยามเดิมซ้ำๆ ได้ผลลัพธ์เดิม
- ตรวจจับและปรับให้ตรงกันเมื่อเกิดดริฟต์ (drift คือสภาพแวดล้อมจริงเบี่ยงจากนิยามที่ประกาศไว้) อย่างต่อเนื่อง โค้ด ไม่ใช่ระบบจริง คือแหล่งความจริง
- ประกอบโครงสร้างพื้นฐานจากโมดูลที่นำกลับมาใช้ซ้ำได้และมีเวอร์ชัน แทนการคัดลอกแล้ววาง
- เขียนนโยบายเป็นโค้ด (policy as code คือกฎขององค์กรที่เขียนเป็นโค้ดที่เครื่องตรวจได้) เพื่อให้ราวกั้นป้องกัน (guardrail) ทำงานอัตโนมัติ ไม่ใช่เพียงคำแนะนำ
- เก็บความลับ (secret) ออกจากนิยาม และอ้างอิงจากตัวจัดการความลับโดยเฉพาะ

## ข้อแนะนำ

### เลือกเครื่องมือแบบประกาศและจัดโครงสร้างรอบโมดูล

ใช้เครื่องมือ IaC แบบประกาศ เช่น [Terraform](https://en.wikipedia.org/wiki/Terraform_(software)), Pulumi หรือทางเลือกแบบเนทีฟของคลาวด์อย่าง CloudFormation และกำหนดมาตรฐานให้ใช้เครื่องมือเดียวกันทั่วทั้งองค์กร เพื่อไม่ให้ภูมิทัศน์เครื่องมือแตกกระจาย แนวปฏิบัติเชิงสถาปัตยกรรมที่สำคัญคือความเป็นโมดูล คือสร้างโมดูลเล็กๆ ที่มีเอกสารชัดเจนและมีเวอร์ชัน ซึ่งจับรูปแบบที่พบบ่อยไว้ (เครือข่ายที่ปฏิบัติตามข้อกำหนด ฐานข้อมูลที่เสริมความแข็งแกร่ง บริการมาตรฐาน) ทีมต่างๆ จึงประกอบสภาพแวดล้อมจากโมดูลเหล่านี้ แทนการเขียนทรัพยากรดิบเอง วิธีนี้กระจายค่าเริ่มต้นที่ดีและการตั้งค่าความมั่นคงปลอดภัยโดยอัตโนมัติ และลดความซ้ำซ้อนลงอย่างมาก

### จัดการสถานะอย่างตั้งใจ

เครื่องมือแบบประกาศติดตามการจับคู่ระหว่างโค้ดกับทรัพยากรจริงไว้ในไฟล์สถานะ (state file) เก็บสถานะไว้ระยะไกลในแบ็กเอนด์ที่ใช้ร่วมกัน เข้ารหัส และควบคุมการเข้าถึง และใช้การล็อกเพื่อไม่ให้การแก้ไขพร้อมกันทำให้สถานะเสียหาย อย่าเก็บสถานะไว้ในแล็ปท็อปเด็ดขาด และอย่าแก้ด้วยมือ ยกเว้นเป็นการกู้คืนทางเลือกสุดท้าย สถานะเป็นข้อมูลอ่อนไหวเพราะอาจมีเมทาดาทาของทรัพยากรและความลับอยู่ จึงต้องปกป้องให้สมกัน

### สร้างโครงสร้างพื้นฐานที่แก้ไขไม่ได้ด้วยโกลเดนอิมเมจ

แทนที่จะแพตช์เซิร์ฟเวอร์ที่กำลังรัน ให้อบ "โกลเดนอิมเมจ" (golden image คืออิมเมจเครื่องหรือคอนเทนเนอร์ที่ตั้งค่าและเสริมความแข็งแกร่งไว้ล่วงหน้า) ที่มีเวอร์ชัน แล้วดีพลอยอินสแตนซ์ใหม่จากอิมเมจนั้น เมื่อต้องการเปลี่ยนแปลงหรือแพตช์ ให้บิลด์อิมเมจใหม่แล้วทยอยปล่อย พร้อมปลดอินสแตนซ์เก่า วิธีนี้ขจัดดริฟต์ของคอนฟิกูเรชัน ทำให้ย้อนกลับได้ง่ายดาย และทำให้ทุกอินสแตนซ์เหมือนกันและย้อนรอยไปถึงบิลด์ที่รู้ว่าดีได้ ไปป์ไลน์สร้างอิมเมจอัตโนมัติควรรวมการเสริมความแข็งแกร่งด้านความมั่นคงปลอดภัยและการสแกน เพื่อให้การปฏิบัติตามข้อกำหนดถูกสร้างไว้ในระดับอิมเมจ

### ตรวจจับและปรับดริฟต์ของคอนฟิกูเรชัน

ดริฟต์เกิดเมื่อสภาพแวดล้อมจริงเบี่ยงจากนิยามของมัน มักเพราะมีคนแก้ไขด้วยมือในภาวะฉุกเฉิน ให้รันการตรวจจับดริฟต์สม่ำเสมอที่เทียบสถานะจริงกับสถานะที่ประกาศไว้และชี้ความแตกต่าง ปฏิบัติต่อดริฟต์เหมือนข้อบกพร่อง ปรับให้ตรงกันด้วยการอัปเดตโค้ดแล้วใช้ซ้ำ ไม่ใช่ปล่อยการเปลี่ยนด้วยมือไว้ สำหรับระบบที่ต้องบังคับใช้คอนฟิกูเรชันต่อเนื่อง ให้ใช้เครื่องมือจัดการคอนฟิกูเรชันที่ทำให้โฮสต์ลู่เข้าสู่สถานะที่ประกาศไว้อยู่เสมอ

### ใช้ GitOps และการดีพลอยแบบดึง (pull-based)

ในแบบจำลอง GitOps คลังโค้ด Git เก็บสถานะที่ต้องการของระบบที่ประกาศไว้ และเอเจนต์อัตโนมัติที่รันอยู่ภายในสภาพแวดล้อมปลายทางดึงสถานะนั้นมาอย่างต่อเนื่องและปรับระบบจริงให้ตรงกัน วิธีนี้พลิกแบบจำลองแบบผลัก (push) ดั้งเดิม ไม่มีระบบภายนอกใดต้องถือข้อมูลรับรองถาวรเพื่อเปลี่ยนสภาพแวดล้อม เพราะสภาพแวดล้อมดึงคอนฟิกของตัวเอง GitOps ให้ร่องรอยการตรวจสอบครบถ้วน (ทุกการเปลี่ยนแปลงคือคอมมิต) ย้อนกลับง่าย (ย้อนคอมมิต) และแก้ดริฟต์ได้เข้มแข็ง (เอเจนต์ยืนยันสถานะที่ต้องการซ้ำอย่างต่อเนื่อง) มีพลังเป็นพิเศษสำหรับ [Kubernetes](https://en.wikipedia.org/wiki/Kubernetes) และสำหรับองค์กรที่ต้องการแหล่งความจริงเดียวที่รีวิวได้

### บังคับใช้ราวกั้นป้องกันด้วยนโยบายเป็นโค้ด

เขียนกฎขององค์กร เช่น ภูมิภาคที่อนุญาต การเข้ารหัสที่บังคับ แท็กที่จำเป็น และการห้ามเปิดสู่สาธารณะ เป็นนโยบายที่เครื่องตรวจได้ โดยใช้เครื่องมืออย่าง Open Policy Agent (OPA) หรือเอนจินนโยบายเฉพาะแพลตฟอร์มอย่าง Sentinel รันการตรวจเหล่านี้ในไปป์ไลน์ก่อนการจัดเตรียม เพื่อให้การละเมิดถูกบล็อกอัตโนมัติ นโยบายเป็นโค้ดเปลี่ยนเจตนาของทีมความมั่นคงปลอดภัยให้เป็นการควบคุมที่รันได้และใช้เสมอกัน และขยายไปถึงการเปลี่ยนแปลงนับพันได้ในแบบที่การรีวิวด้วยมือทำไม่ได้เลย

## ข้อดีข้อเสียและการแลกเปลี่ยน

| ทางเลือก | ข้อดี | ข้อเสีย | เหมาะกับ |
|---|---|---|---|
| IaC แบบประกาศ (Terraform/Pulumi) | สร้างซ้ำได้ รีวิวได้ ตรวจจับดริฟต์ได้ | มีช่วงเรียนรู้ การจัดการสถานะซับซ้อน | แทบทุกทีมในระดับใหญ่ |
| สคริปต์แบบสั่งการ | คุ้นเคย ยืดหยุ่นสำหรับงานครั้งเดียว | ไม่เป็นอิดเอมโพเทนต์ ตรวจสอบและทำซ้ำยาก | กรณีแคบๆ ที่เป็นช่วงเปลี่ยนผ่าน |
| แก้ไขไม่ได้ + โกลเดนอิมเมจ | ไม่มีดริฟต์ ย้อนกลับง่ายมาก | ภาระของไปป์ไลน์สร้างอิมเมจ | กลุ่มเครื่องที่ต้องการความสม่ำเสมอ |
| การจัดการคอนฟิกแบบแก้ไขได้ | ควบคุมต่อเนื่องได้ละเอียด | เสี่ยงดริฟต์ ลู่เข้าช้ากว่า | โฮสต์เก่าหรือโฮสต์อายุยาว |
| GitOps (แบบดึง) | ร่องรอยการตรวจสอบเข้มแข็ง ซ่อมตัวเองได้ | ต้องมีเอเจนต์ในคลัสเตอร์และวินัยการใช้ Git | Kubernetes และคลาวด์เนทีฟ |
| นโยบายเป็นโค้ด | ราวกั้นอัตโนมัติและสม่ำเสมอ | ต้องลงแรงเขียนนโยบายล่วงหน้า | สภาพแวดล้อมที่มีการกำกับดูแล |

ความตึงเครียดหลักคือระหว่างความยืดหยุ่นกับการควบคุม วิธีแบบมือและแบบสั่งการดูเร็วกว่าสำหรับการเปลี่ยนแปลงครั้งเดียว แต่สะสมความไม่สม่ำเสมอที่ซ่อนอยู่ ซึ่งกลายเป็นอัมพาตเมื่อองค์กรโต โครงสร้างพื้นฐานแบบประกาศ แก้ไขไม่ได้ และมีนโยบายกำกับ ต้องการการลงทุนล่วงหน้ามากกว่าและการเปลี่ยนวัฒนธรรมจริงจัง เพราะวิศวกรต้องเลิกแก้ในคอนโซลแบบเร็วๆ แต่ตอบแทนการลงทุนนั้นคืนหลายเท่าในด้านความน่าเชื่อถือ ความสามารถในการตรวจสอบย้อนหลัง และความสามารถในการสร้างทุกอย่างขึ้นใหม่ได้ตามต้องการ

## คำถามที่ควรคุยกับทีม

1. **ใครเป็นเจ้าของไลบรารีโมดูลที่ใช้ร่วมกัน และการปรับปรุงโมดูลไปถึงทุกทีมที่ใช้ได้อย่างไร?** โมดูลจะคุ้มก็ต่อเมื่อการแก้ไขและค่าเริ่มต้นที่เสริมความแข็งแกร่งแล้วแพร่ไปถึงทุกที่ ซึ่งต้องมีเจ้าของที่ชัดเจนและการกำหนดเวอร์ชันจริงจัง ไม่ใช่โฟลเดอร์ที่ทุกคนคัดลอกไปใช้ ตัดสินใจว่าใครดูแลโมดูลเครือข่ายที่ปฏิบัติตามข้อกำหนดและโมดูลฐานข้อมูลที่เสริมความแข็งแกร่ง จะกำหนดเวอร์ชันอย่างไร (เวอร์ชันแบบ semantic พร้อมบันทึกการเปลี่ยนแปลง) และทีมจะดึงการอัปเกรดโดยไม่ต้องวุ่นวายได้อย่างไร ในระดับใหญ่ นี่คือความต่างระหว่างการแก้การตั้งค่าผิดครั้งเดียว กับการไล่ตามแก้ข้ามทรัพยากรนับพันที่แก้ด้วยมือ นำหลักฐานมา ปัจจุบันมีรูปแบบเดียวกันที่ถูกคัดลอกแยกกันกี่ชุด การแก้ไขความมั่นคงปลอดภัยใช้เวลานานเท่าไรกว่าจะถึงทุกสภาพแวดล้อม และทีมตรึงเวอร์ชันโมดูลหรือปล่อยให้ลอย ถ้าแพตช์สำคัญไปถึงทั้งระบบภายในไม่กี่วันไม่ได้ ความเป็นโมดูลของคุณก็เป็นแค่เปลือก

2. **ความถี่ในการตรวจจับดริฟต์ของคุณคือเท่าไร และเกิดอะไรขึ้นจริงๆ เมื่อพบดริฟต์?** ดริฟต์คือสภาพแวดล้อมจริงที่เบี่ยงจากสถานะที่ประกาศไว้อย่างเงียบๆ มักมาจากการแก้ในคอนโซลยามฉุกเฉิน และการยอมให้มันอยู่ทำให้โค้ดของคุณกลายเป็นนิยาย ตัดสินใจว่าจะเทียบสถานะจริงกับสถานะที่ประกาศบ่อยแค่ไหน (รายคืนเป็นค่าเริ่มต้นที่สมเหตุสมผล) และที่สำคัญกว่าคือตัดสินใจการตอบสนอง คือปรับให้ตรงด้วยการอัปเดตโค้ดแล้วใช้ซ้ำ ไม่ใช่ปล่อยการแก้ด้วยมือไว้ ในบริบทที่มีการกำกับดูแล นี่เป็นข้อกำหนดของการควบคุม เพราะผู้ตรวจสอบต้องการให้สถานะที่ประกาศตรงกับความเป็นจริงอย่างต่อเนื่อง นำตัวเลขปัจจุบันมา แต่ละสัปดาห์มีทรัพยากรเกิดดริฟต์กี่รายการ อยู่ในสภาพดริฟต์นานเท่าไร และมีใครรับผิดชอบการปิดหรือไม่ ปฏิบัติต่อทุกดริฟต์เป็นข้อบกพร่องที่มีเจ้าของ ไม่เช่นนั้นหลักประกันเรื่องแหล่งความจริงจะกร่อนจนไม่มีใครเชื่อโค้ด

3. **คุณย้ายไปใช้ GitOps และการปรับให้ตรงแบบดึงแล้วหรือยัง หรือยังมีระบบภายนอกที่ถือข้อมูลรับรองถาวรสำหรับเปลี่ยนระบบจริง?** ในแบบจำลองแบบดึง เอเจนต์ภายในสภาพแวดล้อมปลายทางปรับระบบจริงให้ตรงกับ Git อย่างต่อเนื่อง ซึ่งไม่ต้องให้ระบบภายนอกถือสิทธิ์เขียน และยืนยันสถานะที่ต้องการซ้ำจนดริฟต์แก้ตัวเองได้ นี่คือท่าทีด้านความมั่นคงปลอดภัยและการตรวจสอบที่แข็งแรง เพราะทุกการเปลี่ยนแปลงคือคอมมิต และไม่มีผู้ปฏิบัติงานคนใดต้องถือข้อมูลรับรองถาวรของระบบจริง ต้นทุนมีอยู่จริง คือต้องรันเอเจนต์ในคลัสเตอร์และมีวินัยการใช้ Git เข้มงวด ดังนั้นให้ชั่งเทียบกับระบบอัตโนมัติแบบผลักที่คุณใช้อยู่ นำรายการมาว่าใครและอะไรบ้างที่เปลี่ยนระบบจริงได้โดยตรงตอนนี้ และการเปลี่ยนเหล่านั้นทิ้งร่องรอยการตรวจสอบอะไรไว้ สำหรับ Kubernetes และเขตปลอดภัยที่ต้องการหลักประกันสูง การเปลี่ยนนี้มักคุ้มค่า แต่สำหรับทรัพยากรนิ่งไม่กี่รายการอาจเกินความจำเป็น

4. **สถานะโครงสร้างพื้นฐานของคุณถูกเก็บ ล็อก และควบคุมการเข้าถึงอย่างไร และจะเกิดอะไรขึ้นในวันที่มันเสียหายหรือสูญหาย?** สถานะคือแผนที่ระหว่างโค้ดกับทรัพยากรจริง ไฟล์สถานะที่หายหรือเสียหายอาจทำให้เครื่องมือมองไม่เห็นทรัพยากรที่มันสร้างเอง และล่อให้ใครสักคนสั่งใช้ซ้ำแบบทำลายล้าง สำหรับทีมใหญ่ ความเสี่ยงทวีคูณ เพราะวิศวกรจำนวนมากที่ใช้กับสถานะร่วมต้องมีแบ็กเอนด์ระยะไกลที่เข้ารหัสและล็อก เพื่อไม่ให้การรันพร้อมกันเขียนทับกัน ชั่งความสะดวกของสถานะก้อนใหญ่ก้อนเดียวเทียบกับขอบเขตผลกระทบที่มันสร้าง และพิจารณาแยกสถานะตามสภาพแวดล้อมหรือตามโดเมน เพื่อไม่ให้ความผิดพลาดเดียวล้มได้ทุกอย่าง นำข้อเท็จจริงมา ปัจจุบันสถานะอยู่ที่ไหน มีการบังคับล็อกหรือไม่ ใครอ่านได้ (มันอาจมีความลับ) และเคยซ้อมกู้คืนหรือไม่ ในบริบทองค์กรขนาดใหญ่และภาครัฐ ให้ปฏิบัติต่อแบ็กเอนด์สถานะเป็นสินทรัพย์อ่อนไหวที่ควบคุมการเข้าถึง มีการสำรองข้อมูล บันทึกการตรวจสอบ และรันบุ๊กการกู้คืนของตัวเอง เพราะการเสียมันคือการเสียบันทึกว่ามีอะไรอยู่บ้าง

5. **เมื่อเหตุฉุกเฉินจริงๆ ต้องการการเปลี่ยนด้วยมือ เส้นทางฉุกเฉิน (break-glass) ที่ได้รับอนุญาตคืออะไร และการเปลี่ยนนั้นถูกนำกลับเข้าโค้ดอย่างไร?** ทุกแนวปฏิบัติ IaC ที่เติบโตแล้วจะเจอเหตุตีสามที่การรอไปป์ไลน์ยอมรับไม่ได้ และคำถามที่ตรงไปตรงมาไม่ใช่ว่าการเปลี่ยนด้วยมือจะเกิดหรือไม่ แต่คือคุณควบคุมมันอย่างไร ตัดสินใจล่วงหน้าว่าใครข้ามไปป์ไลน์ได้ แตะอะไรได้บ้าง การกระทำถูกบันทึกอย่างไร และกำหนดเส้นตายที่การเปลี่ยนต้องถูกปรับเข้าโค้ดหรือย้อนกลับ หากไม่มีข้อตกลงนี้ ข้อยกเว้นฉุกเฉินจะกลายเป็นนิสัยประจำวันอย่างเงียบๆ และ ClickOps จะกลับมาทางประตูหลัง นำหลักฐานมา ไตรมาสที่แล้วมีการเปลี่ยนนอกกระบวนการกี่ครั้ง แต่ละครั้งค้างอยู่โดยไม่ถูกปรับให้ตรงนานเท่าไร และการตรวจจับดริฟต์จับได้จริงหรือไม่ สำหรับหน่วยงานที่มีการกำกับดูแลและหน่วยงานสาธารณะ ขั้นตอนฉุกเฉินที่มีเอกสารและบันทึกอัตโนมัติมักเป็นข้อกำหนดของการควบคุม เพราะผู้ตรวจสอบคาดหวังทั้งว่าเหตุฉุกเฉินเกิดได้ และทุกครั้งทิ้งร่องรอยและพาระบบกลับสู่สถานะที่ประกาศไว้

6. **พื้นฐานด้านความมั่นคงปลอดภัยและการปฏิบัติตามข้อกำหนดของคุณถูกเขียนเป็นนโยบายที่บล็อกการเปลี่ยนแปลงที่ไม่ดีโดยอัตโนมัติมากแค่ไหน เทียบกับกฎที่อยู่ในเอกสารและพึ่งให้ใครสักคนจำได้?** ราวกั้นที่เขียนเป็นร้อยแก้วในวิกิถูกละเมิดเป็นประจำ เพราะมันพึ่งให้วิศวกรทุกคนอ่านและปฏิบัติตามภายใต้แรงกดดันของเดดไลน์ ขณะที่กฎเดียวกันที่เขียนเป็นนโยบายเป็นโค้ดจะปฏิเสธการเปลี่ยนแปลงที่ไม่ปฏิบัติตามก่อนที่จะถูกจัดเตรียมเสียอีก สำหรับองค์กรขนาดใหญ่ นี่เป็นวิธีเดียวที่เจตนาของทีมความมั่นคงปลอดภัยจะขยายไปถึงการเปลี่ยนแปลงนับพันโดยไม่กลายเป็นคอขวดของการรีวิว ชั่งต้นทุนล่วงหน้าของการเขียนและดูแลนโยบายเทียบกับต้นทุนซ้ำๆ ของการรีวิวด้วยมือและการแก้ไขหลังเกิดเหตุ และตัดสินใจว่าการควบคุมใด (การเข้ารหัส ภูมิภาคที่อนุมัติ แท็กที่บังคับ ห้ามเปิดสู่สาธารณะ) ต่อรองไม่ได้พอที่จะบังคับเป็นเกตเด็ดขาด นำรายการกฎพื้นฐานปัจจุบันมาและทำเครื่องหมายว่าข้อไหนอัตโนมัติและข้อไหนเป็นแค่คำแนะนำ พร้อมความถี่ที่แต่ละข้อถูกละเมิดในทางปฏิบัติ ในบริบทองค์กรขนาดใหญ่และภาครัฐ นโยบายอัตโนมัติเปลี่ยนการตรวจสอบจากการรวบรวมหลักฐานด้วยมือหลายสัปดาห์ให้เป็นการสืบค้นการควบคุมที่บังคับใช้อยู่ และเปลี่ยนการปฏิบัติตามข้อกำหนดจากการตรวจจับเป็นการป้องกัน

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ความเร็วชนะ ดังนั้นให้ใส่สแต็กทั้งหมดไว้ในคลังโค้ดแบบประกาศเดียว (Terraform เป็นค่าเริ่มต้นที่พบบ่อย) เก็บสถานะไว้ในแบ็กเอนด์ที่มีผู้ให้บริการจัดการและเข้ารหัส และส่งทุกการเปลี่ยนแปลงผ่านพูลรีเควสต์แม้ทีมมีสามคน ข้ามกลไกแพลตฟอร์มหนักๆ ไปก่อน ไม่ต้องมีทีมโมดูลกลาง ยังไม่ต้องมีเอนจินนโยบาย มีแค่ระบบควบคุมเวอร์ชันกับวินัยที่จะไม่คลิกในคอนโซล เพียงเท่านี้คุณก็ได้สภาพแวดล้อมที่สร้างซ้ำได้ ทิ้งเพื่อประหยัดเงินได้ และสร้างใหม่สำหรับเดโมครั้งต่อไปได้

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญด้านแพลตฟอร์มโดยเฉพาะ ให้พึ่งบริการที่มีผู้ให้บริการจัดการและ IaC ที่ผู้ให้บริการคลาวด์หรือผู้ขายของคุณรองรับอยู่แล้ว แทนการตั้งเครื่องมือเฉพาะตัวที่คุณดูแลไม่ไหว เลือกซื้อแพลตฟอร์มที่โฮสต์ให้ซึ่งจัดการค่าเริ่มต้นที่สมเหตุสมผล (การเข้ารหัส การสำรองข้อมูล การแพตช์) ให้คุณ มากกว่าสร้างไปป์ไลน์โกลเดนอิมเมจที่คุณไม่มีใครรัน วางเป้าหมายให้แคบ คือนำทรัพยากรสำคัญไม่กี่รายการเข้าโค้ด เพื่อให้สร้างใหม่ได้หลังความล้มเหลวหรือเมื่อผู้รับเหมาออกไป

**องค์กรขนาดใหญ่.** ปัญหาแกนกลางคือความสม่ำเสมอข้ามหลายทีม บัญชี และภูมิภาค ดังนั้นให้ลงทุนในไลบรารีโมดูลร่วมที่มีเวอร์ชัน สถานะระยะไกลที่ล็อกได้ และนโยบายเป็นโค้ดที่บังคับในไปป์ไลน์ ทีมแพลตฟอร์มกลางเผยแพร่โมดูลที่เสริมความแข็งแกร่งและราวกั้นป้องกัน ขณะที่ทีมผลิตภัณฑ์บริการตนเองภายในกรอบนั้น และการตรวจจับดริฟต์รันต่อเนื่องเพื่อให้ทรัพยากรนับพันอยู่ในสถานะที่รู้จัก จัดงบสำหรับต้นทุนต่อเนื่องของการดูแลโมดูลและนโยบาย เพราะคุณค่าของมันมาจากการที่การแก้ไขหรือค่าเริ่มต้นที่เสริมความแข็งแกร่งแพร่ไปทุกที่พร้อมกัน

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง การรับรอง และความรับผิดชอบต่อสาธารณะผลักให้คุณไปทางโครงสร้างพื้นฐานที่แก้ไขไม่ได้ คอมมิตที่ลงลายมือชื่อ และการปรับให้ตรงแบบ GitOps ภายในเขตปลอดภัยที่ผ่านการรับรอง เพื่อไม่ให้ผู้ปฏิบัติงานคนใดถือข้อมูลรับรองถาวรสำหรับเปลี่ยนระบบจริง ฝังพื้นฐานด้านความมั่นคงปลอดภัยที่จำเป็นไว้ในโกลเดนอิมเมจและนโยบายเป็นโค้ด และให้ประวัติคอมมิตเป็นหลักฐานการตรวจสอบที่เห็นร่องรอยการแก้ไขและพร้อมใช้ตลอดเวลา เลือกเครื่องมือเปิดที่พกพาได้แทนรูปแบบกรรมสิทธิ์ที่ล็อกคุณไว้ และกำหนดขั้นตอนฉุกเฉินกับการบันทึกให้ชัดเจน เพื่อให้การเปลี่ยนแปลงฉุกเฉินยังเป็นไปตามข้อกำหนดการควบคุมคอนฟิกูเรชัน

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปห้าคนกำหนดการตั้งค่า AWS ทั้งหมด ได้แก่ VPC ฐานข้อมูล และบริการคอนเทนเนอร์ ไว้ในคลังโค้ด Terraform เดียว โดยเก็บสถานะไว้ในแบ็กเอนด์ S3 ที่เข้ารหัสและล็อกผ่าน DynamoDB ทุกการเปลี่ยนแปลงผ่านพูลรีเควสต์ แม้แต่วิศวกรเวรเดี่ยวก็เห็นได้ชัดว่าจะมีอะไรเปลี่ยนก่อนรัน apply เมื่อต้องการสภาพแวดล้อมสเตจจิงใหม่สำหรับเดโมใหญ่ พวกเขาคัดลอกโมดูลเล็กๆ แล้วตั้งขึ้นได้ในไม่กี่นาที และรื้อทิ้งเร็วพอกันเพื่อรักษาค่าใช้จ่ายคลาวด์ให้ต่ำ

**องค์กรขนาดใหญ่.** ผู้ค้าปลีกข้ามชาติจัดการโครงสร้างพื้นฐานข้ามหลายบัญชีคลาวด์และภูมิภาค ทีมแพลตฟอร์มกลางเผยแพร่โมดูล Terraform ที่มีเวอร์ชันสำหรับเครือข่าย ฐานข้อมูล และโครงบริการที่ปฏิบัติตามข้อกำหนด และบังคับใช้นโยบาย OPA ที่ปฏิเสธทรัพยากรใดๆ ที่ไม่มีการเข้ารหัสหรือแท็กจัดสรรต้นทุน ทีมผลิตภัณฑ์จัดเตรียมสภาพแวดล้อมของตัวเองแบบบริการตนเอง แต่ทุกการเปลี่ยนแปลงไหลผ่านไปป์ไลน์ที่ตรวจนโยบายอัตโนมัติ การตรวจจับดริฟต์รันทุกคืนและเปิดตั๋วสำหรับการเปลี่ยนด้วยมือใดๆ ทำให้ทรัพยากรนับพันอยู่ในสถานะที่รู้จักและปฏิบัติตามข้อกำหนดอย่างต่อเนื่อง

**ภาครัฐ.** หน่วยงานกลาโหมที่ทำงานในสภาพแวดล้อมที่ต้องการหลักประกันสูงสร้างโกลเดนอิมเมจที่เสริมความแข็งแกร่งโดยฝังพื้นฐานด้านความมั่นคงปลอดภัยที่จำเป็นไว้ และดีพลอยเฉพาะอินสแตนซ์ที่แก้ไขไม่ได้จากอิมเมจเหล่านั้น โครงสร้างพื้นฐานทั้งหมดถูกประกาศไว้ใน Git และปรับให้ตรงโดยเอเจนต์ GitOps ภายในเขตปลอดภัยที่ผ่านการรับรอง ไม่มีผู้ปฏิบัติงานคนใดถือข้อมูลรับรองถาวรสำหรับเปลี่ยนระบบจริงโดยตรง ทุกการเปลี่ยนแปลงคือคอมมิตที่ลงลายมือชื่อ วิธีนี้ให้ผู้ตรวจสอบมีประวัติครบถ้วนที่เห็นร่องรอยการแก้ไข และเป็นไปตามข้อกำหนดการเฝ้าระวังต่อเนื่องและการควบคุมคอนฟิกูเรชันโดยไม่ต้องรวบรวมหลักฐานด้วยมือ

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ผลตอบแทนการลงทุน (ROI) ของ IaC มาจากความเร็ว ความน่าเชื่อถือ และการลดความเสี่ยง สภาพแวดล้อมที่เคยใช้เวลาหลายสัปดาห์ในการจัดเตรียมด้วยมือผ่านตั๋วสร้างได้ในไม่กี่นาที ซึ่งปลดปล่อยวิศวกรและเร่งโครงการ การสร้างซ้ำได้ตัดเวลากู้คืนหลังความล้มเหลวอย่างมาก เพราะสภาพแวดล้อมใดๆ สร้างใหม่จากโค้ดได้ การบังคับใช้นโยบายอัตโนมัติลดความถี่และต้นทุนของเหตุการณ์ด้านความมั่นคงปลอดภัยและข้อค้นพบจากการตรวจสอบ ซึ่งสำหรับองค์กรที่มีการกำกับดูแลอาจเป็นจำนวนมาก

ในบัญชีต้นทุนรวมตลอดอายุการใช้งาน (TCO) ต้นทุนการนำมาใช้รวมถึงเครื่องมือ การฝึกอบรม การสร้างไลบรารีโมดูลและนโยบาย และวินัยที่จะเลิกแก้ไขด้วยมือ ต้นทุนของการไม่ทำนั้นสูงกว่าและทบต้นตามเวลา คือโครงสร้างพื้นฐานแบบสโนว์เฟลกที่ไม่มีใครสร้างใหม่ได้ การจัดเตรียมที่ช้าและผิดพลาดง่าย การตั้งค่าความมั่นคงปลอดภัยที่ผิดซึ่งนำไปสู่การรั่วไหล และการตรวจสอบที่กินแรงงานมือหลายสัปดาห์ สำหรับผู้บริหาร ให้วางกรอบ IaC ว่าเป็นการเปลี่ยนโครงสร้างพื้นฐานจากภาระที่ไม่มีใครจัดการให้เป็นสินทรัพย์ที่มีธรรมาภิบาลและสร้างซ้ำได้ และเป็นกลไกที่ทำให้ความมั่นคงปลอดภัยและการปฏิบัติตามข้อกำหนดเกิดขึ้นอัตโนมัติ ไม่ใช่แค่ความใฝ่ฝัน

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **ClickOps บนระบบจริง.** การแก้ไขด้วยมือในคอนโซลรับประกันดริฟต์และทำลายความสามารถในการสร้างซ้ำ
- **ความลับในโค้ด.** การฝังข้อมูลรับรองไว้ในไฟล์นิยามทำให้มันรั่วเข้าประวัติเวอร์ชันและสถานะ
- **นิยามก้อนเดียวที่ไม่แบ่งโมดูล.** คอนฟิกูเรชันยักษ์อันเดียวที่ไม่มีใครกล้าแก้ไขเปราะบางพอๆ กับการตั้งค่าด้วยมือที่มันมาแทนที่
- **สถานะที่ไม่มีการจัดการ.** ไฟล์สถานะในเครื่องหรือที่ไม่ล็อกนำไปสู่ความเสียหายและโครงสร้างพื้นฐานที่สูญหาย
- **ยอมให้เกิดดริฟต์.** การปล่อยการแก้ไขด้วยมือไว้กร่อนหลักประกันเรื่องแหล่งความจริงจนโค้ดกลายเป็นนิยาย
- **นโยบายเป็นเอกสาร.** กฎที่อยู่ในวิกิแทนการตรวจอัตโนมัติถูกละเมิดเป็นประจำ
- **การคัดลอกวางแพร่กระจาย.** การทำซ้ำคอนฟิกูเรชันข้ามทีมหมายความว่าการแก้ไขและการปรับปรุงไม่เคยแพร่ไปถึงกัน

## แบบจำลองความเป็นผู้ใหญ่

**ระดับ 1 เริ่มต้น.** โครงสร้างพื้นฐานถูกจัดเตรียมด้วยมือผ่านคอนโซลและสคริปต์เฉพาะกิจ สภาพแวดล้อมไม่สม่ำเสมอ ไม่มีเอกสาร และสร้างซ้ำอย่างเชื่อถือได้ไม่ได้ และการกู้คืนจากความล้มเหลวช้าและไม่แน่นอน

**ระดับ 2 พัฒนา.** โครงสร้างพื้นฐานบางส่วนถูกเขียนเป็นโค้ด แต่แนวปฏิบัติต่างกันไปตามทีม การจัดการสถานะไม่สม่ำเสมอ ดริฟต์พบได้ทั่วไป ความลับบางครั้งรั่วเข้าไปในนิยาม และนโยบายถูกบังคับใช้ ถ้ามี ผ่านการรีวิวด้วยมือ

**ระดับ 3 สร้างมาตรฐาน.** IaC แบบประกาศเป็นมาตรฐานตามเอกสารทั่วทั้งองค์กร สร้างจากโมดูลที่มีเวอร์ชันและใช้ร่วมกัน พร้อมสถานะระยะไกลที่จัดการและล็อกไว้ นโยบายเป็นโค้ดบังคับราวกั้นป้องกันในไปป์ไลน์ ความลับถูกอ้างอิงจากตัวจัดการเฉพาะ และการตรวจจับดริฟต์รันตามรอบสม่ำเสมอ

**ระดับ 4 บริหารจัดการ.** แนวปฏิบัติถูกวัดเทียบกับเกณฑ์อ้างอิง คุณติดตามอัตราดริฟต์และเวลาเฉลี่ยในการปรับให้ตรง การรับเวอร์ชันโมดูลข้ามทีม การละเมิดนโยบายที่ถูกบล็อกเทียบกับที่หลุดรอด เวลานำของการจัดเตรียม และสัดส่วนทรัพยากรที่อยู่ภายใต้โค้ดจริง ตัวชี้วัดเหล่านี้กำกับการเปลี่ยนแปลงและชี้ทางลงทุน เพื่อให้การตัดสินใจตั้งอยู่บนหลักฐานแทนเรื่องเล่า

**ระดับ 5 ประสานทั้งระบบ.** โครงสร้างพื้นฐานแก้ไขไม่ได้และขับเคลื่อนด้วย GitOps ซ่อมตัวเองเมื่อเกิดดริฟต์ โดยหลักฐานการปฏิบัติตามข้อกำหนดเกิดขึ้นอัตโนมัติ ไลบรารีโมดูลและนโยบายปรับปรุงต่อเนื่องจากการใช้งานจริงและเหตุการณ์ และแนวปฏิบัติด้านโครงสร้างพื้นฐานบูรณาการกับการวางแผนด้านความมั่นคงปลอดภัย ต้นทุน และการส่งมอบ เพื่อให้ทั้งระบบปรับตัวเมื่อข้อกำหนดเปลี่ยน

## ประเด็นชวนคุย

- เส้นแบ่งระหว่างโมดูลที่มีธรรมาภิบาลจากส่วนกลางกับอิสระของทีมในการกำหนดโครงสร้างพื้นฐานเฉพาะตัวควรอยู่ตรงไหน
- คุณจัดการกับการเปลี่ยนแปลงฉุกเฉินจริงๆ ที่ต้องข้ามไปป์ไลน์ได้อย่างไร โดยไม่ทำให้ ClickOps กลายเป็นเรื่องปกติ
- กลยุทธ์ที่เหมาะสมสำหรับการจัดการและปกป้องสถานะข้ามหลายบัญชีและหลายทีมคืออะไร
- เมื่อไรที่การจัดการคอนฟิกแบบแก้ไขได้ยังมีเหตุผลรองรับ เทียบกับโครงสร้างพื้นฐานที่แก้ไขไม่ได้เต็มรูปแบบ
- คุณรักษาไลบรารีนโยบายเป็นโค้ดให้สอดคล้องกับข้อกำหนดด้านความมั่นคงปลอดภัยและกฎระเบียบที่เปลี่ยนไปได้อย่างไร
- เส้นทางการย้ายที่สมจริงสำหรับโครงสร้างพื้นฐานเก่าที่เกิดก่อน IaC หน้าตาเป็นอย่างไร

## ข้อสรุปสำคัญ

- กำหนดโครงสร้างพื้นฐานแบบประกาศ ควบคุมเวอร์ชัน และปฏิบัติต่อมันเป็นโค้ดที่รีวิวได้และสร้างซ้ำได้
- สร้างจากโมดูลเล็กๆ ที่มีเวอร์ชันเพื่อกระจายค่าเริ่มต้นที่ดีและกำจัดความซ้ำซ้อน
- เลือกโครงสร้างพื้นฐานที่แก้ไขไม่ได้และโกลเดนอิมเมจเพื่อยกเลิกดริฟต์และทำให้ย้อนกลับง่ายขึ้น
- จัดการสถานะอย่างตั้งใจและเก็บความลับออกจากนิยาม
- ใช้ GitOps เพื่อร่องรอยการตรวจสอบที่เข้มแข็งและการปรับให้ตรงที่ซ่อมตัวเองได้
- บังคับราวกั้นป้องกันด้วยนโยบายเป็นโค้ด เพื่อให้การปฏิบัติตามข้อกำหนดถูกป้องกันให้เกิดขึ้น ไม่ใช่ตรวจสอบหลังเหตุการณ์
