# 9.6 วิศวกรรมความโกลาหลและการทดสอบความทนทาน

## ภาพรวมและแรงจูงใจ

[วิศวกรรมความโกลาหล](https://en.wikipedia.org/wiki/Chaos_engineering) (chaos engineering) คือแนวปฏิบัติอย่างมีวินัยในการทดลองกับระบบ เพื่อสร้างความมั่นใจว่าระบบทนต่อสภาวะปั่นป่วนใน production ได้ ชื่อฟังดูบ้าบิ่น และนั่นคือสิ่งแรกที่ต้องปลดทิ้ง วิศวกรรมความโกลาหลไม่ใช่การทุบของพังมั่ว ๆ แล้วหวังว่าจะได้เรียนรู้อะไรสักอย่าง มันเป็นตรงกันข้าม คือวิธีที่ควบคุมได้และขับเคลื่อนด้วยสมมติฐาน ในการฉีดความล้มเหลวที่สมจริงเพื่อให้พบจุดอ่อนก่อนที่ผู้ใช้จะพบ คุณรู้อยู่แล้วว่าระบบจะเจอความล้มเหลว เพราะระบบจริงทุกระบบเจอ คำถามมีข้อเดียวคือคุณจะเจอมันในบ่ายวันอังคารที่มีแผนย้อนกลับพร้อม หรือตอนตีสามในชั่วโมงที่ยุ่งที่สุดโดยไม่รู้เลยว่ากำลังเกิดอะไรขึ้น

สำหรับทีมขนาดใหญ่ เรื่องนี้สำคัญเพราะความซับซ้อนโตเกินกว่าที่ใครจะใช้การตรวจดูแล้วเข้าใจได้ บริการสมัยใหม่คือเครือข่ายของส่วนประกอบหลายสิบหรือหลายร้อยชิ้น แต่ละชิ้นมีค่าหมดเวลา (timeout) การลองใหม่ (retry) แคช และรูปแบบความล้มเหลวของตัวเอง และปฏิสัมพันธ์ระหว่างกันก่อให้เกิดพฤติกรรมที่ผุดขึ้นเองซึ่งแผนภาพสถาปัตยกรรมใดก็ทำนายไม่ได้ คุณอาจรีวิวโค้ด วาดกล่อง แล้วก็ยังโดนตีหัวเมื่อการพึ่งพาที่ช้าทำให้เกิดพายุการลองใหม่ (retry storm) ที่ล้มบริการซึ่งอยู่ห่างออกไปสามช่วง วิศวกรรมความโกลาหลคือวิธีที่คุณใช้ตรวจปฏิสัมพันธ์เหล่านั้นเชิงประจักษ์ ความทนทานของคุณจึงเป็นสิ่งที่ตรวจสอบแล้ว ไม่ใช่สิ่งที่สันนิษฐานเอา

บริบทขององค์กรขนาดใหญ่และภาครัฐยกระดับความเสี่ยง และมากขึ้นเรื่อย ๆ ก็เป็นข้อบังคับ หน่วยกำกับดูแลทางการเงินคาดหวังให้บริษัททดสอบความทนทานเชิงปฏิบัติการกับสถานการณ์ที่รุนแรงแต่เป็นไปได้ และพิสูจน์ว่ารักษาบริการสำคัญให้เดินต่อได้ท่ามกลางการหยุดชะงัก หน่วยงานภาครัฐจัดการซ้อมความต่อเนื่องของการปฏิบัติงาน เพื่อให้บริการสาธารณะที่จำเป็นอยู่รอดจากระบบล่ม ภัยพิบัติ และการโจมตีทางไซเบอร์ ในทั้งสองโลก คำว่า "เราคิดว่ามันจะทนได้" ไม่ใช่คำตอบที่ยอมรับได้สำหรับผู้ตรวจสอบหรือประชาชน วิศวกรรมความโกลาหลให้หลักฐานแก่คุณ บทนี้ต่อยอดจากวิศวกรรมความน่าเชื่อถือของไซต์ (บทที่ 9.1) และรูปแบบความทนทานในบทที่ 3.5 และเชื่อมแน่นกับการจัดการเหตุการณ์ (บทที่ 9.3) และการกู้คืนจากภัยพิบัติ (บทที่ 9.5)

## หลักการสำคัญ

- **สร้างความมั่นใจ ไม่ใช่สร้างความโกลาหล** เป้าหมายคือความทนทานที่ตรวจสอบแล้ว ไม่ใช่การแสดง ทุกการทดลองตอบคำถามเฉพาะเจาะจงว่าระบบทำงานอย่างไรภายใต้ความเครียด
- **นิยามสถานะปกติก่อน** คุณตรวจจับปัญหาไม่ได้หากไม่มีนิยามที่ชัดเจนและวัดได้ว่า "สุขภาพดี" หน้าตาเป็นอย่างไร
- **ตั้งสมมติฐาน** ระบุสิ่งที่คาดว่าจะเกิดก่อนฉีดความผิดพลาด ความแปลกใจคือสิ่งที่ค้นพบ และการไม่มีความแปลกใจก็เป็นสิ่งที่ค้นพบเช่นกัน
- **ลดและจำกัดรัศมีผลกระทบ** เริ่มเล็ก ปกป้องผู้ใช้จริง และขยายขอบเขตเมื่อความมั่นใจโตขึ้นเท่านั้น
- **ควรเลือก production อย่างระมัดระวัง** ความล้มเหลวมีพฤติกรรมต่างไปภายใต้ทราฟฟิกจริง ข้อมูลจริง และขนาดจริง จงสร้างสิทธิ์ที่จะทดสอบที่นั่นให้ได้ก่อน
- **ทำให้เป็นอัตโนมัติสู่การตรวจสอบอย่างต่อเนื่อง** จุดอ่อนที่แก้ไปแล้วครั้งหนึ่งอาจกลับมาเสื่อมอีก ความทนทานที่ทดสอบต่อเนื่องจึงจะยังเป็นจริงอยู่
- **ความล้มเหลวคือครู ไม่ใช่คำตัดสิน** สิ่งที่ค้นพบช่วยปรับปรุงระบบ และไม่เคยเป็นเหตุผลที่จะโทษคนที่รันการทดลอง

## ข้อแนะนำ

### เตรียมข้อกำหนดเบื้องต้นให้พร้อมก่อนฉีดความผิดพลาดแม้แต่ครั้งเดียว

วิศวกรรมความโกลาหลเป็นตัวคูณพลังสำหรับระบบที่เติบโตเต็มที่ และเป็นภาระสำหรับระบบที่ยังไม่โต ก่อนเริ่ม คุณต้องมีสามอย่างให้พร้อม อย่างแรกคือ[ความสามารถในการสังเกตระบบ](https://en.wikipedia.org/wiki/Observability_(software)) (observability) หมายถึงเมตริก ล็อก และเทรซ ที่ทำให้คุณมองเห็นว่าระบบกำลังทำอะไรจากภายนอก เพราะการทดลองที่คุณสังเกตไม่ได้ก็ไม่สอนอะไร อย่างที่สองคือวัตถุประสงค์ระดับบริการ (SLO) หรือนิยามเทียบเท่าของสุขภาพในสถานะปกติ (บทที่ 9.1) เพื่อให้แยกการทดลองที่สำเร็จออกจากการทดลองที่เป็นอันตรายได้แบบเรียลไทม์ อย่างที่สามคือเส้นทางย้อนกลับหรือยกเลิกที่เร็วและเชื่อถือได้ เพื่อให้ทันทีที่การทดลองคุกคามผู้ใช้จริง คุณหยุดมันและคืนบริการปกติได้ในไม่กี่วินาที ถ้าคุณวัดระบบไม่ได้ นิยามสถานะสุขภาพดีไม่ได้ และดึงระบบกลับจากขอบเหวไม่ได้ ก็อย่าเพิ่งรันการทดลองความโกลาหล ให้สร้างความสามารถเหล่านั้นก่อน มันคุ้มค่าในตัวเองอยู่แล้ว

### นิยามสถานะปกติและตั้งสมมติฐานจริง

ทุกการทดลองเริ่มด้วยการเขียนว่า "ปกติ" หน้าตาอย่างไรในรูปที่วัดได้ เช่น อัตราคำขอสำเร็จสูงกว่า 99.9 เปอร์เซ็นต์ ความหน่วงของการชำระเงินต่ำกว่า 400 มิลลิวินาทีที่เปอร์เซ็นไทล์ที่ 95 ความลึกของคิวต่ำกว่าเกณฑ์ นี่คือนิยามสถานะปกติของคุณ และควรสะท้อนสุขภาพที่ผู้ใช้มองเห็น ไม่ใช่ท่อภายใน จากนั้นระบุสมมติฐานด้วยภาษาธรรมดา เช่น "ถ้าเราเพิ่มความหน่วง 300 มิลลิวินาทีให้บริการแนะนำสินค้า หน้าสินค้าจะยังแสดงผลได้ภายในงบความหน่วง เพราะหน้านั้นถือว่าการแนะนำเป็นสิ่งเสริมและหมดเวลาที่ 200 มิลลิวินาที" ตอนนี้คุณมีข้อกล่าวอ้างที่พิสูจน์ว่าผิดได้ เมื่อรันการทดลอง จะเกิดสิ่งดี ๆ อย่างใดอย่างหนึ่งในสองอย่าง ไม่ว่าระบบจะทำงานตามที่ทำนายและความมั่นใจของคุณได้มาอย่างสมควร หรือไม่เป็นเช่นนั้นและคุณพบจุดอ่อนจริงในราคาถูก ตามเงื่อนไขของคุณ โดยมีวิศวกรเฝ้าดูอยู่

### ฉีดความผิดพลาดที่สมจริง ไม่ใช่แบบสุ่ม

ความผิดพลาดที่คุณใส่ควรสะท้อนความล้มเหลวที่ระบบของคุณเจอจริง [การฉีดความผิดพลาด](https://en.wikipedia.org/wiki/Fault_injection) (fault injection) คือการจงใจใส่ข้อผิดพลาดเพื่อทดสอบว่าระบบตอบสนองอย่างไร ให้เมนูที่ดึงมาจากเหตุการณ์ production จริง ฉีดความหน่วงเพื่อจำลองการพึ่งพาที่ช้าหรือลิงก์เครือข่ายที่อิ่มตัว ฉีดข้อผิดพลาด เช่นคืนค่า HTTP 500 หรือปฏิเสธการเชื่อมต่อ เพื่อจำลองบริการปลายทางที่กำลังล้มเหลว ฉีดการใช้ทรัพยากรจนหมดโดยกินซีพียู หน่วยความจำ ดิสก์ หรือ file descriptor เพื่อดูว่าระบบเสื่อมสภาพอย่างไรภายใต้แรงกดดัน ฉีดความล้มเหลวของการพึ่งพาโดยทำให้ฐานข้อมูล แคช คิว หรือ API ของบุคคลที่สามทั้งตัวเข้าถึงไม่ได้ ใน[ระบบกระจาย](https://en.wikipedia.org/wiki/Distributed_computing) ซึ่งส่วนประกอบรันบนเครื่องแยกกันและสื่อสารผ่านเครือข่ายที่ไว้ใจไม่ได้ นี่คือความล้มเหลวที่ครอบงำเหตุล่มจริง ความหน่วงและความล้มเหลวบางส่วน ไม่ใช่การพังแบบสะอาด ๆ คือสิ่งที่ทำให้ระบบพังในทางปฏิบัติ จึงควรถ่วงน้ำหนักการทดลองไปที่ช่วงกลางที่ยุ่งเหยิง

### ตรวจสอบว่ากลไกความทนทานของคุณทำงานจริง

ตรงนี้คือที่ที่วิศวกรรมความโกลาหลคุ้มค่า ระบบของคุณเต็มไปด้วยกลไกที่ควรปกป้องคุณ เช่น ค่าหมดเวลาที่กันไม่ให้ผู้เรียกรอตลอดไป การลองใหม่ที่ปิดบังอาการสะดุดชั่วคราว [เซอร์กิตเบรกเกอร์](https://en.wikipedia.org/wiki/Circuit_breaker_design_pattern) (circuit breaker) ที่หยุดการรัวใส่การพึ่งพาที่กำลังล้มเหลว และ[การสลับระบบสำรอง](https://en.wikipedia.org/wiki/Failover) (failover) ที่เปลี่ยนไปใช้สแตนด์บายเมื่อตัวหลักตาย รูปแบบเหล่านี้ซึ่งกล่าวถึงในบทที่ 3.5 คือความต่างระหว่างปัญหาที่ถูกจำกัดกับการล่มแบบลูกโซ่ ปัญหาคือมันแทบไม่เคยถูกทดสอบภายใต้เงื่อนไขที่มันมีไว้รับมือ ค่าหมดเวลา 30 วินาทีในขณะที่เส้นตายของผู้เรียกเองคือ 2 วินาทีไม่ได้ช่วยอะไร การลองใหม่ที่ไม่มี backoff เปลี่ยนบริการที่กำลังดิ้นรนหนึ่งตัวให้กลายเป็นฝูงสัตว์วิ่งชน (thundering herd) เซอร์กิตเบรกเกอร์ที่ไม่เคยถูกใช้อาจตั้งค่าผิดจนไม่ทริปเลย หรือทริปตลอดเวลา การทดลองความโกลาหลคือวิธียืนยันว่าแต่ละกลไกทำงานตามที่ออกแบบเมื่อความผิดพลาดที่มันเฝ้าระวังมาถึงจริง ให้สมมติว่ากลไกความปลอดภัยทุกตัวที่ไม่เคยทดสอบนั้นพังอยู่ จนกว่าการทดลองจะพิสูจน์เป็นอย่างอื่น

### เริ่มด้วยเกมเดย์ก่อนทำให้เป็นอัตโนมัติ

อย่าเริ่มด้วยแพลตฟอร์มอัตโนมัติที่ฉีดความผิดพลาดต่อเนื่อง ให้เริ่มด้วยเกมเดย์ (game day) คือการซ้อมภาคปฏิบัติตามกำหนดที่ทีมมารวมกัน เลือกสถานการณ์ ฉีดความผิดพลาดในสภาพแวดล้อมที่ควบคุมได้ และดูผลไปด้วยกัน ก่อนหน้านั้นอีกขั้น การซ้อมบนโต๊ะ (tabletop exercise) ซึ่งคุยสถานการณ์กันบนไวต์บอร์ดโดยไม่แตะระบบเลย จะเผยช่องโหว่ของคู่มือปฏิบัติการ การแจ้งเตือน และความเป็นเจ้าของ โดยแทบไม่มีความเสี่ยง เกมเดย์คือทางขึ้นของคุณ มันสร้างกล้ามเนื้อของการตั้งสมมติฐาน การจำกัดรัศมีผลกระทบ และการอ่านระบบภายใต้ความเครียด และสร้างความไว้วางใจจากผู้บริหารและทีมข้างเคียง ซึ่งคุณต้องมีก่อนที่ใครจะยอมให้คุณรันการทดลองใน production มันยังเสริมการรับมือเหตุการณ์โดยตรง เพราะทักษะเหมือนกับที่วิศวกรเข้าเวรใช้ระหว่างเหตุการณ์จริง (บทที่ 9.3) ให้รันเกมเดย์แรก ๆ ใน staging จากนั้นใน production ช่วงเวลาเงียบด้วยรัศมีผลกระทบเล็ก แล้วค่อยขยาย

### จำกัดรัศมีผลกระทบอย่างตั้งใจ

แนวปฏิบัติด้านความปลอดภัยที่สำคัญที่สุดข้อเดียวคือการจำกัดความเสียหายที่อาจเกิดจากทุกการทดลอง ให้เริ่มจากขอบเขตเล็กที่สุดที่ยังสอนอะไรคุณได้ คือหนึ่งอินสแตนซ์ ทราฟฟิกหนึ่งเปอร์เซ็นต์ การพึ่งพาที่ไม่สำคัญหนึ่งตัว หนึ่งโซนความพร้อมใช้งาน กำหนดเงื่อนไขการยกเลิกก่อนเริ่ม ผูกเข้ากับเมตริกสถานะปกติของคุณ และทำให้การหยุดการทดลองเป็นการกระทำเดียวที่ใครก็ตามที่เฝ้าดูอยู่สั่งได้ ควรรันในเวลาทำการเมื่อทีมตื่นตัวและมีกำลังคน ไม่ใช่ข้ามคืนที่ความแปลกใจกลายเป็นเหตุการณ์โดยไม่มีใครเฝ้า ให้ขยายรัศมีผลกระทบก็ต่อเมื่อการทดลองที่เล็กกว่าผ่านไปอย่างสะอาดและความมั่นใจสูงขึ้นจริง วินัยของการจำกัดคือสิ่งที่แยกวิศวกรรมความโกลาหลออกจากการล่มที่คุณก่อเอง

### เติบโตสู่การตรวจสอบความทนทานแบบอัตโนมัติและต่อเนื่อง

เกมเดย์เป็นครั้งคราวช่วยหาจุดอ่อน แต่ระบบเปลี่ยนทุกวัน และการแก้ไขเมื่อไตรมาสก่อนอาจเสื่อมกลับมาอย่างเงียบ ๆ สภาพปลายทางที่เติบโตเต็มที่คือการตรวจสอบต่อเนื่อง คือชุดการทดลองความทนทานที่คัดสรรแล้วซึ่งรันอัตโนมัติในไปป์ไลน์หรือตามตารางเวลา เพื่อให้การเสื่อมของค่าหมดเวลา นโยบายลองใหม่ หรือเส้นทางสลับระบบถูกจับได้ภายในไม่กี่วัน แทนที่จะเจอระหว่างเหตุล่มจริงครั้งถัดไป นี่คือที่ที่เครื่องมืออย่าง [Chaos Monkey](https://en.wikipedia.org/wiki/Chaos_Monkey) ของ Netflix ซึ่งสุ่มปิดอินสแตนซ์ใน production เพื่อบังคับให้วิศวกรสร้างบริการที่ทนการสูญเสียอินสแตนซ์ได้ สร้างชื่อเสียงขึ้นมา ให้ทำเป็นอัตโนมัติเฉพาะการทดลองที่คุณเข้าใจและไว้ใจแล้วจากการรันด้วยมือ ความโกลาหลต่อเนื่องบนระบบที่ยังไม่โตเป็นวิธีสร้างเหตุการณ์ ไม่ใช่สร้างความมั่นใจ

### เชื่อมการทดลองเข้ากับการกู้คืนจากภัยพิบัติและการเรียนรู้จากเหตุการณ์

วิศวกรรมความโกลาหลไม่ได้อยู่โดดเดี่ยว สถานการณ์ที่ใหญ่กว่าและเกิดยากกว่า เช่น สูญเสียทั้งภูมิภาค การสลับฐานข้อมูล การกู้คืนจากข้อมูลสำรอง เป็นเรื่องของการทดสอบการกู้คืนจากภัยพิบัติ (บทที่ 9.5) และเกมเดย์มักเป็นพาหนะที่ดีที่สุดในการซ้อมแผนเหล่านั้น แทนที่จะปล่อยให้เป็นเอกสารที่ไม่เคยทดสอบแล้วเน่าไป ในอีกด้านหนึ่ง ทุกการทดลองที่เผยจุดอ่อนควรเข้าสู่วงจรการเรียนรู้เดียวกับเหตุการณ์จริง (บทที่ 9.3) คือบันทึกสรุปแบบไม่กล่าวโทษ การแก้ไขที่ติดตามได้ และการทดลองติดตามผลเพื่อยืนยันว่าการแก้ไขยังใช้ได้ เมื่อสิ่งที่พบจากความโกลาหล การซ้อมกู้คืนจากภัยพิบัติ และการทบทวนเหตุการณ์ ไหลเข้าสู่แบ็กล็อกงานความทนทานก้อนเดียว คุณจะได้ผลตอบแทนทบต้น แทนที่จะได้การซ้อมแยกส่วนครั้งเดียวจบ

## ข้อดีข้อเสียและการแลกเปลี่ยน

| การตัดสินใจ | ข้อดี | ข้อเสีย |
|---|---|---|
| ทดสอบใน production | ทราฟฟิก ข้อมูล และขนาดจริง สิ่งที่พบเป็นจริง | เสี่ยงต่อผู้ใช้หากการจำกัดล้มเหลว ต้องมีความเป็นผู้ใหญ่ |
| ทดสอบเฉพาะใน staging | ปลอดภัย เดิมพันต่ำ เริ่มง่าย | พลาดพฤติกรรมโลกจริง ความมั่นใจลวง |
| เกมเดย์ด้วยมือ | สร้างทักษะและความไว้วางใจ ต้นทุนเครื่องมือต่ำ | ไม่บ่อย สิ่งที่พบอาจเสื่อมโดยไม่มีใครสังเกต |
| ความโกลาหลอัตโนมัติต่อเนื่อง | จับการเสื่อมได้เร็ว ขยายขนาดได้ | ต้องมีเครื่องมือและความสามารถในการสังเกตระบบที่เติบโตก่อน |
| รัศมีผลกระทบกว้าง | เผยจุดอ่อนเชิงระบบขนาดใหญ่ | เสี่ยงสูง ความผิดพลาดกลายเป็นเหตุการณ์ |
| รัศมีผลกระทบแคบ | ปลอดภัยและควบคุมได้ | อาจพลาดความล้มเหลวข้ามบริการที่ผุดขึ้นเอง |

ความตึงเครียดหลักคือระหว่างความสมจริงกับความปลอดภัย สิ่งที่คุณอยากพบที่สุดมาจาก production เพราะเป็นที่เดียวที่ระบบเจอทราฟฟิกจริง ข้อมูลจริง และขนาดจริง แต่ production ก็คือที่ที่การทดลองที่พลาดทำร้ายผู้ใช้ ทางออกไม่ใช่การเลือกข้างใดข้างหนึ่ง แต่คือการค่อย ๆ สร้างสิทธิ์สู่ production คือพิสูจน์ข้อกำหนดเบื้องต้น ซ้อมใน staging แล้วรันการทดลองเล็ก ๆ ที่จำกัดอย่างดีใน production โดยผูกเงื่อนไขยกเลิกกับเมตริกสด และขยายขอบเขตเมื่อหลักฐานสะสมเท่านั้น ความตึงเครียดที่เกิดซ้ำอีกอย่างคือแบบทำมือกับแบบอัตโนมัติ ซึ่งคลี่คลายด้วยวิธีเดียวกันเมื่อเวลาผ่านไป คือเริ่มด้วยมือเพื่อสร้างความเข้าใจและความไว้วางใจ แล้วทำการทดลองที่คุณพึ่งพาให้เป็นอัตโนมัติ เพื่อให้ความทนทานที่เคยตรวจสอบแล้วยังคงได้รับการตรวจสอบอยู่

## คำถามที่ควรคุยกับทีม

1. **เราพร้อมจะรันการทดลองความโกลาหลจริงหรือไม่ และเราจะรู้ได้อย่างไร?** ความอยากเริ่มฉีดความผิดพลาดเพราะฟังดูล้ำสมัยนั้นล่อใจ แต่วิศวกรรมความโกลาหลบนระบบที่สังเกตไม่ได้ ไม่มีนิยามสุขภาพที่ชัดเจน และไม่มีการย้อนกลับที่เร็ว ก็เป็นแค่การล่มที่ก่อเอง ให้นำหลักฐานที่ซื่อตรงมาในการคุยครั้งนี้ คุณเห็นอัตราคำขอสำเร็จและความหน่วงแบบเรียลไทม์ไหม มีนิยามสถานะปกติที่ตกลงกันหรือยัง และยกเลิกการทดลองแล้วกู้คืนได้ในไม่กี่วินาทีหรือไม่ สำหรับทีมใหญ่ คำตอบมักต่างกันตามบริการ ผลลัพธ์ที่มีประโยชน์จึงเป็นเกณฑ์ความพร้อมที่บริการต้องผ่านก่อนมีสิทธิ์ทดลอง ในสภาพแวดล้อมที่มีกฎระเบียบ เกณฑ์ความพร้อมนี้ยังเป็นมาตรการควบคุมที่แสดงต่อผู้ตรวจสอบได้ ถ้าคำตอบที่ซื่อตรงคือยังไม่พร้อม งานความโกลาหลที่มีค่าที่สุดที่ทำได้ในไตรมาสนี้คือการสร้างความสามารถด้านการสังเกตระบบและการย้อนกลับที่ทำให้คุณพร้อม

2. **นโยบายรัศมีผลกระทบของเราคืออะไร และใครมีอำนาจหยุดการทดลอง?** ทุกการทดลองความโกลาหลมีความเสี่ยงต่อผู้ใช้จริงอยู่บ้าง และความต่างระหว่างสิ่งที่พบอันมีค่ากับเหตุการณ์ที่คุณก่อเองอยู่ที่ว่าจำกัดมันไว้แน่นแค่ไหน ให้คุยขีดจำกัดที่เป็นรูปธรรม คือทราฟฟิกสัดส่วนเท่าไร กี่อินสแตนซ์ สภาพแวดล้อมไหน ช่วงเวลาไหนของวัน และเกณฑ์เมตริกใดที่ยกเลิกการรันอัตโนมัติ ตัดสินใจล่วงหน้าว่าใครเฝ้าแต่ละการทดลองและใครถือสวิตช์ฆ่าแบบการกระทำเดียว เพราะการทดลองที่ไม่มีใครหยุดได้เร็วก็ไม่ได้ถูกจำกัด สำหรับองค์กรใหญ่ นโยบายนี้คือสิ่งที่ทำให้หลายทีมทดลองได้โดยไม่มีทีมใดทำการพึ่งพาที่ใช้ร่วมกันล่มโดยบังเอิญ คำตอบควรถูกเขียนไว้ ตกลงกับทีมที่บริการของคุณอาจกระทบ และถือเป็นเงื่อนไขก่อนรันอะไรใน production

3. **กลไกความทนทานตัวไหนที่เราเชื่อว่าปกป้องเรา และเราเคยทดสอบมันจริงหรือไม่?** ระบบส่วนใหญ่เต็มไปด้วยค่าหมดเวลา การลองใหม่ เซอร์กิตเบรกเกอร์ แคช และเส้นทางสลับระบบ ที่ตั้งค่าไว้ครั้งเดียวและไม่เคยถูกใช้ภายใต้ความล้มเหลวที่มันมีไว้รับมือ ให้ทำรายการกลไกที่คุณพึ่งพา แล้วถามเป็นรายตัวว่าครั้งสุดท้ายที่ตรวจสอบว่าทำงานได้ภายใต้ความผิดพลาดที่ฉีดจริงคือเมื่อไร ข้อพิจารณาที่ขัดกันคือเวลา การตรวจสอบแต่ละกลไกต้องใช้แรงวิศวกรรม และมีเดดไลน์ฟีเจอร์อยู่เสมอ ให้นำหลักฐานโต้แย้งข้อคัดค้านนั้นมา คือต้นทุนของเหตุล่มในอดีตที่เซอร์กิตเบรกเกอร์ที่ทำงานได้หรือค่าหมดเวลาที่ถูกต้องจะสกัดไว้ได้ คำตอบควรเปลี่ยนรายการการป้องกันที่สันนิษฐานไว้อย่างสบายใจให้เป็นแบ็กล็อกการทดลองที่จัดลำดับความสำคัญแล้ว เริ่มจากกลไกที่หากล้มเหลวจะเจ็บที่สุด

4. **อะไรต้องเป็นจริงก่อนที่เราจะรันการทดลองใน production แทน staging และบริการใดสมควรได้สิทธิ์นั้นแล้วในวันนี้?** สิ่งที่คุณอยากพบที่สุดมาจาก production เพราะเป็นที่เดียวที่ระบบพบทราฟฟิกจริง ข้อมูลจริง และขนาดจริง แต่ production ก็เป็นที่เดียวที่การทดลองที่พลาดทำร้ายผู้ใช้จริง สำหรับทีมใหญ่ ความจริงที่ซื่อตรงคือบริการต่าง ๆ อยู่ในระดับความพร้อมต่างกัน กฎเหมารวม "ห้ามความโกลาหลใน production" จึงทิ้งการเรียนรู้ที่ดีที่สุดของคุณ ส่วนกฎเหมารวม "ได้ทั้งหมด" เชิญชวนให้ล่มด้วยตัวเอง ให้นำหลักฐานเป็นรายบริการมา คือคุณภาพของการสังเกตระบบ ว่านิยามสถานะปกติและตั้งการแจ้งเตือนได้หรือยัง ย้อนกลับได้เร็วเพียงใด และประวัติการทดลองใน staging ที่สะอาดซึ่งพอจะเลื่อนระดับให้ได้ ในองค์กรใหญ่และภาครัฐ ให้ผูกประตู production เข้ากับมาตรการควบคุมที่บันทึกไว้ ซึ่งระบุว่าใครอนุมัติการเลื่อนระดับและเงื่อนไขยกเลิกใดผูกกับเมตริกสด เพื่อให้ผู้ตรวจสอบเห็นการตัดสินใจที่จงใจและมีหลักฐาน ไม่ใช่ทีมที่ด้นสดกับผู้ใช้จริง

5. **เมื่อการทดลองความโกลาหลเผยจุดอ่อน สิ่งที่พบนั้นไปที่ไหน และเราจะกันไม่ให้มันเน่าอยู่เฉย ๆ ได้อย่างไร?** โครงการที่ค้นพบจุดอ่อนแต่ไม่เคยแก้แย่กว่าไม่มีโครงการ เพราะมันเผาแรง กัดกร่อนความไว้วางใจ และสอนให้คนคิดว่าการทดลองเป็นละคร แรงกดดันที่ขัดกันคือแผนงานฟีเจอร์เสมอ การแก้เรื่องความทนทานแทบไม่รู้สึกเร่งด่วนเท่าการปล่อยรุ่นถัดไป จนกว่าการล่มที่มันจะป้องกันได้มาถึงจริง ให้นำสถานะปัจจุบันของแบ็กล็อกความทนทานมาคุยว่า สิ่งที่พบจากความโกลาหลเปิดค้างอยู่กี่รายการ รายการเก่าสุดอายุเท่าไร และสิ่งที่พบจากการทดลอง การซ้อมกู้คืนจากภัยพิบัติ และการทบทวนเหตุการณ์ ไหลเข้าคิวร่วมกันหรือกระจายอยู่ตามทีม ตกลงว่าใครเป็นเจ้าของการแก้แต่ละเรื่อง และใครรันการทดลองติดตามผลที่ยืนยันว่าการแก้ใช้ได้ สำหรับองค์กรใหญ่หรือมีกฎระเบียบ ให้ระบุเวทีที่ทบทวนแบ็กล็อกตามรอบเวลาคงที่และมีอำนาจจัดลำดับการแก้ความทนทานเหนือฟีเจอร์ เพราะสิ่งที่พบซึ่งไม่มีใครรับผิดชอบปิดคือความเสี่ยงที่คุณเพียงบันทึกไว้ ไม่ได้กำจัดออก

6. **เราพร้อมจะทำการทดลองใดให้เป็นอัตโนมัติสู่การตรวจสอบต่อเนื่องหรือยัง และเฉพาะเจาะจงคือตัวไหน?** เกมเดย์เป็นครั้งคราวช่วยหาจุดอ่อน แต่ระบบเปลี่ยนทุกวันและการแก้ของไตรมาสก่อนอาจเสื่อมอย่างเงียบ ๆ สภาพปลายทางที่เติบโตเต็มที่จึงเป็นชุดการทดลองที่คัดสรรซึ่งรันอัตโนมัติและจับการเสื่อมได้ภายในไม่กี่วัน อันตรายคือการทำอัตโนมัติเร็วเกินไป ความโกลาหลต่อเนื่องที่ซ้อนบนระบบที่ยังไม่โตและสังเกตได้ไม่ดีสร้างเหตุการณ์เร็วกว่าความเข้าใจ ให้นำรายการการทดลองที่คุณรันด้วยมือมากพอจนไว้ใจได้เต็มที่ มาตรการควบคุมรัศมีผลกระทบและเงื่อนไขยกเลิกที่จะกำกับมันเมื่อไม่มีคนเฝ้า และการเฝ้าติดตามที่จะจับการรันอัตโนมัติที่ผิดพลาดตอนตีสามเมื่อไม่มีใครดูอยู่ สำหรับองค์กรใหญ่หรือหน่วยงานรัฐ ให้ชั่งการตรวจสอบเพิ่มเติมที่การฉีดความผิดพลาดโดยไม่มีคนเฝ้าเชิญมา ได้แก่ การอนุมัติจัดการการเปลี่ยนแปลง ร่องรอยการตรวจสอบที่ทุกการรันอัตโนมัติต้องทิ้งไว้ และความรับผิดชอบที่ชัดเจนเมื่อการทดลองตามตารางไปตรงกับเหตุการณ์จริง ให้ทำอัตโนมัติเฉพาะการทดลองที่คุณเข้าใจแล้ว และคงที่เหลือเป็นแบบทำมือจนกว่าจะได้รับความไว้วางใจเท่ากัน

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ความเร็วและการอยู่รอดมาก่อน จึงไม่ต้องใช้เงินกับแพลตฟอร์มความโกลาหล ให้รันเกมเดย์เก้าสิบนาทีครั้งเดียวใน staging กับการพึ่งพาตัวเดียวที่หากล้มเหลวจะฆ่าคุณได้จริง มักเป็นการชำระเงิน การยืนยันตัวตน หรือที่เก็บข้อมูลหลัก ฉีดความล้มเหลวด้วยพร็อกซีง่าย ๆ หรือฆ่าโปรเซส ดูว่าอะไรพัง แก้ค่าหมดเวลาหรือทางสำรองที่ขาดไป แล้วเดินหน้าต่อ จุดประสงค์ทั้งหมดคือจับการล่มที่ก่อเองอย่างชัดเจนในราคาถูกก่อนลูกค้าเจอ ไม่ใช่สร้างวินัยที่คุณไม่มีคนดูแล

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญด้านความน่าเชื่อถือและงบจำกัด ให้มองการทดสอบความทนทานเป็นการซ้อมเป็นระยะอย่างตั้งใจ ไม่ใช่โครงการที่ต้องจัดคนดูแล พึ่งพาฟีเจอร์ฉีดความล้มเหลวที่ผู้ให้บริการคลาวด์หรือเครื่องมือแบบจัดการให้ของคุณมีอยู่แล้ว แทนการซื้อแพลตฟอร์มเฉพาะ และเน้นการทดลองที่การพึ่งพาไม่กี่ตัวที่ลูกค้าจะสังเกตเห็น ให้มองเป็นการประกัน การใช้เวลาบ่ายหนึ่งยืนยันว่าข้อมูลสำรองกู้คืนได้และการชำระเงินเสื่อมระดับอย่างนุ่มนวล ถูกกว่าเหตุล่มที่พิสูจน์ว่าไม่ได้มาก

**องค์กรขนาดใหญ่.** ปัญหาคือการประสานหลายทีมกับการพึ่งพาที่ใช้ร่วมกันในระดับใหญ่ จึงควรกำหนดมาตรฐานเกณฑ์ความพร้อม นโยบายรัศมีผลกระทบ และการเชื่อมเงื่อนไขยกเลิกที่ทุกทีมต้องผ่านก่อนรันใน production ส่งสิ่งที่พบจากความโกลาหล การซ้อมกู้คืนจากภัยพิบัติ และการทบทวนเหตุการณ์ เข้าแบ็กล็อกความทนทานเดียวที่มีเจ้าของชัดเจน และใช้เกมเดย์รายไตรมาสพร้อมชุดการทดลองอัตโนมัติที่คัดสรรเพื่อตอบความคาดหวังด้านความทนทานเชิงปฏิบัติการด้วยหลักฐาน ควบคุมว่าใครกระทบบริการที่ใช้ร่วมกันได้ เพื่อไม่ให้การทดลองของทีมใดทีมหนึ่งทำให้โครงสร้างพื้นฐานที่ทีมอื่นพึ่งพาล่ม

**ภาครัฐ.** กฎการจัดซื้อ ความโปร่งใส และความรับผิดชอบต่อสาธารณะหล่อหลอมงานนี้ ข้อบังคับความต่อเนื่องของการปฏิบัติงานมักกำหนดให้ซ้อมสม่ำเสมออยู่แล้ว จึงควรรันเป็นเกมเดย์จริงที่ให้ผลการค้นพบที่แท้ ไม่ใช่แฟ้มที่ไม่มีใครเปิด และเก็บร่องรอยการตรวจสอบของทุกการทดลอง รัศมีผลกระทบ และผลลัพธ์ เมื่อจัดซื้อเครื่องมือฉีดความผิดพลาด ให้เรียกร้องว่าต้องอยู่ในกฎความปลอดภัยและการจัดการข้อมูล และสงวนการทดลองใน production บนบริการที่ให้ประชาชนไว้สำหรับช่วงเวลาที่ได้รับอนุมัติและจำกัดแน่นหนา หลักฐานที่โครงการความโกลาหลสร้างขึ้นคือสิ่งที่หน่วยกำกับดูแลหรือผู้ตรวจสอบคาดหวังจะเห็นพอดี

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสิบห้าคนรันเว็บแอปบนบริการไม่กี่ตัวและพึ่ง API ชำระเงินของบุคคลที่สาม ไม่มีใครมีเวลาทำแพลตฟอร์มความโกลาหล ทีมจึงรันเกมเดย์เก้าสิบนาทีใน staging พวกเขาตั้งสมมติฐานว่า ถ้า API ชำระเงินเริ่มคืนข้อผิดพลาด หน้าชำระเงินควรแสดงข้อความให้ลองใหม่ที่ชัดเจนและเข้าคิวคำสั่งซื้อไว้แทนที่จะพัง พวกเขาฉีดการตอบกลับ 500 ด้วยพร็อกซีง่าย ๆ และพบว่าส่วนหน้าค้างตลอดไปเพราะการเรียกฝั่งไคลเอนต์ไม่มีค่าหมดเวลา พวกเขาเพิ่มค่าหมดเวลาและทางสำรองที่เป็นมิตร รันการทดลองซ้ำเพื่อยืนยันการแก้ และเขียนบันทึกสองย่อหน้าในเอกสารร่วม ต้นทุนรวมคือบ่ายหนึ่งกับบั๊กจริงหนึ่งตัวที่จับได้ก่อนลูกค้าเจอ

**องค์กรขนาดใหญ่.** ธนาคารระดับโลกต้องแสดงความทนทานเชิงปฏิบัติการต่อหน่วยกำกับดูแลกับสถานการณ์ที่รุนแรงแต่เป็นไปได้ ทีมความน่าเชื่อถือของธนาคารดำเนินโครงการเกมเดย์รายไตรมาสพร้อมชุดการทดลองอัตโนมัติใน production หนึ่งสถานการณ์สลับฐานข้อมูลธุรกรรมหลักไปยังสแตนด์บายในช่วงทราฟฟิกต่ำ ด้วยรัศมีผลกระทบที่จำกัดอย่างเข้มงวดและเงื่อนไขยกเลิกผูกกับอัตราความสำเร็จของธุรกรรม การรันครั้งแรกเผยว่าบริการกระทบยอดปลายทางมีนโยบายลองใหม่ที่ไม่มี backoff ทำให้โหลดพุ่งจนการกู้คืนล่าช้าเกินเป้าหมายเวลากู้คืนในแผนกู้คืนจากภัยพิบัติ (บทที่ 9.5) ไปมาก สิ่งที่พบถูกใส่ในแบ็กล็อกเดียวกับการทบทวนเหตุการณ์ นโยบายลองใหม่ได้รับการแก้ด้วย exponential backoff และการทดลองติดตามผลยืนยันว่าการสลับระบบเสร็จภายในเป้าหมายแล้ว ทั้งหมดนี้กลายเป็นหลักฐานให้หน่วยกำกับดูแล

**ภาครัฐ.** หน่วยงานระดับชาติที่ดูแลพอร์ทัลสวัสดิการสำหรับประชาชนต้องรักษาความต่อเนื่องของการปฏิบัติงานผ่านการหยุดชะงัก แทนที่จะมองแผนความต่อเนื่องเป็นแฟ้มที่ไม่มีใครเปิด หน่วยงานจัดการซ้อมความต่อเนื่องประจำปีเป็นเกมเดย์จริง ทีมจำลองการสูญเสียศูนย์ข้อมูลหลักและเดินการสลับไปยังไซต์รอง พร้อมกับฉีดความหน่วงเข้าไปในการพึ่งพาการยืนยันตัวตนแยกต่างหาก เพื่อดูว่าพอร์ทัลเสื่อมระดับอย่างนุ่มนวลหรือไม่ พวกเขาพบว่าช่องว่างด้านการเฝ้าติดตามที่ไม่เคยทดสอบทำให้ทีมเข้าเวรมองไม่เห็นว่าบริการยืนยันตัวตนช้าลง การแจ้งเตือนจึงดังช้า หน่วยงานปิดช่องว่างด้านการสังเกตระบบ ปรับปรุงคู่มือปฏิบัติการ และกำหนดการซ้อมเดียวกันในปีหน้า เปลี่ยนข้อกำหนดด้านการปฏิบัติตามข้อกำหนดให้เป็นความทนทานที่ทดสอบแล้วจริงสำหรับบริการสาธารณะที่สำคัญ

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ผลตอบแทนของวิศวกรรมความโกลาหลมาจากการล่มที่ไม่เคยเกิดขึ้น เหตุล่มใหญ่ครั้งเดียวของบริการขนาดใหญ่อาจมีต้นทุนตั้งแต่หลายหมื่นไปถึงหลายล้านจากรายได้ที่เสียไป ค่าปรับตามกฎระเบียบ แรงงานแก้ไข และความเสียหายต่อชื่อเสียงที่ค้างอยู่นานหลังบริการกลับมา การทดลองความโกลาหลเปลี่ยนความแปลกใจที่คาดเดาไม่ได้และแพงเหล่านั้นให้เป็นสิ่งที่พบตามกำหนดในราคาถูก ที่คุณแก้ตามจังหวะของคุณเองโดยมีวิศวกรเฝ้าดูและมีการย้อนกลับพร้อม การพบค่าหมดเวลาที่พังระหว่างเกมเดย์ที่ควบคุมได้มีต้นทุนบ่ายหนึ่ง การพบมันระหว่างเหตุการณ์จริงมีต้นทุนเป็นเหตุล่ม การระดมคนทั้งทีม และความไว้วางใจของผู้ใช้ ตัวเลขเข้าข้างเกมเดย์อย่างห่างลิบ

ต้นทุนรวมตลอดอายุการใช้งานอยู่ในระดับพอประมาณเมื่อข้อกำหนดเบื้องต้นพร้อมแล้ว เพราะวิศวกรรมความโกลาหลใช้การลงทุนด้านการสังเกตระบบ การแจ้งเตือน และการย้อนกลับที่คุณต้องมีอยู่แล้ว ต้นทุนที่ซื่อตรงคือเวลาวิศวกรในการรันการทดลอง เครื่องมือบางอย่างสำหรับฉีดความผิดพลาดและจำกัดรัศมีผลกระทบ และงานด้านวัฒนธรรมในการทำให้ผู้บริหารสบายใจกับการจงใจใส่ความล้มเหลว ข้อหลังคืออุปสรรคจริง และทางผ่านคือเริ่มใน staging แสดงสิ่งที่พบซึ่งเชื่อมกับเงินหรือความเสี่ยง และให้การทดลองใน production ที่จำกัดดีไม่กี่ครั้งสร้างความไว้วางใจ เมื่อจะเสนอต่อผู้บริหาร ให้วางกรอบวิศวกรรมความโกลาหลเป็นการประกันที่วัดได้ คือนำเสนอต้นทุนของเหตุการณ์ล่าสุด แสดงว่าเหตุการณ์ใดที่การทดลองความทนทานจะจับได้ และเสนอโครงการที่เริ่มเล็กและขยายเมื่อพิสูจน์ตัวเองเท่านั้น ในสภาพแวดล้อมที่มีกฎระเบียบและภาครัฐ ให้เพิ่มมุมการปฏิบัติตามข้อกำหนด เพราะการทดสอบความทนทานเชิงปฏิบัติการและการซ้อมความต่อเนื่องถูกคาดหวังมากขึ้นเรื่อย ๆ และโครงการความโกลาหลคือวิธีตอบความคาดหวังนั้นด้วยหลักฐานแทนเอกสาร

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **ความโกลาหลโดยไม่มีการสังเกตระบบ** การฉีดความผิดพลาดเข้าระบบที่มองไม่เห็นคือการเดาที่มีขั้นตอนเพิ่ม คุณจะก่อความเสียหายและไม่ได้เรียนรู้อะไร
- **ไม่มีนิยามสถานะปกติ** ถ้าไม่มีตัวชี้วัดสุขภาพที่ตกลงกัน คุณแยกไม่ออกว่าการทดลองเผยปัญหาหรือก่อปัญหา
- **ไม่มีสมมติฐาน** การทุบของพังแบบสุ่มไม่ใช่วิศวกรรมความโกลาหล แต่เป็นการทำลายข้าวของที่มีชื่อโก้และไม่มีสิ่งที่พบ
- **รัศมีผลกระทบที่ไม่ถูกจำกัด** การข้ามการทดลองเล็กที่ปลอดภัยแล้วไปล้มทั้ง production เปลี่ยนการทดสอบเป็นการล่มที่ก่อเอง
- **ไม่มีเส้นทางยกเลิก** การทดลองที่หยุดทันทีไม่ได้ไม่ใช่การทดลอง แต่เป็นเหตุการณ์ที่รอตัวกระตุ้น
- **ทำให้เป็นอัตโนมัติเร็วเกินไป** ความโกลาหลต่อเนื่องบนระบบที่ยังไม่โตสร้างเหตุการณ์เร็วกว่าความเข้าใจ
- **สิ่งที่พบที่ไม่ไปไหน** การค้นพบจุดอ่อนแล้วไม่แก้เลยทำให้การซ้อมเสียเปล่าและกัดกร่อนความไว้วางใจต่อทั้งโครงการ
- **โทษหลังการทดลองที่พลาด** การลงโทษวิศวกรที่รันการทดลองซึ่งเผยข้อบกพร่องจริง รับประกันว่าไม่มีใครรันการทดลองครั้งถัดไป

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** ความทนทานเป็นสิ่งที่สันนิษฐาน ไม่ได้ทดสอบ ความล้มเหลวถูกค้นพบใน production ระหว่างเหตุการณ์จริง ไม่มีเกมเดย์ ไม่มีการฉีดความผิดพลาด และมักไม่มีนิยามชัดเจนว่าสุขภาพดีหน้าตาเป็นอย่างไร ทีมเรียนรู้จุดอ่อนของตัวเองอย่างยากลำบาก ทีละเหตุล่ม
- **ระดับ 2 พัฒนา:** ทีมรันเกมเดย์เป็นครั้งคราว มักใน staging พร้อมสถานการณ์ที่กำหนดและมีสมมติฐาน นิยามสถานะปกติสำหรับบริการหลักไม่กี่ตัวและมีการสังเกตระบบพื้นฐาน สิ่งที่พบถูกบันทึกและแก้ไปบ้าง แต่แนวปฏิบัติไม่สม่ำเสมอข้ามทีมและขึ้นกับผู้นำรายบุคคล ไม่ใช่วิธีการที่ตั้งมั่น
- **ระดับ 3 สร้างมาตรฐาน:** การทดลองความโกลาหลเป็นแนวปฏิบัติที่บันทึกไว้ทั่วองค์กร พร้อมนโยบายรัศมีผลกระทบ เงื่อนไขยกเลิก และเกณฑ์ความพร้อมที่บริการต้องผ่านก่อนทดลองใน production ที่บังคับใช้ การทดลองรันใน production ภายใต้เงื่อนไขที่ควบคุม สิ่งที่พบไหลเข้าแบ็กล็อกความทนทานร่วมกับการทบทวนเหตุการณ์และการซ้อมกู้คืนจากภัยพิบัติ และกลไกความทนทานถูกตรวจสอบแทนที่จะสันนิษฐาน ทุกทีมทำตามคู่มือเดียวกัน
- **ระดับ 4 บริหารจัดการ:** โครงการถูกวัดและควบคุมด้วยข้อมูลเทียบกับค่าฐาน คุณติดตามความครอบคลุมด้านความทนทาน (บริการสำคัญและกลไกใด เช่น ค่าหมดเวลา การลองใหม่ เซอร์กิตเบรกเกอร์ และการสลับระบบ ที่ตรวจสอบภายใต้ความผิดพลาดที่ฉีดจริงแล้ว และล่าสุดเมื่อไร) อัตราที่การทดลองเผยสิ่งที่พบ เวลาเฉลี่ยในการปิดสิ่งที่พบด้านความทนทาน และความถี่ที่กลไกที่เคยตรวจสอบแล้วเสื่อมกลับ ตัวชี้วัดเหล่านี้ถูกทบทวนตามรอบคงที่ การเลื่อนระดับสู่ production ใช้หลักฐานเป็นเกณฑ์แทนความเห็น และการทดลองถูกจัดลำดับตามความเสี่ยงที่วัดได้ของกลไกที่ยังไม่ได้ตรวจสอบ
- **ระดับ 5 ประสานทั้งระบบ:** ชุดการทดลองที่คัดสรรรันอัตโนมัติอย่างต่อเนื่อง จับการเสื่อมได้ภายในไม่กี่วัน และโครงการปรับตัวเมื่อระบบและภาพความเสี่ยงเปลี่ยน วิศวกรรมความโกลาหลผสานทั่วองค์กรกับไปป์ไลน์การส่งมอบ การเรียนรู้จากเหตุการณ์ และการทดสอบการกู้คืนจากภัยพิบัติ เพื่อให้บริการใหม่สืบทอดการตรวจสอบความทนทานโดยปริยาย ความทนทานเป็นคุณสมบัติของระบบที่ได้รับการตรวจสอบอย่างต่อเนื่อง และผู้บริหารถือว่าโครงการเป็นการบริหารความเสี่ยงมาตรฐานที่ปรับปรุงตามหลักฐาน ไม่ใช่โครงการพิเศษ

## ประเด็นชวนคุย

1. คุณตัดสินอย่างไรว่าบริการใดในองค์กรสมควรได้รันการทดลองความโกลาหลใน production เป็นอันดับแรก และอะไรต้องเป็นจริงก่อนที่มันจะได้สิทธิ์นั้น?
2. เมื่อการทดลองความโกลาหลเผยจุดอ่อนร้ายแรง ใครเป็นเจ้าของการแก้ และคุณกันไม่ให้สิ่งที่พบนั้นนอนนิ่งอยู่ในแบ็กล็อกได้อย่างไร?
3. เส้นแบ่งระหว่างการทดลองความโกลาหล การซ้อมกู้คืนจากภัยพิบัติ และเกมเดย์ในบริบทของคุณอยู่ตรงไหน และความต่างนั้นสำคัญต่อวิธีที่คุณวางแผนมันหรือไม่?
4. คุณจะโน้มน้าวผู้บริหารที่สงสัยได้อย่างไรว่าการจงใจฉีดความล้มเหลวเข้า production ปลอดภัยกว่าสถานะเดิมที่รอเหตุล่มจริง?
5. การทดลองแรกที่เล็กที่สุดและมีค่าที่สุดที่ทีมของคุณรันได้เดือนหน้าคืออะไร และอะไรจะขวางไม่ให้คุณรัน?
6. การทดสอบความทนทานควรต่างกันอย่างไรระหว่างบริการสาธารณะที่ให้ประชาชนซึ่งมีข้อบังคับความต่อเนื่อง กับเครื่องมือภายในองค์กรที่มีผู้ใช้น้อย?

## ข้อสรุปสำคัญ

- วิศวกรรมความโกลาหลคือการทดลองอย่างมีวินัยที่ขับเคลื่อนด้วยสมมติฐานเพื่อสร้างความมั่นใจในความทนทาน ไม่ใช่การทำพังแบบสุ่ม
- สร้างการสังเกตระบบ นิยามสถานะปกติ และการย้อนกลับที่เร็วก่อนฉีดความผิดพลาดแม้แต่ครั้งเดียว
- ฉีดความผิดพลาดที่สมจริง (ความหน่วง ข้อผิดพลาด การใช้ทรัพยากรจนหมด ความล้มเหลวของการพึ่งพา) และใช้มันตรวจสอบว่าค่าหมดเวลา การลองใหม่ เซอร์กิตเบรกเกอร์ และการสลับระบบทำงานได้จริง
- เริ่มด้วยการซ้อมบนโต๊ะและเกมเดย์ จำกัดรัศมีผลกระทบอย่างตั้งใจ และสร้างสิทธิ์สู่ production และระบบอัตโนมัติทีละขั้น
- เชื่อมการทดลองเข้ากับการทดสอบการกู้คืนจากภัยพิบัติ (บทที่ 9.5) และการเรียนรู้จากเหตุการณ์ (บทที่ 9.3) เพื่อให้สิ่งที่พบทบรวมเป็นแบ็กล็อกความทนทานเดียว
- จัดการกับสิ่งที่พบแบบไม่กล่าวโทษและลงมือแก้ไข การทดลองที่บทเรียนไม่ถูกนำไปจัดการแย่กว่าไม่มีการทดลองเลย
