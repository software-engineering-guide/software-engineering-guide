# 2.20 การจัดการข้อผิดพลาด และ รูปแบบความทนทาน

## ภาพรวมและแรงจูงใจ

ทุกโปรแกรมที่คุณเขียนจะต้องมีวันล้มเหลว ดิสก์เต็ม เครือข่ายหลุด บริการหมดเวลา ผู้เรียกส่งข้อมูลขยะเข้ามา หรือไลบรารีที่พึ่งพาคืนค่าบางอย่างที่เอกสารไม่เคยพูดถึง คำถามไม่เคยเป็นว่าความล้มเหลวจะเกิดหรือไม่ แต่เป็นว่าโค้ดของคุณรับมือกับมันด้วยแผน หรือรับมือด้วยความตกใจ การจัดการข้อผิดพลาด (error handling) คืองานฝีมือในการตัดสินใจ ทีละบรรทัดและทีละฟังก์ชัน ว่าโค้ดจะทำอย่างไรเมื่อโลกไม่ให้ความร่วมมือ มันเป็นส่วนที่ไม่หวือหวาที่สุดของงานก่อสร้างซอฟต์แวร์ แต่เป็นส่วนที่ตัดสินได้มากกว่าฟีเจอร์ใดๆ ว่าผู้คนจะไว้วางใจระบบของคุณหรือไม่

บทนี้พูดถึงความทนทาน (resilience) ในระดับโค้ดและคอมโพเนนต์ คือการเลือกภายในฟังก์ชัน โมดูล หรือ API เป็นส่วนเสริมของบทที่ 3.5 ซึ่งว่าด้วยความทนทานในระดับระบบ (การกระจายโหลด การทำสำเนา การสลับระบบสำรองข้ามบริการ) บทที่ 3.5 ทำให้แพลตฟอร์มทั้งตัวยังยืนอยู่ได้เมื่อทั้งภูมิภาคดับ ส่วนบทนี้ทำให้คำขอเพียงหนึ่งรายการไม่ทำลายข้อมูลหรือหายไปโดยไม่เหลือร่องรอย ทั้งสองส่งเสริมกัน circuit breaker ในสถาปัตยกรรมแทบไม่มีความหมายถ้าโค้ดที่อยู่หลังมันกลืนข้อยกเว้นทิ้ง และฟังก์ชันที่ป้องกันตัวดีก็ช่วยคุณไม่ได้ถ้าระบบโดยรอบไม่มีความซ้ำซ้อน บทนี้ยังต่อยอดจากบทที่ 2.9 (การก่อสร้างซอฟต์แวร์) ที่การจัดการข้อผิดพลาดเป็นเพียงวินัยหนึ่งในหลายข้อ ส่วนที่นี่มันกลายเป็นหัวข้อหลักทั้งบท

สำหรับทีมขนาดใหญ่ สิ่งที่ควรได้มาคือความสม่ำเสมอ เมื่อวิศวกรหลายร้อยคนจัดการข้อผิดพลาดกันหลายร้อยแบบ ทุกบริการจะกลายเป็นปริศนา และทุกเหตุการณ์ขัดข้องจะกลายเป็นการขุดค้น ในองค์กรขนาดใหญ่ ความไม่สม่ำเสมอนี้ทำให้ต้นทุนของทุกการตรวจสอบและทุกการเชื่อมต่อสูงขึ้น ส่วนในภาครัฐและระบบที่เดิมพันสูง เดิมพันยิ่งชัดเจนกว่านั้น ความถูกต้อง การล้มเหลวอย่างปลอดภัย และร่องรอยการตรวจสอบที่ชัดเจนไม่ใช่ฟีเจอร์ที่ค่อยเพิ่มทีหลัง แต่เป็นคุณสมบัติที่ระบบต้องมีตั้งแต่คอมมิตแรก ระบบสวัสดิการที่คำนวณผิดโดยไม่มีใครรู้ หรือระบบทะเบียนที่ทำความล้มเหลวหายไปโดยไม่บันทึก ไม่ได้เป็นแค่ระบบมีบั๊ก แต่เป็นระบบที่ไม่น่าไว้วางใจ ในแบบที่กัดกร่อนสถาบันที่อยู่เบื้องหลัง

## หลักการสำคัญ

- แยกให้ออกระหว่างข้อบกพร่อง (fault) ข้อผิดพลาด (error) และความล้มเหลว (failure) แล้วจัดการแต่ละอย่างในชั้นที่เหมาะสม
- เลือกล้มเร็ว (fail-fast) หรือล้มอย่างปลอดภัย (fail-safe) อย่างตั้งใจ ตามบริบท ไม่ปล่อยให้เป็นไปโดยบังเอิญ
- ทำให้สัญญาการจัดการข้อผิดพลาดของทุกฟังก์ชันและทุก API ชัดเจนและตรงไปตรงมา
- ตรวจสอบข้อมูลที่ขอบเขต เชื่อถือข้อมูลภายในขอบเขต และป้องกันตัวโดยไม่หวาดระแวงเกินเหตุ
- ห้ามกลืนข้อผิดพลาดเงียบๆ ให้เปิดเผยมัน ห่อหุ้มมัน หรือจัดการมันอย่างตั้งใจ
- ทำให้การลองใหม่ (retry) ปลอดภัยด้วย idempotence, การหมดเวลา (timeout), การถอยหลังแบบเอกซ์โพเนนเชียล (backoff) และ jitter
- ให้เส้นทางที่เกิดข้อผิดพลาดได้รับความใส่ใจในการออกแบบเท่ากับเส้นทางปกติ

## ข้อแนะนำ

### แยกข้อผิดพลาด ข้อบกพร่อง และความล้มเหลวให้ชัด

คำศัพท์ที่หละหลวมนำไปสู่การจัดการที่หละหลวม ดังนั้นเริ่มจากนิยามให้ชัดก่อน ข้อบกพร่อง (fault) คือความบกพร่องในระบบ เช่น บั๊ก การตั้งค่าผิด หรือบริการที่พึ่งพาล่ม ข้อผิดพลาด (error) คือสถานะภายในที่ไม่ถูกต้องซึ่งเกิดจากข้อบกพร่อง เช่น ค่า null ในที่ที่ควรมีค่า หรือยอดคงเหลือที่กระทบยอดไม่ลงตัวอีกต่อไป ความล้มเหลว (failure) คือสิ่งที่ผู้สังเกตภายนอกมองเห็น เช่น คำขอได้คำตอบผิด หรือไม่ได้คำตอบเลย ข้อบกพร่องหนึ่งอาจก่อข้อผิดพลาดได้หลายอย่าง และข้อผิดพลาดหลายอย่างอาจถูกจับได้ก่อนที่อย่างใดอย่างหนึ่งจะกลายเป็นความล้มเหลวที่มองเห็นได้ ประเด็นทั้งหมดของการจัดการข้อผิดพลาดคือการตัดห่วงโซ่นี้ คือจับข้อผิดพลาดให้ได้ก่อนที่มันจะกลายเป็นความล้มเหลวที่ผู้ใช้หรือผู้ตรวจสอบต้องเจอ

คำศัพท์ชุดนี้ยังบอกด้วยว่าควรลงมือที่ไหน ข้อบกพร่องแก้ไขผ่านการรีวิว การทดสอบ และการตั้งค่า ข้อผิดพลาดแก้ไขตอนรันไทม์ด้วยรูปแบบต่างๆ ในบทนี้ ส่วนความล้มเหลวแก้ไขด้วยความสามารถในการสังเกตระบบ (observability, บทที่ 9.2) และความทนทานระดับระบบของบทที่ 3.5 เมื่อทีมใช้คำเหล่านี้ตรงกัน การทบทวนเหตุการณ์ขัดข้องจะคมขึ้น คุณระบุได้ชัดว่าห่วงโซ่ควรถูกตัดตรงไหนแต่ไม่ถูกตัด แทนที่จะเถียงกันว่า "บั๊ก" คืออะไรกันแน่

### เลือกล้มเร็วหรือล้มอย่างปลอดภัยตามบริบท

[ล้มเร็ว (Fail-fast)](https://en.wikipedia.org/wiki/Fail-fast_system) หมายถึงหยุดทันทีที่มีบางอย่างผิดปกติ ปฏิเสธที่จะเดินหน้าต่อบนสถานะที่เสียหาย เพื่อให้ปัญหาโผล่ขึ้นมาอย่างชัดเจนและอยู่ใกล้สาเหตุ ส่วนล้มอย่างปลอดภัย (fail-safe) หมายถึงถอยไปสู่สถานะที่รู้จักและไม่เป็นอันตราย แล้วให้บริการเท่าที่ทำได้อย่างปลอดภัยต่อไป ไม่มีแบบไหนถูกเสมอไป ทักษะอยู่ที่การเลือกตามบริบท ระหว่างการพัฒนาและที่ขอบเขตภายใน ล้มเร็วเป็นมิตรกับคุณ โปรแกรมที่หยุดเมื่อเงื่อนไขคงที่ถูกละเมิดจะให้ stack trace สั้นๆ แทนที่จะเป็นปริศนายาวเหยียด ในระบบจริงที่ขอบของระบบซึ่งผู้ใช้เห็น ล้มอย่างปลอดภัยมักชนะ แผงแนะนำสินค้าที่ไม่แสดงอะไรเลยยังดีกว่าหน้าชำระเงินที่โหลดไม่ขึ้น

ให้ตัดสินใจเรื่องนี้อย่างตั้งใจสำหรับแต่ละขอบเขตและเขียนการตัดสินใจนั้นไว้ คอมโพเนนต์ควบคุมการบินหรืออุปกรณ์การแพทย์ล้มอย่างปลอดภัยเข้าสู่สถานะที่กำหนดไว้ เพราะการทำงานต่อบนข้อมูลที่เสียหายอาจทำร้ายคนได้ ส่วนการบันทึกบัญชีแยกประเภท (ledger) ล้มเร็ว เพราะการบันทึกรายการที่ผิดแย่กว่าการไม่บันทึกเลย การจับคู่ผิดอันตรายทั้งสองทาง ถ้าใช้ล้มอย่างปลอดภัยในที่ที่ต้องการล้มเร็ว ความเสียหายของข้อมูลจะถูกซ่อนไว้ และถ้าใช้ล้มเร็วในที่ที่ต้องการล้มอย่างปลอดภัย อาการสะดุดเล็กน้อยจะกลายเป็นระบบล่มทั้งตัว

### เลือกกลไกส่งสัญญาณข้อผิดพลาดและใช้ให้สม่ำเสมอ

ภาษาโปรแกรมให้วิธีกว้างๆ สองแบบในการส่งสัญญาณว่ามีบางอย่างผิดพลาด [การจัดการข้อยกเว้น (Exception handling)](https://en.wikipedia.org/wiki/Exception_handling) โยนอ็อบเจ็กต์ขึ้นไปตามสแต็กการเรียกจนกว่าจะมีตัวจัดการจับไว้ ทำให้เส้นทางข้อผิดพลาดแยกออกจากตรรกะหลัก อีกทางเลือกคือค่าข้อผิดพลาดแบบชัดเจน (explicit error value) คือฟังก์ชันคืนทั้งผลลัพธ์และข้อผิดพลาด แล้วผู้เรียกต้องตรวจทั้งสองอย่าง ภาษาสมัยใหม่หลายภาษาทำแบบหลังให้เป็นระบบด้วย [Result type](https://en.wikipedia.org/wiki/Result_type) มักเรียกว่า Result หรือ Either ซึ่งบังคับให้ผู้เรียกแกะออกมาเป็นความสำเร็จหรือความล้มเหลวก่อนจะใช้ค่า แต่ละแบบมีราคาของมัน ข้อยกเว้นทำให้เส้นทางปกติสะอาด แต่ซ่อนการไหลของการควบคุมได้ และล่อให้นักพัฒนาเขียนบล็อก catch ที่จับทุกอย่างซึ่งลบข้อมูลทิ้ง ส่วนผลลัพธ์แบบชัดเจนทำให้ทุกความล้มเหลวมองเห็นได้ในลายเซ็นของฟังก์ชัน แต่เพิ่มพิธีรีตอง และอาจถูกเมินได้ถ้าภาษาไม่บังคับให้ตรวจ

คำตอบที่ถูกต้องไม่ได้อยู่ที่ว่าเลือกกลไกไหนมากเท่ากับความสม่ำเสมอและความซื่อตรง เลือกรูปแบบที่ภาษาและระบบนิเวศของคุณนิยมใช้ แล้วใช้ให้เหมือนกันทั่วทุกบริการ เพื่อให้ผู้อ่านรู้เสมอว่าความล้มเหลวเดินทางอย่างไร สงวนข้อยกเว้นไว้สำหรับเงื่อนไขที่ผิดปกติจริงๆ ไม่ใช่การควบคุมการไหลตามปกติอย่าง "ไม่พบผู้ใช้" ซึ่งควรเป็นผลลัพธ์ปกติมากกว่า ไม่ว่าเลือกแบบไหน อย่าปล่อยให้ความล้มเหลวมองไม่เห็น ค่าข้อผิดพลาดที่ไม่ถูกตรวจอันตรายพอๆ กับบล็อก catch ว่างเปล่า ในโค้ดเบสขนาดใหญ่ ข้อตกลงที่เขียนไว้บวกกับ linter ที่เตือนเมื่อมีข้อผิดพลาดถูกเมิน ดีกว่าความชอบส่วนตัวของใครคนใดคนหนึ่ง

### ทำให้สัญญาการจัดการข้อผิดพลาดชัดเจน

ทุกฟังก์ชันและทุก API มีสัญญาการจัดการข้อผิดพลาดอยู่แล้ว ไม่ว่าจะมีใครเขียนไว้หรือไม่ สัญญานั้นตอบว่า ตรงนี้อะไรอาจผิดพลาดได้ คุณจะรู้ได้อย่างไร และเมื่อเกิดขึ้นแล้วสถานะรับประกันอะไรไว้บ้าง ให้ทำสัญญานั้นให้ชัดเจน บันทึกว่าฟังก์ชันคืนหรือโยนข้อผิดพลาดชนิดใดได้ แยกข้อผิดพลาดที่กู้คืนได้ (ผู้เรียกลองใหม่หรือใช้ทางเลือกสำรองได้อย่างสมเหตุสมผล) ออกจากข้อผิดพลาดที่กู้คืนไม่ได้ (ผู้เรียกแก้ไม่ได้และควรส่งต่อหรือยกเลิก) และระบุว่าฟังก์ชันปล่อยสถานะไว้เหมือนเดิมเมื่อล้มเหลวหรือไม่ คุณสมบัติข้อสุดท้ายนี้บางครั้งเรียกว่าการรับประกันข้อยกเว้นแบบเข้มแข็ง (strong exception guarantee) หมายความว่าการเรียกที่ล้มเหลวเหมือนไม่เคยเกิดขึ้น ซึ่งเป็นสิ่งที่ทำให้ผู้เรียกลองใหม่ได้อย่างปลอดภัย

สำหรับ API สาธารณะหรือที่ใช้ข้ามทีม สัญญานี้เป็นส่วนหนึ่งของอินเทอร์เฟซ จริงพอๆ กับชนิดของพารามิเตอร์ ออกแบบอนุกรมวิธานของข้อผิดพลาด (error taxonomy) ให้เล็กและเสถียร คือชุดหมวดหมู่ที่จำกัด เช่น ข้อผิดพลาดจากการตรวจสอบข้อมูล ไม่พบ ขัดแย้ง ไม่ได้รับอนุญาต บริการที่พึ่งพาไม่พร้อมใช้งาน และข้อผิดพลาดภายใน ผู้เรียกจะได้แตกกิ่งตามหมวดหมู่โดยไม่ต้องแยกวิเคราะห์สตริง อนุกรมวิธานที่ชัดเจนทำให้การจัดการข้อผิดพลาดประกอบรวมกันได้ข้ามหลายบริการ และทำให้ความล้มเหลวตรวจสอบย้อนหลังได้ เพราะทุกความล้มเหลวจับคู่กับชนิดที่รู้จักและมีชื่อ

### ตรวจสอบที่ขอบเขตและป้องกันตัวโดยไม่หวาดระแวง

ให้ถือว่าข้อมูลที่ข้ามขอบเขตความเชื่อถือ (คำขอทางเครือข่าย ไฟล์ ข้อมูลจากผู้ใช้ ข้อความจากบริการอื่น) เป็นข้อมูลที่เป็นอันตรายจนกว่าจะตรวจสอบแล้ว และให้ตรวจสอบที่ขอบเขตนั้น ครั้งเดียวและให้ถี่ถ้วน นี่คือ[การเขียนโปรแกรมเชิงป้องกัน (defensive programming)](https://en.wikipedia.org/wiki/Defensive_programming) ที่ใช้ด้วยวิจารณญาณ ภายในโมดูลที่อินพุตถูกตรวจสอบมาแล้ว การตรวจซ้ำซ้อนทุกบรรทัดจะบดบังตรรกะ และกดความล้มเหลวที่คุณอยากเห็นเสียเอง วินัยคือ ป้องกันให้เข้มที่ขอบ เชื่อใจภายใน ตรวจสอบโครงสร้าง ช่วงค่า และเงื่อนไขคงที่ตรงจุดที่ข้อมูลเข้ามา แปลงข้อมูลเป็นชนิดที่ทำให้สถานะที่ผิดกฎไม่สามารถแสดงออกมาได้ แล้วให้โค้ดภายในสมมติได้ว่ากำลังทำงานกับข้อมูลที่สะอาด

ความหวาดระแวงมีต้นทุนจริง โค้ดที่เต็มไปด้วยการตรวจ null และกิ่งป้องกันอ่านยากขึ้น และที่แย่กว่านั้นคือมักเปลี่ยนความล้มเหลวที่ชัดเจนให้กลายเป็นการยักไหล่เงียบๆ คืนค่าเริ่มต้นแทนที่จะส่งสัญญาณเตือน การป้องกันที่ปิดบังบั๊กไม่ใช่ความปลอดภัย แต่เป็นการเลื่อนปัญหาออกไป

### ทำให้การลองใหม่ปลอดภัย มีขอบเขต และมีมารยาท

ข้อบกพร่องจำนวนมากเป็นแบบชั่วคราว เครือข่ายสะดุดชั่วขณะ บริการกำลังรีสตาร์ต หรือการแย่งล็อกช่วงสั้นๆ ในระบบกระจายใดๆ (บทที่ 3.3) ความล้มเหลวบางส่วนแบบนี้เป็นเรื่องปกติ ไม่ใช่ข้อยกเว้น การลองใหม่เป็นปฏิกิริยาตามธรรมชาติ แต่ลูปลองใหม่แบบไร้เดียงสาเป็นปืนที่บรรจุกระสุนไว้แล้ว ประการแรก ทำให้การดำเนินการที่ลองใหม่เป็น [idempotent](https://en.wikipedia.org/wiki/Idempotence) ซึ่งหมายความว่าทำสองครั้งให้ผลเหมือนทำครั้งเดียว ถ้าไม่มี idempotence การลองใหม่หลังหมดเวลาอาจตัดบัตรซ้ำสองครั้งหรือสร้างระเบียนซ้ำสองรายการ เพราะคุณบอกไม่ได้ว่าความพยายามครั้งแรกล้มเหลวจริง หรือแค่ข้อความตอบรับหายไป ใช้ idempotency key กับการเขียนข้อมูล เพื่อให้ฝั่งรับจำได้และตัดรายการซ้ำออก

ประการที่สอง ใส่ timeout ให้ทุกการเรียกระยะไกล เพื่อไม่ให้บริการที่ค้างลากคุณค้างไปด้วย ประการที่สาม เว้นระยะการลองใหม่ด้วย[การถอยหลังแบบเอกซ์โพเนนเชียล (exponential backoff)](https://en.wikipedia.org/wiki/Exponential_backoff) คือเพิ่มเวลารอเป็นสองเท่าหลังแต่ละครั้ง และเติม jitter (การหน่วงแบบสุ่มเล็กน้อย) เพื่อไม่ให้ไคลเอนต์นับพันที่ฟื้นตัวพร้อมกันพุ่งเข้าหาบริการเป็นพายุ จนบริการที่กำลังฟื้นล้มลงอีกครั้ง ประการที่สี่ จำกัดจำนวนครั้งที่ลองใหม่และเวลารวม แล้วยอมแพ้อย่างสง่างาม การลองใหม่ที่ไม่มีขีดจำกัด ไม่มี backoff ไม่มี jitter และไม่มี idempotence คือหนึ่งในวิธีที่พบบ่อยที่สุดที่ทำให้เรื่องเล็กน้อยกลายเป็นระบบล่มที่เราทำร้ายตัวเอง

### เพิ่ม circuit breaker, bulkhead และการลดระดับบริการอย่างสง่างามในโค้ด

เมื่อบริการที่พึ่งพาล่มจริงๆ การลองเรียกซ้ำมีแต่เสียแรงและทำให้หลุมลึกขึ้น [circuit breaker](https://en.wikipedia.org/wiki/Circuit_breaker_design_pattern) คอยดูอัตราความล้มเหลวของการเรียกไปยังบริการนั้น และเมื่อความล้มเหลวเกินเกณฑ์ ก็ "เปิด" เพื่อล้มทันทีตลอดช่วงพักเย็น แทนที่จะรอการเรียกที่ไร้หวัง หลังช่วงพักจะปล่อยให้การเรียกทดลองผ่านไปหนึ่งครั้ง และปิดกลับหากบริการฟื้นตัวแล้ว วิธีนี้ปกป้องทั้งผู้เรียก (ล้มเร็วและคาดเดาได้ แทนที่จะเจอ timeout สะสม) และบริการที่กำลังลำบาก (มีที่หายใจให้ฟื้นตัว) รูปแบบ bulkhead ซึ่งตั้งชื่อตามห้องกันน้ำของเรือ แยกทรัพยากรออกจากกัน เพื่อไม่ให้บริการที่พึ่งพาตัวเดียวที่ล้นมือกินเธรดหรือการเชื่อมต่อทั้งหมดจนโปรเซสทั้งตัวจม ให้แต่ละบริการที่พึ่งพามีพูลที่มีขอบเขตเป็นของตัวเอง

รูปแบบเหล่านี้จับคู่กับการลดระดับบริการอย่างสง่างาม (graceful degradation) ในระดับโค้ด คือเมื่อบริการที่ไม่จำเป็นใช้ไม่ได้ ให้คืนผลลัพธ์ที่น้อยลงแต่ยังมีประโยชน์ แทนที่จะคืนข้อผิดพลาด เช่น แสดงข้อมูลแคชพร้อมหมายเหตุว่าอาจไม่เป็นปัจจุบัน ซ่อนแผงการปรับแต่งเฉพาะบุคคล หรือเข้าคิวการเขียนไว้ทำทีหลัง นี่คือส่วนเสริมระดับท้องถิ่นของความทนทานระดับระบบในบทที่ 3.5 สถาปัตยกรรมให้ความซ้ำซ้อนข้ามเครื่อง และโค้ดของคุณให้พฤติกรรมที่สมเหตุสมผลเมื่อมีบางส่วนหายไป

### ห่อข้อผิดพลาดด้วยบริบทและอย่ากลืนมัน

ข้อผิดพลาดที่เขียนว่า "connection refused" เมื่อมาถึงชั้นที่อยู่สูงจากจุดเกิดเหตุสิบชั้น แทบไม่มีประโยชน์ เมื่อข้อผิดพลาดถูกส่งต่อขึ้นไป ให้ห่อมันด้วยบริบท ว่าคุณกำลังพยายามทำอะไร เอนทิตีหรือคำขอใด บริการที่พึ่งพาตัวไหน พร้อมเก็บสาเหตุเดิมไว้เพื่อไม่ให้รากของปัญหาหาย ภาษาและไลบรารีที่ดีรองรับการต่อโซ่ข้อผิดพลาดนี้โดยตรง เป้าหมายคือให้บรรทัดล็อกเพียงบรรทัดเดียวบอกวิศวกรเวรได้ว่าอะไรล้มเหลว ระหว่างการดำเนินการใด กับอินพุตอะไร นี่คือวัตถุดิบของความสามารถในการสังเกตระบบในบทที่ 9.2 และการดีบักในบทที่ 2.15

บาปใหญ่คือการกลืนข้อผิดพลาด คือบล็อก catch ว่างเปล่า ค่าที่คืนมาแล้วถูกเมิน หรือ `catch` ที่ล็อกระดับ debug แล้วเดินต่อเหมือนไม่มีอะไรเกิดขึ้น ข้อผิดพลาดที่ถูกกลืนไม่ได้หายไป มันจะโผล่กลับมาทีหลังเป็นข้อมูลเสียหรือข้อบกพร่องที่อธิบายไม่ได้ ซึ่งตอนนั้นแยกขาดจากสาเหตุไปแล้ว ทุกข้อผิดพลาดต้องพบชะตากรรมหนึ่งในสามอย่าง คือจัดการมัน (กู้คืนหรือลดระดับ) ห่อและส่งต่อมันขึ้นไป หรือที่ยอดของสแต็กก็ล็อกมันพร้อมบริบทครบถ้วนแล้วล้มเหลว ถ้าคุณจับข้อผิดพลาดแล้วไม่ทำอะไรเลยสักอย่างจากสามข้อนี้ คุณได้เลือกซ่อนเหตุการณ์ขัดข้องในอนาคตจากตัวคุณเองในอนาคต

## ข้อดีข้อเสียและการแลกเปลี่ยน

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| ข้อยกเว้น (Exceptions) | เส้นทางปกติสะอาด; เมินได้ยากถ้าไม่ถูกตรวจ | การไหลของการควบคุมถูกซ่อน; ล่อให้ใช้ catch-all ที่ลบข้อมูลทิ้ง |
| ค่าข้อผิดพลาดแบบชัดเจน / Result type | ความล้มเหลวเห็นได้ในลายเซ็น; บังคับให้จัดการ | พิธีรีตองมากขึ้น; เมินได้ถ้าไม่มีการบังคับใช้ |
| ล้มเร็ว (Fail-fast) | เปิดเผยบั๊กอย่างชัดเจนและใกล้สาเหตุ | ประสบการณ์ผู้ใช้แย่ถ้าใช้ที่ขอบระบบ |
| ล้มอย่างปลอดภัย (Fail-safe) | ให้บริการต่อไปได้; ปกป้องผู้ใช้และข้อมูล | อาจบดบังความเสียหายถ้าใช้ในที่ที่ต้องการล้มเร็ว |
| ลองใหม่พร้อม backoff | ผ่านพ้นข้อบกพร่องชั่วคราวได้เอง | เพิ่มโหลดและเขียนซ้ำถ้าไม่มี idempotence |
| Circuit breaker | ล้มเร็ว; เปิดโอกาสให้บริการที่พึ่งพาฟื้นตัว | มีสถานะเพิ่มและต้องปรับจูน; อาจบดบังปัญหาที่เป็นถาวร |
| การตรวจสอบเชิงป้องกันที่ขอบเขต | จับข้อมูลเสียได้เร็ว ครั้งเดียว และชัดเจน | ถ้าทำเกินไป ตรรกะจะรก และซ่อนความล้มเหลวจริง |

ความตึงเครียดหลักอยู่ระหว่างความมองเห็นได้กับสัญญาณรบกวน จัดการข้อผิดพลาดเงียบเกินไป ปัญหาจะถูกซ่อนจนแพงเมื่อโผล่ขึ้นมา จัดการเสียงดังและทุกที่ ก็จะจมสัญญาณอยู่ในพิธีรีตอง และบดบังความล้มเหลวที่สำคัญ วิธีแก้คือแยกตามตำแหน่งและเจตนา ให้ดังและเข้มงวดที่ขอบเขต ซึ่งเป็นที่ที่ข้อมูลเสียและความล้มเหลวของบริการที่พึ่งพาเข้ามา ให้เงียบและเชื่อใจภายใน ซึ่งอินพุตสะอาดแล้ว ตัดสินใจเรื่องล้มเร็วหรือล้มอย่างปลอดภัยทีละขอบเขตแล้วเขียนไว้ เป้าหมายคือโค้ดที่ทุกความล้มเหลวมีเจ้าของชัดเจนหนึ่งเดียวและชะตากรรมชัดเจนหนึ่งเดียว และไม่มีอะไรหล่นหายเงียบๆ ตามรอยแตก

## คำถามที่ควรคุยกับทีม

1. **เรามีอนุกรมวิธานข้อผิดพลาดและข้อตกลงการจัดการข้อผิดพลาดร่วมกันทั้งบริการหรือไม่ หรือแต่ละทีมคิดเอาเอง?** ในทีมขนาดใหญ่ นี่คือความต่างระหว่างความล้มเหลวที่ประกอบเข้าด้วยกันได้กับความล้มเหลวที่สร้างความสับสน เมื่อบริการหนึ่งคืน HTTP 500 สำหรับปัญหาการตรวจสอบข้อมูล อีกบริการโยนข้อยกเว้นแบบมีชนิด และบริการที่สามคืน null ทุกการเชื่อมต่อจะกลายเป็นการเจรจา และทุกเหตุการณ์ขัดข้องกลายเป็นแบบฝึกหัดการแปล ลองนำตัวอย่างความล้มเหลวเชิงตรรกะเดียวกัน เช่น "ไม่พบระเบียน" ที่ปรากฏในสามบริการของคุณมาดูว่าส่งสัญญาณต่างกันแค่ไหน คำตอบควรกลายเป็นมาตรฐานที่เขียนไว้ คือชุดหมวดหมู่ข้อผิดพลาดที่จำกัด วิธีส่งสัญญาณที่สม่ำเสมอ และ linter หรือรายการตรวจสอบการรีวิวที่บังคับใช้ ความสม่ำเสมอตรงนี้ให้ผลตอบแทนในทุกการเชื่อมต่อ ทุกการตรวจสอบ และทุกกะเวรในอนาคต

2. **สำหรับแต่ละขอบเขตที่สำคัญ เราเลือกล้มเร็วหรือล้มอย่างปลอดภัยอย่างตั้งใจหรือไม่ และโค้ดตรงกับที่เลือกหรือไม่?** ทีมส่วนใหญ่ไม่เคยตัดสินใจเรื่องนี้อย่างชัดเจน ซึ่งหมายความว่าคนที่เขียนโค้ดคนแรกเป็นผู้ตัดสินแทน และตัดสินไม่สม่ำเสมอ ข้อพิจารณาที่แข่งกันนั้นมีอยู่จริง การล้มอย่างปลอดภัยให้บริการผู้ใช้ต่อไปได้แต่ปล่อยให้ความเสียหายลามได้ ส่วนการล้มเร็วปกป้องข้อมูลแต่อาจเปลี่ยนการล่มเล็กน้อยของบริการที่พึ่งพาให้เป็นความล้มเหลวที่มองเห็นได้ ลองนำประวัติเหตุการณ์ขัดข้องมาดู แล้วถามสำหรับกรณีที่แย่ที่สุดไม่กี่กรณีว่า โค้ดล้มแบบที่คุณจะเลือกถ้าถูกถามล่วงหน้าหรือไม่ หลักฐานที่คุณต้องการคือแผนที่ขอบเขตของคุณพร้อมป้ายกำกับที่ตั้งใจให้แต่ละจุด โดยเฉพาะทุกที่ที่เกี่ยวกับเงิน ความปลอดภัย หรือระเบียนของพลเมือง จุดไหนที่ป้ายกับโค้ดไม่ตรงกัน นั่นคือสิ่งที่ต้องแก้ถัดไป

3. **ครั้งล่าสุดที่เราทดสอบเส้นทางข้อผิดพลาดโดยตั้งใจคือเมื่อไร และมันทำงานตามที่ออกแบบไว้หรือไม่?** เส้นทางข้อผิดพลาดมักเป็นโค้ดที่ถูกทดสอบน้อยที่สุดที่คุณเป็นเจ้าของ แต่เป็นที่ที่ความไว้วางใจชนะหรือแพ้ และ "เราล้มอย่างปลอดภัย" เป็นคำกล่าวอ้างที่คุณยืนยันไม่ได้ถ้าไม่เคยเห็นมันเกิดขึ้นจริง ลูปลองใหม่ที่ไม่มี idempotence, circuit breaker ที่ตั้งเกณฑ์ผิด, ข้อยกเว้นที่ถูกกลืนในกิ่งที่แทบไม่ถูกเรียก สิ่งเหล่านี้ซ่อนอยู่จนกว่าเหตุการณ์จริงจะมาค้นพบให้คุณ ให้นำผลของการฉีดความล้มเหลวโดยตั้งใจ (ฆ่าบริการที่พึ่งพา ทำให้เกิด timeout ส่ง payload ที่ผิดรูป) เข้าไปในสภาพแวดล้อมที่สมจริงมาดู การลงมือต่อจากนั้นคือทำให้การฉีดความล้มเหลวเป็นกิจวัตร เพื่อให้พฤติกรรมการกู้คืน การลดระดับบริการ และการล้มอย่างปลอดภัยถูกพิสูจน์ต่อเนื่องแทนที่จะเพียงหวังไว้ เส้นทางข้อผิดพลาดใดที่คุณไม่เคยกระตุ้น คือคำสัญญาที่คุณยังไม่ได้ทดสอบ

4. **การเขียนข้อมูลของเราอันไหนเป็น idempotent และตรงไหนที่การลองใหม่หลังข้อความตอบรับหายจะทำให้ผลในโลกจริง เช่น การชำระเงินหรือระเบียน ซ้ำซ้อน?** การลองใหม่เป็นปฏิกิริยาเพื่อความทนทานที่พบบ่อยที่สุด และถ้าทำอย่างไม่ระวัง ก็เป็นวิธีที่พบบ่อยที่สุดที่ทำให้อาการสะดุดชั่วคราวกลายเป็นเงินหรือข้อมูลที่ซ้ำซ้อน ในทีมขนาดใหญ่ ตรรกะการลองใหม่มักอยู่ในไคลเอนต์ที่ใช้ร่วมกัน middleware และแต่ละบริการพร้อมกัน ดังนั้นการเขียนครั้งเดียวอาจถูกลองใหม่หลายชั้นโดยไม่มีใครเป็นเจ้าของพฤติกรรมรวม แรงดึงฝั่งตรงข้ามคือ idempotency key การตัดรายการซ้ำ และการเก็บผลลัพธ์ของคำขอ ล้วนเพิ่มพื้นที่เก็บข้อมูลและโค้ด และทีมที่ถูกกดดันเรื่องการส่งมอบมักข้ามไปสำหรับการเขียนที่เข้าใจผิดว่าปลอดภัยอยู่แล้ว ให้นำรายการการเขียนที่ภายนอกมองเห็นทั้งหมดมา โดยทำเครื่องหมายแต่ละรายการว่ามี idempotency key หรือไม่ และฝั่งรับจำและตัดรายการซ้ำอย่างไร ในองค์กรขนาดใหญ่และภาครัฐ ให้ระบุรายการที่เคลื่อนย้ายเงินหรือเปลี่ยนแปลงระเบียนของพลเมืองก่อน เพราะการจ่ายซ้ำหรือสวัสดิการที่ซ้ำซ้อนเป็นข้อค้นพบจากการตรวจสอบและบางครั้งเป็นความเสี่ยงทางกฎหมาย ไม่ใช่แค่ข้อบกพร่อง

5. **timeout, circuit breaker และ bulkhead ของเรามาจากไลบรารีกลางที่ผ่านการทดสอบแล้วหรือไม่ หรือแต่ละทีมเขียนเอง?** รูปแบบเหล่านี้อธิบายง่ายและผิดเพี้ยนเล็กน้อยได้ง่าย เช่น ลืมใส่ timeout เกณฑ์ของ breaker ที่ไม่เคยทำงาน หรือพูลการเชื่อมต่อที่กำหนดขนาดจนบริการที่ช้าตัวเดียวทำให้ทั้งโปรเซสอดอยาก เมื่อทุกทีมเขียนใหม่เอง คุณจะสะสมสำเนาที่เสียเล็กน้อยหลายชุด และไม่มีที่เดียวที่แก้ข้อบกพร่องได้ครั้งเดียวเมื่อพบ ข้อพิจารณาที่แข่งกันคือไลบรารีกลางบังคับอินเทอร์เฟซร่วมและรอบการอัปเกรดร่วม และทีมที่มีรันไทม์หรือความต้องการเรื่องความหน่วงที่ไม่ปกติอาจอึดอัดหรือเลี่ยงไปทางอื่น ให้นำผลสำรวจมาดูว่ามีการลองใหม่และ breaker ที่ต่างกันกี่แบบรันอยู่จริงในระบบจริง และบริการไหนยังไม่มี timeout ในการเรียกออกเลย สำหรับองค์กรขนาดใหญ่หรือหน่วยงานรัฐ ไลบรารีกลางที่ผ่านการตรวจสอบยังให้ผู้ตรวจสอบด้านความมั่นคงปลอดภัยและผู้ตรวจสอบบัญชีรับรองคอมโพเนนต์เดียว แทนที่จะเป็นหลายสิบ ซึ่งลดต้นทุนของทุกการตรวจสอบ

6. **ถ้ามีเหตุการณ์ขัดข้องเมื่อคืนนี้ วิศวกรเวรคนใดก็ตามจะไล่รอยจากบรรทัดล็อกบรรทัดเดียวได้หรือไม่ และผู้ตรวจสอบจะเห็นทุกความล้มเหลวที่ระบบบันทึกไว้ได้ในภายหลังหรือไม่?** ข้อผิดพลาดที่ถูกห่อ จัดหมวดหมู่ และล็อกอย่างดี คือความต่างระหว่างการวินิจฉัยสิบนาทีกับการขุดค้นตอนเที่ยงคืน และข้อผิดพลาดที่ถูกกลืนคือเหตุการณ์ขัดข้องในอนาคตที่คุณซ่อนจากตัวเอง ในทีมขนาดใหญ่ ความล้มเหลวข้ามหลายบริการ ดังนั้นคุณค่าจึงมาจากบริบทที่สม่ำเสมอและ correlation identifier ที่อยู่รอดข้ามการกระโดดเหล่านั้น ไม่ใช่ความขยันของทีมใดทีมหนึ่ง ความตึงเครียดที่แข่งกันคือต้นทุนและสัญญาณรบกวน ล็อกทุกอย่างก็จมสัญญาณและต้องจ่ายค่าเก็บข้อมูล ล็อกน้อยไปก็สร้างเหตุการณ์ขึ้นใหม่ไม่ได้ ให้นำความล้มเหลวจริงล่าสุดมาไล่รอยตั้งแต่ต้นจนจบ โดยจดทุกจุดที่บริบทหายไปหรือข้อผิดพลาดถูกจับแล้วทิ้ง ในระบบที่ถูกกำกับดูแลและภาครัฐ ให้ถือเรื่องนี้เป็นคุณสมบัติด้านการปฏิบัติตามข้อกำหนด เพราะความล้มเหลวที่ตรวจสอบไม่ได้ หรือการตัดสินใจที่อธิบายไม่ได้หลายปีต่อมา เป็นความเสี่ยงทางกฎหมาย ไม่ใช่แค่ช่องว่างด้านปฏิบัติการ

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ด้วยวิศวกรไม่กี่คนและไม่มีเงินทุนเหลือเฟือ ให้ใช้งบการจัดการข้อผิดพลาดตรงจุดที่ความล้มเหลวทำให้เสียลูกค้าหรือข้อมูล ใส่ timeout ให้ทุกการเรียกออก ทำให้การเขียนที่เคลื่อนย้ายเงินเป็น idempotent และเพิ่มกฎ lint ห้ามเมินข้อผิดพลาด ข้ามเฟรมเวิร์กที่ซับซ้อนไปก่อน Result type สำหรับฟังก์ชันหลักและการลดระดับบริการอย่างสง่างามกับบริการที่ไม่สำคัญ ซื้อความปลอดภัยส่วนใหญ่ได้ด้วยงานไม่กี่วัน ล้มเร็วในการพัฒนาเพื่อให้บั๊กโผล่ชัด และอย่าเพิ่งเขียน circuit breaker เองจนกว่าจะมีบริการที่พึ่งพาที่คุ้มกับมันจริงๆ

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญด้านความทนทานในทีมและงบจำกัด ให้พึ่งสิ่งที่ภาษา เฟรมเวิร์ก และผู้ให้บริการคลาวด์ของคุณมีให้อยู่แล้ว แทนที่จะสร้างรูปแบบต่างๆ จากศูนย์ คิวแบบมีผู้จัดการให้ การลองใหม่ฝั่งผู้ให้บริการ และ timeout ของไลบรารีครอบคลุมได้มากกว่าที่ทีมส่วนใหญ่คาด ตั้งกรอบการตัดสินใจเป็นเรื่องซื้อกับสร้าง และซื้อทุกที่ที่ไลบรารีที่เติบโตแล้วจัดการการลองใหม่ backoff และ idempotency ให้ ทุ่มความสนใจที่มีน้อยกับขอบเขตหนึ่งหรือสองจุดที่ธุรกรรมผิดหรือหายจะเจ็บจริงๆ และทำให้จุดเหล่านั้นล้มอย่างปลอดภัยและทิ้งร่องรอยไว้

**องค์กรขนาดใหญ่.** เมื่อมีหลายทีม สิ่งที่ควรได้คือความสม่ำเสมอ มีอนุกรมวิธานข้อผิดพลาดร่วมกัน ไลบรารีกลางสำหรับ timeout การลองใหม่ circuit breaker และ bulkhead และ linter กับรายการตรวจสอบการรีวิวที่บังคับใช้ในไปป์ไลน์ ส่งทุกข้อผิดพลาดเข้าแพลตฟอร์มสังเกตระบบรวมศูนย์พร้อม correlation identifier เพื่อไล่รอยความล้มเหลวข้ามบริการได้ และทำให้การตัดสินใจล้มเร็วหรือล้มอย่างปลอดภัยเป็นมาตรฐานตามขอบเขต เพื่อให้ผู้ตรวจสอบพบรูปแบบที่มีเอกสารและป้องกันได้ แทนที่จะเป็นนิสัยท้องถิ่นที่กระจัดกระจาย บริหารจัดการไลบรารีกลางเหมือนผลิตภัณฑ์จริง เพราะข้อบกพร่องที่แก้ที่นั่นครั้งเดียวคือข้อบกพร่องที่ถูกแก้ทุกที่

**ภาครัฐ.** ความถูกต้อง การล้มอย่างปลอดภัย และร่องรอยการตรวจสอบที่คงทนเป็นภาระผูกพัน ไม่ใช่ความชอบ ล้มเร็วกับทุกเงื่อนไขคงที่ที่ถูกละเมิดและเกี่ยวกับเงินหรือสิทธิ์ ตรวจสอบทุกอินพุตที่พลเมืองกรอกที่ขอบเขต และเขียนแต่ละความล้มเหลวลงล็อกที่แก้ไขไม่ได้ (immutable log) พร้อมบริบทพอที่จะอธิบายและทบทวนการตัดสินใจได้หลายปีต่อมา การจัดซื้อจัดจ้างและอายุการใช้งานระบบที่ยาวนานหมายความว่าสัญญาข้อผิดพลาดต้องมีเอกสาร เพื่อให้ข้าราชการดูแลโค้ดได้นานหลังผู้เขียนเดิมจากไป และคอมโพเนนต์ของผู้ขายรายใดก็ต้องเปิดเผยพฤติกรรมเมื่อล้มเหลว ไม่ซ่อนไว้หลังอินเทอร์เฟซที่ทึบ

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสี่คนปล่อยแอปที่เรียกผู้ให้บริการชำระเงินและบริการอีเมลของบุคคลที่สาม ช่วงแรกพวกเขาเพิ่มลูปลองใหม่แบบไร้เดียงสา แล้วก็เก็บเงินลูกค้าซ้ำสองครั้งทันทีเมื่อ timeout บดบังการเก็บเงินที่สำเร็จไปแล้ว การแก้ปัญหาสอนบทเรียนไว้ พวกเขาเพิ่ม idempotency key ให้ทุกการเขียน ใส่ timeout ให้ทุกการเรียกออก และเปลี่ยนมาใช้ exponential backoff พร้อม jitter พวกเขาใช้ Result type กับฟังก์ชันบริการหลักเพื่อให้ความล้มเหลวปรากฏในลายเซ็น และมีกฎ lint คอยเตือนเมื่อมีข้อผิดพลาดถูกเมิน เมื่อการส่งอีเมลล้มเหลว ขั้นตอนชำระเงินลดระดับบริการอย่างสง่างามด้วยการเข้าคิวข้อความไว้แทนที่จะขวางการขาย วินัยนี้ใช้เวลาไม่กี่วัน และช่วยให้พวกเขาไม่ต้องเจอเหตุการณ์ขัดข้องทั้งชนิดที่จะทำให้เสียทั้งค่าคืนเงินและความไว้วางใจมากกว่านี้มาก

**องค์กรขนาดใหญ่.** บริษัทโลจิสติกส์ระดับโลกที่มีบริการหลายร้อยตัวทำให้การจัดการข้อผิดพลาดเป็นมาตรฐานเดียวกันทั้งหมด ทุกบริการจับคู่ความล้มเหลวเข้ากับอนุกรมวิธานร่วม (การตรวจสอบข้อมูล ไม่พบ ขัดแย้ง บริการที่พึ่งพาไม่พร้อมใช้งาน ข้อผิดพลาดภายใน) ผู้เรียกจึงแตกกิ่งตามหมวดหมู่แทนที่จะแยกวิเคราะห์ข้อความ ไลบรารีกลางให้ circuit breaker การลองใหม่แบบมีขอบเขตพร้อม backoff และ jitter และพูลการเชื่อมต่อแบบ bulkhead เพื่อไม่ให้ใครเขียนรูปแบบเหล่านี้เองแล้วผิด ทุกข้อผิดพลาดถูกล็อกพร้อมบริบทเชื่อมโยง (correlation) ที่ป้อนเข้าแพลตฟอร์มสังเกตระบบในบทที่ 9.2 วิศวกรเวรจึงไล่รอยความล้มเหลวข้ามบริการได้จากบรรทัดเดียว เพราะมาตรฐานสม่ำเสมอและบังคับใช้ในไปป์ไลน์ วิศวกรจึงย้ายไปทำงานกับบริการที่ไม่คุ้นเคยได้อย่างมั่นใจ และผู้ตรวจสอบเห็นได้ว่าทุกความล้มเหลวถูกบันทึก จัดหมวดหมู่ และไล่รอยได้

**ภาครัฐ.** หน่วยงานสวัสดิการแห่งชาติสร้างระบบตรวจสอบสิทธิ์และจ่ายเงิน ซึ่งคำตอบที่ผิดอาจทำให้ใครสักคนไม่ได้เงินค่าเช่าบ้าน หรือจ่ายเกินจากเงินของแผ่นดิน ความถูกต้องและการล้มอย่างปลอดภัยต่อรองไม่ได้ โค้ดจึงล้มเร็วกับเงื่อนไขคงที่ทางการเงินที่ถูกละเมิด การคำนวณที่กระทบยอดไม่ลงตัวจะปฏิเสธที่จะบันทึก แทนที่จะบันทึกตัวเลขที่ผิด ทุกอินพุตที่พลเมืองกรอกถูกตรวจสอบที่ขอบเขต และสถานะที่ผิดกฎถูกทำให้แสดงออกมาไม่ได้ในชนิดข้อมูลของโดเมน ทุกความล้มเหลวถูกเขียนลงล็อกตรวจสอบที่แก้ไขไม่ได้พร้อมบริบทครบถ้วน ตามข้อกำหนดทางกฎหมายที่ว่าการตัดสินใจต้องอธิบายและทบทวนได้หลายปีต่อมา เมื่อบริการที่ไม่สำคัญ เช่น การแสดงตัวอย่างเอกสาร ใช้ไม่ได้ ระบบลดระดับบริการอย่างสง่างาม เจ้าหน้าที่ยังดำเนินการคำร้องต่อได้ ข้าราชการใหม่รับช่วงโค้ดที่สัญญาข้อผิดพลาดมีเอกสาร จึงดูแลได้อย่างปลอดภัยนานหลังผู้เขียนเดิมย้ายไปแล้ว

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ผลตอบแทนจากการจัดการข้อผิดพลาดอย่างมีวินัยปรากฏเป็นเหตุการณ์ขัดข้องที่น้อยลง สั้นลง และถูกลง ระบบล่มในสภาพใช้งานจริงส่วนใหญ่ไม่ได้แปลกประหลาด มันสืบย้อนไปถึงข้อยกเว้นที่ถูกกลืน timeout ที่ขาดหายไป พายุการลองใหม่ หรือขอบเขตที่เชื่อข้อมูลที่ควรตรวจสอบ ทั้งหมดป้องกันได้ด้วยรูปแบบในบทนี้ และทุกเหตุการณ์ที่ป้องกันได้ช่วยประหยัดไม่ใช่แค่ต้นทุนตรงของระบบหยุดทำงาน แต่รวมถึงต้นทุนสะสมของการตอบสนองฉุกเฉิน การเสียลูกค้า และการสืบสวน เพราะข้อผิดพลาดที่ถูกห่อและล็อกอย่างดีวินิจฉัยได้ในไม่กี่นาทีแทนที่จะเป็นหลายชั่วโมง เวลาเฉลี่ยในการกู้คืน (MTTR) จึงลดลง และอัตราความล้มเหลวจากการเปลี่ยนแปลง (change-failure rate) ลดตามไปด้วยเมื่อวิศวกรเลิกกลัวเส้นทางข้อผิดพลาด

ต้นทุนในการนำมาใช้อยู่ในระดับพอเหมาะและเป็นแบบครั้งเดียวเป็นส่วนใหญ่ คุณเขียนอนุกรมวิธานข้อผิดพลาด จัดหาไลบรารีกลางสำหรับการลองใหม่และ circuit breaker เพื่อไม่ให้ทีมต้องคิดใหม่อย่างแย่ๆ เพิ่มกฎ lint ห้ามเมินข้อผิดพลาด และสร้างนิสัยการฉีดความล้มเหลว ส่วนต้นทุนของการละเลยสะสมอย่างเงียบๆ ข้อผิดพลาดที่ถูกกลืนพอกพูนเป็นข้อมูลเสียหายที่แก้คืนได้แพง และการจัดการที่ไม่สม่ำเสมอคูณต้นทุนของทุกการเชื่อมต่อและทุกการตรวจสอบ ในการตั้งค่าที่ถูกกำกับดูแลและภาครัฐ ความล้มเหลวที่ตรวจสอบไม่ได้คือความเสี่ยงด้านการปฏิบัติตามข้อกำหนดและกฎหมาย ไม่ใช่แค่ปัญหาทางวิศวกรรม การนำเสนอต่อผู้บริหารให้เชื่อมวินัยการจัดการข้อผิดพลาดเข้ากับตัวชี้วัดที่พวกเขาติดตามอยู่แล้ว คือความถี่ของเหตุการณ์ขัดข้อง เวลาเฉลี่ยในการกู้คืน อัตราความล้มเหลวจากการเปลี่ยนแปลง และข้อค้นพบจากการตรวจสอบ

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **การกลืนเงียบ:** บล็อก catch ว่างเปล่าและค่าที่คืนมาแล้วถูกเมิน ที่เปลี่ยนความล้มเหลวให้เป็นปริศนาที่มาช้าและขาดจากสาเหตุ
- **การลบด้วย catch-all:** `catch` กว้างๆ ที่ล็อกข้อความทั่วไปแล้วทิ้งข้อผิดพลาดเดิมและบริบทของมัน
- **ลองใหม่โดยไม่มี idempotence:** รันการเขียนที่ไม่เป็น idempotent ซ้ำหลัง timeout จนตัดเงินซ้ำหรือระเบียนซ้ำซ้อน
- **พายุการลองใหม่:** ไม่มี backoff ไม่มี jitter และไม่มีเพดาน ไคลเอนต์จึงซิงโครไนซ์กันและกระหน่ำบริการที่กำลังฟื้นจนล้มอีกครั้ง
- **ไม่มี timeout:** การเรียกระยะไกลที่ไม่มีขอบเขต ปล่อยให้บริการที่พึ่งพาที่ค้างตัวเดียวทำให้เธรดหมดและทั้งโปรเซสหยุดนิ่ง
- **ใช้ข้อยกเว้นเป็นการควบคุมการไหล:** โยนและจับสำหรับผลลัพธ์ปกติอย่าง "ไม่พบ" ซึ่งซ่อนตรรกะและทำให้โค้ดช้าลง
- **การป้องกันแบบหวาดระแวง:** การตรวจทุกบรรทัดที่กลบตรรกะและแปลงความล้มเหลวจริงเป็นค่าเริ่มต้นเงียบๆ
- **ข้อผิดพลาดแบบสตริง (stringly-typed):** ผู้เรียกแยกวิเคราะห์ข้อความข้อผิดพลาด เพราะไม่มีอนุกรมวิธานที่เสถียรและจัดหมวดหมู่ไว้ให้แตกกิ่งตาม
- **ล้มอย่างปลอดภัยในที่ที่ต้องการล้มเร็ว:** ทำงานต่อบนสถานะที่เสียหายในระบบที่คำตอบผิดแย่กว่าไม่มีคำตอบ

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** การจัดการข้อผิดพลาดเป็นแบบเฉพาะกิจและตอบโต้ ตัดสินตามนักพัฒนาแต่ละคน บล็อก catch ว่างและค่าที่คืนมาถูกเมินพบได้ทั่วไป การลองใหม่เป็นแบบไร้เดียงสา ไม่มี timeout และความล้มเหลวโผล่ขึ้นมาเป็นข้อมูลเสียหรือข้อบกพร่องปริศนาโดยไม่มีการล็อกที่สม่ำเสมอ
- **ระดับ 2 พัฒนา:** ทีมนำแนวปฏิบัติพื้นฐานมาใช้ แต่ไม่สม่ำเสมอ ข้อผิดพลาดถูกล็อกพร้อมบริบทบ้าง การกลืนข้อผิดพลาดที่เห็นชัดถูกห้ามปรามในการรีวิว และมี timeout กับการลองใหม่แบบง่ายอยู่ แต่ข้อตกลงต่างกันระหว่างบริการ idempotence เป็นแบบกระท่อนกระแท่น และเส้นทางข้อผิดพลาดแทบไม่ถูกทดสอบ
- **ระดับ 3 สร้างมาตรฐาน:** อนุกรมวิธานข้อผิดพลาดและข้อตกลงการจัดการร่วมกันถูกบันทึกและบังคับใช้ทั่วองค์กร การตรวจสอบที่ขอบเขต การลองใหม่แบบ idempotent พร้อม backoff และ jitter circuit breaker bulkhead และการห่อข้อผิดพลาดเป็นมาตรฐาน จัดหาโดยไลบรารีกลาง และทุกข้อผิดพลาดป้อนเข้าไปป์ไลน์สังเกตระบบรวมศูนย์
- **ระดับ 4 บริหารจัดการ:** พฤติกรรมการจัดการข้อผิดพลาดถูกวัดเทียบกับเส้นฐานและควบคุมด้วยข้อมูล อัตราการลองใหม่ จำนวนครั้งที่ circuit breaker ทริป จำนวน timeout ข้อค้นพบข้อผิดพลาดที่ถูกกลืนจากการวิเคราะห์เชิงสถิต เวลาเฉลี่ยในการกู้คืน และอัตราความล้มเหลวจากการเปลี่ยนแปลง ถูกติดตามรายบริการ เกณฑ์ของ circuit breaker และ timeout ถูกปรับจูนจากข้อมูลความหน่วงและความล้มเหลวที่สังเกตได้ แทนที่จะเดา การฉีดความล้มเหลวรันตามกำหนด และทีมทบทวนตัวชี้วัดเหล่านี้เพื่อจับการถดถอยและให้ทุกการเลือกล้มเร็วหรือล้มอย่างปลอดภัยมีหลักฐานรองรับ
- **ระดับ 5 ประสานทั้งระบบ:** ความทนทานถูกผนวกกับการส่งมอบและการวางแผนความเสี่ยง และปรับปรุงอย่างต่อเนื่อง อนุกรมวิธาน ไลบรารีกลาง และมาตรฐานพัฒนาจากทุกเหตุการณ์ขัดข้อง การทดลอง chaos และการฉีดความล้มเหลวเป็นกิจวัตร และองค์กรปรับ timeout เกณฑ์ breaker กลยุทธ์การลดระดับบริการ และการตัดสินใจที่ขอบเขต ตามที่ทราฟฟิก บริการที่พึ่งพา และภาพความเสี่ยงเปลี่ยนไป

## ประเด็นชวนคุย

1. ในโค้ดเบสของคุณ ข้อผิดพลาดถูกกลืนที่ไหนบ้างในตอนนี้ และคุณจะรู้ได้อย่างไรว่าคุณคิดผิดที่เชื่อว่าไม่มี?
2. การเขียนข้อมูลอันไหนของคุณเป็น idempotent และอันไหนจะทำงานซ้ำสองครั้งถ้าการลองใหม่ทำงานหลังข้อความตอบรับหาย?
3. "ไม่พบผู้ใช้" ควรเป็นข้อยกเว้น ค่าข้อผิดพลาด หรือผลลัพธ์ปกติ และทีมของคุณตอบเรื่องนี้ตรงกันหรือไม่?
4. กฎจริงๆ ของคุณเกี่ยวกับตำแหน่งที่ต้องตรวจสอบข้อมูลคืออะไร และคุณชี้ได้หรือไม่ว่ามีขอบเขตไหนที่เชื่อข้อมูลที่ไม่ควรเชื่อ?
5. คุณตัดสินเกณฑ์และช่วงพักเย็นของ circuit breaker อย่างไร และจะรู้ได้อย่างไรว่าค่าปัจจุบันผิด?
6. ถ้าผู้ตรวจสอบขอดูทุกความล้มเหลวที่ระบบของคุณเจอเมื่อเดือนที่แล้ว คุณจะส่งให้ได้หรือไม่ โดยจัดหมวดหมู่และมีบริบทครบ?

## ข้อสรุปสำคัญ

- แยกข้อบกพร่อง ข้อผิดพลาด และความล้มเหลวให้ออก และตัดห่วงโซ่ก่อนที่ข้อผิดพลาดภายในจะกลายเป็นความล้มเหลวที่มองเห็นได้
- เลือกล้มเร็วหรือล้มอย่างปลอดภัยอย่างตั้งใจทีละขอบเขต และทำให้สัญญาการจัดการข้อผิดพลาดของทุกฟังก์ชันชัดเจน
- ตรวจสอบให้เข้มที่ขอบเขตความเชื่อถือ และเชื่อใจภายใน การป้องกันที่ปิดบังความล้มเหลวคือการเลื่อนปัญหา ไม่ใช่ความปลอดภัย
- ทำให้การลองใหม่ปลอดภัยด้วย idempotence, timeout, exponential backoff และ jitter และเพิ่ม circuit breaker กับการลดระดับบริการอย่างสง่างามในโค้ด
- ห่อข้อผิดพลาดด้วยบริบท ส่งเข้าระบบสังเกตการณ์ และอย่ากลืนมัน ทุกข้อผิดพลาดต้องถูกจัดการ ส่งต่อ หรือถูกล็อกและเปิดเผย
