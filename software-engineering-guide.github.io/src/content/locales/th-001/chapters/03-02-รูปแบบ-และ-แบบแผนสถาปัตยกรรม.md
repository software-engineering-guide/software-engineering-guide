# 3.2 รูปแบบและแบบแผนสถาปัตยกรรม

## ภาพรวมและแรงจูงใจ

รูปแบบสถาปัตยกรรม (architectural style) คือรูปทรงกว้าง ๆ ที่นำกลับมาใช้ซ้ำได้ในการจัดระบบ ได้แก่ ระบบถูกแยกส่วนอย่างไร ส่วนต่าง ๆ สื่อสารกันอย่างไร และเส้นแบ่งอยู่ตรงไหน การเลือกรูปแบบเป็นหนึ่งในการตัดสินใจที่ส่งผลมากที่สุด (และถูกเข้าใจผิดมากที่สุด) ที่องค์กรขนาดใหญ่ทำ บ่อยครั้งการเลือกตามกระแส ("ใคร ๆ ก็ทำ [ไมโครเซอร์วิส](https://en.wikipedia.org/wiki/Microservices)") แทนที่จะดูข้อจำกัดจริงของทีม โดเมน และสภาพการดำเนินงาน ผลที่ได้คือความยุ่งเหยิงสองแบบอย่างใดอย่างหนึ่ง คือระบบกระจายที่องค์กรดำเนินการไม่ไหว หรือ [โมโนลิธ](https://en.wikipedia.org/wiki/Monolithic_application) พันกันยุ่งที่ไม่มีใครแก้ไขได้อย่างปลอดภัย ทั้งสองอย่างไม่ใช่ความผิดของรูปแบบ ทั้งคู่เกิดจากการเลือกรูปแบบที่ไม่เข้ากับสถานการณ์

สำหรับทีมพัฒนาขนาดใหญ่ รูปแบบสำคัญเหนือสิ่งอื่นเพราะ [กฎของคอนเวย์](https://en.wikipedia.org/wiki/Conway%27s_law) โครงสร้างของระบบมักสะท้อนโครงสร้างการสื่อสารขององค์กรที่สร้างมัน ดังนั้นรูปแบบสถาปัตยกรรมจึงเป็นการตัดสินใจด้านการออกแบบองค์กรด้วย การแบ่งระบบเป็นบริการจริง ๆ แล้วคือการตัดสินใจแบ่งทีม ความเป็นเจ้าของ และความรับผิดชอบเวรเฝ้าระบบ (on-call) องค์กรที่มีวิศวกรหลายร้อยคนรับภาระ (และมักจำเป็นต้องมี) บริการแบบละเอียดที่ติดตั้งใช้งานได้อิสระ เพราะความเป็นอิสระนั้นคือวิธีที่หลายทีมส่งงานโดยไม่ขวางกัน แต่ถ้าบังคับรูปแบบเดียวกันกับทีมเล็กทีมเดียว ทีมนั้นจะรับภาษีด้านการดำเนินงานทั้งหมดโดยไม่ได้ประโยชน์ด้านองค์กรเลย

ภาครัฐและองค์กรขนาดใหญ่เพิ่มข้อจำกัดอีกมาก ได้แก่ อายุระบบที่ยาว การควบคุมการเปลี่ยนแปลงที่เข้มงวด วงรอบการจัดซื้อ การเชื่อมกับระบบบันทึกหลักที่ฝังรากลึก และการตรวจสอบย้อนหลังได้ สิ่งเหล่านี้เอื้อต่อรูปแบบที่ทำให้ขอบเขตชัดเจนและตรวจสอบการพึ่งพากันได้ง่าย บทนี้สำรวจรูปแบบหลัก ๆ ตั้งแต่โมโนลิธไปจนถึงไมโครเซอร์วิส [สถาปัตยกรรมขับเคลื่อนด้วยเหตุการณ์](https://en.wikipedia.org/wiki/Event-driven_architecture) กับ [CQRS](https://en.wikipedia.org/wiki/Command_Query_Responsibility_Segregation) และ event sourcing [service mesh](https://en.wikipedia.org/wiki/Service_mesh) และรูปแบบเกตเวย์ [serverless](https://en.wikipedia.org/wiki/Serverless_computing) และวินัยภายในของสถาปัตยกรรม [hexagonal](https://en.wikipedia.org/wiki/Hexagonal_architecture_(software)) และ clean ที่สำคัญกว่านั้น บทนี้ช่วยให้คุณบอกได้ว่าแต่ละแบบเหมาะเมื่อใด

*ดูเพิ่มเติม:* บทที่ 2.2 (หลักการออกแบบซอฟต์แวร์ รวมถึง [Domain-Driven Design](https://en.wikipedia.org/wiki/Domain-driven_design)) บทที่ 3.1 (พื้นฐานสถาปัตยกรรม) และบทที่ 3.3 (ระบบกระจาย)

## หลักการสำคัญ

- **รูปแบบตามแรงที่กระทำ ไม่ใช่ตามกระแส.** เลือกจากขนาดทีม ความซับซ้อนของโดเมน ภาระ และความพร้อมด้านการดำเนินงาน ไม่ใช่เพราะเทคโนโลยีนั้นได้รับความนิยม
- **ศัตรูตัวจริงคือการพึ่งพากัน (coupling) ไม่ใช่จำนวนหน่วยที่ติดตั้งใช้งาน.** โมโนลิธที่แบ่งโมดูลดีชนะระบบกระจายที่เป็นก้อนโคลนใหญ่
- **การกระจายคือต้นทุนที่จ่ายเพื่อความเป็นอิสระ.** แยกก็ต่อเมื่อคุณค่าของการติดตั้งใช้งาน ขยายระบบ หรือแยกความล้มเหลวอย่างอิสระ มากกว่าต้นทุนของการเรียกผ่านเครือข่าย ความล้มเหลวบางส่วน และความสอดคล้องของข้อมูลข้ามบริการ
- **ขอบเขตควรตามโดเมนธุรกิจ.** จัดบริการและโมดูลให้ตรงกับ bounded context (แต่ละอันคือโมเดลโดเมนที่สมบูรณ์ในตัวและมีขอบเขตชัดเจนของตัวเอง) ไม่ใช่ตามชั้นทางเทคนิค
- **ออกแบบด้านในให้ดีไม่ว่าด้านนอกจะเป็นอย่างไร.** การแบ่งชั้นแบบ hexagonal/clean ทำให้ตรรกะธุรกิจเป็นอิสระจากเฟรมเวิร์กและโครงสร้างพื้นฐานในทุกรูปแบบ
- **กฎของคอนเวย์หลีกเลี่ยงไม่ได้ ดังนั้นใช้ให้เป็นประโยชน์.** ออกแบบขอบเขตทีมและสถาปัตยกรรมไปด้วยกัน
- **เริ่มให้ง่ายกว่าที่คิดว่าต้องใช้.** คุณแยกบริการออกจากโมโนลิธแบบแยกโมดูลที่ดีได้ แต่การถอนการกระจายจากไมโครเซอร์วิสที่เร็วเกินไปยากกว่ามาก

## ข้อแนะนำ

### ใช้โมโนลิธแบบแยกโมดูลเป็นค่าเริ่มต้น แยกเมื่อมีหลักฐาน

เริ่มระบบส่วนใหญ่เป็นหน่วยติดตั้งใช้งานเดียวที่มีขอบเขตโมดูลภายในแข็งแรง ได้แก่ อินเทอร์เฟซชัดเจน ไม่ล้วงเข้าไปในข้อมูลของโมดูลอื่น และมีกฎการพึ่งพาที่บังคับใช้จริง คุณจะได้ธุรกรรมที่เรียบง่าย ปรับโครงสร้างโค้ดง่าย และมีสิ่งเดียวให้ติดตั้งและสังเกต แยกโมดูลเป็นบริการของตัวเองเมื่อมีเหตุผลที่เป็นรูปธรรมเท่านั้น เช่น ส่วนที่ต้องขยายเอง ทีมที่ต้องติดตั้งตามจังหวะของตัวเอง โดเมนความล้มเหลวที่ต้องแยก หรือข้อกำหนดด้านเทคโนโลยีที่ต่างจากที่เหลือ เมื่อแยก ให้แยกตามเส้น bounded context เพื่อให้แต่ละบริการเป็นเจ้าของข้อมูลของตัวเองและเปิดสัญญาที่เสถียร

### รู้ว่าไมโครเซอร์วิสคุ้มค่าเมื่อใด

ไมโครเซอร์วิสให้การติดตั้งใช้งานอิสระ การขยายอิสระ การแยกความล้มเหลว และอิสระในการผสมเทคโนโลยี แลกกับการที่ต้องมี CI/CD (การรวมระบบและการส่งมอบต่อเนื่อง) ที่เติบโตแล้ว โครงสร้างพื้นฐานอัตโนมัติ การติดตามแบบกระจาย (distributed tracing) การค้นหาบริการ และวัฒนธรรมเวรเฝ้าระบบ ถามตัวเองอย่างซื่อสัตย์ว่า องค์กรของคุณรันบริการที่ติดตั้งอิสระหลายสิบตัวในระบบจริงได้อย่างน่าเชื่อถือหรือไม่ ถ้าแพลตฟอร์มและความพร้อมด้านการดำเนินงานยังไม่มี ไมโครเซอร์วิสก็แค่คูณโหมดความล้มเหลวโดยไม่ให้ประโยชน์ องค์กรจำนวนมากทำได้ดีที่สุดด้วยบริการขนาดใหญ่หยิบมือที่ตรงกับโดเมนหลัก ไม่ใช่ฝูงบริการจิ๋ว

### ใช้สถาปัตยกรรมขับเคลื่อนด้วยเหตุการณ์ในที่ที่การแยกส่วนและอะซิงโครนัสให้ผลคุ้ม

สถาปัตยกรรมขับเคลื่อนด้วยเหตุการณ์ให้ผู้ผลิตปล่อยข้อเท็จจริงโดยไม่ต้องรู้ว่าใครบริโภค ซึ่งให้การพึ่งพากันหลวม ตัวกันชนสำหรับภาระพุ่ง และวิธีเพิ่มผู้บริโภคใหม่ได้ง่าย ใช้ในที่ที่ขั้นตอนงานเป็นอะซิงโครนัสและตอบสนองตามธรรมชาติ **CQRS** (Command Query Responsibility Segregation) แยกโมเดลการเขียนออกจากโมเดลการอ่านตั้งแต่หนึ่งแบบขึ้นไป ซึ่งช่วยเมื่อภาระหรือรูปร่างของการอ่านและการเขียนต่างกันมาก **Event sourcing** เก็บสถานะเป็นบันทึกเหตุการณ์แบบต่อท้ายเท่านั้นแทนสถานะปัจจุบัน ให้ร่องรอยการตรวจสอบที่สมบูรณ์และการย้อนเวลา ซึ่งทรงพลังสำหรับการเงินและภาครัฐที่ "เรามาถึงค่านี้ได้อย่างไร" เป็นคำถามทางกฎหมาย แต่เพิ่มความซับซ้อนจริงในการจัดเวอร์ชันเหตุการณ์ การสร้างโปรเจกชันใหม่ และการใช้เหตุผลกับความสอดคล้องในที่สุด (eventual consistency) เลือกใช้อย่างตั้งใจ ไม่ใช่เป็นค่าเริ่มต้น

### ใช้รูปแบบเกตเวย์ BFF และ mesh เพื่อจัดการบริการจำนวนมาก

**API gateway** ให้ไคลเอนต์ภายนอกมีจุดเข้าเดียว จัดการการยืนยันตัวตน การจำกัดอัตรา การกำหนดเส้นทาง และการยุติ [TLS](https://en.wikipedia.org/wiki/Transport_Layer_Security) (Transport Layer Security) **Backend-for-Frontend (BFF)** ให้ไคลเอนต์แต่ละประเภท (เว็บ มือถือ API ของพันธมิตร) มีชั้นรวบรวมข้อมูลที่ตัดเย็บเฉพาะของตัวเอง เพื่อหลีกเลี่ยง API แบบเดียวใช้ทุกกรณีที่บวมเกินไป **Service mesh** ย้ายประเด็นที่ตัดผ่านหลายส่วน (mutual TLS การลองใหม่ การหมดเวลา การเลื่อนทราฟฟิก และเทเลเมทรี) ไปไว้ในชั้นโครงสร้างพื้นฐานแบบ sidecar เพื่อไม่ให้ทีมแอปพลิเคชันต้องสร้างซ้ำ เพิ่ม mesh ก็ต่อเมื่อจำนวนบริการทำให้การจัดการเรื่องเหล่านี้รายบริการจัดการไม่ไหว สำหรับบริการไม่กี่ตัว mesh เป็นภาระการดำเนินงานที่ไม่คุ้มค่า

### ชั่งน้ำหนัก serverless อย่างซื่อสัตย์

Function-as-a-service และแพลตฟอร์ม serverless ที่มีผู้ให้บริการดูแลเอาการจัดการเซิร์ฟเวอร์ออกจากมือคุณ ขยายลงถึงศูนย์ได้ และคิดเงินตามการใช้ ซึ่งเหมาะกับงานที่พุ่งเป็นช่วง ๆ ขับเคลื่อนด้วยเหตุการณ์ หรือมีภาระพื้นฐานต่ำ และเหมาะกับทีมเล็ก ข้อแลกเปลี่ยนเป็นของจริง ได้แก่ ความหน่วงตอนเริ่มเย็น (cold start) ข้อจำกัดด้านเวลาประมวลผลและทรัพยากร การทดสอบในเครื่องที่ยากขึ้น การผูกติดผู้ขายที่เป็นไปได้ และต้นทุนที่อาจสูงกว่าโครงสร้างพื้นฐานที่จัดสรรไว้เมื่อปริมาณสูงต่อเนื่อง ใช้ serverless ในที่ที่เศรษฐศาสตร์และความเรียบง่ายด้านการดำเนินงานชนะอย่างชัดเจน อย่าบังคับระบบหลักที่ปริมาณสูงและคงที่เข้าไปเพราะความกระตือรือร้น

### รักษาตรรกะธุรกิจให้สะอาดภายในทุกบริการ

ไม่ว่ารูปแบบภายนอกเป็นอย่างไร ให้รักษาด้านในให้สะอาดด้วย **hexagonal (ports and adapters)** หรือ **clean architecture** คือกฎธุรกิจอยู่ตรงกลาง พึ่งพาเพียงนามธรรม ส่วนเฟรมเวิร์ก ฐานข้อมูล และการส่งข้อความอยู่ที่ขอบเป็นอะแดปเตอร์ที่เปลี่ยนได้ วิธีนี้ทำให้ตรรกะโดเมนที่มีค่าของคุณทดสอบได้โดยไม่ต้องมีโครงสร้างพื้นฐานและพกพาข้ามการเปลี่ยนเทคโนโลยีได้ ซึ่งเป็นข้อได้เปรียบชี้ขาดสำหรับระบบภาครัฐและองค์กรอายุยาวที่จะอยู่นานกว่าเฟรมเวิร์กหลายรุ่น

## ข้อดีข้อเสียและการแลกเปลี่ยน

| รูปแบบ | เหมาะที่สุดเมื่อ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| โมโนลิธแบบแยกโมดูล | ระบบส่วนใหญ่ โดยเฉพาะช่วงแรก | ดำเนินงานง่าย ธุรกรรมและการปรับโครงสร้างโค้ดง่าย | หน่วยติดตั้งเดียว ขยายพร้อมกันทั้งก้อน เสี่ยงสึกกร่อน |
| ไมโครเซอร์วิส | หลายทีม ขนาดใหญ่ แพลตฟอร์มพร้อม | ติดตั้งและขยายอิสระ แยกความล้มเหลว | ความซับซ้อนแบบกระจาย ความสอดคล้องของข้อมูล ต้นทุนดำเนินงานสูง |
| ขับเคลื่อนด้วยเหตุการณ์ / CQRS / event sourcing | ขั้นตอนงานอะซิงโครนัส ต้องการตรวจสอบย้อนหลัง การอ่านและเขียนต่างกันมาก | พึ่งพากันหลวม ตรวจสอบย้อนหลังได้ ขยายการอ่านได้ | ความสอดคล้องในที่สุด การจัดเวอร์ชันเหตุการณ์ ดีบักยากกว่า |
| Serverless | งานพุ่งเป็นช่วงหรือภาระพื้นฐานต่ำ ขับเคลื่อนด้วยเหตุการณ์ | ไม่ต้องจัดการเซิร์ฟเวอร์ ขยายลงถึงศูนย์ จ่ายตามการใช้ | cold start ข้อจำกัด การผูกติดผู้ขาย ต้นทุนสูงเมื่อภาระสูงคงที่ |

ธีมที่เกิดซ้ำคือ คุณซื้อความยืดหยุ่นและความเป็นอิสระด้วยความซับซ้อนด้านการดำเนินงานและด้านความคิด รูปแบบกระจายและขับเคลื่อนด้วยเหตุการณ์ยอมสละความเรียบง่ายของ call stack เดียวและธุรกรรมเดียว เพื่อแลกกับความสามารถในการขยาย ติดตั้ง และล้มเหลวอย่างอิสระ ข้อแลกเปลี่ยนนี้คุ้มเมื่อขนาดใหญ่และมีแพลตฟอร์มที่เติบโตแล้ว ถ้าไม่มี มันคือหายนะ วินัยภายใน (hexagonal/clean) แทบทุกครั้งคุ้มค่า เพราะต้นทุนต่ำและรักษาทางเลือกให้เปลี่ยนรูปแบบได้ภายหลัง

## คำถามที่ควรคุยกับทีม

1. **ก่อนแยกบริการถัดไป คุณจะแยกทีมที่เป็นเจ้าของบริการนั้นด้วยหรือไม่ และใครมีอำนาจทำเช่นนั้น?** กฎของคอนเวย์หมายความว่าเส้นแบ่งบริการคือเส้นแบ่งทีมจริง ๆ การแยกที่แผนผังองค์กรไม่รองรับจะได้โมโนลิธแบบกระจาย คือมีสองหน่วยติดตั้งแต่ใช้รอบปล่อยเดียวและเวรเฝ้าระบบร่วมกัน ในองค์กรขนาดใหญ่ อำนาจจัดโครงสร้างทีมมักอยู่เหนือฝ่ายวิศวกรรม คือสายการบังคับบัญชา การเงิน และ HR ซึ่งเป็นเหตุผลที่สถาปัตยกรรมและการออกแบบองค์กรต้องตัดสินใจไปด้วยกัน นำหลักฐานมาคุย บริการที่เสนอมีทีมที่เป็นเจ้าของตั้งแต่ต้นจนจบ จัดเวรเฝ้าระบบของตัวเอง และติดตั้งตามจังหวะของตัวเองได้หรือไม่ ถ้าไม่ ให้จัดสรรทุนให้ทีมหรือเก็บความสามารถนั้นเป็นโมดูลในโมโนลิธ การแยกโค้ดโดยไม่แยกความเป็นเจ้าของได้ต้นทุนทุกอย่างของการกระจายและไม่ได้ความเป็นอิสระเลย

2. **วันนี้คุณติดตั้งแต่ละบริการอย่างอิสระได้จริงหรือไม่ หรือพวกมันส่งพร้อมกันแบบซ่อนอยู่?** โมโนลิธแบบกระจายคือผลลัพธ์ที่แย่ที่สุดในบทนี้ คุณจ่ายค่าการเรียกผ่านเครือข่าย ความล้มเหลวบางส่วน และความสอดคล้องของข้อมูลข้ามบริการ แต่ก็ยังปล่อยตัวหนึ่งโดยไม่ปล่อยตัวอื่นไม่ได้ สัญญาณบอกเหตุคือฐานข้อมูลร่วม ไลบรารีร่วมที่บังคับให้อัปเกรดพร้อมกัน และการทดสอบบูรณาการที่ต้องรันทั้งระบบรวมกัน สำหรับทีมใหญ่ นี่จำกัดผลผลิตอย่างเงียบ ๆ เพราะทุกทีมต่อคิวรอรอบปล่อยเดียวทั้งที่แผนภาพแสดงความเป็นอิสระ ลองหยิบการเปลี่ยนแปลงล่าสุดหนึ่งรายการแล้วนับว่ามีกี่บริการที่ต้องติดตั้งพร้อมกันจึงจะปลอดภัย ถ้าจำนวนนั้นมากกว่าหนึ่งสำหรับการเปลี่ยนที่แตะความสามารถเดียว ขอบเขตของคุณผิด ทางแก้มักเป็นการให้แต่ละบริการมีข้อมูลของตัวเองและสัญญาที่เสถียรมีเวอร์ชัน ไม่ใช่เพิ่มบริการอีก

3. **การแยกบริการที่มีอยู่ข้อใดเลิกคุ้มค่าแล้ว และคุณจะรวมกลับหรือไม่?** นิสัยขั้นสูงสุดของบทนี้คือมองการตัดสินใจเรื่องรูปแบบเป็นสิ่งที่ย้อนกลับได้ คือแยกเมื่อมีปัจจัยขับเคลื่อน และรวมกลับเมื่อปัจจัยนั้นหายไป องค์กรส่วนใหญ่แยกอย่างเดียว ทำให้นาโนเซอร์วิสและบริการเอนทิตีที่คุยกันจุกจิกสะสมจนภาระการประสานงานและเครือข่ายใหญ่กว่างานที่แต่ละบริการทำ มองหาบริการที่ติดตั้งพร้อมกันเสมอ ที่ดำรงอยู่เพราะตารางฐานข้อมูลไม่ใช่ความสามารถทางธุรกิจ หรือที่การกระโดดผ่านเครือข่ายครองความหน่วงของคำขอไปแล้ว ในองค์กรขนาดใหญ่และภาครัฐ ที่มีการตรวจสอบจำนวนคนและงบประมาณ การพับบริการบางสองตัวกลับเป็นบริการขนาดใหญ่ตัวเดียวเป็นการเคลื่อนไหวที่ชอบธรรมและประหยัดต้นทุน ไม่ใช่การยอมรับความล้มเหลว นำการรวมกลับขึ้นโต๊ะอย่างเปิดเผยเท่ากับการแยก และตัดสินทั้งสองด้วยหลักฐานชุดเดียวกัน

4. **แพลตฟอร์มและความพร้อมด้านเวรเฝ้าระบบของคุณรองรับรูปแบบที่คุณเสนอได้จริงหรือไม่ และคุณระบุช่องว่างเฉพาะเจาะจงได้หรือไม่ก่อนผูกมัด?** ไมโครเซอร์วิส mesh และแกนหลักขับเคลื่อนด้วยเหตุการณ์ให้ประโยชน์ก็ต่อเมื่อวางบน CI/CD ที่เติบโต การติดตามแบบกระจาย การค้นหาบริการ และวัฒนธรรมเวรเฝ้าระบบที่คิดเรื่องความล้มเหลวบางส่วนได้ องค์กรใหญ่มักตัดสินรูปแบบเป้าหมายในเวทีสถาปัตยกรรมแล้วค้นพบแพลตฟอร์มที่ขาดทีหลัง เมื่อมีบริการหลายสิบตัวในระบบจริงแล้วและทุกเหตุขัดข้องใช้เวลาเป็นชั่วโมงในการวินิจฉัย ชั่งความน่าดึงดูดของการติดตั้งและขยายอิสระเทียบกับคำถามเรียบ ๆ ว่าใครรันมันตอนตีสาม การแยกที่ปลดปล่อยทีมให้ส่งงานขนานกันก็คูณโหมดความล้มเหลวที่แต่ละทีมต้องเข้าใจเช่นกัน นำการสำรวจอย่างซื่อสัตย์มาคุย ได้แก่ ความถี่ในการติดตั้งปัจจุบัน เวลาเฉลี่ยในการกู้คืน (MTTR) มีการติดตามข้ามขอบเขตบริการหรือไม่ และทีมหนึ่งดูแลบริการได้จริงกี่ตัว ในองค์กรขนาดใหญ่และภาครัฐ ให้เพิ่มระยะเวลานำของการจัดซื้อและการจ้างงานสำหรับความสามารถแพลตฟอร์มที่คุณขาด เพราะรูปแบบที่สมมติว่ามี mesh และทีมแพลตฟอร์มที่คุณยังไม่ได้จัดสรรทุนคือแผนที่จะดูแลระบบที่รองรับไม่ไหว

5. **ส่วนไหนของโดเมนที่ร่องรอยการตรวจสอบแบบ event sourcing เต็มรูปแบบเป็นความจำเป็นทางกฎหมาย ไม่ใช่แค่ความสะดวก และใครมีอำนาจตัดสิน?** Event sourcing และ CQRS ให้ประวัติที่สมบูรณ์และสร้างคืนได้และโมเดลการอ่านที่ขยายได้เอง แต่คุณต้องจ่ายด้วยการจัดเวอร์ชันเหตุการณ์ การสร้างโปรเจกชันใหม่ และการใช้เหตุผลกับความสอดคล้องในที่สุดตลอดอายุระบบ ถ้าใช้กับโดเมนที่ไม่เคยต้องการร่องรอยการตรวจสอบ ความซับซ้อนนั้นคือภาษีล้วน ๆ ถ้าไม่ใช้กับโดเมนที่ "เรามาถึงค่านี้ได้อย่างไร" เป็นคำถามทางกฎหมาย การไม่มีมันคือความล้มเหลวด้านการปฏิบัติตามข้อกำหนด ข้อพิจารณาที่แข่งกันคือการตรวจสอบย้อนหลังได้และการขยายการสืบค้นด้านหนึ่ง กับความยากในการดีบักและภาระทางความคิดของนักพัฒนาอีกด้านหนึ่ง การตัดสินใจจึงควรอยู่กับคนที่เข้าใจทั้งภาระผูกพันตามกฎหมายและภาระการดำเนินงาน ไม่ใช่คนที่กระตือรือร้นกับแบบแผนนี้มากที่สุด นำข้อกำหนดทางกฎหมายหรือสัญญาเรื่องการเก็บรักษาและการสร้างคืน ปริมาณเหตุการณ์ที่คาดไว้ และการประมาณงานจัดเวอร์ชันและโปรเจกชันอย่างซื่อสัตย์มาคุย ในการเงิน ภาษี และภาครัฐ ที่การสร้างการตัดสินใจคืนอีกหลายปีต่อมาอาจเป็นหน้าที่ตามกฎหมาย จงระบุเจ้าของผู้รับผิดชอบที่ลงนามว่า bounded context หนึ่งต้องหรือไม่ต้องมีบันทึกเหตุการณ์ที่เปลี่ยนแปลงไม่ได้

6. **คุณจะป้องกันไม่ให้โมโนลิธแบบแยกโมดูลสึกกร่อนอย่างไร เพื่อให้การแยกในภายหลังยังคงถูก และอะไรจะบังคับขอบเขต?** เหตุผลทั้งหมดของการเริ่มด้วยโมโนลิธแบบแยกโมดูลอยู่บนคำมั่นว่าขอบเขตภายในที่สะอาดทำให้การแยกบริการภายหลังจ่ายไหว แต่ขอบเขตเหล่านั้นเสื่อมอย่างเงียบ ๆ ทันทีที่กำหนดส่งล่อให้โมดูลหนึ่งล้วงข้อมูลของอีกโมดูล สำหรับทีมใหญ่ที่มีผู้ร่วมพัฒนามาก ความตั้งใจดีและการทบทวนโค้ดอย่างเดียวรักษาเส้นไว้ไม่ได้ ถ้าไม่มีกลไกบังคับ โมโนลิธจะค่อย ๆ กลายเป็นก้อนโคลนใหญ่ที่รูปแบบนี้ตั้งใจจะหลีกเลี่ยง ชั่งแรงเสียดทานของกฎการพึ่งพาและอินเทอร์เฟซโมดูลที่บังคับใช้ เทียบกับต้นทุนของการค้นพบหลายปีต่อมาว่าไม่มีขอบเขตใดเป็นจริงและทุกการแยกหมายถึงการแกะสถานะร่วม นำหลักฐานมาคุย ขอบเขตโมดูลถูกบังคับด้วยเครื่องมือบิลด์ การวิเคราะห์เชิงสถิต หรือโครงสร้างแพ็กเกจ หรือเป็นเพียงข้อตกลงที่บันทึกไว้ซึ่งการรวมโค้ดหกครั้งล่าสุดเมินไป ในระบบองค์กรและภาครัฐอายุยาวที่ต้องผ่านการควบคุมการเปลี่ยนแปลงเข้มงวดและเฟรมเวิร์กหลายรุ่น จงมองการบังคับขอบเขตเป็นมาตรการควบคุมที่ตรวจสอบได้ เพื่อให้ทางเลือกที่จะกระจายภายหลังเป็นสิ่งที่คุณรักษาไว้จริง ไม่ใช่สิ่งที่คุณสมมติว่ายังมี

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ใช้โมโนลิธแบบแยกโมดูลเดียวเป็นค่าเริ่มต้นและต้านแรงดึงของไมโครเซอร์วิส เพราะทรัพยากรที่หายากที่สุดของคุณคือความใส่ใจทางวิศวกรรม และฝูงบริการคือภาษีด้านการดำเนินงานที่คุณจ่ายไม่ไหวก่อนค้นพบความเหมาะสมของผลิตภัณฑ์กับตลาด รักษาขอบเขตโมดูลให้สะอาดเพื่อแยกภายหลังได้ และใช้ serverless ในที่ที่การขยายลงถึงศูนย์และการจ่ายตามการใช้เหมาะกับภาระที่พุ่งเป็นช่วงและพื้นฐานต่ำของคุณ แยกเพียงอย่างเดียวเมื่อมีปัจจัยที่เป็นรูปธรรมปรากฏ เช่น ตัวส่งการแจ้งเตือนที่พุ่งเป็นช่วง และอย่าแยกก่อนหน้านั้น

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีทีมแพลตฟอร์มและงบจำกัด ให้เลือกโมโนลิธหรือบริการขนาดใหญ่หยิบมือบนแพลตฟอร์มที่มีผู้ให้บริการดูแล และซื้อโครงสร้างพื้นฐานแบบโฮสต์แทนการสร้าง mesh การติดตาม และการค้นหาบริการเอง ชั่งน้ำหนัก serverless และฐานข้อมูลที่มีผู้ให้บริการดูแลเป็นวิธีเลี่ยงการรันเซิร์ฟเวอร์เลย และระวังการออกแบบแบบกระจายที่คุณไม่มีใครแบกภาระด้านการดำเนินงาน สถาปัตยกรรมที่ใช่คือสถาปัตยกรรมที่คนหนึ่งหรือสองคนติดตั้ง สังเกต และกู้คืนได้จริง

**องค์กรขนาดใหญ่.** ปัญหาจริงคือหลายทีมและกฎของคอนเวย์ จัดบริการขนาดใหญ่ให้ตรงกับ bounded context และความเป็นเจ้าของของทีม และลงทุนอย่างตั้งใจในแพลตฟอร์ม (CI/CD การติดตาม mesh และการค้นหาบริการ) ที่ทำให้การกระจายปลอดภัย กำหนดมาตรฐานรูปแบบเกตเวย์ BFF และ clean architecture ภายในเพื่อให้กลุ่มต่าง ๆ เลิกประดิษฐ์ซ้ำ และกำกับดูแลการแยกและการรวมกลับเป็นการตัดสินใจเชิงพอร์ตโฟลิโอที่อิงหลักฐานแทนความชอบของท้องถิ่น จัดงบต้นทุนการดำเนินงานของทุกการแยกอย่างชัดเจน เพราะในขนาดของคุณ ความล้มเหลวแบบโมโนลิธกระจายนั้นแพงและแก้ช้า

**ภาครัฐ.** อายุระบบที่ยาว การควบคุมการเปลี่ยนแปลงที่เข้มงวด วงรอบการจัดซื้อ และการตรวจสอบย้อนหลังได้ กำหนดทางเลือก เลือกรูปแบบที่มีขอบเขตชัดเจนตรวจสอบได้และสัญญาที่คงทนซึ่งอยู่นานกว่าผู้ขายและเฟรมเวิร์กหลายรุ่น Event sourcing คุ้มความซับซ้อนในที่ที่การสร้างการตัดสินใจที่เกี่ยวกับประชาชนคืนเป็นหน้าที่ตามกฎหมาย จึงควรใช้อย่างตั้งใจกับบัญชีแยกประเภทหลัก และรักษา clean architecture ภายในทุกบริการเพื่อแยกกฎที่เปลี่ยนไปทุกงบประมาณ มองการพกพาได้และการออกจาก serverless หรือแพลตฟอร์มผู้ขายแบบเฉพาะเจ้าเป็นข้อกำหนดการจัดซื้อ ไม่ใช่เรื่องคิดทีหลัง

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสี่คนที่สร้างผลิตภัณฑ์จัดตารางเวลารู้สึกถูกกดดันให้เริ่มด้วยไมโครเซอร์วิสเพราะคู่แข่งเขียนบล็อกถึงมัน แต่พวกเขาต้านไว้ พวกเขาส่งโมโนลิธแบบแยกโมดูลเดียวที่มีขอบเขตภายในชัดเจน (การจัดตารางเวลา การเรียกเก็บเงิน การแจ้งเตือน) เป็นโมดูลแยกในหน่วยติดตั้งเดียว วิศวกรคนเดียวจึงรันทั้งระบบในเครื่องได้และการปล่อยคือการ push ครั้งเดียว เมื่อผลิตภัณฑ์เริ่มมีแรงฉุด มีเพียงตัวส่งการแจ้งเตือนซึ่งกระจายออกไปทางอีเมลและ SMS ภายใต้ภาระที่พุ่งเป็นช่วงที่ถูกดึงออกเป็นบริการของตัวเอง พวกเขาไม่ต้องรับภาษีด้านการดำเนินงานของบริการหนึ่งโหลขณะยังตามหาความเหมาะสมของผลิตภัณฑ์กับตลาด

**องค์กรขนาดใหญ่.** บริษัทอีคอมเมิร์ซขนาดใหญ่เริ่มจากโมโนลิธแบบแยกโมดูล เมื่อทราฟฟิกโตและทีมเพิ่ม บริษัทดึงโดเมนที่ภาระสูงสุดและวิวัฒน์อย่างอิสระที่สุด (แค็ตตาล็อก ตะกร้า ชำระเงิน และค้นหา) ออกเป็นบริการแยก แต่ละตัวเป็นเจ้าของข้อมูลของตัวเอง การชำระเงินปล่อยเหตุการณ์ที่คลังสินค้า การจัดส่ง และการวิเคราะห์บริโภคผ่านแกนหลักเหตุการณ์ ผู้บริโภคใหม่ (การตรวจจับการฉ้อโกง ระบบสะสมแต้ม) จึงเกาะเข้ามาได้โดยไม่แตะการชำระเงิน API gateway จัดการการยืนยันตัวตนและการจำกัดอัตรา และ BFF ปรับขนาดข้อมูลให้เหมาะกับมือถือ โดเมนที่ทราฟฟิกต่ำกว่าที่เหลืออยู่ในโมโนลิธ ซึ่งหลีกเลี่ยงการแตกกระจายที่ไม่จำเป็น

**ภาครัฐ.** หน่วยงานภาษีสร้างแพลตฟอร์มการประเมินบน event sourcing สำหรับบัญชีแยกประเภทหลัก เพราะทุกการเปลี่ยนแปลงภาระภาษีของผู้เสียภาษีต้องสร้างคืนได้และตรวจสอบตามกฎหมายได้นานหลายปี คำสั่ง (ยื่นแบบ ใช้การชำระเงิน ออกการปรับปรุง) ผลิตเหตุการณ์ที่เปลี่ยนแปลงไม่ได้ และโมเดลการอ่านฉายยอดคงเหลือปัจจุบันให้เจ้าหน้าที่และประชาชน CQRS ให้ฝั่งสืบค้นที่เปิดให้สาธารณะขยายเองได้ในฤดูยื่นภาษีช่วงพีคโดยไม่ทำให้ฝั่งเขียนเสี่ยง ภายใน แต่ละบริการเป็นไปตาม clean architecture กฎการประเมินซึ่งเปลี่ยนทุกงบประมาณจึงแยกออกจากเทคโนโลยีการจัดเก็บและการส่งข้อความ

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

เงินที่เดิมพันในการเลือกรูปแบบมหาศาล เพราะการตัดสินใจนี้ย้อนกลับแพง ถ้านำไมโครเซอร์วิสมาใช้เร็วเกินไป คุณจะทำให้ต้นทุนรวมตลอดอายุการใช้งาน (TCO) พองขึ้นจากการสร้างแพลตฟอร์ม โครงสร้างพื้นฐานซ้ำซ้อน การดีบักแบบกระจาย และภาระการดำเนินงานที่หนักขึ้น ซึ่งเป็นต้นทุนที่อยู่กับคุณตลอดอายุระบบ ถ้าปฏิเสธที่จะแยกโมโนลิธที่ล้นจริง ๆ คุณจะจำกัดผลผลิตการส่งมอบ ทีมต่อคิวรอรอบปล่อยร่วมและทุกการเปลี่ยนแปลงทำให้ทั้งระบบเสี่ยง การคุยเรื่องผลตอบแทนการลงทุน (ROI) จริง ๆ แล้วคือการจับคู่ค่าใช้จ่ายด้านการดำเนินงานกับความต้องการขององค์กร

นำเสนอเหตุผลต่อผู้บริหารในแง่ของผลผลิตและความเสี่ยง ไม่ใช่เทคโนโลยี การติดตั้งใช้งานอิสระหมายถึงหลายทีมส่งงานขนานกันและระยะเวลานำที่สั้นลง ซึ่งคือความเร็วทางธุรกิจที่วัดได้ การแยกความล้มเหลวหมายถึงการล่มทั้งระบบน้อยลงและรัศมีผลกระทบเล็กลง ซึ่งคือความพร้อมใช้งานและการปกป้องชื่อเสียงที่วัดได้ แต่ก็ต้องซื่อสัตย์พอ ๆ กันเรื่องการลงทุนแพลตฟอร์มที่แต่ละรูปแบบเรียกร้อง mesh การติดตาม และความเติบโตของ CI/CD เป็นข้อกำหนดเบื้องต้น ไม่ใช่ส่วนเสริม และต้นทุนของมันอยู่ใน TCO สำหรับหลายองค์กร เส้นทางที่ถูกที่สุดคือโมโนลิธแบบแยกโมดูลที่ดีในตอนนี้ พร้อมขอบเขตภายในที่สะอาดซึ่งทำให้การแยกภายหลังถูก วิธีนี้ซื้อทางเลือกที่จะกระจายโดยไม่ต้องจ่ายก่อนที่จะต้องใช้

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **โมโนลิธแบบกระจาย.** บริการที่ต้องติดตั้งพร้อมกันและใช้ฐานข้อมูลร่วม ได้ต้นทุนทั้งหมดของการกระจายและไม่ได้ความเป็นอิสระเลย
- **นาโนเซอร์วิส.** บริการที่ละเอียดจนภาระการประสานงานและเครือข่ายใหญ่กว่างานที่มันทำ
- **ไมโครเซอร์วิสโดยไม่มีแพลตฟอร์ม.** แยกก่อนมี CI/CD การติดตาม และความพร้อมด้านเวรเฝ้าระบบ โหมดความล้มเหลวคูณทวี
- **บริการเอนทิตี.** แยกตามตารางฐานข้อมูล ("บริการผู้ใช้" "บริการคำสั่งซื้อ") แทนที่จะแยกตามความสามารถทางธุรกิจ บังคับให้ต้องเรียกข้ามบริการจุกจิกทุกการดำเนินการ
- **Event sourcing ทุกที่.** ใช้กับโดเมนที่ไม่ต้องการร่องรอยการตรวจสอบ จ่ายภาษีความซับซ้อนโดยไม่ได้ประโยชน์
- **เกตเวย์เป็นโมโนลิธ.** ใส่ตรรกะธุรกิจใน API gateway สร้างจุดคอขวดกลางขึ้นมาใหม่
- **แกนหลักผูกกับเฟรมเวิร์ก.** ตรรกะธุรกิจพันกับเฟรมเวิร์กเว็บหรือ ORM (object-relational mapping) ทำให้ทั้งการทดสอบและการเปลี่ยนเทคโนโลยีเจ็บปวด

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1: เริ่มต้น.** รูปแบบถูกเลือกตามกระแสหรือโดยบังเอิญ คุณมีโมโนลิธพันกันยุ่งหนึ่งก้อนหรือความยุ่งเหยิงแบบกระจายโดยไม่ตั้งใจ ขอบเขตตามชั้นทางเทคนิคหรือประวัติศาสตร์แทนโดเมน และการแยกเกิดแบบตั้งรับเมื่อมีอะไรพัง
- **ระดับ 2: พัฒนา.** บางทีมวาดขอบเขตโมดูลอย่างตั้งใจภายในโมโนลิธหรือตั้งบริการขนาดใหญ่ไม่กี่ตัว และบางประเด็นที่ตัดผ่านหลายส่วนถูกจัดการอย่างสม่ำเสมอ แนวปฏิบัติไม่สม่ำเสมอ กลุ่มหนึ่งจัดบริการตาม bounded context ขณะที่อีกกลุ่มยังแยกตามตารางฐานข้อมูล และการแยกยังทำแบบเฉพาะกิจ
- **ระดับ 3: สร้างมาตรฐาน.** แนวทางที่บันทึกไว้ถูกบังคับใช้ทั้งองค์กร บริการสอดคล้องกับ bounded context และเป็นเจ้าของข้อมูลของตน ใช้รูปแบบเกตเวย์และ BFF ในที่ที่เหมาะสม การแบ่งชั้นภายในแบบ clean หรือ hexagonal เป็นมาตรฐาน และทุกการแยกต้องมีปัจจัยขับเคลื่อนที่ระบุไว้ ขอบเขตโมดูลถูกบังคับด้วยเครื่องมือ ไม่ใช่แค่ข้อตกลง
- **ระดับ 4: บริหารจัดการ.** การตัดสินใจเรื่องรูปแบบถูกวัดและควบคุมเทียบกับเส้นฐาน คุณติดตามความถี่ในการติดตั้งและระยะเวลานำต่อบริการ เวลาเฉลี่ยในการกู้คืน จำนวนบริการที่ต้องติดตั้งพร้อมกันสำหรับการเปลี่ยนแปลงทั่วไป และความหน่วงจากการกระโดดผ่านเครือข่าย และเทียบต้นทุนของแต่ละการแยกกับความเป็นอิสระที่มันควรซื้อ หลักฐาน ไม่ใช่ความชอบ เป็นตัวตัดสินว่าขอบเขตหนึ่งจะอยู่รอดหรือไม่ และการเบี่ยงไปสู่โมโนลิธแบบกระจายถูกจับด้วยตัวชี้วัดแทนที่จะเป็นเหตุล่ม
- **ระดับ 5: ประสานทั้งระบบ.** สถาปัตยกรรมถูกผสานกับการออกแบบองค์กรและปรับตัวอย่างต่อเนื่อง แพลตฟอร์มที่เติบโตแล้ว (CI/CD การติดตาม และ mesh ในที่ที่สมควร) ทำให้ทั้งการกระจายและการรวมกลับราคาถูก ทีมแยกเป็นประจำเมื่อมีปัจจัยขับเคลื่อนและพับบริการกลับเมื่อปัจจัยหายไป และการเลือกรูปแบบถูกปรับสมดุลใหม่ตามโครงสร้างทีม ภาระ และภาพความเสี่ยงที่เปลี่ยนทั่วทั้งระบบ

## ประเด็นชวนคุย

1. โมโนลิธเป็นจุดแข็งจริง ๆ ตรงไหนในระบบของคุณ และเป็นคอขวดจริง ๆ ตรงไหน
2. ปัจจัยขับเคลื่อนที่เป็นรูปธรรมอะไรจะทำให้การแยกบริการถัดไปของคุณสมเหตุสมผล และคุณระบุได้ก่อนสร้างหรือไม่
3. องค์กรของคุณมีความพร้อมด้านการดำเนินงานที่ไมโครเซอร์วิสเรียกร้องหรือไม่ อะไรที่ขาด
4. ส่วนไหนของโดเมนที่ร่องรอยการตรวจสอบแบบ event sourcing เต็มรูปแบบเป็นความจำเป็นทางกฎหมายหรือธุรกิจ เทียบกับแค่ดีถ้ามี
5. ขอบเขตบริการปัจจุบันของคุณสะท้อนขอบเขตทีมดีแค่ไหน และการสอดคล้องนั้นช่วยหรือทำร้าย
6. ถ้าคุณต้องเปลี่ยนเฟรมเวิร์กเว็บหรือฐานข้อมูลในปีหน้า คุณต้องเขียนตรรกะธุรกิจใหม่มากแค่ไหน

## ข้อสรุปสำคัญ

- เลือกรูปแบบสถาปัตยกรรมจากแรงที่กระทำจริง (ขนาดทีม โดเมน ภาระ ความพร้อมด้านการดำเนินงาน) ไม่ใช่จากกระแส
- โมโนลิธแบบแยกโมดูลคือค่าเริ่มต้นที่ถูกต้องสำหรับระบบส่วนใหญ่ แยกบริการเมื่อมีปัจจัยขับเคลื่อนที่เป็นรูปธรรมและตามเส้น bounded context เท่านั้น
- ไมโครเซอร์วิสแลกความซับซ้อนด้านการดำเนินงานและความคิดกับการติดตั้ง ขยาย และแยกความล้มเหลวอย่างอิสระ และต้องมีแพลตฟอร์มที่เติบโตแล้ว
- ขับเคลื่อนด้วยเหตุการณ์ CQRS และ event sourcing ให้การแยกส่วนและการตรวจสอบย้อนหลังได้ โดยแลกกับความสอดคล้องในที่สุดและความซับซ้อนของการจัดเวอร์ชัน จงนำมาใช้อย่างตั้งใจ
- เกตเวย์ BFF และ mesh ช่วยควบคุมระบบที่มีบริการมาก แต่เพิ่มน้ำหนัก แนะนำเมื่อขนาดเรียกร้อง ไม่ใช่ก่อนหน้านั้น
- ใช้สถาปัตยกรรม hexagonal/clean ภายในทุกบริการเพื่อให้ตรรกะธุรกิจที่มีค่าทดสอบได้และคงทนข้ามการเปลี่ยนเทคโนโลยี
