# 3.8 ความสามารถในการทำงานร่วมกันและมาตรฐานเปิด

## ภาพรวมและแรงจูงใจ

[ความสามารถในการทำงานร่วมกัน](https://en.wikipedia.org/wiki/Interoperability) (interoperability) คือความสามารถของระบบตั้งแต่สองระบบขึ้นไปในการแลกเปลี่ยนข้อมูลและนำข้อมูลที่แลกเปลี่ยนกันไปใช้ได้ โดยที่ทั้งสองฝ่ายไม่ต้องรู้การทำงานภายในของอีกฝ่าย **[มาตรฐานเปิด](https://en.wikipedia.org/wiki/Open_standard)** (open standard) คือข้อกำหนดที่เปิดเผยต่อสาธารณะ พัฒนาและดูแลผ่านกระบวนการที่โปร่งใสและอาศัยฉันทามติ และนำไปพัฒนาใช้ได้ฟรี (หรือภายใต้เงื่อนไขที่เป็นธรรม สมเหตุสมผล และไม่เลือกปฏิบัติ) เพื่อให้ใครก็สร้างระบบที่เป็นไปตามมาตรฐานได้โดยไม่ต้องขออนุญาตจากผู้ขายรายเดียว การออกแบบเพื่อความสามารถในการทำงานร่วมกันหมายถึงการสร้างระบบที่เชื่อมต่อกันผ่านข้อกำหนดที่เผยแพร่และใช้ร่วมกันเหล่านี้ แทนที่จะผ่าน**การเชื่อมต่อแบบสั่งทำเฉพาะ** (bespoke integration) ซึ่งเป็นตัวเชื่อมที่สร้างขึ้นเฉพาะงานเพื่อเชื่อมสองระบบพอดี และต้องสร้างใหม่ทุกครั้งที่ฝ่ายใดฝ่ายหนึ่งเปลี่ยนแปลง

สำหรับองค์กรขนาดใหญ่ ความสามารถในการทำงานร่วมกันไม่ใช่ของตกแต่ง แต่เป็นพื้นฐานที่ทุกอย่างรันอยู่บนมัน องค์กรซื้อกิจการ เปลี่ยนผู้ขาย และเย็บระบบภายในและระบบของบุคคลภายนอกหลายสิบระบบเข้าด้วยกัน และมาตรฐานเปิดคือสิ่งที่ทำให้ส่วนประกอบใหม่เสียบเข้ามาได้โดยไม่ต้องเขียนใหม่ สำหรับภาครัฐ ความเสี่ยงยิ่งสูงขึ้นอีก บริการสาธารณะถูกส่งมอบข้ามหลายหน่วยงาน หลายระดับของรัฐบาล และผู้จัดหาเอกชน และไม่มีหน่วยงานเดียวควบคุมระบบทั้งหมด ประชาชนที่ยื่นขอสวัสดิการอาจแตะระบบยืนยันตัวตน ภาษี สุขภาพ และสวัสดิการสังคมที่เป็นของต่างกระทรวง ระบบเหล่านั้นต้องทำงานร่วมกันได้ ไม่เช่นนั้นบริการล้มเหลว หน่วยงานรัฐยังเปลี่ยนผู้จัดหาตามรอบการจัดซื้อที่นับเป็นปี การพึ่งพาอินเทอร์เฟซเฉพาะของผู้ขายรายเดียวจึงกลายเป็นกับดักที่ยาวนานและแพง

รูปแบบความล้มเหลวที่เกิดซ้ำคือสิ่งตรงข้ามของความสามารถในการทำงานร่วมกัน: **[การผูกติดกับผู้ขาย](https://en.wikipedia.org/wiki/Vendor_lock-in)** (proprietary lock-in) ที่ข้อมูลและกระบวนการขององค์กรพันกับรูปแบบและอินเทอร์เฟซนอกมาตรฐานของผู้ขายรายเดียวจนการเปลี่ยน การเชื่อมต่อ หรือแม้แต่การอ่านข้อมูลในภายหลังมีต้นทุนสูงจนทำไม่ไหว มาตรฐานเปิดคือการป้องกันหลัก บทนี้ครอบคลุมระดับที่ระบบต้องทำงานร่วมกัน มาตรฐานที่ทำให้เป็นไปได้ และวิธีออกแบบ จัดซื้อ และรับรองเพื่อให้ได้ความสามารถนี้ มันเชื่อมโยงใกล้ชิดกับ API และการออกแบบอินเทอร์เฟซ (บทที่ 2.3) ระบบแบบกระจาย (บทที่ 3.3) ยุทธศาสตร์และธรรมาภิบาลข้อมูล (บทที่ 7.1) การจัดซื้อและโอเพนซอร์ส (บทที่ 10.3) และการปฏิบัติตามกฎและธรรมาภิบาล (บทที่ 4.6)

## หลักการสำคัญ

- **ความสามารถในการทำงานร่วมกันต้องออกแบบใส่ไว้ ไม่ใช่เอามาแปะทีหลัง** ตัดสินใจเรื่องมาตรฐานก่อนสร้าง เพราะการมาแก้ภายหลังหมายถึงการเขียนอินเทอร์เฟซใหม่และการย้ายข้อมูล
- **เลือกมาตรฐานเปิดมากกว่าการเชื่อมต่อแบบสั่งทำเฉพาะ** อินเทอร์เฟซที่เป็นไปตามมาตรฐานรองรับพันธมิตรทุกรายทั้งปัจจุบันและอนาคต ตัวเชื่อมแบบสั่งทำรองรับได้แค่รายเดียว
- **ความสามารถในการทำงานร่วมกันมีหลายระดับ** การส่งข้อมูลข้ามสาย (ระดับเทคนิค) ไร้ค่า ถ้าสองฝ่ายเข้าใจความหมายของข้อมูลไม่ตรงกัน (ระดับความหมาย)
- **ความหมายอยู่ในคำศัพท์ที่ใช้ร่วมกัน** ตัวระบุ ระบบรหัส และศัพท์เฉพาะ คือสิ่งที่ทำให้ข้อมูลที่แลกเปลี่ยนใช้งานได้ ไม่ใช่แค่ส่งผ่านได้
- **มาตรฐานเป็นของจริงก็ต่อเมื่อคุณทำตามมันจริง** คำกล่าวว่า "รองรับ [FHIR](https://en.wikipedia.org/wiki/Fast_Healthcare_Interoperability_Resources)" โดยไม่มีการทดสอบความสอดคล้องคือการตลาด ไม่ใช่ความสามารถในการทำงานร่วมกัน
- **การผูกติดกับผู้ขายเป็นการตัดสินใจเรื่องต้นทุนรวมตลอดอายุการใช้งาน** ตัวเลือกกรรมสิทธิ์ที่ถูกวันนี้มักเป็นระบบที่ติดกับดักราคาแพงในวันหน้า
- **ภาครัฐทวีความจำเป็น** บริการสาธารณะข้ามขอบเขตองค์กรที่ไม่มีใครควบคุม มาตรฐานเปิดจึงมักเป็นข้อบังคับ ไม่ใช่แค่ความชอบ

## ข้อแนะนำ

### ออกแบบให้ครบทั้งสี่ระดับของความสามารถในการทำงานร่วมกัน

กรอบความสามารถในการทำงานร่วมกันของยุโรป (European Interoperability Framework) และแบบจำลองที่เกี่ยวข้องอธิบายสี่ระดับ และระบบต้องบรรลุทุกระดับจึงจะทำงานร่วมกันได้จริง **ระดับเทคนิค** (technical) คือท่อส่ง: เครือข่าย โปรโตคอล และการขนส่ง (เช่น [HTTPS](https://en.wikipedia.org/wiki/HTTPS)) ที่เคลื่อนข้อมูลระหว่างระบบ **ระดับวากยสัมพันธ์** (syntactic) คือข้อตกลงเรื่องโครงสร้างและรูปแบบ หรือไวยากรณ์ของข้อความ เช่น [JSON](https://en.wikipedia.org/wiki/JSON) (JavaScript Object Notation รูปแบบข้อมูลข้อความน้ำหนักเบา) หรือ [XML](https://en.wikipedia.org/wiki/XML) (eXtensible Markup Language) **ระดับความหมาย** (semantic) คือข้อตกลงเรื่องความหมาย: ฟิลด์ที่ชื่อ `gender` หรือรหัส `250.00` มีความหมายเดียวกันสำหรับทั้งสองฝ่าย **ระดับองค์กร** (organizational) คือการสอดคล้องของกระบวนการ ธรรมาภิบาล บทบาท และข้อตกลงทางกฎหมาย: ใครได้รับอนุญาตให้ส่งอะไรให้ใคร ภายใต้ข้อตกลงการแบ่งปันข้อมูลฉบับใด และเพื่อวัตถุประสงค์ใด โครงการเชื่อมต่อส่วนใหญ่ทำสองระดับแรกได้ดีและล้มเหลวที่ระดับสามและสี่ ให้ถือความสามารถในการทำงานร่วมกันระดับความหมายและระดับองค์กรเป็นงานออกแบบชั้นหนึ่ง ไม่ใช่เรื่องที่คิดทีหลัง

### ทำให้ชั้นการแลกเปลี่ยนข้อมูลและ API เป็นมาตรฐาน

ใช้มาตรฐานเปิดที่นำไปใช้อย่างกว้างขวางสำหรับวิธีที่ระบบอธิบายและเปิดเผยอินเทอร์เฟซของตน สำหรับ API บนเว็บ (Application Programming Interface สัญญาที่กำหนดไว้ซึ่งระบบหนึ่งใช้เรียกอีกระบบหนึ่ง) ให้ใช้ **[OpenAPI Specification](https://en.wikipedia.org/wiki/OpenAPI_Specification)** ซึ่งเป็นคำอธิบาย [REST](https://en.wikipedia.org/wiki/REST) (Representational State Transfer) API ที่ไม่ผูกกับผู้ขายและอ่านด้วยเครื่องได้ ทั้งบันทึกอินเทอร์เฟซและสร้างโค้ดฝั่งไคลเอนต์ เซิร์ฟเวอร์ การทดสอบ และตัวจำลองได้ สำหรับรูปแบบข้อมูลที่ส่ง ให้เลือก JSON เพราะใช้กันแพร่หลายและมนุษย์อ่านง่าย และใช้ XML ในที่ที่ระบบนิเวศนั้นกำหนดมาตรฐานไว้แล้ว ในที่ที่ต้องการการสื่อสารประสิทธิภาพสูงที่มีชนิดข้อมูลเข้มงวดระหว่างบริการ ให้พิจารณา **[gRPC](https://en.wikipedia.org/wiki/GRPC)** (เฟรมเวิร์กการเรียกโพรซีเดอร์ระยะไกล) กับ **[Protocol Buffers](https://en.wikipedia.org/wiki/Protocol_Buffers) (Protobuf)** ซึ่งเป็นรูปแบบไบนารีที่กะทัดรัดและมีสคีมากำหนด และตัวมันเองก็เป็นข้อกำหนดเปิด ประเด็นไม่ใช่เทคโนโลยีเฉพาะ แต่คือสัญญานั้นถูกเผยแพร่ อ่านด้วยเครื่องได้ และพัฒนาโดยอิสระได้ ดูบทที่ 2.3 สำหรับรายละเอียดของการออกแบบอินเทอร์เฟซ

### ใช้มาตรฐานที่เป็นที่ยอมรับในโดเมนของคุณ

ภาคส่วนส่วนใหญ่ลงตัวที่มาตรฐานความสามารถในการทำงานร่วมกันเฉพาะโดเมนแล้ว ให้ใช้มันแทนการคิดเอง ด้านสุขภาพเป็นตัวอย่างนำ **[HL7](https://en.wikipedia.org/wiki/Health_Level_7)** (Health Level Seven องค์กรมาตรฐานและมาตรฐานการส่งข้อความรุ่นเก่า) ถูก **FHIR** (Fast Healthcare Interoperability Resources) แทนที่เป็นส่วนใหญ่สำหรับงานใหม่ ซึ่งเป็นมาตรฐานสมัยใหม่ที่จำลองแนวคิดทางคลินิก (ผู้ป่วย ผลการตรวจ ยา) เป็นทรัพยากรเว็บที่แลกเปลี่ยนผ่าน REST API โดยใช้ JSON หรือ XML ด้านการเงิน **[ISO 20022](https://en.wikipedia.org/wiki/ISO_20022)** เป็นมาตรฐานเปิดสำหรับข้อความการชำระเงินและการเงินที่มีโครงสร้างและมีคำอธิบายประกอบอุดม ปัจจุบันระบบชำระเงินทั่วโลกนำไปใช้ ด้านข้อมูลภูมิสารสนเทศ **[OGC](https://en.wikipedia.org/wiki/Open_Geospatial_Consortium) (Open Geospatial Consortium)** เผยแพร่มาตรฐานเช่น WMS และ WFS สำหรับบริการแผนที่และฟีเจอร์ ตัวอย่างอื่นรวมถึง OASIS และ UBL สำหรับเอกสารธุรกิจ และ IFC (BuildingSMART) สำหรับงานก่อสร้าง การเลือกมาตรฐานที่เป็นที่ยอมรับซื้อระบบนิเวศทั้งชุดของเครื่องมือ ผู้จัดหา และบุคลากรที่ผ่านการฝึกที่สอดคล้องกับมาตรฐาน

### ยึดความหมายไว้กับตัวระบุ ระบบรหัส และออนโทโลยี

ความสามารถในการทำงานร่วมกันระดับความหมายต้องมีคำศัพท์ร่วม ใช้**ตัวระบุ**มาตรฐานเพื่อให้สิ่งเดียวกันในโลกจริงมีการอ้างอิงเดียวกันทุกที่ (เช่น รหัสประเทศ ISO, LEI สำหรับนิติบุคคล หรือเลขประจำตัวผู้ป่วยแห่งชาติ) ใช้**ระบบรหัส**และ**ศัพท์เฉพาะ**ที่เผยแพร่ (รายการควบคุมของแนวคิดที่มีรหัสและมีความหมายกำหนดไว้) แทนข้อความอิสระ: [SNOMED CT](https://en.wikipedia.org/wiki/SNOMED_CT) และ [LOINC](https://en.wikipedia.org/wiki/LOINC) สำหรับศัพท์ทางคลินิก [ICD](https://en.wikipedia.org/wiki/International_Classification_of_Diseases) (International Classification of Diseases) สำหรับการวินิจฉัย Unicode สำหรับข้อความ ในที่ที่ความสัมพันธ์ระหว่างแนวคิดสำคัญ ให้ใช้**[ออนโทโลยี](https://en.wikipedia.org/wiki/Ontology_(information_science))** (แบบจำลองที่เป็นทางการและอ่านด้วยเครื่องได้ของแนวคิดและความสัมพันธ์ระหว่างกัน) ที่แสดงด้วยมาตรฐานเช่น RDF และ OWL (W3C Web Ontology Language) การกำกับดูแลคำศัพท์เหล่านี้เป็นความรับผิดชอบด้านธรรมาภิบาลข้อมูล ดูบทที่ 7.1

### เชื่อมต่อผ่านรูปแบบที่อิงมาตรฐาน ไม่ใช่การเดินสายแบบจุดต่อจุด

เลือกรูปแบบสถาปัตยกรรมที่ทำให้จำนวนการเชื่อมต่อโตเป็นเส้นตรงแทนที่จะโตแบบรวมกลุ่ม ระบบ **N** ระบบที่เดินสายแบบจุดต่อจุดอาจต้องการตัวเชื่อมแบบสั่งทำสูงถึง N×(N−1)/2 ตัว ขณะที่ระบบ N ระบบเดียวกันที่แต่ละระบบทำตามมาตรฐานร่วมต้องการเพียง N การพัฒนาของมาตรฐานนั้น ใช้เกตเวย์ สัญญา API ที่เผยแพร่ และแบบจำลองข้อมูลกลาง (canonical data model) เพื่อให้ผู้เข้าร่วมรายใหม่เชื่อมต่อครั้งเดียวกับมาตรฐาน แทนที่จะเชื่อมกับทุกระบบที่มีอยู่ นี่ยังเป็นยาแก้การผูกติดกับผู้ขาย: เพราะสัญญาเป็นแบบเปิด จึงเปลี่ยนผู้ขายได้โดยไม่ต้องแตะทุกคนที่เชื่อมต่ออยู่

### กำหนดให้มีการทดสอบความสอดคล้องและการรับรอง

มาตรฐานให้คุณค่าก็ต่อเมื่อการพัฒนาทำตามมันจริง ยืนยันให้มี**การทดสอบความสอดคล้อง** (conformance testing: การตรวจอัตโนมัติว่าการพัฒนาตรงตามข้อกำหนด) โดยใช้ชุดทดสอบและตัวตรวจสอบที่เผยแพร่ (เช่น ตัวตรวจสอบของ FHIR และการทดสอบ Touchstone หรือการตรวจสอบสคีมา OpenAPI ในไปป์ไลน์บิลด์ของคุณ) ในที่ที่มีโครงการ**การรับรอง** (certification) อย่างเป็นทางการ (หน่วยงานอิสระรับรองความสอดคล้อง เช่นในโครงการรับรองไอทีด้านสุขภาพระดับชาติ) ให้เลือกผลิตภัณฑ์ที่ได้รับการรับรองและกำหนดให้ต้องมีการรับรองในสัญญา ฝังการตรวจความสอดคล้องไว้ในการรวมระบบต่อเนื่อง เพื่อให้การเบี่ยงจากมาตรฐานทำให้บิลด์ล้มเหลวแทนที่จะปรากฏในระบบจริง

## ข้อดีข้อเสียและการแลกเปลี่ยน

| แนวทาง | ข้อดี | ข้อเสีย / ต้นทุน |
|---|---|---|
| มาตรฐานเปิด | มีผู้จัดหาหลายราย ไม่ผูกติดกับผู้ขาย มีเครื่องมือในระบบนิเวศ พันธมิตรในอนาคตเชื่อมต่อได้ถูก | มาตรฐานอาจกว้างหรือซับซ้อน รับฟีเจอร์เฉพาะทางได้ช้า พัฒนาตามจังหวะของคณะกรรมการ |
| การเชื่อมต่อจุดต่อจุดแบบสั่งทำ | เร็วสำหรับการเชื่อมต่อแรก พอดีเป๊ะ เรียนรู้ล่วงหน้าน้อย | ต้นทุนโตแบบรวมกลุ่ม เปราะบาง ต้องทำใหม่ทุกครั้งที่เปลี่ยน ก่อให้เกิดการผูกติดกับผู้ขาย |
| รูปแบบ/API เฉพาะของผู้ขาย | ฟีเจอร์ครบ มีผู้ขายสนับสนุน เริ่มเร็วในระบบนิเวศเดียว | ผูกติดกับผู้ขาย ต้นทุนการเปลี่ยน ดึงข้อมูลออกยากภายหลัง อำนาจกำหนดราคาย้ายไปที่ผู้ขาย |
| มาตรฐานเฉพาะโดเมน (FHIR, ISO 20022) | ความหมายร่วม บุคลากรที่ผ่านการฝึก สอดคล้องกับผู้กำกับดูแล | เส้นโค้งการเรียนรู้ การแมปข้อมูลระบบเดิม ภาระการจัดการเวอร์ชันและโปรไฟล์ |

ข้อแลกเปลี่ยนหลักคือความสะดวกระยะสั้นเทียบกับทางเลือกระยะยาว การเชื่อมต่อแบบสั่งทำหรือเฉพาะของผู้ขายเกือบทุกครั้งตั้งขึ้นได้เร็วกว่าสำหรับการเชื่อมต่อแรก ซึ่งเป็นเหตุผลที่องค์กรไหลไปสู่การผูกติดทีละการตัดสินใจที่สมเหตุสมผล มาตรฐานเปิดจ่ายต้นทุนล่วงหน้า (เรียนรู้ข้อกำหนด แมปข้อมูลที่มีอยู่ สร้างการทดสอบความสอดคล้อง) และคืนทุนทุกครั้งที่พันธมิตร ผู้จัดหา หรือระบบใหม่เข้ามาโดยไม่ต้องเขียนใหม่ สำหรับระบบที่มีอายุยาวและมีผู้เข้าร่วมหลายราย ซึ่งบรรยายแพลตฟอร์มองค์กรและภาครัฐเกือบทั้งหมด เส้นทางที่อิงมาตรฐานชนะขาด สำหรับการเชื่อมต่อแบบหนึ่งต่อหนึ่งที่ใช้แล้วทิ้งจริง ๆ แบบสั่งทำอาจสมเหตุสมผล ความผิดพลาดคือการปฏิบัติต่อแพลตฟอร์มอายุยาวเหมือนเป็นการเชื่อมต่อที่ใช้แล้วทิ้ง

## คำถามที่ควรคุยกับทีม

1. **ใครเป็นเจ้าของความสามารถในการทำงานร่วมกันระดับองค์กร (ข้อตกลงการแบ่งปันข้อมูล แบบจำลองความยินยอม และการสอดคล้องของกระบวนการ) ที่การเชื่อมต่อทางเทคนิคของคุณพึ่งพา** โครงการส่วนใหญ่ทำระดับเทคนิคและวากยสัมพันธ์ได้ดีแล้วติดที่ระดับองค์กร: ข้อมูลมาถึงและแยกวิเคราะห์ได้ แต่ไม่มีข้อตกลงใดกำกับว่าใครส่งอะไรให้ใคร เพื่อวัตถุประสงค์ใด ภายใต้ความยินยอมแบบไหน ในภาครัฐ ข้อมูลของประชาชนข้ามหน่วยงานที่แต่ละแห่งเป็นเจ้าของระบบและตอบต่อฐานกฎหมายที่ต่างกัน อินเทอร์เฟซ FHIR ที่สมบูรณ์แบบจึงไร้ค่าจนกว่าจะมีข้อตกลงการแบ่งปันและแบบจำลองความยินยอม นำการแลกเปลี่ยนข้ามขอบเขตที่สำคัญที่สุดของคุณมา และระบุตราสารทางกฎหมายและเจ้าของที่รับผิดชอบทั้งสองฝ่าย ไม่ใช่แค่ API ถ้าเจ้าของไม่มีชื่อ การเชื่อมต่อจะผ่านทุกการทดสอบทางเทคนิคแต่ยังถูกบล็อกในระบบจริง ให้ปฏิบัติต่อข้อตกลงเหล่านี้เป็นผลงานการออกแบบด้วยความเข้มงวดเท่ากับสคีมาของข้อความ

2. **คุณพึ่งส่วนขยายเฉพาะของมาตรฐานมากแค่ไหน และการพัฒนาอื่นที่สอดคล้องกับมาตรฐานยังคุยกับคุณได้หรือไม่** มาตรฐานมีช่องทางหนี และการใช้มันมากเกินไปคือการผูกติดโดยพฤตินัยที่สวมป้ายความเปิด: คุณอ้างว่าใช้ FHIR หรือ ISO 20022 แต่ไม่มีผู้ขายอิสระรายใดทำงานร่วมกับสำเนียงของคุณได้จริง สิ่งนี้คืบเข้ามาทีละการปรับแต่งที่สมเหตุสมผล จึงควรที่ระบบขนาดใหญ่จะวัดมันอย่างตั้งใจ นำข้อความจริงมาและนับว่าความหมายของมันขึ้นกับฟิลด์มาตรฐานเทียบกับส่วนขยายที่กำหนดเองเท่าไร สัดส่วนที่กำหนดเองยิ่งสูง ความสามารถในการพกพายิ่งอ่อนและอำนาจกำหนดราคาของผู้ขายเดิมยิ่งแข็ง ให้เลือกการทำโปรไฟล์ภายในกฎของมาตรฐาน และส่งช่องว่างกลับไปให้มาตรฐาน แทนส่วนขยายส่วนตัว จุดประสงค์ทั้งหมดของเส้นทางเปิดคือเปลี่ยนผู้ขายได้โดยไม่แตะทุกคนที่เชื่อมต่อ และส่วนขยายกัดกร่อนสิ่งนั้นอย่างเงียบ ๆ

3. **คุณใช้เวอร์ชันและโปรไฟล์ใดของแต่ละมาตรฐาน และใครกำกับดูแลการเลือกนั้นทั่วทั้งระบบ** "รองรับมาตรฐาน" ไม่มีความหมายถ้าไม่มีวินัยเรื่องเวอร์ชันและโปรไฟล์ เพราะสองระบบอาจอ้างว่าใช้ FHIR หรือ ISO 20022 ทั้งคู่แต่ยังคุยกันไม่ได้ถ้าใช้เวอร์ชันหรือโปรไฟล์ต่างกัน ในองค์กรขนาดใหญ่ที่มีผู้จัดหาหลายรายและรอบการจัดซื้อยาว เวอร์ชันเลื่อนห่างกันอย่างเงียบ ๆ จนการเชื่อมต่อพัง นำบัญชีรายการของทุกอินเทอร์เฟซ มาตรฐาน เวอร์ชัน และโปรไฟล์ของมันมาด้วย และระบุว่าใครรับผิดชอบการรักษาให้สอดคล้องกันและการวางแผนอัปเกรด ฝังเวอร์ชันและโปรไฟล์ไว้ในการทดสอบความสอดคล้องของไปป์ไลน์ เพื่อให้การเบี่ยงทำให้บิลด์ล้มเหลวแทนที่จะปรากฏในระบบจริง ถ้าไม่มีธรรมาภิบาลนี้ ระบบที่สอดคล้องในนามก็ยังทำงานร่วมกันไม่ได้ ซึ่งเป็นความล้มเหลวที่มาตรฐานเปิดมีไว้เพื่อป้องกัน

4. **เมื่อสัญญาหรือผู้จัดหาบอกว่า "รองรับมาตรฐาน" การทดสอบอิสระใดพิสูจน์ได้จริง และการทดสอบนั้นรันที่ไหน** คำอ้างเรื่องความสอดคล้องที่ไม่มีการทดสอบรองรับคือการตลาด และมันล้มเหลวในที่ที่แย่ที่สุด: ในระบบจริง หลังจากเงินเปลี่ยนมือและระบบเริ่มใช้งานแล้ว สำหรับองค์กรขนาดใหญ่ที่ซื้อจากผู้จัดหาหลายราย ความล่อใจคือยอมรับช่องติ๊กในแบบสอบถาม เพราะการยืนยันให้มีการตรวจสอบความสอดคล้องทำให้การจัดซื้อช้าลงและจำกัดผู้เสนอราคา นำตัวตรวจสอบหรือชุดทดสอบที่เผยแพร่ของแต่ละมาตรฐานที่คุณพึ่งพา (เช่น ตัวตรวจสอบ FHIR และ Touchstone หรือการตรวจสอบสคีมา OpenAPI) ตัวอย่างข้อความจริงที่ผ่านมัน และข้อสัญญาที่ผูกการตรวจรับและการชำระเงินกับการผ่านการทดสอบนั้นมาด้วย แรงดึงที่ขัดกันคือความเร็วเทียบกับหลักฐาน: ผลิตภัณฑ์ที่ได้รับการรับรองอาจแพงกว่าและใช้เวลานำเข้านานกว่า แต่ผลิตภัณฑ์ที่ไม่ได้ตรวจสอบโอนความล้มเหลวมาให้ทีมเชื่อมต่อของคุณ ในภาครัฐและบริบทที่มีการกำกับดูแล ที่มีโครงการรับรองไอทีสุขภาพหรือการชำระเงินระดับชาติ ให้กำหนดการรับรองในสัญญาและเชื่อมตัวตรวจสอบเข้ากับการรวมระบบต่อเนื่องเพื่อให้การเบี่ยงทำให้บิลด์ล้มเหลว เพราะคำยืนยันที่คุณไม่เคยทดสอบคือภาระที่คุณจะค้นพบระหว่างการตรวจสอบหรือระบบล่ม

5. **การเชื่อมต่อของคุณยังเป็นจุดต่อจุดอยู่เท่าไร และต้นทุนแบบรวมกลุ่มที่แท้จริงของการปล่อยไว้อย่างนั้นคืออะไร** ตัวเชื่อมหนึ่งต่อหนึ่งแบบสั่งทำเป็นสิ่งที่สร้างเร็วที่สุดสำหรับการเชื่อมต่อแรกและแพงที่สุดในการเป็นเจ้าของทั่วทั้งระบบ เพราะจำนวนโตเข้าหา N×(N−1)/2 ในขณะที่มาตรฐานร่วมต้องการแค่ N การพัฒนา ในองค์กรขนาดใหญ่ ความกระจัดกระจายนี้สะสมทีละการตัดสินใจที่สมเหตุสมผลจนแผนผังการเชื่อมต่อดูแลไม่ไหว และทุกการเปลี่ยนระบบกระเพื่อมผ่านตัวเชื่อมที่เปราะบางหลายสิบตัว นำบัญชีรายการการเชื่อมต่อที่จัดประเภทเป็นจุดต่อจุดเทียบกับอิงมาตรฐาน จำนวนตัวเชื่อมที่ถูกแตะโดยการแทนที่ระบบใหญ่ครั้งล่าสุดของคุณ และการประมาณเวลาวิศวกรรมที่ใช้ดูแลการเชื่อมต่อแบบกำหนดเองมาด้วย ความตึงเครียดคือการย้ายสายจุดต่อจุดที่ใช้งานอยู่ไปไว้หลังเกตเวย์หรือแบบจำลองกลางเป็นงานจริงที่ไม่มีผลตอบแทนเป็นฟีเจอร์ทันที จึงแพ้แผนงานถ้าไม่มีใครวัดต้นทุนการแบกรับ สำหรับแพลตฟอร์มองค์กรและภาครัฐที่อยู่เป็นทศวรรษและเพิ่มผู้เข้าร่วมเรื่อย ๆ เส้นทางจุดต่อจุดคือภาษีที่ค่อย ๆ จ่าย ให้ระบุเจ้าของสถาปัตยกรรมการเชื่อมต่อและแผนที่จะส่งผู้เข้าร่วมรายใหม่ผ่านมาตรฐานแทนการเชื่อมกับทุกระบบเดิม

6. **คุณส่งความหมายด้วยข้อความอิสระในที่ที่ระบบรหัสหรือศัพท์เฉพาะที่เผยแพร่ควรทำหน้าที่นั้นอยู่ตรงไหน และใครกำกับดูแลคำศัพท์เหล่านั้น** ความสามารถในการทำงานร่วมกันระดับความหมายคือที่ที่การเชื่อมต่อส่วนใหญ่ล้มเหลวอย่างเงียบ ๆ: ข้อมูลมาถึงและแยกวิเคราะห์ได้ แต่การวินิจฉัย สกุลเงิน หรือประเทศที่เก็บเป็นสตริงไร้ข้อจำกัดมีความหมายหนึ่งสำหรับผู้ส่งและต่างออกไปเล็กน้อยสำหรับผู้รับ สำหรับองค์กรขนาดใหญ่ ต้นทุนมองไม่เห็นจนกว่าการรายงาน การวิเคราะห์ หรือผู้กำกับดูแลจะเผยว่าแนวคิดเดียวกันถูกลงรหัสสามแบบในสามระบบ นำตัวอย่างฟิลด์ที่ปัจจุบันเก็บเป็นข้อความอิสระ ตัวระบุและระบบรหัสมาตรฐานที่แทนได้ (SNOMED CT และ LOINC สำหรับข้อมูลทางคลินิก รหัส ISO สำหรับประเทศและสกุลเงิน LEI สำหรับนิติบุคคล) และอัตราข้อผิดพลาดหรือความพยายามกระทบยอดที่ข้อความอิสระซ่อนอยู่ มาด้วย ข้อพิจารณาที่ขัดกันคือการแมปข้อมูลระบบเดิมเข้ากับคำศัพท์ควบคุมเป็นงานละเอียดที่ไม่เคยได้เดโม จึงถูกจัดเงินไม่พอเมื่อเทียบกับชั้นการขนส่ง ในภาครัฐ ที่ระเบียนของประชาชนประกอบจากระบบอิสระหลายระบบและรหัสที่ไม่ตรงกันอาจทำให้ปฏิเสธสวัสดิการหรือทำให้ระเบียนสุขภาพเสียหาย ให้ถือธรรมาภิบาลคำศัพท์เป็นความรับผิดชอบด้านธรรมาภิบาลข้อมูลที่มีชื่อ (บทที่ 7.1) ไม่ใช่รายละเอียดการพัฒนาที่ปล่อยให้แต่ละทีมจัดการเอง

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ความเร็วชนะ และมาตรฐานเปิดคือวิธีที่ทีมเล็ก ๆ เข้าถึงลูกค้าจำนวนมากโดยไม่ต้องสร้างตัวเชื่อมจำนวนมาก พูดรูปแบบที่พันธมิตรทุกรายรองรับอยู่แล้ว (OAuth สำหรับลงชื่อเข้าใช้ iCalendar สำหรับการนัดหมาย webhook สำหรับเหตุการณ์ JSON บนสัญญา OpenAPI) เพื่อให้การเชื่อมต่อครั้งเดียวเข้าถึงลูกค้าหลายพัน และการเปลี่ยนผู้ขายแตะอะแดปเตอร์ตัวเดียว หลีกเลี่ยงการคิดรูปแบบของตัวเองหรือเดินสายสแตกของลูกค้าแต่ละรายด้วยมือ นั่นคืองานดูแลในอนาคตที่คุณจัดคนไม่ไหว เส้นทางมาตรฐานแพงกว่าเล็กน้อยล่วงหน้าและรักษาต้นทุนการเปลี่ยนให้ต่ำในตลาดที่คุณยังทำนายไม่ได้

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญด้านการเชื่อมต่อและงบประมาณจำกัด ให้ถือความสามารถในการทำงานร่วมกันเป็นการตัดสินใจซื้อ ไม่ใช่โครงการสร้าง เลือกเครื่องมือที่พูดมาตรฐานเปิดของภาคส่วนคุณอยู่แล้วและเปิดเผย API ที่มีเอกสาร เพื่อให้ข้อมูลของคุณพกพาได้ถ้าเปลี่ยนผู้จัดหา ถามผู้ขายที่จะซื้อด้วยว่าคุณจะนำข้อมูลออกได้อย่างไรและในรูปแบบใดก่อนลงนาม เพราะตัวเลือกกรรมสิทธิ์ที่ถูกวันนี้คือระบบที่ติดกับดักในวันหน้า คุณแทบไม่ได้รันการทดสอบความสอดคล้องเอง จึงควรพึ่งผลิตภัณฑ์ที่ได้รับการรับรองหรือทำงานร่วมกับผู้อื่นได้อย่างกว้างขวาง

**องค์กรขนาดใหญ่.** ความท้าทายคือการกำกับดูแลความสามารถในการทำงานร่วมกันข้ามหลายทีม ผู้จัดหา และรอบการจัดซื้อที่ยาว กำหนดมาตรฐานโดเมน (FHIR, ISO 20022, OGC) และสัญญา OpenAPI ที่เผยแพร่ จากนั้นเก็บบัญชีรายการของทุกอินเทอร์เฟซพร้อมเวอร์ชัน โปรไฟล์ และเจ้าของที่รับผิดชอบ เพื่อไม่ให้ระบบที่สอดคล้องในนามเลื่อนห่างกัน ส่งผู้เข้าร่วมรายใหม่ผ่านเกตเวย์และแบบจำลองกลางแทนการเดินสายจุดต่อจุด เชื่อมการตรวจสอบความสอดคล้องเข้ากับการรวมระบบต่อเนื่อง และวัดว่าทราฟฟิกของคุณขึ้นกับฟิลด์มาตรฐานเทียบกับส่วนขยายเฉพาะเท่าไร จัดการการผูกติดและความสามารถในการพกพาเป็นจุดยืนด้านต้นทุนรวมตลอดอายุการใช้งานที่ตั้งใจ ไม่ใช่อุบัติเหตุ

**ภาครัฐ.** มาตรฐานเปิดมักเป็นข้อบังคับ เพราะบริการสาธารณะข้ามหน่วยงานที่ไม่มีองค์กรเดียวควบคุมและผู้จัดหาเปลี่ยนตามรอบหลายปี กำหนดการทดสอบความสอดคล้อง และในที่ที่มีโครงการ การรับรองระดับชาติ ไว้ในทุกสัญญา และเรียกร้องความสามารถในการพกพาข้อมูลเพื่อไม่ให้ผู้ขายที่จากไปยึดข้อมูลของสาธารณะเป็นตัวประกัน ยึดความหมายไว้กับตัวระบุระดับชาติและศัพท์เฉพาะที่เผยแพร่ เพื่อให้ระเบียนของประชาชนมีความหมายเดียวกันข้ามกรม และจัดการความสามารถในการทำงานร่วมกันระดับองค์กรผ่านข้อตกลงการแบ่งปันข้อมูลที่ชัดเจนและแบบจำลองความยินยอมพร้อมเจ้าของที่รับผิดชอบที่มีชื่อ ความโปร่งใสและเงินภาษีของสาธารณะต่างสนับสนุนเส้นทางที่เปิดและพัฒนาโดยอิสระได้เหนือความสะดวกแบบกรรมสิทธิ์ใด ๆ

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปเล็ก ๆ ที่สร้างแอปเพิ่มผลิตภาพของทีมเชื่อมต่อกับเครื่องมือเดิมของลูกค้าผ่านมาตรฐานเปิดแทนตัวเชื่อมแบบสั่งทำ: OAuth สำหรับลงชื่อเข้าใช้ iCalendar สำหรับการนัดหมาย และ webhook สำหรับเหตุการณ์ เพราะพูดรูปแบบที่ผู้ให้บริการปฏิทินและการยืนยันตัวตนทุกรายรองรับอยู่แล้ว การเชื่อมต่อครั้งเดียวจึงเข้าถึงลูกค้าหลายพันรายแทนที่จะเป็นรายเดียว และการเปลี่ยนผู้ขายระบบชำระเงินหรืออีเมลในภายหลังแตะอะแดปเตอร์ตัวเดียว ถ้าสร้างลิงก์แบบกำหนดเองกับสแตกของลูกค้าแต่ละรายด้วยมือ ทุกโลโก้ใหม่จะหมายถึงตัวเชื่อมอีกตัวที่ต้องเขียนและดูแล

**องค์กรขนาดใหญ่.** ธนาคารข้ามชาติปรับปรุงการชำระเงินข้ามพรมแดนโดยย้ายจากรูปแบบข้อความกรรมสิทธิ์รุ่นเก่าไปเป็น **ISO 20022** เพราะมาตรฐานนี้บรรจุข้อมูลที่มีโครงสร้างและมีคำอธิบายประกอบอุดม (ผู้จ่าย ผู้รับ วัตถุประสงค์ ฟิลด์ด้านกฎระเบียบ) แทนข้อความอิสระ ระบบปลายน้ำสำหรับการคัดกรองการทุจริต การกระทบยอด และการรายงานจึงใช้รูปแบบกลางเดียวแทนตัวแยกวิเคราะห์แบบสั่งทำหลายสิบตัว เมื่อธนาคารเปลี่ยนผู้ขายเกตเวย์การชำระเงินในภายหลัง ผู้จัดหารายใหม่พูด ISO 20022 อยู่แล้ว การเปลี่ยนจึงแตะเกตเวย์ ไม่ใช่ร้อยระบบที่อยู่เบื้องหลัง มาตรฐานเปิดเปลี่ยนการย้ายผู้ขายจากการสร้างใหม่หลายปีให้เป็นการแทนที่ที่จำกัดขอบเขต

**ภาครัฐ.** หน่วยบริการสุขภาพแห่งชาติต้องการให้โรงพยาบาล คลินิก ห้องปฏิบัติการ และแอปสำหรับประชาชน (สร้างโดยผู้จัดหาต่างกันตลอดสองทศวรรษ) แบ่งปันระเบียนอย่างปลอดภัย หน่วยงานกำหนดให้ใช้ **FHIR** สำหรับการแลกเปลี่ยนข้อมูล: แต่ละระบบเปิดเผยข้อมูลผู้ป่วย ผลการตรวจ และยาเป็นทรัพยากร FHIR ผ่าน REST API โดยใช้ตัวระบุมาตรฐาน (เลขประจำตัวผู้ป่วยแห่งชาติ) และศัพท์ทางคลินิก (SNOMED CT สำหรับภาวะ LOINC สำหรับผลแล็บ) เพื่อให้รหัสมีความหมายเดียวกันทุกที่ ผู้จัดหาต้องผ่านการตรวจสอบความสอดคล้อง FHIR และมีการรับรองไอทีสุขภาพระดับชาติก่อนเชื่อมต่อ ระบบคลินิกใหม่เชื่อมต่อครั้งเดียวกับมาตรฐาน FHIR แทนการสร้างลิงก์แบบสั่งทำกับทุกระบบเดิม และประชาชนดูระเบียนรวมที่ประกอบจากระบบอิสระหลายระบบได้ ความสามารถในการทำงานร่วมกันระดับองค์กรจัดการผ่านข้อตกลงการแบ่งปันข้อมูลที่กำกับว่าใครเข้าถึงอะไรได้และทำไม เป็นไปตามข้อผูกพันด้านการปฏิบัติตามกฎ (บทที่ 4.6)

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ข้อโต้แย้งทางการเงินของมาตรฐานเปิดคือข้อโต้แย้งเรื่องต้นทุนรวมตลอดอายุการใช้งาน (TCO) ตลอดอายุของระบบ ไม่ใช่ราคาป้ายของการเชื่อมต่อแรก ต้นทุนการเชื่อมต่อแบบสั่งทำโตตามจำนวนการเชื่อมต่อและต้องจ่ายอีกทุกครั้งที่เปลี่ยน ต้นทุนการเชื่อมต่อที่อิงมาตรฐานจ่ายครั้งเดียวต่อผู้เข้าร่วมและเฉลี่ยตลอดทั้งระบบ ผลตอบแทนจากการลงทุน (ROI) ปรากฏในแรงงานเชื่อมต่อที่ลดลง การนำพันธมิตรและผู้จัดหาใหม่เข้าระบบที่เร็วขึ้น ต้นทุนการเปลี่ยนที่ต่ำลงเมื่อผู้ขายทำงานไม่ดี และการหลีกเลี่ยงภาษีการผูกติดแบบคลาสสิกที่ผู้จัดหารายเดียวขึ้นราคาเพราะไม่มีคู่แข่งเสนอราคาได้

สำหรับผู้บริหาร ให้วางกรอบเหตุผลรอบทางเลือกและการแข่งขัน มาตรฐานเปิดรักษาการจัดซื้อให้แข่งขันได้ (บทที่ 10.3) เมื่ออินเทอร์เฟซเผยแพร่และผ่านการทดสอบความสอดคล้อง ผู้ขายหลายรายเสนอราคาบนเงื่อนไขเท่ากันได้ ซึ่งกดราคาลงและยกคุณภาพขึ้นตลอดสัญญาที่ต่อเนื่อง มันยังลดความเสี่ยงของอนาคต เพราะการเปลี่ยนแปลงด้านกฎระเบียบ การควบรวม และโครงการปรับปรุงระบบล้วนถูกลงเมื่อข้อมูลและอินเทอร์เฟซพกพาได้ ต้นทุนแฝงที่ใหญ่ที่สุดของการเพิกเฉยมาตรฐานคือการย้ายที่ถูกบังคับในที่สุด: การดึงข้อมูลจากรูปแบบกรรมสิทธิ์ภายหลังเมื่อผู้ขายเดิมไปแล้วหรือไม่ให้ความร่วมมือ มักมีต้นทุนหลายเท่าของที่การออกแบบอิงมาตรฐานจะใช้ล่วงหน้า รัฐบาลตระหนักเรื่องนี้มากขึ้นและกำหนดมาตรฐานเปิดเป็นข้อบังคับเพื่อปกป้องเงินภาษีจากการผูกติดตลอดหลายทศวรรษ

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **เข้าใจว่าความสามารถในการทำงานร่วมกันระดับเทคนิคคืองานทั้งหมด** ข้อความมาถึงและแยกวิเคราะห์ได้ แต่สองฝ่ายเห็นไม่ตรงกันว่าฟิลด์หมายถึงอะไร ข้อมูลจึงผิดอย่างเงียบ ๆ
- **"อิงมาตรฐาน" แค่ในนาม** ผลิตภัณฑ์อ้างว่ารองรับมาตรฐานแต่ไม่เคยผ่านการทดสอบความสอดคล้องและเบี่ยงเบนในทางปฏิบัติ
- **ใช้ข้อความอิสระทั้งที่มีระบบรหัส** เก็บการวินิจฉัย สกุลเงิน หรือประเทศเป็นสตริงไร้ข้อจำกัดทำลายความสามารถในการทำงานร่วมกันระดับความหมาย
- **ส่วนขยายเฉพาะที่กลืนมาตรฐาน** ใช้ช่องทางหนีของมาตรฐานมากจนไม่มีการพัฒนาอื่นทำงานร่วมกันได้: การผูกติดโดยพฤตินัยที่สวมป้ายความเปิด
- **ความกระจัดกระจายของจุดต่อจุด** เพิ่มตัวเชื่อมแบบสั่งทำอีกหนึ่งตัวทุกครั้ง จนแผนผังการเชื่อมต่อเป็นความยุ่งเหยิงแบบรวมกลุ่มที่ดูแลไม่ไหว
- **ความโกลาหลของเวอร์ชันและโปรไฟล์** ไม่มีธรรมาภิบาลว่าใช้เวอร์ชันหรือโปรไฟล์ใดของมาตรฐาน ระบบที่สอดคล้องในนามจึงยังคุยกันไม่ได้
- **เพิกเฉยความสามารถในการทำงานร่วมกันระดับองค์กร** การแลกเปลี่ยนทางเทคนิคที่สมบูรณ์แบบถูกบล็อกเพราะไม่มีข้อตกลงการแบ่งปันข้อมูล แบบจำลองความยินยอม หรือการสอดคล้องของกระบวนการ
- **สร้างมาตรฐานของตัวเอง** คิดรูปแบบเฉพาะทั้งที่มีมาตรฐานโดเมนที่สุกงอมและมีผู้ใช้แล้ว และรับภาระการดูแลทั้งหมดไปตลอดกาล

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น.** การเชื่อมต่อเป็นแบบเฉพาะกิจและจุดต่อจุด รูปแบบเป็นกรรมสิทธิ์หรือไม่มีเอกสาร ความหมายส่งผ่านข้อความอิสระและความรู้ปากต่อปาก การเปลี่ยนระบบหรือผู้ขายใด ๆ เป็นโครงการใหญ่ การผูกติดแพร่หลายและแทบไม่มีใครตระหนัก
- **ระดับ 2 พัฒนา.** รูปแบบทั่วไปเช่น JSON หรือ XML ปรากฏ และบาง API มีเอกสาร แต่แนวปฏิบัติต่างกันแต่ละทีม ความสามารถในการทำงานร่วมกันยังเป็นระดับวากยสัมพันธ์เป็นส่วนใหญ่ ข้อตกลงด้านความหมายไม่สม่ำเสมอและทำรายโครงการ เลือกมาตรฐานแบบตั้งรับ และอ้างความสอดคล้องแต่ไม่ได้ทดสอบ
- **ระดับ 3 สร้างมาตรฐาน.** มาตรฐานการแลกเปลี่ยนข้อมูลเปิด (OpenAPI และมาตรฐานโดเมนที่เกี่ยวข้องเช่น FHIR หรือ ISO 20022) มีเอกสารและกำหนดเป็นข้อบังคับทั่วองค์กร ตัวระบุ ระบบรหัส และศัพท์เฉพาะที่ใช้ร่วมกันให้ความสามารถในการทำงานร่วมกันระดับความหมาย การทดสอบความสอดคล้องเป็นส่วนของไปป์ไลน์การส่งมอบ และการเชื่อมต่อเป็นไปตามรูปแบบที่อิงมาตรฐานแทนการเดินสายจุดต่อจุด
- **ระดับ 4 บริหารจัดการ.** ความสามารถในการทำงานร่วมกันถูกวัดและควบคุมเทียบกับเส้นฐาน มีการติดตามและทบทวนตัวชี้วัด: สัดส่วนของการเชื่อมต่อที่อิงมาตรฐานเทียบกับจุดต่อจุด สัดส่วนของความหมายของข้อความที่ขึ้นกับฟิลด์มาตรฐานเทียบกับส่วนขยายกรรมสิทธิ์ อัตราผ่านการทดสอบความสอดคล้องในไปป์ไลน์ การเบี่ยงของเวอร์ชันและโปรไฟล์ทั่วระบบ และ lead time กับอัตราข้อบกพร่องของการนำผู้เข้าร่วมรายใหม่เข้าระบบ เวอร์ชันและโปรไฟล์ได้รับการกำกับดูแล ผู้จัดหาต้องมีการรับรองและมีการตรวจสอบ และความเสี่ยงจากการผูกติดถูกวัดปริมาณแทนการคาดเดา การตัดสินใจรับ อัปเกรด หรือเลิกอินเทอร์เฟซทำบนหลักฐานนี้
- **ระดับ 5 ประสานทั้งระบบ.** ความสามารถในการทำงานร่วมกันได้รับการปรับปรุงต่อเนื่องและผสานทั่วองค์กร ความสามารถในการทำงานร่วมกันระดับองค์กร (ข้อตกลง ความยินยอม การสอดคล้องของกระบวนการ) ถูกจัดการอย่างเป็นระบบควบคู่ไปกับชั้นเทคนิค องค์กรมีส่วนร่วมกลับไปยังมาตรฐานที่พึ่งพา และความสามารถในการพกพาเป็นข้อจำกัดการออกแบบถาวร ทั้งระบบปรับตัวเมื่อมาตรฐานพัฒนาและผู้เข้าร่วมเข้าออก ปรับสมดุลสถาปัตยกรรมการเชื่อมต่อและธรรมาภิบาลคำศัพท์ตามหลักฐานที่วัดได้ ไม่ใช่ตามเหตุการณ์

## ประเด็นชวนคุย

1. สำหรับการแลกเปลี่ยนข้อมูลที่สำคัญที่สุดของคุณ ระดับใดในสี่ระดับ (เทคนิค วากยสัมพันธ์ ความหมาย องค์กร) ที่อ่อนที่สุดในวันนี้
2. ถ้าผู้ขายหลักของคุณขึ้นราคาเป็นสองเท่าตอนต่อสัญญา การเปลี่ยนจะใช้เวลาและเงินเท่าไร และอะไรทำให้เป็นเช่นนั้น
3. การเชื่อมต่อใดของคุณที่เป็นจุดต่อจุด และต้องทำอะไรเพื่อย้ายไปไว้หลังมาตรฐานเปิดร่วม
4. คุณเก็บข้อความอิสระในที่ที่ระบบรหัสหรือศัพท์เฉพาะที่เผยแพร่แทนได้ตรงไหน และข้อความอิสระซ่อนข้อผิดพลาดอะไรอยู่
5. "รองรับมาตรฐาน" ในสัญญาของคุณกำหนดให้ผ่านการทดสอบความสอดคล้องหรือการรับรองอิสระหรือไม่ หรือเป็นเพียงคำยืนยัน
6. ข้อบังคับมาตรฐานเปิดใด (ระดับชาติหรือภาคส่วน) ที่ใช้กับคุณอยู่แล้ว และคุณปฏิบัติตามจริงหรือแค่อ้าง

## ข้อสรุปสำคัญ

- ความสามารถในการทำงานร่วมกันหมายถึงการใช้ข้อมูลที่แลกเปลี่ยน ไม่ใช่แค่ส่งผ่าน ออกแบบให้ครบสี่ระดับ: เทคนิค วากยสัมพันธ์ ความหมาย และองค์กร
- เลือกมาตรฐานที่เปิด เผยแพร่ และพัฒนาโดยอิสระได้ แทนการเชื่อมต่อแบบสั่งทำและรูปแบบกรรมสิทธิ์ ซึ่งก่อให้เกิดการผูกติดและต้นทุนแบบรวมกลุ่ม
- ทำให้ชั้น API และการแลกเปลี่ยนข้อมูลเป็นมาตรฐาน (OpenAPI, JSON/XML, gRPC/Protobuf) และใช้มาตรฐานที่เป็นที่ยอมรับของโดเมนคุณ (FHIR ในสุขภาพ ISO 20022 ในการเงิน OGC ในภูมิสารสนเทศ)
- ยึดความหมายไว้กับตัวระบุ ระบบรหัส ศัพท์เฉพาะ และออนโทโลยีที่ใช้ร่วมกัน ความสามารถในการทำงานร่วมกันระดับความหมายคือที่ที่การเชื่อมต่อส่วนใหญ่ล้มเหลวอย่างเงียบ ๆ
- กำหนดให้มีการทดสอบความสอดคล้อง และการรับรองในที่ที่มี มาตรฐานเป็นของจริงก็ต่อเมื่อการพัฒนาสอดคล้องตามมันอย่างพิสูจน์ได้
- ตัดสินการเลือกด้วยต้นทุนรวมตลอดอายุการใช้งานและทางเลือกตลอดอายุระบบ สำหรับแพลตฟอร์มอายุยาวที่มีหลายฝ่าย (เกือบทุกระบบองค์กรและภาครัฐ) มาตรฐานเปิดชนะ และรัฐบาลกำหนดเป็นข้อบังคับมากขึ้น

## แหล่งอ้างอิงและอ่านเพิ่มเติม

- HL7 International, *FHIR (Fast Healthcare Interoperability Resources)* specification (hl7.org/fhir)
- ISO 20022, *Universal financial industry message scheme* (iso20022.org)
- OpenAPI Initiative, *OpenAPI Specification* (Linux Foundation)
- Open Geospatial Consortium (OGC) standards (WMS, WFS, and successors)
- European Commission, *European Interoperability Framework (EIF)* and the Interoperable Europe Act
- UK Government, *Open Standards Principles* and the Technology Code of Practice (GOV.UK)
- W3C, *RDF*, *OWL (Web Ontology Language)*, and semantic-web standards
- SNOMED International (*SNOMED CT*), Regenstrief Institute (*LOINC*), and WHO (*ICD*) terminologies
- gRPC and Protocol Buffers specifications (Cloud Native Computing Foundation / open source)
- NIST and IEEE literature on systems interoperability and conformance testing
