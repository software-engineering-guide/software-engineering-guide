# 2.3 เอพีไอและการออกแบบอินเทอร์เฟซ

## ภาพรวมและแรงจูงใจ

[เอพีไอ](https://en.wikipedia.org/wiki/API) (API: application programming interface หรืออินเทอร์เฟซสำหรับการเขียนโปรแกรมประยุกต์) คือสัญญาที่ซอฟต์แวร์ชิ้นหนึ่งใช้เสนอความสามารถให้อีกชิ้นหนึ่ง เป็นจุดที่ทีม ระบบ และองค์กรมาพบกัน และเป็นสิ่งที่ทนทานที่สุดและแพงที่สุดถ้าทำผิด ลายเซ็นของฟังก์ชันภายในปรับโครงสร้างใหม่ได้อย่างอิสระ แต่เอพีไอที่เผยแพร่แล้วต่างออกไป มันคือคำมั่นสัญญาต่อผู้ใช้ที่เราอาจไม่เคยพบหน้า และการทำให้มันพังคือการทำให้พวกเขาพัง เมื่อองค์กรแยก[โมโนลิธ](https://en.wikipedia.org/wiki/Monolithic_application)ออกเป็นบริการ และเปิดความสามารถให้พาร์ตเนอร์และสาธารณะ เอพีไอจึงกลายเป็นพื้นผิวหลักของผลิตภัณฑ์และความเสี่ยงหลักของการเชื่อมต่อ

สำหรับทีมใหญ่ เอพีไอคือสิ่งที่ทำให้ผู้คนทำงานอย่างเป็นอิสระ อินเทอร์เฟซที่ออกแบบดีช่วยให้เราเปลี่ยนส่วนภายในได้โดยไม่ต้องประสานกับผู้ใช้ทุกราย ซึ่งเป็นจุดประสงค์ทั้งหมดของเส้นแบ่งบริการ อินเทอร์เฟซที่ออกแบบไม่ดีทำให้รายละเอียดภายในรั่ว บังคับให้ปล่อยระบบพร้อมกันทั้งหมด และเปลี่ยนชุดบริการให้เป็นโมโนลิธแบบกระจาย คือบริการที่แยกจากกันแต่พึ่งพากันแน่นจนต้องสร้างและปล่อยพร้อมกัน การออกแบบเอพีไอของคุณกำหนดโดยตรงว่าทีมของคุณเคลื่อนไหวได้อิสระเพียงไร

ในองค์กรขนาดใหญ่และภาครัฐ เอพีไอยังมีภาระเรื่องการปฏิบัติตามข้อกำหนด ความมั่นคงปลอดภัย และอายุการใช้งาน เอพีไอภาครัฐอาจต้องเป็นไปตาม[มาตรฐานเปิด](https://en.wikipedia.org/wiki/Open_standard) คงเสถียรหลายปี และให้บริการนักพัฒนาภายนอกที่เราประสานงานด้วยไม่ได้ เอพีไอขององค์กรเป็นรากฐานของการเชื่อมต่อกับพาร์ตเนอร์ที่มีระดับการให้บริการตามสัญญา ทั้งหมดนี้ยกระดับมาตรฐานของวินัยด้านเวอร์ชัน[ความเข้ากันได้ย้อนหลัง](https://en.wikipedia.org/wiki/Backward_compatibility) ธรรมาภิบาล และประสบการณ์ของนักพัฒนา

## หลักการสำคัญ

- ออกแบบสัญญาก่อน อินเทอร์เฟซคือการตัดสินใจเชิงผลิตภัณฑ์ที่ตั้งใจ ไม่ใช่ผลพลอยได้ของการลงมือสร้าง
- ปรับให้เหมาะกับประสบการณ์ของผู้ใช้เอพีไอ ไม่ใช่ความสะดวกของเราเอง
- ถือความเข้ากันได้ย้อนหลังเป็นคำมั่นสัญญา การเปลี่ยนแปลงที่ทำให้พังต้องมีเวอร์ชันใหม่และเส้นทางการย้าย
- ทำให้สิ่งที่ง่ายเป็นสิ่งที่ถูกต้อง ด้วยค่าเริ่มต้นที่สมเหตุสมผล ข้อผิดพลาดที่คาดเดาได้ และข้อตกลงที่สม่ำเสมอ
- ออกแบบรองรับความล้มเหลว [ความสามารถทำซ้ำได้ผลเท่าเดิม](https://en.wikipedia.org/wiki/Idempotence) (idempotency: คำขอที่ส่งซ้ำให้ผลเท่ากับส่งครั้งเดียว) การลองใหม่ การแบ่งหน้า (pagination) และ[การจำกัดอัตรา](https://en.wikipedia.org/wiki/Rate_limiting) (rate limiting) เป็นเรื่องชั้นหนึ่ง ไม่ใช่ความคิดตามหลัง
- เลือกรูปแบบโปรโตคอลให้เหมาะกับลักษณะการโต้ตอบ ไม่ใช่ตามกระแส
- กำกับดูแลเอพีไอเหมือนผลิตภัณฑ์ มีเจ้าของ วงจรชีวิต และเอกสาร

## ข้อแนะนำ

### ทำงานแบบเอพีไอมาก่อนและขับเคลื่อนด้วยสัญญา

กำหนดและทบทวนสัญญาของเอพีไอ ซึ่งรวมทรัพยากร การดำเนินการ สคีมา และความหมายของข้อผิดพลาด ก่อนเขียนการทำงานจริง ใช้ข้อกำหนดที่เครื่องอ่านได้ เพื่อให้สัญญาสร้างเอกสาร โครงโค้ดฝั่งไคลเอนต์และเซิร์ฟเวอร์ เซิร์ฟเวอร์จำลอง (mock server) และการตรวจสอบความถูกต้องได้ ผู้ใช้จึงเริ่มเชื่อมต่อกับตัวจำลองได้ระหว่างที่เราสร้าง และสัญญากลายเป็นแหล่งความจริงเดียวที่ทั้งสองฝ่ายทดสอบเทียบ

### เลือกรูปแบบการโต้ตอบอย่างตั้งใจ

เลือกระหว่าง [REST](https://en.wikipedia.org/wiki/REST) (representational state transfer), [GraphQL](https://en.wikipedia.org/wiki/GraphQL), [gRPC](https://en.wikipedia.org/wiki/GRPC) และ[การส่งข้อความแบบขับเคลื่อนด้วยเหตุการณ์](https://en.wikipedia.org/wiki/Event-driven_architecture)ตามลักษณะการโต้ตอบ ไม่ใช่ความชอบส่วนตัว ใช้ REST สำหรับอินเทอร์เฟซที่เน้นทรัพยากร เชื่อมต่อกันได้กว้าง และแคชได้ ใช้ GraphQL เมื่อไคลเอนต์หลากหลายต้องการอ่านข้อมูลแบบยืดหยุ่นและรวมข้อมูลจากกราฟที่ซับซ้อน ใช้ gRPC สำหรับการเรียกที่ประสิทธิภาพสูงและกำหนดชนิดข้อมูลเข้มงวดระหว่างบริการภายใน ใช้การส่งข้อความแบบขับเคลื่อนด้วยเหตุการณ์สำหรับเวิร์กโฟลว์แบบอะซิงโครนัสที่พึ่งพากันหลวม และสำหรับแพร่กระจายการเปลี่ยนสถานะ ระบบใหญ่จำนวนมากใช้หลายรูปแบบพร้อมกัน แต่ละอย่างอยู่ในที่ที่เหมาะ

### กำหนดเวอร์ชันและเลิกใช้อย่างมีวินัย

ใช้กลยุทธ์การกำหนดเวอร์ชันที่ชัดเจนและนโยบายการเลิกใช้ที่เผยแพร่ ได้แก่วิธีจัดประเภทการเปลี่ยนแปลง ระยะเวลาที่สนับสนุนเวอร์ชันเก่า และวิธีแจ้งผู้ใช้ ขีดเส้นชัดเจนระหว่างการเปลี่ยนแปลงที่เข้ากันได้ย้อนหลัง (เพิ่มฟิลด์ที่ไม่บังคับ เอนด์พอยต์ใหม่) กับการเปลี่ยนแปลงที่ทำให้พัง (ลบหรือเปลี่ยนชื่อฟิลด์ เปลี่ยนชนิดหรือความหมาย) อย่านำความหมายของฟิลด์ที่มีอยู่ไปใช้ใหม่ ให้ผู้ใช้มีช่วงเวลาซ้อนทับเพื่อย้าย และสื่อสารกำหนดการล่วงหน้านาน ๆ

### ทำให้ความหมายของข้อผิดพลาดสม่ำเสมอและเครื่องอ่านได้

ส่งข้อผิดพลาดที่มีโครงสร้างและคาดเดาได้ ได้แก่รหัสที่เครื่องอ่านได้และคงที่ ข้อความที่มนุษย์อ่านได้ และบริบทมากพอที่จะลงมือแก้ โดยไม่เปิดเผยรายละเอียดภายในที่อ่อนไหว ใช้ความหมายของสถานะเดียวกันทุกเอนด์พอยต์ เพื่อให้ไคลเอนต์จัดการข้อผิดพลาดได้เหมือนกันหมด บันทึกทุกข้อผิดพลาดที่ผู้ใช้อาจเจอ

### สร้างความสามารถทำซ้ำได้ผลเท่าเดิม การแบ่งหน้า และการจำกัดอัตราไว้ตั้งแต่ต้น

ทำให้การเขียนลองซ้ำได้อย่างปลอดภัยด้วยการรองรับคีย์ idempotency เพื่อให้ไคลเอนต์ที่ลองใหม่หลังหมดเวลาไม่ตัดเงินซ้ำหรือสร้างซ้ำ แบ่งหน้าทุกเอนด์พอยต์ที่ส่งรายการตั้งแต่วันแรก และเลือกการแบ่งหน้าแบบเคอร์เซอร์สำหรับชุดข้อมูลใหญ่หรือเปลี่ยนแปลงบ่อย ใช้และบันทึกขีดจำกัดอัตรา และส่งสถานะขีดจำกัดปัจจุบันกลับให้ไคลเอนต์ เพื่อให้ถอยหลังได้อย่างนุ่มนวล

### กำกับดูแลเอพีไอและลงทุนกับประสบการณ์ของนักพัฒนา

ปฏิบัติต่อเอพีไอแต่ละตัวเป็นผลิตภัณฑ์ มีเจ้าของ วงจรชีวิต และรายการในแคตตาล็อก จัดการทบทวนการออกแบบหรือคณะกรรมการมาตรฐานเอพีไอ เพื่อให้อินเทอร์เฟซสม่ำเสมอข้ามทีม ลงทุนกับประสบการณ์ของนักพัฒนา ได้แก่เอกสารอ้างอิงที่ถูกต้อง คู่มือเริ่มต้นเร็ว ตัวอย่าง แซนด์บ็อกซ์ และบันทึกการเปลี่ยนแปลง ในระบบนิเวศขนาดใหญ่ พอร์ทัลหรือแคตตาล็อกที่ทำให้ค้นพบเอพีไอได้เป็นสิ่งจำเป็น

## ข้อดีข้อเสียและการแลกเปลี่ยน

| รูปแบบ | เหมาะกับ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| REST / HTTP | เอพีไอสาธารณะที่เน้นทรัพยากร | ใช้กันทั่วไป แคชได้ เรียบง่าย เชื่อมต่อกันได้ | ดึงข้อมูลเกินหรือไม่พอ ต้องไปกลับหลายรอบ สัญญาหลวมถ้าไม่ระบุข้อกำหนด |
| GraphQL | การอ่านที่ยืดหยุ่นสำหรับไคลเอนต์หลากหลาย | ไคลเอนต์ระบุคิวรีเอง เอนด์พอยต์เดียว สคีมาเข้มแข็ง | แคชและจำกัดอัตราซับซ้อน เสี่ยงเรื่องต้นทุนของคิวรี เซิร์ฟเวอร์ซับซ้อน |
| gRPC | การเรียกภายในที่ประสิทธิภาพสูง | เร็ว กะทัดรัด กำหนดชนิดข้อมูลเข้มงวด รองรับสตรีม | เบราว์เซอร์รองรับไม่ดี มนุษย์อ่านยากกว่า เครื่องมือหนักกว่า |
| ขับเคลื่อนด้วยเหตุการณ์ | เวิร์กโฟลว์แบบอะซิงโครนัสที่พึ่งพากันหลวม | พึ่งพากันหลวม ขยายได้ ทนทาน | ใช้เหตุผลยากกว่า ความสอดคล้องในที่สุด (eventual consistency) ภาระด้านปฏิบัติการสูง |

กลยุทธ์การกำหนดเวอร์ชันแลกเสถียรภาพกับการดูแลรักษา การรองรับเวอร์ชันเก่าหลายตัวปกป้องผู้ใช้ แต่ทำให้โค้ดที่ต้องดูแลและทดสอบเพิ่มเป็นทวีคูณ ความเข้ากันได้ย้อนหลังแลกอิสระของเราเองกับเสถียรภาพของผู้ใช้ ซึ่งมักเป็นการแลกที่ถูกต้องสำหรับเอพีไอที่ใช้กันกว้างขวาง ภาพใหญ่คือ ต้นทุนของการตัดสินใจเรื่องเอพีไอที่ผิดต้องจ่ายโดยผู้ใช้ทุกคนตลอดอายุของอินเทอร์เฟซ จึงคุ้มที่จะใช้แรงออกแบบที่เส้นแบ่งมากกว่าแทบทุกที่อื่น

## คำถามที่ควรคุยกับทีม

1. **จะจัดประเภทการเปลี่ยนแปลงว่าเข้ากันได้ย้อนหลังหรือทำให้พังอย่างไร และการตรวจอัตโนมัติอะไรที่จับการพังเงียบ ๆ ได้ก่อนปล่อย?** บทนี้ขีดเส้นแข็งว่า การเพิ่มฟิลด์ที่ไม่บังคับและเอนด์พอยต์ใหม่ปลอดภัย ขณะที่การลบหรือเปลี่ยนชื่อฟิลด์ เปลี่ยนชนิด หรือนำความหมายของฟิลด์ไปใช้ใหม่ ทำให้ผู้ใช้พัง ในทีมใหญ่ คนที่ทำการเปลี่ยนแปลงมักมองไม่เห็นผู้ใช้ทุกราย การปรับ "เล็กน้อย" จึงอาจทำให้พาร์ตเนอร์ที่เราไม่เคยคุยด้วยพังอย่างเงียบ ๆ นำสัญญาณที่เป็นรูปธรรมมาที่การประชุม คือคุณรันการตรวจความเข้ากันได้ของสัญญาอัตโนมัติใน CI เทียบกับข้อกำหนดที่เผยแพร่หรือไม่ หรือพึ่งให้ใครสักคนจำกฎได้ ในองค์กรขนาดใหญ่และภาครัฐ ที่การเปลี่ยนแปลงที่ทำให้พังบังคับให้ต้องย้ายอย่างประสานงานข้ามพาร์ตเนอร์ทุกราย และอาจข้ามการเปลี่ยนผู้ขายและการเปลี่ยนรัฐบาล ต้นทุนขยายตามจำนวนผู้ใช้ ตัดสินใจกฎการจัดประเภทและติดตั้งด่านตรวจความเข้ากันได้ เพื่อให้การเปลี่ยนแปลงที่เข้ากันไม่ได้ทำให้บิลด์ล้ม แทนที่จะเป็นการเชื่อมต่อที่ล้ม

2. **ตัวพื้นฐานด้านความน่าเชื่อถือใด ได้แก่คีย์ idempotency การแบ่งหน้า และการจำกัดอัตรา ที่ต้องมีบนทุกเอนด์พอยต์ใหม่ตั้งแต่วันแรก?** บทนี้ยืนยันว่าสิ่งเหล่านี้เป็นเรื่องชั้นหนึ่ง เพราะการเติมคีย์ idempotency ภายหลังบนเอนด์พอยต์ตัดเงินที่ใช้งานจริง หรือการเพิ่มการแบ่งหน้าให้รายการที่ส่งออกไปแล้ว คือการเปลี่ยนแปลงที่ทำให้พังเอง ระบบนิเวศขนาดใหญ่ขยายปัญหานี้ เอนด์พอยต์ที่ใช้ได้ตอนทดสอบพังเมื่อเจอปริมาณข้อมูลจริง และการเขียนที่ไม่ idempotent ทำให้เครือข่ายสะดุดครั้งเดียวกลายเป็นการตัดเงินซ้ำ นำหลักฐานมาว่าเอนด์พอยต์ปัจจุบันตัวใดขาดสิ่งเหล่านี้ และพายุการลองซ้ำจะเกิดอะไรขึ้น ทำค่าเริ่มต้นเหล่านี้ให้ต่อรองไม่ได้สำหรับเอนด์พอยต์ใหม่ คือการแบ่งหน้าแบบเคอร์เซอร์ทุกรายการ คีย์ idempotency ทุกการเขียน และขีดจำกัดอัตราที่บันทึกไว้และส่งสถานะปัจจุบันกลับ เปลี่ยนการย้ายที่ถูกบังคับในอนาคตให้เป็นนิสัยการออกแบบครั้งเดียว

3. **คุณออกแบบและทบทวนสัญญาก่อนเขียนการทำงานจริงหรือไม่ หรืออินเทอร์เฟซรั่วออกมาจากโค้ด?** ข้อแนะนำแบบเอพีไอมาก่อนขอข้อกำหนดที่เครื่องอ่านได้และผ่านการทบทวนล่วงหน้า ซึ่งสร้างเอกสาร โครงโค้ด และตัวจำลอง และให้ผู้ใช้เชื่อมต่อกับตัวจำลองได้ระหว่างที่เราสร้าง เมื่อสัญญาตามหลังการลงมือทำ อินเทอร์เฟซจะเปิดเผยโครงสร้างฐานข้อมูลภายในและเปลี่ยนไปทุกครั้งที่การทำงานเปลี่ยน ซึ่งเป็นรูปแบบที่ไม่ควรทำอันดับหนึ่งในบทนี้ สัญญาณที่ควรตรวจคือ ผู้ใช้เริ่มเชื่อมต่อกับตัวจำลองของคุณได้วันนี้หรือไม่ หรือต้องรอแบ็กเอนด์ที่รันอยู่ สำหรับเอพีไอสาธารณะและเอพีไอของพาร์ตเนอร์ ที่อินเทอร์เฟซเป็นพื้นผิวของผลิตภัณฑ์และเป็นสิ่งที่แพงที่สุดถ้าทำผิด การใช้เวลาหนึ่งวันกับสัญญาช่วยประหยัดแรงสนับสนุนที่วนไปมาหลายสัปดาห์ ทำให้การทบทวนสัญญาเป็นขั้นตอนที่ต้องมีก่อนเริ่มลงมือสร้าง

4. **เมื่อสองทีมต้องเปิดเผยความสามารถเดียวกัน รูปแบบการโต้ตอบใดชนะ และใครมีอำนาจปฏิเสธโปรโตคอลที่สี่?** บทนี้บอกให้เลือก REST, GraphQL, gRPC หรือการส่งข้อความแบบขับเคลื่อนด้วยเหตุการณ์ตามความเหมาะสมของการโต้ตอบ แต่ในระดับใหญ่ ความเสี่ยงจริงคือทุกทีมเลือกของโปรดของตัวเอง และผู้ใช้เจอข้อตกลงที่ต่างกันทุกเอนด์พอยต์ องค์กรใหญ่ต้องจ่ายค่าความกระจัดกระจายนั้นในไลบรารีไคลเอนต์ เกตเวย์ การเฝ้าติดตาม และภาระทางความคิดของผู้เชื่อมต่อทุกคนที่ต้องเรียนสี่สำนวนแทนที่จะเป็นหนึ่งเดียว นำบัญชีโปรโตคอลที่ใช้งานจริงอยู่แล้ว การโต้ตอบที่แต่ละตัวถูกเลือกมารองรับ และผู้ใช้ที่ใช้มากกว่าหนึ่งตัว มาคุย ข้อพิจารณาฝั่งตรงข้ามก็มีจริง ค่าเริ่มต้นร่วมลดความบานปลาย แต่คำสั่งที่เข้มงวดบังคับให้ปัญหาแบบ gRPC ต้องลงหลุมแบบ REST ระบุคณะกรรมการมาตรฐานหรือการทบทวนสถาปัตยกรรมที่เป็นเจ้าของกระบวนการข้อยกเว้น เพราะในระบบองค์กรและภาครัฐ การแพร่หลายของรูปแบบกลายเป็นภาษีถาวรต่อการเชื่อมต่อ และย้อนกลับยากเมื่อพาร์ตเนอร์พึ่งพาแต่ละตัวแล้ว

5. **นโยบายการเลิกใช้ที่เผยแพร่ของเราคืออะไร และเราพิสูจน์ได้หรือไม่ว่าเราทำตามช่วงเวลาสนับสนุนที่ประกาศไว้จริง?** บทนี้มองการกำหนดเวอร์ชันและการเลิกใช้เป็นวินัย คือนโยบายที่เขียนไว้ว่าเวอร์ชันเก่าอยู่ได้นานเท่าไร แจ้งผู้ใช้อย่างไร และมีช่วงซ้อนทับให้ย้ายเท่าไร คำสัญญาที่บังคับไม่ได้แย่กว่าไม่มีเลย เพราะระบบนิเวศขนาดใหญ่มีผู้ใช้ที่เราไม่เคยคุยด้วย ซึ่งจะเรียกเวอร์ชันที่เลิกแล้วต่อไปจนกว่ามันจะพังบนระบบจริง นำหลักฐานมาคุย ได้แก่วันนี้แบกเวอร์ชันที่ใช้งานอยู่กี่เวอร์ชัน การใช้งานจริงของแต่ละตัว เห็นหรือไม่ว่าผู้ใช้รายใดยังเรียกเอนด์พอยต์ที่เลิกใช้ และการยุติครั้งล่าสุดประกาศล่วงหน้านานแค่ไหน แรงกดดันฝั่งตรงข้ามคือต้นทุนการดูแลเทียบกับเสถียรภาพของผู้ใช้ และทั้งสองจริงทั้งคู่ สำหรับพาร์ตเนอร์องค์กรที่มีระดับการให้บริการตามสัญญา และเอพีไอภาครัฐที่ต้องอยู่รอดข้ามการเปลี่ยนรัฐบาลและผู้ขาย ช่วงเวลาสนับสนุนคือพันธะที่อาจอยู่นานกว่าทีมที่ให้ไว้ ดังนั้นตัดสินว่าใครเป็นเจ้าของ และจะพิสูจน์ว่าการยุติปลอดภัยก่อนที่มันจะเกิดอย่างไร

6. **เรารู้ได้อย่างไรว่าประสบการณ์ของนักพัฒนาของเราดี หรือแค่สันนิษฐานเพราะเอพีไอใช้ได้สำหรับเรา?** บทนี้วางกรอบเอพีไอแต่ละตัวเป็นผลิตภัณฑ์ที่การยอมรับขึ้นอยู่กับเอกสารอ้างอิงที่ถูกต้อง คู่มือเริ่มต้นเร็ว ตัวอย่าง แซนด์บ็อกซ์ บันทึกการเปลี่ยนแปลง และแคตตาล็อกที่ค้นพบได้ ทีมมักเข้าใจผิดว่า "เอพีไอทำงานได้" เท่ากับ "เอพีไอใช้ได้" และช่องว่างนั้นปรากฏเป็นตั๋วสนับสนุน การเชื่อมต่อที่ล้มเหลว และผู้ใช้ที่ยอมแพ้เงียบ ๆ นำสัญญาณที่วัดได้มาแทนความเห็น ได้แก่เวลาถึงการเรียกครั้งแรกที่สำเร็จของผู้เชื่อมต่อใหม่ ปริมาณตั๋วสนับสนุนต่อเอนด์พอยต์ เอกสารที่เผยแพร่ล้าสมัยกว่าสัญญาจริงเพียงใด และผู้มาใหม่ช่วยตัวเองจากพอร์ทัลได้โดยไม่ต้องอีเมลหาทีมเราหรือไม่ ความตึงเครียดคือเอกสารและพอร์ทัลกินแรงจริงที่แย่งกับการส่งมอบฟีเจอร์ แต่ในระบบนิเวศขนาดใหญ่ ประสบการณ์นักพัฒนาที่แย่ผลักต้นทุนการเชื่อมต่อไปที่ผู้ใช้หลายร้อยรายพร้อมกัน ในภาครัฐ ที่เอพีไอเปิดให้บริการนักพัฒนาภายนอกที่เราประสานงานไม่ได้และมักมีข้อบังคับเรื่องความโปร่งใส อินเทอร์เฟซที่ใช้ได้ จัดทำเอกสารดี และค้นพบได้ เป็นส่วนหนึ่งของพันธะความรับผิดชอบต่อสาธารณะ ไม่ใช่ของแถม

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** เมื่อมีวิศวกรสองสามคนและไม่มีเวลาให้พิธีรีตอง ให้รักษาสัญญาให้เบาแต่จริง คือข้อกำหนดที่เครื่องอ่านได้ฉบับเดียวที่ลูกค้าพันธมิตรออกแบบรายแรก ๆ เชื่อมต่อได้ระหว่างที่คุณสร้าง อย่าเพิ่งตั้งเกตเวย์เอพีไอ แคตตาล็อก หรือคณะกรรมการธรรมาภิบาล แต่ให้ล็อกสองนิสัยที่เพิ่มทีหลังเจ็บปวด คือคีย์ idempotency บนการเขียนและการแบ่งหน้าแบบเคอร์เซอร์บนรายการ เพราะการเติมภายหลังบนเอนด์พอยต์ที่ใช้งานอยู่คือการเปลี่ยนแปลงที่ทำให้พังซึ่งคุณรับไม่ไหว เลือกรูปแบบการโต้ตอบเดียว เกือบทุกครั้งคือ REST เพื่อไม่ให้แบกความบานปลายของโปรโตคอลเข้าสู่ปีแรก

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญเอพีไอโดยเฉพาะและงบจำกัด ให้พึ่งเครื่องมือที่สร้างเอกสาร ตัวจำลอง และโครงโค้ดไคลเอนต์จากข้อกำหนด เพื่อให้คนทำงานทั่วไปดูแลอินเทอร์เฟซได้โดยไม่ต้องเชี่ยวชาญโปรโตคอลลึก ชั่งซื้อกับสร้างให้หนัก เกตเวย์สำเร็จรูปหรือแพลตฟอร์มจัดการเอพีไอให้การจำกัดอัตรา คีย์ และพอร์ทัลนักพัฒนาที่ไม่เช่นนั้นคุณต้องทำเอง รักษาพื้นผิวให้เล็กและข้อตกลงให้สม่ำเสมอ เพราะทุกเอนด์พอยต์เพิ่มและทุกรูปแบบข้อผิดพลาดที่ทำเฉพาะกิจคือสิ่งที่ทีมบาง ๆ ต้องสนับสนุนไปตลอด

**องค์กรขนาดใหญ่.** ข้ามทีมอิสระจำนวนมาก ปัญหาหลักคือความสม่ำเสมอโดยไม่กลายเป็นคอขวด ได้แก่คู่มือรูปแบบร่วม การทบทวนมาตรฐานเอพีไอ แคตตาล็อกที่ทำให้ค้นพบอินเทอร์เฟซได้ และการตรวจความเข้ากันได้ย้อนหลังอัตโนมัติใน CI เพื่อให้การพังเงียบ ๆ ทำให้บิลด์ล้มแทนการเชื่อมต่อ กำกับดูแลเอพีไอแต่ละตัวเป็นผลิตภัณฑ์ที่มีเจ้าของระบุชื่อ วงจรชีวิต และนโยบายการเลิกใช้ที่เผยแพร่ และวัดการยอมรับ ภาระการสนับสนุน และความถี่ของการเปลี่ยนแปลงที่ทำให้พัง เพื่อให้พอร์ตโฟลิโอแข็งแรง ทำรูปแบบการโต้ตอบและกฎการกำหนดเวอร์ชันให้เป็นมาตรฐานทั้งองค์กร เพราะในระดับนี้ ความกระจัดกระจายคือค่าเริ่มต้นที่แพง

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง ข้อบังคับมาตรฐานเปิด และความรับผิดชอบต่อสาธารณะกำหนดทุกการเลือก เผยแพร่สัญญาอย่างเปิดเผย ทำตามมาตรฐานเปิดที่กำหนด และให้แซนด์บ็อกซ์กับเอกสารอ้างอิงเพื่อให้นักพัฒนาภายนอกที่คุณประสานงานไม่ได้ช่วยตัวเองได้ ถือความเข้ากันได้ย้อนหลังระยะยาวเป็นข้อกำหนดเชิงนโยบาย เพราะการเชื่อมต่อต้องอยู่รอดข้ามการเปลี่ยนรัฐบาลและผู้ขาย และทำให้การเปลี่ยนแปลงที่ทำให้พังเกิดน้อย ถูกกำกับเข้มงวด และประกาศล่วงหน้านาน รักษาเอพีไอและเอกสารให้โปร่งใสพอรับการตรวจสอบจากสาธารณะและผู้ตรวจสอบ และหลีกเลี่ยงรูปแบบที่เป็นกรรมสิทธิ์ซึ่งจะกักขังรัฐบาลชุดต่อไป

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัประยะเริ่มต้นที่ส่งเอพีไอสาธารณะตัวแรกเขียนสัญญาเป็นข้อกำหนดที่เครื่องอ่านได้ก่อนเขียนโค้ด เพื่อให้ลูกค้าพันธมิตรออกแบบสองรายเชื่อมต่อกับตัวจำลองได้ระหว่างที่แบ็กเอนด์ยังสร้างอยู่ แม้จะมีผู้ใช้เพียงหยิบมือ ก็เพิ่มคีย์ idempotency ให้เอนด์พอยต์ตัดเงินและการแบ่งหน้าแบบเคอร์เซอร์ให้ทุกรายการ เพราะการเติมภายหลังเมื่อพาร์ตเนอร์พึ่งพาเอพีไอแล้วจะเป็นการเปลี่ยนแปลงที่ทำให้พังซึ่งรับไม่ไหว สัญญาล่วงหน้าใช้เวลาหนึ่งวันและประหยัดการสนับสนุนที่วนไปมาหลายสัปดาห์

**องค์กรขนาดใหญ่.** บริษัทชำระเงินขนาดใหญ่เปิดเอพีไอ REST สาธารณะให้ร้านค้าหลายพันราย ทุกเอนด์พอยต์ที่เขียนรับคีย์ idempotency เพื่อให้การลองใหม่ผ่านเครือข่ายไม่สร้างการตัดเงินซ้ำ ทุกเอนด์พอยต์ที่ส่งรายการใช้การแบ่งหน้าแบบเคอร์เซอร์ ข้อผิดพลาดมีรหัสคงที่ที่บันทึกในเอกสารอ้างอิงสาธารณะ นโยบายการเลิกใช้อย่างเป็นทางการรับประกันช่วงเวลาสนับสนุนที่ยาวนานสำหรับทุกเวอร์ชัน พร้อมการแจ้งล่วงหน้าและคู่มือการย้าย วินัยนี้เป็นข้อได้เปรียบทางการแข่งขัน ผู้เชื่อมต่อเชื่อมั่นว่าเอพีไอจะไม่พังใต้เท้าพวกเขา

**ภาครัฐ.** บริการดิจิทัลระดับชาติเผยแพร่เอพีไอเปิดสำหรับข้อมูลพลเมือง ตามมาตรฐานเปิดที่กำหนดและกระบวนการออกแบบแบบเอพีไอมาก่อน สัญญาถูกระบุและทบทวนก่อนสร้าง เผยแพร่ในแคตตาล็อกเอพีไอกลางของรัฐบาล และให้บริการพร้อมแซนด์บ็อกซ์ เพื่อให้นักพัฒนาบุคคลที่สามซึ่งประสานงานทีละรายไม่ได้เชื่อมต่อได้เอง ความเข้ากันได้ย้อนหลังระยะยาวเป็นข้อกำหนดเชิงนโยบาย เพราะการเชื่อมต่อต้องอยู่รอดข้ามการเปลี่ยนรัฐบาลและผู้ขาย การเปลี่ยนแปลงที่ทำให้พังจึงเกิดน้อยและถูกกำกับเข้มงวด

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

การออกแบบเอพีไอที่ดีลดต้นทุนการเชื่อมต่อ ซึ่งมักเป็นต้นทุนก้อนใหญ่ที่สุดของการเชื่อมระบบและการรับพาร์ตเนอร์ ด้วยเอพีไอที่ชัดเจน เสถียร และมีเอกสารดี ผู้ใช้เชื่อมต่อได้ในไม่กี่วันโดยไม่ต้องเปิดตั๋วสนับสนุนเลยสักใบ เอพีไอที่ไม่ดีสร้างภาระการสนับสนุนไม่รู้จบ การเชื่อมต่อที่ล้มเหลว และความเสียหายต่อชื่อเสียง เมื่อเอพีไอเองคือผลิตภัณฑ์ ประสบการณ์ของนักพัฒนาขับเคลื่อนการยอมรับและรายได้โดยตรง

ต้นทุนแฝงที่ใหญ่ที่สุดคือการเปลี่ยนแปลงที่ทำให้พัง ทุกการเปลี่ยนแปลงที่ทำให้พังบังคับให้ต้องย้ายอย่างประสานงานข้ามผู้ใช้ทั้งหมด ทั้งทีมภายในและพาร์ตเนอร์ภายนอก และต้นทุนรวมขยายตามจำนวนผู้ใช้และความยากที่พวกเขาจะย้ายพร้อมกัน การลงทุนล่วงหน้ากับการออกแบบที่สัญญามาก่อน ความเข้ากันได้ย้อนหลัง และวินัยด้านเวอร์ชัน หลีกเลี่ยงเหตุการณ์การย้ายทั้งองค์กรที่แพงเหล่านี้ เมื่อคุยกับผู้นำ ให้วางกรอบคุณภาพเอพีไอเป็นจุดงัดสำหรับความเป็นอิสระของทีม การเติบโตของระบบนิเวศพาร์ตเนอร์ และการหลีกเลี่ยงการย้ายที่ถูกบังคับซึ่งแพง ติดตามเวลาการเชื่อมต่อ ปริมาณตั๋วสนับสนุน และความถี่ของการเปลี่ยนแปลงที่ทำให้พังเป็นหลักฐาน

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **เอพีไอที่ลงมือก่อน:** อินเทอร์เฟซเปิดเผยโครงสร้างฐานข้อมูลภายในและเปลี่ยนทุกครั้งที่การทำงานเปลี่ยน
- **การเปลี่ยนแปลงที่ทำให้พังอย่างเงียบ ๆ:** นำฟิลด์ไปใช้ใหม่หรือเข้มงวดการตรวจสอบโดยไม่ขยับเวอร์ชัน ทำให้ผู้ใช้พังอย่างคาดเดาไม่ได้
- **อินเทอร์เฟซที่พูดมาก:** การออกแบบที่ต้องไปกลับหลายรอบสำหรับการดำเนินการเชิงตรรกะเดียว ทำร้ายประสิทธิภาพและการใช้งาน
- **ข้อตกลงที่ไม่สม่ำเสมอ:** ทุกเอนด์พอยต์คิดชื่อ รูปแบบข้อผิดพลาด และการแบ่งหน้าของตัวเอง ไคลเอนต์จึงสรุปรวมไม่ได้
- **ไม่มีการแบ่งหน้าหรือการจำกัดอัตรา:** เอนด์พอยต์ที่ใช้ได้ตอนทดสอบแต่พังเมื่อเจอปริมาณข้อมูลหรือโหลดจริง
- **การเขียนที่ไม่ idempotent:** การลองใหม่ทำให้เกิดข้อมูลซ้ำ เครือข่ายสะดุดครั้งเดียวทำให้ข้อมูลเสียหาย
- **เวอร์ชันบานปลาย:** มีเวอร์ชันที่ใช้งานอยู่มากเกินไปโดยไม่มีการเลิกใช้ ทำให้ภาระดูแลทวีจนจัดการไม่ไหว
- **เอกสารเป็นความคิดตามหลัง:** เอกสารอ้างอิงที่ไม่มีหรือล้าสมัย ผลักต้นทุนการเชื่อมต่อทั้งหมดไปให้ผู้ใช้

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** เอพีไอเกิดจากการลงมือสร้างเป็นผลพลอยได้ ไม่มีข้อตกลงร่วม อินเทอร์เฟซเปิดเผยโครงสร้างฐานข้อมูลภายใน การเปลี่ยนแปลงที่ทำให้พังเกิดบ่อย ไม่ประกาศ และถูกค้นพบเมื่อการเชื่อมต่อของผู้ใช้ล้ม
- **ระดับ 2 พัฒนา:** บางทีมทำตามข้อตกลง REST พื้นฐาน กำหนดเวอร์ชันแบบไม่เป็นทางการ และเขียนเอกสารด้วยมือ แต่การปฏิบัติไม่สม่ำเสมอข้ามทีม idempotency การแบ่งหน้า และการจำกัดอัตราปรากฏบางเอนด์พอยต์และไม่ปรากฏบางตัว ผู้ใช้ยังต้องเรียนรู้ความแปลกของเอพีไอแต่ละตัวไปทีละกรณี
- **ระดับ 3 สร้างมาตรฐาน:** การออกแบบที่สัญญามาก่อนพร้อมข้อกำหนดที่เครื่องอ่านได้ถูกบันทึกและบังคับใช้ทั้งองค์กร นโยบายการเลิกใช้ที่เผยแพร่ ความหมายข้อผิดพลาดที่สม่ำเสมอ และ idempotency การแบ่งหน้าแบบเคอร์เซอร์ และการจำกัดอัตราที่บังคับมีบนทุกเอนด์พอยต์ใหม่ คู่มือรูปแบบร่วมและการทบทวนมาตรฐานเอพีไอรักษาอินเทอร์เฟซให้สม่ำเสมอข้ามทีม
- **ระดับ 4 บริหารจัดการ:** พอร์ตโฟลิโอเอพีไอถูกวัดและควบคุมเทียบกับเส้นฐาน การตรวจความเข้ากันได้ย้อนหลังอัตโนมัติเป็นด่านของทุกการเปลี่ยนแปลงใน CI และติดตามเวลาถึงการเรียกครั้งแรกที่สำเร็จ ปริมาณตั๋วสนับสนุนต่อเอนด์พอยต์ ความถี่ของการเปลี่ยนแปลงที่ทำให้พัง จำนวนเวอร์ชันที่ใช้งานอยู่ และการใช้งานรายเอนด์พอยต์ เพื่อให้การเลิกใช้และการตัดสินใจออกแบบอิงหลักฐานแทนความเห็น เอพีไอแต่ละตัวเป็นผลิตภัณฑ์ที่ถูกกำกับในแคตตาล็อกพร้อมเจ้าของระบุชื่อ และตัวชี้วัดกระตุ้นการลงมือเมื่อบริการเบี่ยงจากเป้าหมาย
- **ระดับ 5 ประสานทั้งระบบ:** กลยุทธ์เอพีไอถูกปรับปรุงอย่างต่อเนื่องและผสานทั้งองค์กร แคตตาล็อก เกตเวย์ กฎการกำหนดเวอร์ชัน และด่านความเข้ากันได้ทำงานเป็นระบบเดียว องค์กรเลิกใช้ รวม และกำหนดขอบเขตอินเทอร์เฟซใหม่เป็นกิจวัตรตามการยอมรับและต้นทุนที่วัดได้ มาตรฐานรูปแบบการโต้ตอบและการกำหนดเวอร์ชันปรับตามการเปลี่ยนแปลงของระบบนิเวศ พาร์ตเนอร์ และเทคโนโลยี และการเปลี่ยนแปลงที่ทำให้พังเกิดน้อยและจัดการได้ดี

## ประเด็นชวนคุย

- จะตัดสินอย่างไรว่าเอพีไอภายในเสถียรพอที่จะเผยแพร่ภายนอก?
- ช่วงเวลาสนับสนุนที่เหมาะสมสำหรับเวอร์ชันที่เลิกใช้ในบริบทของคุณคือเท่าไร และใครจ่าย?
- GraphQL หรือ gRPC ควรเข้ามาแทน REST ภายในที่ไหน และที่ไหนที่มันจะเพิ่มความซับซ้อนมากกว่าคุณค่า?
- จะบังคับความสม่ำเสมอของเอพีไอข้ามทีมอิสระจำนวนมากโดยไม่กลายเป็นคอขวดได้อย่างไร?
- เอพีไอที่ AI ใช้ได้และอินเทอร์เฟซเครื่องมือของเอเจนต์ควรเปลี่ยนข้อตกลงการออกแบบของคุณอย่างไร?
- การตรวจอัตโนมัติอะไรที่จับการเปลี่ยนแปลงที่เข้ากันไม่ได้ย้อนหลังได้ก่อนปล่อย?

## ข้อสรุปสำคัญ

- ออกแบบสัญญาก่อน เอพีไอคือผลิตภัณฑ์และคำมั่นสัญญาที่ยืนยาว
- ความเข้ากันได้ย้อนหลังปกป้องผู้ใช้ การเปลี่ยนแปลงที่ทำให้พังต้องมีเวอร์ชันใหม่และเส้นทางการย้าย
- เลือก REST, GraphQL, gRPC หรือเหตุการณ์ตามความเหมาะสมของการโต้ตอบ ไม่ใช่ตามกระแส
- สร้าง idempotency การแบ่งหน้า การจำกัดอัตรา และข้อผิดพลาดที่สม่ำเสมอตั้งแต่วันแรก
- กำกับดูแลเอพีไอเป็นผลิตภัณฑ์ มีเจ้าของ แคตตาล็อก และประสบการณ์นักพัฒนาที่แข็งแรง
