# 4.7 การจัดการตัวตนและสิทธิ์การเข้าถึง

## ภาพรวมและแรงจูงใจ

ทุกคำขอที่เข้ามาถึงระบบของคุณมีข้ออ้างแฝงมาด้วยเสมอ: *ฉันได้รับอนุญาตให้ทำสิ่งนี้* การจัดการตัวตนและสิทธิ์การเข้าถึง (identity and access management หรือ IAM) คือวินัยในการตัดสินว่าข้ออ้างนั้นเป็นจริงหรือไม่ มันตอบสองคำถามที่แยกจากกันซึ่งคนมักสับสนปนกันตลอด [การพิสูจน์ตัวตน](https://en.wikipedia.org/wiki/Authentication) (authentication) พิสูจน์ว่าคุณคือใคร [การกำหนดสิทธิ์](https://en.wikipedia.org/wiki/Authorization) (authorisation) ตัดสินว่าเมื่อพิสูจน์ตัวตนแล้วคุณทำอะไรได้บ้าง ถ้าแยกสองแนวคิดนี้ให้ชัดในหัว ความสับสนในสาขานี้จะหายไปครึ่งหนึ่ง

สำหรับทีมขนาดใหญ่ ตัวตนกลายเป็นการควบคุมที่สำคัญที่สุดที่คุณมีโดยไม่รู้ตัว บทที่ 4.3 ชี้ว่าตัวตนคือขอบเขตป้องกันใหม่ และบทที่ 4.1 สร้างแนวคิดซีโรทรัสต์ (zero trust) ไว้บนฐานนั้น: เมื่อคุณเลิกไว้ใจเครือข่าย สิ่งเดียวที่เหลือให้ไว้ใจคือตัวตนที่ผ่านการยืนยันและนโยบายที่ชัดเจน การเปลี่ยนแปลงนี้หมายความว่ากระบวนการรีเซ็ตรหัสผ่านที่อ่อนแอหรือบัญชีบริการที่ถูกลืมไม่ใช่บั๊กเล็ก ๆ อีกต่อไป มันคือประตูหน้า การรั่วไหลจริงส่วนใหญ่ไม่ใช่การโจมตีอันชาญฉลาดผ่านช่องโหว่ด้านความปลอดภัยของหน่วยความจำ แต่เป็นข้อมูลรับรองที่ถูกขโมย สิทธิ์ที่กว้างเกินไป และบัญชีที่ควรปิดไปตั้งหลายเดือนก่อน

เดิมพันสูงขึ้นในบริบทขององค์กรขนาดใหญ่และภาครัฐ องค์กรระดับโลกต้องรับมือกับไดเรกทอรีที่ซ้อนทับกันหลายสิบแห่ง ผู้เข้าและออกเป็นพันคนต่อเดือน และพันธมิตรที่ต้องการสิทธิ์เฉพาะส่วนในระบบของคุณ หน่วยงานรัฐเพิ่มชั้นของข้อมูลรับรองแบบสมาร์ทการ์ด ระดับการรับรองตัวตนที่กำหนดโดยกฎหมาย และผู้ตรวจสอบที่จะถามเป็นลายลักษณ์อักษรว่าใครเข้าถึงบันทึกชิ้นหนึ่งได้บ้างในวันหนึ่ง บทนี้มีจุดยืนชัดเจนว่าจะสร้างชั้นตัวตนที่ตอบคำถามเหล่านั้นได้ดีโดยไม่ทำให้คนทำงานติดขัดได้อย่างไร

## หลักการสำคัญ

- **การพิสูจน์ตัวตนและการกำหนดสิทธิ์เป็นคนละปัญหา** การพิสูจน์ตัวตนและการให้สิทธิ์ต้องมีการออกแบบและการทบทวนแยกกัน
- **หนึ่งตัวตน หลายระบบ** รวมเป็นแหล่งความจริงเดียวสำหรับกลุ่มตัวตนแต่ละกลุ่ม การที่ไดเรกทอรีกระจัดกระจายคือบั๊กด้านความมั่นคงปลอดภัย
- **สิทธิ์น้อยที่สุดเป็นค่าเริ่มต้น** เริ่มจากไม่มีสิทธิ์เลยแล้วเพิ่มอย่างตั้งใจ ทั้งสำหรับคนและเครื่อง
- **ข้อมูลรับรองทุกอย่างเป็นของชั่วคราว** ใช้ข้อมูลรับรองอายุสั้นที่ออกให้อัตโนมัติแทนความลับอายุยาว
- **การถอนสิทธิ์สำคัญเท่ากับการให้สิทธิ์** สิทธิ์ที่อยู่เกินความจำเป็นคือความเสี่ยงล้วน ๆ
- **ทนต่อฟิชชิงดีกว่าจำง่าย** ย้ายการพิสูจน์ตัวตนไปสู่พาสคีย์ (passkey) และปัจจัยที่ผูกกับฮาร์ดแวร์
- **เครื่องก็เป็นตัวตนเช่นกัน** เวิร์กโหลด ไปป์ไลน์ และบริการต้องมีตัวตนที่จัดการได้ ไม่ใช่กุญแจคงที่ที่ใช้ร่วมกัน
- **สิทธิ์การเข้าถึงคือวงจรชีวิต ไม่ใช่เหตุการณ์เดียว** ให้ ทบทวน และเพิกถอนตามกำหนดเวลา และพิสูจน์ได้ว่าทำแล้ว

## ข้อแนะนำ

### แยกการพิสูจน์ตัวตนออกจากการกำหนดสิทธิ์ และรวมศูนย์ทั้งสองอย่าง

พิสูจน์ตัวตนผ่านผู้ให้บริการตัวตน (identity provider หรือ IdP) เพียงหนึ่งเดียว ซึ่งเป็นระบบที่ยืนยันตัวตนและออกโทเค็นที่ระบบอื่นไว้ใจ จากนั้นให้แต่ละแอปพลิเคชันตัดสินใจเรื่องสิทธิ์เองจากตัวตนและแอตทริบิวต์ที่โทเค็นนั้นพกมา การแยกนี้ช่วยให้คุณยกระดับการพิสูจน์ตัวตนได้ครั้งเดียวสำหรับทุกคน ขณะที่ตรรกะสิทธิ์ละเอียดยังอยู่ใกล้ข้อมูลที่มันปกป้อง นำ[การลงชื่อเข้าใช้ครั้งเดียว](https://en.wikipedia.org/wiki/Single_sign-on) (single sign-on หรือ SSO) มาใช้ ซึ่งการพิสูจน์ตัวตนครั้งเดียวให้เข้าถึงหลายแอปพลิเคชันได้ เพื่อให้คนของคุณมีการเข้าสู่ระบบที่แข็งแรงหนึ่งครั้งแทนที่จะมีสี่สิบครั้งที่อ่อนแอ การเชื่อมโยงตัวตนข้ามองค์กร (federation) ขยายความไว้วางใจแบบเดียวกันข้ามขอบเขตองค์กร ทำให้ตัวตนของพันธมิตรเข้าถึงระบบของคุณได้โดยที่คุณไม่ต้องจัดการรหัสผ่านของเขา

### ใช้โปรโตคอลสมัยใหม่ให้ตรงกับหน้าที่จริงของแต่ละตัว

มาตรฐานสามตัวทำงานหลักเกือบทั้งหมด และแต่ละตัวมีหน้าที่ของมัน **OpenID Connect (OIDC)** คือชั้นตัวตนที่สร้างบน [OAuth](https://en.wikipedia.org/wiki/OAuth) 2.0 ใช้ตอบว่า *ผู้ใช้คนนี้คือใคร* สำหรับการลงชื่อเข้าใช้บนเว็บและมือถือ **OAuth 2.0** เป็นกรอบการกำหนดสิทธิ์สำหรับการเข้าถึงแบบมอบหมาย ใช้ให้แอปพลิเคชันเรียก API แทนผู้ใช้โดยไม่เห็นรหัสผ่านของเขาเลย (บทที่ 2.3) **Security Assertion Markup Language (SAML)** เป็นมาตรฐานการเชื่อมโยงตัวตนแบบ XML รุ่นเก่า ยังคงเป็นกำลังหลักของ SSO ระดับองค์กรเข้าสู่แอปพลิเคชันธุรกิจที่มีอยู่เดิม ความผิดพลาดที่พบบ่อยคือหยิบ OAuth มาพิสูจน์ตัวตนโดยตรง OAuth ให้สิทธิ์เข้าถึงทรัพยากร ส่วน OIDC อยู่ชั้นบนเพื่อยืนยันตัวตน เลือก OIDC สำหรับการลงชื่อเข้าใช้ของผู้ใช้ใหม่ ใช้ SAML ต่อไปในที่ที่แคตตาล็อกองค์กรของคุณต้องการ และอย่าคิดรูปแบบโทเค็นของตัวเอง

### ทำให้การพิสูจน์ตัวตนทนต่อฟิชชิง

รหัสผ่านอย่างเดียวป้องกันไม่ได้เมื่อขยายขนาด กำหนดให้ใช้การพิสูจน์ตัวตนหลายปัจจัย (multi-factor authentication หรือ MFA) ซึ่งรวมสิ่งที่คุณรู้ สิ่งที่คุณมี และสิ่งที่คุณเป็น กับทุกบัญชีของมนุษย์โดยไม่มีข้อยกเว้น แล้วก้าวข้ามปัจจัยที่อ่อนแอ: รหัสใช้ครั้งเดียวทาง SMS ถูกฟิชชิงได้และถูกสลับซิมได้ จุดหมายที่แข็งแรงคือ[พาสคีย์](https://en.wikipedia.org/wiki/Passkey)และมาตรฐาน WebAuthn ที่อยู่เบื้องหลัง (API ของเบราว์เซอร์สำหรับการพิสูจน์ตัวตนด้วยกุญแจสาธารณะ) ซึ่งผูกการเข้าสู่ระบบกับกุญแจส่วนตัวที่อยู่ในฮาร์ดแวร์และกับต้นทาง (origin) ของเว็บไซต์จริง ทำให้หน้าเว็บปลอมเก็บเกี่ยวอะไรที่มีค่าไม่ได้ พาสคีย์ยังไม่ต้องใช้รหัสผ่าน ซึ่งผู้ใช้ของคุณจะขอบคุณ ให้นับการกู้คืนบัญชีและการรีเซ็ตรหัสผ่านเป็นส่วนหนึ่งของพื้นผิวการพิสูจน์ตัวตน เพราะผู้โจมตีที่เอาชนะ MFA ของคุณไม่ได้ก็จะหันไปโจมตีกระบวนการรีเซ็ตแทน

### จัดการวงจรชีวิตผู้เข้า-ผู้ย้าย-ผู้ออก และถอนสิทธิ์ให้เร็ว

ตัวตนคือวงจรชีวิต **ผู้เข้า (joiner)** ต้องได้สิทธิ์ที่ถูกต้องตั้งแต่วันแรก **ผู้ย้าย (mover)** ที่เปลี่ยนบทบาทต้องได้สิทธิ์ใหม่ และที่สำคัญคือต้องถูกถอนสิทธิ์เดิม ไม่เช่นนั้นก็จะค่อย ๆ สะสมกุญแจของทั้งอาคาร **ผู้ออก (leaver)** ต้องสูญเสียสิทธิ์ทั้งหมดอย่างทันท่วงที ควรภายในไม่กี่นาทีหลังวันสุดท้าย ข้ามทุกระบบ ขับเคลื่อนเรื่องนี้จากแหล่งที่เชื่อถือได้ ซึ่งมักเป็นระบบทรัพยากรบุคคล เพื่อให้การเปลี่ยนสถานะที่นั่นให้สิทธิ์และถอนสิทธิ์ปลายทางโดยอัตโนมัติ ทำให้เป็นอัตโนมัติ เช็กลิสต์ออกงานแบบทำมือพลาดบางอย่างเสมอ และบัญชีที่พลาดนั้นคือบัญชีที่จะไปโผล่ในรายงานเหตุการณ์

### เลือกแบบจำลองการกำหนดสิทธิ์และเขียนเป็นนโยบายในรูปโค้ด

ให้สิทธิ์ด้วย[การควบคุมการเข้าถึงตามบทบาท](https://en.wikipedia.org/wiki/Role-based_access_control) (role-based access control หรือ RBAC) ซึ่งกำหนดสิทธิ์ให้บทบาทตามหน้าที่งานและกำหนดคนให้บทบาท เพราะคิดตามง่ายและตรวจสอบง่าย ใช้[การควบคุมการเข้าถึงตามแอตทริบิวต์](https://en.wikipedia.org/wiki/Attribute-based_access_control) (attribute-based access control หรือ ABAC) ในที่ที่ต้องการการตัดสินใจที่รู้บริบทจากแอตทริบิวต์ เช่น แผนก ระดับชั้นข้อมูล ที่ตั้ง หรือช่วงเวลาของวัน องค์กรที่ผู้ใหญ่ส่วนใหญ่ใช้แบบผสม: RBAC สำหรับการให้สิทธิ์ขั้นหยาบ ABAC สำหรับเงื่อนไขละเอียด ไม่ว่าจะเลือกแบบใด ให้เขียนการกำหนดสิทธิ์เป็น **นโยบายในรูปโค้ด (policy-as-code)**: กฎที่เขียนในรูปแบบที่ควบคุมเวอร์ชัน ทดสอบได้ และทบทวนได้ ไม่ใช่คลิกตั้งค่าในคอนโซล นโยบายในรูปโค้ดทำให้การตัดสินใจเรื่องสิทธิ์ตรวจสอบได้ เปรียบเทียบความต่างได้ และสอดคล้องกันข้ามสภาพแวดล้อม และให้คุณทดสอบการเปลี่ยนสิทธิ์ก่อนส่งขึ้นระบบ

### บังคับใช้สิทธิ์น้อยที่สุดด้วยการเข้าถึงแบบทันเวลาและ PAM

ใช้[หลักการสิทธิ์น้อยที่สุด](https://en.wikipedia.org/wiki/Principle_of_least_privilege): ทุกตัวตนได้สิทธิ์ขั้นต่ำที่ต้องใช้และไม่เกินนั้น สิทธิ์ที่ค้างอยู่ถาวรคือศัตรู เพราะสิทธิ์ที่ให้ถาวรคือสิทธิ์ที่ผู้โจมตีคนใดก็ใช้ได้ทุกเมื่อที่ยึดบัญชีนั้นได้ ให้เลือก**การเข้าถึงแบบทันเวลา (just-in-time หรือ JIT)** ซึ่งบุคคลขอสิทธิ์สูงขึ้นสำหรับช่วงเวลาที่จำกัด ได้รับหลังอนุมัติ และสูญเสียสิทธิ์นั้นอัตโนมัติเมื่อหมดช่วง สำหรับบัญชีอันตรายที่สุดของคุณ ให้ใช้**การจัดการสิทธิ์ระดับสูง (privileged access management หรือ PAM)**: ระบบที่เก็บข้อมูลรับรองผู้ดูแลระบบไว้ในตู้นิรภัย เป็นตัวกลางและบันทึกเซสชันที่มีสิทธิ์สูง และออกสิทธิ์ยกระดับเมื่อร้องขอ เป้าหมายคือไม่มีสิทธิ์ผู้ดูแลระบบค้างถาวรเลย เพื่อให้แม้แล็ปท็อปถูกยึดทั้งเครื่องก็ไม่ได้อะไรที่คงทน

### ให้ตัวตนที่แท้จริงแก่เครื่องและเวิร์กโหลด

มนุษย์เป็นเพียงครึ่งเดียวของตัวตนทั้งหมดของคุณ บริการ ไปป์ไลน์ คอนเทนเนอร์ และฟังก์ชันล้วนพิสูจน์ตัวตนกับบางสิ่ง และบ่อยเกินไปที่ทำด้วยความลับอายุยาวที่แปะไว้ในไฟล์ตั้งค่า ให้แทนกุญแจคงที่ด้วย**ตัวตนของเวิร์กโหลด (workload identity)** ที่จัดการได้: ข้อมูลรับรองอายุสั้นที่ออกให้เวิร์กโหลดโดยอัตโนมัติตามที่ที่มันรันและสิ่งที่มันเป็น ใช้ mutual TLS (mTLS) ซึ่งทั้งสองฝั่งของการเชื่อมต่อแสดงใบรับรอง สำหรับการพิสูจน์ตัวตนระหว่างบริการ เก็บความลับที่เหลือไว้ในตัวจัดการความลับ (secrets manager) โดยเฉพาะที่มีการหมุนเวียน ไม่เคยอยู่ในซอร์สโค้ดหรืออิมเมจ (บทที่ 4.2) ข้อมูลรับรองเวิร์กโหลดอายุสั้นที่หมุนเวียนอัตโนมัติขจัดสาเหตุที่พบบ่อยที่สุดของการรั่วไหลข้อมูลรับรองบนคลาวด์

### ทำให้ตัวตนเป็นระนาบควบคุม และทบทวนสิทธิ์อย่างต่อเนื่อง

ในสถาปัตยกรรมซีโรทรัสต์ (บทที่ 4.1) ตัวตนคือที่ที่นโยบายถูกตัดสินและบังคับใช้ จึงควรลงทุนที่นั่นให้สมน้ำสมเนื้อ จากนั้นปิดวงจรด้วย**การทบทวนสิทธิ์ (access review)** หรือที่เรียกว่าการรับรองซ้ำ (recertification): ตามกำหนดเวลา เจ้าของระบบแต่ละระบบยืนยันว่าทุกคนและทุกเครื่องที่มีสิทธิ์ยังต้องใช้อยู่ และเพิกถอนสิ่งที่พิสูจน์ความจำเป็นไม่ได้ ป้อนทุกเหตุการณ์การพิสูจน์ตัวตนและกำหนดสิทธิ์เข้าสู่เส้นทางการตรวจสอบย้อนหลังที่ตอบได้ว่า *ใครเข้าถึงอะไร เมื่อไร และภายใต้นโยบายใด* (บทที่ 4.6) การทบทวนสิทธิ์คือวิธีสู้กับการสะสมสิทธิ์ (privilege creep) ซึ่งเป็นการสะสมสิทธิ์อย่างช้า ๆ ที่การให้สิทธิ์แต่ละครั้งไม่เคยดูไม่สมเหตุสมผล แต่รวมกันแล้วทำให้บัญชีทรงพลังเกินไปมาก

## ข้อดีข้อเสียและการแลกเปลี่ยน

| การตัดสินใจ | ข้อดี | ข้อเสีย |
|---|---|---|
| IdP แบบรวมศูนย์พร้อม SSO | เข้าสู่ระบบแข็งแรงครั้งเดียว นโยบายสอดคล้อง ตรวจสอบง่าย | จุดล้มเหลวจุดเดียว ระบบล่มทำให้ทุกคนเข้าไม่ได้ |
| RBAC | เรียบง่าย ตรวจสอบได้ คุ้นเคย | บทบาทระเบิดจำนวน หยาบเกินไปสำหรับความต้องการที่ไวต่อบริบท |
| ABAC | ละเอียด รู้บริบท ขยายตามแอตทริบิวต์ได้ | ออกแบบ ทดสอบ และคิดตามได้ยากกว่า |
| พาสคีย์ / WebAuthn | ทนต่อฟิชชิง ไม่ต้องใช้รหัสผ่าน แข็งแรง | ขั้นตอนกู้คืนและอุปกรณ์หายต้องออกแบบอย่างรอบคอบ |
| การเข้าถึงแบบทันเวลา | สิทธิ์ค้างถาวรเกือบเป็นศูนย์ | มีแรงเสียดทาน ต้องมีเส้นทางอนุมัติที่เร็วและเชื่อถือได้ |
| การเชื่อมโยงตัวตนกับพันธมิตร | ไม่ต้องจัดการรหัสผ่านภายนอก ความไว้วางใจจำกัดขอบเขต | ความไว้วางใจขึ้นกับสุขอนามัยของพันธมิตรเอง |
| กุญแจบริการอายุยาว | ตั้งค่าง่ายมาก | รั่วง่าย สาเหตุอันดับหนึ่งของการรั่วไหลข้อมูลรับรอง |

ความตึงเครียดหลักคือความมั่นคงปลอดภัยเทียบกับแรงเสียดทาน ทุกการควบคุมที่ลดพื้นผิวการโจมตี (MFA กับทุกอย่าง การยกระดับสิทธิ์แบบ JIT อายุข้อมูลรับรองสั้น) ก็เพิ่มหนึ่งขั้นตอนให้วันของใครบางคน และคนจะหาทางเลี่ยงการควบคุมที่ลำบากเกินไป วิธีแก้คือทำให้เส้นทางที่ปลอดภัยเป็นเส้นทางที่ง่าย: SSO เพื่อให้การพิสูจน์ตัวตนที่แข็งแรงเหลือแค่แตะครั้งเดียว พาสคีย์เพื่อไม่มีรหัสผ่านให้พิมพ์ และการให้สิทธิ์อัตโนมัติเพื่อให้สิทธิ์ที่ถูกต้องปรากฏขึ้นเอง ใช้งบแรงเสียดทานในที่ที่รัศมีความเสียหายใหญ่ที่สุด คือสิทธิ์ระดับสูงและการเข้าถึงระบบจริง และทำให้การเข้าถึงในชีวิตประจำวันแทบไม่มีแรงเสียดทาน

## คำถามที่ควรคุยกับทีม

1. **คุณเพิกถอนสิทธิ์ทั้งหมดของคนที่ออกวันนี้ได้เร็วแค่ไหนจริง ๆ และรู้ได้อย่างไรว่าสำเร็จ?** ความเร็วของการถอนสิทธิ์เป็นตัวชี้วัดตรง ๆ ของความเป็นผู้ใหญ่ด้านตัวตนของคุณ เพราะผู้ออกที่สิทธิ์ยังค้างคือบัญชีที่ไม่มีใครเฝ้าดูแต่มีสิทธิ์จริง ในองค์กรขนาดใหญ่ที่มีระบบแยกกันหลายสิบระบบ คำตอบตรง ๆ มักเป็น "เราไม่แน่ใจ" และช่องว่างมักเป็นแอปพลิเคชันที่ไม่เคยเชื่อมกับผู้ให้บริการตัวตนกลาง นำกรณีคนลาออกล่าสุดมาจริง ๆ และไล่ตามทุกระบบที่เขาแตะได้ ตรวจเวลาว่าสิทธิ์แต่ละอย่างสิ้นสุดเมื่อไรจริง ตัดสินใจเป้าหมาย เช่น เพิกถอนทั้งหมดภายในหนึ่งชั่วโมงหลังสถานะในระบบทรัพยากรบุคคลเปลี่ยน และติดตั้งเครื่องมือวัดเพื่อให้พิสูจน์ได้ ไม่ใช่หวังเอา ถ้าระบบใดพึ่งให้ใครสักคนจำขั้นตอนทำมือ นั่นคือบัญชีที่การรั่วไหลในอนาคตจะใช้

2. **คุณยังมีสิทธิ์ระดับสูงที่ค้างถาวรและข้อมูลรับรองคงที่อายุยาวที่ไหนบ้าง และต้องทำอะไรเพื่อกำจัดมัน?** สิทธิ์ผู้ดูแลระบบที่ค้างถาวรและกุญแจบริการถาวรคือสองทรัพย์สินที่ผู้โจมตีต้องการที่สุด เพราะคงทนและทรงพลัง ทำบัญชีรายชื่อมนุษย์ทุกคนที่มีสิทธิ์เข้าถึงระบบจริงหรือสิทธิ์ผู้ดูแลแบบเปิดตลอดเวลา และทุกบริการที่พิสูจน์ตัวตนด้วยกุญแจคงที่ แล้วถามตัวเองตรง ๆ ว่ารายการใดย้ายไปใช้การยกระดับสิทธิ์แบบ JIT หรือตัวตนเวิร์กโหลดอายุสั้นได้ ข้อพิจารณาที่ขัดกันคือความกลัวในการดำเนินงาน: ทีมเก็บสิทธิ์ค้างถาวรไว้เพราะช่วงฉุกเฉิน (break-glass) รู้สึกปลอดภัยกว่าเมื่อมีมัน ดังนั้นคุณต้องทำให้การยกระดับสิทธิ์ฉุกเฉินเร็วและเชื่อถือได้ก่อนจะถอนสิทธิ์ค้างถาวร นำรายการมาที่การคุย แล้วจัดอันดับตามรัศมีความเสียหาย เริ่มที่การเข้าถึงระบบจริงและสิทธิ์ผู้ดูแลก่อน สภาวะปลายทางที่ควรตั้งเป้าคือไม่มีสิทธิ์ผู้ดูแลค้างถาวรและไม่มีกุญแจคงที่ที่อยู่ได้นานกว่าการ deploy ครั้งเดียว

3. **คุณมีตัวตนที่เชื่อถือได้หนึ่งเดียวต่อคนและต่อเวิร์กโหลด หรือหลายตัว และความกระจัดกระจายนั้นทำให้เสียอะไรไปบ้าง?** ไดเรกทอรีที่กระจัดกระจาย ที่คน ๆ เดียวมีห้าบัญชีใน ห้าระบบพร้อมแอตทริบิวต์ที่เพี้ยนไปเรื่อย ๆ คือที่ที่ช่องว่างการถอนสิทธิ์และสิทธิ์กำพร้าถือกำเนิด การรวมเป็นแหล่งความจริงเดียวสำหรับกลุ่มตัวตนแต่ละกลุ่มเป็นหนึ่งในการลงทุนที่ให้ผลคุ้มค่าที่สุดที่ทีมขนาดใหญ่ทำได้ เพราะทุกการควบคุมปลายทางขึ้นกับการรู้ว่าสองระเบียนคือคนเดียวกัน นำบัญชีรายการที่เก็บตัวตนของคุณมาและแยกว่าแห่งไหนเป็นแหล่งที่เชื่อถือได้ แห่งไหนเป็นสำเนาเพื่อความสะดวกที่ไม่มีใครกำกับดูแล ข้อแลกเปลี่ยนคือการรวมเป็นการย้ายขนาดใหญ่ที่ไม่หวือหวาซึ่งแย่งความสนใจกับงานฟีเจอร์ ตัดสินใจว่าต้นทุนต่อเนื่องของความกระจัดกระจาย ในรูปความเจ็บปวดตอนตรวจสอบและความเสี่ยงการรั่วไหล คุ้มกับการสนับสนุนเงินให้การย้ายนั้นตอนนี้ แทนที่จะรอหลังเหตุการณ์ครั้งถัดไป

4. **ปัจจัยพิสูจน์ตัวตนที่แข็งแรงที่สุดของคุณทนต่อฟิชชิงจริงหรือไม่ และอะไรขวางคุณไม่ให้เลิกใช้รหัสผ่านอย่างถาวร?** ปัจจัยที่ผู้โจมตีฟิชชิงไม่ได้คือสิ่งที่ยุติการขโมยข้อมูลรับรองในฐานะเส้นทางการรั่วไหลหลักของคุณ และพาสคีย์ที่ผูกกับ WebAuthn เป็นทางเลือกเดียวที่ติดตั้งได้กว้างขวางซึ่งผ่านเกณฑ์นั้น ในองค์กรขนาดใหญ่ ภาพตรง ๆ มักปนกัน: พาสคีย์สำหรับบางคน รหัสใช้ครั้งเดียวทาง SMS สำหรับบางคน และแอปพลิเคชันรุ่นเก่าหางยาวที่ยังรับรหัสผ่านอย่างเดียว ข้อพิจารณาที่ขัดกันเป็นเรื่องจริง เพราะพาสคีย์ย้ายปัญหายากไปที่การกู้คืนและอุปกรณ์หาย และขั้นตอนกู้คืนที่ซุ่มซ่ามจะกลายเป็นเป้าอ่อนใหม่ที่ผู้โจมตีหันไปโจมตีแทน นำตัวเลขความครอบคลุมแยกตามชนิดปัจจัย รายการแอปพลิเคชันที่ยังถอยกลับไปใช้รหัสผ่าน และเส้นทางกู้คืนบัญชีที่ออกแบบแล้วซึ่งคุณไว้ใจได้ต่อการหลอกลวงทางสังคมของคนที่ตั้งใจจริงมาด้วย ในบริบทองค์กรและภาครัฐ ให้ผูกเป้าหมายกับระดับการรับรองที่กำหนดโดยกฎหมาย เพราะระบบระดับสูงที่ยังอนุญาตปัจจัยที่ถูกฟิชชิงได้มีช่องว่างด้านการปฏิบัติตามข้อกำหนดด้วย ไม่ใช่แค่ด้านความมั่นคงปลอดภัย

5. **คุณตัดสินใจอย่างไรว่าแต่ละตัวตนได้สิทธิ์อะไร และคุณเปรียบเทียบความต่าง ทดสอบ และพิสูจน์การตัดสินใจนั้นก่อนส่งขึ้นระบบได้หรือไม่?** ช่องว่างระหว่าง "ใครบางคนคลิกตั้งสิทธิ์ในคอนโซล" กับ "นโยบายที่ผ่านการทบทวนและควบคุมเวอร์ชัน" คือความต่างระหว่างแบบจำลองสิทธิ์ที่คุณตรวจสอบได้กับแบบที่ทำได้แค่ขอโทษ สำหรับทีมขนาดใหญ่ แรงกดดันคือปล่อยให้แต่ละแอปพลิเคชันงอกกฎเฉพาะของตัวเอง ซึ่งสร้างบทบาทระเบิดจำนวนฝั่ง RBAC และเงื่อนไขที่ทดสอบไม่ได้ฝั่ง ABAC อย่างเงียบ ๆ จนไม่มีใครบอกได้ว่าการให้สิทธิ์หนึ่งอนุญาตอะไรจริง ๆ ข้อพิจารณาที่ขัดกันคือความเร็วในการส่งมอบ เพราะการเขียนการกำหนดสิทธิ์เป็นนโยบายในรูปโค้ดเพิ่มขั้นตอนทบทวนที่การคลิกคอนโซลไม่มี และทีมที่ถูกเร่งก็ไม่พอใจแรงเสียดทานนั้นจนกว่าการตรวจสอบที่ล้มเหลวหรือการให้สิทธิ์กว้างเกินไปครั้งแรกจะพิสูจน์เหตุผลให้ นำการเปลี่ยนสิทธิ์จริงหนึ่งรายการมาและไล่ตามว่าจะถูกเสนอ ทดสอบ ทบทวน และย้อนกลับอย่างไร พร้อมจำนวนบทบาทที่คุณมีและกี่บทบาทที่ไม่มีใครอธิบายได้ ในบริบทองค์กรและภาครัฐ ผู้ตรวจสอบจะขอให้คุณแสดงว่าใครเข้าถึงบันทึกหนึ่งได้และภายใต้กฎใดในวันหนึ่ง และมีเพียงนโยบายที่เปรียบเทียบความต่างและทดสอบได้เท่านั้นที่ตอบเรื่องนี้ได้โดยไม่ต้องเร่งรีบ

6. **การทบทวนสิทธิ์ครั้งล่าสุดเพิกถอนอะไรที่เป็นเรื่องจริงเมื่อไร และใครรับผิดชอบเมื่อการสะสมสิทธิ์ไม่ได้รับการตรวจสอบ?** การทบทวนสิทธิ์คือการควบคุมที่สู้กับการสะสมสิทธิ์อย่างช้า ๆ ที่การให้สิทธิ์แต่ละครั้งไม่เคยดูไม่สมเหตุสมผล และการทบทวนที่ไม่เคยเพิกถอนอะไรเลยคือละครแห่งการทบทวนที่ผลิตเอกสารแทนความปลอดภัย ในองค์กรขนาดใหญ่ รูปแบบความล้มเหลวคือการประทับตราอนุมัติ: เจ้าของระบบรับรองซ้ำหลายร้อยรายการในการนั่งครั้งเดียว อนุมัติทั้งหมดเพราะการประเมินแต่ละรายการจริง ๆ น่าเบื่อ และแรงจูงใจให้สิทธิ์ไหลต่อไปแรงกว่าแรงจูงใจให้ตัด ข้อพิจารณาที่ขัดกันคือการทบทวนที่มีความหมายกินเวลาเจ้าของและบางครั้งทำให้ขั้นตอนทำงานของใครบางคนพัง เมื่อสิทธิ์ที่เขาพึ่งพาอย่างเงียบ ๆ หายไป ดังนั้นคุณต้องทำให้การทบทวนมุ่งเป้าและขับเคลื่อนด้วยความเสี่ยง ไม่ใช่รายการเรียงต่อกันไม่แยกแยะ นำอัตราการเพิกถอนจากรอบล่าสุด จำนวนสิทธิ์เฉลี่ยต่อคน และหลักฐานว่าใครเป็นเจ้าของการรับรองซ้ำของแต่ละระบบมาด้วย ในบริบทองค์กรและภาครัฐ ให้ระบุชื่อเจ้าหน้าที่ผู้รับผิดชอบของแต่ละการทบทวนและรอบเวลาที่เขาถูกกำกับ เพราะการสะสมสิทธิ์ที่ไม่มีใครรับผิดชอบจับให้ได้คือเงื่อนไขที่ทั้งผู้ตรวจสอบและผู้โจมตีใช้ประโยชน์

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ซื้อระบบตัวตน อย่าสร้าง ผู้ให้บริการตัวตนแบบโฮสต์เพียงหนึ่งเดียวที่มี SSO บังคับพาสคีย์ และออกงานได้ในคลิกเดียว ให้วิศวกรไม่กี่คนมีสถานะระดับองค์กรด้วยค่าบริการต่อที่นั่ง พึ่งตัวตนเวิร์กโหลดที่ผู้ให้บริการมีมาในตัว เพื่อไม่ให้มีกุญแจคลาวด์อายุยาวแม้แต่ดอกเดียวในไปป์ไลน์ของคุณ และใช้ OIDC กับ OAuth 2.0 แบบสำเร็จรูป แทนการคิดการจัดการโทเค็นเองที่คุณไม่มีปัญญาดูแล

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญด้านตัวตนในทีม ให้เลือก SSO และ MFA ที่แถมมากับเครื่องมือที่คุณจ่ายเงินอยู่แล้ว และเปิดใช้มัน แทนการหาแพลตฟอร์มแยกต่างหาก มองปัญหาผู้เข้า-ผู้ย้าย-ผู้ออกเป็นเช็กลิสต์สั้น ๆ ที่เขียนไว้และผูกกับคนที่ดูแลการจ้างงาน และเลือกพาสคีย์เพราะมันขจัดภาระฝ่ายช่วยเหลือเรื่องรีเซ็ตรหัสผ่านที่คุณไม่มีคนว่างไปจัดการ หลีกเลี่ยงการล็อกอินที่ใช้ร่วมกัน เพราะเป็นนิสัยราคาถูกที่ภายหลังทำให้การระบุผู้รับผิดชอบและการเพิกถอนเป็นไปไม่ได้

**องค์กรขนาดใหญ่.** งานคือการรวมและธรรมาภิบาลข้ามหลายไดเรกทอรีและหลายทีม: ผู้ให้บริการตัวตนที่เชื่อถือได้หนึ่งเดียวที่ขับเคลื่อนโดยระบบทรัพยากรบุคคล ขั้นตอนผู้เข้า-ผู้ย้าย-ผู้ออกแบบอัตโนมัติ RBAC สำหรับหน้าที่งานกับ ABAC สำหรับบริบท และการจัดการสิทธิ์ระดับสูงพร้อมการบันทึกเซสชัน เขียนการกำหนดสิทธิ์เป็นนโยบายในรูปโค้ดเพื่อให้การเปลี่ยนแปลงเปรียบเทียบความต่างและทดสอบได้ ทำการทบทวนสิทธิ์ตามกำหนดที่เพิกถอนจริง และกำหนดมาตรฐานอินเทอร์เฟซเพื่อให้แอปพลิเคชันเชื่อมเข้าตัวตนกลาง แทนที่แต่ละตัวจะงอกหน้าล็อกอินของตัวเอง

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง ความโปร่งใส และความรับผิดชอบต่อสาธารณะขับเคลื่อนการออกแบบ ผูกการพิสูจน์ตัวตนกับข้อมูลรับรองฮาร์ดแวร์ เช่นสมาร์ทการ์ด PIV หรือ CAC กำหนดระดับการรับรองตัวตนตาม NIST SP 800-63 เพื่อให้ระบบที่เสี่ยงสูงกว่าต้องใช้ปัจจัยที่รับรองระดับสูงกว่า และเก็บบันทึกการตรวจสอบที่แก้ไขไม่ได้ซึ่งตอบได้ว่าใครเข้าถึงอะไรเมื่อไรอย่างแน่ชัด เผยแพร่การจัดการตัวตนที่ประชาชนใช้ด้วยภาษาธรรมดา แยกชุดตัวตนของลูกค้ากับของบุคลากร และให้ทุกการกระทำที่มีสิทธิ์สูงบนระบบอ่อนไหวผ่านตัวกลางและถูกบันทึกสำหรับผู้ตรวจสอบที่จะถาม

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปยี่สิบคนไม่มีกำลังจัดทีมตัวตน จึงซื้อ พนักงานทุกคนลงชื่อเข้าใช้ผ่านผู้ให้บริการตัวตนแบบโฮสต์หนึ่งเดียวด้วย SSO เข้าอีเมล ระบบโฮสต์โค้ด คอนโซลคลาวด์ และแอปภายใน และบังคับใช้พาสคีย์ จึงไม่มีรหัสผ่านให้ฟิชชิง การออกงานทำได้ในคลิกเดียว: ปิดบุคคลนั้นในผู้ให้บริการตัวตนก็ตัดสิทธิ์ทุกที่พร้อมกัน สำหรับผลิตภัณฑ์ของตัวเอง พวกเขาใช้ OIDC สำหรับการลงชื่อเข้าใช้ของผู้ใช้ และ OAuth 2.0 เพื่อให้การเชื่อมต่อต่าง ๆ เรียก API ของพวกเขาด้วยโทเค็นที่จำกัดขอบเขต การพิสูจน์ตัวตนจากบริการสู่คลาวด์ใช้ตัวตนเวิร์กโหลดที่ผู้ให้บริการมีมาในตัว จึงไม่มีกุญแจคลาวด์อายุยาวแม้แต่ดอกเดียวในไปป์ไลน์ ทั้งหมดนี้จ่ายค่าบริการต่อที่นั่งเพียงเล็กน้อย และได้สถานะด้านตัวตนที่แข็งแรงกว่าที่องค์กรหลายแห่งมี

**องค์กรขนาดใหญ่.** ธนาคารข้ามชาติสะสมไดเรกทอรีสี่แห่งและแอปพลิเคชันหลายร้อยตัวมาตลอดทศวรรษ บางตัวเชื่อมด้วย SAML บางตัวมีล็อกอินของตัวเอง ธนาคารสนับสนุนเงินให้โครงการรวมระบบ: ผู้ให้บริการตัวตนที่เชื่อถือได้หนึ่งเดียวขับเคลื่อนโดยระบบทรัพยากรบุคคล พร้อมขั้นตอนผู้เข้า-ผู้ย้าย-ผู้ออกแบบอัตโนมัติที่ให้สิทธิ์ตอนจ้างและเพิกถอนภายในไม่กี่นาทีหลังสิ้นสุดการจ้าง RBAC ครอบคลุมหน้าที่งานมาตรฐาน ขณะที่ ABAC บังคับกฎถิ่นที่เก็บข้อมูลและระดับการอนุญาตสำหรับการเข้าถึงข้ามพรมแดน ผู้ดูแลระบบไม่มีสิทธิ์เข้าถึงระบบจริงแบบค้างถาวร พวกเขาขอยกระดับสิทธิ์แบบ JIT ผ่านระบบจัดการสิทธิ์ระดับสูงที่บันทึกทุกเซสชัน การทบทวนสิทธิ์รายไตรมาสบังคับให้เจ้าของระบบรับรองซ้ำหรือเพิกถอน และทุกการตัดสินใจเขียนเป็นนโยบายในรูปโค้ดเพื่อให้ผู้ตรวจสอบเปรียบเทียบความต่างได้ว่าอะไรเปลี่ยนและเมื่อไร

**ภาครัฐ.** หน่วยงานรัฐบาลกลางออกสมาร์ทการ์ดยืนยันตัวตนส่วนบุคคล (PIV) และสมาร์ทการ์ดเทียบเท่าของทหารที่เรียกว่า common access card (CAC) ให้บุคลากร เพื่อให้การพิสูจน์ตัวตนผูกกับข้อมูลรับรองฮาร์ดแวร์ ไม่ใช่รหัสผ่าน โครงการตัวตนของหน่วยงานทำตามแนวทางการจัดการตัวตน ข้อมูลรับรอง และสิทธิ์การเข้าถึงของรัฐบาลกลาง (FICAM) และกำหนดระดับการรับรองตัวตนตามแนวปฏิบัติ NIST SP 800-63 ของสถาบันมาตรฐานและเทคโนโลยีแห่งชาติสหรัฐฯ เพื่อให้ระบบที่เสี่ยงสูงกว่าต้องใช้ข้อมูลรับรองระดับสูงกว่า บริการที่ประชาชนใช้ใช้ชุดตัวตนลูกค้าแยกต่างหากที่ระดับการรับรองต่ำกว่าพร้อม MFA ที่แข็งแรง การทบทวนสิทธิ์และบันทึกการตรวจสอบที่แก้ไขไม่ได้ป้อนตรงเข้าหลักฐานการอนุญาตต่อเนื่องของหน่วยงาน (บทที่ 4.6) และทุกการกระทำที่มีสิทธิ์สูงบนระบบความลับผ่านตัวกลางและถูกบันทึก

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ผลตอบแทน (ROI) ของการลงทุนด้านตัวตนมาจากการย้ายเวกเตอร์การรั่วไหลหลักของคุณออกจากเขตอันตราย ข้อมูลรับรองที่ถูกขโมยและบัญชีที่มีสิทธิ์เกินเป็นสาเหตุของเหตุการณ์จริงเป็นสัดส่วนมาก และแต่ละเหตุการณ์มีหางที่หนัก: การตอบสนองต่อเหตุการณ์ ค่าปรับจากหน่วยงานกำกับดูแล การแจ้งเตือนการรั่วไหล และความเสียหายต่อชื่อเสียงที่ยาวนาน MFA ที่ทนต่อฟิชชิงเพียงอย่างเดียวก็ขจัดเส้นทางบุกรุกที่พบบ่อยที่สุด และการถอนสิทธิ์อัตโนมัติปิดช่องว่างบัญชีกำพร้าที่เปลี่ยนการลาออกตามปกติให้เป็นการเปิดเผยความเสี่ยง นี่คือการลดความเสี่ยงที่ถูกที่สุดอย่างหนึ่งต่อเงินหนึ่งดอลลาร์ที่จ่าย

ต้นทุนรวมตลอดอายุการใช้งาน (TCO) มีอยู่จริงแต่มีขอบเขต รวมค่าไลเซนส์ผู้ให้บริการตัวตน แพลตฟอร์มจัดการสิทธิ์ระดับสูงและความลับ งานวิศวกรรมเชื่อมทุกแอปพลิเคชันเข้ากับตัวตนกลาง และงานทบทวนสิทธิ์ที่ต่อเนื่อง ต้นทุนที่ใหญ่กว่าอยู่ที่ระดับองค์กร: การรวมไดเรกทอรีและการเติม SSO ให้แอปพลิเคชันรุ่นเก่าเป็นงานช้าและไม่หวือหวาที่แย่งกับฟีเจอร์ ให้ชั่งเทียบกับทางเลือกอื่น ตัวตนที่กระจัดกระจายจ่ายเงินก้อนเดียวกันตลอดไปในรูปการออกงานด้วยมือ การเร่งทำตามการตรวจสอบ และการรีเซ็ตรหัสผ่านของฝ่ายช่วยเหลือ บวกต้นทุนในที่สุดของการรั่วไหลที่ความกระจัดกระจายทำให้มีโอกาสเกิด เมื่อนำเสนอเหตุผลต่อผู้บริหาร ให้วางกรอบตัวตนเป็นระนาบควบคุมของซีโรทรัสต์: การรวมและการทำให้เป็นอัตโนมัติเป็นการลงทุนครั้งเดียวที่ลดทั้งความเสี่ยงการรั่วไหลและต้นทุนประจำของการตรวจสอบ การออกงาน และการสนับสนุนด้านสิทธิ์

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **บัญชีกำพร้า** สิทธิ์ที่อยู่เกินกว่าตัวบุคคลหรือวัตถุประสงค์ โดยเฉพาะบัญชีบริการที่ไม่มีใครเฝ้าดูและผู้รับเหมาที่ถูกลืม
- **ผู้ดูแลระบบค้างถาวรทุกที่** สิทธิ์ระดับสูงแบบเปิดตลอดแทนการยกระดับแบบทันเวลา ทำให้บัญชีผู้ดูแลใดที่ถูกยึดมีอำนาจคงทน
- **กุญแจคงที่อายุยาว** ข้อมูลรับรองบริการที่แปะไว้ในไฟล์ตั้งค่าหรือ CI ไม่เคยหมดอายุ และในที่สุดก็รั่ว
- **ไดเรกทอรีกระจัดกระจาย** คนเดียวมีหลายบัญชีที่ไม่มีใครกำกับดูแล ทำให้ไม่มีการเปลี่ยนแปลงใดแพร่ไปถึงครบ
- **บัญชีที่ใช้ร่วมกัน** ข้อมูลรับรองที่หลายคนใช้ ทำลายการระบุผู้รับผิดชอบและทำให้การเพิกถอนเป็นไปไม่ได้
- **SMS เป็นปัจจัยที่แข็งแรงของคุณ** ถือว่ารหัสใช้ครั้งเดียวที่ถูกฟิชชิงและสลับซิมได้เพียงพอเป็น MFA
- **บทบาทระเบิดจำนวน** บทบาท RBAC แคบ ๆ มากเกินไปจนแบบจำลองตรวจสอบไม่ได้และไม่มีใครรู้ว่าบทบาทหนึ่งให้อะไร
- **การถอนสิทธิ์เป็นเช็กลิสต์ทำมือ** ขั้นตอนออกงานโดยมนุษย์ที่ย่อมพลาดบัญชีสำคัญสักบัญชี
- **ใช้ OAuth เพื่อพิสูจน์ตัวตน** ถือว่าโทเค็นเข้าถึงเป็นหลักฐานของตัวตน แทนที่จะใช้ OIDC
- **ละครแห่งการทบทวน** การรับรองซ้ำสิทธิ์ที่ประทับตราอนุมัติโดยไม่มีใครประเมินความจำเป็นจริง ๆ

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** แต่ละแอปพลิเคชันมีล็อกอินของตัวเอง ใช้รหัสผ่านโดยไม่มี MFA ที่สม่ำเสมอ การให้สิทธิ์และการออกงานเป็นแบบทำมือ ตั้งรับ และช้า บัญชีกำพร้าสะสม ข้อมูลรับรองบริการเป็นกุญแจคงที่อายุยาว ไม่มีการทบทวนสิทธิ์ ให้สิทธิ์แล้วไม่เคยกลับมาดู
- **ระดับ 2 พัฒนา:** SSO ครอบคลุมแอปพลิเคชันหลักผ่านผู้ให้บริการตัวตนกลาง แต่ความครอบคลุมไม่สม่ำเสมอข้ามทีม MFA บังคับสำหรับการเข้าถึงของมนุษย์ส่วนใหญ่ มี RBAC พื้นฐาน ผู้เข้า-ผู้ย้าย-ผู้ออกเป็นอัตโนมัติบางส่วนจากระบบทรัพยากรบุคคล บางบัญชีที่มีสิทธิ์สูงถูกเก็บไว้ในตู้นิรภัย การทบทวนสิทธิ์เกิดเป็นครั้งคราวและไม่สม่ำเสมอ
- **ระดับ 3 สร้างมาตรฐาน:** ผู้ให้บริการตัวตนที่รวมแล้วเป็นแหล่งที่เชื่อถือได้สำหรับบุคลากร พร้อมการให้สิทธิ์อัตโนมัติและการถอนสิทธิ์ทันทีที่บังคับทั้งองค์กร MFA ที่ทนต่อฟิชชิงเป็นมาตรฐานและบันทึกไว้ RBAC บวก ABAC เขียนเป็นนโยบายในรูปโค้ด มีการจัดการสิทธิ์ระดับสูงพร้อมบันทึกเซสชัน ตัวตนเวิร์กโหลดแทนกุญแจคงที่ส่วนใหญ่ การทบทวนสิทธิ์ตามกำหนดถูกบังคับและตรวจสอบเทียบกับนโยบายที่เขียนไว้ซึ่งทุกทีมทำตาม
- **ระดับ 4 บริหารจัดการ:** โครงการตัวตนถูกวัดเทียบกับเกณฑ์อ้างอิงและควบคุมด้วยข้อมูล คุณติดตามเวลาถอนสิทธิ์จากการเปลี่ยนสถานะในระบบทรัพยากรบุคคลจนเพิกถอนครบ ความครอบคลุมของ MFA และพาสคีย์ตามกลุ่มประชากร จำนวนบัญชีที่มีสิทธิ์ระดับสูงค้างถาวร จำนวนกุญแจคงที่อายุยาวที่ยังใช้อยู่ จำนวนบัญชีกำพร้า และอัตราการเพิกถอนจากการทบทวนสิทธิ์ ตัวชี้วัดมีเป้าหมาย เช่น เพิกถอนครบภายในหนึ่งชั่วโมงและไม่มีการให้สิทธิ์ผู้ดูแลค้างถาวรใหม่สุทธิ และการละเมิดเกณฑ์กระตุ้นการสอบสวน ไม่ใช่การยักไหล่ การเปลี่ยนแปลงการกำหนดสิทธิ์ถูกทดสอบในไปป์ไลน์ และการตัดสินใจไป/ไม่ไปของการให้สิทธิ์แต่ละครั้งขับเคลื่อนด้วยหลักฐาน ไม่ใช่ความเคยชิน
- **ระดับ 5 ประสานทั้งระบบ:** ตัวตนเป็นระนาบควบคุมของซีโรทรัสต์ที่ปรับปรุงต่อเนื่อง บูรณาการกับการวางแผนด้านความมั่นคงปลอดภัย ความเสี่ยง และผู้เข้า-ผู้ย้าย-ผู้ออกทั่วองค์กร พาสคีย์เป็นค่าเริ่มต้นและรหัสผ่านกำลังถูกเลิกใช้ บรรลุสิทธิ์ค้างถาวรเป็นศูนย์ด้วยการยกระดับแบบทันเวลา และทุกเวิร์กโหลดใช้ข้อมูลรับรองอายุสั้นที่หมุนเวียนอัตโนมัติและ mTLS การกำหนดสิทธิ์เป็นนโยบายในรูปโค้ดเต็มรูปแบบ การทบทวนสิทธิ์เป็นแบบต่อเนื่องและขับเคลื่อนด้วยความเสี่ยง การถอนสิทธิ์เกือบทันที และทุกการตัดสินใจสร้างหลักฐานการตรวจสอบโดยอัตโนมัติ แบบจำลองปรับตามสัญญาณความเสี่ยงที่เปลี่ยนไป กระชับหรือผ่อนสิทธิ์แบบไดนามิก ไม่ใช่ตามรอบเวลาที่ตายตัว

## ประเด็นชวนคุย

1. ต้องทำอะไรเพื่อไปถึงสิทธิ์ผู้ดูแลค้างถาวรเป็นศูนย์ และเส้นทางฉุกเฉิน (break-glass) แบบใดจะทำให้ปลอดภัย
2. ABAC คุ้มกับความซับซ้อนของมันตรงไหนในสภาพแวดล้อมของคุณ เทียบกับการอยู่กับ RBAC ธรรมดา
3. ควรเลิกใช้รหัสผ่านเพื่อไปใช้พาสคีย์อย่างเข้มข้นแค่ไหน และขั้นตอนกู้คืนแบบใดมาแทนที่
4. แอปพลิเคชันใดยังอยู่นอกผู้ให้บริการตัวตนกลางของคุณ และอะไรทำให้มันยังอยู่ตรงนั้น
5. คุณให้พันธมิตรและลูกค้าเข้าถึงแบบจำกัดขอบเขตโดยไม่รับสุขอนามัยด้านความมั่นคงปลอดภัยของเขามาด้วยได้อย่างไร
6. ตัวชี้วัดเดียวใดที่จับความเร็วการถอนสิทธิ์ของคุณได้ดีที่สุด และวันนี้คุณวัดมันอยู่หรือไม่

## ข้อสรุปสำคัญ

- การพิสูจน์ตัวตนพิสูจน์ว่าคุณคือใคร การกำหนดสิทธิ์ตัดสินว่าคุณทำอะไรได้ ออกแบบและทบทวนแยกกัน
- รวมเป็นผู้ให้บริการตัวตนที่เชื่อถือได้หนึ่งเดียวพร้อม SSO ไดเรกทอรีที่กระจัดกระจายคือข้อบกพร่องด้านความมั่นคงปลอดภัย ไม่ใช่ความสะดวก
- ทำวงจรชีวิตผู้เข้า-ผู้ย้าย-ผู้ออกให้เป็นอัตโนมัติ และทำให้การถอนสิทธิ์เร็วและพิสูจน์ได้
- ใช้ OIDC สำหรับการลงชื่อเข้าใช้ของผู้ใช้ OAuth 2.0 สำหรับการเข้าถึง API แบบมอบหมาย และ SAML ในที่ที่แคตตาล็อกองค์กรต้องการ อย่าใช้ OAuth เป็นการพิสูจน์ตัวตน
- ย้ายการพิสูจน์ตัวตนไปสู่พาสคีย์และ WebAuthn ที่ทนต่อฟิชชิง บังคับ MFA ทุกที่ และมองปัจจัยที่อ่อนแอเป็นมาตรการชั่วคราว
- บังคับใช้สิทธิ์น้อยที่สุดด้วยการเข้าถึงแบบทันเวลาและการจัดการสิทธิ์ระดับสูง ตั้งเป้าสิทธิ์ผู้ดูแลค้างถาวรเป็นศูนย์
- ให้ตัวตนที่แท้จริงแก่เครื่องด้วยข้อมูลรับรองเวิร์กโหลดอายุสั้นและ mTLS กำจัดกุญแจคงที่อายุยาว
- ทำให้ตัวตนเป็นระนาบควบคุมของซีโรทรัสต์ (บทที่ 4.1) และปิดวงจรด้วยการทบทวนสิทธิ์อย่างต่อเนื่องและหลักฐานการตรวจสอบ (บทที่ 4.6)
