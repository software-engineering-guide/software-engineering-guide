# 4.2 ความมั่นคงปลอดภัยแอปพลิเคชัน

## ภาพรวมและแรงจูงใจ

ความมั่นคงปลอดภัยแอปพลิเคชันคือจุดที่ภัยคุกคามเชิงนามธรรมมาพบกับโค้ดจริง การละเมิดส่วนใหญ่ที่เป็นข่าวสืบย้อนไปถึงข้อบกพร่องในชั้นแอปพลิเคชัน ไม่ว่าจะเป็นการแทรกคำสั่ง (injection) กระบวนการพิสูจน์ตัวตนที่พัง ความลับ (secret) ที่เปิดเผย หรือไลบรารีที่พึ่งพาซึ่งถูกเจาะ สำหรับทีมใหญ่ที่ส่งมอบบริการจำนวนมาก ส่วนที่ยากไม่ใช่การรู้ว่าข้อบกพร่องเหล่านี้มีอยู่ แต่คือการป้องกันให้ได้อย่างสม่ำเสมอทั่วโค้ดเบสที่กว้างใหญ่ซึ่งคนนับพันเขียนมาหลายปี

สำหรับองค์กรขนาดใหญ่ ความมั่นคงปลอดภัยแอปพลิเคชันเป็นเรื่องของความไว้วางใจของลูกค้าและพันธะตามกฎระเบียบ ข้อบกพร่องในขั้นตอนการเข้าสู่ระบบหรือเส้นทางการชำระเงินอาจนำไปสู่การฉ้อโกง ค่าปรับ และการบังคับเปิดเผยการละเมิด ระบบภาครัฐเผชิญความเสี่ยงทางเทคนิคแบบเดียวกันแต่กับข้อมูลที่เดิมพันสูงกว่า ได้แก่ สิทธิ์รับสวัสดิการ ข้อมูลภาษี ข้อมูลกระบวนการยุติธรรมทางอาญา และโครงสร้างพื้นฐานของประเทศ ในทั้งสองบริบท แอปพลิเคชันคือประตูหน้า และผู้โจมตีสำรวจประตูนั้นอยู่ตลอดเวลาแบบอัตโนมัติ

บทนี้ครอบคลุมแนวปฏิบัติที่ทำให้แอปพลิเคชันทนทาน ได้แก่ การรู้จักและป้องกันช่องโหว่ประเภทที่พบบ่อย การตรวจสอบข้อมูลนำเข้าและการเข้ารหัสข้อมูลส่งออก การทำการพิสูจน์ตัวตนและการอนุญาตสิทธิ์ให้ถูกต้อง การจัดการความลับ และการรักษาความปลอดภัยห่วงโซ่อุปทานซอฟต์แวร์ ซึ่งเป็นตัวกำหนดพื้นผิวการโจมตีจริงของคุณมากขึ้นเรื่อย ๆ

*ดูเพิ่มเติม:* บทที่ 4.1 (พื้นฐานความมั่นคงปลอดภัย การสร้างแบบจำลองภัยคุกคาม และวงจรการพัฒนาที่ปลอดภัย) บทที่ 10.3 (ห่วงโซ่อุปทานโอเพนซอร์สและการอนุญาตใช้สิทธิ์) และบทที่ 10.2 (SBOM ความเสี่ยง และการให้ความเชื่อมั่น)

## หลักการสำคัญ

- **ไม่เชื่อข้อมูลนำเข้า** ถือว่าข้อมูลทุกอย่างที่ข้ามขอบเขตความไว้วางใจเป็นอันตราย จนกว่าจะผ่านการตรวจสอบ
- **ค่าเริ่มต้นที่ปลอดภัย** เส้นทางที่ปลอดภัยควรเป็นเส้นทางที่ง่าย พฤติกรรมที่ไม่ปลอดภัยควรต้องใช้ความพยายามที่ตั้งใจและมองเห็นได้
- **ล้มเหลวแบบปิด (fail closed)** เมื่อการตรวจความปลอดภัยทำไม่สำเร็จ ให้ปฏิเสธการเข้าถึงแทนที่จะอนุญาต
- **การป้องกันเชิงลึกในชั้นแอปพลิเคชัน** รวมการตรวจสอบ การเข้ารหัสข้อมูลส่งออก การทำคำสั่งแบบพารามิเตอร์ และการป้องกันของเฟรมเวิร์กเข้าด้วยกัน อย่าพึ่งอย่างใดอย่างหนึ่งอย่างเดียว
- **สิทธิ์น้อยที่สุดสำหรับตัวตนและโทเคน** จำกัดขอบเขตข้อมูลรับรองให้แคบและให้หมดอายุเร็ว
- **ไลบรารีที่คุณพึ่งพาคือโค้ดของคุณ** คุณรับผิดชอบความมั่นคงปลอดภัยของทุกอย่างที่ส่งมอบ รวมถึงส่วนประกอบของบุคคลที่สามและโอเพนซอร์ส
- **มาตรฐานดีกว่าการคิดเอง** ใช้เฟรมเวิร์กที่ผ่านการพิสูจน์แล้ว เช่น ASVS ของ [OWASP](https://en.wikipedia.org/wiki/OWASP) (Open Worldwide Application Security Project) แทนการคิดมาตรการควบคุมของตัวเอง

## ข้อแนะนำ

### รู้จักและป้องกัน OWASP Top 10 และตรวจสอบด้วย ASVS

OWASP Top 10 คือรายการมาตรฐานของอุตสาหกรรมที่รวบรวมความเสี่ยงสำคัญที่สุดของเว็บแอปพลิเคชัน ได้แก่ การควบคุมการเข้าถึงที่พัง ความล้มเหลวด้านการเข้ารหัสลับ การแทรกคำสั่ง การออกแบบที่ไม่ปลอดภัย การตั้งค่าความมั่นคงปลอดภัยผิดพลาด ส่วนประกอบที่มีช่องโหว่ ความล้มเหลวด้านการพิสูจน์ตัวตน ความล้มเหลวด้านความถูกต้องสมบูรณ์ของข้อมูล ความล้มเหลวด้านการบันทึกล็อก และ server-side request forgery ถือเป็นความรู้ที่วิศวกรทุกคนต้องมี ไม่ใช่แค่เอกสารอ้างอิงด้านการปฏิบัติตามข้อกำหนดที่เก็บเข้าแฟ้ม

หากต้องการมาตรฐานที่เข้มงวดและทดสอบได้ ให้ใช้ **OWASP Application Security Verification Standard (ASVS)** ASVS กำหนดข้อกำหนดด้านความมั่นคงปลอดภัยไว้สามระดับของความเชื่อมั่น ทำให้ได้มาตรการควบคุมที่จับต้องและตรวจสอบได้สำหรับใช้ออกแบบและทดสอบ เลือกระดับที่เหมาะกับความเสี่ยงของแต่ละแอปพลิเคชัน แล้วตรวจสอบเทียบกับระดับนั้น

### ตรวจสอบข้อมูลนำเข้าและเข้ารหัสข้อมูลส่งออก

ข้อบกพร่องประเภทการแทรกคำสั่งยังคงเป็นหนึ่งในประเภทที่สร้างความเสียหายมากที่สุด ก็เพราะเผลอทำให้เกิดขึ้นได้ง่ายมาก ป้องกันด้วยมาตรการหลายชั้น

- **ตรวจสอบข้อมูลนำเข้า** เทียบกับรายการที่อนุญาต (allow-list) อย่างเข้มงวด (ชนิด ความยาว รูปแบบ และช่วงค่าที่คาดหวัง) ปฏิเสธแทนการกรองให้สะอาดทุกครั้งที่ทำได้
- **ใช้คำสั่งแบบพารามิเตอร์** และ[คำสั่งที่เตรียมไว้ล่วงหน้า](https://en.wikipedia.org/wiki/Prepared_statement) (prepared statement) กับการเข้าถึงฐานข้อมูลทั้งหมด อย่าสร้าง SQL ด้วยการต่อสตริงเด็ดขาด ใช้ตัวสร้างคำสั่งและ ORM (object-relational mapper) ที่ปลอดภัยอย่างถูกวิธี
- **เข้ารหัสข้อมูลส่งออก** ตามบริบท HTML แอตทริบิวต์ HTML JavaScript URL และ CSS ต่างต้องการการเข้ารหัสต่างกัน พึ่งการ escape อัตโนมัติของเฟรมเวิร์กและเข้าใจข้อจำกัดของมัน
- **ป้องกัน[ครอสไซต์สคริปติง](https://en.wikipedia.org/wiki/Cross-site_scripting) (XSS)** ด้วยการเข้ารหัสข้อมูลส่งออกบวก Content Security Policy ที่เข้มแข็งเป็นชั้นที่สอง
- **ป้องกันการแทรกคำสั่งระบบและการแทรกแม่แบบ** โดยไม่เรียกเชลล์ด้วยข้อมูลที่ไม่น่าเชื่อถือ และใช้แม่แบบที่ไม่มีตรรกะหรือทำงานในกล่องทราย

### ทำการพิสูจน์ตัวตนและการอนุญาตสิทธิ์ให้ถูกต้อง

การพิสูจน์ตัวตนยืนยันว่าผู้ใช้คือใคร การอนุญาตสิทธิ์ตัดสินว่าเขาทำอะไรได้บ้าง ทั้งสองอย่างพลาดบ่อย จึงต้องทำให้ถูก

- เลือกโปรโตคอลที่ได้รับการยอมรับ คือ **[OAuth 2.0](https://en.wikipedia.org/wiki/OAuth)** สำหรับการมอบอำนาจ และ **[OpenID Connect](https://en.wikipedia.org/wiki/OpenID_Connect) (OIDC)** สำหรับการพิสูจน์ตัวตน อย่าสร้างเองตั้งแต่ศูนย์
- บังคับใช้ **[การยืนยันตัวตนหลายปัจจัย](https://en.wikipedia.org/wiki/Multi-factor_authentication) (MFA)** โดยเฉพาะกับการเข้าถึงระดับสิทธิ์สูงและระดับผู้ดูแลระบบ
- เก็บรหัสผ่านเป็นแฮชที่ใส่ salt เท่านั้น โดยใช้อัลกอริทึมสมัยใหม่ที่ช้าและใช้หน่วยความจำมาก (เช่น [Argon2](https://en.wikipedia.org/wiki/Argon2) หรือ [bcrypt](https://en.wikipedia.org/wiki/Bcrypt)) ห้ามเก็บหรือบันทึกล็อกข้อมูลรับรองแบบข้อความธรรมดา
- จัดการ **เซสชัน** อย่างระมัดระวัง สร้างโทเคนที่แข็งแรงทางการเข้ารหัสลับ ตั้งแฟล็กคุกกี้ secure และ HttpOnly หมุนเวียนเมื่อสิทธิ์เปลี่ยน และให้เซสชันที่ไม่ได้ใช้หมดอายุ
- บังคับ **การอนุญาตสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ทุกคำขอ** โดยตรวจว่าตัวตนที่พิสูจน์แล้วเป็นเจ้าของหรือเข้าถึงทรัพยากรชิ้นนั้นได้จริง การอนุญาตสิทธิ์ระดับอ็อบเจกต์ที่พัง (broken object-level authorisation) คือการเปลี่ยน ID เพื่อเข้าถึงข้อมูลของผู้ใช้คนอื่น เป็นข้อบกพร่องของ API ที่พบบ่อยและร้ายแรงที่สุดอย่างหนึ่ง
- รวมศูนย์ตรรกะการอนุญาตสิทธิ์เท่าที่ทำได้ เพื่อให้นโยบายสม่ำเสมอและตรวจสอบได้

### จัดการความลับและหมุนเวียนกุญแจ

ความลับที่ฝังอยู่ในซอร์สโค้ดเป็นสาเหตุของการละเมิดที่เกิดซ้ำแล้วซ้ำอีก สร้างนิสัยที่มีวินัยเรื่องการจัดการความลับ

- เก็บความลับไว้ในตัวจัดการความลับหรือห้องนิรภัย (vault) โดยเฉพาะ ไม่ใช่ในซอร์ส ไฟล์ตั้งค่า หรือตัวแปรสภาพแวดล้อมที่ถูกคอมมิตเข้าระบบควบคุมเวอร์ชัน
- สแกนคอมมิตและที่เก็บโค้ดเพื่อหาความลับรั่วไหลโดยอัตโนมัติ และขวางการรวมโค้ดที่ทำให้เกิดขึ้น
- หมุนเวียนกุญแจและข้อมูลรับรองสม่ำเสมอ และทันทีเมื่อสงสัยว่าถูกเปิดเผย เลือกข้อมูลรับรองอายุสั้นที่ออกให้อัตโนมัติแทนข้อมูลรับรองคงที่อายุยาว
- ใช้สิทธิ์น้อยที่สุดกับความลับทุกตัว จำกัดขอบเขตให้ตรงกับที่ต้องใช้พอดี
- เข้ารหัสความลับขณะจัดเก็บและระหว่างส่ง และตรวจสอบการเข้าถึง

### รักษาความปลอดภัยห่วงโซ่อุปทานซอฟต์แวร์

แอปพลิเคชันสมัยใหม่ส่วนใหญ่ประกอบจากส่วนประกอบของบุคคลที่สาม ทำให้ห่วงโซ่อุปทานเป็นพื้นผิวการโจมตีหลัก

- จัดทำ **[รายการส่วนประกอบซอฟต์แวร์](https://en.wikipedia.org/wiki/Software_bill_of_materials) (SBOM)** สำหรับทุกแอปพลิเคชัน เพื่อให้รู้ว่าส่งมอบอะไรบ้างอย่างแน่ชัดและตอบสนองได้เร็วเมื่อมีช่องโหว่ใหม่
- สแกนไลบรารีที่พึ่งพาอย่างต่อเนื่อง (Software Composition Analysis หรือ SCA) และแก้ส่วนประกอบที่มีช่องโหว่ที่รู้จักโดยเร็ว
- ตรึงและตรวจสอบเวอร์ชันของไลบรารีที่พึ่งพา ใช้ lockfile และรีจิสทรีที่เชื่อถือได้
- นำ **SLSA** (Supply-chain Levels for Software Artifacts) มาใช้เพื่อยกระดับความถูกต้องสมบูรณ์ของการสร้าง และสร้างการรับรอง **ที่มา (provenance)** ที่อธิบายว่าอาร์ติแฟกต์ถูกสร้างมาอย่างไร
- **ลงนามอาร์ติแฟกต์** และตรวจสอบลายเซ็นก่อนนำไปใช้งาน เพื่อเชื่อมั่นได้ว่าสิ่งที่รันอยู่คือสิ่งที่คุณสร้าง
- รักษาความปลอดภัยของระบบสร้าง (build system) เอง เพราะสายส่งมอบงาน CI ที่ถูกเจาะอาจฉีดโค้ดอันตรายเข้าสู่ผู้ใช้ปลายทางทุกราย

## ข้อดีข้อเสียและการแลกเปลี่ยน

| การตัดสินใจ | ข้อดี | ข้อเสีย |
|---|---|---|
| ซื้อ/ใช้ผู้ให้บริการระบุตัวตน (OIDC) | ผ่านการใช้งานจริงมาแล้ว มี MFA ในตัว โค้ดที่ต้องรักษาความปลอดภัยน้อยลง | พึ่งพาผู้ขาย ต้องใช้แรงบูรณาการ มีค่าใช้จ่าย |
| สร้างระบบพิสูจน์ตัวตนเอง | ควบคุมได้เต็มที่ ไม่พึ่งพาภายนอก | พลาดง่ายมาก ต้องดูแลหนัก |
| ตรวจสอบด้วย allow-list อย่างเข้มงวด | ปิดช่องโหว่ได้ทั้งประเภท | อาจทำให้กรณีขอบที่ถูกต้องใช้ไม่ได้ ต้องทำงานล่วงหน้ามากขึ้น |
| ข้อมูลรับรองอายุสั้น | หน้าต่างการถูกละเมิดแคบ เพิกถอนอัตโนมัติ | ต้องมีโครงสร้างพื้นฐานการออกข้อมูลรับรองที่แข็งแรง |
| อัปเดตไลบรารีที่พึ่งพาอย่างเข้มข้น | ช่องโหว่ที่รู้จักน้อยลง | เปลี่ยนแปลงบ่อย อาจมีการเปลี่ยนที่ทำให้ใช้ไม่ได้ ภาระการทดสอบ |
| SBOM + การลงนาม + provenance | ตอบสนองเหตุการณ์ได้เร็ว ความไว้วางใจที่ตรวจสอบได้ | ต้องลงทุนเครื่องมือและกระบวนการ ต้องเปลี่ยนวัฒนธรรม |

ข้อแลกเปลี่ยนที่เกิดซ้ำคือความเข้มงวดล่วงหน้าเทียบกับความเสี่ยงที่เปิดอยู่ต่อเนื่อง การสร้างระบบพิสูจน์ตัวตนเองหรือข้ามสุขอนามัยของไลบรารีที่พึ่งพารู้สึกเร็วในวันนี้และต้องจ่ายแพงมากในภายหลัง การใช้มาตรฐานที่ผ่านการพิสูจน์แล้วและมาตรการห่วงโซ่อุปทานอัตโนมัติต้องออกแรงตอนนี้ แต่เปลี่ยนความเสี่ยงที่ไร้ขอบเขตและคาดเดาไม่ได้ให้เป็นความเสี่ยงที่บริหารได้และมีขอบเขต สำหรับทีมใหญ่ ตัวคูณจากระบบอัตโนมัติสำคัญที่สุด มาตรการที่ใส่ครั้งเดียวในแม่แบบเส้นทางปูทางจะปกป้องทุกบริการที่ใช้แม่แบบนั้น

## คำถามที่ควรคุยกับทีม

1. **คุณจะฝังมาตรการควบคุม ASVS ข้อใดลงในเฟรมเวิร์กเส้นทางปูทางของคุณ เพื่อให้วิศวกรได้ใช้ฟรี ๆ?** การเคลื่อนไหวที่ให้ผลสูงสุดสำหรับทีมใหญ่คือทำให้เส้นทางปลอดภัยเป็นค่าเริ่มต้น เพื่อให้มาตรการที่เขียนครั้งเดียวในเฟรมเวิร์กกลางปกป้องทุกบริการที่นำไปใช้ ตัดสินใจว่าข้อกำหนด ASVS ข้อใด (คำสั่งแบบพารามิเตอร์ การเข้ารหัสข้อมูลส่งออก แฟล็กเซสชันที่ปลอดภัย การตรวจการอนุญาตสิทธิ์ฝั่งเซิร์ฟเวอร์) ควรอยู่ในแม่แบบแทนที่จะอยู่ในความจำของวิศวกรแต่ละคน สำหรับพอร์ตโฟลิโอระดับองค์กรใหญ่และภาครัฐ ให้ตัดสินด้วยว่าแอปพลิเคชันใดต้องการ ASVS ระดับ 2 เทียบกับระดับ 3 และผูกกับความอ่อนไหวของข้อมูลที่แต่ละระบบแตะ นำรายการบริการของคุณมาทำเครื่องหมายว่าตัวใดรับค่าเริ่มต้นเหล่านี้อยู่แล้วและตัวใดเขียนความมั่นคงปลอดภัยเองด้วยมือ เพราะตัวที่ทำเองคือที่ซ่อนของการแทรกคำสั่งและการควบคุมการเข้าถึงที่พัง ถ้าค่าเริ่มต้นที่ปลอดภัยอยู่แค่ในหน้าวิกิ มันจะถูกข้ามเมื่อถูกเร่งส่งมอบ ดังนั้นใส่ไว้ในโค้ด

2. **คุณจะค้นหาและแก้การอนุญาตสิทธิ์ระดับอ็อบเจกต์ที่พังในทุก API ได้อย่างไร ไม่ใช่เฉพาะตัวใหม่?** การเปลี่ยน ID เพื่อเข้าถึงข้อมูลของผู้ใช้คนอื่นเป็นหนึ่งในข้อบกพร่องของ API ที่พบบ่อยและร้ายแรงที่สุด และซ่อนอยู่ในจุดเชื่อมต่อเก่าที่มีมาก่อนมาตรฐานปัจจุบันของคุณ การอนุญาตสิทธิ์ฝั่งเซิร์ฟเวอร์ทุกคำขอและทุกอ็อบเจกต์คือกฎ แต่ส่วนที่ยากคือการตรวจสอบว่ากฎนี้ใช้ได้ทั่วโค้ดเบสที่กว้างใหญ่อายุหลายปีที่หลายมือเขียน ตัดสินใจว่าจะรวมศูนย์ตรรกะการอนุญาตสิทธิ์ เพิ่มการทดสอบอัตโนมัติที่พยายามเข้าถึงข้ามผู้เช่า (cross-tenant) หรือทดสอบเจาะจงกับ API เสี่ยงสูงสุดก่อน นำรายการจุดเชื่อมต่อที่เปิดเผยตัวระบุอ็อบเจกต์มาจัดอันดับตามความอ่อนไหวของสิ่งที่คืนค่า ถ้าไม่ตรวจกวาดอย่างตั้งใจ คุณจะยังส่งมอบข้อบกพร่องนี้ต่อไปและรู้ก็ต่อเมื่อนักวิจัยหรือผู้โจมตีพบ

3. **แผนรับมือช่องโหว่ของไลบรารีที่พึ่งพาซึ่งแพร่หลายครั้งต่อไปคืออะไร: คุณหาและแพตช์ทุกบริการที่ได้รับผลกระทบได้เร็วแค่ไหน?** เมื่อข้อบกพร่องร้ายแรงโผล่ในไลบรารียอดนิยม บริษัทที่มี SBOM แม่นยำระบุบริการที่ได้รับผลกระทบได้ในไม่กี่ชั่วโมง ขณะที่รายอื่นใช้เวลาหลายสัปดาห์ค้นหา และช่องว่างด้านความเร็วนี้ตัดสินว่าคุณเสียหายแค่ไหน ตัดสินใจตอนนี้ว่าจะจัดทำ SBOM ให้ทุกอาร์ติแฟกต์หรือไม่ การสแกนไลบรารีที่พึ่งพารันในทุกสายส่งมอบงานหรือไม่ และใครเป็นผู้ตัดสินการแพตช์ฉุกเฉิน สำหรับผู้ซื้อที่อยู่ภายใต้กฎระเบียบและภาครัฐ SBOM และ provenance ที่ลงนามเป็นเงื่อนไขของการทำธุรกิจมากขึ้นเรื่อย ๆ ความพร้อมนี้จึงปกป้องรายได้ด้วย นำคำตอบที่ซื่อตรงจากการซ้อมมาดู เลือกไลบรารีที่ใช้กว้างขวางหนึ่งตัวแล้วจับเวลาว่าใช้เวลานานแค่ไหนในการไล่รายชื่อบริการทุกตัวที่ส่งมอบมัน ถ้าคำตอบวัดเป็นวัน ให้ลงทุนกับการจัดทำบัญชีและการลงนามก่อนที่เหตุการณ์ครั้งหน้าจะบังคับให้ทำ

4. **คุณจะย้ายจากความลับแบบคงที่อายุยาวไปสู่ข้อมูลรับรองอายุสั้นที่ออกให้อัตโนมัติได้อย่างไร และระบบใดขวางอยู่ตอนนี้?** ความลับที่ฝังในโค้ดและอายุยาวเป็นสาเหตุของการละเมิดที่เกิดซ้ำ และทางแก้คือข้อมูลรับรองอายุสั้นที่ออกตามต้องการ ซึ่งขึ้นอยู่กับโครงสร้างพื้นฐานการออกข้อมูลรับรองที่ระบบเก่ามักใช้ไม่ได้ สำหรับทีมใหญ่ อันตรายคือการนำไปใช้ไม่สม่ำเสมอ แพลตฟอร์มสมัยใหม่หมุนกุญแจทุกชั่วโมงในขณะที่บริการเก่ายังส่งมอบรหัสผ่านฐานข้อมูลแบบคงที่ในไฟล์ตั้งค่า ตัดสินใจว่าภาระงานใดใช้ตัวจัดการความลับหรือระบบตัวตนของภาระงาน (workload identity) ได้ทันที ตัวใดต้องลงทุนก่อน และใครเป็นเจ้าของคู่มือการหมุนกุญแจทันทีที่สงสัยว่ากุญแจรั่ว นำบัญชีรายการข้อมูลรับรองทุกตัวที่ใช้อยู่มาดู พร้อมอายุการใช้งาน รัศมีความเสียหายหากถูกเปิดเผย และการสแกนคอมมิตจะจับได้ก่อนรวมโค้ดหรือไม่ ในบริบทองค์กรใหญ่และภาครัฐ ผูกเรื่องนี้กับการตรวจสอบ ผู้ตรวจคาดหวังหลักฐานของการหมุนเวียน การเข้าถึงที่จำกัดขอบเขต และการบันทึกล็อกการเข้าถึงของทุกความลับมากขึ้นเรื่อย ๆ และข้อมูลรับรองคงที่ที่หมุนไม่ได้หากไม่หยุดระบบคือข้อค้นพบที่รอการเขียนลงรายงาน

5. **คุณยังรันระบบพิสูจน์ตัวตนที่สร้างเองหรือไม่สม่ำเสมอที่ไหนอยู่ และมีแผนรวมไปสู่โปรโตคอลที่ผ่านการพิสูจน์แล้วอย่างไร?** การสร้างระบบพิสูจน์ตัวตนเองเป็นหนึ่งในวิธีที่ง่ายที่สุดที่จะทำให้เกิดข้อบกพร่องแยบยลที่ถูกโจมตีได้ แต่สภาพแวดล้อมขนาดใหญ่ส่วนใหญ่ยังมีขั้นตอนการเข้าสู่ระบบแบบเก่าอย่างน้อยหนึ่งตัวที่มีมาก่อนการตัดสินใจใช้ OAuth 2.0 และ OIDC เป็นมาตรฐาน แรงกดดันที่ขัดกันนั้นมีอยู่จริง การย้ายขั้นตอนเก่าเสี่ยงทำให้ผู้ใช้และการเชื่อมต่อเดิมพัง ส่วนการปล่อยไว้ทำให้เป้าหมายมูลค่าสูงถูกป้องกันไม่พอ ตัดสินใจว่าจะรวมไปที่ผู้ให้บริการระบุตัวตนรายเดียว บังคับ MFA ให้ทั่วถึง และกำหนดเส้นตายปลดระวางขั้นตอนเฉพาะกิจแต่ละตัว หรือยอมรับข้อยกเว้นที่บันทึกไว้พร้อมมาตรการชดเชย นำแผนที่เส้นทางพิสูจน์ตัวตนทุกเส้นในระบบมาดู ว่าเส้นใดบังคับ MFA เส้นใดเก็บรหัสผ่านด้วยแฮชแบบใช้หน่วยความจำมากสมัยใหม่ และเส้นใดเป็นแบบทำเอง สำหรับพอร์ตโฟลิโอองค์กรใหญ่และภาครัฐ เพิ่มมุมการปฏิบัติตามข้อกำหนด มาตรฐานอย่าง NIST SP 800-63 กำหนดความคาดหวังที่เป็นรูปธรรมสำหรับความเชื่อมั่นด้านตัวตน และขั้นตอนที่ทำเองซึ่งพิสูจน์เรื่องเหล่านี้ไม่ได้จะผ่านการตรวจสอบหรือการทบทวนอำนาจอนุญาตให้ใช้งาน (authority-to-operate) ไม่ได้

6. **คุณตรวจสอบอย่างไรว่ามาตรการเหล่านี้ใช้ได้จริงบนระบบจริง และพิสูจน์ได้ด้วยหลักฐานแทนการกล่าวอ้างหรือไม่?** การเขียนค่าเริ่มต้นที่ปลอดภัยไม่เหมือนกับการรู้ว่าทุกบริการยังทำตาม และมาตรการจะผุพังเงียบ ๆ เมื่อโค้ดเปลี่ยน ข้อยกเว้นสะสม และจุดเชื่อมต่อใหม่ถูกส่งมอบ สำหรับทีมใหญ่ คำถามคือความครอบคลุม บริการใดรันการวิเคราะห์แบบสถิต การสแกนไลบรารีที่พึ่งพา และการทดสอบแบบพลวัตหรือการทดสอบเจาะระบบ และคุณรู้ได้อย่างไรว่าบริการที่ข้ามไปไม่ใช่แอปพลิเคชันเสี่ยงสูงสุดของคุณ ตัดสินใจว่าการตรวจสอบใดบังคับในสายส่งมอบงานเทียบกับทำเป็นระยะ ใครคัดแยกข้อค้นพบ และเก็บหลักฐานอะไรไว้แสดงว่ามาตรการถูกทดสอบและผ่านในวันที่กำหนด นำแผนที่ความครอบคลุมปัจจุบัน เวลาเฉลี่ยในการแก้ไขตามระดับความรุนแรง และรายชื่อแอปพลิเคชันที่ไม่มีการทดสอบล่าสุดมาดู ในบริบทที่อยู่ภายใต้กฎระเบียบและภาครัฐ หลักฐานนี้ไม่ใช่ทางเลือก ผู้ตรวจสอบ เจ้าหน้าที่ผู้มีอำนาจอนุญาต และผู้สืบสวนการละเมิดล้วนขอหลักฐานว่ามาตรการถูกตรวจสอบแล้ว และนโยบายที่ไม่มีบันทึกการทดสอบแทบไม่เคยทำให้พวกเขาพอใจ

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** เมื่อมีวิศวกรสองถึงสามคนและไม่มีผู้เชี่ยวชาญด้านความมั่นคงปลอดภัย แรงส่งของคุณคือการรับความมั่นคงปลอดภัยมาแทนการสร้างเอง ใช้ผู้ให้บริการ OIDC แบบมีผู้ดูแล พึ่งเฟรมเวิร์กที่ ORM ทำคำสั่งแบบพารามิเตอร์เป็นค่าเริ่มต้น และเก็บความลับไว้ในตัวจัดการความลับของแพลตฟอร์มแทนไฟล์ `.env` ที่เพื่อนร่วมทีมอาจคอมมิตโดยไม่ตั้งใจ เปิดการสแกนไลบรารีที่พึ่งพาอัตโนมัติที่เปิด pull request แพตช์ให้ และถือว่าเท่านี้พอก่อน อย่าสร้างระบบพิสูจน์ตัวตนหรือการเข้ารหัสลับเอง เพราะคำสั่งที่ถูกแทรกเพียงหนึ่งครั้งหรือกุญแจที่รั่วเพียงหนึ่งดอกอาจจบบริษัทก่อนที่จะมีลูกค้า

**ธุรกิจขนาดเล็ก.** คุณน่าจะไม่มีผู้เชี่ยวชาญด้านความมั่นคงปลอดภัยแอปพลิเคชันและมีงบจำกัด ดังนั้นซื้อมาตรการที่ฝังอยู่ในเครื่องมือและแพลตฟอร์มที่จ่ายอยู่แล้วแทนการจ้างฝ่ายเฉพาะ เลือกผู้ให้บริการระบุตัวตนแบบโฮสต์ที่มี MFA รวมอยู่ ฐานข้อมูลแบบมีผู้ดูแลที่ชี้นำให้คุณเข้าถึงแบบพารามิเตอร์ และผู้ให้บริการที่เก็บโค้ดที่สแกนคอมมิตหาความลับรั่วไหลให้ตั้งแต่แรก ใช้ความสนใจอันหายากไปกับพื้นฐาน OWASP Top 10 ที่เป็นต้นเหตุของการละเมิดในโลกจริงส่วนใหญ่ และเลือกผู้ขายที่ส่งมอบค่าเริ่มต้นที่ปลอดภัยซึ่งปิดเล่น ๆ ไม่ได้

**องค์กรขนาดใหญ่.** ข้ามหลายทีม ความท้าทายคือความสม่ำเสมอ ฝังมาตรการ ASVS ลงในเฟรมเวิร์กเส้นทางปูทางเพื่อให้ทุกบริการใหม่ได้รับคำสั่งแบบพารามิเตอร์ การเข้ารหัสข้อมูลส่งออก เซสชันที่ปลอดภัย และการอนุญาตสิทธิ์ฝั่งเซิร์ฟเวอร์ไปฟรี ๆ จัดทำ SBOM ที่แม่นยำและการสแกนไลบรารีที่พึ่งพาทั้งระบบ เพื่อให้ช่องโหว่ของไลบรารีที่แพร่หลายครั้งต่อไปเป็นเรื่องของชั่วโมงไม่ใช่สัปดาห์ รวมศูนย์นโยบายการอนุญาตสิทธิ์เพื่อให้การเข้าถึงข้ามผู้เช่าทดสอบได้ ใช้ผู้ให้บริการระบุตัวตนรายเดียวเป็นมาตรฐานพร้อมบังคับ MFA และบริหารความมั่นคงปลอดภัยแอปพลิเคชันเป็นพอร์ตโฟลิโอที่มีธรรมาภิบาล โดยแบ่งระดับ ASVS ตามความเสี่ยงและมีหลักฐานที่ตรวจสอบได้

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง ความโปร่งใส และความรับผิดชอบต่อสาธารณะหล่อหลอมมาตรการที่คุณต้องแสดงให้เห็น ไม่ใช่แค่ลงมือทำ ตรวจสอบบริการที่ประชาชนใช้เทียบกับ OWASP ASVS ในระดับที่เหมาะกับความอ่อนไหวของข้อมูล ลงนามทุกอาร์ติแฟกต์ที่นำไปใช้งานและรับรอง provenance ตาม SLSA เพื่อให้เป็นไปตามข้อบังคับด้านห่วงโซ่อุปทาน และออกข้อมูลรับรองอายุสั้นจากห้องนิรภัยกลางพร้อมบันทึกล็อกการเข้าถึงเต็มรูปแบบ เตรียมแสดงให้ผู้ตรวจสอบและเจ้าหน้าที่ผู้มีอำนาจอนุญาตเห็นห่วงโซ่การครอบครองที่บันทึกไว้จากซอร์สถึงระบบจริง และจัดความเชื่อมั่นด้านตัวตนให้สอดคล้องกับมาตรฐานที่เผยแพร่ เช่น NIST SP 800-63

## ตัวอย่าง

**สตาร์ทอัป.** ทีม SaaS ที่มีวิศวกรสามคนข้ามการสร้างระบบเข้าสู่ระบบเอง และใช้ผู้ให้บริการ OIDC แบบมีผู้ดูแลตั้งแต่วันแรก ได้ MFA และการรีเซ็ตรหัสผ่านที่ปลอดภัยโดยไม่ต้องเขียนโค้ดที่เกี่ยวกับความมั่นคงปลอดภัยซึ่งพลาดไม่ได้ ทีมพึ่ง ORM ของเฟรมเวิร์กให้คำสั่งเป็นแบบพารามิเตอร์ตามค่าเริ่มต้น เก็บความลับไว้ในตัวจัดการความลับของแพลตฟอร์มแทนไฟล์ `.env` ที่เพื่อนร่วมทีมอาจคอมมิตโดยไม่ตั้งใจ และเปิดการสแกนไลบรารีที่พึ่งพาอัตโนมัติที่เปิด pull request เมื่อไลบรารีต้องการแพตช์ ไม่มีอะไรในนี้ทำให้ทีมช้าลง และทำให้กุญแจที่รั่วหนึ่งดอกหรือคำสั่งที่ถูกแทรกหนึ่งครั้งไม่จบบริษัทก่อนที่จะมีลูกค้า

**องค์กรขนาดใหญ่.** แพลตฟอร์มค้าปลีกที่ให้บริการผู้ซื้อหลายสิบล้านคนกำหนดมาตรฐานการพิสูจน์ตัวตนบน OIDC ผ่านผู้ให้บริการระบุตัวตนรายเดียว บังคับ MFA สำหรับพนักงาน และการพิสูจน์ตัวตนเพิ่มขั้น (step-up) สำหรับการเปลี่ยนแปลงบัญชีที่มีมูลค่าสูง การเข้าถึงฐานข้อมูลทั้งหมดผ่าน ORM ที่ตั้งค่าให้คำสั่งเป็นแบบพารามิเตอร์ และ Content Security Policy หนุนหลังการเข้ารหัสข้อมูลส่งออก หลังช่องโหว่ที่เป็นข่าวใหญ่ในไลบรารีบันทึกล็อกยอดนิยม SBOM ของบริษัทช่วยให้ระบุบริการที่ได้รับผลกระทบทั้งหมดได้ภายในไม่กี่ชั่วโมงและแพตช์เสร็จภายในสองวัน ขณะที่คู่แข่งที่ไม่มีบัญชีรายการใช้เวลาหลายสัปดาห์ค้นหา

**ภาครัฐ.** หน่วยงานสวัสดิการของรัฐบาลกลางสร้างบริการที่ประชาชนใช้โดยตรวจสอบเทียบกับ OWASP ASVS ระดับ 2 และระดับ 3 สำหรับส่วนประกอบที่จัดการข้อมูลอ่อนไหวที่สุด ความลับอยู่ในห้องนิรภัยกลางที่ออกข้อมูลรับรองอายุสั้น การสแกนคอมมิตขวางกุญแจที่รั่วทุกดอก ทุกอาร์ติแฟกต์ที่นำไปใช้งานถูกลงนามและรับรอง provenance ตาม SLSA ตอบสนองข้อบังคับระดับรัฐบาลกลางเรื่องห่วงโซ่อุปทานซอฟต์แวร์ที่ตรวจสอบได้ และให้ผู้ตรวจสอบเห็นห่วงโซ่การครอบครองที่ชัดเจนจากซอร์สถึงระบบจริง

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

การใช้จ่ายด้านความมั่นคงปลอดภัยแอปพลิเคชันคือการลดความเสี่ยงของการละเมิดประเภทที่เกิดบ่อยที่สุดและแพงที่สุด ต้นทุนรวมตลอดอายุการใช้งาน (TCO) รวมเครื่องมือ (เครื่องสแกน ตัวจัดการความลับ ผู้ให้บริการระบุตัวตน) เวลาวิศวกรในการแก้ข้อค้นพบ และแรงเสียดทานเล็กน้อยของค่าเริ่มต้นที่ปลอดภัย เทียบกับต้นทุนของการข้าม การละเมิดจากการแทรกคำสั่งและการควบคุมการเข้าถึงที่พังเปิดเผยข้อมูลหลายล้านรายการเป็นประจำ นำมาซึ่งค่าปรับตามกฎระเบียบ การแจ้งเตือนที่บังคับ ความสูญเสียจากการฉ้อโกง สปรินต์แก้ไข และความเสียหายต่อชื่อเสียงที่กดรายได้ลงเป็นปี

ผลตอบแทนการลงทุน (ROI) สูงที่สุดเมื่อมาตรการเป็นอัตโนมัติและนำกลับมาใช้ซ้ำ การบูรณาการตัวตนที่ตั้งค่าดีหนึ่งจุด ชั้นคำสั่งสืบค้นที่เสริมความแข็งแกร่งหนึ่งชั้นในเฟรมเวิร์กกลาง และสายส่งมอบงานหนึ่งสายที่ขวางไลบรารีที่มีช่องโหว่ ปกป้องทั้งระบบด้วยต้นทุนส่วนเพิ่มต่อบริการ โดยเฉพาะมาตรการห่วงโซ่อุปทานเปลี่ยนจากทางเลือกเป็นสิ่งจำเป็น ไลบรารีที่ถูกเจาะอาจทำให้ลูกค้าของคุณทุกรายกลายเป็นเหยื่อ และหน่วยงานกำกับดูแลกับผู้ซื้อระดับองค์กรเรียกร้อง SBOM และ provenance ที่ลงนามเป็นเงื่อนไขของการทำธุรกิจมากขึ้นเรื่อย ๆ เมื่อนำเสนอเหตุผลต่อผู้บริหาร ผูกการลงทุนกับความเสี่ยงเฉพาะที่ระบุชื่อได้ และกับข้อกำหนดด้านการจัดซื้อและการปฏิบัติตามข้อกำหนดที่ขวางรายได้หากคุณทำไม่ได้

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **คิดค้นการเข้ารหัสลับหรือระบบพิสูจน์ตัวตนเอง** เกือบทุกครั้งก่อให้เกิดข้อบกพร่องแยบยลที่ถูกโจมตีได้
- **ตรวจสอบเฉพาะฝั่งไคลเอนต์** ถูกหลบเลี่ยงได้ง่ายดาย เซิร์ฟเวอร์ต้องตรวจสอบทุกอย่างซ้ำ
- **การกรองด้วยรายการต้องห้าม (blocklist)** พยายามลบอักขระ "เลว" แทนที่จะอนุญาตเฉพาะอักขระดี ผู้โจมตีหาช่องว่างเจอเสมอ
- **ความลับในซอร์สหรือไฟล์สภาพแวดล้อม** สาเหตุเดียวที่พบบ่อยที่สุดของการรั่วไหลของข้อมูลรับรอง
- **มองข้ามการอนุญาตสิทธิ์เมื่อเข้าถึงอ็อบเจกต์** สมมติว่าผู้ใช้ที่พิสูจน์ตัวตนแล้วเข้าถึงอ็อบเจกต์ใดก็ได้ที่เดา ID ได้
- **ตั้งแล้วลืมไลบรารีที่พึ่งพา** ไม่เคยอัปเดตส่วนประกอบของบุคคลที่สามจนกว่าการละเมิดจะบังคับให้ทำ
- **มอง Top 10 เป็นเส้นชัย** มันคือพื้น ไม่ใช่มาตรฐานที่ครอบคลุม ใช้ ASVS เมื่อต้องการความลึก
- **บันทึกล็อกข้อมูลอ่อนไหว** รหัสผ่าน โทเคน และ PII (ข้อมูลที่ระบุตัวบุคคลได้) ในล็อกกลายเป็นการละเมิดที่รอวันเกิด

## แบบจำลองความเป็นผู้ใหญ่

**ระดับ 1 เริ่มต้น.** ความมั่นคงปลอดภัยแอปพลิเคชันขึ้นอยู่กับความรู้ของนักพัฒนาแต่ละคนและตอบสนองหลังเกิดเหตุเท่านั้น ไม่มีมาตรการมาตรฐาน ความลับอยู่ในซอร์ส ไลบรารีที่พึ่งพาแทบไม่ถูกอัปเดต การพิสูจน์ตัวตนเป็นแบบทำเองและเฉพาะกิจ และข้อบกพร่องการแทรกคำสั่งหรือการควบคุมการเข้าถึงที่พังถูกพบโดยบังเอิญ ไม่ใช่โดยกระบวนการ

**ระดับ 2 พัฒนา.** เริ่มมีแนวปฏิบัติพื้นฐานแต่ต่างกันไปตามทีม ความตระหนักรู้เรื่อง OWASP Top 10 ขยายตัว มีการป้องกันระดับเฟรมเวิร์กบางส่วน และมีตัวจัดการความลับแต่ใช้ไม่สม่ำเสมอ การสแกนไลบรารีที่พึ่งพารันเป็นครั้งคราว ระบบใหม่ใช้ผู้ให้บริการระบุตัวตนมาตรฐาน ขณะที่บริการเก่ายังคงขั้นตอนเข้าสู่ระบบที่ทำเองไว้ไม่แตะต้อง

**ระดับ 3 สร้างมาตรฐาน.** มาตรการควบคุมมีเอกสารและบังคับใช้ทั้งองค์กร ข้อกำหนดที่อิง ASVS ถูกกำหนดตามระดับความเสี่ยง คำสั่งแบบพารามิเตอร์และการเข้ารหัสข้อมูลส่งออกเป็นเรื่องปกติ และต้องใช้ผู้ให้บริการระบุตัวตนกลางที่มี MFA ความลับถูกจัดการและสแกนอัตโนมัติ มีการจัดทำ SBOM และการสแกนไลบรารีที่พึ่งพารันในทุกสายส่งมอบงาน

**ระดับ 4 บริหารจัดการ.** แนวปฏิบัติถูกวัดและควบคุมเทียบกับเส้นฐาน ความครอบคลุมของการสแกนและการทดสอบ เวลาเฉลี่ยในการแก้ไขตามระดับความรุนแรง สัดส่วนบริการที่รับค่าเริ่มต้นของเส้นทางปูทาง อายุการหมุนเวียนของข้อมูลรับรองและความลับ และความสอดคล้องกับ ASVS ถูกติดตามบนแดชบอร์ดทั้งหมด ข้อยกเว้นถูกบันทึกพร้อมวันหมดอายุ การเบี่ยงจากเส้นฐานกระตุ้นให้เกิดการลงมือ และการปล่อยถูกควบคุมด้วยเกณฑ์ความมั่นคงปลอดภัยที่กำหนดไว้ ไม่ใช่การตัดสินตามความรู้สึก

**ระดับ 5 ประสานทั้งระบบ.** ความมั่นคงปลอดภัยถูกปรับปรุงต่อเนื่องและบูรณาการทั่วองค์กร ค่าเริ่มต้นที่ปลอดภัยถูกฝังในเฟรมเวิร์กเส้นทางปูทางเพื่อให้เส้นทางปลอดภัยเป็นไปโดยอัตโนมัติ ใช้ข้อมูลรับรองอายุสั้นทุกที่ และความเชื่อมั่นห่วงโซ่อุปทานเต็มรูปแบบด้วยการลงนามและ provenance (SLSA) เป็นมาตรฐาน การตรวจสอบเกิดอย่างต่อเนื่อง การตอบสนองต่อช่องโหว่ใหม่รวดเร็วและวัดผลได้ และทุกเหตุการณ์ป้อนกลับเข้าแม่แบบร่วม เพื่อให้การแก้ไขครั้งเดียวเสริมความแข็งแกร่งให้ทั้งระบบ

## ประเด็นชวนคุย

1. ตรรกะการอนุญาตสิทธิ์ควรอยู่ที่ไหนจึงจะทั้งสม่ำเสมอและดูแลได้ข้ามบริการจำนวนมาก
2. ควรอัปเดตไลบรารีที่พึ่งพาแข็งขันแค่ไหน เมื่อต้องแลกเปลี่ยนระหว่างความเสี่ยงที่เปิดอยู่กับการเปลี่ยนแปลงบ่อย
3. ระดับ ASVS ใดเหมาะกับแอปพลิเคชันแต่ละประเภทในพอร์ตโฟลิโอของคุณ
4. คุณจะกำจัดความลับอายุยาวโดยไม่สร้างโครงสร้างพื้นฐานการออกข้อมูลรับรองที่เปราะบางได้อย่างไร
5. องค์กรของคุณต้องทำอะไรบ้างจึงจะผลิตและใช้ SBOM และ provenance สำหรับทุกอาร์ติแฟกต์ได้
6. คุณจะป้องกันไม่ให้ค่าเริ่มต้นที่ปลอดภัยถูกปิดเมื่อถูกเร่งส่งมอบได้อย่างไร

## ข้อสรุปสำคัญ

- OWASP Top 10 คือความรู้จำเป็น ส่วน ASVS ให้มาตรฐานที่ทดสอบได้
- ซ้อนชั้นการตรวจสอบข้อมูลนำเข้า คำสั่งแบบพารามิเตอร์ และการเข้ารหัสข้อมูลส่งออกเพื่อเอาชนะการแทรกคำสั่งและ XSS
- ใช้โปรโตคอลที่ผ่านการพิสูจน์แล้ว (OAuth 2.0, OIDC) และบังคับ MFA อย่าสร้างระบบพิสูจน์ตัวตนจากศูนย์
- บังคับการอนุญาตสิทธิ์ฝั่งเซิร์ฟเวอร์ทุกคำขอและทุกอ็อบเจกต์
- เก็บความลับให้พ้นซอร์ส จัดการแบบรวมศูนย์ และหมุนไปสู่ข้อมูลรับรองอายุสั้น
- ห่วงโซ่อุปทานคือพื้นผิวการโจมตีหลัก ใช้ SBOM, SCA, การลงนาม และ provenance (SLSA)
- มาตรการอัตโนมัติที่นำกลับมาใช้ซ้ำได้ปกป้องทั้งระบบด้วยต้นทุนส่วนเพิ่มต่อบริการ
