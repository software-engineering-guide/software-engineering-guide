# 2.7 เอกสารประกอบ

## ภาพรวมและแรงจูงใจ

[เอกสารประกอบ](https://en.wikipedia.org/wiki/Software_documentation) (documentation) คือความรู้ที่เขียนไว้ ซึ่งช่วยให้คนใช้ ดูแลระบบ และเปลี่ยนแปลงซอฟต์แวร์ได้ โดยไม่ต้องปะติดปะต่อความเข้าใจจากโค้ดเพียงอย่างเดียว มีหลายประเภท เช่น วิธีเริ่มต้นใช้งาน วิธีทำงานหนึ่งอย่างให้สำเร็จ ระบบมีโครงสร้างอย่างไร วิธีรับมือเหตุการณ์ฉุกเฉิน และ [API](https://en.wikipedia.org/wiki/API) รับและคืนค่าอะไร แต่ละประเภทรับใช้ผู้อ่านที่ต่างกันซึ่งมีความต้องการต่างกัน เอกสารประกอบที่ดีไม่ใช่ของเสริม มันคือความต่างระหว่างความรู้ที่ขยายไปทั่วองค์กรขนาดใหญ่ได้ กับความรู้ที่อยู่แค่ในหัวของคนไม่กี่คน

สำหรับทีมขนาดใหญ่ เอกสารประกอบคือแนวป้องกันที่ดีที่สุดต่อความเสี่ยงเรื่องคนสำคัญ (key-person risk คืออันตรายเมื่อความรู้ที่สำคัญอยู่กับคนเพียงคนเดียวหรือไม่กี่คน) และเป็นวิธีที่เร็วที่สุดในการปฐมนิเทศคนใหม่ เมื่อวิศวกรหลายร้อยคนพึ่งพาระบบที่ตนไม่ได้สร้าง และคนเข้า ย้าย และออกอยู่ตลอดเวลา องค์กรจะทำงานได้ก็ต่อเมื่อความรู้ถูกเขียนไว้และหาเจอง่าย ระบบที่ไม่มีเอกสารจะเปราะบาง มีแต่ผู้สร้างเท่านั้นที่เปลี่ยนแปลงได้อย่างปลอดภัย และเมื่อผู้สร้างจากไป องค์กรก็สูญเสียความสามารถในการดูแลซอฟต์แวร์ของตัวเอง นี่เป็นหนึ่งในความล้มเหลวที่พบบ่อยและแพงที่สุดในระดับใหญ่

บริบทองค์กรขนาดใหญ่และภาครัฐยกระดับความเสี่ยงขึ้นอีก ระบบอยู่นาน ดังนั้นเอกสารของคุณต้องรับใช้ผู้ดูแลในอีกหลายปี หรือหลายสิบปีหลังจากทีมเดิมจากไปแล้ว ระบอบการกำกับดูแลและการตรวจสอบมักบังคับให้มีเอกสารบางอย่างเป็นหลักฐานของการควบคุม เช่น บันทึกสถาปัตยกรรม [รันบุ๊ก](https://en.wikipedia.org/wiki/Runbook) (runbook คือขั้นตอนปฏิบัติการและรับมือเหตุการณ์ทีละขั้น) และบันทึกการตัดสินใจ ระบบภาครัฐที่ส่งต่อระหว่างผู้ขายพึ่งเอกสารทั้งหมดในการส่งต่อความรู้ข้ามขอบเขตสัญญา และเอกสารก็ขึ้นชื่อว่าเสื่อมสภาพง่าย ความท้าทายที่แท้จริงจึงคือการรักษาให้ถูกต้องเมื่อซอฟต์แวร์เปลี่ยนไป

## หลักการสำคัญ

- เขียนให้ผู้อ่านเฉพาะกลุ่มที่มีความต้องการเฉพาะ เอกสารแต่ละประเภทรับใช้จุดประสงค์ต่างกัน
- เก็บเอกสารไว้ใกล้โค้ดและปฏิบัติต่อมันเหมือนโค้ด (docs-as-code)
- ความถูกต้องสำคัญกว่าความครบถ้วน เอกสารที่เชื่อถือได้จำนวนน้อยดีกว่าเอกสารจำนวนมากที่ผิด
- สร้างอัตโนมัติสิ่งที่สร้างได้ อย่าดูแลด้วยมือสิ่งที่เครื่องมือผลิตได้จากแหล่งความจริง
- สู้กับการเสื่อมของเอกสารอย่างจริงจัง เอกสารที่ล้าสมัยแย่กว่าไม่มีเลย เพราะมันทำให้เข้าใจผิด
- ทำให้เอกสารค้นพบได้ ความรู้ที่หาไม่เจอเท่ากับไม่มี
- บันทึกการตัดสินใจและเหตุผล ไม่ใช่แค่สถานะปัจจุบัน

## ข้อแนะนำ

### นำ docs-as-code มาใช้

เก็บเอกสารไว้ใน[ระบบควบคุมเวอร์ชัน](https://en.wikipedia.org/wiki/Version_control)ร่วมกับโค้ดที่มันอธิบาย เขียนด้วยมาร์กอัปแบบข้อความธรรมดา และทบทวนผ่านกระบวนการ pull request เดียวกัน วิธีนี้ทำให้มีเวอร์ชัน ทบทวนได้ และอยู่ใกล้โค้ด คุณจึงอัปเดตทั้งสองอย่างพร้อมกันได้ เผยแพร่ผ่านสายงานอัตโนมัติเพื่อให้เวอร์ชันล่าสุดพร้อมใช้เสมอ การปฏิบัติต่อเอกสารเหมือนโค้ดนำวินัยเดียวกันที่ทำให้โค้ดน่าเชื่อถือมาใช้ คือการทบทวน ประวัติ และระบบอัตโนมัติ

### จัดโครงสร้างเนื้อหาด้วยกรอบ Diátaxis

จัดเอกสารเป็นสี่ประเภทที่แยกจากกัน เพราะการผสมกันไม่ดีกับผู้อ่านคนไหนเลย ได้แก่ บทเรียน (tutorial มุ่งการเรียนรู้ สำหรับมือใหม่) คู่มือวิธีทำ (how-to guide มุ่งงาน สำหรับเป้าหมายเฉพาะ) เอกสารอ้างอิง (reference มุ่งข้อมูล แม่นยำและครบถ้วน) และคำอธิบาย (explanation มุ่งความเข้าใจ คือเหตุผลและบริบท) แยกสี่ประเภทนี้ออกจากกัน แล้วทุกอย่างจะเขียน เปิดหา และดูแลง่ายขึ้น เพราะแต่ละหน้ามีหน้าที่เดียวและผู้อ่านกลุ่มเดียวอย่างชัดเจน

### ดูแลเอกสารปฏิบัติการที่จำเป็น

ให้ทุกที่เก็บโค้ดมี [README](https://en.wikipedia.org/wiki/README) ที่ชัดเจนเป็นประตูหน้า บอกว่ามันคืออะไร build และรันอย่างไร และไปต่อที่ไหน เขียนรันบุ๊กสำหรับงานปฏิบัติการและการรับมือเหตุการณ์ เพื่อให้ใครก็ตามที่อยู่เวรลงมือได้ ไม่ใช่แค่ผู้เชี่ยวชาญ เก็บเอกสารสถาปัตยกรรมที่อธิบายโครงสร้างและส่วนประกอบสำคัญของระบบ และจัดเอกสารปฐมนิเทศที่ช่วยให้วิศวกรใหม่ทำงานได้เร็ว เอกสารเหล่านี้คือสิ่งที่คุณจะคิดถึงที่สุดเมื่อไม่มี

### สร้าง API docs และ changelog จากแหล่งความจริง

สร้างเอกสารอ้างอิง API จากสัญญาที่เครื่องอ่านได้หรือคำอธิบายประกอบในโค้ด เพื่อให้มันเบี่ยงจากอินเทอร์เฟซจริงไม่ได้ เก็บ[บันทึกการเปลี่ยนแปลง](https://en.wikipedia.org/wiki/Changelog) (changelog) โดยควรสร้างจากคอมมิตที่มีโครงสร้างหรือบันทึกรุ่นที่ปล่อย เพื่อให้ผู้ใช้เห็นว่าระหว่างเวอร์ชันมีอะไรเปลี่ยน การทำสิ่งเหล่านี้ให้เป็นอัตโนมัติเอาเอกสารที่เสื่อมง่ายที่สุดซึ่งต้องดูแลด้วยมือออกไปจากภาระของคุณ และรักษาให้เชื่อถือได้

### บันทึกการตัดสินใจด้านสถาปัตยกรรม

จดการตัดสินใจด้านสถาปัตยกรรมและการออกแบบที่สำคัญเป็นบันทึกแบบเบาที่ลงวันที่ ซึ่งระบุบริบท การตัดสินใจ และผลที่ตามมา บันทึกการตัดสินใจ (decision record) เหล่านี้เก็บเหตุผลที่มิฉะนั้นจะสูญหาย เพื่อให้ผู้ดูแลในอนาคตเห็นว่าทำไมระบบจึงเป็นแบบนี้ แทนที่จะตั้งข้อสงสัยหรือทำความผิดพลาดเก่าซ้ำ มันให้ผลตอบแทนเป็นพิเศษตลอดอายุการใช้งานที่ยาวนานของระบบองค์กรขนาดใหญ่และภาครัฐ

### สู้กับการเสื่อมของเอกสารอย่างตั้งใจ

ถือว่าเอกสารที่ล้าสมัยเป็นข้อบกพร่อง อัปเดตเอกสารในการเปลี่ยนแปลงเดียวกับที่เปลี่ยนพฤติกรรม และทำให้เป็นสิ่งที่คาดหวังในการทบทวน มอบความเป็นเจ้าของให้ทุกเอกสารสำคัญมีคนรับผิดชอบ ทบทวนเอกสารที่มีคุณค่าสูงเรื่องความถูกต้องเป็นครั้งคราว ตัดสิ่งที่ล้าสมัยออก และลบหรือติดป้ายให้ชัดกับสิ่งที่คุณไม่เชื่อถืออีกต่อไป เอกสารที่เสื่อมน้อยที่สุดคือเอกสารที่มีชีวิต ซึ่งสร้างหรือทดสอบเทียบกับตัวระบบเอง

### ลงทุนกับการจัดการความรู้และการค้นพบได้

ทำให้เอกสารค้นหาเจอด้วยระบบค้นหาที่ดี การนำทางที่ชัดเจน และที่อยู่ที่รู้กัน เพื่อให้คนหาสิ่งที่ต้องการได้โดยไม่ต้องถามใคร อย่าปล่อยให้มันกระจายไปตามวิกิและเครื่องมือที่ไม่เชื่อมกันมากเกินไป และเก็บ[ความรู้โดยปริยาย](https://en.wikipedia.org/wiki/Tacit_knowledge) (tacit knowledge) คือความเข้าใจที่ไม่เป็นทางการซึ่งอยู่ในกระทู้แชตและในหัวคน มาเป็นรูปแบบที่คงทนและค้นเจอ ก่อนที่มันจะหลุดมือไป

## ข้อดีข้อเสียและการแลกเปลี่ยน

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| Docs-as-code | มีเวอร์ชัน ทบทวนได้ อยู่ใกล้โค้ด เสื่อมน้อย | ต้องใช้วินัยของวิศวกร ไม่เป็นมิตรกับผู้เขียนที่ไม่ใช่สายเทคนิค |
| วิกิ / ฐานความรู้ | แก้ไขง่าย ทุกคนเข้าถึงได้ | เบี่ยงจากโค้ด กระจัดกระจาย เสื่อมโดยไม่มีใครรู้ |
| เอกสารที่สร้างอัตโนมัติ (API, changelog) | ถูกต้องเสมอ ดูแลน้อย | จำกัดตามที่แหล่งความจริงแสดงออกได้ ต้องมีเครื่องมือ |
| คำอธิบายที่เขียนด้วยมือ | มีบริบทและเหตุผลที่สมบูรณ์ซึ่งเครื่องผลิตไม่ได้ | ใช้แรงงานมาก มีแนวโน้มล้าสมัย |
| โครงสร้าง Diátaxis | แต่ละหน้ามีจุดประสงค์ชัด เปิดหาและดูแลง่ายกว่า | ต้องใช้ความพยายามจัดโครงสร้างล่วงหน้า ผู้เขียนต้องมีวินัย |

ข้อแลกเปลี่ยนหลักคือความพยายามเทียบกับความถูกต้องและความคงทน เอกสารที่เขียนถูกที่สุด คือหน้าวิกิรวดเร็ว ก็เป็นเอกสารที่เสื่อมและกระจัดกระจายง่ายที่สุดด้วย เอกสารที่คงทนที่สุด ซึ่งสร้างจากแหล่งความจริงหรือทบทวนเหมือนโค้ด ต้องใช้วินัยล่วงหน้ามากกว่าแต่ยังเชื่อถือได้ กฎง่าย ๆ ที่ดี คือสร้างอัตโนมัติสิ่งที่ทำได้ เก็บส่วนที่เหลือไว้ใกล้โค้ดและทบทวนเหมือนโค้ด และเก็บคำอธิบายที่เขียนด้วยมือซึ่งใช้แรงมากไว้สำหรับเหตุผลที่มีแต่มนุษย์ให้ได้

## คำถามที่ควรคุยกับทีม

1. **เอกสารของคุณแยกตามความต้องการของผู้อ่านหรือไม่ หรือบทเรียน เอกสารอ้างอิง และคำอธิบายปะปนกันอยู่ในหน้าเดียว?** บทนี้แนะนำการแบ่งแบบ Diátaxis เป็นบทเรียน คู่มือวิธีทำ เอกสารอ้างอิง และคำอธิบาย และระบุว่าการผสมประเภทเป็นรูปแบบที่ไม่ควรทำเพราะไม่ดีกับผู้อ่านคนไหนเลย ในระดับใหญ่ มือใหม่ที่เรียนรู้ระบบกับวิศวกรเวรที่หาข้อเท็จจริงเฉพาะต้องการหน้าคนละแบบ และหน้าที่ผสมกันทำให้ทั้งสองช้าลง ให้นำสัญญาณมาดู เลือกเอกสารที่มีคนเข้าชมมากที่สุดแล้วตรวจว่าแต่ละหน้ามีหน้าที่เดียวและผู้อ่านกลุ่มเดียวชัดเจนหรือไม่ จัดโครงสร้างใหม่ให้กับหน้าที่แย่ที่สุดให้เป็นประเภทที่แยกกัน เพื่อให้ทุกหน้าเขียน เปิดหา และรักษาให้ทันสมัยได้ง่ายขึ้น โครงสร้างนั้นคือสิ่งที่ทำให้เอกสารดูแลได้เมื่อองค์กรโต

2. **คุณบันทึกการตัดสินใจด้านสถาปัตยกรรมที่สำคัญพร้อมเหตุผลหรือไม่ หรือบันทึกแค่สถานะปัจจุบัน?** บทนี้แนะนำบันทึกการตัดสินใจแบบเบาที่ลงวันที่ ซึ่งระบุบริบท การตัดสินใจ และผลที่ตามมา และระบุว่ามันให้ผลตอบแทนมากที่สุดตลอดอายุการใช้งานที่ยาวนานของระบบองค์กรขนาดใหญ่และภาครัฐ ถ้าไม่มี ผู้ดูแลในอีกหลายปีข้างหน้าจะมองไม่เห็นว่าทำไมระบบจึงเป็นแบบนี้ จึงสงสัยการเลือกที่ถูกต้อง หรือทำความผิดพลาดเก่าซ้ำ ให้นำการตัดสินใจยาก ๆ เมื่อเร็ว ๆ นี้ที่เหตุผลตอนนี้อยู่แค่ในกระทู้แชตหรือความทรงจำของใครบางคนมาเป็นสัญญาณที่จับต้องได้ นำรูปแบบบันทึกการตัดสินใจสั้น ๆ มาใช้ และทำให้การเขียนบันทึกเป็นส่วนหนึ่งของทุกการเปลี่ยนแปลงการออกแบบที่สำคัญ เหตุผลคือความรู้ที่มีแต่มนุษย์ให้ได้ และเสื่อมเร็วที่สุดเมื่อไม่ได้เขียนไว้

3. **วิศวกรเวรคนไหนก็ตามรับมือเหตุการณ์ฉุกเฉินจากรันบุ๊กของคุณเพียงอย่างเดียวได้หรือไม่ โดยไม่ต้องเรียกคนที่สร้างระบบ?** บทนี้ระบุว่ารันบุ๊กเป็นเอกสารปฏิบัติการที่จำเป็น เพื่อให้ใครก็ตามที่อยู่เวรลงมือได้ ไม่ใช่แค่ผู้เชี่ยวชาญ และอธิบายทีมภาครัฐที่รับช่วงระบบมาได้ก็เพราะรันบุ๊กส่งต่อความรู้ข้ามขอบเขตสัญญา ความเสี่ยงเรื่องคนสำคัญคือความล้มเหลวที่สิ่งนี้ป้องกัน เมื่อผู้เชี่ยวชาญคนเดียวติดต่อไม่ได้หรือจากไป ขั้นตอนการกู้คืนที่ไม่มีเอกสารเปลี่ยนเหตุการณ์ปกติให้เป็นระบบล่ม ให้นำหลักฐานมาดู หยิบเหตุการณ์ล่าสุดมาตรวจว่ารันบุ๊กอย่างเดียวจะแก้ได้หรือไม่ เขียนและทดสอบรันบุ๊กสำหรับขั้นตอนที่คนกลัว และถือว่ารันบุ๊กที่ยืนด้วยตัวเองไม่ได้เป็นข้อบกพร่อง นั่นคือความต่างระหว่างการกู้คืนตอนตีสองกับการส่งต่อเรื่องขึ้นไปตอนตีสอง

4. **API reference และ changelog ของคุณฉบับไหนสร้างจากแหล่งความจริง และฉบับไหนยังดูแลด้วยมือและค่อย ๆ เบี่ยงไปอย่างเงียบ ๆ?** บทนี้บอกให้สร้างเอกสารอ้างอิงจากสัญญาที่เครื่องอ่านได้หรือคำอธิบายประกอบในโค้ด เพื่อไม่ให้ต่างจากอินเทอร์เฟซจริง และระบุว่าการดูแลด้วยมือกับเนื้อหาที่สร้างอัตโนมัติได้เป็นรูปแบบที่ไม่ควรทำ สำหรับทีมขนาดใหญ่ เอกสาร API ที่เขียนด้วยมือและตามหลังอินเทอร์เฟซจริงแย่กว่าไม่มี ผู้ใช้ทุกคนที่เชื่อมันเขียนการเชื่อมต่อที่พัง และความล้มเหลวไปโผล่ไกลจากหน้าล้าสมัยที่เป็นต้นเหตุ ให้นำสัญญาณที่จับต้องได้มาดู สุ่มอินเทอร์เฟซที่ใช้มากที่สุดสองสามตัว แล้วเทียบเอกสารอ้างอิงที่เผยแพร่กับสัญญาจริงว่าเบี่ยงไปไกลแค่ไหน ที่พบการเบี่ยง ให้ผูกเอกสารอ้างอิงกับการ build เพื่อให้สร้างใหม่ทุกครั้งที่เปลี่ยน และเลิกใช้สำเนาที่ดูแลด้วยมือ ในองค์กรขนาดใหญ่และภาครัฐ ที่อินเทอร์เฟซถูกใช้ข้ามทีม ผู้ขาย และขอบเขตสัญญาที่คุณมองไม่เห็น เอกสารอ้างอิงที่สร้างอัตโนมัติและเป็นที่ยอมรับมักเป็นสิ่งเดียวที่กันไม่ให้ผู้เชื่อมต่อสร้างตามเรื่องแต่ง

5. **ใครเป็นเจ้าของเอกสารที่มีคุณค่าสูงแต่ละฉบับ และวันนี้คุณจะรู้ได้อย่างไรว่าฉบับหนึ่งล้าสมัยไปแล้ว?** บทนี้ถือว่าเอกสารที่ล้าสมัยเป็นข้อบกพร่อง และเตือนว่าเอกสารที่ไม่มีเจ้าของจะเสื่อมเพราะการอัปเดตไม่ใช่งานของใคร ขณะที่เอกสารล้าสมัยที่ถูกนำเสนอว่าเป็นปัจจุบันทำลายความไว้ใจในเอกสารทั้งหมดของคุณ ในระดับใหญ่ อันตรายไม่ใช่หน้าที่ผิดหน้าเดียว แต่คือความมั่นใจที่ค่อย ๆ กร่อน เมื่อผู้อ่านถูกคำแนะนำล้าสมัยหลอกแล้ว พวกเขาก็เลิกเชื่อทั้งคลังและกลับไปรบกวนคนอื่นแทน ให้นำแผนที่ความเป็นเจ้าของเอกสารที่สำคัญที่สุดและคำตอบตรง ๆ ว่าตรวจพบการเสื่อมอย่างไร ไม่ว่าจะด้วยรอบการทบทวน การสร้างอัตโนมัติ การทดสอบเทียบกับระบบ หรือแค่โชค มอบเจ้าของที่มีชื่อให้ทุกเอกสารที่สำคัญ และเลือกเอกสารที่มีชีวิตซึ่งสร้างหรือทดสอบอัตโนมัติ เพื่อให้ความล้าสมัยปรากฏโดยกลไก แทนที่จะรู้จากผู้อ่านที่อับอาย สำหรับระบบองค์กรขนาดใหญ่และภาครัฐที่อยู่นานกว่าทีมเดิม เอกสารที่ไม่มีเจ้าของคือภาระที่ผู้ตรวจสอบหรือผู้ขายที่รับช่วงจะเรียกเก็บจากคุณในที่สุด

6. **เอกสารของคุณค้นพบได้ง่ายแค่ไหน และความรู้สำคัญมากน้อยเพียงใดที่ยังอยู่แค่ในกระทู้แชตและในหัวคน?** บทนี้บอกว่าความรู้ที่หาไม่เจอเท่ากับไม่มี เตือนไม่ให้ปล่อยเอกสารกระจายไปตามวิกิและเครื่องมือที่ไม่เชื่อมกันมากเกินไป และเร่งให้เก็บความรู้โดยปริยายเป็นรูปแบบที่คงทนและค้นเจอก่อนที่มันจะหลุดมือไป ในองค์กรขนาดใหญ่ ข้อเท็จจริงเดียวกันมักถูกค้นพบใหม่ ถามซ้ำ และตอบซ้ำเป็นร้อยครั้ง เพราะไม่มีใครหาเจอว่าเคยเขียนไว้ที่ไหน และการจากไปทุกครั้งพาบริบทที่ทดแทนไม่ได้ออกประตูไปด้วย ให้นำหลักฐานมาดู นับว่าคุณดูแลที่เก็บเอกสารแยกกันกี่แห่ง ลองหาข้อเท็จจริงสำคัญสามเรื่องด้วยการค้นหาอย่างเดียว และจดว่าคำตอบจริงไปอยู่ในความทรงจำของใครหรือข้อความที่ถูกฝังไว้ตรงไหน รวมไปที่ที่อยู่เดียวที่รู้กันซึ่งมีการค้นหาจริงและการนำทางที่ชัดเจน และทำให้การเก็บความรู้โดยปริยายเป็นส่วนปกติของงาน ไม่ใช่การกู้ภัยแบบวีรบุรุษ ในภาครัฐและบริบทที่จ้างภายนอกมาก ที่ระบบส่งต่อระหว่างผู้ขายและทีมตามสัญญา ความรู้ที่เขียนไว้และค้นพบได้เป็นสิ่งเดียวที่รอดจากการส่งมอบ

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** เมื่อมีวิศวกรไม่กี่คนและไม่มีเงินสำรองเหลือ ให้เขียนเอกสารเฉพาะสิ่งที่ระบบล่มตอนตีสองหรือพนักงานใหม่ต้องใช้จริง ๆ ได้แก่ README จริงต่อหนึ่งบริการ รันบุ๊กที่ทดสอบแล้วหนึ่งฉบับสำหรับขั้นตอน deploy และกู้คืนที่ทุกคนกลัว และบันทึกสั้น ๆ ลงวันที่ไม่กี่ฉบับเกี่ยวกับการตัดสินใจที่คุณมิฉะนั้นจะลืม สร้างเอกสาร API จากสัญญาโดยอัตโนมัติ เพื่อไม่ต้องดูแลด้วยมือเลย อย่าสร้างแพลตฟอร์มเอกสาร โฟลเดอร์มาร์กอัปที่มีเวอร์ชันข้างโค้ดก็พอจนกว่าจะรู้สึกเจ็บปวดจริง

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีนักเขียนเทคนิคและงบจำกัด ให้พึ่งเอกสารที่เครื่องมือของคุณสร้างให้อยู่แล้วและ docs-as-code แบบเบา แทนโครงการที่มีเจ้าหน้าที่ มองการเลือกเป็นเรื่องซื้อหรือสร้าง เลือกแพลตฟอร์มที่ผลิตเอกสารอ้างอิงปัจจุบันและฐานความรู้ที่ค้นหาได้เองมากกว่าวิกิที่คุณต้องดูแลด้วยมือ ใช้แรงอันมีค่าไปกับเอกสารสองสามฉบับที่ถ้าขาดแล้วธุรกิจจะหยุด และให้หน้าที่ผิดหรือขาดหายเป็นตัวกระตุ้นให้แก้เรื่องความเป็นเจ้าของ

**องค์กรขนาดใหญ่.** ข้ามหลายทีม ปัญหาคือความสม่ำเสมอและการค้นพบได้ ได้แก่ สายงาน docs-as-code ร่วม โครงสร้างร่วมอย่าง Diátaxis เอกสารอ้างอิง API และ changelog ที่สร้างอัตโนมัติ และบันทึกการตัดสินใจที่ใช้เหมือนกันทุกที่ เพื่อไม่ให้ความรู้กระจายไปตามวิกิหลายสิบแห่ง มอบความเป็นเจ้าของให้ทุกเอกสารที่มีคุณค่าสูง และวัดความถูกต้อง ไม่ใช่แค่การมีอยู่ ถือบันทึกสถาปัตยกรรม รันบุ๊ก และบันทึกการตัดสินใจเป็นหลักฐานการตรวจสอบ และทำวิธีผลิตให้เป็นมาตรฐาน เพื่อให้การทบทวนการควบคุมพบร่องรอยที่มีเอกสารและป้องกันได้ ไม่ใช่การวิ่งวุ่น

**ภาครัฐ.** กฎการจัดซื้อและความรับผิดชอบต่อสาธารณะทำให้เอกสารเป็นสิ่งที่ต้องส่งมอบ ไม่ใช่ความกรุณา เขียนเอกสารสถาปัตยกรรม รันบุ๊ก และบันทึกการตัดสินใจลงในสัญญาเป็นอาร์ติแฟกต์ที่บังคับ ทบทวนความถูกต้อง เพื่อให้ความรู้รอดจากการเปลี่ยนผู้ขายและให้ใครก็ตามที่รับช่วงดำเนินการระบบได้ กำหนดให้ผู้ปฏิบัติงานที่ได้รับอนุญาตคนใดก็ตามรับมือเหตุการณ์ฉุกเฉินจากรันบุ๊กได้เพียงอย่างเดียว และเก็บบันทึกการตัดสินใจเป็นบันทึกสาธารณะที่โปร่งใสว่าทำไมจึงเลือกเช่นนั้น เอกสารที่บางเกินไปในที่นี้ไม่ใช่ความไม่สะดวกส่วนตัว แต่กลายเป็นการวิศวกรรมย้อนกลับที่แพงซึ่งเงินภาษีของประชาชนเป็นผู้จ่าย

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปห้าคนเขียน README จริงสำหรับแต่ละบริการและรันบุ๊กสั้น ๆ สำหรับขั้นตอน deploy และกู้คืนที่ทุกคนกลัว เพื่อให้ระบบล่มตอนตีสองไม่ต้องพึ่งการปลุกผู้ก่อตั้งคนเดียวที่รู้จักระบบ พวกเขาสร้างเอกสาร API จากสัญญาแทนการเขียนเอง และจดบันทึกลงวันที่ไม่กี่ฉบับอธิบายว่าทำไมจึงเลือกฐานข้อมูลและแนวทางการยืนยันตัวตนแบบนั้น มันยังคงเบา แต่หมายความว่าพนักงานคนที่หกและเจ็ดปฐมนิเทศจากเอกสาร ไม่ใช่ด้วยการรบกวนทุกคน

**องค์กรขนาดใหญ่.** บริษัทซอฟต์แวร์ขนาดใหญ่เก็บเอกสารทั้งหมดไว้ในที่เก็บโค้ดเดียวกับโค้ด เขียนด้วยมาร์กอัปและทบทวนใน pull request ควบคู่ไปกับการเปลี่ยนแปลงที่มันอธิบาย เอกสารอ้างอิง API สร้างจากสัญญาของบริการ จึงไม่เบี่ยง changelog สร้างจากคอมมิตที่มีโครงสร้าง และบันทึกการตัดสินใจด้านสถาปัตยกรรมเก็บเหตุผลเบื้องหลังการเลือกสำคัญ เว็บไซต์เอกสารที่เผยแพร่ถูกสร้างอัตโนมัติทุกครั้งที่รวมโค้ด วิศวกรใหม่ทำงานได้เร็วเพราะคู่มือปฐมนิเทศและรันบุ๊กเป็นปัจจุบันและค้นเจอ และวิศวกรเวรพึ่งรันบุ๊กแทนการเรียกผู้เขียนเดิม

**ภาครัฐ.** หน่วยงานระดับชาติรับช่วงระบบจากผู้รับเหมาที่กำลังจากไป โดยพึ่งเอกสารทั้งหมดในการส่งต่อความรู้ข้ามขอบเขตสัญญา เพราะผู้ขายเดิมดูแลเอกสารสถาปัตยกรรม รันบุ๊ก และบันทึกการตัดสินใจเป็นสิ่งที่ต้องส่งมอบตามข้อบังคับ ทีมใหม่จึงดำเนินการและแก้ไขระบบได้โดยไม่ต้องมีผู้เขียนเดิม ในจุดที่เอกสารบาง หน่วยงานเผชิญกับการวิศวกรรมย้อนกลับที่แพง ประสบการณ์นั้นผลักดันนโยบายใหม่ คือเอกสารเป็นสิ่งที่ต้องส่งมอบตามสัญญา ทบทวนความถูกต้องแทนที่จะมองเป็นเรื่องรอง และรันบุ๊กต้องให้ผู้ปฏิบัติงานที่ได้รับอนุญาตคนใดก็ตามรับมือเหตุการณ์ฉุกเฉินได้

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

เอกสารให้ผลตอบแทนคืนมาเป็นเวลาปฐมนิเทศที่สั้นลง ความเสี่ยงเรื่องคนสำคัญที่ลดลง การรับมือเหตุการณ์ที่เร็วขึ้น และต้นทุนการเปลี่ยนแปลงที่ต่ำลงตลอดอายุของระบบ วิศวกรใหม่ที่ทำงานได้ภายในไม่กี่วันแทนที่จะเป็นสัปดาห์ เจ้าหน้าที่เวรที่แก้เหตุการณ์จากรันบุ๊กแทนการส่งต่อเรื่องขึ้นไป ผู้ดูแลที่เปลี่ยนแปลงระบบได้อย่างมั่นใจหลายปีหลังจากสร้าง สิ่งเหล่านี้คือการประหยัดที่ใหญ่และเกิดซ้ำ ซึ่งทบกันขึ้นไปในองค์กรขนาดใหญ่และอายุระบบที่ยาว

เอกสารมีต้นทุนอะไร? คือแรงที่ใช้เขียนและดูแล แล้วการ*ไม่*เขียนเอกสารมีต้นทุนอะไร? คุณจ่ายต่อเนื่อง ทั้งการปฐมนิเทศที่ช้า คำถามซ้ำ ๆ คอขวดจากคนสำคัญ การกู้คืนเหตุการณ์ที่ช้าลง และในกรณีสุดโต่งคือระบบที่ไม่มีใครเปลี่ยนแปลงได้อย่างปลอดภัย บังคับให้เขียนใหม่หรือวิศวกรรมย้อนกลับที่แพง ในกรณีเปลี่ยนผู้ขายและการตรวจสอบ เอกสารที่ขาดหายอาจมีต้นทุนตามสัญญาและการปฏิบัติตามข้อกำหนดโดยตรง เมื่อต้องการโน้มน้าวผู้บริหาร ให้ใส่ตัวเลขให้เวลาปฐมนิเทศ เวลารับมือเหตุการณ์ และปริมาณความรู้สำคัญที่อยู่ในหัวของแต่ละคน จากนั้นวางกรอบ docs-as-code และการสร้างอัตโนมัติเป็นวิธีได้เอกสารที่คงทนโดยไม่มีภาระการดูแลที่เพิ่มตามกัน และย้ำว่าเอกสารที่ไม่ถูกต้องเป็นภาระ ดังนั้นการลงทุนต้องรวมการรักษาให้เป็นปัจจุบันด้วย

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **เอกสารล้าสมัยที่ถูกนำเสนอว่าเป็นปัจจุบัน:** ทำให้ผู้อ่านเข้าใจผิดและทำลายความไว้ใจในเอกสารทั้งหมด
- **วิกิเขียนครั้งเดียว:** หน้าที่ถูกสร้างแล้วไม่เคยอัปเดต เบี่ยงจากความจริงอย่างเงียบ ๆ
- **เอกสารกระจัดกระจาย:** ความรู้ที่กระจายอยู่ในหลายเครื่องมือและวิกิจนหาอะไรไม่เจอ
- **ผสมประเภทเอกสาร:** บทเรียน เอกสารอ้างอิง และคำอธิบายปะปนกันในหน้าเดียว ไม่ดีกับผู้อ่านคนไหนเลย
- **ดูแลด้วยมือกับเนื้อหาที่สร้างอัตโนมัติได้:** เอกสาร API ที่เขียนด้วยมือซึ่งต้องเบี่ยงจากอินเทอร์เฟซจริงอย่างหลีกเลี่ยงไม่ได้
- **ความรู้ที่อยู่ในตัวคน (tribal knowledge):** ความเข้าใจสำคัญที่เก็บไว้ในหัวคนและประวัติแชตเท่านั้น สูญหายเมื่อพวกเขาจากไป
- **เอกสารเป็นเรื่องรอง:** เขียนตอนท้าย ถ้าเขียนเลย แทนที่จะเขียนไปพร้อมการเปลี่ยนแปลง
- **ไม่มีเจ้าของ:** เอกสารที่ไม่มีผู้รับผิดชอบจะเสื่อมเพราะการอัปเดตไม่ใช่งานของใคร

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น.** เอกสารมีน้อย กระจัดกระจาย และล้าสมัย และความรู้อยู่ในหัวคน สิ่งที่มีอยู่ถูกเขียนครั้งเดียวแล้วไม่เคยถูกแตะอีก เมื่อระบบล่มหรือมีคนจากไป จึงหมายถึงการวิศวกรรมย้อนกลับระบบ
- **ระดับ 2 พัฒนา.** มีเอกสารสำคัญ เช่น README และรันบุ๊กไม่กี่ฉบับ แต่ดูแลไม่สม่ำเสมอและหาเจอยาก บางทีมเขียนดี บางทีมแทบไม่เขียน และไม่มีความคาดหวังร่วมกันว่าที่เก็บโค้ดควรมีอะไรหรือควรอยู่ที่ไหน
- **ระดับ 3 สร้างมาตรฐาน.** docs-as-code เป็นเรื่องปกติทั่วองค์กร มีโครงสร้างร่วมอย่าง Diátaxis เอกสารอ้างอิง API และ changelog ที่สร้างอัตโนมัติ บันทึกการตัดสินใจ และความคาดหวังในการทบทวนว่าเอกสารเปลี่ยนไปพร้อมกับโค้ดที่มันอธิบาย ทุกเอกสารที่มีคุณค่าสูงมีเจ้าของที่มีชื่อ และมีที่อยู่ที่รู้กันที่เดียวพร้อมการค้นหาจริง
- **ระดับ 4 บริหารจัดการ.** เอกสารถูกวัด ไม่ใช่แค่มีอยู่ คุณติดตามความครอบคลุมของเอกสารจำเป็น อัตราการเปลี่ยนเอกสารเทียบกับอัตราการเปลี่ยนโค้ด เวลาปฐมนิเทศ การแก้เหตุการณ์จากรันบุ๊กอย่างเดียว และความสดใหม่เทียบกับเกณฑ์ความล้าสมัยที่กำหนด และทบทวนตัวชี้วัดเหล่านั้นเทียบกับเกณฑ์อ้างอิง การเสื่อมถูกจับโดยกลไกผ่านการสร้างอัตโนมัติ การทดสอบเทียบกับระบบ และการตรวจลิงก์และความถูกต้อง และหน้าที่ล้าสมัยถูกติดธงหรือตัดออกตามหลักฐาน ไม่ใช่โดยบังเอิญ
- **ระดับ 5 ประสานทั้งระบบ.** เอกสารได้รับการปรับปรุงอย่างต่อเนื่องและบูรณาการทั่วองค์กร คือมีชีวิต สร้างหรือทดสอบเทียบกับระบบเป็นส่วนใหญ่ มีเจ้าของ ค้นพบได้ และปรับตัวได้ ตัวชี้วัดป้อนกลับไปยังจุดที่คุณลงทุน การเก็บความรู้โดยปริยายเป็นส่วนปกติของงาน และคลังเอกสารถูกปรับสมดุลและตัดแต่งอย่างกระตือรือร้นเมื่อระบบ ทีม และผู้อ่านเปลี่ยนไป

## ประเด็นชวนคุย

- เอกสารฉบับไหนที่ถ้าหายไปพรุ่งนี้จะทำร้ายองค์กรของคุณมากที่สุด และตอนนี้มันมีอยู่และเป็นปัจจุบันหรือไม่?
- คุณทำให้การอัปเดตเอกสารเป็นส่วนธรรมชาติของการเปลี่ยนโค้ด แทนที่จะเป็นงานบ้านแยกต่างหากได้อย่างไร?
- ตรงไหนที่คุณแทนเอกสารที่เขียนด้วยมือด้วยเอกสารที่สร้างอัตโนมัติผูกกับแหล่งความจริงได้?
- คุณวัดอย่างไรว่าเอกสารถูกต้องและถูกใช้ ไม่ใช่แค่มีอยู่?
- ผู้ช่วย AI ควรเปลี่ยนวิธีที่คุณเขียน ดูแล และค้นหาเอกสารอย่างไร และตรงไหนที่มันอาจนำเนื้อหาที่ฟังดูน่าเชื่อแต่ผิดเข้ามา?
- คุณเก็บความรู้โดยปริยายอย่างไรก่อนที่คนที่ถือมันจะจากไป?

## ข้อสรุปสำคัญ

- ปฏิบัติต่อเอกสารเหมือนโค้ด คือมีเวอร์ชัน ทบทวน อยู่ใกล้แหล่งต้นทาง และเผยแพร่อัตโนมัติ
- จัดโครงสร้างเนื้อหาตามความต้องการของผู้อ่านด้วยบทเรียน คู่มือวิธีทำ เอกสารอ้างอิง และคำอธิบาย
- ดูแลสิ่งจำเป็นที่มีคุณค่าสูง ได้แก่ README รันบุ๊ก เอกสารสถาปัตยกรรม เอกสารปฐมนิเทศ และบันทึกการตัดสินใจ
- สร้าง API docs และ changelog อัตโนมัติ เพื่อไม่ให้เบี่ยงจากแหล่งความจริง
- สู้กับการเสื่อมด้วยความเป็นเจ้าของ ความคาดหวังในการทบทวน และการตัดแต่ง เอกสารที่ไม่ถูกต้องแย่กว่าไม่มี
