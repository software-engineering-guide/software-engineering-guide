# 12.2 รายการตรวจสอบ

รายการตรวจสอบเหล่านี้เป็นเอกสารอ้างอิงฉบับเปิดดูเร็วที่หยิบไปใช้ได้ทันที คัดลอกรายการใดก็ได้ไปใส่ในแม่แบบ pull request หน้าวิกิ ตั๋วงาน หรือวาระการประชุมทบทวน แล้วปรับข้อให้เข้ากับบริบทของคุณ ให้มองแต่ละข้อเป็นสิ่งที่คนหนึ่งคนตรวจสอบและตอบได้ว่าใช่หรือไม่ใช่ รายการตรวจสอบเป็นเครื่องช่วยจำและมาตรฐานร่วมกัน ไม่ใช่สิ่งทดแทนวิจารณญาณ ลบข้อที่ไม่เกี่ยวข้องและเพิ่มข้อที่โดเมนของคุณต้องการ

แนวทางใช้ให้ได้ผลดี:

- ทำรายการตรวจสอบให้สั้นพอที่คนจะทำจนครบจริง หากรายการถูกข้ามเป็นประจำ แปลว่ายาวหรือกว้างเกินไป
- ทำข้อที่เครื่องตรวจสอบได้ (การจัดรูปแบบ การทดสอบ การสแกน) ให้เป็นอัตโนมัติ เพื่อให้คนเอาความสนใจไปใช้กับข้อที่ต้องใช้วิจารณญาณ
- กำหนดเวอร์ชันให้รายการตรวจสอบและทบทวนเป็นระยะ รายการที่ไม่เคยเปลี่ยนเลยน่าจะไม่ได้ถูกใช้
- แยกข้อที่เป็นเงื่อนไขบังคับออกจากข้อที่เป็นข้อแนะนำ เมื่อความแตกต่างนี้สำคัญต่อกระบวนการของคุณ

## รายการตรวจสอบการทบทวนโค้ด

สำหรับผู้ทบทวนที่ตรวจการเปลี่ยนแปลงของคนอื่น

- [ ] การเปลี่ยนแปลงทำตามที่คำอธิบายและตั๋วงานที่ลิงก์ไว้ระบุ
- [ ] ขอบเขตโฟกัสที่ประเด็นเชิงตรรกะเดียว การเปลี่ยนแปลงที่ไม่เกี่ยวข้องถูกแยกออกไป
- [ ] การออกแบบเข้ากับสถาปัตยกรรมที่มีอยู่ และไม่สร้างการพึ่งพากันที่หลีกเลี่ยงได้ง่ายกว่า
- [ ] กรณีขอบ เส้นทางข้อผิดพลาด และรูปแบบความล้มเหลวได้รับการจัดการ ไม่ใช่แค่เส้นทางปกติ
- [ ] มีการทดสอบที่มีความหมาย และจะล้มเหลวหากพฤติกรรมถดถอย
- [ ] การตั้งชื่อ โครงสร้าง และคอมเมนต์ทำให้ผู้อ่านในอนาคตเข้าใจโค้ดได้
- [ ] ไม่มีความลับ ข้อมูลรับรอง โทเค็น หรือข้อมูลส่วนบุคคลถูกคอมมิตเข้ามา
- [ ] อินพุตที่อ่อนไหวด้านความมั่นคงปลอดภัยได้รับการตรวจสอบ เข้ารหัส หรือกำหนดพารามิเตอร์อย่างเหมาะสม
- [ ] อินเทอร์เฟซสาธารณะ สัญญา และความเข้ากันได้แบบย้อนหลังยังคงอยู่ หรือถูกกำหนดเวอร์ชันอย่างตั้งใจ
- [ ] การบันทึกล็อก เมตริก และการรายงานข้อผิดพลาดเพียงพอสำหรับการดูแลการเปลี่ยนแปลงนี้ในโปรดักชัน
- [ ] เอกสาร runbook และคอนฟิกูเรชันถูกอัปเดตให้ตรงกับการเปลี่ยนแปลง
- [ ] ฟีดแบ็กแยกระหว่างประเด็นที่ต้องแก้กับข้อเสนอแนะ และใช้ถ้อยคำที่พูดถึงโค้ด

## รายการตรวจสอบสำหรับผู้เขียน pull request

สำหรับผู้เขียนก่อนขอให้ทบทวน

- [ ] PR เล็กและโฟกัสพอที่จะทบทวนอย่างละเอียดได้ในการนั่งทบทวนครั้งเดียว
- [ ] คำอธิบายระบุว่าอะไรเปลี่ยน ทำไม และตรวจสอบอย่างไร
- [ ] ตั๋วงาน issue หรือเอกสารออกแบบที่ลิงก์ไว้ให้บริบทที่จำเป็นแก่ผู้ทบทวน
- [ ] การตรวจสอบอัตโนมัติทั้งหมดผ่านทั้งในเครื่องหรือใน CI (บิลด์ lint การจัดรูปแบบ การทดสอบ การสแกน)
- [ ] พฤติกรรมใหม่และที่เปลี่ยนไปมีการทดสอบครอบคลุม
- [ ] การปรับโครงสร้างโค้ดเชิงกลไกแยกจากการเปลี่ยนพฤติกรรม
- [ ] ทบทวนด้วยตนเองเสร็จแล้ว: คุณอ่าน diff ของตัวเองทีละบรรทัดแล้ว
- [ ] ไม่มีโค้ดดีบัก บล็อกที่คอมเมนต์ทิ้งไว้ ความลับ หรือไฟล์หลงเหลือ
- [ ] การย้ายข้อมูลฐานข้อมูล feature flag และการเปลี่ยนคอนฟิกมีเอกสารและย้อนกลับได้
- [ ] การเปลี่ยนแปลงที่ทำให้ของเดิมใช้ไม่ได้ถูกระบุไว้ชัดเจนพร้อมเส้นทางการย้าย
- [ ] มีภาพหน้าจอ ภาพบันทึก หรือตัวอย่างผลลัพธ์ในจุดที่ช่วยการทบทวน
- [ ] ขอผู้ทบทวนที่เหมาะสมและผู้อนุมัติตามบทบาทที่จำเป็นแล้ว

## นิยามของคำว่าเสร็จ (Definition of Done)

มาตรฐานร่วมที่งานชิ้นหนึ่งต้องผ่านก่อนถือว่าเสร็จสมบูรณ์

- [ ] เกณฑ์การยอมรับในตั๋วงานครบทุกข้อและสาธิตได้
- [ ] โค้ดผ่านการทบทวนโดยเพื่อนร่วมงานและได้รับอนุมัติจากผู้ทบทวนที่กำหนด
- [ ] เขียนการทดสอบอัตโนมัติ ผ่าน และรวมเข้ามาพร้อมการเปลี่ยนแปลง
- [ ] โค้ดถูกรวมเข้าสายหลักและปรับใช้ผ่านไปป์ไลน์ได้อย่างราบรื่น
- [ ] ไม่มีข้อบกพร่องที่ทราบและเกินเกณฑ์ความรุนแรงที่ตกลงกันค้างอยู่
- [ ] เอกสาร ข้อความช่วยเหลือ และ runbook ถูกอัปเดต
- [ ] มีความสามารถในการสังเกตระบบครบ: มีล็อก เมตริก และการแจ้งเตือนที่เกี่ยวข้อง
- [ ] พิจารณาและจัดการผลกระทบด้านความมั่นคงปลอดภัยและความเป็นส่วนตัวแล้ว
- [ ] ข้อกำหนดด้านการเข้าถึงได้ของการเปลี่ยนแปลงนี้บรรลุแล้ว หากเป็นส่วนที่ผู้ใช้เห็น
- [ ] ตั้งค่า feature flag แล้วและตกลงแผนการปล่อยแล้ว
- [ ] เจ้าของผลิตภัณฑ์หรือผู้มีส่วนได้ส่วนเสียยอมรับผลลัพธ์แล้ว
- [ ] งานต่อเนื่องใด ๆ ถูกบันทึกเป็นตั๋วงานที่ติดตามได้ ไม่ปล่อยให้เป็นความเข้าใจที่ไม่ได้พูดออกมา

## ความพร้อมก่อนเปิดใช้งานจริงในโปรดักชัน

ก่อนส่งการเปลี่ยนแปลงสำคัญหรือบริการใหม่ขึ้นโปรดักชัน

- [ ] แผนการปล่อยมีเอกสาร รวมขั้นตอนแบบเป็นระยะหรือ canary และเกณฑ์ความสำเร็จ
- [ ] แผนย้อนกลับมีเอกสาร ผ่านการทดสอบ และดำเนินการได้อย่างรวดเร็ว
- [ ] การทดสอบความจุและภาระงานแสดงว่าระบบรองรับความต้องการปกติและช่วงสูงสุดได้
- [ ] การเฝ้าติดตาม แดชบอร์ด และการแจ้งเตือนทำงานและผ่านการตรวจสอบก่อนเปิดตัว
- [ ] จัดตารางเวรเฝ้าระบบแล้ว และผู้ตอบสนองรู้จักระบบ
- [ ] มี runbook สำหรับสถานการณ์ล้มเหลวและการปฏิบัติการที่น่าจะเกิดที่สุด
- [ ] ยืนยันแล้วว่าการพึ่งพา การเชื่อมต่อ และบุคคลที่สามพร้อม และเข้าใจขีดจำกัดอัตราการเรียก
- [ ] การทบทวนความมั่นคงปลอดภัยและการลงนามอนุมัติที่จำเป็นเสร็จสมบูรณ์
- [ ] การย้ายข้อมูล (ถ้ามี) ผ่านการทดสอบตั้งแต่ต้นจนจบพร้อมแผนถอยกลับที่ตรวจสอบแล้ว
- [ ] feature flag ทำให้ปิดการเปลี่ยนแปลงได้โดยไม่ต้องปรับใช้ใหม่
- [ ] ได้รับการอนุมัติด้านกฎหมาย ความเป็นส่วนตัว และการปฏิบัติตามข้อกำหนดในจุดที่จำเป็น
- [ ] แผนการสื่อสารครอบคลุมผู้มีส่วนได้ส่วนเสีย ฝ่ายสนับสนุน และลูกค้า
- [ ] เจ้าของที่ระบุชื่อได้ตัดสินใจ go/no-go เทียบกับเกณฑ์ที่ชัดเจน

## รายการตรวจสอบการทบทวนความมั่นคงปลอดภัย / แบบจำลองภัยคุกคาม

สำหรับประเมินสถานะความมั่นคงปลอดภัยของการเปลี่ยนแปลงหรือระบบ

- [ ] ระบุและบันทึกขอบเขตความไว้วางใจและการไหลของข้อมูลแล้ว
- [ ] บังคับใช้การยืนยันตัวตนที่ทุกจุดเข้าที่ต้องการ
- [ ] การตรวจสอบสิทธิ์บังคับหลักสิทธิ์น้อยที่สุดกับทุกการกระทำและทรัพยากร
- [ ] อินพุตจากภายนอกทั้งหมดได้รับการตรวจสอบ และเอาต์พุตถูกเข้ารหัสให้เหมาะกับปลายทาง
- [ ] ความลับเก็บในห้องนิรภัย (vault) ที่มีการจัดการ ไม่อยู่ในโค้ดหรือคอนฟิก และหมุนเวียนเปลี่ยนได้
- [ ] ข้อมูลถูกเข้ารหัสทั้งระหว่างส่งและขณะจัดเก็บตามที่การจัดชั้นข้อมูลกำหนด
- [ ] สแกนการพึ่งพากันหาช่องโหว่ที่ทราบและอัปเดตให้เป็นปัจจุบัน
- [ ] บรรเทาความเสี่ยงของ injection, deserialisation และ SSRF สำหรับอินพุตที่ไม่น่าไว้ใจ
- [ ] เหตุการณ์ที่เกี่ยวกับความมั่นคงปลอดภัยถูกบันทึกล็อกโดยไม่บันทึกข้อมูลอ่อนไหว
- [ ] การจำกัดอัตรา โควตา และการป้องกันการใช้ในทางที่ผิดคุ้มครองปลายทางที่เปิดสู่ภายนอก
- [ ] ข้อความแสดงข้อผิดพลาดไม่รั่วไหล stack trace ส่วนภายใน หรือรายละเอียดอ่อนไหว
- [ ] ภัยคุกคามที่ระบุผ่าน STRIDE หรือวิธีคล้ายกันถูกบันทึกพร้อมมาตรการบรรเทาหรือความเสี่ยงที่ยอมรับ
- [ ] วางแผนหรือทำการทดสอบความมั่นคงปลอดภัย (SAST, DAST หรือการทดสอบเจาะระบบ) เสร็จแล้ว

## รายการตรวจสอบความเป็นส่วนตัวและการคุ้มครองข้อมูล (แบบ DPIA)

สำหรับการประมวลผลที่เกี่ยวข้องกับข้อมูลส่วนบุคคลหรือข้อมูลอ่อนไหว

- [ ] ข้อมูลส่วนบุคคลที่เก็บถูกทำบัญชี จัดชั้น และลดให้เหลือเท่าที่จำเป็น
- [ ] ฐานทางกฎหมายหรืออำนาจของแต่ละวัตถุประสงค์การประมวลผลมีเอกสาร
- [ ] บังคับใช้การจำกัดวัตถุประสงค์: ใช้ข้อมูลเฉพาะตามวัตถุประสงค์ที่ระบุ
- [ ] กำหนดระยะเวลาการเก็บรักษา และทำการลบหรือทำให้ไม่ระบุตัวตนโดยอัตโนมัติ
- [ ] สามารถปฏิบัติตามสิทธิของเจ้าของข้อมูล (การเข้าถึง การแก้ไข การลบ การโอนย้ายข้อมูล) ได้
- [ ] ความยินยอม (หากอาศัยความยินยอม) ให้โดยอิสระ เฉพาะเจาะจง และเพิกถอนได้
- [ ] บุคคลที่สามและผู้ประมวลผลผูกพันตามข้อกำหนดการคุ้มครองข้อมูลที่เพียงพอ
- [ ] การโอนข้อมูลข้ามพรมแดนมีกลไกทางกฎหมายที่เหมาะสมรองรับ
- [ ] การเข้าถึงข้อมูลส่วนบุคคลถูกจำกัด บันทึกล็อก และทบทวน
- [ ] ประเมินความเสี่ยงด้านความเป็นส่วนตัวต่อบุคคล และบรรเทาหรือยกระดับต่อ
- [ ] กำหนดกระบวนการตรวจจับและแจ้งเหตุข้อมูลรั่วไหลแล้ว
- [ ] บันทึกทางเลือกการออกแบบเพื่อความเป็นส่วนตัวโดยเริ่มต้นและโดยค่าเริ่มต้นสำหรับฟีเจอร์
- [ ] เจ้าหน้าที่คุ้มครองข้อมูลหรือผู้ทบทวนความเป็นส่วนตัวลงนามอนุมัติแล้วในจุดที่จำเป็น

## รายการตรวจสอบการเข้าถึงได้ (WCAG)

สำหรับส่วนติดต่อผู้ใช้ที่ผู้ใช้เห็น สอดคล้องกับหลักการของ WCAG

- [ ] เข้าถึงและใช้งานเนื้อหาทั้งหมดได้ด้วยแป้นพิมพ์อย่างเดียว
- [ ] ลำดับโฟกัสสมเหตุสมผล และมีตัวบ่งชี้โฟกัสที่มองเห็นได้
- [ ] คอนทราสต์ของสีข้อความได้ตามอัตราส่วนเป้าหมาย (โดยทั่วไป 4.5:1 สำหรับข้อความเนื้อหา)
- [ ] รูปภาพและเนื้อหาที่ไม่ใช่ข้อความมีข้อความทดแทนที่มีความหมาย
- [ ] ช่องกรอกแบบฟอร์มมีป้ายกำกับที่เชื่อมโยงกันและข้อความแสดงข้อผิดพลาดที่ชัดเจน
- [ ] หัวเรื่อง landmark และโครงสร้างถูกทำเครื่องหมายเชิงความหมาย
- [ ] คอมโพเนนต์แบบโต้ตอบเปิดเผยชื่อ บทบาท และสถานะที่ถูกต้องแก่เทคโนโลยีช่วยเหลือ
- [ ] เนื้อหาจัดเรียงใหม่ได้และใช้งานได้ที่การขยาย 200% และบนหน้าจอขนาดเล็ก
- [ ] ปรับขีดจำกัดเวลาได้ และหยุดการเคลื่อนไหวหรือเนื้อหาที่เล่นอัตโนมัติชั่วคราวได้
- [ ] สีไม่ใช่วิธีเดียวในการสื่อสารข้อมูล
- [ ] สื่อมีคำบรรยาย และมีถอดความหรือคำบรรยายเสียงในจุดที่จำเป็น
- [ ] ทดสอบส่วนติดต่อด้วยโปรแกรมอ่านหน้าจอและเครื่องมือตรวจการเข้าถึงได้อัตโนมัติ

## รายการตรวจสอบการทบทวนการออกแบบ API

ก่อนเผยแพร่หรือเปลี่ยน API

- [ ] การตั้งชื่อทรัพยากรและการดำเนินการสอดคล้องและคาดเดาได้
- [ ] สัญญาถูกระบุในสคีมาที่เครื่องอ่านได้ (เช่น OpenAPI)
- [ ] กำหนดกลยุทธ์การกำหนดเวอร์ชัน และรักษาหรือจัดการความเข้ากันได้แบบย้อนหลัง
- [ ] การแบ่งหน้า การกรอง และการเรียงลำดับเป็นไปตามธรรมเนียมที่สอดคล้องกัน
- [ ] การตอบกลับข้อผิดพลาดใช้โครงสร้าง รหัส และข้อความที่นำไปปฏิบัติได้อย่างสอดคล้องกัน
- [ ] ระบุการยืนยันตัวตนและการให้สิทธิ์สำหรับทุกการดำเนินการ
- [ ] กำหนดและบังคับใช้การตรวจสอบอินพุตและขีดจำกัดขนาด
- [ ] กำหนดภาวะนิจพล (idempotency) สำหรับการดำเนินการที่คาดว่าจะมีการลองใหม่
- [ ] บันทึกขีดจำกัดอัตรา โควตา และพฤติกรรมการชะลอ
- [ ] การหมดเวลา การลองใหม่ และความหมายของความล้มเหลวชัดเจนสำหรับไคลเอนต์
- [ ] ลดและให้เหตุผลการเปิดเผยข้อมูลอ่อนไหวในการตอบกลับ
- [ ] เอกสารมีตัวอย่างสำหรับทุกการดำเนินการและกรณีข้อผิดพลาด
- [ ] กำหนดนโยบายการเลิกใช้และกรอบเวลาการยุติ

## รายการตรวจสอบการทบทวนการตัดสินใจด้านสถาปัตยกรรม (ADR)

สำหรับทบทวนบันทึกการตัดสินใจด้านสถาปัตยกรรมที่เสนอ

- [ ] ระบุบริบทและปัญหาที่กำลังแก้อย่างชัดเจน
- [ ] ระบุการตัดสินใจอย่างไม่กำกวมเป็นทางเลือกเดียว
- [ ] พิจารณาและเปรียบเทียบทางเลือกที่สมจริงอย่างน้อยสองทาง
- [ ] บันทึกผลที่ตามมาทั้งด้านบวกและด้านลบ
- [ ] จัดการผลกระทบที่ไม่ใช่เชิงหน้าที่ (ประสิทธิภาพ ความมั่นคงปลอดภัย ต้นทุน การดำเนินงาน)
- [ ] การตัดสินใจสอดคล้องกับหลักการที่มีอยู่และ ADR ก่อนหน้า หรือระบุอย่างชัดเจนว่าแทนที่ของเดิม
- [ ] ปรึกษาทีมและผู้มีส่วนได้ส่วนเสียที่ได้รับผลกระทบแล้ว
- [ ] ประเมินความสามารถในการย้อนกลับและต้นทุนของการเปลี่ยนแปลง
- [ ] ระบุสมมติฐานและข้อจำกัดอย่างชัดเจน
- [ ] ตั้งสถานะ (เสนอ ยอมรับ ถูกแทนที่) และลงวันที่
- [ ] ค้นหาการตัดสินใจได้และมีลิงก์จากระบบที่เกี่ยวข้อง
- [ ] การดำเนินการต่อเนื่องหรือการย้ายระบบใด ๆ ถูกบันทึกเป็นงานที่ติดตามได้

## รายการตรวจสอบการตอบสนองต่อเหตุการณ์ขัดข้อง

ระหว่างเหตุการณ์ขัดข้องในโปรดักชันที่กำลังเกิดขึ้น

- [ ] ประกาศเหตุการณ์และมอบหมายผู้บัญชาการเหตุการณ์หนึ่งคน
- [ ] ประเมินและสื่อสารความรุนแรง ขอบเขต และผลกระทบต่อลูกค้า
- [ ] เปิดช่องทางสื่อสารเฉพาะและบันทึกเหตุการณ์
- [ ] มอบหมายบทบาทให้ชัดเจน: ผู้บัญชาการ หัวหน้าฝ่ายสื่อสาร และหัวหน้าฝ่ายปฏิบัติการ
- [ ] ให้ความสำคัญกับการบรรเทาและการกู้คืนบริการก่อนการวิเคราะห์หาสาเหตุราก
- [ ] แจ้งสถานะแก่ผู้มีส่วนได้ส่วนเสียเป็นประจำตามจังหวะที่กำหนด
- [ ] จดไทม์ไลน์ของเหตุการณ์ การกระทำ และการตัดสินใจขณะที่เกิดขึ้น
- [ ] ยกระดับไปยังผู้ตอบสนองเพิ่มเติมหรือผู้ขายเมื่อจำเป็น
- [ ] แจ้งฝ่ายกฎหมาย ความมั่นคงปลอดภัย และการปฏิบัติตามข้อกำหนด หากเกี่ยวข้องกับข้อมูลหรือกฎระเบียบ
- [ ] ตรวจสอบการแก้ไขและยืนยันว่าระบบกู้คืนสมบูรณ์แล้ว
- [ ] ปิดเหตุการณ์อย่างเป็นทางการและสื่อสารการแก้ไขเสร็จสิ้น
- [ ] นัดหมายการทบทวนเหตุการณ์แบบไม่กล่าวโทษก่อนที่ทุกคนจะแยกย้าย

## รายการตรวจสอบการทบทวนเหตุการณ์ (postmortem)

สำหรับการทบทวนย้อนหลังหลังเหตุการณ์ขัดข้อง

- [ ] การทบทวนเป็นแบบไม่กล่าวโทษและโฟกัสที่ระบบและปัจจัยที่มีส่วน
- [ ] บันทึกไทม์ไลน์ของเหตุการณ์ที่เป็นข้อเท็จจริงและมีการประทับเวลา
- [ ] วัดผลกระทบต่อลูกค้าและธุรกิจเป็นตัวเลข (ระยะเวลา ขอบเขต ต้นทุน)
- [ ] วิเคราะห์การตรวจจับ: พบปัญหาได้อย่างไรและเมื่อใด
- [ ] วิเคราะห์การตอบสนอง: อะไรช่วย และอะไรทำให้การกู้คืนช้า
- [ ] ระบุสาเหตุที่มีส่วนหลายข้อ ไม่ใช่แค่สาเหตุรากเดียว
- [ ] บันทึกสิ่งที่ไปได้ดีด้วย ไม่ใช่เฉพาะสิ่งที่ผิดพลาด
- [ ] รายการสิ่งที่ต้องทำเฉพาะเจาะจง มอบหมายเจ้าของ และมีกำหนดส่ง
- [ ] รายการสิ่งที่ต้องทำครอบคลุมการป้องกัน การตรวจจับ และการบรรเทา
- [ ] ติดตามรายการต่อเนื่องจนเสร็จใน backlog ปกติ
- [ ] แบ่งปันรายงานทบทวนอย่างกว้างขวางเพื่อให้คนอื่นเรียนรู้ได้
- [ ] ทบทวนแบบรูปเชิงระบบข้ามเหตุการณ์เป็นระยะ

## รายการตรวจสอบความพร้อมเข้าเวรเฝ้าระบบ

ก่อนที่ใครจะเริ่มเวรเฝ้าระบบ

- [ ] ผู้ตอบสนองเข้าถึงระบบ แดชบอร์ด และเครื่องมือทั้งหมดที่ต้องใช้ได้
- [ ] การแจ้งเตือนส่งถึงผู้ตอบสนองได้อย่างเชื่อถือได้และผ่านการทดสอบ
- [ ] ทราบเส้นทางการยกระดับและผู้ติดต่อเวรสำรอง และข้อมูลเป็นปัจจุบัน
- [ ] มี runbook สำหรับการแจ้งเตือนที่พบบ่อยที่สุดและรุนแรงที่สุด
- [ ] ผู้ตอบสนองผ่านการปฐมนิเทศหรือการเรียนรู้จากการสังเกตสำหรับระบบเหล่านี้แล้ว
- [ ] ส่งต่อการเปลี่ยนแปลงล่าสุด เหตุการณ์ที่ยังดำเนินอยู่ และปัญหาที่ทราบ
- [ ] ปรับเกณฑ์การแจ้งเตือนให้ลดสัญญาณรบกวนและการเรียกที่เป็นผลบวกลวงให้น้อยที่สุด
- [ ] ผู้ตอบสนองรู้วิธีประกาศเหตุการณ์และติดต่อผู้บัญชาการ
- [ ] เข้าถึงโปรดักชันได้จากสภาพแวดล้อมการทำงานของผู้ตอบสนอง
- [ ] บันทึกช่องทางสื่อสารและผู้ติดต่อของผู้มีส่วนได้ส่วนเสีย
- [ ] เผยแพร่ตารางเวรเฝ้าระบบและไม่มีช่องว่างของการครอบคลุม
- [ ] ค่าตอบแทน ความคาดหวัง และขีดจำกัดภาระงานของการเข้าเวรชัดเจน

## รายการตรวจสอบการกำหนด SLO

เมื่อกำหนดวัตถุประสงค์ระดับบริการ

- [ ] ระบุเส้นทางผู้ใช้หรือความสามารถที่ SLO ปกป้องอย่างชัดเจน
- [ ] ตัวบ่งชี้ระดับบริการ (SLI) กำหนดเป็นปริมาณที่ชัดเจนและวัดได้
- [ ] วัด SLI จากมุมมองของผู้ใช้ให้มากที่สุดเท่าที่ทำได้
- [ ] ตั้งเป้าหมายวัตถุประสงค์ในระดับที่ผู้ใช้ต้องการจริง ไม่ใช่ 100%
- [ ] ระบุช่วงเวลาการวัด (เช่น 28 วันแบบเลื่อน)
- [ ] คำนวณและเข้าใจงบความผิดพลาดที่ได้จากเป้าหมาย
- [ ] มีนโยบายกำหนดว่าจะเกิดอะไรขึ้นเมื่องบความผิดพลาดหมด
- [ ] แหล่งข้อมูลของ SLI เชื่อถือได้และมีการติดตั้งเครื่องมือวัด
- [ ] การแจ้งเตือนผูกกับอัตราการเผางบ (burn rate) ไม่ใช่แค่การละเมิดเกณฑ์
- [ ] เจ้าของและผู้มีส่วนได้ส่วนเสียเห็นพ้องว่า SLO สมจริงและมีความหมาย
- [ ] บันทึก SLO และแสดงบนแดชบอร์ด
- [ ] มีตารางเวลาทบทวนและปรับ SLO เมื่อบริการพัฒนาไป

## รายการตรวจสอบไปป์ไลน์ CI/CD

สำหรับไปป์ไลน์การรวมโค้ดและการส่งมอบอย่างต่อเนื่อง

- [ ] ทุกคอมมิตกระตุ้นการบิลด์และรันการทดสอบอัตโนมัติ
- [ ] ไปป์ไลน์ล้มเหลวเร็วและรายงานผลต่อผู้เขียนอย่างชัดเจน
- [ ] lint การจัดรูปแบบ และการวิเคราะห์แบบสถิตทำงานอัตโนมัติ
- [ ] การทดสอบหน่วย การทดสอบการผสาน และการทดสอบแบบครบวงจรที่เกี่ยวข้องรันในไปป์ไลน์
- [ ] การสแกนความมั่นคงปลอดภัยและการพึ่งพาทำงานทุกบิลด์
- [ ] อาร์ติแฟกต์ของการบิลด์มีเวอร์ชัน ไม่เปลี่ยนแปลง และเก็บในรีจิสทรี
- [ ] ฉีดความลับเข้าอย่างปลอดภัยและไม่พิมพ์ลงล็อก
- [ ] การปรับใช้เป็นอัตโนมัติและทำซ้ำได้ข้ามสภาพแวดล้อม
- [ ] กำหนดและใช้กลยุทธ์การปรับใช้ (canary, blue-green, rolling)
- [ ] การย้อนกลับเป็นอัตโนมัติหรือเป็นการกระทำเดียวที่มีเอกสาร
- [ ] สิทธิ์ของไปป์ไลน์เป็นไปตามหลักสิทธิ์น้อยที่สุดและตรวจสอบย้อนหลังได้
- [ ] เก็บคอนฟิกของไปป์ไลน์ในระบบควบคุมเวอร์ชันเป็นโค้ด
- [ ] สร้างที่มาของการบิลด์และ SBOM ในจุดที่จำเป็น

## รายการตรวจสอบการทบทวนโครงสร้างพื้นฐานเป็นโค้ด

สำหรับทบทวนโครงสร้างพื้นฐานที่กำหนดเป็นโค้ด

- [ ] การเปลี่ยนแปลงแสดงเป็นโค้ดทั้งหมดและนำไปใช้ผ่านไปป์ไลน์
- [ ] ทบทวนแผนหรือผลลัพธ์ dry-run ก่อนนำไปใช้
- [ ] เก็บสถานะอย่างปลอดภัยพร้อมการล็อกเพื่อป้องกันการเปลี่ยนแปลงพร้อมกัน
- [ ] ทรัพยากรเป็นไปตามธรรมเนียมการตั้งชื่อ การติดแท็ก และความเป็นเจ้าของ
- [ ] ใช้บทบาทและนโยบาย IAM แบบสิทธิ์น้อยที่สุด ไม่ใช้ wildcard หากหลีกเลี่ยงได้
- [ ] ลดการเปิดเผยทางเครือข่าย ไม่มีการเข้าถึงสาธารณะโดยไม่ตั้งใจ
- [ ] อ้างอิงความลับและค่าอ่อนไหวจาก vault ไม่ฝังไว้ในโค้ด
- [ ] เปิดการเข้ารหัสสำหรับที่เก็บข้อมูล ฐานข้อมูล และการส่งผ่าน
- [ ] การเปลี่ยนแปลงมีภาวะนิจพลและนำไปใช้ซ้ำได้อย่างปลอดภัย
- [ ] เข้าใจรัศมีผลกระทบ (blast radius) และระบุการเปลี่ยนแปลงที่ทำลายล้างไว้ชัดเจน
- [ ] พิจารณาผลกระทบด้านต้นทุนของการเปลี่ยนแปลง
- [ ] โมดูลนำกลับมาใช้ได้ มีเวอร์ชัน และมีการทดสอบ
- [ ] มีการตรวจจับการเบี่ยงเบน (drift) เพื่อจับการเปลี่ยนแปลงนอกช่องทาง

## รายการตรวจสอบการปล่อยโมเดล AI/ML

ก่อนปล่อยโมเดลแมชชีนเลิร์นนิงสู่โปรดักชัน

- [ ] บันทึกการใช้งานที่ตั้งใจ ขอบเขต และข้อจำกัดของโมเดล
- [ ] ตรวจสอบที่มา สัญญาอนุญาต และความยินยอมของข้อมูลสำหรับฝึกและประเมินผล
- [ ] ข้อมูลและโมเดลมีเวอร์ชันและทำซ้ำได้
- [ ] ประเมินประสิทธิภาพกับข้อมูลทดสอบที่เป็นตัวแทนและแยกไว้ต่างหาก
- [ ] ประเมินความเป็นธรรมและอคติข้ามกลุ่มย่อยที่เกี่ยวข้อง
- [ ] ประเมินโมเดลเทียบกับตัวเดิมที่ใช้อยู่หรือเกณฑ์พื้นฐาน
- [ ] เข้าใจรูปแบบความล้มเหลว กรณีขอบ และพฤติกรรมนอกการกระจายของข้อมูล
- [ ] ประเมินและบรรเทาความเสี่ยงด้านความปลอดภัย การใช้ในทางที่ผิด และผลลัพธ์ที่เป็นอันตราย
- [ ] มีการเฝ้าติดตามการเบี่ยงเบน คุณภาพข้อมูล และการเสื่อมของประสิทธิภาพ
- [ ] มีการย้อนกลับหรือสำรองไปใช้โมเดลก่อนหน้าหรือเส้นทางแบบอิงกฎ
- [ ] มีการกำกับดูแลโดยมนุษย์หรือช่องทางอุทธรณ์สำหรับการตัดสินใจที่มีผลสำคัญ
- [ ] การทบทวนความเป็นส่วนตัวครอบคลุมข้อมูลฝึกและอินพุตกับเอาต์พุตของการอนุมาน
- [ ] เผยแพร่ model card หรือเอกสารเทียบเท่าให้ผู้มีส่วนได้ส่วนเสีย

## รายการตรวจสอบคุณภาพไปป์ไลน์ข้อมูล

สำหรับไปป์ไลน์ข้อมูลที่ป้อนให้การวิเคราะห์หรือผลิตภัณฑ์

- [ ] ตรวจสอบสคีมาของข้อมูลต้นทาง และตรวจจับการเปลี่ยนสคีมา
- [ ] การนำเข้าจัดการระเบียนที่มาช้า ซ้ำ และไม่เรียงลำดับได้ถูกต้อง
- [ ] การตรวจคุณภาพข้อมูล (ความสมบูรณ์ ความไม่ซ้ำ ช่วงค่า) ทำงานอัตโนมัติ
- [ ] ระเบียนที่ล้มเหลวถูกกักไว้และแสดงให้เห็น ไม่ถูกทิ้งเงียบ ๆ
- [ ] ทดสอบการแปลงด้วยอินพุตตัวแทนและกรณีขอบ
- [ ] ไปป์ไลน์มีภาวะนิจพลและรันซ้ำหลังล้มเหลวได้อย่างปลอดภัย
- [ ] เฝ้าติดตามความสดใหม่และความหน่วงของผลลัพธ์เทียบกับความคาดหวัง
- [ ] บันทึกสายธารข้อมูล (lineage) เพื่อให้ผู้ใช้ทราบว่าข้อมูลมาจากไหน
- [ ] ข้อมูลส่วนบุคคลและอ่อนไหวถูกจัดชั้น ปิดบัง หรือจำกัดอย่างเหมาะสม
- [ ] รองรับและบันทึกการเติมย้อนหลัง (backfill) และการประมวลผลซ้ำ
- [ ] การแจ้งเตือนบอกเจ้าของเมื่อเกิดความล้มเหลวและการละเมิดคุณภาพ
- [ ] บังคับใช้นโยบายการเก็บรักษาและการลบกับข้อมูลที่จัดเก็บ
- [ ] บันทึกผู้ใช้ปลายทางและ SLA

## รายการตรวจสอบการรับโอเพนซอร์สและการทบทวนสัญญาอนุญาต

ก่อนนำส่วนประกอบโอเพนซอร์สมาใช้

- [ ] ระบุสัญญาอนุญาตของส่วนประกอบและอยู่ในรายการที่อนุมัติ
- [ ] เข้าใจและปฏิบัติตามภาระของสัญญาอนุญาต (การระบุแหล่งที่มา copyleft ประกาศ)
- [ ] ยืนยันความเข้ากันได้ของสัญญาอนุญาตกับรูปแบบการแจกจ่ายของคุณ
- [ ] โครงการได้รับการดูแลอย่างต่อเนื่องและมีชุมชนที่แข็งแรง
- [ ] ตรวจช่องโหว่ที่ทราบและใช้เวอร์ชันที่เป็นปัจจุบัน
- [ ] ทำบัญชีส่วนประกอบนี้และการพึ่งพาต่อเนื่อง (transitive) ของมัน
- [ ] ทบทวนสถานะความมั่นคงปลอดภัยและประวัติเหตุการณ์ที่ผ่านมา
- [ ] ส่วนประกอบตอบความต้องการจริงโดยไม่ซ้ำซ้อนมาก
- [ ] พิจารณาต้นทุนการเลิกใช้และความสามารถในการแทนที่ส่วนประกอบ
- [ ] บันทึกส่วนประกอบไว้ใน SBOM
- [ ] มีเจ้าของที่ระบุชื่อรับผิดชอบติดตามการอัปเดตและประกาศแจ้งเตือน
- [ ] ปฏิบัติตามนโยบายการส่งการแก้ไขกลับสู่โครงการต้นทางและการแยกสาขา (fork) ภายใน หากมีการแก้ไข

## รายการตรวจสอบความเสี่ยงจากผู้ขาย / บุคคลที่สาม

ก่อนรับผู้ขายหรือบริการภายนอกเข้ามา

- [ ] กำหนดความต้องการทางธุรกิจและข้อมูลที่ผู้ขายจะเข้าถึงอย่างชัดเจน
- [ ] ประเมินสถานะความมั่นคงปลอดภัยของผู้ขาย (การรับรอง การตรวจสอบ แบบสอบถาม)
- [ ] ข้อกำหนดการประมวลผลข้อมูล ความเป็นเจ้าของ และการลบเมื่อเลิกใช้ชัดเจนในสัญญา
- [ ] เปิดเผยผู้ประมวลผลช่วงและที่ตั้งข้อมูลของผู้ขาย และยอมรับได้
- [ ] ตรวจสอบการปฏิบัติตามกฎระเบียบที่เกี่ยวข้อง
- [ ] บันทึกเวลาทำงาน การสนับสนุน และข้อผูกพัน SLA
- [ ] ภาระและกรอบเวลาการแจ้งเหตุข้อมูลรั่วไหลอยู่ในสัญญา
- [ ] จำกัดการเข้าถึงตามหลักสิทธิ์น้อยที่สุดและเพิกถอนได้
- [ ] ประเมินความต่อเนื่องทางธุรกิจและผลกระทบหากผู้ขายล้มเหลว
- [ ] มีแผนการเลิกใช้และย้ายข้อมูลเพื่อหลีกเลี่ยงการผูกติดกับผู้ขาย
- [ ] เข้าใจต้นทุน เงื่อนไขการต่ออายุ และข้อกำหนดการเปลี่ยนราคา
- [ ] เพิ่มผู้ขายเข้าทะเบียนความเสี่ยงพร้อมวันที่ทบทวน

## รายการตรวจสอบความพร้อมด้านการปฏิบัติตามข้อกำหนดของภาครัฐ (แบบ ATO / FedRAMP)

สำหรับระบบที่ต้องได้รับอนุญาตอย่างเป็นทางการให้ดำเนินการ

- [ ] กำหนดและวาดแผนภาพขอบเขตระบบและการไหลของข้อมูล
- [ ] จัดประเภทข้อมูลตามระดับผลกระทบและความอ่อนไหว
- [ ] เลือกและปรับเกณฑ์พื้นฐานของมาตรการควบคุมที่ใช้ได้
- [ ] แผนความมั่นคงปลอดภัยของระบบบันทึกวิธีที่ใช้แต่ละมาตรการควบคุม
- [ ] ดำเนินมาตรการควบคุม มีหลักฐาน และโยงเข้ากับแผน
- [ ] การเฝ้าติดตามต่อเนื่องและการสแกนช่องโหว่ทำงานอยู่
- [ ] แผนปฏิบัติการและหมุดหมาย (plan of action and milestones) ติดตามข้อค้นพบที่ค้างอยู่จนแก้ไข
- [ ] การควบคุมการเข้าถึง การบันทึกล็อกเพื่อตรวจสอบย้อนหลัง และการบริหารตัวตนเป็นไปตามข้อกำหนด
- [ ] การเข้ารหัสใช้อัลกอริทึมที่ได้รับอนุมัติและโมดูลที่ผ่านการตรวจสอบรับรอง
- [ ] แผนการตอบสนองต่อเหตุการณ์มีเอกสารและผ่านการทดสอบ
- [ ] แผนฉุกเฉินและการกู้คืนจากภัยพิบัติมีเอกสารและผ่านการทดสอบ
- [ ] การประเมินหรือการตรวจสอบมาตรการควบคุมโดยผู้ประเมินอิสระเสร็จสมบูรณ์
- [ ] ผู้มีอำนาจอนุญาตมีผลการประเมินความเสี่ยงที่จำเป็นต่อการให้อนุญาต
- [ ] กำหนดเหตุที่ต้องขออนุญาตใหม่และจังหวะการอนุญาตต่อเนื่อง
