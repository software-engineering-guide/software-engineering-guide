# 5.6 วิศวกรรมส่วนหน้า

## ภาพรวมและแรงจูงใจ

วิศวกรรมส่วนหน้า (frontend engineering) คือศาสตร์ของการสร้างชั้นของซอฟต์แวร์ที่หันเข้าหาผู้ใช้ ได้แก่โค้ดที่ทำงานในเบราว์เซอร์หรือบนอุปกรณ์ และเปลี่ยนงานออกแบบ เนื้อหา และข้อมูลให้เป็นอินเทอร์เฟซที่ใช้งานได้จริง ครอบคลุมการเลือกเฟรมเวิร์กและสถาปัตยกรรม กลยุทธ์การเรนเดอร์ การจัดการสถานะ ประสิทธิภาพ และความยืดหยุ่นท่ามกลางความหลากหลายมหาศาลของเบราว์เซอร์ อุปกรณ์ และสภาพเครือข่ายในโลกจริง ส่วนหน้าคือจุดที่งานต้นน้ำทั้งหมด (UX การออกแบบ เนื้อหา การเข้าถึง การทำให้เป็นสากล) ไปถึงผู้ใช้ได้สำเร็จ หรือล้มเหลวไม่เป็นท่า

สำหรับทีมขนาดใหญ่ ส่วนหน้าเป็นงานที่ท้าทายเป็นพิเศษ เพราะต้องเผชิญสภาพแวดล้อมที่องค์กรควบคุมไม่ได้ เบราว์เซอร์ อุปกรณ์ การเชื่อมต่อ และการตั้งค่าของผู้ใช้ต่างกันมาก และแพลตฟอร์ม (เว็บ) ก็พัฒนาไปไม่หยุด เมื่อขยายขนาด การเลือกเชิงสถาปัตยกรรมจะทบต้น เฟรมเวิร์กที่เลือกวันนี้กำหนดกรอบการจ้างงาน ประสิทธิภาพ และความสามารถในการดูแลไปอีกหลายปี และการตัดสินใจเล็กๆ นับพันเรื่องเกี่ยวกับขนาดบันเดิลและการเรนเดอร์รวมกันกลายเป็นประสบการณ์ที่ผู้ใช้ได้รับจริง มาตรฐานร่วม ไลบรารีคอมโพเนนต์ งบประสิทธิภาพ และรูปแบบสถาปัตยกรรม คือสิ่งที่ป้องกันไม่ให้ทีมอิสระจำนวนมากสร้างผลลัพธ์ที่ช้า ไม่สม่ำเสมอ และเปราะบาง

ความเกี่ยวข้องกับองค์กรขนาดใหญ่และภาครัฐนั้นเด่นชัด องค์กรดูแลแอปพลิเคชันอายุยาวที่ความยั่งยืนของเฟรมเวิร์กและความสามารถในการดูแลสำคัญกว่าความใหม่ และมีหลายทีมที่ต้องทำงานร่วมกัน รัฐบาลให้บริการประชาชนทั้งหมด รวมถึงผู้ที่ใช้อุปกรณ์เก่า การเชื่อมต่อที่ช้าหรือจำกัดปริมาณข้อมูล และเทคโนโลยีช่วยเหลือ ทำให้ประสิทธิภาพ[การปรับปรุงแบบก้าวหน้า](https://en.wikipedia.org/wiki/Progressive_enhancement) (progressive enhancement) และความยืดหยุ่น ไม่ใช่ส่วนเสริมความสวยงาม แต่เป็นเส้นแบ่งระหว่างบริการที่ใช้ได้กับทุกคนกับบริการที่กันคนที่เสียเปรียบที่สุดออกไป บริการของรัฐที่ใช้ได้เฉพาะบนโทรศัพท์รุ่นล่าสุดที่เชื่อมต่อเร็ว ย่อมล้มเหลวต่อพันธกิจของตน

## หลักการสำคัญ

- ส่วนหน้าทำงานในสภาพแวดล้อมที่คุณควบคุมไม่ได้ ให้ออกแบบรองรับความหลากหลายและความล้มเหลว
- เลือกเทคโนโลยีที่น่าเบื่อแต่ทนทานสำหรับระบบอายุยาว ให้ความสำคัญกับความสามารถในการดูแลและการจ้างงาน
- ประสิทธิภาพเป็นฟีเจอร์ และสำหรับผู้ใช้จำนวนมาก เป็นเงื่อนไขของการเข้าถึง
- การปรับปรุงแบบก้าวหน้า: ส่งมอบประสบการณ์แกนกลางที่ใช้งานได้ก่อน แล้วค่อยเพิ่มส่วนเสริม
- ส่งโค้ดให้น้อยลง โค้ดที่เร็วและเชื่อถือได้ที่สุดคือโค้ดที่คุณไม่ต้องส่ง
- เลือกกลยุทธ์การเรนเดอร์ให้เหมาะกับประเภทเนื้อหาและความต้องการของผู้ใช้ ไม่ใช่ตามกระแส
- ความยืดหยุ่น: อินเทอร์เฟซควรลดระดับอย่างนุ่มนวลเมื่อมีสิ่งผิดพลาด ไม่ใช่พังทั้งหมด
- มาตรฐานและฟีเจอร์ของแพลตฟอร์มอยู่ได้นานกว่าเฟรมเวิร์ก ให้พึ่งพาแพลตฟอร์ม

## ข้อแนะนำ

### เลือกเฟรมเวิร์กเพื่อความยั่งยืนและความเหมาะสม ไม่ใช่เพื่อกระแส

เลือกเทคโนโลยีส่วนหน้าตามปัญหา ทีม ระยะเวลาการดูแล และตลาดการจ้างงาน ไม่ใช่ตามสิ่งที่กำลังฮิต สำหรับระบบองค์กรและภาครัฐที่มีอายุยาว ให้เลือกเทคโนโลยีที่เติบโตเต็มที่และมีผู้สนับสนุนดี มีแหล่งบุคลากรมาก ปล่อยรุ่นอย่างมั่นคง และมีเส้นทางอัปเกรดชัดเจน ชั่งต้นทุนรวมของการเปลี่ยนเฟรมเวิร์กไปมา เพราะการเขียนใหม่ทั้งแพงและเสี่ยง เลือกแนวทางที่พึ่ง[มาตรฐานเว็บ](https://en.wikipedia.org/wiki/Web_standards) เพื่อให้การลงทุนอยู่รอดเมื่อเฟรมเวิร์กผลัดเปลี่ยน และแยกโค้ดเฉพาะเฟรมเวิร์กไว้หลังขอบเขตที่ชัดเจน เพื่อไม่ให้แอปพลิเคชันตกเป็นตัวประกันของวงจรชีวิตไลบรารีเดียว

### เลือกกลยุทธ์การเรนเดอร์ให้ตรงกับความต้องการ

กลยุทธ์การเรนเดอร์หลักแต่ละแบบเหมาะกับเนื้อหาต่างกัน การเรนเดอร์ฝั่งเซิร์ฟเวอร์ (SSR) ให้การแสดงผลครั้งแรกเร็วและดีต่อ SEO ([การเพิ่มประสิทธิภาพการค้นหา](https://en.wikipedia.org/wiki/Search_engine_optimization)) และทำงานได้โดยไม่ต้องมี JavaScript ฝั่งไคลเอนต์ เหมาะกับหน้าที่เน้นเนื้อหาและเปิดให้สาธารณะ [การสร้างเว็บไซต์แบบสถิต](https://en.wikipedia.org/wiki/Static_site_generator) (SSG) เรนเดอร์ล่วงหน้าตอนบิลด์เพื่อความเร็วและการแคชสูงสุด เหมาะกับเนื้อหาที่เปลี่ยนไม่บ่อย การเรนเดอร์ฝั่งไคลเอนต์ (CSR) เหมาะกับประสบการณ์แบบแอปที่โต้ตอบมากหลังการยืนยันตัวตน การสตรีมและไฮเดรชันแบบก้าวหน้าส่งและเปิดใช้งานหน้าทีละส่วน เพื่อให้ผู้ใช้เห็นและใช้เนื้อหาได้เร็วขึ้น ระบบขนาดใหญ่จำนวนมากผสมแนวทางเหล่านี้ตามเส้นทาง แทนที่จะเลือกแบบเดียวทั้งระบบ จัดการสถานะอย่างตั้งใจ แยกสถานะฝั่งเซิร์ฟเวอร์ สถานะใน URL และสถานะ UI ภายในออกจากกัน และอย่าจับทุกอย่างรวมไว้ที่ที่เก็บส่วนกลางก้อนใหญ่เพียงก้อนเดียว

### มองประสิทธิภาพเป็นวินัยที่มีงบและมีการวัด

กำหนดงบประสิทธิภาพ (ขีดจำกัดที่ชัดเจนของขนาดบันเดิล จำนวนคำขอ และตัวชี้วัดสำคัญ) และบังคับใช้ใน CI เพื่อให้การถดถอยทำให้บิลด์ล้มเหลว ติดตาม Core Web Vitals (การโหลด การโต้ตอบ และเสถียรภาพทางภาพ) ด้วยการเฝ้าสังเกตผู้ใช้จริงจากอุปกรณ์และเครือข่ายจริง ไม่ใช่แค่การทดสอบในห้องแล็บบนเครื่องเร็ว ลด JavaScript อย่างเด็ดขาด แยกโค้ด (code-split) และ[โหลดแบบเลื่อน](https://en.wikipedia.org/wiki/Lazy_loading) (lazy-load) เพื่อให้ผู้ใช้ดาวน์โหลดเฉพาะที่หน้าจอนั้นต้องการ เลื่อนงานที่ไม่สำคัญออกไป และเลือกใช้ความสามารถของแพลตฟอร์มแทนไลบรารีหนักๆ ปรับภาพและฟอนต์ให้เหมาะสม แคชให้มีประสิทธิผล และวัดผลบนอุปกรณ์ระดับล่างที่เป็นตัวแทนและการเชื่อมต่อที่ช้า

### สร้างด้วยการปรับปรุงแบบก้าวหน้าและความยืดหยุ่น

เริ่มจากพื้นฐานที่ใช้งานได้ด้วย HTML เชิงความหมาย และใช้ JavaScript น้อยที่สุดหรือไม่ใช้เลย แล้วค่อยเพิ่มส่วนเสริมสำหรับไคลเอนต์ที่รองรับ วิธีนี้ทำให้งานหลักยังทำได้เมื่อสคริปต์โหลดไม่สำเร็จ อุปกรณ์เก่า หรือเครือข่ายไม่เสถียร ซึ่งเป็นความจริงที่พบบ่อย ไม่ใช่กรณีขอบ จัดการข้อผิดพลาดอย่างนุ่มนวล แสดงสถานะที่เป็นประโยชน์สำหรับการโหลด ข้อมูลว่าง ข้อผิดพลาด และออฟไลน์ แทนหน้าจอว่างหรือตัวหมุนที่หมุนไม่รู้จบ สำหรับบริการที่ผู้คนพึ่งพา ให้พิจารณาเทคนิคแบบออฟไลน์ก่อน (offline-first) เพื่อให้แอปยังใช้ได้เมื่อการเชื่อมต่อขาดๆ หายๆ และซิงก์เมื่อกลับมาเชื่อมต่อ

### รับรองความเข้ากันได้ข้ามเบราว์เซอร์ ข้ามอุปกรณ์ และกับเทคโนโลยีช่วยเหลือ

ทดสอบกับเบราว์เซอร์ อุปกรณ์ และเทคโนโลยีช่วยเหลือที่ผู้ใช้ของคุณมีจริง โดยอิงข้อมูลวิเคราะห์จริง ไม่ใช่เครื่องของทีมเอง ใช้การปรับปรุงแบบก้าวหน้าและการตรวจจับฟีเจอร์ แทนที่จะสมมติว่าฟีเจอร์ใหม่สุดของแพลตฟอร์มมีให้ใช้ทุกที่ สร้างแบบ[ปรับตามขนาดหน้าจอ](https://en.wikipedia.org/wiki/Responsive_web_design) (ดูบทระบบการออกแบบ) เพื่อให้โค้ดเบสเดียวรองรับตั้งแต่โทรศัพท์ถึงเดสก์ท็อป ผนวกการเข้าถึงและการทำให้เป็นสากลเข้าไปในสถาปัตยกรรมส่วนหน้าตั้งแต่ต้น ไม่ใช่เป็นรอบแก้ไขทีหลัง

### กำกับดูแลส่วนหน้าในฐานะโครงสร้างพื้นฐานร่วม

จัดให้มีไลบรารีคอมโพเนนต์กลาง การตรวจโค้ด (linting) การจัดรูปแบบ และเครื่องมือบิลด์ เพื่อให้ทีมสม่ำเสมอและทำงานได้เต็มที่ กำหนดแนวทางสถาปัตยกรรม (จัดโครงสร้างแอปพลิเคชันอย่างไร จัดการสถานะอย่างไร แยกบันเดิลอย่างไร) และงบประสิทธิภาพที่บังคับใช้ใน CI สำหรับส่วนหน้าขนาดใหญ่มาก ให้พิจารณาสถาปัตยกรรมแบบโมดูลหรือไมโครฟรอนต์เอนด์ (micro-frontend) ที่ให้ทีมปล่อยรุ่นได้อย่างอิสระ แต่ชั่งความซับซ้อนที่เพิ่มขึ้นและต้นทุนด้านประสิทธิภาพให้รอบคอบ เพราะมันไม่ได้ฟรี

## ข้อดีข้อเสียและการแลกเปลี่ยน

| การตัดสินใจ | ข้อดี | ข้อเสีย |
|---|---|---|
| เฟรมเวิร์กยอดนิยมที่เติบโตเต็มที่ | มีแหล่งบุคลากรมาก มั่นคง มีผู้สนับสนุน | อาจมีภาระของระบบเดิม ใช้ฟีเจอร์ใหม่ล่าสุดช้ากว่า |
| เฟรมเวิร์กใหม่ล่าสุด | ฟีเจอร์ทันสมัย ประสิทธิภาพดีขึ้น | เสี่ยงต่อการเปลี่ยนแปลงบ่อย แหล่งบุคลากรน้อย ความยั่งยืนไม่แน่นอน |
| SSR / SSG | แสดงผลครั้งแรกเร็ว ดีต่อ SEO ใช้ได้โดยไม่มี JS | ซับซ้อนที่ฝั่งเซิร์ฟเวอร์หรือตอนบิลด์ มีความท้าทายด้านการแคช |
| CSR (SPA) | โต้ตอบได้ลึก ให้ความรู้สึกแบบแอป | โหลดครั้งแรกช้า พึ่ง JS เสียทั้ง SEO และความยืดหยุ่น |
| JavaScript ฝั่งไคลเอนต์หนัก | ฟีเจอร์เต็มที่ | ประสิทธิภาพแย่บนอุปกรณ์ระดับล่าง เปราะบาง |
| การปรับปรุงแบบก้าวหน้า | ยืดหยุ่น ครอบคลุมทุกคน ใช้ได้ทุกที่ | ต้องออกแบบมากขึ้นเพื่อกำหนดพื้นฐานที่ใช้งานได้ |
| ไมโครฟรอนต์เอนด์ | ทีมปล่อยรุ่นอิสระ ขยายขนาดได้ | ซับซ้อน ไลบรารีที่พึ่งพาซ้ำซ้อน ภาระด้านประสิทธิภาพ |

ข้อแลกเปลี่ยนที่เกิดซ้ำๆ คือความอุดมสมบูรณ์และความสะดวกของนักพัฒนา เทียบกับการเข้าถึง ประสิทธิภาพ และความยืดหยุ่น แนวทางที่ใช้ฝั่งไคลเอนต์หนักๆ สร้างได้สบายและสาธิตได้ดีบนเครื่องเร็ว แต่กันผู้ใช้ที่มีอุปกรณ์และเครือข่ายอ่อนออกไป สำหรับกลุ่มผู้ใช้ในองค์กรและโดยเฉพาะภาครัฐ ให้เอียงน้ำหนักไปทางประสิทธิภาพ การปรับปรุงแบบก้าวหน้า และความทนทาน เพราะต้นทุนของการกันผู้ใช้ออกไปนั้นสูงและมักต่อรองไม่ได้

## คำถามที่ควรคุยกับทีม

1. **เราแยกโค้ดเฉพาะเฟรมเวิร์กอย่างไร เพื่อไม่ให้แอปพลิเคชันตกเป็นตัวประกันของวงจรชีวิตไลบรารีเดียว?** สำหรับระบบองค์กรและภาครัฐที่มีอายุยาว การเปลี่ยนเฟรมเวิร์กไปมาคือค่าใช้จ่ายที่เลี่ยงได้ที่ใหญ่ที่สุด การเขียนใหม่ทั้งแพงและเสี่ยง และไลบรารีที่กำลังฮิตวันนี้จะกำหนดกรอบการจ้างงานและการดูแลไปอีกหลายปี การพึ่งมาตรฐานเว็บและวางโค้ดเฉพาะเฟรมเวิร์กไว้หลังขอบเขตที่ชัดเจน ทำให้ตรรกะธุรกิจและเนื้อหาของคุณอยู่รอดเมื่อเฟรมเวิร์กผลัดเปลี่ยนรอบหน้า ตัดสินใจว่ารอยต่อเหล่านั้นอยู่ตรงไหน และวิศวกรใหม่จะแยกโค้ดของแพลตฟอร์มออกจากโค้ดของเฟรมเวิร์กได้หรือไม่ ลองประเมินว่าการย้ายเฟรมเวิร์กครั้งล่าสุดมีต้นทุนเท่าไร หรือครั้งที่กำลังจะมาจะมีต้นทุนเท่าไร ถ้าตรรกะแกนกลางผูกติดกับ API ของไลบรารีเดียว ให้ประเมินราคาของการพึ่งพากันนั้นก่อนจะปกป้องการเลือกเฟรมเวิร์ก

2. **เราจับคู่กลยุทธ์การเรนเดอร์ตามเส้นทาง หรือบังคับกลยุทธ์เดียวทั้งผลิตภัณฑ์?** การเรนเดอร์ฝั่งเซิร์ฟเวอร์ให้การแสดงผลครั้งแรกเร็วและใช้ได้โดยไม่ต้องมี JavaScript ฝั่งไคลเอนต์สำหรับเนื้อหาสาธารณะ การสร้างแบบสถิตให้ความเร็วสูงสุดสำหรับหน้าที่เปลี่ยนไม่บ่อย และการเรนเดอร์ฝั่งไคลเอนต์เหมาะกับส่วนที่โต้ตอบแบบแอปหลังเข้าสู่ระบบ การบังคับแบบเดียวทั้งระบบจะทำให้หน้าสาธารณะช้าเพราะ JavaScript หนัก หรือทำหน้าเนื้อหาง่ายๆ ให้ซับซ้อนเกินจำเป็น สำหรับภาครัฐนี่คือเรื่องการเข้าถึง เพราะบริการที่ใช้ได้ก็ต่อเมื่อโหลดบันเดิลใหญ่เสร็จแล้ว จะกันผู้ใช้อุปกรณ์เก่าและเครือข่ายช้าออกไป ลองนำเส้นทางสำคัญมาติดป้ายว่าแต่ละเส้นทางใช้กลยุทธ์ใดอยู่จริงในวันนี้ ถ้าหน้าสาธารณะต้องใช้ JavaScript จึงจะแสดงเนื้อหา ให้ตัดสินใจว่านั่นเป็นการเลือกอย่างตั้งใจหรือเกิดขึ้นโดยบังเอิญ

3. **การจัดการสถานะของเรามีวินัยแค่ไหน และเรากำลังรวมทุกอย่างไว้ที่ที่เก็บส่วนกลางก้อนใหญ่เกินไปหรือไม่?** การแยกสถานะฝั่งเซิร์ฟเวอร์ สถานะใน URL และสถานะ UI ภายในออกจากกัน ช่วยป้องกันการพึ่งพากันและพายุการเรนเดอร์ซ้ำที่ทำให้ส่วนหน้าขนาดใหญ่ช้าและเปราะบาง แต่ค่าเริ่มต้นที่ชวนให้ทำคือเททุกอย่างลงที่เก็บส่วนกลางเดียว ปัญหานี้ทบต้นเมื่อขยายขนาด เพราะหลายทีมที่แตะที่เก็บร่วมเดียวกันสร้างการพึ่งพากันที่มองไม่เห็นและประสิทธิภาพที่คาดเดาไม่ได้ ตกลงกันว่าสถานะแต่ละชนิดควรอยู่ที่ไหน และอะไรไม่ควรอยู่ในที่เก็บส่วนกลาง ลองยกคอมโพเนนต์ที่เรนเดอร์ซ้ำมากกว่าที่ควรแล้วไล่หาสาเหตุ ถ้าคำตอบคือที่เก็บกลางที่บวมเกินไป ให้กำหนดขอบเขตก่อนที่การพึ่งพากันจะแข็งตัว

4. **งบประสิทธิภาพของเราคืออะไร ทำให้บิลด์ล้มเหลวใน CI จริงหรือไม่ และวัดบนอุปกรณ์ที่ผู้ใช้ของเรามีอยู่จริงหรือเปล่า?** งบที่ไม่มีใครบังคับใช้ก็เป็นแค่ความหวัง และงบที่วัดเฉพาะบนแล็ปท็อปเร็วๆ ของทีมก็อธิบายผู้ใช้ที่ไม่มีอยู่จริง สำหรับองค์กรขนาดใหญ่ งบคือกลไกเดียวที่ควบคุมขนาดบันเดิลและ Core Web Vitals ไว้ได้ เมื่อทีมหลายสิบทีมเพิ่มฟีเจอร์บนพื้นผิวร่วมเดียวกัน เพราะไม่มีผู้ตรวจคนเดียวที่จะมองเห็นการถดถอยทุกจุดด้วยตา แรงกดดันอีกด้านคือความเร็วในการส่งมอบ บิลด์ที่ล้มเหลวเพราะเกินไปไม่กี่กิโลไบต์ให้ความรู้สึกขวางทาง จนกว่าจะประเมินราคาของผู้ใช้ที่หนีไปซึ่งมันป้องกันไว้ ลองนำงบปัจจุบัน ข้อมูลเฝ้าสังเกตผู้ใช้จริงจากอุปกรณ์ระดับล่างและเครือข่ายช้า และรายการรุ่นที่การถดถอยหลุดออกไป มาดูด้วยกัน ในภาครัฐ ที่พันธกิจคือให้บริการประชาชนทั้งหมดรวมถึงผู้ใช้โทรศัพท์เก่าและข้อมูลจำกัด ให้ผูกงบกับผู้ใช้ที่ช้าที่สุดหนึ่งในสิบ ไม่ใช่ค่ากลาง และทำให้ด่านใน CI เป็นเรื่องต่อรองไม่ได้

5. **บริการใดของเราต้องใช้ได้โดยไม่มี JavaScript ฝั่งไคลเอนต์ และเราทดสอบเส้นทางนั้นจริงหรือไม่?** การปรับปรุงแบบก้าวหน้าอ้างได้ง่ายและพังเงียบๆ ได้ง่าย เพราะเส้นทางที่เสริมแล้วคือเส้นทางที่นักพัฒนาใช้ทุกวัน ขณะที่พื้นฐานเน่าอยู่โดยไม่มีใครทดสอบ การตัดสินใจเรื่องนี้อย่างตั้งใจสำคัญเมื่อขยายขนาด เพราะหลายทีมที่ส่งขึ้นแพลตฟอร์มเดียวกันจะสมมติว่าสคริปต์โหลดได้เสมอ เว้นแต่มาตรฐานร่วมบอกไว้เป็นอย่างอื่น และการพึ่งพาที่แข็งเพียงจุดเดียวอาจทำให้งานหลักพังสำหรับทุกคนที่บันเดิลโหลดไม่สำเร็จ ข้อแลกเปลี่ยนนี้มีอยู่จริง พื้นฐานที่ใช้ได้โดยไม่มี JavaScript ต้องใช้แรงออกแบบและจำกัดวิธีสร้างการโต้ตอบ ลองนำเส้นทางผู้ใช้สำคัญ การทดสอบที่โหลดแต่ละเส้นทางโดยปิดสคริปต์หรือให้สคริปต์ล้มเหลว และหลักฐานว่าสคริปต์โหลดไม่สำเร็จบ่อยแค่ไหนในสนามจริง มาดูด้วยกัน สำหรับบริการสาธารณะ แบบฟอร์มสวัสดิการหรือภาษีที่พังเมื่อสคริปต์หมดเวลาเพียงตัวเดียว ไม่ใช่ประสบการณ์ที่ลดระดับ แต่คือประชาชนที่ทำหน้าที่ตามกฎหมายไม่สำเร็จ จึงควรถือพื้นฐานนี้เป็นข้อกำหนดด้านการปฏิบัติตามกฎ ไม่ใช่ของเสริมที่ดีถ้ามี

6. **ไมโครฟรอนต์เอนด์คุ้มกับความซับซ้อนของมันเมื่อไรจริงๆ และใครเป็นผู้ตัดสินก่อนที่ทีมจะหยิบมาใช้?** การปล่อยรุ่นอย่างอิสระของแต่ละทีมน่าสนใจ แต่ไมโครฟรอนต์เอนด์มาพร้อมความซับซ้อนแบบระบบกระจาย ไลบรารีที่พึ่งพาซ้ำซ้อน และภาษีด้านประสิทธิภาพที่ผู้ใช้จ่ายด้วยการโหลดที่ช้าลง หากไม่มีจุดตัดสินใจร่วม ทีมที่กระตือรือร้นจะนำมาใช้เพราะความสะดวกขององค์กรก่อนที่ขนาดจะคุ้มกับต้นทุน และทั้งผลิตภัณฑ์ต้องรับภาระส่วนเกินนั้น สิ่งที่ต้องชั่งอีกด้านคืออิสระของทีม ทีมที่ส่งบนโค้ดเบสร่วมเดียวกันอาจขวางกันเอง และเมื่อขนาดใหญ่จริง การพึ่งพากันนั้นก็เป็นปัญหาราคาแพงอีกแบบ ลองนำจำนวนทีมที่แตะพื้นผิวนั้น ความติดขัดในการปล่อยรุ่นที่เกิดขึ้นจริงในวันนี้ และการประเมินที่วัดได้ของการที่เพย์โหลดซ้ำซ้อนซึ่งการแยกจะก่อขึ้น มาประกอบการพิจารณา สำหรับแพลตฟอร์มองค์กรและภาครัฐ ที่การตัดสินใจเชิงสถาปัตยกรรมผูกมัดหลายทีมไปอีกหลายปีและต้องผ่านการตรวจสอบและการส่งมอบงาน ให้กำหนดเกณฑ์ที่ชัดเจนและบันทึกไว้ พร้อมเจ้าของที่อนุมัติการย้าย แทนที่จะปล่อยให้แต่ละทีมตัดสินใจเอง

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ความเร็วและการเข้าถึงสำคัญทั้งคู่เมื่อทุกการสมัครมีความหมาย จึงควรต้านทานแรงดึงดูดของแอปหน้าเดียว (single-page app) ที่หนักสำหรับหน้าสาธารณะ เรนเดอร์ฝั่งเซิร์ฟเวอร์สำหรับหน้าการตลาดและขั้นตอนสมัครใช้งาน เพื่อให้โหลดเร็วบนโทรศัพท์ระดับกลางและข้อมูลที่สัญญาณไม่นิ่งที่ลูกค้ากลุ่มแรกของคุณใช้ และเก็บการโต้ตอบฝั่งไคลเอนต์ไว้สำหรับแอปหลังเข้าสู่ระบบ ตั้งงบขนาดบันเดิลง่ายๆ หนึ่งข้อใน CI เพื่อไม่ให้ไลบรารีที่ไม่ระวังทำให้หน้าบวมโดยไม่รู้ตัว และพึ่งมาตรฐานเว็บเพื่อให้โค้ดเบสเล็กๆ ดูแลง่ายเมื่อคุณจ้างคนเพิ่ม

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญส่วนหน้าโดยเฉพาะและงบจำกัด ให้เลือกเฟรมเวิร์กกระแสหลักที่มีผู้สนับสนุนดีหรือเครื่องมือสร้างเว็บไซต์แบบโฮสต์ แทนของที่สร้างเฉพาะ เพื่อให้คุณจ้างจากแหล่งบุคลากรขนาดใหญ่ และซื้อการดูแลแทนที่จะจ้างคนมาดูแลเอง มองการเลือกนี้เป็นเรื่องความทนทาน ตัวเลือกที่ถูกที่สุดคือตัวเลือกที่คุณไม่ถูกบังคับให้เขียนใหม่ในสองปี ยืนยันให้ได้หน้าที่เร็วและเป็นมิตรกับมือถือ พร้อมมาร์กอัปที่เข้าถึงได้ตั้งแต่แรก เพราะหน้าชำระเงินที่ช้าหรือพังทำให้เสียลูกค้าที่คุณเสียไม่ได้

**องค์กรขนาดใหญ่.** ปัญหาคือความสม่ำเสมอข้ามหลายทีม ได้แก่ไลบรารีคอมโพเนนต์กลาง รูปแบบสถาปัตยกรรมที่ตกลงร่วมกัน เครื่องมือตรวจโค้ดและบิลด์ และงบประสิทธิภาพที่บังคับใช้ใน CI เพื่อไม่ให้ทีมใดทำให้ภาพรวมถดถอยโดยเงียบๆ เลือกเฟรมเวิร์กเพื่อความยั่งยืนและการจ้างงาน ไม่ใช่ความใหม่ แยกโค้ดเฉพาะเฟรมเวิร์กไว้หลังขอบเขตเพื่อรอดการย้ายครั้งต่อไป และจับคู่กลยุทธ์การเรนเดอร์ตามแต่ละพื้นผิว บริหารส่วนหน้าเป็นโครงสร้างพื้นฐานร่วมด้วยการเฝ้าสังเกตผู้ใช้จริง ธรรมาภิบาล และบันทึกที่ตรวจสอบได้ว่าทำไมจึงเลือกสถาปัตยกรรมแต่ละอย่าง

**ภาครัฐ.** คุณให้บริการประชาชนทั้งหมด รวมถึงผู้ที่ใช้อุปกรณ์เก่า การเชื่อมต่อช้าหรือจำกัดข้อมูล และเทคโนโลยีช่วยเหลือ ดังนั้นการปรับปรุงแบบก้าวหน้าและประสิทธิภาพจึงเป็นพันธะ ไม่ใช่ส่วนเสริมความสวยงาม กำหนดให้พื้นฐานที่ใช้ได้โดยไม่มี JavaScript เป็นกฎเด็ดขาดสำหรับบริการที่ประชาชนใช้ กำหนดงบของหน้าตามผู้ใช้ที่ช้าที่สุด ไม่ใช่ค่ากลาง และทำให้งานหลักยังทำสำเร็จได้เมื่อสคริปต์ล้มเหลว เรื่องการจัดซื้อจัดจ้างและความโปร่งใสก็เกี่ยวข้อง ให้เลือกเทคโนโลยีที่ทนทานและอิงมาตรฐาน หลีกเลี่ยงการผูกขาดกับผู้ขายรายเดียว บันทึกข้อกำหนดด้านการเข้าถึงและประสิทธิภาพไว้ในสัญญา และต้องแสดงได้ว่าบริการใช้ได้กับผู้ใช้ที่เสียเปรียบที่สุด ไม่ใช่แค่อุปกรณ์สาธิต

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัประยะเริ่มต้นแห่งหนึ่งเกือบสร้างเว็บไซต์การตลาดและขั้นตอนสมัครใช้งานเป็นแอปหน้าเดียวที่หนัก แต่ลูกค้าเป้าหมายคือผู้ซื้อที่มักใช้โทรศัพท์ระดับกลางบนข้อมูลมือถือที่สัญญาณไม่นิ่ง ผู้ก่อตั้งสองคนจึงเรนเดอร์หน้าสาธารณะฝั่งเซิร์ฟเวอร์ให้โหลดเร็วและใช้ได้ก่อนที่ JavaScript จะทำงาน และเก็บการโต้ตอบฝั่งไคลเอนต์ไว้สำหรับแอปหลังเข้าสู่ระบบ พวกเขาตั้งงบขนาดบันเดิลง่ายๆ ใน CI เพื่อไม่ให้ไลบรารีที่ไม่ระวังทำให้หน้าบวมโดยไม่รู้ตัว การโหลดครั้งแรกที่เบาและเร็วช่วยเพิ่มจำนวนผู้สมัครได้อย่างวัดผลได้ และการพึ่งมาตรฐานเว็บทำให้โค้ดเบสเล็กๆ ดูแลง่ายเมื่อจ้างคนเพิ่ม

**องค์กรขนาดใหญ่.** บริษัทบริการทางการเงินแห่งหนึ่งปรับปรุงชุดแอปพลิเคชันภายในและสำหรับลูกค้าที่กระจัดกระจาย โดยทำให้เป็นมาตรฐานบนเฟรมเวิร์กที่เติบโตเต็มที่ ไลบรารีคอมโพเนนต์ร่วม และงบประสิทธิภาพที่บังคับใช้ใน CI กลยุทธ์การเรนเดอร์เลือกตามแต่ละพื้นผิว คือหน้าที่เรนเดอร์ฝั่งเซิร์ฟเวอร์และแคชได้สำหรับการตลาดและเนื้อหาสาธารณะ และแอปที่เรนเดอร์ฝั่งไคลเอนต์หลังเข้าสู่ระบบสำหรับแดชบอร์ดที่โต้ตอบ งบบันเดิลและการเฝ้าสังเกตผู้ใช้จริงจับการถดถอยได้ก่อนปล่อยรุ่น ทำให้เวลาโหลดเร็วทั่วทุกทีมของบริษัท และลดความเสี่ยงจากการเปลี่ยนเฟรมเวิร์กบ่อยที่เคยบังคับให้เขียนใหม่อย่างสิ้นเปลือง

**ภาครัฐ.** ทีมบริการดิจิทัลแห่งชาติสร้างบริการสำหรับประชาชนโดยถือการปรับปรุงแบบก้าวหน้าเป็นกฎเด็ดขาด ทุกบริการทำงานได้ด้วย HTML เชิงความหมายและการเรนเดอร์ฝั่งเซิร์ฟเวอร์ก่อน และ JavaScript เป็นเพียงส่วนเสริม ทำให้มั่นใจว่าบริการทำงานได้บนโทรศัพท์เก่า การเชื่อมต่อในชนบทที่ช้า และเทคโนโลยีช่วยเหลือ ซึ่งเป็นกลุ่มที่รัฐบาลกันออกไปไม่ได้ งบประสิทธิภาพทำให้หน้าเบาและเร็วบนอุปกรณ์ระดับล่าง และการลดระดับอย่างนุ่มนวลหมายความว่าสคริปต์ที่ล้มเหลวจะไม่ขวางใครจากการยื่นคำขอสวัสดิการ ผลคือบริการที่เร็ว ยืดหยุ่น เข้าถึงได้ และใช้ได้กับประชาชนทั้งหมด

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

การเลือกด้านวิศวกรรมส่วนหน้าขับเคลื่อนรายได้ การเข้าถึง และต้นทุน ประสิทธิภาพผูกกับอัตราการเปลี่ยนเป็นลูกค้า การมีส่วนร่วม และการทำงานให้สำเร็จโดยตรง ประสบการณ์ที่เร็วกว่าทำได้ดีกว่าประสบการณ์ที่ช้ากว่าอย่างวัดผลได้ และสำหรับผู้ใช้ที่มีอุปกรณ์อ่อน ประสิทธิภาพคือเส้นแบ่งระหว่างการใช้บริการกับการทิ้งไป การปรับปรุงแบบก้าวหน้าและการรองรับหลายอุปกรณ์ขยายกลุ่มเป้าหมายที่เข้าถึงได้ ซึ่งสำหรับภาครัฐคือพันธกิจ และสำหรับองค์กรคือส่วนแบ่งตลาด การเลือกเฟรมเวิร์กและสถาปัตยกรรมที่ดีลดความถี่และต้นทุนของการเขียนใหม่ ซึ่งเป็นค่าใช้จ่ายที่เลี่ยงได้ที่ใหญ่ที่สุดในวิศวกรรมส่วนหน้า

ด้านต้นทุนรวมตลอดอายุการใช้งาน (TCO) ต้นทุนของการนำมาใช้คือวินัยของงบประสิทธิภาพและการทดสอบ แรงที่ใช้กับการปรับปรุงแบบก้าวหน้า และการลงทุนในเครื่องมือร่วมและไลบรารีคอมโพเนนต์ ต้นทุนของการไม่นำมาใช้ต้องจ่ายด้วยประสบการณ์ที่ช้าซึ่งทำให้เสียผู้ใช้และรายได้ การกันผู้ใช้อุปกรณ์ระดับล่างและเทคโนโลยีช่วยเหลือออกไป (พร้อมความเสี่ยงทางกฎหมายในภาครัฐ) แอปพลิเคชันเปราะบางที่พังในสนามจริง และการเปลี่ยนเฟรมเวิร์กกับการเขียนใหม่ที่แพงเพราะวิ่งตามกระแส ปัญหาส่วนหน้าปรากฏเป็นการละทิ้งของผู้ใช้และภาระซัพพอร์ตที่กระจายตัว ไม่ใช่รายการค่าใช้จ่ายเดียว จึงลงทุนไม่พอได้ง่าย

เมื่อต้องเสนอผู้บริหาร ให้เชื่อม Core Web Vitals และเวลาโหลดเข้ากับกรวยการเปลี่ยนเป็นลูกค้าและการทำงานให้สำเร็จ ประเมินจำนวนผู้ใช้ที่ถูกกันออกไปโดยแนวทางฝั่งไคลเอนต์หนัก และประเมินต้นทุนของการเขียนใหม่ที่ผ่านมาหรือกำลังจะมา เทียบกับความมั่นคงของสถาปัตยกรรมที่ทนทานและอิงมาตรฐาน เล่างบประสิทธิภาพและการปรับปรุงแบบก้าวหน้าว่าเป็นการลดความเสี่ยงและขยายการเข้าถึง

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **การวิ่งตามเฟรมเวิร์ก**: เขียนใหม่บนไลบรารีล่าสุด สร้างความผันผวนโดยผู้ใช้ไม่ได้ประโยชน์
- **ประสบการณ์ที่ต้องมี JavaScript เท่านั้น**: ไม่มีอะไรทำงานจนกว่าบันเดิลใหญ่จะโหลดและรัน กันผู้ใช้จำนวนมากออกไป
- **ทดสอบเฉพาะบนอุปกรณ์เร็ว**: แล็ปท็อปรุ่นเรือธงของทีมซ่อนประสบการณ์จริงของผู้ใช้
- **ไม่สนใจขนาดบันเดิล**: ไลบรารีที่พึ่งพาโตไม่จำกัดจนหน้าช้าทุกที่
- **ไม่มีงบประสิทธิภาพ**: การถดถอยสะสมอย่างเงียบๆ ทีละรุ่น
- **ความล้มเหลวแบบหน้าจอว่าง**: ไม่มีสถานะโหลด ว่าง ข้อผิดพลาด หรือออฟไลน์ คำขอที่ล้มเหลวทำให้หน้าพัง
- **สถานะส่วนกลางที่รวมศูนย์เกินไป**: ทุกอย่างอยู่ในที่เก็บเดียว สร้างการพึ่งพากันและพายุการเรนเดอร์ซ้ำ
- **ไมโครฟรอนต์เอนด์ก่อนเวลา**: ความซับซ้อนแบบระบบกระจายและเพย์โหลดซ้ำซ้อน โดยไม่มีขนาดที่คุ้มกับต้นทุน
- **ละเลยการเข้าถึงและ i18n ในสถาปัตยกรรม**: มาเพิ่มทีหลังด้วยต้นทุนสูง

## แบบจำลองความเป็นผู้ใหญ่

**ระดับ 1 เริ่มต้น.** ส่วนหน้าแบบเฉพาะกิจที่แต่ละทีมสร้างเองโดยไม่มีมาตรฐานร่วม โค้ดฝั่งไคลเอนต์หนัก ไม่มีงบประสิทธิภาพ ทดสอบเฉพาะบนอุปกรณ์ของทีมเอง การเลือกเฟรมเวิร์กทำตามความชอบหรือกระแส และสคริปต์ที่ล้มเหลวอาจทำให้ผู้ใช้จ้องหน้าจอว่าง

**ระดับ 2 พัฒนา.** บางทีมใช้เครื่องมือร่วมและไลบรารีคอมโพเนนต์ แต่การปฏิบัติไม่สม่ำเสมอทั้งองค์กร วัดประสิทธิภาพเป็นครั้งคราวแทนที่จะมีงบหรือบังคับใช้ กลยุทธ์การเรนเดอร์มักเหมือนกันหมดไม่ว่าเนื้อหาจะเป็นแบบใด และการทดสอบข้ามอุปกรณ์มีจำกัดและทำด้วยมือ

**ระดับ 3 สร้างมาตรฐาน.** เลือกเฟรมเวิร์กและสถาปัตยกรรมอย่างตั้งใจเพื่อความยั่งยืน และบันทึกไว้และบังคับใช้ทั้งองค์กร จับคู่กลยุทธ์การเรนเดอร์ตามแต่ละพื้นผิว การปรับปรุงแบบก้าวหน้าและการลดระดับอย่างนุ่มนวลเป็นมาตรฐาน และไลบรารีคอมโพเนนต์ร่วม การตรวจโค้ด และเครื่องมือบิลด์ใช้กับทุกทีม การรองรับข้ามเบราว์เซอร์ การเข้าถึง และการทำให้เป็นสากลถูกสร้างไว้ในตัว ไม่ใช่มาเพิ่มทีหลัง

**ระดับ 4 บริหารจัดการ.** ส่วนหน้าถูกวัดและควบคุมด้วยข้อมูล งบประสิทธิภาพถูกบังคับใช้ใน CI เพื่อให้การถดถอยทำให้บิลด์ล้มเหลว และติดตาม Core Web Vitals ด้วยการเฝ้าสังเกตผู้ใช้จริงจากอุปกรณ์ระดับล่างและเครือข่ายช้าจริง เทียบกับเส้นฐานที่ชัดเจน รายงานและทบทวนขนาดบันเดิล ความครอบคลุมของสถานะข้อผิดพลาดและออฟไลน์ และสัดส่วนผู้ใช้ที่ได้รับบริการบนการเชื่อมต่อที่ช้าที่สุด เพื่อให้การตัดสินใจอยู่บนหลักฐานแทนความเห็น

**ระดับ 5 ประสานทั้งระบบ.** ประสิทธิภาพ ความยืดหยุ่น และการเข้าถึงได้รับการปรับปรุงอย่างต่อเนื่องและผูกกับผลลัพธ์ทางธุรกิจทั่วทั้งองค์กร ส่วนหน้าพึ่งมาตรฐานเว็บเพื่อความทนทาน แยกการพึ่งพาเฟรมเวิร์กออกเพื่อให้การย้ายถูก และปรับสถาปัตยกรรมอย่างยืดหยุ่นตามที่อุปกรณ์ แพลตฟอร์ม และข้อมูลผู้ใช้จริงเปลี่ยนไป ประชาชนทั้งหมดและทุกอุปกรณ์เป็นเรื่องสำคัญอันดับแรก และแนวปฏิบัติส่วนหน้าผสานกับการออกแบบ การเข้าถึง และการวางแผนผลิตภัณฑ์ ไม่ใช่เรื่องแยกต่างหาก

## ประเด็นชวนคุย

- จะตัดสินอย่างไรว่าเมื่อไรการย้ายเฟรมเวิร์กคุ้มกับต้นทุนและความเสี่ยง
- Core Web Vitals และงบบันเดิลใดควรเป็นเกณฑ์เด็ดขาดที่ทำให้บิลด์ล้มเหลว
- การปรับปรุงแบบก้าวหน้าจำเป็นอย่างยิ่งที่ใด และแอปฝั่งไคลเอนต์ยอมรับได้ที่ใด
- จะรักษาสถาปัตยกรรมส่วนหน้าให้สม่ำเสมอข้ามหลายทีมที่เป็นอิสระได้อย่างไร
- ไมโครฟรอนต์เอนด์คุ้มกับความซับซ้อนของมันเมื่อไรจริงๆ
- ควรสร้างการทดสอบบนอุปกรณ์จริงและเครือข่ายช้าไว้ในสายงานอย่างไร

## ข้อสรุปสำคัญ

- ส่วนหน้าทำงานในสภาพแวดล้อมที่คุณควบคุมไม่ได้ ออกแบบรองรับความหลากหลายและความล้มเหลว
- เลือกเทคโนโลยีที่ทนทานและมีผู้สนับสนุนดีสำหรับระบบอายุยาว และพึ่งมาตรฐานเว็บ
- จับคู่กลยุทธ์การเรนเดอร์ (SSR, SSG, CSR, การสตรีม) กับเนื้อหาและความต้องการ ซึ่งมักผสมกันตามเส้นทาง
- มองประสิทธิภาพเป็นวินัยที่มีงบและมีการวัด บังคับใช้ใน CI ด้วยข้อมูลผู้ใช้จริง
- สร้างด้วยการปรับปรุงแบบก้าวหน้า เพื่อให้ประสบการณ์แกนกลางใช้ได้ทุกที่
- ส่ง JavaScript ให้น้อยลง แยกโค้ด โหลดแบบเลื่อน และเลือกใช้ความสามารถของแพลตฟอร์ม
- โดยเฉพาะสำหรับภาครัฐ ประสิทธิภาพและความยืดหยุ่นเป็นเงื่อนไขของการเข้าถึงอย่างเท่าเทียม
