# 3.16 เกตเวย์เอพีไอ และ เซอร์วิสเมช

## ภาพรวมและแรงจูงใจ

ทันทีที่คุณแยกโปรแกรมก้อนเดียวออกเป็นหลายบริการ คำถามใหม่ก็ปรากฏขึ้น: ใครดูแลทราฟฟิกระหว่างบริการเหล่านั้น และทราฟฟิกที่เข้ามาจากภายนอก? คุณตอบคำถามนี้แย่ได้ด้วยการกระจายเรื่องเดียวกัน (การยืนยันตัวตน การลองใหม่ timeout ขีดจำกัดอัตรา การบันทึก) ไปใส่ในทุกบริการด้วยมือ หรือตอบได้ดีด้วยการผลักเรื่องเหล่านั้นลงไปในชั้นร่วมที่ทุกบริการได้รับไปฟรี ๆ บทนี้ว่าด้วยชั้นแบบนั้นสองชั้น [API gateway](https://en.wikipedia.org/wiki/API_management) อยู่ที่ประตูหน้าและจัดการทราฟฟิกที่เข้ามาจากไคลเอนต์ [Service mesh](https://en.wikipedia.org/wiki/Service_mesh) อยู่ระหว่างบริการของคุณและจัดการทราฟฟิกที่ไหลระหว่างกัน ทั้งสองแก้ปัญหาที่เกี่ยวข้องกันในที่ต่างกัน และการสับสนระหว่างสองอย่างนี้เป็นความผิดพลาดที่พบบ่อยและแพง

วงการตั้งชื่อทิศทางทราฟฟิกสองแบบด้วยอุปมาทิศ ทราฟฟิกเหนือ-ใต้ (north-south) คือทราฟฟิกที่ข้ามขอบเขตของระบบคุณ: แอปมือถือ เบราว์เซอร์ หรือพาร์ทเนอร์ที่เรียกเข้ามา ทราฟฟิกตะวันออก-ตะวันตก (east-west) คือทราฟฟิกที่อยู่ภายในระบบของคุณ: บริการ A เรียกบริการ B ซึ่งเรียกบริการ C เพื่อตอบคำขอเดียว API gateway เป็นผู้เชี่ยวชาญด้านเหนือ-ใต้ Service mesh เป็นผู้เชี่ยวชาญด้านตะวันออก-ตะวันตก การรักษาความแตกต่างนี้ให้คมคือแนวคิดที่มีประโยชน์ที่สุดในบทนี้ เพราะมันบอกว่าเครื่องมือใดเป็นเจ้าของนโยบายใด และกันไม่ให้คุณทำงานเดียวกันซ้ำสองรอบ

สำหรับทีมขนาดใหญ่ ชั้นเหล่านี้คือวิธีที่คุณบังคับใช้นโยบายครั้งเดียวแทนที่จะเป็นร้อยครั้ง เมื่อการยืนยันตัวตน การเข้ารหัสระหว่างทาง และขีดจำกัดอัตราอยู่ในชั้นร่วม การแก้ไขด้านความมั่นคงปลอดภัยจะไปถึงทุกบริการในวันที่คุณปล่อยชั้นนั้น แทนที่จะรอคิวงานค้างนับร้อย ในบริบทองค์กรขนาดใหญ่และภาครัฐ การรวมศูนย์นั้นมักเป็นประเด็นหลัก ผู้ตรวจสอบต้องการจุดเดียวที่พิสูจน์ได้ซึ่งตรวจสิทธิ์การเข้าถึงและเข้ารหัสทราฟฟิก และ gateway หรือ mesh ร่วมให้สิ่งนั้นได้ ซึ่งก็คือจุดบังคับใช้นโยบาย (policy enforcement point) บทนี้ต่อยอดจากรูปแบบสถาปัตยกรรมในบทที่ 3.2 ความจริงของระบบแบบกระจายในบทที่ 3.3 และพื้นฐานเครือข่ายในบทที่ 3.13 และแปลงสิ่งเหล่านั้นเป็นแนวทางที่เป็นรูปธรรมว่าใครจัดการทราฟฟิกของคุณ

## หลักการสำคัญ

- แยกเหนือ-ใต้ (gateway) ออกจากตะวันออก-ตะวันตก (mesh) ให้แต่ละอย่างเป็นเจ้าของทิศทางของตน
- ผลักเรื่องที่ตัดผ่านทุกบริการ (cross-cutting concerns) ลงชั้นร่วม เพื่อเขียนครั้งเดียวแทนที่จะเขียนรายบริการ
- นำ service mesh มาใช้เมื่อจำนวนบริการทำให้การเดินสายรายบริการเป็นต้นทุนที่ใหญ่กว่า
- กำหนดจุดบังคับใช้นโยบายหนึ่งจุดต่อเรื่องหนึ่ง อย่าปล่อยให้ gateway และ mesh ทำงานเดียวกันทั้งคู่
- ให้บริการบาง: แพลตฟอร์มจัดการการขนส่ง บริการจัดการตรรกะทางธุรกิจ
- ให้ความสำคัญกับเครือข่ายแบบ zero trust ที่อิงตัวตน มากกว่าความเชื่อใจที่อิงตำแหน่งในเครือข่าย
- ซื้อความซับซ้อนในการดำเนินงานของ mesh ด้วยสายตาที่เปิดกว้าง และวัดว่าคุ้มหรือไม่

## ข้อแนะนำ

### เข้าใจว่า API gateway ทำอะไร

API gateway คือจุดเข้าเดียวที่อยู่หน้าบริการของคุณและเป็นตัวกลางของทุกคำขอจากโลกภายนอก ในรูปแบบที่ง่ายที่สุดมันคือ[รีเวิร์สพร็อกซี](https://en.wikipedia.org/wiki/Reverse_proxy)ที่ฉลาด (เซิร์ฟเวอร์ที่รับคำขอจากไคลเอนต์แล้วส่งต่อไปยังแบ็กเอนด์ที่ถูกต้อง) แต่ gateway สมกับชื่อด้วยการทำมากกว่าการส่งต่อ มันกำหนดเส้นทางแต่ละคำขอไปยังบริการที่ถูกต้องตามพาธ โฮสต์ หรือเฮดเดอร์ มันยืนยันตัวตนผู้เรียก (ตรวจว่าเป็นใคร) และอนุญาตคำขอ (ตรวจว่าทำอะไรได้บ้าง) บริการที่อยู่ข้างหลังจึงเชื่อได้ว่าคำขอผ่านประตูหน้ามาแล้ว มันบังคับใช้ขีดจำกัดอัตรา (rate limiting, จำกัดจำนวนคำขอต่อไคลเอนต์ในช่วงเวลาหนึ่ง) และโควตา (จำกัดการใช้งานรวมในช่วงเวลาที่ยาวกว่า) เพื่อไม่ให้ไคลเอนต์ที่ส่งเสียงดังหรือล่วงละเมิดรายเดียวแย่งทรัพยากรจากรายอื่น

Gateway ยังปรับรูปทราฟฟิกด้วย การแปลงคำขอ (request transformation) เขียนเฮดเดอร์ใหม่ แปลระหว่างโปรโตคอล หรือปรับรูปแบบของไคลเอนต์เก่าให้ตรงกับที่บริการใหม่คาดหวัง การประกอบ API (API composition) ให้ gateway กระจายคำขอขาเข้าหนึ่งรายการไปยังหลายบริการแล้วเย็บการตอบสนองรวมเป็นหนึ่งเดียว ไคลเอนต์จึงเรียกครั้งเดียวแทนหกครั้ง การรองรับเวอร์ชันให้คุณรัน API v1 และ v2 คู่กันและส่งไคลเอนต์แต่ละรายไปยังเวอร์ชันที่มันคาดหวัง ซึ่งซื้อพื้นที่ให้คุณพัฒนาต่อได้โดยไม่ทำให้ใครพัง การรวมเรื่องเหล่านี้ไว้ที่ขอบทำให้บริการของคุณจดจ่อกับตรรกะทางธุรกิจ และให้ที่เดียวสำหรับสังเกต รักษาความปลอดภัย และควบคุมอัตราทุกสิ่งที่เข้ามา การออกแบบ API ที่ gateway อยู่หน้าเป็นเรื่องของบทที่ 2.3 และการตรวจตัวตนที่มันทำอิงบทที่ 4.7

### ใช้รูปแบบ backend-for-frontend สำหรับไคลเอนต์ที่ต่างกัน

API เอนกประสงค์ตัวเดียวมักให้บริการเว็บแอป แอปมือถือ และการเชื่อมต่อพาร์ทเนอร์พร้อมกัน และให้บริการทุกฝ่ายได้แย่เล็กน้อย ไคลเอนต์มือถือต้องการข้อมูลขนาดเล็กและรอบการเดินทางน้อยเพราะแบนด์วิดท์และแบตเตอรี่มีน้อย ไคลเอนต์เว็บรับการตอบสนองที่ถี่กว่าและมั่งคั่งกว่าได้ ส่วนพาร์ทเนอร์ต้องการสัญญาที่คงที่และไม่สร้างเซอร์ไพรส์ รูปแบบ [backend for frontend](https://en.wikipedia.org/wiki/Backend_for_frontend) (BFF) แก้ความตึงเครียดนี้ด้วยการให้ไคลเอนต์แต่ละประเภทมี gateway บางของตัวเองที่ปรับให้เข้ากับความต้องการของไคลเอนต์นั้น และอยู่หน้าบริการร่วมที่อยู่ข้างหลัง

BFF คือ gateway ที่มีกลุ่มผู้ใช้แคบกว่า BFF ของมือถือประกอบและตัดทอนการตอบสนองเพื่อให้แอปเรียกครั้งเดียวอย่างมีประสิทธิภาพ BFF ของเว็บเปิดรูปทรงที่เต็มกว่า BFF ของพาร์ทเนอร์ถือสัญญาที่เปลี่ยนช้าและกำกับเวอร์ชันอย่างระมัดระวัง แต่ละทีมพัฒนา BFF ของตนได้โดยไม่ต้องรอทีมอื่น ซึ่งมักเป็นข้อได้เปรียบที่แท้จริง เพราะลดการพึ่งพากันระหว่างทีมไคลเอนต์ ต้นทุนคือชิ้นส่วนที่เคลื่อนไหวมากขึ้นและตรรกะที่ซ้ำกันระหว่าง BFF บ้าง จึงควรสงวนรูปแบบนี้ไว้สำหรับกรณีที่ความต้องการของไคลเอนต์แตกต่างกันจริง เมื่อทุกไคลเอนต์ต้องการสิ่งเดียวกัน gateway ตัวเดียวง่ายกว่าและดีกว่า

### เข้าใจว่า service mesh ทำอะไร

Service mesh จัดการทราฟฟิกตะวันออก-ตะวันตกระหว่างบริการของคุณ โดยไม่ต้องให้บริการเหล่านั้นเปลี่ยนโค้ด mesh แบบคลาสสิกทำงานด้วยการติดตั้งพร็อกซี[ไซด์คาร์](https://en.wikipedia.org/wiki/Sidecar_pattern) (sidecar, โพรเซสพร็อกซีขนาดเล็กที่รันอยู่ข้างอินสแตนซ์ของแต่ละบริการและดักทราฟฟิกเครือข่ายทั้งหมดของมัน) บริการของคุณคิดว่ากำลังคุยกับบริการอื่นโดยตรง แต่ความจริงมันคุยกับไซด์คาร์ในเครื่อง ซึ่งเป็นผู้ทำการเรียกเครือข่ายจริง เมื่อทุกคำขอไหลผ่านพร็อกซีที่แพลตฟอร์มควบคุม mesh จึงบังคับพฤติกรรมให้เหมือนกันทุกบริการ ทุกภาษา โดยไม่มีไลบรารีร่วมที่ต้องคอยซิงก์

มันบังคับอะไรบ้าง? หนึ่ง [mutual TLS](https://en.wikipedia.org/wiki/Mutual_authentication) (mTLS) ที่ทั้งสองฝั่งของทุกการเชื่อมต่อแสดงใบรับรองและเข้ารหัสทราฟฟิก การเรียกระหว่างบริการจึงยืนยันตัวตนและเป็นส่วนตัวโดยค่าเริ่มต้น สอง การจัดการทราฟฟิก: mesh เลื่อนทราฟฟิกเปอร์เซ็นต์เล็ก ๆ ไปยังเวอร์ชันใหม่สำหรับการปล่อยแบบ canary แบ่งทราฟฟิกตามเฮดเดอร์เพื่อทดสอบ หรือสะท้อนทราฟฟิกไปยังบริการเงา (shadow) สาม ความยืดหยุ่น: การลองใหม่ timeout และ circuit breaking (รูปแบบในบทที่ 2.20) ที่ใช้ที่ชั้นแพลตฟอร์ม ตั้งค่าด้วยนโยบายแทนที่จะเขียนโค้ดในแต่ละบริการ สี่ ความสามารถในการสังเกตระบบ: เพราะทุกคำขอผ่านพร็อกซี mesh จึงส่งเมตริก บันทึก และ distributed trace ที่สม่ำเสมอสำหรับทราฟฟิกระหว่างบริการทั้งหมด ป้อนแนวปฏิบัติด้านการสังเกตระบบในบทที่ 9.2 ผู้เขียนบริการไม่ต้องเขียนอะไรเหล่านี้เลยแต่ได้ทั้งหมด

### รู้จักรูปแบบไซด์คาร์และทางเลือกแบบไม่ใช้ไซด์คาร์

โมเดลไซด์คาร์สง่างามแต่ไม่ฟรี แต่ละอินสแตนซ์ของบริการต้องรันคอนเทนเนอร์พร็อกซีเพิ่มที่ใช้หน่วยความจำและ CPU และทุกการเรียกมีฮอปเครือข่ายเพิ่มสองครั้ง (เข้าไซด์คาร์ในเครื่องและออกจากไซด์คาร์ปลายทาง) เพิ่มความหน่วงเล็กน้อย เมื่อมีบริการไม่กี่ตัว ภาระนี้มองไม่เห็น แต่เมื่อมีพ็อดนับพัน มันกลายเป็นรายการจริงในบิลการประมวลผลและงบความหน่วงของคุณ ต้นทุนนั้นผลักดันคลื่นของแนวทางแบบไม่มีไซด์คาร์ (sidecarless หรือ proxyless)

มีสองทิศทางที่สำคัญ ทิศทางหนึ่งย้ายฟังก์ชันของ mesh ออกจากไซด์คาร์รายพ็อดไปไว้ในพร็อกซีรายโหนด บริการหลายตัวบนเครื่องเดียวกันใช้พร็อกซีตัวเดียวร่วมกันแทนที่จะรันของตัวเอง ซึ่งแลกการแยกส่วนบางอย่างกับภาระที่ลดลงมาก อีกทิศทางคือแนวทาง proxyless ฝังตรรกะของ mesh เข้าในบริการโดยตรงผ่านไลบรารีบางเบาหรือรันไทม์ ขจัดฮอปเพิ่มไปเลย แลกกับการพึ่งพารายภาษา พัฒนาการใหม่ผลักฟังก์ชันบางอย่างของ mesh เข้าไปในเคอร์เนลของระบบปฏิบัติการด้วย [eBPF](https://en.wikipedia.org/wiki/EBPF) (เทคโนโลยีสำหรับรันโปรแกรมในแซนด์บ็อกซ์ภายในเคอร์เนล Linux) ซึ่งบังคับนโยบายและเก็บเทเลเมทรีได้ด้วยภาระน้อยกว่าพร็อกซีในพื้นที่ผู้ใช้ คุณไม่จำเป็นต้องเดิมพันกับผู้ชนะรายเดียววันนี้ แต่ต้องรู้ว่า ภาษีของไซด์คาร์เป็นของจริง ทางเลือกมีอยู่ และการเลือกแพลตฟอร์มของคุณไม่ควรขังคุณไว้จนนำมาใช้ภายหลังไม่ได้ รูปแบบเหล่านี้ตั้งอยู่บนรากฐานการจัดการคอนเทนเนอร์ในบทที่ 8.3

### ตัดสินว่าเมื่อใด mesh คุ้มกับความซับซ้อน

Service mesh ทรงพลังและซับซ้อนจริงในการรัน มันเพิ่มคอนโทรลเพลนที่ต้องดำเนินงาน พร็อกซีที่ต้องอัปเกรด ใบรับรองที่ต้องหมุนเวียน และชั้นใหม่ที่ต้องดีบักเมื่อคำขอหายไป ความซับซ้อนนี้คุ้มที่จะซื้อเมื่อคุณมีบริการมากพอที่การเดินสายเรื่องเหล่านี้ด้วยมือรายบริการและรายภาษามีต้นทุนมากกว่าการรัน mesh สัญญาณคร่าว ๆ คือขนาดและความหลากหลายของภาษา: หลายสิบหรือหลายร้อยบริการที่เขียนด้วยหลายภาษา ซึ่งไลบรารีร่วมสำหรับ mTLS และการลองใหม่จะเป็นฝันร้ายที่ต้องรักษาให้สอดคล้อง ที่ขนาดนั้น mesh คุ้มทุนด้วยความสม่ำเสมอและความปลอดภัยที่พิสูจน์ได้

Mesh ไม่คุ้มความซับซ้อนเมื่อคุณมีบริการไม่กี่ตัว ภาษาเดียว หรือทีมเล็ก สำหรับระบบขนาดพอประมาณ ไลบรารีหรือเฟรมเวิร์กที่ดีให้ mTLS การลองใหม่ และเมตริกด้วยภาระการดำเนินงานน้อยกว่า mesh เต็มรูปแบบมาก และ gateway ธรรมดากับไลบรารีไคลเอนต์ที่สมเหตุสมผลมักครอบคลุมทุกอย่างที่คุณต้องการ การนำ mesh มาใช้เพราะมันเป็นที่นิยม ก่อนที่ขนาดของคุณต้องการ เป็นวิธีที่พบบ่อยที่ใช้เวลาหนึ่งปีดำเนินงานโครงสร้างพื้นฐานที่แก้ปัญหาที่คุณไม่มี เริ่มจาก gateway เพิ่มรูปแบบความยืดหยุ่นในโค้ดหรือไลบรารี แล้วค่อยหยิบ mesh เมื่อจำนวนบริการและภาษาทำให้แนวทางรายบริการแพงกว่า นี่คือวินัยเดียวกันว่า "คุ้มกับความซับซ้อนหรือไม่" ที่บทเรื่องคลาวด์และระบบแบบกระจาย (3.11 และ 3.3) กลับมาพูดถึงซ้ำแล้วซ้ำอีก

### หลีกเลี่ยงการจัดการซ้ำซ้อนเมื่อ gateway และ mesh ทับซ้อนกัน

Gateway และ mesh ทับซ้อนกัน และการทับซ้อนคือที่ที่ทีมทำร้ายตัวเอง ทั้งคู่ลองใหม่ได้ ทั้งคู่บังคับ timeout ได้ ทั้งคู่ตรวจตัวตนได้ ทั้งคู่เก็บเทเลเมทรีได้ ถ้า gateway ลองคำขอใหม่สามครั้งและ mesh ก็ลองใหม่สามครั้งทุกฮอปภายใน การลองใหม่ของไคลเอนต์ครั้งเดียวอาจระเบิดเป็นการเรียกแบ็กเอนด์หลายสิบครั้งและเปลี่ยนสะดุดเล็กน้อยให้เป็น retry storm ถ้าทั้งสองชั้นบังคับ timeout และชั้นในยาวกว่าชั้นนอก ชั้นนอกจะยอมแพ้ขณะที่ชั้นในยังทำงานต่อ เสียแรงไปกับการตอบสนองที่ไม่มีใครอ่าน

ทางแก้คือการแบ่งงานที่ชัดเจน เขียนไว้และตกลงกัน มอบหมายแต่ละเรื่องให้ชั้นเดียวเท่านั้น Gateway เป็นเจ้าของเรื่องเหนือ-ใต้: การยืนยันตัวตนผู้ใช้ปลายทาง ขีดจำกัดอัตราและโควตาภายนอก การแปลงคำขอ และการประกอบ API สำหรับไคลเอนต์ Mesh เป็นเจ้าของเรื่องตะวันออก-ตะวันตก: mTLS ระหว่างบริการ การลองใหม่และ circuit breaking ภายใน และการเลื่อนทราฟฟิกระหว่างเวอร์ชันของบริการ ในที่ที่เรื่องหนึ่งอยู่ได้ทั้งสองชั้น ให้เลือกเจ้าของหนึ่งราย และให้อีกชั้นปล่อยผ่าน ตั้งงบประมาณการลองใหม่และลำดับชั้นของ timeout ให้ timeout ชั้นนอกยาวกว่างานภายในที่มันรอเสมอ เป้าหมายคือทุกคำขอมีที่เดียวที่จัดการแต่ละเรื่อง และไม่มีคำขอใดถูกลองใหม่ ยืนยันตัวตน หรือบันทึกซ้ำสองครั้งโดยบังเอิญ

### ปฏิบัติต่อ gateway และ mesh เป็นจุดบังคับใช้นโยบายสำหรับ zero trust

เหตุผลที่ลึกที่สุดในการรันชั้นเหล่านี้คือสถาปัตยกรรมความมั่นคงปลอดภัย [Zero trust](https://en.wikipedia.org/wiki/Zero_trust_security_model) คือหลักการที่ว่าไม่มีคำขอใดได้รับความไว้วางใจเพราะมันมาจากที่ใด ทุกคำขอต้องพิสูจน์ตัวตนและสิทธิ์ของตน แม้อยู่ภายในเครือข่ายของคุณเอง โมเดลเก่าเชื่อทุกสิ่งที่อยู่ภายในขอบเขตแล้ว ซึ่งหมายความว่าบริการที่ถูกเจาะรายเดียวเดินไปไหนก็ได้ตามใจ Zero trust แทนที่ความเชื่อใจตามตำแหน่งในเครือข่ายด้วยความเชื่อใจตามตัวตนในทุกฮอป และ gateway กับ mesh คือจุดบังคับใช้ตามธรรมชาติที่ตัวตนนั้นถูกตรวจ

Gateway คือจุดบังคับใช้นโยบายสำหรับตัวตนภายนอก: มันตรวจผู้ใช้ปลายทางหรือพาร์ทเนอร์ก่อนที่อะไรจะไปถึงบริการของคุณ Mesh คือจุดบังคับใช้นโยบายสำหรับตัวตนของเวิร์กโหลด: ทุกบริการได้ตัวตนเชิงวิทยาการเข้ารหัสลับ mTLS พิสูจน์ตัวตนนั้นในทุกการเรียก และนโยบายตัดสินว่าบริการใดคุยกับบริการใดได้ ทั้งสองรวมกันให้การป้องกันเชิงลึก ที่คำขอถูกตรวจที่ขอบและตรวจอีกครั้งระหว่างบริการ การถูกเจาะของบริการหนึ่งจึงไม่ให้สิทธิ์เคลื่อนที่อย่างเสรีไปยังบริการที่เหลือ ในการติดตั้งหลายคลัสเตอร์และหลายภูมิภาค mesh ขยายโครงข่ายตัวตนนี้ข้ามขอบเขตคลัสเตอร์ได้ บริการในคลัสเตอร์หนึ่งจึงยืนยันตัวตนกับบริการในอีกคลัสเตอร์ด้วยการรับประกัน mTLS เดียวกับที่ใช้ภายในเครื่อง ให้เครือข่ายแบบ zero trust ที่สม่ำเสมอแม้เมื่อรอยเท้าแผ่ออกไป รากฐานด้านตัวตนตรงนี้เชื่อมโดยตรงกับบทที่ 4.7

## ข้อดีข้อเสียและการแลกเปลี่ยน

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| API gateway | ที่เดียวสำหรับการยืนยันตัวตน ขีดจำกัดอัตรา การประกอบ และการกำกับเวอร์ชัน | เป็นคอขวดจุดเดียวที่ต้องขยายและรักษาให้พร้อมใช้งานสูง |
| Backend for frontend | ไคลเอนต์แต่ละรายได้ API ที่ปรับให้เข้ากันและพัฒนาได้อิสระ | ต้องรัน gateway มากขึ้น ตรรกะซ้ำกันข้าม BFF |
| Service mesh (ไซด์คาร์) | mTLS การลองใหม่ และการสังเกตระบบที่สม่ำเสมอโดยไม่แก้โค้ด | ภาระของพร็อกซี ความหน่วง และคอนโทรลเพลนที่ต้องดำเนินงาน |
| Mesh แบบไม่มีไซด์คาร์ / proxyless | ภาระและความหน่วงต่ำกว่าไซด์คาร์รายพ็อด | ยังไม่บรรลุนิติภาวะ การแยกส่วนอ่อนกว่าหรือต้องพึ่งพารายภาษา |
| ความยืดหยุ่นแบบอิงไลบรารี | รันง่าย ไม่ต้องมีโครงสร้างพื้นฐานเพิ่ม | ซ้ำกันรายภาษา รักษาให้สอดคล้องยากเมื่อขยาย |
| Mesh ข้ามคลัสเตอร์ | ตัวตนแบบ zero trust ที่สม่ำเสมอทุกที่ | ความซับซ้อนด้านการดำเนินงานและเครือข่ายมาก |

ความตึงเครียดหลักคือความสม่ำเสมอเทียบกับต้นทุนการดำเนินงาน ชั้นร่วมซื้อความสอดคล้อง ความปลอดภัยที่พิสูจน์ได้ และนโยบายที่เขียนครั้งเดียว แต่มันเป็นระบบจริงที่คุณต้องรัน ขยาย รักษาความปลอดภัย และดีบัก และมันแทรกตัวเองเข้าไปในเส้นทางของทุกคำขอ แก้ความตึงเครียดด้วยขนาดและความต้องการ Gateway มักคุ้มทันทีที่คุณมีไคลเอนต์ภายนอก เพราะเรื่องที่มันรวมศูนย์คือเรื่องที่หลีกเลี่ยงไม่ได้ Mesh คุ้มทีหลัง เมื่อจำนวนบริการและภาษาทำให้การเดินสายรายบริการเป็นเส้นทางที่แพงกว่า ต่ำกว่าเกณฑ์นั้น ไลบรารีและ gateway ธรรมดาให้ประโยชน์ส่วนใหญ่ในต้นทุนเพียงเศษเสี้ยว เหนือเกณฑ์นั้น ความสม่ำเสมอของ mesh คุ้มค่าน้ำหนักของมัน ความผิดพลาดในทั้งสองทิศคือการนำมาใช้ตามกระแสแทนความต้องการ: mesh เร็วเกินไปคือหนึ่งปีของการโกนขนจามรี (yak-shaving) และ mesh ที่ข้ามไปนานเกินไปคือการทำ mTLS ที่ไม่สอดคล้องกันนับร้อยแบบที่เขียนเอง

## คำถามที่ควรคุยกับทีม

1. **สำหรับแต่ละเรื่องที่ตัดผ่านทุกบริการ (การยืนยันตัวตน การลองใหม่ timeout ขีดจำกัดอัตรา การเข้ารหัส เทเลเมทรี) ชั้นใดชั้นเดียวเป็นเจ้าของ และทุกคนบอกชื่อเจ้าของได้โดยไม่ต้องเดาหรือไม่?** นี่คือคำถามที่ป้องกันการจัดการซ้ำซ้อน และทีมส่วนใหญ่ไม่เคยตอบอย่างชัดเจน ซึ่งหมายความว่าคำตอบต่างกันไปตามบริการและผู้เขียน นำรายการเรื่องต่าง ๆ มาเรียงด้านซ้าย และชั้นของคุณ (ไลบรารีไคลเอนต์ gateway mesh แต่ละบริการ) ด้านบน แล้วเติมตารางด้วยกัน จุดที่สองช่องถูกติ๊กสำหรับเรื่องเดียวคือ retry storm และ timeout inversion ที่รอเกิด แถวที่ว่างคือเรื่องที่ไม่มีใครจัดการเลย สิ่งที่ส่งมอบคือตารางที่ตกลงกันฉบับเดียว เผยแพร่ในที่ที่ทุกทีมเห็น ซึ่งบอกว่าชั้นเดียวเป็นเจ้าของแต่ละเรื่องและชั้นอื่นปล่อยผ่าน ตารางนั้นมีค่ากว่าการกำหนดค่า gateway หรือ mesh มากมาย เพราะเป็นสิ่งที่ทำให้สองชั้นไม่ต่อสู้กัน

2. **เรามีบริการและความหลากหลายของภาษามากพอที่จะคุ้มกับ service mesh จริงหรือ หรือกำลังจะซื้อคอนโทรลเพลนมาแก้ปัญหาที่เราไม่มี?** Mesh เป็นข้อผูกพันด้านการดำเนินงานที่จริงจัง และคำตอบที่ซื่อตรงสำหรับหลายทีมคือไลบรารีที่ดีบวก gateway จะรับใช้พวกเขาได้ดีกว่าในวันนี้ นำจำนวนบริการจริง จำนวนภาษาที่ใช้เขียน และการประเมินที่ซื่อตรงว่าตรรกะเครือข่ายที่ซ้ำกันทำให้เจ็บแค่ไหนตอนนี้มา แล้วนำอีกด้านมาด้วย: ใครจะดำเนินงาน mesh อัปเกรดพร็อกซี หมุนใบรับรอง และถูกเรียกตัวเมื่อมันส่งคำขอผิดทาง ถ้าความเจ็บปวดของการเดินสายรายบริการน้อยกว่าต้นทุนการรัน mesh คุณก็ได้คำตอบแล้ว คือรอ ถ้าคุณจมอยู่กับโค้ด mTLS และการลองใหม่ที่ไม่สอดคล้องกันข้ามหลายสิบบริการหลายภาษา mesh ก็คุ้มค่าที่จะมี ประเด็นคือตัดสินจากหลักฐาน ไม่ใช่จากภาพที่การบรรยายในงานประชุมทำให้ mesh ดูเป็น

3. **ขอบเขต zero trust ของเราวันนี้อยู่ที่ไหน และจะเกิดอะไรขึ้นถ้าบริการภายในหนึ่งถูกเจาะ?** หลายระบบยังเชื่อทุกอย่างที่อยู่ในเครือข่ายแล้ว ซึ่งหมายความว่าบริการที่ถูกเจาะรายเดียวเคลื่อนที่ด้านข้างไปถึงทุกอย่างอื่นได้ และทีมมักค้นพบเรื่องนี้ระหว่างเหตุการณ์ ไล่ดูรัศมีความเสียหายอย่างซื่อตรง: ถ้าผู้โจมตีครอบครองบริการหนึ่งของคุณ มันเรียกอะไรได้ อ่านอะไรได้ และอะไรหยุดมัน นำคำตอบปัจจุบันของคุณเรื่องการยืนยันตัวตนและการเข้ารหัสการเรียกระหว่างบริการมา และระบุให้ชัดว่าการเรียกใดได้รับการปกป้องด้วย mTLS และการเรียกใดเป็นความเชื่อใจแบบข้อความธรรมดาที่อิงว่าอยู่ในเครือข่ายเดียวกัน การกระทำที่ตามมาคือแผนที่ตั้งใจสำหรับการเข้าถึงแบบอิงตัวตนในทุกฮอป โดย gateway ตรวจตัวตนภายนอกและ mesh หรือสิ่งเทียบเท่าตรวจตัวตนของเวิร์กโหลด เพื่อให้การถูกเจาะถูกจำกัดไว้แทนที่จะเป็นหายนะ แม้คุณยังไม่พร้อมรัน mesh เต็มรูปแบบ การระบุว่าขอบเขตความเชื่อใจจริง ๆ อยู่ที่ไหนก็เป็นก้าวแรกที่ซื่อตรง

4. **ถ้าชั้น API gateway ของเราล้มตอนนี้ ระบบดับไปมากแค่ไหน และเราทดสอบความล้มเหลวนั้นแล้วหรือแค่สมมติว่ามันไม่เกิด?** Gateway รวมศูนย์มากจนการล่มของมันพาทุกอย่างข้างหลังออฟไลน์ และทีมใหญ่มักลงทุนเรื่องความซ้ำซ้อนของมันน้อยเกินไปเพราะมันทำงานเงียบ ๆ จนกว่าจะไม่ทำ ชั่งแรงดึงที่แข่งกัน: gateway เดี่ยวที่เรียบง่ายให้เหตุผลได้ง่ายและรันถูก ขณะที่ชั้นที่ขยายแนวนอนหลายโซนมีราคาสูงกว่าและเพิ่มการกำหนดค่า failover และความซับซ้อนของตัวเอง นำตัวเลขจริงมาคุย รวมถึงจำนวนอินสแตนซ์ที่รันวันนี้ ครอบคลุมกี่ availability zone เวลา failover เท่าไร และครั้งสุดท้ายที่คุณทำ game day ที่ปิด gateway โดยตั้งใจคือเมื่อไร สำหรับแพลตฟอร์มองค์กรและภาครัฐที่มีคำมั่นเรื่องเวลาทำงานหรือระดับบริการตามกฎหมาย ให้เพิ่มค่าปรับตามสัญญาหรือกฎระเบียบสำหรับการล่ม เพราะประตูหน้าที่ไม่มีความซ้ำซ้อนคือความเสี่ยงด้านความพร้อมใช้งานที่คุณยอมรับเงียบ ๆ แทนทุกบริการและทุกประชาชนที่อยู่ข้างหลัง

5. **เราวัดภาษีไซด์คาร์ที่ mesh ของเราเก็บจริงหรือยัง และมีแผนสำหรับทางเลือกแบบไม่มีไซด์คาร์และ eBPF หรือเรากำลังจ่ายโดยไม่รู้?** ที่ขนาดใหญ่ ภาระของพร็อกซีรายพ็อดทั้งในการประมวลผลและความหน่วงเลิกเป็นสิ่งที่มองไม่เห็นและกลายเป็นรายการจริงในงบประมาณ แต่หลายทีมรันไซด์คาร์นับพันโดยไม่เคยวัดต้นทุน ความตึงเครียดอยู่ระหว่างความบรรลุนิติภาวะและการแยกส่วนของโมเดลไซด์คาร์ด้านหนึ่ง กับภาระที่ต่ำกว่าของพร็อกซีรายโหนด ไลบรารี proxyless หรือแนวทาง eBPF ในเคอร์เนลอีกด้านหนึ่ง ซึ่งใหม่กว่าและแลกการแยกส่วนบางอย่างหรือเพิ่มการพึ่งพารายภาษา นำตัวเลขที่วัดได้มา: หน่วยความจำและ CPU ที่พร็อกซีใช้ทั่วฟลีต ความหน่วงส่วนหางที่เพิ่มต่อฮอป และสัดส่วนของบิลการประมวลผลที่ mesh แทน สำหรับองค์กรขนาดใหญ่ที่รัน mesh ข้ามพ็อดนับพัน หรือแพลตฟอร์มภาครัฐที่ถูกตรวจสอบงบ นี่คือการตัดสินใจเรื่องการใช้จ่ายที่การกำกับดูแลจะถามในที่สุด การรู้ภาษีและรู้ว่าการเลือกแพลตฟอร์มของคุณเปิดทางเลือกที่ถูกกว่าไว้หรือไม่จึงเป็นการตรวจสอบสถานะพื้นฐาน (due diligence)

6. **ไคลเอนต์แต่ละประเภทต้องการ backend for frontend ของตัวเองจริงหรือ หรือเรากำลังจะทำตรรกะซ้ำข้าม gateway สำหรับไคลเอนต์ที่ต้องการสิ่งเดียวกันจริง ๆ?** รูปแบบ BFF ลดการพึ่งพากันของทีมไคลเอนต์และให้แต่ละทีมพัฒนาสัญญาที่ปรับเฉพาะได้ แต่ BFF ใหม่ทุกตัวคือ gateway อีกตัวที่ต้องรัน รักษาความปลอดภัย และซิงก์ และตรรกะที่ซ้ำกันระหว่างมันค่อย ๆ กลายเป็นภาษีการบำรุงรักษา ข้อพิจารณาที่แข่งกันคืออิสระของทีมและประสิทธิภาพเฉพาะไคลเอนต์เทียบกับต้นทุนการดำเนินงานและการไหลเลื่อนของ gateway ที่คล้ายกันจำนวนมาก นำหลักฐานมาว่าความต้องการของไคลเอนต์แตกต่างกันจริงแค่ไหน: ขนาดข้อมูล จำนวนรอบการเดินทาง จังหวะการกำกับเวอร์ชัน และบ่อยแค่ไหนที่การเปลี่ยนของไคลเอนต์หนึ่งจะขวางอีกไคลเอนต์ภายใต้ gateway ร่วมตัวเดียว ในองค์กรขนาดใหญ่ที่มีทีมไคลเอนต์มากมาย หรือแพลตฟอร์มภาครัฐที่ให้บริการเว็บแอปสาธารณะ แอปมือถือ และการเชื่อมต่อพาร์ทเนอร์พร้อมกัน คำถามที่ซื่อตรงคือความแตกต่างนั้นคุ้มกับการขยายพันธุ์หรือไม่ เพราะ BFF ต่อไคลเอนต์ที่ทุกรายต้องการรูปทรงเดียวกันคือความรกรุงรังที่คุณจะจ่ายค่าบำรุงรักษาไปอีกหลายปี

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ปล่อย API gateway และข้าม mesh เมื่อมีบริการไม่กี่ตัวและทีมเล็กจิ๋ว gateway ตัวเดียวจัดการการยืนยันตัวตน ขีดจำกัดอัตรา และการประกอบ ขณะที่ไลบรารีไคลเอนต์ร่วมให้ mTLS และการลองใหม่ด้วยเศษเสี้ยวของต้นทุนคอนโทรลเพลน ทรัพยากรที่ขาดแคลนที่สุดของคุณคือความสนใจของวิศวกร ดังนั้น mesh ที่คุณดำเนินงานไม่ได้คือภาระ ไม่ใช่คูเมือง ทำให้ gateway มีความซ้ำซ้อนพอจะรอดเมื่อโหนดหนึ่งตาย และกลับมาพิจารณา mesh เมื่อจำนวนบริการและความหลากหลายของภาษาบังคับให้ต้องถามเท่านั้น

**ธุรกิจขนาดเล็ก.** คุณไม่มีทีมแพลตฟอร์มที่จะรัน mesh ดังนั้นพึ่งสิ่งที่แพลตฟอร์มโฮสติ้งหรือผลิตภัณฑ์ gateway ให้มาตั้งแต่แกะกล่อง: TLS ที่มีผู้ดูแล ขีดจำกัดอัตราในตัว และ gateway แบบโฮสต์แทนตัวที่คุณต้องแพตช์เอง วางกรอบทางเลือกเป็นซื้อเทียบกับสร้าง และให้ซื้อ เพราะ API gateway แบบมีผู้ดูแลมีต้นทุนต่ำกว่าชั่วโมงวิศวกรที่ใช้ดำเนินงานของตัวเอง ปฏิบัติต่อการเข้ารหัสระหว่างบริการภายในเป็นคุณสมบัติที่แพลตฟอร์มของคุณให้ ไม่ใช่โครงการที่ต้องจัดคนมาทำ

**องค์กรขนาดใหญ่.** ด้วยบริการนับร้อยข้ามหลายทีมและหลายภาษา mesh คุ้มกับความซับซ้อน และงานที่แท้จริงคือธรรมาภิบาล: การแบ่งงานที่เขียนไว้ฉบับเดียวเพื่อให้ gateway และ mesh ไม่จัดการเรื่องใดซ้ำซ้อน mTLS และเทเลเมทรีที่สม่ำเสมอ และทีมแพลตฟอร์มที่เป็นเจ้าของการอัปเกรดพร็อกซีและการหมุนใบรับรอง ผู้ตรวจสอบต้องการจุดบังคับใช้ที่พิสูจน์ได้จุดเดียวสำหรับการเข้าถึงและการเข้ารหัส จึงทำให้อินเทอร์เฟซเป็นมาตรฐานและทำให้นโยบายเป็นสิ่งที่ทีมสืบทอดแทนที่จะเขียนใหม่ จัดการภาษีไซด์คาร์เป็นรายการงบประมาณจริง และเปิดทางเลือกแบบไม่มีไซด์คาร์ไว้เพื่อไม่ให้ติดกับดักไม่สามารถใช้แนวทางที่ถูกกว่าภายหลัง

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง ความโปร่งใส และความรับผิดชอบต่อสาธารณะหล่อหลอมสถาปัตยกรรม ปฏิบัติต่อ gateway และ mesh เป็นกระดูกสันหลังของ zero trust ที่หน่วยกำกับดูแลคาดหวัง: ประชาชนและพาร์ทเนอร์ทุกรายถูกยืนยันตัวตนที่ประตูหน้า ทุกการเรียกภายในถูกยืนยันตัวตนและเข้ารหัสด้วยตัวตนของเวิร์กโหลด และมีร่องรอยการตรวจสอบที่ทุกจุดบังคับใช้ซึ่งพิสูจน์ว่าการเข้าถึงถูกตรวจที่ไหนและทราฟฟิกถูกเข้ารหัสที่ไหน เลือกมาตรฐานเปิดและการกำหนดค่าที่พกพาได้มากกว่าการผูกมัดกับผู้ขายที่กฎการจัดซื้ออาจห้าม และเผยแพร่ในที่ที่เหมาะสมว่าแพลตฟอร์มปกป้องข้อมูลประชาชนอย่างไรเมื่อข้ามแต่ละขอบเขต

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสิบสองคนรันแปดบริการหลัง API gateway ตัวเดียว Gateway ทำงานเหนือ-ใต้ทั้งหมด: ยืนยันตัวตนผู้ใช้ด้วยการตรวจโทเคน บังคับขีดจำกัดอัตรารายแพ็กเกจเพื่อไม่ให้ผู้ใช้ระดับฟรีท่วมระบบ และประกอบ endpoint ที่พูดมากสองสามตัวเป็นการเรียกเดียวที่เป็นมิตรกับมือถือ สำหรับทราฟฟิกตะวันออก-ตะวันตกพวกเขาจงใจข้าม service mesh เพราะแปดบริการในสองภาษาไม่คุ้มกับคอนโทรลเพลน แทนที่จะใช้ พวกเขาได้ mTLS และการลองใหม่จากไลบรารีไคลเอนต์ร่วมและการจัดการใบรับรองในตัวของแพลตฟอร์ม และเก็บ trace ด้วยเอเจนต์เบา ๆ เมื่อภายหลังเพิ่มไคลเอนต์มือถือเฉพาะที่ต้องการข้อมูลกระชับกว่า พวกเขาแนะนำ backend for frontend ของมือถือไว้ข้าง gateway ของเว็บที่มีอยู่ พวกเขากลับมาพิจารณาเรื่อง mesh ทุกปีและตัดสินใจอย่างถูกต้องว่ายังไม่ข้ามเกณฑ์ที่ mesh จะคุ้ม

**องค์กรขนาดใหญ่.** ธนาคารข้ามชาติรันบริการหลายร้อยตัวข้ามหลายทีมและหลายภาษา และที่นี่ service mesh คุ้มกับความซับซ้อน ทุกบริการได้ตัวตนของเวิร์กโหลดและ mTLS โดยค่าเริ่มต้น ทราฟฟิกภายในทั้งหมดจึงถูกยืนยันตัวตนและเข้ารหัสโดยไม่มีทีมใดต้องเขียนโค้ดเข้ารหัส ซึ่งทำให้ทั้งองค์กรความมั่นคงปลอดภัยและผู้ตรวจสอบที่ต้องการจุดบังคับใช้ที่พิสูจน์ได้จุดเดียวพอใจ Mesh ใช้การลองใหม่ timeout และ circuit breaking ที่สม่ำเสมอด้วยนโยบาย และเลื่อนทราฟฟิกทีละน้อยสำหรับการปล่อยแบบ canary การปล่อยที่เสียจึงแตะผู้ใช้หนึ่งเปอร์เซ็นต์ก่อนจะแตะทั้งหมด ชั้นของ API gateway อยู่หน้าทราฟฟิกภายนอกและของพาร์ทเนอร์ เป็นเจ้าของการยืนยันตัวตน โควตา และการกำกับเวอร์ชัน พร้อมกฎที่เขียนไว้อย่างหนักแน่นว่าการลองใหม่ภายในอยู่ใน mesh เท่านั้นและขีดจำกัดอัตราภายนอกอยู่ใน gateway เท่านั้น ทั้งสองชั้นจึงไม่จัดการคำขอใดซ้ำซ้อน เทเลเมทรีที่สม่ำเสมอจากพร็อกซีทุกตัวป้อนแพลตฟอร์มสังเกตระบบกลางที่ให้วิศวกรเวรเรียกคนเดียวไล่ตามคำขอข้ามหลายสิบฮอปของบริการได้

**ภาครัฐ.** หน่วยงานภาษีแห่งชาติปรับปรุงแพลตฟอร์มยื่นแบบสำหรับประชาชนให้ทันสมัยและปฏิบัติต่อ gateway และ mesh เป็นกระดูกสันหลังของสถาปัตยกรรม zero trust ที่หน่วยกำกับดูแลกำหนด API gateway เป็นประตูหน้าที่ควบคุม: ประชาชนและพาร์ทเนอร์ทุกรายถูกยืนยันตัวตนและอนุญาตที่นั่น ขีดจำกัดอัตราภายนอกปกป้องระบบระหว่างช่วงพุ่งก่อนกำหนดยื่นแบบ และรูปแบบไคลเอนต์เก่าถูกแปลงที่ขอบเพื่อให้การเชื่อมต่อแบบเดิมยังใช้งานได้ ข้างหลังนั้น service mesh ให้ทุกบริการภายในมีตัวตนเชิงวิทยาการเข้ารหัสลับและบังคับ mTLS ในทุกการเรียก ไม่มีบริการใดได้รับความเชื่อใจเพียงเพราะอยู่ในเครือข่าย และนโยบายการเข้าถึงระบุอย่างชัดเจนว่าบริการใดเรียกบริการใดได้ เพราะแพลตฟอร์มครอบคลุมหลายศูนย์ข้อมูลเพื่อความยืดหยุ่น mesh จึงขยายการรับประกันด้านตัวตนและการเข้ารหัสเดียวกันข้ามคลัสเตอร์ ให้เครือข่ายแบบ zero trust ที่สม่ำเสมอทั่วประเทศ ทุกจุดบังคับใช้ส่งร่องรอยการตรวจสอบ หน่วยงานจึงพิสูจน์ต่อหน่วยกำกับดูแลได้ว่าการเข้าถึงถูกตรวจที่ไหนและทราฟฟิกถูกเข้ารหัสที่ไหน

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ผลตอบแทนของ gateway เห็นได้ง่ายและมักมาก แทนที่ทุกบริการจะเขียนการยืนยันตัวตน ขีดจำกัดอัตรา และการบันทึกคำขอใหม่ คุณสร้างสิ่งเหล่านั้นครั้งเดียวที่ขอบและทุกบริการได้รับไป การแก้ไขด้านความมั่นคงปลอดภัยหรือนโยบายขีดจำกัดอัตราใหม่ปล่อยได้ในการปล่อยเดียวแทนที่จะเป็นร้อยครั้ง ซึ่งย่นเวลาในการปิดช่องโหว่และลดต้นทุนของทุกการตรวจสอบ เพราะมีที่เดียวให้ตรวจ คุณสมบัติการประกอบและการกำกับเวอร์ชันลดรอบการเดินทางของไคลเอนต์และให้คุณพัฒนา API ได้โดยไม่ทำให้ผู้เรียกพัง ซึ่งลดทั้งต้นทุนด้านความหน่วงและภาษีการประสานงานระหว่างทีม สำหรับระบบเกือบทุกแบบที่มีไคลเอนต์ภายนอก gateway คุ้มทุนได้เร็ว

Service mesh มีเหตุผลทางธุรกิจที่ละเอียดอ่อนกว่า เพราะต้นทุนรวมตลอดอายุการใช้งานของมันเป็นของจริงและต่อเนื่อง คุณจ่ายค่าประมวลผลและความหน่วงของพร็อกซี จ่ายค่าวิศวกรที่ดำเนินงานคอนโทรลเพลน และจ่ายค่าเส้นโค้งการเรียนรู้ของการดีบักชั้นใหม่ ต้นทุนนั้นสมเหตุสมผลเมื่อทางเลือกอื่น (การทำ mTLS การลองใหม่ และเทเลเมทรีรายบริการรายภาษา) จะใหญ่กว่า และที่แย่กว่าคือไม่สอดคล้องกันในแบบที่สร้างช่องว่างด้านความปลอดภัยและระบบล่ม ที่ขนาดสูง mesh แปลงวิธีแก้ที่เปราะบางที่เขียนเองนับร้อยเป็นวิธีเดียวที่สม่ำเสมอและพิสูจน์ได้ และ ROI ปรากฏเป็นเหตุการณ์ด้านความมั่นคงปลอดภัยที่น้อยลง การปล่อยที่ปลอดภัยและเร็วขึ้นผ่านการเลื่อนทราฟฟิก และความสามารถในการสังเกตระบบที่ดีขึ้นอย่างมาก ต่ำกว่าขนาดนั้น การคำนวณที่ซื่อตรงมักเอนไปทางไลบรารีและ gateway และก้าวที่มีวินัยคือรอ เพื่อนำเสนอเหตุผลต่อผู้บริหาร ให้เชื่อม gateway กับเมตริกที่พวกเขาติดตามอยู่แล้ว (เวลาแก้ไขช่องโหว่ ต้นทุนการตรวจสอบ ภาระการประสานงาน API) และเชื่อม mesh กับการจำกัดวงเหตุการณ์ด้านความมั่นคงปลอดภัย ความปลอดภัยของการปล่อย และต้นทุนของการซ้ำซ้อนข้ามภาษาที่มันมาแทน

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **Mesh ก่อนที่จะต้องการ:** นำ service mesh เต็มรูปแบบมาใช้กับบริการไม่กี่ตัว ซื้อคอนโทรลเพลนมาแก้ปัญหาที่ยังไม่มี
- **ลองใหม่สองชั้น:** Gateway และ mesh ลองใหม่ทั้งคู่ การเรียกของไคลเอนต์ครั้งเดียวจึงคูณเป็น retry storm ของแบ็กเอนด์ที่ขยายระบบล่ม
- **Timeout inversion:** timeout ชั้นในยาวกว่าชั้นนอก ผู้เรียกจึงยอมแพ้ขณะที่ผู้ถูกเรียกยังทำงานกับการตอบสนองที่ไม่มีใครอ่าน
- **Gateway เป็นโมโนลิธ:** ยัดตรรกะทางธุรกิจเข้า gateway จนมันกลายเป็นคอขวดร่วมที่ทุกทีมต้องประสานกันเพื่อเปลี่ยน
- **จุดล้มเหลวจุดเดียว:** รัน gateway อินสแตนซ์เดียวโดยไม่มีความซ้ำซ้อน ประตูหน้าที่ล่มจึงพาทุกบริการข้างหลังล่มไปด้วย
- **เชื่อใจเครือข่าย:** ถือว่าทุกอย่างภายในขอบเขตปลอดภัย บริการที่ถูกเจาะตัวเดียวจึงเคลื่อนที่ด้านข้างไปถึงทุกอย่างได้
- **ความเป็นเจ้าของทับซ้อน:** ไม่มีการแบ่งงานที่เขียนไว้ เรื่องเดียวกันจึงถูกจัดการในทั้งสองชั้นโดยบังเอิญและไม่มีใครรู้ว่าชั้นไหนเป็นผู้ชี้ขาด
- **BFF ที่ขยายพันธุ์:** สร้าง backend for frontend ต่อไคลเอนต์ทั้งที่ไคลเอนต์ต้องการสิ่งเดียวกัน ทำให้ gateway ทวีคูณและตรรกะซ้ำกันโดยไม่ได้อะไร
- **เพิกเฉยต่อภาษีไซด์คาร์:** ติดตั้งไซด์คาร์นับพันโดยไม่วัดภาระการประมวลผลและความหน่วง แล้วสงสัยว่างบประมาณหายไปไหน

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** บริการคุยกันโดยตรงโดยไม่มีชั้นร่วม การยืนยันตัวตน การลองใหม่ และ timeout เขียนด้วยมือรายบริการและไม่สอดคล้องกัน ทราฟฟิกภายในมักเป็นข้อความธรรมดาและเชื่อใจเพราะอยู่ในเครือข่าย และไม่มีที่เดียวสำหรับบังคับใช้นโยบายหรือสังเกตทราฟฟิก การตัดสินใจเป็นแบบตั้งรับ ทำทีละบริการเมื่อปัญหาปรากฏ
- **ระดับ 2 พัฒนา:** API gateway อยู่หน้าทราฟฟิกภายนอกและรวมศูนย์การยืนยันตัวตน ขีดจำกัดอัตรา และการกำหนดเส้นทาง แต่เรื่องตะวันออก-ตะวันตกจัดการด้วยไลบรารีร่วมที่การนำไปใช้ไม่สม่ำเสมอ บางบริการมี mTLS หลายบริการไม่มี ทีมตระหนักถึงความแตกต่างระหว่างเหนือ-ใต้กับตะวันออก-ตะวันตก แต่ความเป็นเจ้าของไม่เป็นทางการและแนวปฏิบัติต่างกันไปในแต่ละทีม
- **ระดับ 3 สร้างมาตรฐาน:** เรื่องเหนือ-ใต้และตะวันออก-ตะวันตกแยกกันอย่างสะอาดด้วยการแบ่งงานที่เขียนไว้และใช้ทั่วองค์กร Gateway เป็นเจ้าของตัวตนภายนอก โควตา และการประกอบ mesh หรือชั้นไลบรารีที่สม่ำเสมอเป็นเจ้าของ mTLS การลองใหม่ และเทเลเมทรีภายใน การทับซ้อนถูกแก้ไขเพื่อไม่ให้เรื่องใดถูกจัดการซ้ำซ้อน ทราฟฟิกภายในเข้ารหัสและตรวจตัวตนโดยค่าเริ่มต้น และมาตรฐานถูกบันทึกและบังคับใช้แทนที่จะปล่อยให้แต่ละทีมตัดสินใจ
- **ระดับ 4 บริหารจัดการ:** ชั้นทราฟฟิกถูกวัดและควบคุมเทียบกับเส้นฐาน คุณติดตามภาษีไซด์คาร์ในการประมวลผลและความหน่วงส่วนหางต่อฮอป ความพร้อมใช้งานของ gateway และ mesh เทียบกับงบประมาณข้อผิดพลาด เหตุการณ์ retry amplification และ timeout inversion ความครอบคลุมของ mTLS เป็นเปอร์เซ็นต์ของการเรียกภายใน และเวลาที่ใช้ผลักการเปลี่ยนนโยบายไปทั่วฟลีต เมตริกกำกับการตัดสินใจ: การอัปเกรดพร็อกซี งบประมาณการลองใหม่ใหม่ หรือกฎ canary ถูกตัดสินจากข้อมูลเทียบกับเส้นฐานแทนสัญชาตญาณ และการเบี่ยงเบนจากมาตรฐานทุกครั้งกระตุ้นการแก้ไข
- **ระดับ 5 ประสานทั้งระบบ:** Gateway และ mesh เป็นจุดบังคับใช้นโยบายสำหรับสถาปัตยกรรม zero trust ที่บรรลุนิติภาวะ โดยตรวจตัวตนในทุกฮอปข้ามคลัสเตอร์และภูมิภาค การเลื่อนทราฟฟิกขับเคลื่อนการส่งมอบแบบก้าวหน้าที่ปลอดภัย การสังเกตระบบสม่ำเสมอและมั่งคั่ง และองค์กรประเมินและนำแนวทางแบบไม่มีไซด์คาร์ proxyless และ eBPF มาใช้อย่างต่อเนื่องในที่ที่คุ้มค่า ชั้นทราฟฟิกบูรณาการกับความมั่นคงปลอดภัย การส่งมอบ และการวางแผนความจุ และปรับตัวเมื่อขนาด ภาษา และภาพความเสี่ยงเปลี่ยนไป

## ประเด็นชวนคุย

1. ถ้า API gateway ตัวเดียวของคุณล่มตอนนี้ จะมีกี่บริการที่เข้าถึงไม่ได้ และแผนทำให้ประตูหน้ามีความซ้ำซ้อนคืออะไร?
2. เรื่องใดในระบบของคุณที่ปัจจุบันถูกจัดการทั้งใน gateway และในบริการ (หรือไลบรารี) และคุณจะพิสูจน์ได้อย่างไรว่าไม่ถูกจัดการซ้ำซ้อน?
3. ที่จำนวนบริการและภาษาเท่าไรที่ทีมของคุณจะเห็นพ้องว่า mesh คุ้มกับความซับซ้อนในที่สุด และคุณอยู่ห่างจากเส้นนั้นแค่ไหน?
4. ถ้าผู้โจมตีเจาะบริการภายในหนึ่งตัวพรุ่งนี้ มันจะเข้าถึงบริการอื่นใดได้บ้าง และการตรวจตัวตนแบบใดจะหยุดมัน?
5. Mesh แบบไม่มีไซด์คาร์หรือแบบ eBPF บรรลุนิติภาวะพอสำหรับแพลตฟอร์มของคุณหรือยัง และคุณจะวัดอะไรเพื่อตัดสิน?
6. ไคลเอนต์ที่ต่างกันของคุณแต่ละรายต้องการ backend for frontend ของตัวเองจริงหรือ หรือคุณกำลังจะทำตรรกะซ้ำที่ใช้ร่วมกันได้?

## ข้อสรุปสำคัญ

- แยกทราฟฟิกเหนือ-ใต้ (จัดการโดย API gateway) ออกจากทราฟฟิกตะวันออก-ตะวันตก (จัดการโดย service mesh) แต่ละอย่างเป็นเจ้าของทิศทางของตน และการสับสนทำให้เกิดการจัดการซ้ำซ้อน
- Gateway รวมศูนย์การกำหนดเส้นทาง การยืนยันตัวตน การอนุญาต ขีดจำกัดอัตรา โควตา การแปลงคำขอ การประกอบ และการกำกับเวอร์ชัน ทำให้บริการบางและนโยบายอยู่ในที่เดียว
- Service mesh ให้ mTLS การเลื่อนทราฟฟิก การลองใหม่และ circuit breaking ระดับแพลตฟอร์ม และการสังเกตระบบที่สม่ำเสมอโดยไม่เปลี่ยนโค้ดบริการ แบบคลาสสิกผ่านพร็อกซีไซด์คาร์
- นำ mesh มาใช้เมื่อจำนวนบริการและภาษาทำให้การเดินสายรายบริการเป็นเส้นทางที่แพงกว่าเท่านั้น ต่ำกว่านั้นไลบรารีบวก gateway ชนะ และภาษีไซด์คาร์เป็นของจริงพอที่ควรเฝ้าดู
- ปฏิบัติต่อ gateway และ mesh เป็นจุดบังคับใช้นโยบายของสถาปัตยกรรม zero trust มอบหมายแต่ละเรื่องที่ตัดผ่านทุกบริการให้ชั้นเดียวเท่านั้น และตรวจตัวตนในทุกฮอปข้ามคลัสเตอร์
