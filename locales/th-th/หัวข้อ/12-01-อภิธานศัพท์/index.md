# 12.1 อภิธานศัพท์

อภิธานศัพท์นี้ให้นิยามของคำศัพท์และตัวย่อที่ใช้ทั่วทั้งเล่ม เรียงตามลำดับตัวอักษรภาษาอังกฤษ หากรายการใดมีตัวย่อที่นิยมใช้ จะแสดงไว้ในวงเล็บ นิยามตั้งใจเขียนให้กระชับ หากต้องการรายละเอียดเพิ่มเติมให้ดูบทที่เกี่ยวข้อง

## A

**[ABAC (Attribute-Based Access Control)](https://en.wikipedia.org/wiki/Attribute-based_access_control)** (การควบคุมการเข้าถึงตามคุณลักษณะ): แบบจำลองการให้สิทธิ์ที่อนุญาตการเข้าถึงโดยอิงจากคุณลักษณะที่ประเมินได้ของผู้ใช้ ทรัพยากร การกระทำ และสภาพแวดล้อม (เช่น แผนก ระดับการอนุญาตเข้าถึงข้อมูล ช่วงเวลาของวัน) แทนการใช้บทบาทตายตัว ให้การควบคุมที่ละเอียดและขับเคลื่อนด้วยนโยบาย แต่แลกมาด้วยความซับซ้อนที่มากกว่า RBAC

**[Accessibility (a11y)](https://en.wikipedia.org/wiki/Computer_accessibility)** (การเข้าถึงได้): แนวปฏิบัติในการออกแบบและสร้างซอฟต์แวร์ให้ผู้พิการสามารถรับรู้ เข้าใจ นำทาง และใช้งานได้ คำย่อ "a11y" มาจากตัวอักษร 11 ตัวระหว่าง "a" กับ "y"

**ADR (Architecture Decision Record)** (บันทึกการตัดสินใจด้านสถาปัตยกรรม): เอกสารสั้นที่มีการกำหนดเวอร์ชัน บันทึกการตัดสินใจสำคัญด้านสถาปัตยกรรมหรือเทคนิคเรื่องเดียว บริบท ทางเลือกที่พิจารณา และผลที่ตามมา ADR สร้างประวัติที่คงทนและตรวจทานได้ว่าเหตุใดระบบจึงเป็นอย่างที่เป็น

**Aggregate** (แอกกรีเกต): ใน Domain-Driven Design คือกลุ่มของออบเจกต์ในโดเมนที่ถือเป็นหน่วยเดียวสำหรับการเปลี่ยนแปลงข้อมูล โดยมีเอนทิตีหนึ่งทำหน้าที่เป็นรากของแอกกรีเกต (aggregate root) ซึ่งบังคับใช้เงื่อนไขที่ต้องเป็นจริงเสมอ (invariant) แอกกรีเกตกำหนดขอบเขตของความสอดคล้องและทรานแซกชัน

**[API (Application Programming Interface)](https://en.wikipedia.org/wiki/API)** (อินเทอร์เฟซสำหรับการเขียนโปรแกรมประยุกต์): สัญญาที่กำหนดไว้ซึ่งซอฟต์แวร์ชิ้นหนึ่งใช้ขอบริการหรือข้อมูลจากอีกชิ้นหนึ่ง API ที่ออกแบบดีจะซ่อนรายละเอียดการสร้าง และให้อินเทอร์เฟซที่เสถียรและมีเวอร์ชัน

**API-first** (ออกแบบ API ก่อน): แนวทางการพัฒนาที่ออกแบบและตกลงสัญญา API กันก่อนลงมือสร้าง เพื่อให้ผู้ใช้และผู้ให้บริการทำงานขนานกันได้ตามข้อกำหนดร่วมกัน

**arc42**: โครงสร้างแบบเปิดที่อิงแม่แบบสำหรับจัดทำเอกสารสถาปัตยกรรมซอฟต์แวร์ แบ่งเป็นสิบสองหัวข้อ ครอบคลุมบริบท ข้อจำกัด องค์ประกอบ พฤติกรรมขณะรัน การปรับใช้ และการตัดสินใจ

**[ARIA (Accessible Rich Internet Applications)](https://en.wikipedia.org/wiki/WAI-ARIA)**: ข้อกำหนดของ W3C ที่นิยามบทบาท สถานะ และคุณสมบัติ เพื่อให้คอมโพเนนต์เว็บแบบไดนามิกและแบบกำหนดเองเป็นที่เข้าใจของเทคโนโลยีช่วยเหลือ เช่น โปรแกรมอ่านหน้าจอ

**ASR (Architecturally Significant Requirement)** (ข้อกำหนดที่มีนัยสำคัญต่อสถาปัตยกรรม): ข้อกำหนดที่มีผลวัดได้และกว้างขวางต่อสถาปัตยกรรม เช่น ข้อจำกัดด้านประสิทธิภาพ ความพร้อมใช้งาน ความมั่นคงปลอดภัย หรือกฎระเบียบ ASR ขับเคลื่อนการตัดสินใจเชิงออกแบบที่สำคัญที่สุด

**ASVS (Application Security Verification Standard)**: มาตรฐานของ OWASP ที่ให้รายการตรวจสอบแบบแบ่งระดับของข้อกำหนดและการทดสอบด้านความมั่นคงปลอดภัย สำหรับออกแบบ สร้าง และตรวจสอบแอปพลิเคชันที่ปลอดภัย

**[Autoscaling](https://en.wikipedia.org/wiki/Autoscaling)** (การปรับขนาดอัตโนมัติ): การปรับจำนวน (หรือขนาด) ของอินสแตนซ์คอมพิวต์ที่ทำงานอยู่โดยอัตโนมัติตามภาระงาน เพื่อให้ความจุตามความต้องการโดยไม่ต้องแทรกแซงด้วยมือ ช่วยเสริมแต่ไม่อาจแทนการวางแผนความจุอย่างตั้งใจ

**[Availability](https://en.wikipedia.org/wiki/Availability)** (ความพร้อมใช้งาน): สัดส่วนเวลาที่ระบบทำงานและให้บริการคำขอได้ มักระบุเป็น "ไนน์" (เช่น 99.9%) เป็นเป้าหมายความน่าเชื่อถือหลักที่กำหนดไว้ใน SLO และ SLA

## B

**Backpressure** (แรงดันย้อนกลับ): กลไกควบคุมการไหลที่คอมโพเนนต์ซึ่งรับภาระหนักส่งสัญญาณไปยังผู้ผลิตต้นทางให้ชะลอลง เพื่อป้องกันคิวที่โตไม่มีขอบเขตและความล้มเหลวแบบลูกโซ่ เป็นหัวใจของระบบสตรีมและระบบที่ขับเคลื่อนด้วยข้อความที่เชื่อถือได้

**[BDD (Behaviour-Driven Development)](https://en.wikipedia.org/wiki/Behavior-driven_development)** (การพัฒนาที่ขับเคลื่อนด้วยพฤติกรรม): แนวปฏิบัติแบบร่วมมือที่เขียนข้อกำหนดเป็นตัวอย่างพฤติกรรมที่เป็นรูปธรรมและมนุษย์อ่านเข้าใจ (มักอยู่ในรูป Given/When/Then) ซึ่งทำหน้าที่เป็นการทดสอบเพื่อการยอมรับแบบอัตโนมัติไปพร้อมกัน

**BFF (Backend for Frontend)**: รูปแบบสถาปัตยกรรมที่สร้างบริการแบ็กเอนด์เฉพาะสำหรับฟรอนต์เอนด์หรือประเภทไคลเอนต์หนึ่ง ๆ ปรับรูปแบบและการรวมข้อมูลให้ตรงกับความต้องการของไคลเอนต์นั้น

**[BI (Business Intelligence)](https://en.wikipedia.org/wiki/Business_intelligence)** (ธุรกิจอัจฉริยะ): เครื่องมือ กระบวนการ และแนวปฏิบัติสำหรับรวบรวม ผสาน และวิเคราะห์ข้อมูลธุรกิจ เพื่อสนับสนุนการทำรายงาน แดชบอร์ด และการตัดสินใจ

**Blameless postmortem** (การทบทวนเหตุการณ์แบบไม่กล่าวโทษ): การทบทวนเหตุการณ์ขัดข้องที่เน้นสาเหตุเชิงระบบและการเรียนรู้ แทนการหาคนผิด ด้วยความเชื่อว่าคนเราทำสิ่งที่สมเหตุสมผลตามข้อมูลและแรงจูงใจที่มีอยู่

**[Blue-green deployment](https://en.wikipedia.org/wiki/Blue-green_deployment)** (การปรับใช้แบบ blue-green): กลยุทธ์การปล่อยที่รันสภาพแวดล้อมโปรดักชันที่เหมือนกันสองชุด ("blue" และ "green") โดยส่งทราฟฟิกไปที่ชุดหนึ่งขณะอัปเดตอีกชุด ทำให้สลับและย้อนกลับได้เกือบทันที

**[BM25](https://en.wikipedia.org/wiki/Okapi_BM25)**: ฟังก์ชันจัดอันดับที่ใช้กันกว้างขวางสำหรับการค้นหาข้อความเต็ม ให้คะแนนว่าเอกสารตรงกับคำค้นเพียงใด โดยใช้ความถี่ของคำ ความถี่เอกสารผกผัน และความยาวเอกสาร เป็นค่าเริ่มต้นของการจัดอันดับตามคำในเสิร์ชเอนจินจำนวนมาก

**Bounded context** (บริบทที่มีขอบเขต): ใน Domain-Driven Design คือขอบเขตที่ชัดเจนซึ่งแบบจำลองโดเมนหนึ่งและภาษาร่วม (ubiquitous language) ของมันใช้ได้อย่างสอดคล้องกัน ช่วยป้องกันไม่ให้แนวคิดปะปนกันข้ามส่วนต่าง ๆ ของระบบขนาดใหญ่

**Build cache** (แคชของการบิลด์): ที่เก็บผลลัพธ์การบิลด์ที่คำนวณไว้แล้ว โดยใช้อินพุตที่ก่อให้เกิดผลลัพธ์เป็นคีย์ เพื่อให้งานที่ไม่เปลี่ยนแปลงถูกนำกลับมาใช้แทนการบิลด์ใหม่ แคชบิลด์ระยะไกลที่ใช้ร่วมกันทำให้ทั้งทีมและ CI ใช้ผลของกันและกันได้

**[Bus factor](https://en.wikipedia.org/wiki/Bus_factor)** (ปัจจัยรถบัส): จำนวนคนที่ต้องหายไป (เปรียบเปรยว่า "ถูกรถบัสชน") ก่อนที่โครงการจะชะงักเพราะขาดความรู้ที่จำเป็น ค่าต่ำบ่งบอกว่าความเชี่ยวชาญกระจุกตัวและไม่ได้บันทึกไว้ และเป็นความเสี่ยงขององค์กร

## C

**[Cache eviction policy](https://en.wikipedia.org/wiki/Cache_replacement_policies)** (นโยบายการขับรายการออกจากแคช): กฎที่แคชใช้ตัดสินว่าจะนำรายการใดออกเมื่อเต็ม เช่น ใช้ล่าสุดน้อยที่สุด (LRU) หรือใช้บ่อยน้อยที่สุด (LFU) นโยบายนี้กำหนดอัตราการเจอข้อมูลในแคช (hit rate) และคุณค่าของแคชไปด้วย

**[Cache invalidation](https://en.wikipedia.org/wiki/Cache_invalidation)** (การทำให้แคชใช้ไม่ได้): ปัญหาการลบหรืออัปเดตข้อมูลในแคชเมื่อแหล่งข้อมูลต้นทางเปลี่ยน เพื่อไม่ให้ผู้อ่านเห็นค่าที่ล้าสมัย เป็นที่รู้กันว่าเป็นหนึ่งในปัญหาที่ยากที่สุดในวงการคอมพิวเตอร์

**[Cache stampede](https://en.wikipedia.org/wiki/Cache_stampede)** (แคชพังพร้อมกัน): รูปแบบความล้มเหลวที่ไคลเอนต์จำนวนมากพลาดแคชของคีย์เดียวกันพร้อมกัน แล้วกรูกันไปที่ต้นทางจนท่วม ป้องกันได้ด้วยการรวมคำขอ (request coalescing) และการกระจายเวลาหมดอายุ เรียกอีกอย่างว่า thundering herd

**Canary release** (การปล่อยแบบ canary): เทคนิคการปรับใช้ที่เปิดเวอร์ชันใหม่ให้ผู้ใช้หรือทราฟฟิกกลุ่มเล็กก่อน คอยดูปัญหา แล้วขยายการปล่อยทีละน้อยหากตัวชี้วัดยังปกติดี

**[CAP theorem](https://en.wikipedia.org/wiki/CAP_theorem)** (ทฤษฎีบท CAP): หลักการที่ระบุว่าที่เก็บข้อมูลแบบกระจายรับประกันได้อย่างมากสองในสามข้อพร้อมกัน ได้แก่ ความสอดคล้อง (Consistency) ความพร้อมใช้งาน (Availability) และความทนต่อการแบ่งเครือข่าย (Partition tolerance) เนื่องจากเลี่ยงการแบ่งเครือข่ายไม่ได้ นักออกแบบจึงต้องแลกเปลี่ยนระหว่างความสอดคล้องกับความพร้อมใช้งานในช่วงนั้น

**[C4 model](https://en.wikipedia.org/wiki/C4_model)** (แบบจำลอง C4): แนวทางเบา ๆ สำหรับทำภาพสถาปัตยกรรมซอฟต์แวร์ในสี่ระดับของนามธรรม ได้แก่ System Context, Containers, Components และ Code

**[CD (Continuous Delivery / Continuous Deployment)](https://en.wikipedia.org/wiki/Continuous_delivery)** (การส่งมอบ/การปรับใช้อย่างต่อเนื่อง): Continuous Delivery รักษาซอฟต์แวร์ให้พร้อมปล่อยอยู่เสมอ ปรับใช้ได้ทุกเมื่อโดยมีการอนุมัติด้วยมือ ส่วน Continuous Deployment ปล่อยทุกการเปลี่ยนแปลงที่ผ่านไปป์ไลน์โดยอัตโนมัติ

**[CDN (Content Delivery Network)](https://en.wikipedia.org/wiki/Content_delivery_network)** (เครือข่ายส่งมอบเนื้อหา): เครือข่ายเซิร์ฟเวอร์ขอบ (edge) ที่กระจายตามภูมิศาสตร์ ทำหน้าที่แคชและให้บริการเนื้อหาใกล้ผู้ใช้ ลดความหน่วงและแบ่งเบาภาระโครงสร้างพื้นฐานต้นทาง

**Chain-of-thought prompting** (การเขียนพรอมต์แบบลำดับความคิด): เทคนิคการเขียนพรอมต์ที่ให้โมเดลภาษาไล่เรียงขั้นตอนการให้เหตุผลระหว่างทางก่อนตอบ ช่วยให้ทำปัญหาหลายขั้นตอนได้ดีขึ้น แลกกับผลลัพธ์ที่ยาวและช้าลง

**[CI (Continuous Integration)](https://en.wikipedia.org/wiki/Continuous_integration)** (การรวมโค้ดอย่างต่อเนื่อง): แนวปฏิบัติที่นักพัฒนารวมการเปลี่ยนแปลงเข้าสู่สายหลักที่ใช้ร่วมกันบ่อย ๆ โดยการรวมแต่ละครั้งถูกตรวจสอบด้วยการบิลด์และชุดทดสอบอัตโนมัติ เพื่อตรวจพบปัญหาการผสานตั้งแต่เนิ่น ๆ

**[CI/CD](https://en.wikipedia.org/wiki/CI/CD)**: ไปป์ไลน์ที่รวม Continuous Integration กับ Continuous Delivery/Deployment เข้าด้วยกัน เพื่อทำการบิลด์ ทดสอบ และปล่อยซอฟต์แวร์โดยอัตโนมัติ

**CMMC (Cybersecurity Maturity Model Certification)**: โครงการของกระทรวงกลาโหมสหรัฐฯ ที่รับรองวุฒิภาวะด้านความมั่นคงปลอดภัยไซเบอร์ของผู้รับเหมาที่จัดการข้อมูลสัญญาของรัฐบาลกลางและข้อมูลที่ไม่เป็นความลับแต่ต้องควบคุม

**[Cohesion](https://en.wikipedia.org/wiki/Cohesion_(computer_science))** (ความเกาะเกี่ยวกัน): ระดับที่องค์ประกอบภายในโมดูลเข้ากันและรับใช้จุดประสงค์เดียวที่นิยามไว้ชัดเจน ความเกาะเกี่ยวสูงคู่กับการพึ่งพากันต่ำเป็นเครื่องหมายของการออกแบบที่ดูแลรักษาง่าย

**Context window** (หน้าต่างบริบท): ปริมาณข้อความสูงสุด วัดเป็นโทเค็น ที่โมเดลภาษาพิจารณาได้ในคราวเดียว ครอบคลุมทั้งอินพุตและเอาต์พุต เป็นงบที่มีจำกัดซึ่งการออกแบบพรอมต์และบริบทต้องบริหารอย่างตั้งใจ

**[Conway's Law](https://en.wikipedia.org/wiki/Conway's_law)** (กฎของคอนเวย์): ข้อสังเกตว่าโครงสร้างของระบบมักสะท้อนโครงสร้างการสื่อสารขององค์กรที่สร้างมัน "inverse Conway manoeuvre" คือการจัดทีมอย่างตั้งใจเพื่อให้ได้สถาปัตยกรรมที่ต้องการ

**Core Web Vitals**: ชุดตัวชี้วัดประสิทธิภาพเว็บที่ยึดผู้ใช้เป็นศูนย์กลางซึ่ง Google กำหนดไว้ (เช่น Largest Contentful Paint, Interaction to Next Paint และ Cumulative Layout Shift) วัดการโหลด การโต้ตอบ และความเสถียรทางสายตา

**[Cost of delay](https://en.wikipedia.org/wiki/Cost_of_delay)** (ต้นทุนของความล่าช้า): ต้นทุนทางเศรษฐศาสตร์ของการที่บางอย่างยังไม่เสร็จ แสดงเป็นมูลค่าที่สูญเสียต่อหนึ่งหน่วยเวลา การทำให้ชัดเจนเปลี่ยนการจัดลำดับความสำคัญจากความเห็นให้เป็นเลขคณิต และเป็นฐานของกฎการจัดลำดับเช่น weighted shortest job first

**[Coupling](https://en.wikipedia.org/wiki/Coupling_(computer_programming))** (การพึ่งพากัน): ระดับของการพึ่งพากันระหว่างโมดูลหรือบริการ การพึ่งพากันหลวม ๆ จำกัดผลกระทบลูกคลื่นของการเปลี่ยนแปลง และเป็นเป้าหมายหลักของสถาปัตยกรรมที่ดี

**CQRS (Command Query Responsibility Segregation)** (การแยกความรับผิดชอบระหว่างคำสั่งและคำค้น): รูปแบบที่แยกแบบจำลองที่ใช้เปลี่ยนสถานะ (คำสั่ง) ออกจากแบบจำลองที่ใช้อ่านสถานะ (คำค้น) ทำให้ปรับแต่งและขยายขนาดแต่ละฝั่งได้อิสระ

**[CVE (Common Vulnerabilities and Exposures)](https://en.wikipedia.org/wiki/Common_Vulnerabilities_and_Exposures)**: ทะเบียนสาธารณะของช่องโหว่ความมั่นคงปลอดภัยที่เปิดเผยแล้ว แต่ละรายการมีรหัสเฉพาะ เพื่อให้เครื่องมือและทีมอ้างถึงข้อบกพร่องเดียวกันได้อย่างไม่กำกวม

**CWV**: ดู Core Web Vitals

## D

**[DAST (Dynamic Application Security Testing)](https://en.wikipedia.org/wiki/Dynamic_application_security_testing)** (การทดสอบความมั่นคงปลอดภัยของแอปพลิเคชันแบบไดนามิก): การทดสอบความมั่นคงปลอดภัยที่สำรวจแอปพลิเคชันที่กำลังทำงานจากภายนอก โดยไม่เข้าถึงซอร์สโค้ด เพื่อหาช่องโหว่ที่ปรากฏขณะรัน

**Data-ink ratio** (สัดส่วนหมึกข้อมูล): หลักการของ Edward Tufte ที่ว่าแผนภูมิควรใช้หมึกส่วนใหญ่กับตัวข้อมูลเอง และใช้กับการตกแต่งน้อยที่สุด โดยตัดเส้นตาราง กรอบ และ chartjunk ที่ไม่ได้ให้ข้อมูลออก

**[Data mesh](https://en.wikipedia.org/wiki/Data_mesh)**: สถาปัตยกรรมข้อมูลแบบกระจายศูนย์และรูปแบบการดำเนินงาน ที่ถือว่าข้อมูลเป็นผลิตภัณฑ์ซึ่งทีมโดเมนเป็นเจ้าของ โดยมีโครงสร้างพื้นฐานแพลตฟอร์มแบบบริการตนเองและธรรมาภิบาลแบบสหพันธ์คอยสนับสนุน

**[Data visualisation](https://en.wikipedia.org/wiki/Data_and_information_visualization)** (การแสดงข้อมูลด้วยภาพ): แนวปฏิบัติในการเข้ารหัสข้อมูลเป็นรูปแบบที่มองเห็นได้ (ตำแหน่ง ความยาว สี และอื่น ๆ) เพื่อให้เห็นแบบรูป การเปรียบเทียบ และแนวโน้ม และตัดสินใจได้ดีขึ้น

**[DDD (Domain-Driven Design)](https://en.wikipedia.org/wiki/Domain-driven_design)** (การออกแบบที่ขับเคลื่อนด้วยโดเมน): แนวทางออกแบบซอฟต์แวร์ที่วางแบบจำลองไว้ที่โดเมนธุรกิจ ใช้ภาษาร่วม (ubiquitous language) บริบทที่มีขอบเขต และหน่วยประกอบอย่างเอนทิตี ออบเจกต์ค่า และแอกกรีเกต

**Design tokens** (โทเค็นการออกแบบ): ค่าที่ตั้งชื่อไว้และไม่ผูกกับแพลตฟอร์ม (สี ระยะห่าง ตัวอักษร และอื่น ๆ) ที่เก็บการตัดสินใจด้านการออกแบบ เพื่อให้ใช้ร่วมกันได้อย่างสอดคล้องทั่วทั้งระบบการออกแบบและผลิตภัณฑ์หลายตัว

**DevEx / DevX (Developer Experience)** (ประสบการณ์ของนักพัฒนา): คุณภาพโดยรวมของการที่นักพัฒนาใช้เครื่องมือ แพลตฟอร์ม และกระบวนการในแต่ละวัน ครอบคลุมแรงเสียดทาน ความเร็วของฟีดแบ็ก และภาระทางความคิด

**[DevOps](https://en.wikipedia.org/wiki/DevOps)**: วัฒนธรรมและชุดแนวปฏิบัติที่รวมการพัฒนาซอฟต์แวร์กับการปฏิบัติการเข้าด้วยกัน เพื่อย่นรอบการส่งมอบ เพิ่มความถี่ในการปรับใช้ และเพิ่มความน่าเชื่อถือด้วยระบบอัตโนมัติและความเป็นเจ้าของร่วมกัน

**DORA (DevOps Research and Assessment)**: โครงการวิจัยและตัวชี้วัดการส่งมอบสี่ตัวที่ใช้กันแพร่หลาย (ความถี่ในการปรับใช้ ระยะเวลานำของการเปลี่ยนแปลง อัตราการเปลี่ยนแปลงที่ล้มเหลว และเวลาในการกู้คืนบริการ) ใช้เทียบเคียงประสิทธิภาพการส่งมอบซอฟต์แวร์

**DPIA (Data Protection Impact Assessment)** (การประเมินผลกระทบด้านการคุ้มครองข้อมูล): การประเมินอย่างเป็นระบบซึ่ง GDPR กำหนดสำหรับการประมวลผลที่มีความเสี่ยงสูง เพื่อระบุและลดความเสี่ยงด้านความเป็นส่วนตัวก่อนเริ่มโครงการ

**Drift (configuration)** (การเบี่ยงเบนของคอนฟิกูเรชัน): การที่สถานะจริงของระบบค่อย ๆ ห่างจากสถานะที่ประกาศหรือตั้งใจไว้ มักเกิดจากการแก้ไขด้วยมือ Infrastructure as Code และ GitOps มุ่งตรวจจับและแก้ไขสิ่งนี้

**Drift (model)** (การเบี่ยงเบนของโมเดล): ในแมชชีนเลิร์นนิง คือประสิทธิภาพของโมเดลที่เสื่อมลงตามเวลา เมื่อคุณสมบัติทางสถิติของข้อมูลนำเข้า (data drift) หรือความสัมพันธ์ที่ถูกสร้างแบบจำลอง (concept drift) เปลี่ยนไป

**[DR (Disaster Recovery)](https://en.wikipedia.org/wiki/Disaster_recovery)** (การกู้คืนจากภัยพิบัติ): กลยุทธ์ ขั้นตอน และโครงสร้างพื้นฐานสำหรับกู้คืนบริการและข้อมูลหลังเหตุการณ์ใหญ่ที่ก่อให้เกิดการหยุดชะงัก โดยทั่วไปกำกับด้วยเป้าหมาย RTO และ RPO

**[DRY (Don't Repeat Yourself)](https://en.wikipedia.org/wiki/Don't_repeat_yourself)** (อย่าทำซ้ำ): หลักการออกแบบที่ว่าความรู้ทุกชิ้นควรมีตัวแทนที่เป็นทางการเพียงหนึ่งเดียว เพื่อลดความซ้ำซ้อนและความเสี่ยงที่การอัปเดตจะไม่สอดคล้องกัน

## E

**East-west traffic** (ทราฟฟิกแนวตะวันออก-ตะวันตก): ทราฟฟิกเครือข่ายระหว่างบริการภายในระบบหรือศูนย์ข้อมูล ต่างจากทราฟฟิกแนวเหนือ-ใต้ที่ไหลระหว่างระบบกับไคลเอนต์ภายนอก โดยทั่วไป service mesh ดูแลทราฟฟิกแนวตะวันออก-ตะวันตก

**[Edge computing](https://en.wikipedia.org/wiki/Edge_computing)** (การประมวลผลที่ขอบเครือข่าย): การรันการประมวลผลและการจัดเก็บใกล้จุดที่ข้อมูลถูกสร้างหรือถูกใช้ แทนที่จะอยู่ศูนย์กลาง เพื่อลดความหน่วงและแบนด์วิดท์ เครือข่ายส่งมอบเนื้อหาเป็นรูปแบบแรกเริ่มที่แพร่หลาย

**[Elasticity](https://en.wikipedia.org/wiki/Elasticity_(cloud_computing))** (ความยืดหยุ่นของทรัพยากร): ความสามารถของระบบในการได้มาและคืนทรัพยากรโดยอัตโนมัติตามความต้องการที่เปลี่ยนไป เพื่อให้ความจุตามภาระงานได้ใกล้ชิด

**[ELT (Extract, Load, Transform)](https://en.wikipedia.org/wiki/Extract,_load,_transform)**: รูปแบบการผสานข้อมูลที่โหลดข้อมูลดิบเข้าที่เก็บปลายทางก่อน แล้วแปลงที่นั่น โดยใช้ประโยชน์จากขนาดของคลังข้อมูลและ lakehouse สมัยใหม่

**[Embedding](https://en.wikipedia.org/wiki/Word_embedding)** (เอมเบดดิง): การแทนข้อความ รูปภาพ หรือข้อมูลอื่นด้วยเวกเตอร์ตัวเลขหนาแน่น วางตำแหน่งให้สิ่งที่คล้ายกันอยู่ใกล้กัน เอมเบดดิงเป็นพลังของการค้นหาเชิงความหมายและเวกเตอร์ และของ retrieval-augmented generation

**[EN 301 549](https://en.wikipedia.org/wiki/EN_301_549)**: มาตรฐานยุโรปที่กำหนดข้อกำหนดด้านการเข้าถึงได้สำหรับผลิตภัณฑ์และบริการ ICT ซึ่งการจัดซื้อภาครัฐทั่ว EU อ้างอิง และสอดคล้องกับ WCAG

**Error budget** (งบความผิดพลาด): ปริมาณความไม่น่าเชื่อถือที่ SLO ยอมให้ในช่วงเวลาหนึ่ง เมื่อใช้หมด ทีมจะให้ความสำคัญกับงานด้านความน่าเชื่อถือก่อนฟีเจอร์ใหม่ ช่วยประสานความตึงเครียดระหว่างความเร็วกับเสถียรภาพ

**[ETL (Extract, Transform, Load)](https://en.wikipedia.org/wiki/Extract,_transform,_load)**: รูปแบบการผสานข้อมูลที่ดึงข้อมูลจากแหล่ง แปลงเป็นรูปแบบเป้าหมาย แล้วโหลดเข้าปลายทาง เช่น คลังข้อมูล

**[EU AI Act](https://en.wikipedia.org/wiki/Artificial_Intelligence_Act)** (กฎหมายปัญญาประดิษฐ์ของสหภาพยุโรป): กฎระเบียบของสหภาพยุโรปที่จัดประเภทระบบ AI ตามความเสี่ยงและกำหนดภาระผูกพันตามนั้น ห้ามการใช้งานบางอย่างและกำกับระบบความเสี่ยงสูงอย่างเข้มงวด

**[Eventual consistency](https://en.wikipedia.org/wiki/Eventual_consistency)** (ความสอดคล้องในที่สุด): แบบจำลองความสอดคล้องในระบบกระจายที่เรพลิกาอาจต่างกันชั่วคราว แต่จะลู่เข้าสู่สถานะเดียวกันเมื่อการอัปเดตหยุดแพร่กระจาย

## F

**[Feature flag / feature toggle](https://en.wikipedia.org/wiki/Feature_toggle)** (สวิตช์เปิดปิดฟีเจอร์): กลไกเปิดหรือปิดฟังก์ชันขณะรันโดยไม่ต้องปรับใช้ใหม่ ใช้สำหรับการปล่อยแบบค่อยเป็นค่อยไป การทดลอง และการควบคุมการปฏิบัติการ

**Feature store** (ที่เก็บฟีเจอร์): ระบบศูนย์กลางสำหรับกำหนด จัดเก็บ และให้บริการฟีเจอร์ของแมชชีนเลิร์นนิงที่คัดสรรแล้วอย่างสอดคล้องทั้งการฝึกและการอนุมาน ลดความซ้ำซ้อนและความเหลื่อมล้ำระหว่างการฝึกกับการให้บริการ (training/serving skew)

**[FedRAMP (Federal Risk and Authorisation Management Program)](https://en.wikipedia.org/wiki/FedRAMP)**: โครงการของรัฐบาลสหรัฐฯ ที่กำหนดมาตรฐานการประเมินความมั่นคงปลอดภัย การอนุญาต และการเฝ้าติดตามต่อเนื่องสำหรับบริการคลาวด์ที่หน่วยงานรัฐบาลกลางใช้

**Few-shot prompting** (การเขียนพรอมต์แบบให้ตัวอย่างไม่กี่ชุด): การให้ตัวอย่างงานที่ทำเสร็จแล้วจำนวนหนึ่งแก่โมเดลภาษาในพรอมต์ เพื่อแสดงงานและรูปแบบผลลัพธ์ที่ต้องการ ต่างจาก zero-shot ที่ให้คำสั่งโดยไม่มีตัวอย่าง

**FinOps**: วินัยและแนวปฏิบัติทางวัฒนธรรมที่นำความรับผิดชอบทางการเงินมาสู่ค่าใช้จ่ายคลาวด์ที่ผันแปร ให้ทีมวิศวกรรม การเงิน และธุรกิจร่วมเป็นเจ้าของต้นทุนและคุณค่า

**[FISMA (Federal Information Security Modernisation Act)](https://en.wikipedia.org/wiki/Federal_Information_Security_Management_Act)**: กฎหมายสหรัฐฯ ที่กำหนดให้หน่วยงานรัฐบาลกลางจัดทำ บันทึก และเฝ้าติดตามโครงการความมั่นคงปลอดภัยของข้อมูล ซึ่งปฏิบัติจริงส่วนใหญ่ผ่านแนวทางของ NIST

**Flow efficiency** (ประสิทธิภาพของการไหลของงาน): สัดส่วนของระยะเวลานำทั้งหมดที่งานชิ้นหนึ่งถูกลงมือทำจริง ไม่ใช่รอคอย คำนวณจากเวลาที่เพิ่มคุณค่าหารด้วยระยะเวลานำทั้งหมด ระบบส่วนใหญ่ต่ำอย่างน่าตกใจ มักไม่ถึง 15 เปอร์เซ็นต์

**Four-eyes principle** (หลักการสี่ตา): มาตรการควบคุมที่กำหนดให้การกระทำสำคัญต้องมีคนทบทวนหรืออนุมัติอย่างน้อยสองคน เพื่อลดโอกาสเกิดข้อผิดพลาดหรือการทุจริต

**[Fuzz testing (fuzzing)](https://en.wikipedia.org/wiki/Fuzzing)** (การทดสอบแบบ fuzz): เทคนิคการทดสอบอัตโนมัติที่ป้อนอินพุตที่ผิดรูป สุ่ม หรือไม่คาดคิดให้โปรแกรม เพื่อค้นหาการล่ม ช่องโหว่ด้านความมั่นคงปลอดภัย และข้อบกพร่องในกรณีขอบ

## G

**[GDPR (General Data Protection Regulation)](https://en.wikipedia.org/wiki/General_Data_Protection_Regulation)** (กฎระเบียบการคุ้มครองข้อมูลส่วนบุคคลของสหภาพยุโรป): กฎระเบียบของสหภาพยุโรปที่กำกับการประมวลผลข้อมูลส่วนบุคคล ให้สิทธิแก่บุคคลและกำหนดภาระแก่ผู้ควบคุมและผู้ประมวลผลข้อมูล พร้อมบทลงโทษที่สูงหากไม่ปฏิบัติตาม

**GitOps**: รูปแบบการดำเนินงานที่ใช้ Git เป็นแหล่งความจริงเดียวสำหรับโครงสร้างพื้นฐานและแอปพลิเคชันแบบประกาศ (declarative) โดยระบบอัตโนมัติปรับระบบจริงให้ตรงกับสถานะที่คอมมิตไว้อย่างต่อเนื่อง

**Golden path / paved road** (เส้นทางทอง / ถนนลาดยาง): วิธีสร้างและส่งมอบซอฟต์แวร์เริ่มต้นที่มีการสนับสนุนดีและมีแนวทางชัดเจนภายในองค์กร ออกแบบให้ทางเลือกที่ปลอดภัย สอดคล้องกฎระเบียบ และเชื่อถือได้เป็นทางเลือกที่ง่ายที่สุด

**Golden record** (ระเบียนทอง): ในการบริหารข้อมูลหลัก (master data management) คือเวอร์ชันเดียวที่ผ่านการกระทบยอดและเป็นทางการของเอนทิตีทางธุรกิจ (เช่น ลูกค้า) ซึ่งประกอบขึ้นจากระบบต้นทางหลายระบบด้วยกฎการจับคู่และกฎการเลือกค่าที่คงอยู่ (survivorship)

**[Gradual typing](https://en.wikipedia.org/wiki/Gradual_typing)** (ระบบชนิดข้อมูลแบบค่อยเป็นค่อยไป): แนวทางของระบบชนิดข้อมูลที่ให้การกำหนดชนิดแบบสถิตและแบบพลวัตอยู่ร่วมกันในโค้ดเบสเดียว จึงเพิ่มชนิดข้อมูลทีละน้อยให้โปรแกรมที่เดิมไม่มีชนิดได้ type hint และตัวตรวจชนิดข้อมูลแบบทางเลือกเป็นตัวอย่างที่พบบ่อย

**[GraphQL](https://en.wikipedia.org/wiki/GraphQL)**: ภาษาคำค้นและรันไทม์สำหรับ API ที่ให้ไคลเอนต์ขอเฉพาะข้อมูลที่ต้องการได้ในการเรียกเดียว โดยใช้สคีมาที่มีชนิดข้อมูลเข้มงวด

**[gRPC](https://en.wikipedia.org/wiki/gRPC)**: เฟรมเวิร์กการเรียกโพรซีเดอร์ระยะไกลประสิทธิภาพสูงแบบสัญญานำ (contract-first) ใช้ HTTP/2 และโดยทั่วไปใช้ Protocol Buffers เพื่อการสื่อสารระหว่างบริการอย่างมีประสิทธิภาพ

## H

**Hermetic build** (การบิลด์แบบปิดสนิท): การบิลด์ที่พึ่งพาเฉพาะอินพุตที่ประกาศไว้ชัดเจนและแยกจากสภาพแวดล้อมของเครื่องโฮสต์ จึงให้ผลลัพธ์เดียวกันไม่ว่ารันที่ไหน ความปิดสนิทเป็นรากฐานของการบิลด์ที่ทำซ้ำได้และการแคชที่เชื่อถือได้

**[HSM (Hardware Security Module)](https://en.wikipedia.org/wiki/Hardware_security_module)** (โมดูลความมั่นคงปลอดภัยด้านฮาร์ดแวร์): อุปกรณ์ฮาร์ดแวร์ที่ทนต่อการแกะรื้อ ทำหน้าที่สร้าง จัดเก็บ และใช้กุญแจเข้ารหัส ให้การป้องกันกุญแจที่แข็งแรงกว่าวิธีที่ใช้ซอฟต์แวร์ล้วน ๆ

**[HIPAA (Health Insurance Portability and Accountability Act)](https://en.wikipedia.org/wiki/Health_Insurance_Portability_and_Accountability_Act)**: กฎหมายสหรัฐฯ ที่กำหนดข้อกำหนดการปกป้องข้อมูลสุขภาพที่ได้รับการคุ้มครอง (PHI) และกำกับการใช้และการเปิดเผยข้อมูลนั้น รวมถึงเรื่องอื่น ๆ

**Horizontal scaling** (การขยายแนวนอน): การเพิ่มความจุด้วยการเพิ่มอินสแตนซ์หรือโหนด ("scaling out") แทนการทำให้โหนดเดียวทรงพลังขึ้น เป็นรากฐานของสถาปัตยกรรมขนาดใหญ่ที่ยืดหยุ่นทนทานส่วนใหญ่

## I

**[IaC (Infrastructure as Code)](https://en.wikipedia.org/wiki/Infrastructure_as_code)** (โครงสร้างพื้นฐานเป็นโค้ด): แนวปฏิบัติในการกำหนดและจัดเตรียมโครงสร้างพื้นฐานผ่านคอนฟิกที่เครื่องอ่านได้และอยู่ภายใต้การควบคุมเวอร์ชัน แทนกระบวนการด้วยมือ ทำให้ทำซ้ำและตรวจทานได้

**[IAM (Identity and Access Management)](https://en.wikipedia.org/wiki/Identity_management)** (การบริหารตัวตนและการเข้าถึง): กรอบของนโยบายและเทคโนโลยีที่ทำให้ตัวตนที่ถูกต้องเข้าถึงทรัพยากรที่ถูกต้องในเวลาที่ถูกต้อง

**IDP / IdP**: "IDP" มักหมายถึง Internal Developer Platform ชั้นเครื่องมือบริการตนเองที่ซ่อนความซับซ้อนของโครงสร้างพื้นฐานให้ทีมผลิตภัณฑ์ ส่วน "IdP" หมายถึง Identity Provider บริการที่ยืนยันตัวตนผู้ใช้และออกการรับรอง (assertion) ให้ดูบริบทเพื่อแยกสองคำนี้

**[Idempotency](https://en.wikipedia.org/wiki/Idempotence)** (ภาวะนิจพล): คุณสมบัติที่ทำการดำเนินการหลายครั้งได้ผลเท่ากับทำครั้งเดียว จำเป็นต่อการลองใหม่อย่างปลอดภัยในระบบกระจายและ API

**[i18n (Internationalisation)](https://en.wikipedia.org/wiki/Internationalization_and_localization)** (การทำให้เป็นสากล): การออกแบบและสร้างซอฟต์แวร์ให้ปรับใช้กับภาษา ภูมิภาค และธรรมเนียมทางวัฒนธรรมต่าง ๆ ได้โดยไม่ต้องแก้ทางวิศวกรรม คำย่อมาจากตัวอักษร 18 ตัวระหว่าง "i" กับ "n"

**Immutable artefact** (อาร์ติแฟกต์ที่ไม่เปลี่ยนแปลง): ผลลัพธ์จากการบิลด์ที่เมื่อสร้างและกำหนดเวอร์ชันแล้วจะไม่ถูกแก้ไขอีก การเปลี่ยนแปลงใด ๆ ให้เวอร์ชันใหม่ ความไม่เปลี่ยนแปลงทำให้ทำซ้ำการปล่อยได้ และให้บิลด์ครั้งเดียวแล้วเลื่อนอาร์ติแฟกต์เดียวกันข้ามสภาพแวดล้อม

**InnerSource**: การนำแนวปฏิบัติการพัฒนาแบบโอเพนซอร์ส (ความโปร่งใส คลังโค้ดที่ใช้ร่วมกัน และการมีส่วนร่วมข้ามทีม) มาใช้ภายในองค์กรเดียว

**IaC drift**: ดู Drift (configuration)

**[Inverted index](https://en.wikipedia.org/wiki/Inverted_index)** (ดัชนีผกผัน): โครงสร้างข้อมูลหลักของเสิร์ชเอนจิน ที่แมปแต่ละคำไปยังรายการเอกสารที่มีคำนั้น ทำให้ตอบคำค้นได้โดยไม่ต้องไล่ทุกเอกสาร

**[ISO/IEC 27001](https://en.wikipedia.org/wiki/ISO/IEC_27001)**: มาตรฐานสากลที่กำหนดข้อกำหนดของระบบบริหารจัดการความมั่นคงปลอดภัยของข้อมูล (ISMS) ให้กรอบที่รับรองได้สำหรับจัดการความเสี่ยงด้านความมั่นคงปลอดภัยของข้อมูล

**ISO/IEC 42001**: มาตรฐานสากลที่กำหนดข้อกำหนดของระบบบริหารจัดการ AI ให้องค์กรมีกรอบที่รับรองได้สำหรับกำกับการพัฒนาและการใช้ AI อย่างรับผิดชอบ

## J

**[JWT (JSON Web Token)](https://en.wikipedia.org/wiki/JSON_Web_Token)**: รูปแบบโทเค็นกะทัดรัดที่ลงลายเซ็น (และเข้ารหัสได้ตามต้องการ) ใช้ส่งข้อมูลการอ้างสิทธิ์ (claim) ระหว่างฝ่ายต่าง ๆ มักใช้ยืนยันตัวตนและให้สิทธิ์ในระบบเว็บและ API

## K

**[Kanban](https://en.wikipedia.org/wiki/Kanban_(development))** (คัมบัง): วิธีทำงานแบบลีนที่ทำให้งานมองเห็นได้บนบอร์ด จำกัดงานที่กำลังทำ และบริหารการไหลของงาน เพื่อเพิ่มอัตราส่งมอบและความคาดการณ์ได้

**[KISS (Keep It Simple, Stupid)](https://en.wikipedia.org/wiki/KISS_principle)** (ทำให้เรียบง่าย): หลักการออกแบบที่เลือกวิธีแก้ที่เรียบง่ายที่สุดที่ตอบความต้องการได้ เพราะความซับซ้อนที่ไม่จำเป็นเพิ่มต้นทุนและความเสี่ยง

**KMS (Key Management Service)** (บริการจัดการกุญแจ): ระบบสำหรับสร้าง จัดเก็บ หมุนเวียน และควบคุมการเข้าถึงกุญแจเข้ารหัส มักมี HSM หนุนหลัง

**[KPI (Key Performance Indicator)](https://en.wikipedia.org/wiki/Performance_indicator)** (ตัวชี้วัดผลงานหลัก): ตัววัดเชิงปริมาณที่ใช้ติดตามความคืบหน้าสู่วัตถุประสงค์ทางธุรกิจหรือการปฏิบัติการเฉพาะอย่าง

## L

**Lakehouse**: สถาปัตยกรรมข้อมูลที่รวมการจัดเก็บที่ต้นทุนต่ำและยืดหยุ่นของ data lake เข้ากับฟีเจอร์การจัดการ ทรานแซกชัน และประสิทธิภาพของคลังข้อมูล

**[Lead time](https://en.wikipedia.org/wiki/Lead_time)** (ระยะเวลานำ): เวลาที่ผ่านไปตั้งแต่มีการขอ (หรือคอมมิต) การเปลี่ยนแปลง จนถึงส่งมอบเข้าโปรดักชัน เป็นตัวชี้วัดการส่งมอบหลักของ DORA

**[Least privilege](https://en.wikipedia.org/wiki/Principle_of_least_privilege)** (หลักสิทธิ์น้อยที่สุด): หลักความมั่นคงปลอดภัยที่ให้ผู้ใช้ กระบวนการ หรือระบบแต่ละอย่างเข้าถึงได้เท่าที่จำเป็นต่อหน้าที่ขั้นต่ำเท่านั้น เพื่อจำกัดความเสียหายจากการถูกบุกรุกหรือความผิดพลาด

**[Little's Law](https://en.wikipedia.org/wiki/Little's_law)** (กฎของลิตเทิล): ผลจากทฤษฎีคิวที่ว่าจำนวนรายการเฉลี่ยในระบบที่เสถียรเท่ากับอัตราการมาถึงเฉลี่ยคูณเวลาเฉลี่ยที่แต่ละรายการอยู่ในระบบ เชื่อมโยงงานที่กำลังทำ อัตราส่งมอบ และระยะเวลานำ

**[LLM (Large Language Model)](https://en.wikipedia.org/wiki/Large_language_model)** (โมเดลภาษาขนาดใหญ่): โมเดลแมชชีนเลิร์นนิงที่ฝึกด้วยคลังข้อความขนาดใหญ่มากเพื่อทำนายและสร้างภาษา ทำงานอย่างการสรุป การแปล และการสร้างโค้ดได้

**[l10n (Localisation)](https://en.wikipedia.org/wiki/Language_localisation)** (การปรับให้เข้ากับท้องถิ่น): การปรับซอฟต์แวร์ที่ทำให้เป็นสากลแล้วให้เข้ากับท้องถิ่น (locale) เฉพาะ รวมถึงการแปล การจัดรูปแบบ และธรรมเนียมทางวัฒนธรรม คำย่อมาจากตัวอักษร 10 ตัวระหว่าง "l" กับ "n"

## M

**[MDM (Master Data Management)](https://en.wikipedia.org/wiki/Master_data_management)** (การบริหารข้อมูลหลัก): วินัยและเครื่องมือสำหรับสร้างและรักษามุมมองเดียวที่เป็นทางการและสอดคล้องกันของเอนทิตีทางธุรกิจหลัก (เช่น ลูกค้าหรือสินค้า) ข้ามระบบ

**MITRE ATT&CK**: ฐานความรู้สาธารณะที่คัดสรรไว้ของยุทธวิธีและเทคนิคของผู้โจมตีในโลกจริง ใช้กันกว้างขวางในการวางแผนการฝึก red team นำทางวิศวกรรมการตรวจจับ และอธิบายภัยคุกคามด้วยคำศัพท์ร่วมกัน

**Mean Time to Recovery (MTTR)** (เวลาเฉลี่ยในการกู้คืน): เวลาเฉลี่ยที่ใช้กู้คืนบริการหลังความล้มเหลว เป็นตัวชี้วัดความน่าเชื่อถือและการจัดการเหตุการณ์ที่พบบ่อย

**[Mob programming](https://en.wikipedia.org/wiki/Mob_programming)** (การเขียนโปรแกรมแบบม็อบ): แนวปฏิบัติที่ทั้งทีมทำงานเดียวกันบนคอมพิวเตอร์เครื่องเดียวกัน สลับกันเป็นผู้พิมพ์ เพื่อแบ่งปันความรู้และตัดสินใจร่วมกัน

**[MLOps (Machine Learning Operations)](https://en.wikipedia.org/wiki/MLOps)**: ชุดแนวปฏิบัติที่ปรับใช้ เฝ้าติดตาม และดูแลโมเดลแมชชีนเลิร์นนิงในโปรดักชันอย่างเชื่อถือได้และมีประสิทธิภาพ ขยายหลักการ DevOps ไปยังวงจรชีวิตของ ML

**[Monorepo](https://en.wikipedia.org/wiki/Monorepo)**: คลังควบคุมเวอร์ชันเดียวที่เก็บโค้ดของหลายโครงการหรือทั้งองค์กร ทำให้ใช้เครื่องมือร่วมกันและเปลี่ยนแปลงข้ามโครงการแบบอะตอมมิกได้ แลกกับเครื่องมือขยายขนาดเฉพาะทาง

**mTLS (mutual TLS)**: การตั้งค่า Transport Layer Security ที่ทั้งสองฝ่ายแสดงและตรวจสอบใบรับรอง จึงยืนยันตัวตนซึ่งกันและกัน เป็นค่าเริ่มต้นของทราฟฟิกระหว่างบริการใน service mesh และเครือข่าย zero-trust ดู[การยืนยันตัวตนซึ่งกันและกัน](https://en.wikipedia.org/wiki/Mutual_authentication)ด้วย

**[Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)** (การทดสอบแบบกลายพันธุ์): เทคนิคที่ใส่ข้อบกพร่องเล็ก ๆ ("mutant") เข้าไปในโค้ดโดยตั้งใจ เพื่อตรวจว่าชุดทดสอบจับได้หรือไม่ วัดประสิทธิผลที่แท้จริงของชุดทดสอบ

## N

**[NDCG (Normalised Discounted Cumulative Gain)](https://en.wikipedia.org/wiki/Discounted_cumulative_gain)**: ตัวชี้วัดคุณภาพการจัดอันดับที่ให้รางวัลเมื่อวางผลลัพธ์ที่เกี่ยวข้องสูงไว้ใกล้ส่วนบนของรายการ โดยปรับให้เป็นมาตรฐานเพื่อเทียบคะแนนข้ามคำค้นได้ เป็นหลักในการประเมินความเกี่ยวข้องของการค้นหา

**[NIST (National Institute of Standards and Technology)](https://en.wikipedia.org/wiki/National_Institute_of_Standards_and_Technology)**: หน่วยงานรัฐบาลกลางสหรัฐฯ ที่เอกสารเผยแพร่พิเศษและกรอบงานเป็นมาตรฐานอ้างอิงกันกว้างขวางด้านความมั่นคงปลอดภัยไซเบอร์ ความเป็นส่วนตัว และ AI

**NIST AI RMF (AI Risk Management Framework)**: กรอบงานแบบสมัครใจของ NIST สำหรับระบุ ประเมิน และจัดการความเสี่ยงของระบบ AI ตลอดวงจรชีวิต จัดตามหน้าที่ Govern, Map, Measure และ Manage

**[NIST SP 800-53](https://en.wikipedia.org/wiki/NIST_Special_Publication_800-53)**: แค็ตตาล็อกมาตรการควบคุมความมั่นคงปลอดภัยและความเป็นส่วนตัวของ NIST สำหรับระบบสารสนเทศของรัฐบาลกลาง ใช้เป็นเกณฑ์พื้นฐานกันกว้างขวางไกลเกินภาครัฐ

**NIST SP 800-171**: เอกสารเผยแพร่ของ NIST ที่กำหนดข้อกำหนดการปกป้องข้อมูลที่ไม่เป็นความลับแต่ต้องควบคุม (CUI) ในระบบที่ไม่ใช่ของรัฐบาลกลาง เป็นหัวใจของการปฏิบัติตามข้อกำหนดของผู้รับเหมาด้านกลาโหม

**[NFR (Non-Functional Requirement)](https://en.wikipedia.org/wiki/Non-functional_requirement)** (ข้อกำหนดที่ไม่ใช่เชิงหน้าที่): ข้อกำหนดที่อธิบายว่าระบบควรประพฤติตัวอย่างไร (คุณลักษณะอย่างประสิทธิภาพ ความมั่นคงปลอดภัย ความน่าเชื่อถือ หรือความใช้งานง่าย) แทนที่จะบอกว่าทำหน้าที่อะไร

**North-south traffic** (ทราฟฟิกแนวเหนือ-ใต้): ทราฟฟิกเครือข่ายระหว่างระบบกับไคลเอนต์ภายนอก (เข้าและออกจากศูนย์ข้อมูลหรือคลัสเตอร์) ต่างจากทราฟฟิกแนวตะวันออก-ตะวันตกระหว่างบริการภายใน โดยทั่วไป API gateway ดูแลทราฟฟิกแนวเหนือ-ใต้

## O

**Observability** (ความสามารถในการสังเกตระบบ): ระดับที่สถานะภายในของระบบอนุมานได้จากเอาต์พุตภายนอก โดยทั่วไปทำได้ผ่านเทเลเมทรี ได้แก่ เมตริก ล็อก และเทรซ

**[OKR (Objectives and Key Results)](https://en.wikipedia.org/wiki/OKR)** (วัตถุประสงค์และผลลัพธ์หลัก): กรอบการตั้งเป้าหมายที่จับคู่วัตถุประสงค์เชิงคุณภาพกับผลลัพธ์หลักที่วัดได้ไม่กี่ข้อ เพื่อให้องค์กรสอดคล้องและมีโฟกัส

**OpenTelemetry (OTel)**: มาตรฐานเปิดและชุดเครื่องมือที่ไม่ผูกกับผู้ขาย สำหรับสร้าง รวบรวม และส่งออกข้อมูลเทเลเมทรี (เทรซ เมตริก และล็อก) จากซอฟต์แวร์

**OPA (Open Policy Agent)**: เอนจินนโยบายอเนกประสงค์แบบโอเพนซอร์สที่ประเมินนโยบาย (เขียนด้วยภาษา Rego) เพื่อบังคับใช้กฎการให้สิทธิ์และคอนฟิกูเรชันทั่วทั้งสแตก ทำให้ทำนโยบายเป็นโค้ด (policy as code) ได้

**OSPO (Open Source Program Office)** (สำนักงานโครงการโอเพนซอร์ส): หน่วยงานในองค์กรที่ประสานกลยุทธ์ ธรรมาภิบาล การปฏิบัติตามข้อกำหนด และการมีส่วนร่วมกับชุมชนด้านโอเพนซอร์ส จัดการทั้งการใช้และการมีส่วนร่วม

**[OWASP (Open Worldwide Application Security Project)](https://en.wikipedia.org/wiki/OWASP)**: ชุมชนไม่แสวงหากำไรที่ผลิตทรัพยากรด้านความมั่นคงปลอดภัยของแอปพลิเคชันที่ใช้กันกว้างขวางและเข้าถึงได้ฟรี รวมถึง OWASP Top Ten และ ASVS

## P

**[PACELC](https://en.wikipedia.org/wiki/PACELC_theorem)**: ส่วนขยายของทฤษฎีบท CAP ที่ว่า หากมีการแบ่งเครือข่าย (Partition) ระบบแลกเปลี่ยนระหว่างความพร้อมใช้งาน (Availability) กับความสอดคล้อง (Consistency) ไม่เช่นนั้น (Else) ในการทำงานปกติจะแลกเปลี่ยนระหว่างความหน่วง (Latency) กับความสอดคล้อง

**[PCI DSS (Payment Card Industry Data Security Standard)](https://en.wikipedia.org/wiki/Payment_Card_Industry_Data_Security_Standard)**: มาตรฐานความมั่นคงปลอดภัยที่อุตสาหกรรมบัตรชำระเงินดูแล กำหนดข้อกำหนดสำหรับองค์กรที่จัดเก็บ ประมวลผล หรือส่งผ่านข้อมูลผู้ถือบัตร

**[Penetration testing](https://en.wikipedia.org/wiki/Penetration_test)** (การทดสอบเจาะระบบ): การโจมตีจำลองที่ได้รับอนุญาตโดยผู้ทดสอบที่ชำนาญ เพื่อค้นหาและพิสูจน์ช่องโหว่ที่ถูกใช้ประโยชน์ได้ก่อนผู้โจมตีตัวจริง ส่งมอบเป็นข้อค้นพบที่จัดลำดับความสำคัญและนำไปปฏิบัติได้

**[PII (Personally Identifiable Information)](https://en.wikipedia.org/wiki/Personal_data)** (ข้อมูลที่ระบุตัวบุคคลได้): ข้อมูลที่ระบุตัวบุคคลเฉพาะได้ ทั้งโดยลำพังหรือเมื่อรวมกับข้อมูลอื่น การจัดการข้อมูลนี้อยู่ภายใต้กฎหมายความเป็นส่วนตัวและนโยบายภายใน

**Platform engineering** (วิศวกรรมแพลตฟอร์ม): วินัยในการสร้างและดำเนินงานแพลตฟอร์มภายในแบบบริการตนเองและเส้นทางทอง (golden path) ที่ลดภาระทางความคิดและเร่งทีมผลิตภัณฑ์

**POUR**: หลักการนำทางสี่ข้อของ Web Content Accessibility Guidelines คือเนื้อหาต้องรับรู้ได้ (Perceivable) ใช้งานได้ (Operable) เข้าใจได้ (Understandable) และแข็งแรงทนทาน (Robust)

**Production readiness review** (การทบทวนความพร้อมสู่โปรดักชัน): การตรวจสอบอย่างเป็นระบบก่อนบริการขึ้นใช้งานจริงหรือรับหน้าที่เวรเฝ้าระบบ เพื่อยืนยันว่าเป็นไปตามมาตรฐานด้านความสามารถในการสังเกตระบบ ความน่าเชื่อถือ ความมั่นคงปลอดภัย runbook และการสนับสนุนการปฏิบัติการ

**[Prompt engineering](https://en.wikipedia.org/wiki/Prompt_engineering)** (วิศวกรรมพรอมต์): แนวปฏิบัติในการออกแบบและปรับแต่งคำสั่ง บริบท และตัวอย่างที่ให้แก่โมเดลภาษา เพื่อให้ได้ผลลัพธ์ที่เชื่อถือได้และมีคุณภาพสูง ถือเป็นวินัยทางวิศวกรรมที่มีเวอร์ชันและมีการทดสอบ ไม่ใช่การลองผิดลองถูก

**[Prompt injection](https://en.wikipedia.org/wiki/Prompt_injection)** (การแทรกพรอมต์): การโจมตีที่อินพุตซึ่งสร้างขึ้นมาโดยเฉพาะทำให้โมเดลภาษาละเลยคำสั่งที่ตั้งใจไว้และทำตามคำสั่งของผู้โจมตีแทน เป็นคู่เทียบในยุค AI ของช่องโหว่การแทรกคำสั่ง และเป็นความเสี่ยงด้านความมั่นคงปลอดภัยหลักของแอปพลิเคชัน LLM

**Property-based testing** (การทดสอบตามคุณสมบัติ): เทคนิคการทดสอบที่ตรวจว่าคุณสมบัติที่ระบุไว้เป็นจริงกับอินพุตที่สร้างอัตโนมัติจำนวนมาก แทนที่จะพึ่งตัวอย่างที่เลือกด้วยมืออย่างเดียว

**Pull request (PR) / merge request (MR)**: ชุดการเปลี่ยนแปลงที่เสนอให้ทบทวนและหารือก่อนรวมเข้าสาขาที่ใช้ร่วมกัน เป็นหน่วยหลักของการทบทวนโค้ดในเวิร์กโฟลว์ส่วนใหญ่

**Purple team**: การฝึกร่วมกันที่ทีมความมั่นคงปลอดภัยฝั่งรุก (red) และฝั่งรับ (blue) ทำงานด้วยกันแบบเรียลไทม์ เพื่อให้การโจมตีและการตรวจจับที่ออกแบบมาจับการโจมตีนั้นถูกปรับเข้าหากัน

## Q

**Quality gate** (ด่านคุณภาพ): จุดตรวจอัตโนมัติในไปป์ไลน์ที่ต้องผ่าน (เช่น ได้ตามเกณฑ์ความครอบคลุมของการทดสอบ ความมั่นคงปลอดภัย หรือประสิทธิภาพ) ก่อนที่การเปลี่ยนแปลงจะเดินหน้าต่อได้

**[Quorum](https://en.wikipedia.org/wiki/Quorum_(distributed_computing))** (องค์ประชุม): ในระบบกระจาย คือจำนวนโหนดขั้นต่ำที่ต้องเห็นพ้องกันเพื่อให้การดำเนินการ (เช่น การอ่านหรือเขียน) ถือว่าสำเร็จ ใช้รักษาความสอดคล้องแม้เกิดความล้มเหลว

## R

**[RACI](https://en.wikipedia.org/wiki/Responsibility_assignment_matrix)**: แบบจำลองการมอบหมายความรับผิดชอบที่ระบุผู้เกี่ยวข้องแต่ละคนในงานหรือการตัดสินใจว่าเป็นผู้ปฏิบัติ (Responsible) ผู้รับผิดชอบสูงสุด (Accountable) ผู้ให้คำปรึกษา (Consulted) หรือผู้รับแจ้ง (Informed)

**[RAG (Retrieval-Augmented Generation)](https://en.wikipedia.org/wiki/Retrieval-augmented_generation)** (การสร้างที่เสริมด้วยการค้นคืน): เทคนิคที่ยึดผลลัพธ์ของโมเดลภาษาไว้กับข้อมูลจริง โดยค้นคืนเอกสารหรือข้อมูลที่เกี่ยวข้องก่อนแล้วส่งให้เป็นบริบท ช่วยเพิ่มความแม่นยำและลดการหลอน (hallucination)

**[RBAC (Role-Based Access Control)](https://en.wikipedia.org/wiki/Role-based_access_control)** (การควบคุมการเข้าถึงตามบทบาท): แบบจำลองการให้สิทธิ์ที่กำหนดสิทธิ์ให้บทบาทและกำหนดบทบาทให้ผู้ใช้ ทำให้การบริหารง่ายขึ้นโดยจัดการการเข้าถึงที่ระดับบทบาท

**[Red team](https://en.wikipedia.org/wiki/Red_team)**: กลุ่มที่เลียนแบบผู้โจมตีสมจริง มักโจมตีทั้งองค์กรโดยไม่แจ้งผู้ป้องกัน เพื่อทดสอบการตรวจจับและการตอบสนอง ไม่ใช่แค่ไล่นับช่องโหว่ เทียบกับ blue team (ฝั่งป้องกัน)

**[Reference data](https://en.wikipedia.org/wiki/Reference_data)** (ข้อมูลอ้างอิง): รายการรหัสและการจัดประเภทที่ควบคุมไว้และเปลี่ยนช้า ใช้จัดหมวดหมู่ข้อมูลอื่น เช่น รหัสประเทศ สกุลเงิน และค่าสถานะ การกำกับดูแลให้เป็นคำศัพท์ร่วมที่มีเวอร์ชันช่วยให้ระบบสอดคล้องกัน

**Rego**: ภาษานโยบายแบบประกาศที่ Open Policy Agent ใช้แสดงกฎสำหรับการตัดสินใจเรื่องการให้สิทธิ์และคอนฟิกูเรชัน

**[REST (Representational State Transfer)](https://en.wikipedia.org/wiki/REST)**: รูปแบบสถาปัตยกรรมสำหรับแอปพลิเคชันเครือข่ายที่ใช้การดำเนินการแบบไร้สถานะผ่าน HTTP บนทรัพยากรที่ระบุตำแหน่งได้ เป็นที่นิยมเพราะเรียบง่ายและมีเครื่องมือรองรับกว้างขวาง

**[Reverse proxy](https://en.wikipedia.org/wiki/Reverse_proxy)** (รีเวิร์สพร็อกซี): เซิร์ฟเวอร์ที่อยู่หน้าบริการแบ็กเอนด์หนึ่งตัวหรือมากกว่า และส่งต่อคำขอของไคลเอนต์ไปให้ โดยทั่วไปทำหน้าที่ยุติ TLS กระจายภาระ แคช และเป็นจุดเข้าเดียว

**[RFC (Request for Comments)](https://en.wikipedia.org/wiki/Request_for_Comments)** (ข้อเสนอเพื่อขอความเห็น): ข้อเสนอที่เขียนเป็นลายลักษณ์อักษรและเวียนเพื่อรับฟีดแบ็กก่อนการตัดสินใจหรือการเปลี่ยนแปลงทางเทคนิคที่สำคัญ ส่งเสริมความโปร่งใสและความเป็นเจ้าของร่วมกัน (คำนี้ยังใช้เรียกชุดเอกสารมาตรฐานอินเทอร์เน็ตด้วย)

**[ROI (Return on Investment)](https://en.wikipedia.org/wiki/Return_on_investment)** (ผลตอบแทนการลงทุน): ตัววัดคุณค่าที่ได้จากการลงทุนเมื่อเทียบกับต้นทุน ใช้อธิบายเหตุผลและจัดลำดับความสำคัญของการตัดสินใจด้านวิศวกรรมและเทคโนโลยี

**[RPA (Robotic Process Automation)](https://en.wikipedia.org/wiki/Robotic_process_automation)** (ระบบอัตโนมัติด้วยหุ่นยนต์ซอฟต์แวร์): "หุ่นยนต์" ซอฟต์แวร์ที่ทำงานซ้ำ ๆ ตามกฎโดยอัตโนมัติ ด้วยการโต้ตอบกับส่วนติดต่อผู้ใช้และระบบที่มีอยู่เหมือนที่คนทำ

**RPO (Recovery Point Objective)** (วัตถุประสงค์จุดกู้คืน): ปริมาณข้อมูลที่ยอมให้สูญหายได้สูงสุดซึ่งวัดเป็นเวลา (เช่น "ไม่เกินห้านาที") กำหนดว่าต้องปกป้องข้อมูลบ่อยเพียงใด

**RTO (Recovery Time Objective)** (วัตถุประสงค์เวลากู้คืน): ระยะเวลาสูงสุดที่ยอมรับได้ในการกู้คืนบริการหลังเกิดการหยุดชะงัก เป็นแนวทางการออกแบบและการลงทุนด้านการกู้คืนจากภัยพิบัติ

## S

**Saga**: รูปแบบสำหรับจัดการความสอดคล้องของข้อมูลข้ามบริการในทรานแซกชันแบบกระจาย โดยเรียงลำดับทรานแซกชันย่อยในเครื่องและออกการกระทำชดเชยเมื่อขั้นตอนใดล้มเหลว

**[SAFe (Scaled Agile Framework)](https://en.wikipedia.org/wiki/Scaled_agile_framework)**: กรอบงานสำหรับนำแนวปฏิบัติแบบ agile และลีนไปใช้ทั่วองค์กรขนาดใหญ่ ประสานหลายทีม ได้รับการยกย่องเรื่องโครงสร้างและถูกวิจารณ์เรื่องความหนักเกินไป

**[SAST (Static Application Security Testing)](https://en.wikipedia.org/wiki/Static_application_security_testing)** (การทดสอบความมั่นคงปลอดภัยของแอปพลิเคชันแบบสถิต): การทดสอบความมั่นคงปลอดภัยที่วิเคราะห์ซอร์สโค้ด ไบต์โค้ด หรือไบนารีโดยไม่รัน เพื่อหาช่องโหว่ตั้งแต่ช่วงต้นของการพัฒนา

**SBOM (Software Bill of Materials)** (บัญชีรายการส่วนประกอบซอฟต์แวร์): รายการส่วนประกอบและการพึ่งพาในซอฟต์แวร์ชิ้นหนึ่งที่เป็นทางการและเครื่องอ่านได้ ใช้จัดการความเสี่ยงของห่วงโซ่อุปทานและช่องโหว่

**SCA (Software Composition Analysis)** (การวิเคราะห์องค์ประกอบซอฟต์แวร์): เครื่องมือที่ระบุส่วนประกอบโอเพนซอร์สและของบุคคลที่สามในโค้ดเบส และแจ้งช่องโหว่ที่ทราบและความเสี่ยงด้านสัญญาอนุญาต

**[Scrum](https://en.wikipedia.org/wiki/Scrum_(software_development))** (สครัม): กรอบงาน agile ที่จัดงานเป็นรอบที่มีความยาวคงที่ (สปรินต์) พร้อมบทบาท กิจกรรม และอาร์ติแฟกต์ที่กำหนด เพื่อส่งมอบส่วนเพิ่มของคุณค่า

**[Section 508](https://en.wikipedia.org/wiki/Section_508_Amendment_to_the_Rehabilitation_Act_of_1973)**: กฎหมายสหรัฐฯ ที่กำหนดให้หน่วยงานรัฐบาลกลางทำให้เทคโนโลยีอิเล็กทรอนิกส์และสารสนเทศของตนเข้าถึงได้สำหรับผู้พิการ ในทางปฏิบัติสอดคล้องกับ WCAG

**Semantic search** (การค้นหาเชิงความหมาย): การค้นหาที่จับคู่ตามความหมายแทนคำหลักที่ตรงตัว โดยทั่วไปทำด้วยการเทียบเอมเบดดิงของคำค้นกับเอกสาร มักใช้ร่วมกับการค้นหาตามคำในแนวทางแบบผสม

**[Service mesh](https://en.wikipedia.org/wiki/Service_mesh)**: ชั้นโครงสร้างพื้นฐานเฉพาะ มักสร้างด้วยพร็อกซีแบบ sidecar ที่จัดการเรื่องการสื่อสารระหว่างบริการ เช่น mutual TLS การลองใหม่ การหมดเวลา การเลื่อนทราฟฟิก และความสามารถในการสังเกตระบบ โดยไม่ให้ไปอยู่ในโค้ดแอปพลิเคชัน

**Sidecar**: โพรเซสหรือคอนเทนเนอร์ผู้ช่วยที่ปรับใช้ควบคู่กับอินสแตนซ์แอปพลิเคชันหลัก เพื่อให้ความสามารถสนับสนุน (เช่น พร็อกซีของ service mesh) โดยไม่ต้องแก้ตัวแอปพลิเคชัน

**[SIEM (Security Information and Event Management)](https://en.wikipedia.org/wiki/Security_information_and_event_management)**: ระบบที่รวบรวมและเชื่อมโยงล็อกและเหตุการณ์ด้านความมั่นคงปลอดภัยทั่วสภาพแวดล้อม เพื่อให้ตรวจจับ แจ้งเตือน และสืบสวนได้

**[SLA (Service Level Agreement)](https://en.wikipedia.org/wiki/Service-level_agreement)** (ข้อตกลงระดับการให้บริการ): ข้อผูกพันที่เป็นทางการระหว่างผู้ให้บริการกับลูกค้า ระบุระดับบริการที่คาดหวังและผลที่ตามมาหากทำไม่ได้

**SLI (Service Level Indicator)** (ตัวบ่งชี้ระดับบริการ): ตัววัดเชิงปริมาณของแง่มุมหนึ่งของคุณภาพบริการ เช่น ความหน่วงของคำขอหรืออัตราข้อผิดพลาด ซึ่งป้อนเข้าสู่ SLO

**SLO (Service Level Objective)** (วัตถุประสงค์ระดับบริการ): ค่าเป้าหมายหรือช่วงค่าของ SLI ที่กำหนดระดับความน่าเชื่อถือที่ต้องการ เป็นพื้นฐานของงบความผิดพลาด

**SLSA (Supply-chain Levels for Software Artifacts)**: กรอบงานของข้อกำหนดด้านความมั่นคงปลอดภัยแบบไล่ระดับ เพื่อยกระดับความสมบูรณ์และที่มาของอาร์ติแฟกต์ซอฟต์แวร์ตลอดกระบวนการบิลด์และปล่อย

**SOAR (Security Orchestration, Automation, and Response)**: เครื่องมือและแนวปฏิบัติที่ทำให้ปฏิบัติการด้านความมั่นคงปลอดภัยเป็นอัตโนมัติและประสานกัน เช่น การคัดแยกเบื้องต้นและเพลย์บุ๊กการตอบสนอง เพื่อเพิ่มความเร็วและความสม่ำเสมอ

**SOC 2 (System and Organisation Controls 2)**: กรอบการตรวจสอบและรายงานตาม Trust Services Criteria ของ AICPA ที่ประเมินมาตรการควบคุมขององค์กรผู้ให้บริการด้านความมั่นคงปลอดภัย ความพร้อมใช้งาน ความสมบูรณ์ของการประมวลผล การรักษาความลับ และความเป็นส่วนตัว

**[SOLID](https://en.wikipedia.org/wiki/SOLID)**: หลักการออกแบบเชิงวัตถุห้าข้อ (Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation และ Dependency Inversion) ที่ส่งเสริมโค้ดที่ดูแลรักษาง่ายและยืดหยุ่น

**[SOX (Sarbanes-Oxley Act)](https://en.wikipedia.org/wiki/Sarbanes-Oxley_Act)**: กฎหมายสหรัฐฯ ที่กำหนดข้อกำหนดด้านการรายงานทางการเงินและการควบคุมภายในของบริษัทมหาชน ส่งผลต่อระบบไอทีที่รองรับข้อมูลทางการเงิน

**SPACE**: กรอบงานวัดผลิตภาพของนักพัฒนาใน 5 มิติ ได้แก่ ความพึงพอใจและความเป็นอยู่ที่ดี (Satisfaction and well-being) ประสิทธิภาพ (Performance) กิจกรรม (Activity) การสื่อสารและความร่วมมือ (Communication and collaboration) และประสิทธิภาพกับการไหลของงาน (Efficiency and flow) โดยเตือนไม่ให้ใช้ตัววัดตัวเดียว

**[SRE (Site Reliability Engineering)](https://en.wikipedia.org/wiki/Site_reliability_engineering)** (วิศวกรรมความน่าเชื่อถือของไซต์): วินัยที่นำแนวทางวิศวกรรมซอฟต์แวร์มาใช้กับการปฏิบัติการ ใช้ SLO งบความผิดพลาด และระบบอัตโนมัติเพื่อรันระบบที่เชื่อถือได้ในระดับใหญ่

**SSDF (Secure Software Development Framework)**: กรอบงานของ NIST (SP 800-218) ว่าด้วยแนวปฏิบัติระดับสูงของการพัฒนาอย่างปลอดภัย ครอบคลุมการเตรียมองค์กร การปกป้องซอฟต์แวร์ การผลิตซอฟต์แวร์ที่ปลอดภัยดี และการตอบสนองต่อช่องโหว่

**[Static analysis](https://en.wikipedia.org/wiki/Static_program_analysis)** (การวิเคราะห์แบบสถิต): การตรวจซอร์สโค้ด ไบต์โค้ด หรือไบนารีโดยไม่รัน เพื่อหาข้อบกพร่อง การละเมิดสไตล์ และช่องโหว่ด้านความมั่นคงปลอดภัย โดยทั่วไปทำผ่าน linter ตัวตรวจชนิดข้อมูล และตัววิเคราะห์เฉพาะทางที่เชื่อมกับตัวแก้ไขและไปป์ไลน์

**[STRIDE](https://en.wikipedia.org/wiki/STRIDE_model)**: อนุกรมวิธานการสร้างแบบจำลองภัยคุกคามที่จัดภัยคุกคามเป็น Spoofing (การปลอมแปลง), Tampering (การแก้ไขโดยมิชอบ), Repudiation (การปฏิเสธความรับผิด), Information disclosure (การเปิดเผยข้อมูล), Denial of service (การปฏิเสธการให้บริการ) และ Elevation of privilege (การยกระดับสิทธิ์)

## T

**[TCO (Total Cost of Ownership)](https://en.wikipedia.org/wiki/Total_cost_of_ownership)** (ต้นทุนรวมตลอดอายุการใช้งาน): ต้นทุนตลอดอายุของระบบหรือการตัดสินใจ รวมการจัดหา การดำเนินงาน การบำรุงรักษา และการปลดระวางในที่สุด ไม่ใช่แค่ราคาแรกเริ่ม

**[TDD (Test-Driven Development)](https://en.wikipedia.org/wiki/Test-driven_development)** (การพัฒนาที่ขับเคลื่อนด้วยการทดสอบ): แนวปฏิบัติที่เขียนการทดสอบอัตโนมัติที่ล้มเหลวก่อนโค้ดที่ทำให้ผ่าน แล้วปรับโครงสร้างโค้ด (refactoring) เป็นรอบสั้น ๆ ซ้ำ ๆ เพื่อขับเคลื่อนการออกแบบและให้ครอบคลุม

**[Technical debt](https://en.wikipedia.org/wiki/Technical_debt)** (หนี้ทางเทคนิค): ต้นทุนในอนาคตที่แฝงอยู่จากการเลือกวิธีแก้ที่ทำได้เร็วตอนนี้แทนวิธีที่ดีกว่าแต่ใช้เวลานานกว่า ซึ่งต้องจัดการอย่างตั้งใจ ไม่ใช่สะสมโดยไม่รู้ตัว

**TF-IDF (Term Frequency-Inverse Document Frequency)**: รูปแบบการถ่วงน้ำหนักแบบคลาสสิกที่ให้คะแนนความสำคัญของคำต่อเอกสารตามความถี่ที่ปรากฏในเอกสารนั้น หักลบด้วยความแพร่หลายของคำทั่วทั้งคลังเอกสาร เป็นพื้นฐานของการจัดอันดับการค้นหาตามคำจำนวนมาก

**[Theory of constraints](https://en.wikipedia.org/wiki/Theory_of_constraints)** (ทฤษฎีข้อจำกัด): แนวทางการจัดการที่ถือว่าอัตราส่งมอบของระบบถูกจำกัดโดยคอขวดเดียวในเวลาใดเวลาหนึ่ง ความพยายามปรับปรุงจึงควรโฟกัสที่ข้อจำกัดนั้นจนกว่ามันจะย้ายไปที่อื่น

**[Threat modelling](https://en.wikipedia.org/wiki/Threat_model)** (การสร้างแบบจำลองภัยคุกคาม): แนวปฏิบัติอย่างเป็นระบบในการระบุ ไล่รายการ และจัดลำดับความสำคัญของภัยคุกคามที่อาจเกิดกับระบบ เพื่อออกแบบการป้องกันตั้งแต่เนิ่น ๆ

**Toil** (งานซ้ำซากที่ไม่สร้างคุณค่า): ใน SRE คืองานปฏิบัติการที่ทำด้วยมือ ซ้ำ ๆ และทำเป็นอัตโนมัติได้ ซึ่งเพิ่มตามขนาดของบริการเป็นเส้นตรงและไม่ให้คุณค่าถาวร การลดงานนี้คืนความจุไปให้งานวิศวกรรม

**Trunk-based development** (การพัฒนาบนสายหลัก): แนวปฏิบัติด้านการควบคุมซอร์สที่นักพัฒนารวมการเปลี่ยนแปลงเล็ก ๆ เข้าสาขาร่วมเดียวบ่อย ๆ ลดสาขาอายุยาวและความเจ็บปวดจากการรวมโค้ด

**[Type inference](https://en.wikipedia.org/wiki/Type_inference)** (การอนุมานชนิดข้อมูล): ฟีเจอร์ของภาษาที่หาชนิดข้อมูลของนิพจน์ได้เองโดยอัตโนมัติ ให้ความปลอดภัยของการกำหนดชนิดแบบสถิตเป็นส่วนใหญ่โดยไม่ต้องเขียนทุกชนิดด้วยมือ

**[Type system](https://en.wikipedia.org/wiki/Type_system)** (ระบบชนิดข้อมูล): ชุดกฎที่ภาษาใช้กำหนดและตรวจสอบชนิดข้อมูล จับข้อผิดพลาดได้ทั้งกลุ่มก่อนโปรแกรมรัน และบันทึกเจตนา ระบบชนิดข้อมูลมีตั้งแต่แบบพลวัตถึงแบบสถิต และจากอ่อนถึงเข้มงวด

## U

**Ubiquitous language** (ภาษาร่วม): ใน Domain-Driven Design คือคำศัพท์ร่วมที่แม่นยำซึ่งนักพัฒนาและผู้เชี่ยวชาญโดเมนใช้อย่างสอดคล้องกัน และสะท้อนตรง ๆ ในโค้ดและแบบจำลอง

**[UAT (User Acceptance Testing)](https://en.wikipedia.org/wiki/Acceptance_testing)** (การทดสอบเพื่อการยอมรับของผู้ใช้): การทดสอบโดยผู้ใช้ปลายทางหรือตัวแทนของพวกเขา เพื่อยืนยันว่าระบบตอบสนองความต้องการทางธุรกิจก่อนรับเข้าสู่การปล่อย

**[UX / UI (User Experience / User Interface)](https://en.wikipedia.org/wiki/User_experience)** (ประสบการณ์ผู้ใช้ / ส่วนติดต่อผู้ใช้): User Experience คือคุณภาพโดยรวมของการที่คนโต้ตอบกับผลิตภัณฑ์ ส่วน User Interface คือพื้นผิวทางภาพและการโต้ตอบที่เฉพาะเจาะจงซึ่งการโต้ตอบนั้นเกิดขึ้น

## V

**[Value object](https://en.wikipedia.org/wiki/Value_object)** (ออบเจกต์ค่า): ใน Domain-Driven Design คือออบเจกต์ที่ไม่เปลี่ยนแปลงและถูกนิยามด้วยแอตทริบิวต์ทั้งหมดของมัน แทนที่จะมีเอกลักษณ์เฉพาะ เช่น จำนวนเงินหรือช่วงวันที่

**[Value stream mapping](https://en.wikipedia.org/wiki/Value-stream_mapping)** (การทำแผนผังสายธารคุณค่า): เทคนิคการวาดทุกขั้นตอนจากไอเดียถึงคุณค่าที่ส่งมอบ แยกเวลาที่เพิ่มคุณค่าออกจากเวลารอ เพื่อให้คอขวด การส่งต่องาน และวงจรการทำซ้ำมองเห็นและปรับปรุงได้

**[Vector database](https://en.wikipedia.org/wiki/Vector_database)** (ฐานข้อมูลเวกเตอร์): ที่เก็บข้อมูลที่ปรับให้เหมาะกับการทำดัชนีและค้นหาเวกเตอร์เอมเบดดิงมิติสูงตามความคล้ายคลึง เป็นกระดูกสันหลังที่พบบ่อยของการค้นหาเชิงความหมายและ retrieval-augmented generation

**Vertical scaling** (การขยายแนวตั้ง): การเพิ่มความจุด้วยการทำให้โหนดเดียวทรงพลังขึ้น ("scaling up") ทำได้ง่ายแต่ถูกจำกัดในที่สุดด้วยเครื่องที่ใหญ่ที่สุดที่หาได้

**[VCS (Version Control System)](https://en.wikipedia.org/wiki/Version_control)** (ระบบควบคุมเวอร์ชัน): เครื่องมืออย่าง Git ที่บันทึกการเปลี่ยนแปลงของไฟล์ตามเวลา เพื่อให้ทบทวนประวัติ ดูแลสาขา และประสานงานได้

**[Vulnerability scanning](https://en.wikipedia.org/wiki/Vulnerability_scanner)** (การสแกนช่องโหว่): การตรวจระบบ คอนเทนเนอร์ หรือโค้ดโดยอัตโนมัติเทียบกับฐานข้อมูลจุดอ่อนและการตั้งค่าผิดพลาดที่ทราบ ครอบคลุมกว้างและถูก และเสริมความลึกของการทดสอบเจาะระบบด้วยมือ

## W

**[WCAG (Web Content Accessibility Guidelines)](https://en.wikipedia.org/wiki/Web_Content_Accessibility_Guidelines)**: ชุดแนวทางของ W3C ที่ได้รับการยอมรับในระดับสากล จัดตามหลักการ POUR และระดับความสอดคล้อง A, AA และ AAA สำหรับทำให้เนื้อหาเว็บเข้าถึงได้

**Wardley map**: เทคนิคกลยุทธ์เชิงภาพที่วางความสามารถตามคุณค่าต่อผู้ใช้และวุฒิภาวะเชิงวิวัฒนาการ เพื่อประกอบการตัดสินใจเรื่องสร้างเองหรือซื้อ และการลงทุน

**Work in progress (WIP) limit** (เพดานงานที่กำลังทำ): ขีดจำกัดจำนวนรายการที่อยู่ในขั้นตอนหนึ่งของเวิร์กโฟลว์พร้อมกันได้ เป็นแนวปฏิบัติหลักของ Kanban ที่ช่วยให้งานไหลดีขึ้นโดยเผยคอขวดและลดภาระของการทำงานขนานกันมากเกินไป

**WSJF (Weighted Shortest Job First)**: วิธีจัดลำดับความสำคัญที่เรียงงานโดยหารต้นทุนของความล่าช้าด้วยระยะเวลาโดยประมาณ เพื่อให้งานที่สั้นที่สุด เร่งด่วนที่สุด และมีคุณค่าสูงสุดถูกทำก่อน

## X

**[XSS (Cross-Site Scripting)](https://en.wikipedia.org/wiki/Cross-site_scripting)**: ช่องโหว่เว็บที่ผู้โจมตีแทรกสคริปต์ประสงค์ร้ายให้ทำงานในเบราว์เซอร์ของผู้ใช้คนอื่น อาจขโมยข้อมูลหรือยึดเซสชันได้

## Y

**[YAGNI (You Aren't Gonna Need It)](https://en.wikipedia.org/wiki/You_aren't_gonna_need_it)** (คุณจะไม่ได้ใช้มัน): หลักการที่แนะนำไม่ให้สร้างฟังก์ชันตามการเดา เพราะความต้องการที่คาดไว้มักไม่เกิดขึ้นจริงและเพิ่มต้นทุนกับความซับซ้อน

## Z

**[Zero trust](https://en.wikipedia.org/wiki/Zero_trust_security_model)** (ไม่ไว้วางใจใคร): แบบจำลองความมั่นคงปลอดภัยที่ไม่ถือว่ามีความไว้วางใจโดยปริยายจากตำแหน่งในเครือข่าย และตรวจสอบทุกคำขอเข้าถึงอย่างต่อเนื่องเทียบกับตัวตน อุปกรณ์ และบริบท ตามคติ "never trust, always verify" (ไม่ไว้ใจ ตรวจสอบเสมอ)
