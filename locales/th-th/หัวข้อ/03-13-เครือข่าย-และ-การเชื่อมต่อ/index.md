# 3.13 เครือข่ายและการเชื่อมต่อ

## ภาพรวมและแรงจูงใจ

ทุกคำขอที่แอปพลิเคชันของคุณส่งออกไปต้องข้ามเครือข่าย และเครือข่ายไม่สนใจเส้นตายของคุณ ระหว่างโค้ดของคุณกับฐานข้อมูล ผู้ให้บริการชำระเงิน หรือเบราว์เซอร์ มีชุดของส่วนที่เคลื่อนไหวอยู่ ได้แก่ การแปลงชื่อ การกำหนดเส้นทาง การควบคุมความคับคั่ง การจับมือเข้ารหัส ตัวกระจายโหลด พร็อกซี และไฟร์วอลล์ วิศวกรแอปพลิเคชันส่วนใหญ่มองทั้งหมดนี้เป็นท่อเรียบ ๆ ที่เชื่อถือได้ และสมมติฐานนั้นคือแหล่งใหญ่ที่สุดของเหตุการณ์ในระบบการผลิต [ความเข้าใจผิดของการประมวลผลแบบกระจาย](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing) แบบคลาสสิก (เครือข่ายเชื่อถือได้ ความหน่วงเป็นศูนย์ แบนด์วิดท์ไม่จำกัด โทโพโลยีไม่เปลี่ยน ต้นทุนการขนส่งเป็นศูนย์) ระบุความเชื่อที่เปลี่ยนอาการสะดุดเล็กน้อยให้กลายเป็นเหตุขัดข้องได้อย่างตรงจุด บทนี้ไม่ใช่หลักสูตรใบรับรองด้านเครือข่าย แต่เป็นความรู้เชิงปฏิบัติที่วิศวกรแอปพลิเคชันต้องใช้จริง เพื่อสร้างระบบที่ยังทำงานได้เมื่อเครือข่ายทำตัวไม่ดี

สำหรับองค์กรขนาดใหญ่ การเชื่อมต่อคือที่ที่สถาปัตยกรรมพบกับฟิสิกส์และการเมืองพร้อมกัน องค์กรระดับโลกเย็บศูนย์ข้อมูล ภูมิภาคคลาวด์ API ของพันธมิตร และระบบเดิมเข้าด้วยกัน และแต่ละฮอปเพิ่มความหน่วง โหมดความล้มเหลว และขอบเขตความมั่นคงปลอดภัยที่ต้องมีคนเป็นเจ้าของ ภาครัฐเพิ่มกฎที่เข้มงวดว่าทราฟฟิกเข้าและออกจากเครือข่ายของตนอย่างไร และข้อมูลของประชาชนเดินทางไปที่ใดได้ ความต่างระหว่างทีมที่เข้าใจเครือข่ายกับทีมที่ละเลยมันปรากฏเป็นตัวเลขความพร้อมใช้งาน เวลาโหลดหน้า รายงานการละเมิด และข้อค้นพบจากการตรวจสอบ เนื้อหานี้เชื่อมกับระบบแบบกระจาย (บทที่ 3.3) ความสามารถในการขยายขนาดและความทนทาน (บทที่ 3.5) ความมั่นคงปลอดภัยของโครงสร้างพื้นฐานและคลาวด์ (บทที่ 4.3) และการเข้ารหัสลับและการจัดการกุญแจ (บทที่ 4.8)

ข่าวดีคือคุณไม่จำเป็นต้องเชี่ยวชาญโปรโตคอลการกำหนดเส้นทางเพื่อสร้างระบบที่ทนทาน คุณต้องรู้ว่าชั้นไหนสำคัญต่อการตัดสินใจของคุณ ความหน่วงมาจากไหน ชื่อถูกแปลงอย่างไร การเชื่อมต่อถูกรักษาความมั่นคงปลอดภัยและกระจายโหลดอย่างไร และวิธีล้มเหลวอย่างนุ่มนวลที่ขอบเขตเครือข่าย ทำสิ่งเหล่านี้ให้ถูก แล้วเครือข่ายส่วนใหญ่จะกลายเป็นฐานที่ไว้ใจได้

## หลักการสำคัญ

- **เครือข่ายคือสิ่งที่ต้องพึ่งพา ไม่ใช่สิ่งที่มีให้เสมอ** มองทุกการเรียกระยะไกลว่าอาจช้า หลุด หรือโกหกว่าเสร็จแล้วหรือยัง
- **ความหน่วงถูกกำหนดโดยระยะทางและจำนวนรอบการเดินทาง** คุณชนะความเร็วแสงไม่ได้ จึงต้องลดจำนวนรอบและย้ายข้อมูลเข้าใกล้ผู้ใช้
- **ชื่อล้มเหลวบ่อยกว่าเครื่อง** การแปลงชื่อและใบรับรองก่อให้เกิดเหตุขัดข้องในสัดส่วนที่น่าตกใจ จึงต้องมองมันเป็นเรื่องการดำเนินงานชั้นหนึ่ง
- **รักษาความมั่นคงปลอดภัยและยุติการเข้ารหัสอย่างตั้งใจ** รู้ให้ชัดว่าทราฟฟิกถูกเข้ารหัสที่ไหน ถูกถอดรหัสที่ไหน และใครถือกุญแจ
- **ทุกขอบเขตเครือข่ายต้องมี timeout และทางสำรอง** การรอแบบไม่มีขอบเขตและการลองใหม่แบบมองไม่เห็นผล เปลี่ยนการพึ่งพาที่ช้าเพียงตัวเดียวเป็นเหตุขัดข้องทั่วระบบ
- **ตั้งค่าเริ่มต้นเป็นปฏิเสธที่ขอบ** แบ่งส่วนเครือข่าย ควบคุมสิ่งที่ออกไปได้ และสมมติว่าเขตป้องกันรอบนอกมีรูรั่วอยู่แล้ว
- **สังเกตการเชื่อมต่อ ไม่ใช่แค่โค้ด** ข้อผิดพลาดการเชื่อมต่อ การส่งซ้ำ เวลาจับมือ และความหน่วงของ DNS เป็นสัญญาณที่ล็อกของคุณมักพลาดไป

## ข้อแนะนำ

### เข้าใจชั้นที่ส่งผลต่อการตัดสินใจของคุณจริง ๆ

คุณไม่จำเป็นต้องท่องแบบจำลองเจ็ดชั้นให้ครบ แต่ต้องมีแผนที่ในหัว ที่ชั้นการขนส่ง [Transmission Control Protocol](https://en.wikipedia.org/wiki/Transmission_Control_Protocol) (TCP) ให้สายไบต์ที่เรียงลำดับและเชื่อถือได้ โดยแลกกับการจับมือและการอุดตันที่หัวแถว (head-of-line blocking) ขณะที่ User Datagram Protocol (UDP) ให้ดาตาแกรมราคาถูกที่ไม่เรียงลำดับและไม่รับประกันการส่ง ทราฟฟิกคำขอ/การตอบที่ต้องเชื่อถือได้ใช้ TCP ส่วนสื่อเรียลไทม์ เกม และเทเลเมทรีบางประเภทใช้ UDP เพราะแพ็กเก็ตที่มาช้าแย่กว่าแพ็กเก็ตที่หาย

วิวัฒนาการของ Hypertext Transfer Protocol ([HTTP](https://en.wikipedia.org/wiki/HTTP)) เปลี่ยนเพดานประสิทธิภาพของคุณ HTTP/1.1 จัดการหนึ่งคำขอต่อหนึ่งการเชื่อมต่อในแต่ละครั้ง เบราว์เซอร์จึงเปิดหลายการเชื่อมต่อและคุณจ่ายค่าจับมือซ้ำ ๆ HTTP/2 ส่งหลายสตรีมผ่านการเชื่อมต่อ TCP เดียว ซึ่งขจัดการอุดตันที่หัวแถวระดับแอปพลิเคชัน แต่ไม่ใช่ระดับ TCP แพ็กเก็ตหายเพียงชิ้นเดียวทำให้ทุกสตรีมบนการเชื่อมต่อนั้นชะงัก HTTP/3 ทำงานบน QUIC ซึ่งเป็นการขนส่งบน UDP ที่ให้แต่ละสตรีมส่งอย่างอิสระ ตั้งการเชื่อมต่อเร็วขึ้น และย้ายการเชื่อมต่อข้ามการเปลี่ยนเครือข่ายได้ คุณแทบไม่ได้สร้างสิ่งเหล่านี้เอง แต่คุณเลือกมันในตัวกระจายโหลด เครือข่ายส่งเนื้อหา (CDN) และไคลเอนต์ของคุณ และการเลือกนั้นปรากฏในความหน่วงส่วนหาง

### มอง DNS และใบรับรองเป็นระบบการผลิต

[Domain Name System](https://en.wikipedia.org/wiki/Domain_Name_System) (DNS) แปลงชื่อที่มนุษย์อ่านได้เป็นที่อยู่ และอยู่หน้าแทบทุกคำขอ เหตุขัดข้องใหญ่จำนวนมากอย่างน่าทึ่งสืบไปถึง DNS ได้ ไม่ว่าจะเป็นการเปลี่ยนเรคอร์ดผิด โซนที่หมดอายุ ตัวแปลงชื่อที่กำหนดค่าผิด ชั้นแคชที่ให้คำตอบเก่า หรือเซิร์ฟเวอร์ที่เป็นผู้มีอำนาจตอบช้าจนเพิ่มหลายร้อยมิลลิวินาทีให้ไบต์แรก ปฏิบัติต่อการเปลี่ยน DNS ด้วยความเข้มงวดเท่ากับการปรับใช้โค้ด ใช้ค่า time-to-live (TTL) ที่สมเหตุสมผล เพื่อให้ย้ายทราฟฟิกได้เร็วระหว่างเหตุการณ์โดยไม่เชิญชวนให้เกิดแคชเก่าในการทำงานปกติ และเฝ้าติดตามความหน่วงและอัตราความล้มเหลวของการแปลงชื่อเป็นเมตริกจริง

ใบรับรองสมควรได้รับความจริงจังเท่ากัน เมื่อใบรับรอง [Transport Layer Security](https://en.wikipedia.org/wiki/Transport_Layer_Security) (TLS) หมดอายุโดยไม่มีใครสังเกต ทั้งบริการดับพร้อมกัน และความล้มเหลวนั้นไม่เหมือนบั๊กของโค้ดเลย ทำให้การออกและต่ออายุเป็นอัตโนมัติ ติดตามวันหมดอายุแบบรวมศูนย์ และแจ้งเตือนล่วงหน้านานก่อนกำหนด ตัดสินใจอย่างตั้งใจว่า TLS สิ้นสุดที่ไหน ที่ตัวกระจายโหลดขอบ ที่พร็อกซี หรือไปจนถึงบริการ การสิ้นสุดที่ขอบทำให้ทราฟฟิกภายในเรียบง่ายขึ้นแต่ปล่อยฮอปภายในไม่เข้ารหัส เว้นแต่คุณเข้ารหัสใหม่ ผู้ออกใบรับรอง การหมุนเวียนกุญแจ และการเลือกชุดเข้ารหัสอยู่ในบทที่ 4.8 ประเด็นเชิงปฏิบัติการที่นี่คือ DNS และใบรับรองล้มเหลวอย่างเงียบ ๆ และลากทุกอย่างไปด้วย จึงต้องติดตั้งเครื่องมือวัดและทำให้ทั้งสองอย่างเป็นอัตโนมัติ

### กระจายโหลดที่ชั้นที่ถูกต้องและใช้พร็อกซีให้เป็นประโยชน์

[การกระจายโหลด](https://en.wikipedia.org/wiki/Load_balancing_(computing)) (load balancing) กระจายทราฟฟิกไปยังแบ็กเอนด์จำนวนมาก และที่ที่คุณทำมันสำคัญ ตัวกระจายโหลดชั้น 4 (L4) กำหนดเส้นทางตามที่อยู่ IP และพอร์ตโดยไม่อ่านเนื้อหา จึงเร็ว ไม่ขึ้นกับโปรโตคอล และถูก ตัวกระจายโหลดชั้น 7 (L7) เข้าใจ HTTP จึงกำหนดเส้นทางตามพาธหรือเฮดเดอร์ ยุติ TLS ลองคำขอ idempotent ใหม่ และบังคับขีดจำกัดอัตราได้ โดยแลกกับงานต่อคำขอที่มากขึ้น ทราฟฟิกแอปพลิเคชันส่วนใหญ่ต้องการ reverse proxy L7 หรือ API gateway ที่ขอบ เพื่อให้มีที่เดียวสำหรับจัดการ TLS การยืนยันตัวตน การกำหนดเส้นทาง และความสามารถในการสังเกตระบบ สงวน L4 ไว้สำหรับปริมาณงานดิบหรือโปรโตคอลที่ไม่ใช่ HTTP

การตรวจสุขภาพ (health check) คือสิ่งที่ทำให้การกระจายโหลดปลอดภัย กำหนดค่าให้สะท้อนความพร้อมจริง ไม่ใช่แค่ "โปรเซสทำงานอยู่" เพื่อให้แบ็กเอนด์ที่เข้าถึงฐานข้อมูลไม่ได้ถูกดึงออกจากการหมุนเวียนก่อนที่มันจะส่งข้อผิดพลาด และระบายการเชื่อมต่อเมื่อปรับใช้ เพื่อให้คำขอที่อยู่ระหว่างทางเสร็จก่อน API gateway รวมศูนย์ประเด็นที่ตัดผ่านทั้งระบบ (การยืนยันตัวตน การจำกัดอัตรา การปรับรูปคำขอ การกำหนดเวอร์ชัน) แต่ก็กลายเป็นสิ่งที่ต้องพึ่งพาอย่างวิกฤตและคอขวดที่อาจเกิดขึ้น จึงต้องให้งบความพร้อมใช้งานและความสามารถในการสังเกตระบบเท่ากับบริการหลักใด ๆ

### ย้ายข้อมูลเข้าใกล้ผู้ใช้ด้วย CDN และขอบ

ความหน่วงถูกครอบงำโดยเวลาไป-กลับ และเวลาไป-กลับถูกครอบงำโดยระยะทาง [เครือข่ายส่งเนื้อหา](https://en.wikipedia.org/wiki/Content_delivery_network) (content delivery network, CDN) แคชเนื้อหาไว้ที่จุดให้บริการใกล้ผู้ใช้ เพื่อให้เนื้อหาคงที่ และมากขึ้นเรื่อย ๆ รวมถึงคำตอบแบบไดนามิกและแบบเฉพาะบุคคล ถูกส่งจากห่างไปไม่กี่มิลลิวินาที แทนที่จะข้ามมหาสมุทร สำหรับผลิตภัณฑ์ใด ๆ ที่หันหน้าสู่ผู้ใช้และมีผู้ชมกระจายตามภูมิศาสตร์ CDN เป็นหนึ่งในการลงทุนด้านประสิทธิภาพที่ให้ผลตอบแทนสูงที่สุดที่คุณทำได้ และยังทำหน้าที่เป็นโล่ที่ดูดซับทราฟฟิกพุ่งและการโจมตีแบบปริมาณ

ผลักงานไปที่ขอบในที่ที่ช่วยได้ การยุติ TLS ที่ขอบลดความหน่วงของการจับมือ เพราะรอบการเดินทางที่แพงเกิดใกล้ผู้ใช้ และการแคชคำตอบ API ที่ตำแหน่งขอบลดความยาวเส้นทางสำหรับคำขอทั่วไป ข้อแลกเปลี่ยนคือการทำให้แคชเป็นโมฆะ ยิ่งข้อมูลอยู่ใกล้และถูกแคชมากเท่าไร ยิ่งรับประกันความสดใหม่ได้ยากขึ้นเท่านั้น จึงต้องระบุให้ชัดว่าสิ่งใดเก่าได้และเก่าได้นานแค่ไหน เรื่องนี้เชื่อมกับการพูดถึงการแคชและประสิทธิภาพในบทที่ 3.5

### ทำให้ขอบเขตเครือข่ายทนทานโดยค่าเริ่มต้น

ทุกการเรียกระยะไกลคือที่ที่เครือข่ายทำร้ายคุณได้ จึงห่อแต่ละอันด้วยวินัยเดียวกัน ตั้ง timeout ที่ชัดเจนในทุกการเรียก เพราะการพึ่งพาที่ค้างจะใช้พูลการเชื่อมต่อและเธรดของคุณจนหมดและทำให้ทุกอย่างด้านหลังชะงัก ลองใหม่เฉพาะการดำเนินการที่ทำซ้ำได้อย่างปลอดภัย ใช้ exponential backoff พร้อมจิตเตอร์เพื่อไม่ให้อาการสะดุดกลายเป็นพายุการลองใหม่ที่ประสานกัน และจำกัดจำนวนครั้งทั้งหมดและเวลาทั้งหมด เพิ่ม circuit breaker เพื่อให้หลังจากความล้มเหลวถึงเกณฑ์ คุณล้มเหลวเร็วในช่วงพัก แทนที่จะกองคำขอใส่บริการที่กำลังจมอยู่แล้ว รูปแบบเหล่านี้ครอบคลุมโดยละเอียดในบทที่ 3.3 ประเด็นที่นี่คือมันควรอยู่ที่ขอบเขตเครือข่ายโดยเฉพาะ และควรเป็นค่าเริ่มต้นของแพลตฟอร์มที่ใช้ร่วมกัน ไม่ใช่สิ่งที่แต่ละทีมคิดค้นใหม่

จัดสรรงบ timeout ลงไปตามสายการเรียก หากคำขอที่หันหน้าสู่ผู้ใช้มีงบสองวินาทีและข้ามสี่ฮอป แต่ละฮอปต้องรู้ว่าเหลือเวลาน้อยแค่ไหนและล้มเหลวเร็ว แทนที่จะลองใหม่ลงสู่ความว่างเปล่า ใช้การเชื่อมต่อซ้ำผ่านการทำพูลและ keep-alive เพื่อไม่ต้องจ่ายค่าจับมือ TCP และ TLS ใหม่ทุกคำขอ และดูความหน่วงส่วนหาง ไม่ใช่แค่ค่าเฉลี่ย เพราะหนึ่งเปอร์เซ็นต์ที่ช้าที่สุดคือสิ่งที่ผู้ใช้จำได้และเป็นสิ่งที่ลุกลามภายใต้โหลด

### ออกแบบและกำกับดูแลโทโพโลยีเครือข่ายของคุณ

ในคลาวด์ เครือข่ายของคุณคือซอฟต์แวร์ที่คุณกำหนดค่า จึงกำหนดค่ามันอย่างตั้งใจ ใส่ภาระงานใน virtual private cloud (VPC) และแบ่งส่วน ชั้นที่หันหน้าสู่สาธารณะ ชั้นแอปพลิเคชัน และชั้นข้อมูลอยู่ในซับเน็ตแยกกันพร้อมกฎที่อนุญาตเฉพาะทราฟฟิกที่ควรมี ควบคุมทราฟฟิกขาออก (egress) อย่างตั้งใจเท่ากับขาเข้า การเข้าถึงขาออกที่ไม่ถูกควบคุมคือวิธีที่ข้อมูลออกไประหว่างการละเมิด และวิธีที่ภาระงานที่ถูกเจาะเข้าถึงเซิร์ฟเวอร์สั่งการและควบคุม จึงส่งทราฟฟิกขาออกผ่านเกตเวย์ที่ควบคุม และอนุญาตเฉพาะปลายทางที่ต้องเข้าถึงจริง วางแผนสำหรับ IPv6 แทนที่จะมองเป็นเรื่องคิดทีหลัง เพราะที่อยู่ที่หมดและข้อกำหนดของพันธมิตรจะบังคับให้ต้องใช้ในที่สุด และการติดตั้งย้อนหลังเจ็บปวด

นำ[แบบจำลองความมั่นคงปลอดภัยแบบ zero trust](https://en.wikipedia.org/wiki/Zero_trust_security_model) มาใช้ คือเลิกมอง "อยู่ภายในเครือข่าย" ว่าเชื่อถือได้ และยืนยันตัวตนกับให้สิทธิ์ทุกคำขอตามตัวตน ไม่ใช่ตำแหน่งในเครือข่าย ในทางปฏิบัติหมายถึง mutual TLS ระหว่างบริการ ข้อมูลรับรองอายุสั้น และนโยบายที่ไม่สมมติว่าคำขอปลอดภัยเพียงเพราะมาจากซับเน็ตข้างเคียง service mesh ส่งมอบสิ่งนี้ได้อย่างสม่ำเสมอเป็นส่วนใหญ่ ด้วยการรันพร็อกซี sidecar ข้างแต่ละบริการ mesh ให้ mutual TLS การลองใหม่และ timeout ที่สอดคล้องกัน และเทเลเมทรีต่อฮอป โดยไม่เปลี่ยนโค้ดแอปพลิเคชัน มันเพิ่มความซับซ้อนในการดำเนินงานและความหน่วงบ้าง จึงนำมาใช้เมื่อจำนวนบริการทำให้การบังคับใช้แบบสม่ำเสมอที่ไม่ต้องแก้โค้ดคุ้มกับภาระ Zero trust และการแบ่งส่วนพัฒนาต่อในบทที่ 4.3 และ 8.3

## ข้อดีข้อเสียและการแลกเปลี่ยน

| การตัดสินใจ | ข้อดี | ข้อเสีย / ต้นทุน |
|---|---|---|
| ตัวกระจายโหลด L7 / API gateway | กำหนดเส้นทางอัจฉริยะ ยุติ TLS ยืนยันตัวตน จำกัดอัตรา สังเกตระบบได้ | ความหน่วงต่อคำขอมากขึ้น เป็นสิ่งพึ่งพาร่วมที่วิกฤต |
| ตัวกระจายโหลด L4 | เร็ว ไม่ขึ้นกับโปรโตคอล ถูก | มองหรือทำอะไรกับ HTTP ไม่ได้ ไม่มีการกำหนดเส้นทางที่ตระหนักถึงเนื้อหา |
| ยุติ TLS ที่ขอบ | จับมือเร็วขึ้น แบ็กเอนด์เรียบง่ายขึ้น | ฮอปภายในไม่เข้ารหัส เว้นแต่เข้ารหัสใหม่ |
| CDN และการแคชที่ขอบ | ลดความหน่วงได้มาก ดูดซับทราฟฟิกพุ่งและการโจมตี | ทำแคชให้เป็นโมฆะและข้อมูลเก่า ต้นทุนและการกำหนดค่าเพิ่ม |
| Service mesh | mTLS การลองใหม่ เทเลเมทรีที่สม่ำเสมอโดยไม่แก้แอป | ความซับซ้อนในการดำเนินงาน ความหน่วงและต้นทุนทรัพยากรของ sidecar |
| HTTP/3 บน QUIC | ไม่มีการอุดตันที่หัวแถวระดับการขนส่ง ตั้งต้นเร็ว ย้ายการเชื่อมต่อได้ | เครื่องมือใหม่กว่า UDP บางครั้งถูกจำกัด ดีบักยากกว่า |

ความตึงเครียดหลักคือระหว่างการควบคุมกับความเรียบง่าย ทุกส่วนประกอบที่มีความสามารถซึ่งคุณเพิ่มที่ขอบเขตเครือข่าย (เกตเวย์ L7, mesh, CDN, พร็อกซีขาออก) ซื้อความฉลาดในการกำหนดเส้นทาง การบังคับใช้ความมั่นคงปลอดภัย และการมองเห็นให้คุณ และแต่ละอย่างก็เพิ่มฮอป โหมดความล้มเหลว และสิ่งที่ต้องดำเนินการด้วย แก้ด้วยการผลักประเด็นที่ใช้ร่วมกันไปยังโครงสร้างพื้นฐานร่วมเฉพาะเมื่อมีหลายทีมต้องการมากพอจะคุ้มกับภาระการดำเนินงาน และรักษาเส้นทางที่เร็วให้สั้น สตาร์ทอัปสองคนที่ยุติ TLS ที่ตัวกระจายโหลดที่มีผู้ดูแลให้แล้วจบ กำลังตัดสินใจแลกเปลี่ยนได้ดีกว่าทีมเดียวกันที่สร้าง service mesh เอง องค์กรที่มีพันบริการแต่ไม่มี mutual TLS ที่สม่ำเสมอและการควบคุมขาออก กำลังทำแย่กว่า

## คำถามที่ควรคุยกับทีม

1. **TLS สิ้นสุดที่ไหนในแต่ละเส้นทางคำขอของคุณ และทุกคนวาดมันได้ตรงกันหรือไม่?** ฟังดูเหมือนเรื่องจุกจิกจนกว่าจะเกิดเหตุการณ์ หากครึ่งทีมเชื่อว่าทราฟฟิกถูกเข้ารหัสตั้งแต่ต้นจนจบ และอีกครึ่งรู้ว่ามันถูกถอดรหัสที่ขอบและส่งเป็นข้อความธรรมดาไปยังแบ็กเอนด์ คุณมีทั้งช่องโหว่ด้านความมั่นคงปลอดภัยและกับดักด้านการดีบัก สำหรับองค์กรใหญ่ คำถามนี้ผูกตรงกับการปฏิบัติตามข้อกำหนด หน่วยงานกำกับดูแลและผู้ตรวจสอบจะถามว่าข้อมูลของประชาชนหรือลูกค้าเดินทางแบบไม่เข้ารหัสที่ไหน และ "เราไม่แน่ใจ" คือข้อค้นพบ ให้นำแผนภาพจริงของเส้นทางจริงหนึ่งเส้นจากไคลเอนต์ถึงฐานข้อมูล ทำเครื่องหมายทุกจุดที่การเข้ารหัสเริ่มและหยุด และใครถือใบรับรองและกุญแจแต่ละตัวมาคุยกัน คำตอบควรบอกคุณว่าต้องเข้ารหัสภายในใหม่หรือไม่ mutual TLS ควรอยู่ตรงไหน และใบรับรองใดจะทำให้บริการล่มหากหมดอายุ หากไม่มีใครวาดมันได้อย่างมั่นใจ ช่องว่างนั้นคืองานแรกของคุณ

2. **จะเกิดอะไรกับระบบของคุณเมื่อ DNS ช้าหรือผิด และคุณทดสอบจริงแล้วหรือยัง?** DNS อยู่ต้นน้ำของแทบทุกคำขอ แต่ทีมส่วนใหญ่ไม่เคยสังเกตระบบของตนภายใต้ DNS ที่เสื่อมสภาพ ตัวแปลงชื่อที่ช้าเพิ่มความหน่วงให้ทุกการเชื่อมต่อใหม่ แคชเก่าอาจส่งทราฟฟิกไปยังโฮสต์ที่ปลดระวางแล้ว และการเปลี่ยนเรคอร์ดที่ผิดอาจกลืนทั้งบริการภายในไม่กี่วินาที ในองค์กรใหญ่ รัศมีความเสียหายกว้างกว่า เพราะการค้นพบบริการภายใน การเชื่อมต่อกับพันธมิตร และปลายทางคลาวด์ ล้วนพิงการแปลงชื่อ ให้นำการตั้งค่า DNS TTL เมตริกความหน่วงของการแปลงชื่อหากมี และรันบุ๊กสำหรับการเปลี่ยนเรคอร์ดที่ผิดมาคุยกัน แล้วถามว่าคุณย้ายทราฟฟิกระหว่างเหตุการณ์ได้เร็วแค่ไหนจริง ๆ คำตอบควรขับเคลื่อนว่าคุณเฝ้าติดตามการแปลงชื่อเป็นเมตริกชั้นหนึ่ง ปรับ TTL เพื่อทั้งความคล่องตัวและประสิทธิภาพแคช และซ้อมการสลับระบบสำรองของ DNS หรือไม่ หากคุณไม่เคยทำให้ DNS ล้มเหลวในการทดสอบที่ควบคุม การทดลองนั้นควรอยู่ในปฏิทิน

3. **รูปแบบความทนทานที่ขอบเขตเครือข่ายอันใดเป็นค่าเริ่มต้นของแพลตฟอร์ม และอันใดที่ทุกทีมกำลังคิดค้นใหม่?** Timeout การลองใหม่แบบจำกัดพร้อมจิตเตอร์ circuit breaker การทำพูลการเชื่อมต่อ และการสืบรอยต่อฮอป ถูกและเชื่อถือได้ที่สุดเมื่อสร้างครั้งเดียวและทุกคนรับสืบทอด ถ้าปล่อยให้แต่ละทีมทำเอง มันจะเลื่อนไหล บางการเรียกไม่มี timeout บางอันลองการดำเนินการที่ไม่ idempotent ใหม่ บางอันไม่ปล่อยเทเลเมทรีระดับการเชื่อมต่อ และช่องว่างปรากฏเฉพาะภายใต้โหลด สำหรับทีมใหญ่ นี่คือทางเลือกขององค์กรว่าความทนทานอยู่ที่ไหน ในไลบรารีที่ใช้ร่วมกันหรือชั้นแพลตฟอร์ม เทียบกับกระจัดกระจายข้ามบริการ ให้นำการตรวจสอบตัวอย่างบริการที่นับว่ากี่บริการตั้ง timeout ที่ชัดเจนในทุกการเรียกระยะไกลและส่ง correlation identifier ตั้งแต่ต้นจนจบ หากตัวเลขต่ำ ทางแก้คือการลงทุนในแพลตฟอร์ม และการทำให้เป็นมาตรฐานยังทำให้ความทนทานทดสอบและตรวจสอบได้ ซึ่งสำคัญขึ้นเรื่อย ๆ ในภาคส่วนที่มีการกำกับดูแล คำตอบควรบอกคุณว่าจะให้ทุนความสามารถของแพลตฟอร์มเครือข่าย หรือจะจ่ายค่าความไม่สอดคล้องในเหตุการณ์ต่อไป

4. **ภาระงานแต่ละตัวของคุณเข้าถึงอะไรบนอินเทอร์เน็ตสาธารณะได้ตอนนี้ และใครอนุมัติปลายทางขาออกแต่ละแห่งเหล่านั้น?** ขาเข้าได้รับความสนใจเพราะเป็นที่ที่ผู้โจมตีมาเคาะประตู แต่ขาออกคือวิธีที่ข้อมูลออกไปจริง ๆ ระหว่างการละเมิด และวิธีที่ภาระงานที่ถูกเจาะโทรกลับไปหาเซิร์ฟเวอร์สั่งการและควบคุม ทีมส่วนใหญ่ลิสต์สิ่งที่คุยกับพวกเขาได้ง่ายกว่าสิ่งที่พวกเขาคุยด้วยมาก และความไม่สมมาตรนั้นคือช่องว่างที่ผู้โจมตีใช้ ข้อพิจารณาที่ขัดกันคือความฝืด รายการอนุญาตปลายทางที่อนุมัติแล้วชะลอนักพัฒนาที่อยากเรียก API บุคคลที่สามตัวใหม่วันนี้ ดังนั้นการถกที่ซื่อสัตย์คือคุณยอมแลกความสะดวกเท่าไรเพื่อรัศมีความเสียหายที่หดลง ให้นำกฎขาออกปัจจุบันของบริการตัวแทนหนึ่งตัว การจับภาพว่ามันเชื่อมต่อที่ไหนจริงในสัปดาห์ที่ผ่านมา และกระบวนการ (หากมี) สำหรับการอนุมัติปลายทางใหม่มาคุยกัน สำหรับระบบขององค์กรและภาครัฐ นี่ไม่ใช่สุขอนามัยทางเลือกแต่เป็นรายการตรวจสอบ การป้องกันขอบเขตและรายการสินค้าคงคลังของขาออกคือสิ่งที่หน่วยงานกำกับดูแลและกฎขอบเขตเครือข่ายเรียกร้องให้คุณสร้าง และ "ภาระงานใดก็เข้าถึงที่ไหนก็ได้" คือข้อค้นพบที่คุณจะถูกสั่งให้แก้ไข

5. **timeout และการลองใหม่ของคุณประกอบกันเป็นงบประมาณเดียวที่สอดคล้องกันตลอดสายการเรียกแต่ละสายหรือไม่ หรือทุกฮอปเดาแยกกัน?** คำขอที่หันหน้าสู่ผู้ใช้ซึ่งข้ามสี่บริการมีเส้นตายเดียวที่ผู้ใช้รู้สึกจริง แต่แต่ละฮอปมักตั้ง timeout เองในท้องถิ่น ลองใหม่ลงสู่บริการที่ยอมแพ้ไปแล้ว และทำให้งบตั้งแต่ต้นจนจบพังขณะทำงานเพิ่ม สำหรับทีมใหญ่ อันตรายเป็นแบบผุดขึ้นเอง timeout ต่อบริการที่สมเหตุสมผลแต่ละตัวประกอบกันเป็นการชะงักแบบลุกลามและพายุการลองใหม่ที่ประสานกัน ซึ่งไม่มีทีมใดเห็นได้จากแดชบอร์ดของตน ความตึงเครียดอยู่ระหว่างอิสระในท้องถิ่น ซึ่งแต่ละทีมปรับขีดจำกัดของตนเอง กับเส้นตายที่ส่งต่อซึ่งทุกฮอปอ่านและทำให้สั้นลงเมื่อเวลาถูกใช้ไป ให้นำเส้นทางคำขอจริงพร้อมนโยบาย timeout และการลองใหม่ที่แต่ละฮอป งบตั้งแต่ต้นจนจบที่ผลิตภัณฑ์สัญญาไว้ และตัวเลขความหน่วงส่วนหางของคุณ (p99 ไม่ใช่ค่าเฉลี่ย) ภายใต้โหลดมาคุยกัน ในบริบทที่มีการกำกับดูแลและความพร้อมใช้งานสูง ให้เชื่อมเรื่องนี้กับเป้าหมายการกู้คืนของคุณ สายที่ล้มเหลวเร็วภายในงบไม่ได้ทำให้การพึ่งพาที่ช้าเพียงตัวเดียวกลายเป็นการละเมิดเป้าหมายระดับบริการ และการละเมิดนั้นคือตัวเลขที่ผู้นำและผู้ตรวจสอบจะขอให้คุณอธิบาย

6. **ที่จำนวนบริการและรูปแบบทราฟฟิกเท่าไร การบังคับใช้แบบสม่ำเสมอ (service mesh, เกตเวย์ L7, การแคชที่ขอบ) จึงคุ้มกับภาระการดำเนินงาน และวันนี้คุณอยู่ตรงไหนบนเส้นโค้งนั้น?** ทุกส่วนประกอบที่มีความสามารถซึ่งคุณเพิ่มที่ขอบเขตเครือข่ายซื้อความฉลาดในการกำหนดเส้นทาง ความมั่นคงปลอดภัย และการมองเห็น และแต่ละอย่างก็เพิ่มฮอป โหมดความล้มเหลว และสิ่งที่ต้องดำเนินการตลอดยี่สิบสี่ชั่วโมง นำ mesh มาใช้เร็วเกินไป คุณจะจมบริการไม่กี่ตัวในความซับซ้อนของ sidecar นำมาใช้ช้าเกินไป คุณก็มีพันบริการโดยไม่มี mutual TLS ที่สม่ำเสมอหรือการลองใหม่ที่สอดคล้อง ข้อพิจารณาที่แข่งกันคือคุณค่าของการบังคับใช้ที่สม่ำเสมอและไม่ต้องแก้โค้ดข้ามหลายทีม เทียบกับต้นทุนจริงของการรัน control plane ความหน่วงที่เพิ่ม และคนที่หายากที่ดีบักมันได้ ให้นำจำนวนบริการปัจจุบันและเส้นโค้งการเติบโต สัดส่วนบริการที่อยู่บนไคลเอนต์ร่วมซึ่งให้การรับประกันเดียวกันแล้ว และพื้นที่เผื่อความหน่วงที่คุณมีให้ใช้ มาคุยกัน สำหรับองค์กรใหญ่หรือหน่วยงานรัฐ การตัดสินใจยังเป็นเรื่องธรรมาภิบาลด้วย mesh หรือเกตเวย์กลางช่วยให้ทีมแพลตฟอร์มปล่อยนโยบายทุกที่พร้อมกัน ซึ่งทรงพลังสำหรับการปฏิบัติตามข้อกำหนดและอันตรายหากจุดคอขวดเดียวนั้นมีทรัพยากรไม่พอ จึงตั้งงบมันเป็นโครงสร้างพื้นฐานหลักพร้อมเป้าหมายความพร้อมใช้งานของตนเอง ไม่ใช่โครงการข้างเคียง

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** พึ่งพาโครงสร้างพื้นฐานที่มีผู้ดูแลให้ และใช้ความสนใจด้านวิศวกรรมที่หายากไปกับผลิตภัณฑ์ ไม่ใช่แพ็กเก็ต ตัวกระจายโหลด L7 ที่มีผู้ดูแลให้ซึ่งยุติ TLS ด้วยใบรับรองที่ต่ออายุอัตโนมัติ บวก CDN หน้าแอปของคุณ ซื้อทราฟฟิกที่เข้ารหัส กระจายโหลด และเร็วทั่วโลกโดยไม่ต้องมีทีมปฏิบัติการ ห่อทุกการเรียกภายนอกด้วยไคลเอนต์ร่วมขนาดเล็กที่มี timeout และการลองใหม่แบบจำกัด และต้านทานการใช้ service mesh จนกว่าคุณจะมีบริการมากกว่าคนที่จะรันมันมาก

**ธุรกิจขนาดเล็ก.** คุณไม่มีผู้เชี่ยวชาญด้านเครือข่ายและงบประมาณจำกัด จึงมองการเชื่อมต่อเป็นสิ่งที่ซื้อแบบกำหนดค่าแล้ว ไม่ใช่สิ่งที่สร้าง เลือกผู้ให้บริการคลาวด์หรือแพลตฟอร์มที่ค่าเริ่มต้นให้ใบรับรองอัตโนมัติ การจัดการ DNS และไฟร์วอลล์ที่สมเหตุสมผลอยู่แล้ว และเปิดสิ่งที่พวกเขามีให้แทนที่จะประกอบเอง ในที่ที่คุณต้องตัดสินใจ ให้เลือกตัวเลือกที่มีผู้ดูแลให้ การจ่ายผู้จำหน่ายให้ต่ออายุใบรับรองและเฝ้า DNS ถูกกว่าเหตุขัดข้องจากการหมดอายุที่ถูกลืมมาก

**องค์กรขนาดใหญ่.** ปัญหาของคุณคือความสอดคล้องกันข้ามหลายทีมและภูมิภาค ได้แก่ mutual TLS ที่สม่ำเสมอ timeout และการลองใหม่ที่เป็นมาตรฐาน การควบคุมขาออก และการเฝ้าติดตามใบรับรองและ DNS ที่ไม่มีทีมใดเลือกไม่ร่วมได้ ผลักสิ่งเหล่านี้เข้าโครงสร้างพื้นฐานแพลตฟอร์มร่วม (service mesh เกตเวย์ภายใน ไลบรารีไคลเอนต์ร่วม) เพื่อให้ความทนทานถูกสืบทอดแทนที่จะคิดค้นใหม่ และจัดการขอบเขตเครือข่ายด้วยงบความพร้อมใช้งานและความสามารถในการสังเกตระบบเท่ากับบริการหลักใด ๆ แบ่งส่วน VPC กำกับดูแลขาออกจากส่วนกลาง และมองโทโพโลยีเป็นซอฟต์แวร์ที่คุณตรวจสอบ

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง ความโปร่งใส และความรับผิดชอบต่อสาธารณะกำหนดทุกขอบเขต ส่งทราฟฟิกขาออกสู่อินเทอร์เน็ตผ่านเกตเวย์ที่แข็งแกร่งและเฝ้าติดตามจำนวนน้อย ทำรายการสินค้าคงคลังของทุกปลายทางภายนอก และรันสถาปัตยกรรม zero trust ที่บริการยืนยันตัวตนด้วยตัวตนพร้อมข้อมูลรับรองอายุสั้น ไม่ใช่ด้วยตำแหน่งในเครือข่าย ปฏิบัติต่อการจัดการ DNS และใบรับรองเป็นโครงสร้างพื้นฐานสำคัญพร้อมการเฝ้าติดตามโดยเฉพาะ เพราะใบรับรองหมดอายุเพียงใบเดียวบนบริการที่หันหน้าสู่ประชาชนเชิญชวนให้ทั้งสาธารณะและฝ่ายนิติบัญญัติตรวจสอบ และเก็บหลักฐานให้ตรวจสอบได้ เพื่อให้การทบทวนการป้องกันขอบเขตพบการออกแบบที่บันทึกไว้และปกป้องได้

## ตัวอย่าง

**สตาร์ทอัป.** บริษัทซอฟต์แวร์แบบบริการสิบคนรันทุกอย่างหลังตัวกระจายโหลด L7 ที่มีผู้ดูแลให้ตัวเดียวซึ่งยุติ TLS ด้วยใบรับรองที่ต่ออายุอัตโนมัติ และใส่ CDN หน้าเว็บแอปพลิเคชันและ API ส่วนผสมนั้นให้การโหลดหน้าที่เร็วทั่วโลก ดูดซับทราฟฟิกพุ่งเป็นครั้งคราวจากการเปิดตัวผลิตภัณฑ์ และปกป้องต้นทางโดยไม่ต้องมีทีมปฏิบัติการโดยเฉพาะ พวกเขาตั้ง timeout ที่ชัดเจนและการลองใหม่แบบจำกัดในทุกการเรียกไปยังผู้ให้บริการชำระเงินและบริการอีเมล ห่อไว้ในไคลเอนต์ร่วมขนาดเล็ก เพื่อให้บุคคลที่สามที่ช้าไม่ทำให้คำขอของผู้ใช้ค้าง พวกเขาต้านทานการเพิ่ม service mesh เพราะกับบริการสิบกว่าตัว ต้นทุนการดำเนินงานจะเกินประโยชน์ และโครงสร้างพื้นฐานที่มีผู้ดูแลให้ก็ให้ทราฟฟิกที่เข้ารหัสและกระจายโหลดอยู่แล้ว

**องค์กรขนาดใหญ่.** ผู้ค้าปลีกข้ามชาติรันข้ามสามภูมิภาคคลาวด์และศูนย์ข้อมูลในองค์กรแบบเดิม เชื่อมต่อด้วยลิงก์ส่วนตัวแทนอินเทอร์เน็ตสาธารณะ เพื่อให้ทราฟฟิกสินค้าคงคลังและการชำระเงินไม่เคยข้ามเครือข่ายเปิด แต่ละภูมิภาคอยู่ใน VPC ที่แบ่งส่วนพร้อมซับเน็ตสาธารณะ แอปพลิเคชัน และข้อมูลแยกกัน และทราฟฟิกขาออกทั้งหมดไหลผ่านเกตเวย์ขาออกที่อนุญาตเฉพาะปลายทางที่อนุมัติแล้ว ภาระงานที่ถูกเจาะจึงขโมยข้อมูลออกไปอย่างเงียบ ๆ ไม่ได้ บริการหลายร้อยตัวสื่อสารผ่าน service mesh ที่บังคับ mutual TLS ทุกที่และใช้การลองใหม่ timeout และการสืบรอยที่สม่ำเสมอ ให้ทีมแพลตฟอร์มกลางปล่อยนโยบายการลองใหม่ใหม่ได้โดยไม่แตะโค้ดแอปพลิเคชัน การเฝ้าติดตามใบรับรองแบบรวมศูนย์แจ้งการหมดอายุล่วงหน้าหลายวัน และระบบอัตโนมัติหมุนเวียนก่อนที่ลูกค้าจะสังเกต

**ภาครัฐ.** หน่วยงานระดับชาติดำเนินงานภายใต้กฎการป้องกันขอบเขตเครือข่ายที่ส่งทราฟฟิกขาออกสู่อินเทอร์เน็ตทั้งหมดผ่านเกตเวย์ที่แข็งแกร่งและเฝ้าติดตามจำนวนน้อย สอดคล้องกับโมเดลการเชื่อมต่ออินเทอร์เน็ตที่เชื่อถือได้ ทราฟฟิกระหว่างหน่วยงานรันบนการเชื่อมต่อส่วนตัว และทุกปลายทางภายนอกถูกทำรายการ ทีมความมั่นคงปลอดภัยจึงรู้ว่าอะไรเข้าออกได้ หน่วยงานรันสถาปัตยกรรม zero trust ที่บริการยืนยันตัวตนต่อกันด้วยตัวตนพร้อมข้อมูลรับรองอายุสั้น และไม่มีคำขอใดได้รับความไว้วางใจเพียงเพราะมาจากภายในเขตป้องกัน การจัดการ DNS และใบรับรองถูกมองเป็นโครงสร้างพื้นฐานสำคัญพร้อมการเฝ้าติดตามโดยเฉพาะ เพราะใบรับรองหมดอายุเพียงใบเดียวหรือการเปลี่ยนโซนที่ผิดอาจทำให้พอร์ทัลสิทธิประโยชน์ที่หันหน้าสู่ประชาชนออฟไลน์และก่อให้เกิดการตรวจสอบจากทั้งสาธารณะและฝ่ายนิติบัญญัติ

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

วินัยด้านเครือข่ายซื้อได้ถูก และการขาดมันถูกจ่ายในช่วงเวลาที่แย่ที่สุด การลงทุนส่วนใหญ่เป็นครั้งเดียวและมีรูปแบบเป็นแพลตฟอร์ม ได้แก่ ไคลเอนต์ร่วมที่มี timeout และการลองใหม่ การจัดการใบรับรองอัตโนมัติ การเฝ้าติดตาม DNS VPC ที่แบ่งส่วนอย่างสมเหตุสมผล และการแคชที่ขอบ แต่ละอย่างเป็นประโยชน์ต่อทุกทีมที่สืบทอด ต้นทุนส่วนเพิ่มต่อทีมจึงต่ำในขณะที่ผลตอบแทนทบกัน CDN โดยเฉพาะมักคุ้มทุนสองเท่า คือลดต้นทุนแบนด์วิดท์ต้นทาง ในขณะที่ปรับปรุงตัวเลขการเปลี่ยนเป็นลูกค้าและการมีส่วนร่วมที่ตามมาจากการโหลดหน้าที่เร็วขึ้น

ต้นทุนของการข้ามงานนี้วัดเป็นเหตุขัดข้องและการละเมิด ใบรับรองที่หมดอายุหรือการเปลี่ยน DNS ที่ผิดสามารถทำให้ทั้งผลิตภัณฑ์ออฟไลน์ในไม่กี่นาที โดยการแก้ล่าช้าเพราะวิศวกรไล่ตามชั้นที่ผิด timeout ที่ขาดไปทำให้การพึ่งพาที่ช้าตัวเดียวลุกลามเป็นแพลตฟอร์มชะงักทั้งหมด ขาออกที่ไม่ถูกควบคุมเปลี่ยนภาระงานที่ถูกเจาะตัวเดียวให้เป็นเหตุการณ์ขโมยข้อมูล ให้วางกรอบกรณีต่อผู้นำด้วยสิ่งที่พวกเขาติดตามอยู่แล้ว ได้แก่ ความพร้อมใช้งาน เวลาเฉลี่ยในการกู้คืน เวลาโหลดหน้า และความเสี่ยงของการละเมิด การจัดการใบรับรองและ DNS แบบอัตโนมัติป้องกันเหตุขัดข้องที่ทำร้ายตัวเองทั้งประเภท การลงทุนด้านขอบและ CDN ขยับเมตริกประสิทธิภาพของผลิตภัณฑ์ และการแบ่งส่วนกับการควบคุมขาออกลดรัศมีความเสียหายของการละเมิด ข้อโต้แย้งด้านต้นทุนรวมตลอดอายุการใช้งาน (TCO) คือสิ่งที่เกิดซ้ำตลอดคู่มือนี้ การสร้างความสามารถนี้เข้าไปเป็นเพียงเศษเสี้ยวของต้นทุนในการเติมมันย้อนหลังหลังเหตุการณ์ที่บังคับให้ต้องทำ

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **สมมติว่าเครือข่ายเชื่อถือได้และเร็ว** เขียนโค้ดเหมือนการเรียกระยะไกลเป็นการเรียกในเครื่อง ไม่มี timeout ไม่มีการลองใหม่ และไม่จัดการกรณี "หมดเวลาแต่อาจเสร็จไปแล้ว"
- **จัดการใบรับรองด้วยมือ** ติดตามวันหมดอายุในสเปรดชีตหรือความจำของใครบางคน รับประกันเหตุขัดข้องในที่สุดเมื่อมันหมดอายุโดยไม่มีใครสังเกต
- **เมิน DNS ในฐานะระบบการดำเนินงาน** ไม่มีการเฝ้าติดตามการแปลงชื่อ ตั้ง TTL อย่างสะเพร่า และเปลี่ยนเรคอร์ดโดยไม่มีความเข้มงวดแบบการปรับใช้
- **ลองใหม่โดยไม่มี idempotency หรือ backoff** ผลข้างเคียงซ้ำและพายุการลองใหม่ที่ประสานกันซึ่งขยายอาการสะดุดเล็กน้อยเป็นเหตุขัดข้อง
- **ไว้ใจเครือข่ายภายใน** มองทุกอย่างภายในเขตป้องกันว่าปลอดภัย โดยมีทราฟฟิกภายในที่ไม่เข้ารหัสและไม่มีการให้สิทธิ์ตามตัวตน
- **ขาออกที่ไม่ถูกควบคุม** ปล่อยให้ภาระงานเข้าถึงปลายทางขาออกใดก็ได้ มอบเส้นทางขโมยข้อมูลและช่องทางไปยังเซิร์ฟเวอร์สั่งการให้ผู้โจมตี
- **เส้นทางคำขอที่พูดมาก** สายการเรียกแบบซิงโครนัสลึกที่แต่ละฮอปเพิ่มหนึ่งรอบการเดินทาง ความหน่วงส่วนหางจึงพองขึ้นภายใต้โหลด
- **นำ service mesh มาใช้เร็วเกินไป** รับความซับซ้อนและความหน่วงของ sidecar สำหรับบริการไม่กี่ตัวที่ไคลเอนต์ร่วมรับใช้ได้ดีกว่า

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** การเรียกระยะไกลถูกมองเหมือนการเรียกในเครื่อง Timeout และการลองใหม่ขาดหายหรือไร้เดียงสา และ "หมดเวลาแต่อาจเสร็จไปแล้ว" ไม่ได้รับการจัดการ ใบรับรองและ DNS ถูกจัดการด้วยมือและก่อให้เกิดเหตุขัดข้องที่ไม่คาดคิด ไม่มีการแบ่งส่วน และทราฟฟิกภายในได้รับความไว้วางใจโดยค่าเริ่มต้น งานด้านการเชื่อมต่อเป็นแบบตั้งรับ เกิดขึ้นหลังจากเหตุการณ์บังคับเท่านั้น
- **ระดับ 2 พัฒนา:** บางทีมนำแนวปฏิบัติพื้นฐานมาใช้ แต่ไม่สม่ำเสมอข้ามบริการ มี timeout และการลองใหม่แบบง่ายในบางที่ TLS ถูกยุติที่ตัวกระจายโหลด และใบรับรองส่วนใหญ่เป็นอัตโนมัติ CDN อยู่หน้าเนื้อหาคงที่และมีการแบ่งส่วนเครือข่ายพื้นฐาน แม้ขาออกจะเปิดเกือบทั้งหมดและแต่ละทีมคิดค้นไคลเอนต์ของตนเอง สิ่งที่ทีมหนึ่งทำได้ดี อีกทีมยังไม่ได้เริ่ม
- **ระดับ 3 สร้างมาตรฐาน:** เครือข่ายที่ทนทานถูกบันทึกและบังคับใช้ทั่วองค์กร Timeout, backoff พร้อมจิตเตอร์ และ circuit breaker เป็นมาตรฐานผ่านไลบรารีร่วมหรือเกตเวย์ที่ทุกทีมสืบทอด DNS และใบรับรองถูกเฝ้าติดตามและทำให้เป็นอัตโนมัติเหมือนระบบการผลิต VPC ถูกแบ่งส่วนพร้อมขาเข้าและขาออกที่ควบคุม มีการเก็บเทเลเมทรีระดับการเชื่อมต่อทุกที่ และหลักการ zero trust กำลังถูกนำมาใช้เป็นนโยบาย ไม่ใช่การทดลองของทีมเดียว
- **ระดับ 4 บริหารจัดการ:** ขอบเขตเครือข่ายถูกวัดและควบคุมเทียบกับเส้นฐาน ไม่ใช่แค่ทำให้เป็นมาตรฐาน ความหน่วงของการแปลงชื่อ เวลาจับมือ TLS อัตราการส่งซ้ำและข้อผิดพลาดการเชื่อมต่อ ความหน่วงส่วนหาง (p99 ไม่ใช่ค่าเฉลี่ย) ระยะเวลาล่วงหน้าก่อนใบรับรองหมดอายุ และการละเมิดนโยบายขาออก ถูกติดตามบนแดชบอร์ดพร้อมเกณฑ์แจ้งเตือนและงบข้อผิดพลาด การตัดสินใจไป/ไม่ไปและเรื่องความจุขับเคลื่อนด้วยข้อมูลนั้น การซ้อมทำให้ DNS และการพึ่งพาล้มเหลวถูกรันตามกำหนดและวัดผล และการถดถอยของสัญญาณใดก็ตามถูกจับและมีเจ้าของ แทนที่จะค้นพบในเหตุขัดข้องครั้งต่อไป
- **ระดับ 5 ประสานทั้งระบบ:** เครือข่ายที่ทนทานเป็นค่าเริ่มต้นของแพลตฟอร์มที่ได้รับการปรับปรุงอย่างต่อเนื่อง ผสานทั่วองค์กรและปรับตัวตามการเปลี่ยนแปลง Mutual TLS และการให้สิทธิ์ตามตัวตนสม่ำเสมอ มักผ่าน service mesh กลยุทธ์ขอบและ CDN ถูกปรับเทียบกับข้อมูลความหน่วงสด ขาออกถูกกำกับดูแลเต็มที่ และโทโพโลยี ผู้ให้บริการ และการเลือกเส้นทางถูกปรับสมดุลเมื่อต้นทุน ความเสี่ยง และทราฟฟิกเปลี่ยนไป การตัดสินใจด้านเครือข่ายถูกถักทอเข้ากับการวางแผนด้านความจุ ความมั่นคงปลอดภัย และธุรกิจ และองค์กรใช้เหตุผลอย่างชัดเจนเกี่ยวกับรอบการเดินทาง ความหน่วงส่วนหาง และโหมดความล้มเหลวของขอบเขตเป็นเรื่องปกติ

## ประเด็นชวนคุย

1. หากผู้ให้บริการ DNS หลักหรือตัวแปลงชื่อของคุณเสื่อมสภาพไปหนึ่งชั่วโมง ระบบของคุณจะยังทำงานได้เท่าไร และคุณจะรู้ได้อย่างไร
2. บริการใดของคุณที่ยังส่งทราฟฟิกแบบไม่เข้ารหัสเมื่อมัน "อยู่ภายใน" เครือข่ายแล้ว และต้องทำอะไรจึงจะปิดช่องว่างนั้น
3. สายการเรียกแบบซิงโครนัสที่ลึกที่สุดในสถาปัตยกรรมของคุณอยู่ที่ไหน และคำขอของผู้ใช้ทั่วไปเกิดรอบการเดินทางบนเครือข่ายกี่รอบจริง
4. timeout ของคุณประกอบกันลงไปตามสายการเรียกเป็นงบประมาณที่สอดคล้องกันหรือไม่ หรือแต่ละชั้นตั้งของตนเองแล้วหวังว่าจะได้ผล
5. ภาระงานของคุณเข้าถึงอะไรบนอินเทอร์เน็ตสาธารณะได้ตอนนี้ และใครอนุมัติปลายทางขาออกแต่ละแห่งเหล่านั้น
6. ที่จำนวนบริการเท่าไร การบังคับใช้แบบสม่ำเสมอของ service mesh จะเกินต้นทุนการดำเนินงานสำหรับองค์กรของคุณ และคุณใกล้ถึงจุดนั้นแค่ไหน

## ข้อสรุปสำคัญ

- เครือข่ายคือสิ่งที่ต้องพึ่งพาซึ่งมีโหมดความล้มเหลวของตนเอง ออกแบบทุกการเรียกระยะไกลเพื่อความช้า การสูญหาย และความไม่ชัดเจนว่าเสร็จหรือยัง ไม่ใช่แค่ความสำเร็จหรือความล้มเหลวที่ชัดเจน
- ความหน่วงถูกกำหนดโดยรอบการเดินทางและระยะทาง จึงลดฮอป ใช้การเชื่อมต่อซ้ำ และย้ายข้อมูลเข้าใกล้ผู้ใช้ด้วย CDN และขอบ
- DNS และใบรับรอง TLS ล้มเหลวอย่างเงียบ ๆ และทำให้ทั้งบริการล่ม ทำให้เป็นอัตโนมัติและเฝ้าติดตามทั้งสองอย่างเหมือนระบบการผลิต
- กระจายโหลดที่ชั้นที่เหมาะกับทราฟฟิก และวางประเด็นร่วมไว้หลังเกตเวย์ L7 เฉพาะเมื่อต้นทุนด้านความพร้อมใช้งานและความสามารถในการสังเกตระบบคุ้มค่า
- ทำให้ขอบเขตเครือข่ายทนทานโดยค่าเริ่มต้นด้วย timeout การลองใหม่แบบจำกัดพร้อมจิตเตอร์ และ circuit breaker โดยเหมาะที่สุดคือเป็นค่าเริ่มต้นของแพลตฟอร์มที่สืบทอดกัน
- แบ่งส่วน VPC ของคุณ กำกับดูแลขาออก วางแผนสำหรับ IPv6 และนำ zero trust มาใช้ เพื่อให้การอยู่ "ภายใน" เครือข่ายไม่ให้ความไว้วางใจโดยอัตโนมัติ
