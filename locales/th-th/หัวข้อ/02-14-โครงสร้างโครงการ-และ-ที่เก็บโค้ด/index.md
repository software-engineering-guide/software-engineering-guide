# 2.14 โครงสร้างโครงการ และ ที่เก็บโค้ด

## ภาพรวมและแรงจูงใจ

โครงสร้างโครงการและที่เก็บโค้ดคือการจัดระเบียบทางกายภาพของโค้ดเบส ได้แก่โฟลเดอร์ ไฟล์ และข้อตกลงการตั้งชื่อ ที่กำหนดว่าแต่ละสิ่งอยู่ที่ไหน *ที่เก็บโค้ด* (repository มักย่อว่า "repo") คือภาชนะที่[ควบคุมเวอร์ชัน](https://en.wikipedia.org/wiki/Version_control)ซึ่งเก็บไฟล์ของโครงการและประวัติของมัน *โครงการ* (project) ซึ่งบางครั้งเรียกว่า *โซลูชัน* (solution) เมื่อรวมหลายส่วนประกอบที่เกี่ยวข้องกัน คือหน่วยตรรกะของซอฟต์แวร์ที่คุณกำลังสร้าง โครงสร้างคือแผนที่ที่คุณใช้ค้นหา ทำความเข้าใจ และเปลี่ยนแปลงซอฟต์แวร์นั้น

ในทีมเล็ก คนคนเดียวเก็บผังทั้งหมดไว้ในหัวได้ ในทีมใหญ่ที่มีวิศวกรหลายร้อยหรือหลายพันคน การย้ายระหว่างทีมบ่อยครั้ง และผู้รับเหมาที่เข้าออก ที่เก็บโค้ดทุกแห่งที่จัดระเบียบต่างกันเรียกเก็บภาษีทางความคิดใหม่ทุกครั้ง เมื่อคุณเปิดที่เก็บโค้ดที่ไม่คุ้นเคย คุณควรเดาได้ว่าซอร์ส การทดสอบ เอกสาร และคอนฟิกูเรชันการนำไปใช้งานอยู่ที่ไหน โดยไม่ต้องอ่านคู่มือ เมื่อทุกที่เก็บโค้ดตอบคำถามเหล่านั้นในแบบเดียวกัน การย้ายคนจึงถูกและการเริ่มงานเร็ว เมื่อแต่ละที่เก็บโค้ดเป็นสโนว์เฟลก (snowflake) ที่ไม่เหมือนใคร ทุกการสลับบริบทกลายเป็นโครงการวิจัยเล็กๆ

ในองค์กรขนาดใหญ่และภาครัฐ โครงสร้างที่สอดคล้องกันยังเป็นเรื่องของการควบคุมและการประกันด้วย ผู้ตรวจสอบ ผู้ทบทวนด้านความมั่นคงปลอดภัย และผู้ดูแลระยะยาว ซึ่งมักทำงานหลายปีหลังจากผู้เขียนเดิมจากไปแล้ว ต้องหาเอกสารข้อกำหนด ไฟล์ใบอนุญาต นโยบายความมั่นคงปลอดภัย และนิยามการสร้างได้อย่างน่าเชื่อถือ ผังที่คาดเดาได้ยังทำให้เครื่องมืออัตโนมัติ (เครื่องสแกน เครื่องวิเคราะห์การพึ่งพา การตรวจสอบการปฏิบัติตามกฎระเบียบ) ทำงานแบบเดียวกันทั่วพอร์ตโฟลิโอของระบบ บทนี้จึงมองโครงสร้างเป็นข้อตกลงที่คุณตัดสินใจครั้งเดียวและใช้ทุกที่ มันเกี่ยวข้องใกล้ชิดกับมาตรฐานการเขียนโค้ดและรูปแบบ (บทที่ 2.1) การควบคุมเวอร์ชันและการจัดการซอร์ส (บทที่ 2.6) และเอกสารประกอบ (บทที่ 2.7)

## หลักการสำคัญ

- ยึด*[หลักการแปลกใจน้อยที่สุด](https://en.wikipedia.org/wiki/Principle_of_least_astonishment)* (principle of least surprise) ผังควรตรงกับที่วิศวกรผู้มีประสบการณ์คาดหวัง เพื่อไม่ต้องท่องจำอะไร
- ความสอดคล้องข้ามที่เก็บโค้ดชนะความฉลาดเฉพาะที่ โครงสร้างที่เหมือนกันพอสมควรทุกที่มีค่ากว่าโครงสร้างที่สมบูรณ์แบบเพียงที่เดียว
- [README](https://en.wikipedia.org/wiki/README) คือประตูหน้า ผู้มาใหม่ควรปรับทิศทางตัวเองได้จากมันเพียงอย่างเดียว
- ทำให้โครงสร้างอธิบายตัวเองได้ผ่านการตั้งชื่อ เพื่อให้โฟลเดอร์และไฟล์ประกาศวัตถุประสงค์ของตัวเอง
- บังคับโครงสร้างด้วยโครงเริ่มต้นและแม่แบบ ไม่ใช่ด้วยกำลังใจและความเห็นในการทบทวน
- แยกความสนใจทางกายภาพ ซอร์ส การทดสอบ เอกสาร การสร้าง และการนำไปใช้งานควรอยู่ในที่ที่แยกกันและคาดเดาได้
- จัดระเบียบการพึ่งพาให้ไหลทิศทางเดียว จากแกนที่มั่นคงไปสู่ขอบที่ผันผวน

## ข้อแนะนำ

### ใช้ผังระดับบนสุดที่สอดคล้องกัน

กำหนดชุดโฟลเดอร์ระดับบนสุดมาตรฐานที่ทุกที่เก็บโค้ดใช้เมื่อเหมาะสม และบันทึกว่าแต่ละโฟลเดอร์มีไว้ทำอะไร ข้อตกลงทั่วไปที่ไม่ผูกกับผู้ขายประกอบด้วย โฟลเดอร์ซอร์ส (มักเป็น `src`) สำหรับโค้ดที่ใช้งานจริง โฟลเดอร์ทดสอบ (มักเป็น `test` หรือ `tests`) สำหรับการทดสอบอัตโนมัติ โฟลเดอร์ `docs` สำหรับเอกสาร โฟลเดอร์ `build` สำหรับนิยามและผลลัพธ์ของการสร้าง โฟลเดอร์ `deploy` สำหรับการนำไปใช้งานและ*[โครงสร้างพื้นฐานในรูปแบบโค้ด](https://en.wikipedia.org/wiki/Infrastructure_as_code)* (infrastructure as code: นิยามที่เครื่องอ่านได้ของเซิร์ฟเวอร์ เครือข่าย และบริการ ครอบคลุมในบทที่ 8.2) โฟลเดอร์ `scripts` สำหรับระบบอัตโนมัติและเครื่องมือของนักพัฒนา โฟลเดอร์ `examples` สำหรับตัวอย่างที่รันได้ และโฟลเดอร์ `spec` หรือ `specification` สำหรับความต้องการและข้อกำหนดการออกแบบ ไม่ใช่ทุกที่เก็บโค้ดต้องมีทุกโฟลเดอร์ แต่ในที่ที่มีเรื่องนั้นอยู่ มันควรอยู่ในที่ที่คาดหวังด้วยชื่อที่คาดหวัง

### ทำให้ README เป็นจุดเริ่มต้น

กำหนดให้มีไฟล์ README ที่รากของที่เก็บโค้ดเป็นจุดเริ่มต้นที่เป็นหนึ่งเดียวและเป็นที่ยึดถือ มันควรระบุว่าโครงการคืออะไร สร้างและรันอย่างไร รันการทดสอบอย่างไร หาเอกสารเชิงลึกได้ที่ไหน ใครเป็นเจ้าของ และร่วมพัฒนาอย่างไร README ไม่ใช่ชุดเอกสารทั้งหมด แต่เป็นดัชนีที่ชี้ไปยังส่วนที่เหลือ (บทที่ 2.7) มอง README ที่ขาดหรือล้าสมัยเป็นข้อบกพร่อง เพราะมันคือสิ่งแรกที่วิศวกรใหม่ ผู้ตรวจสอบ หรือผู้เชื่อมต่อทุกคนจะอ่าน

### สร้างมาตรฐานให้ไฟล์ตัวแก้ไขและคอนฟิกูเรชัน

เก็บคอนฟิกูเรชันตัวแก้ไขและเครื่องมือที่ใช้ร่วมกันไว้ในที่เก็บโค้ด เพื่อให้ผู้ร่วมพัฒนาทุกคนได้พฤติกรรมที่สอดคล้องกันโดยอัตโนมัติ ไฟล์ `.editorconfig` (ไฟล์ง่ายๆ ที่ไม่ผูกกับตัวแก้ไขซึ่งกำหนดกฎช่องว่าง การเยื้อง และการขึ้นบรรทัดใหม่) รักษารูปแบบพื้นฐานให้เหมือนกันข้ามตัวแก้ไขและระบบปฏิบัติการต่างๆ เพิ่มไฟล์ละเว้นสำหรับระบบควบคุมเวอร์ชัน (เพื่อไม่ให้ผลลัพธ์การสร้างและชิ้นงานท้องถิ่นถูกคอมมิตเด็ดขาด) พร้อมคอนฟิกูเรชันตัวจัดรูปแบบและตัวตรวจโค้ด (linter) ที่ใช้ร่วมกันตามที่อธิบายในบทที่ 2.1 ไฟล์เหล่านี้ทำให้ข้อตกลงของที่เก็บโค้ดมีผลจริง ไม่ใช่แค่บันทึกไว้

### กำหนดข้อตกลงการตั้งชื่อและโฟลเดอร์

ตกลงข้อตกลงการตั้งชื่อโฟลเดอร์และไฟล์ (รูปแบบตัวพิมพ์ ตัวคั่น เอกพจน์กับพหูพจน์ และคำต่อท้ายที่จำเป็น เช่นที่ระบุว่าเป็นการทดสอบ) และใช้อย่างสม่ำเสมอ ชื่อควรเผยเจตนาและตรงกับคำศัพท์โดเมนที่ใช้ที่อื่นในองค์กร เป้าหมายง่ายๆ คือเส้นทางควรสื่อความหมาย เพื่อให้การอ่านชื่อโฟลเดอร์หรือไฟล์บอกได้ว่าข้างในมีอะไรโดยไม่ต้องเปิด

### จัดระเบียบชั้นและการพึ่งพาอย่างตั้งใจ

จัดโครงสร้างโค้ดเบสให้ชั้นสถาปัตยกรรมปรากฏในผังโฟลเดอร์ และให้การพึ่งพาไหลทิศทางเดียวที่สมเหตุสมผล นโยบายระดับสูงไม่ควรพึ่งรายละเอียดระดับต่ำ โค้ดร่วมที่มั่นคงควรอยู่ในที่ที่หลายโมดูลเข้าถึงได้โดยไม่สร้างวงวน เมื่อคุณทำให้การแบ่งชั้นเป็นกายภาพ สะท้อนในต้นไม้ไดเรกทอรี วิศวกรมีแนวโน้มเคารพมันมากขึ้น และการละเมิดสังเกตเห็นได้ง่ายขึ้นในการทบทวนและในการตรวจสอบการพึ่งพาอัตโนมัติ

### บังคับโครงสร้างด้วยโครงเริ่มต้นและแม่แบบ

จัดให้มี*[โครงเริ่มต้น](https://en.wikipedia.org/wiki/Scaffold_%28programming%29)* (scaffolding) คือการสร้างโครงการเริ่มต้นโดยอัตโนมัติ เพื่อให้ที่เก็บโค้ดใหม่เริ่มต้นอย่างถูกต้องอยู่แล้ว *แม่แบบ* (template) หรือ *cookiecutter* (โครงโครงการที่ใส่พารามิเตอร์ได้ ซึ่งสร้างที่เก็บโค้ดสำเร็จรูปจากคำตอบของคำถามไม่กี่ข้อ) บรรจุผังมาตรฐาน README ไฟล์คอนฟิกูเรชัน และการตั้งค่า [CI](https://en.wikipedia.org/wiki/Continuous_integration) ไว้ในที่เดียว เมื่อวิศวกรสร้างบริการใหม่จากแม่แบบร่วม ความสอดคล้องกลายเป็นค่าเริ่มต้นแทนที่จะเป็นความใฝ่ฝัน และการปรับปรุงแม่แบบไหลไปสู่โครงการในอนาคต

### รักษาโครงสร้างให้สอดคล้องกันข้ามหลายที่เก็บโค้ดในระดับใหญ่

มองผังนั้นเองเป็นมาตรฐานที่มีธรรมาภิบาล คือดูแลจากส่วนกลางเหมือนมาตรฐานวิศวกรรมอื่นๆ (บทที่ 1.7) และกำหนดเวอร์ชันเหมือนโค้ด (บทที่ 2.6) เผยแพร่มัน จัดหาแม่แบบที่ทำให้มันเป็นจริง และอนุญาตให้เบี่ยงเบนผ่านกระบวนการยกเว้นที่มีเอกสารเท่านั้น เพื่อให้ "มาตรฐาน" ยังคงความหมาย ในระดับพอร์ตโฟลิโอ คุณค่าเกือบทั้งหมดของโครงสร้างมาจากความเหมือนกันข้ามที่เก็บโค้ด การเบี่ยงห่าง (drift) จึงเป็นความเสี่ยงหลักที่ต้องจัดการ

### ให้โครงสร้างช่วยตัดสินเรื่อง monorepo กับ multi-repo

เชื่อมโครงสร้างกับการตัดสินใจเรื่องขอบเขตของที่เก็บโค้ดที่ครอบคลุมในบทที่ 2.6 *[monorepo](https://en.wikipedia.org/wiki/Monorepo)* (ที่เก็บโค้ดเดียวที่เก็บหลายโครงการ) ต้องมีข้อตกลงภายในที่ชัดเจนสำหรับแยกโครงการและโค้ดร่วมของมัน เพื่อให้ต้นไม้ต้นเดียวนำทางได้ แนวทาง *multi-repo* (ที่เก็บโค้ดเล็กๆ จำนวนมาก หนึ่งต่อโครงการหรือบริการ) ต้องมีความสอดคล้องข้ามที่เก็บโค้ดที่แข็งแรง เพื่อให้แต่ละที่เก็บโค้ดรู้สึกคุ้นเคยแม้ยืนอยู่ลำพัง ไม่ว่าทางใด โครงสร้างที่มีเอกสารและมีแม่แบบคือสิ่งที่ทำให้การนำทางคาดเดาได้ การเลือกขอบเขตเปลี่ยนว่าคุณใช้ข้อตกลงที่ไหน ไม่ใช่ว่าคุณต้องการมันหรือไม่

## ข้อดีข้อเสียและการแลกเปลี่ยน

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| ผังมาตรฐานเข้มงวดทั้งองค์กร | คุ้นเคยทันที วิศวกรย้ายได้ เครื่องมือเหมือนกัน | บางครั้งไม่เหมาะกับโครงการที่ไม่ธรรมดา ต้องมีธรรมาภิบาล |
| อิสระในการจัดผังของแต่ละทีม | ปรับให้เหมาะเฉพาะที่ ทีมมีอิสระสูง | กระจัดกระจาย การสลับบริบทแพง เครื่องมือไม่สอดคล้อง |
| โครงเริ่มต้นและแม่แบบ | ที่เก็บโค้ดถูกต้องโดยค่าเริ่มต้น การเปลี่ยนแปลงแพร่ไปได้ | ต้องดูแลแม่แบบ เสี่ยงที่ที่เก็บโค้ดที่สร้างแล้วจะเบี่ยงห่าง |
| ลำดับชั้นโฟลเดอร์ลึกและเป็นชั้น | โครงสร้างชัดเจน ขอบเขตชัด | ภาระในการนำทาง เส้นทางยาว เสี่ยงออกแบบเกินจำเป็น |
| ผังแบนและตื้น | สแกนง่าย พิธีรีตองน้อย | แยกส่วนได้ไม่ดี พังเมื่อโครงการโต |

ข้อแลกเปลี่ยนหลักคือความเหมือนกันกับความเป็นอิสระ ผังมาตรฐานเดียวขจัดความฝืดสำหรับวิศวกรจำนวนมากที่ย้ายระหว่างโค้ดเบส โดยแลกกับโครงการที่ความต้องการไม่เข้ากับแม่พิมพ์เป็นครั้งคราว ในองค์กรใหญ่ ผลประโยชน์รวมจากความคุ้นเคยเกือบทุกครั้งมากกว่าความสูญเสียเฉพาะที่นั้น นั่นคือเหตุผลที่ท่าทีที่แนะนำคือมาตรฐานค่าเริ่มต้นที่แข็งแรงพร้อมเส้นทางยกเว้นที่มีเอกสาร (บทที่ 1.7) แทนที่จะเป็นความเหมือนกันที่แข็งทื่อหรือเสรีภาพที่ไม่มีการจัดการ ข้อแลกเปลี่ยนรองคือความลึกกับความเรียบง่าย คือมีโครงสร้างพอที่จะแยกความสนใจจริง แต่ไม่มากจนการนำทางกลายเป็นการเดินป่าผ่านโฟลเดอร์ว่างเปล่า

## คำถามที่ควรคุยกับทีม

1. **เมื่อวิศวกรย้ายไปยังที่เก็บโค้ดของเราที่ไม่คุ้นเคย ใช้เวลานานเท่าไรกว่าจะหาการทดสอบ คอนฟิกูเรชันการนำไปใช้งาน และเจ้าของเจอ** นี่คือภาษีการนำทางที่โครงสร้างมีไว้เพื่อกำจัด และในระดับพอร์ตโฟลิโอมันถูกจ่ายหลายพันครั้งต่อปีเป็นก้อนเล็กๆ ที่รวมกันเป็นเวลาวิศวกรรมที่เสียไปมหาศาล ประเด็นของหลักการแปลกใจน้อยที่สุดคือวิศวกรผู้มีประสบการณ์ควรเดาได้ว่าซอร์ส การทดสอบ เอกสาร และการนำไปใช้งานอยู่ที่ไหนโดยไม่ต้องอ่านคู่มือ การทดสอบที่ตรงไปตรงมาจึงคือการเดานั้นสำเร็จข้ามที่เก็บโค้ดของคุณหรือไม่ นำตัวเลขจริงมาที่การประชุม จับเวลาตัวเองขณะปรับทิศทางในที่เก็บโค้ดภายในที่ไม่คุ้นเคยสองสามแห่ง หรือดึงข้อมูลการเริ่มงานว่าผู้เข้าใหม่ใช้เวลานานเท่าไรกว่าจะทำการเปลี่ยนแปลงครั้งแรก ถ้าคำตอบวัดเป็นหลายวันของการค้นคว้าแทนที่จะเป็นไม่กี่นาทีของการจำได้ คุณได้ประเมินปริมาณต้นทุนของที่เก็บโค้ดแบบสโนว์เฟลก และมันพิสูจน์การลงทุนครั้งเดียวในผังมาตรฐานที่ทุกที่เก็บโค้ดใช้ร่วมกัน

2. **ชั้นสถาปัตยกรรมของเราปรากฏในต้นไม้โฟลเดอร์ หรือวงวนของการพึ่งพาซ่อนอยู่ในผังแบน** โครงสร้างไม่ได้มีไว้เพื่อการค้นหาเจออย่างเดียว เมื่อคุณทำให้การแบ่งชั้นเป็นกายภาพ วิศวกรเคารพมัน และผู้ทบทวนกับการตรวจสอบการพึ่งพาอัตโนมัติมองเห็นการละเมิดได้ ขณะที่กองแบนๆ ปล่อยให้การพึ่งพากันที่ไม่เหมาะสมและวงวนคืบคลานเข้ามาโดยไม่มีใครสังเกตจนการเปลี่ยนแปลงกลายเป็นอันตราย ในระบบใหญ่ที่อยู่ยาว นี่คือสิ่งที่กันไม่ให้นโยบายระดับสูงพึ่งรายละเอียดระดับต่ำอย่างเงียบๆ และเป็นการกร่อนที่ป้องกันถูกแต่ถอยกลับแพง นำกราฟการพึ่งพาของคุณมาหรือรันการตรวจอย่างรวดเร็ว มีวงวนหรือไม่ และมีสิ่งที่มั่นคงพึ่งสิ่งที่ผันผวนหรือไม่ คำตอบควรผลักให้คุณสะท้อนชั้นในไดเรกทอรีและเพิ่มการตรวจทิศทางการพึ่งพาอัตโนมัติ เพื่อให้ขอบเขตมองเห็นได้ในต้นไม้และถูกบังคับในสายพาน แทนที่จะอยู่เพียงในแบบจำลองทางความคิดของใครสักคน

3. **ที่เก็บโค้ดใหม่ของเราเริ่มต้นถูกต้องจากแม่แบบ หรือเราพึ่งหน้าวิกิและเจตนาดี** โครงสร้างที่บังคับด้วยโครงเริ่มต้นคือค่าเริ่มต้น โครงสร้างที่อธิบายในเอกสารจะเบี่ยงห่าง เพราะความเป็นจริงตามสิ่งที่สร้างที่เก็บโค้ด ไม่ใช่สิ่งที่หน้าหนึ่งบอกว่าควรเป็น สำหรับองค์กรใหญ่หรือที่อยู่ภายใต้กฎระเบียบ นี่ยังเป็นเรื่องการประกันด้วย เมื่อทุกที่เก็บโค้ดถูกสร้างจากแม่แบบร่วม เครื่องสแกนความมั่นคงปลอดภัย เครื่องวิเคราะห์การพึ่งพา และผู้ตรวจสอบพบใบอนุญาต นโยบายความมั่นคงปลอดภัย ข้อกำหนด และนิยามการสร้างในที่เดียวกันทุกครั้ง ข้ามผู้ขายและข้ามหลายปี นำหลักฐานมา ที่เก็บโค้ดล่าสุดของคุณกี่แห่งถูกสร้างจากแม่แบบมาตรฐานเทียบกับประกอบด้วยมือ และที่ใช้แม่แบบเบี่ยงห่างไปแล้วแค่ไหน สิ่งที่ต้องทำคือทำให้แม่แบบเป็นวิธีง่ายเพียงวิธีเดียวในการเริ่มที่เก็บโค้ด กำกับดูแลมันเป็นมาตรฐานที่มีเวอร์ชันพร้อมเส้นทางยกเว้นที่มีเอกสาร และตรวจจับการเบี่ยงห่างโดยอัตโนมัติ เพราะความเหมือนกันคือที่ที่คุณค่าของโครงสร้างเกือบทั้งหมดอยู่

4. **เราตัดสินใจหรือยังว่ามาตรฐานของเราครอบคลุม monorepo หรือหลายที่เก็บโค้ดแยกกัน และข้อตกลงเดียวกันใช้ได้จริงทั้งสองฝั่งของขอบเขตนั้นหรือไม่** การเลือกขอบเขตของที่เก็บโค้ดเปลี่ยนว่าคุณใช้ข้อตกลงที่ไหน ไม่ใช่ว่าคุณต้องการมันหรือไม่ และการทำผิดหมายถึงต้นไม้ยักษ์ต้นเดียวที่ไม่มีใครนำทางได้ หรือที่เก็บโค้ดกระจัดกระจายที่แต่ละแห่งรู้สึกแปลกหน้า monorepo ต้องการข้อตกลงภายในที่ชัดเจนสำหรับแยกโครงการและโค้ดร่วมของมัน เพื่อให้ต้นไม้ต้นเดียวนำทางได้ ขณะที่แนวทาง multi-repo ต้องการความสอดคล้องข้ามที่เก็บโค้ดที่แข็งแรง เพื่อให้แต่ละที่เก็บโค้ดที่ยืนอยู่ลำพังยังรู้สึกคุ้นเคย นำรายการปัจจุบันมา มีที่เก็บโค้ดกี่แห่ง โค้ดร่วมถูกแยกภายใน monorepo ใดอย่างไร และการทดสอบจับเวลาว่าวิศวกรหาโครงการในต้นไม้ใหญ่ได้เร็วเท่ากับหาในที่เก็บโค้ดเดี่ยวหรือไม่ สำหรับองค์กรขนาดใหญ่หรือโครงการภาครัฐที่ผู้ขายต่างรายส่งมอบที่เก็บโค้ดแยกกัน ให้ตัดสินใจอย่างตั้งใจว่าส่วนใดของข้อตกลงเป็นสากลและส่วนใดเฉพาะขอบเขต เพราะผู้ตรวจสอบและเครื่องมือแพลตฟอร์มต้องทำงานแบบเดียวกันไม่ว่าโค้ดจะมาเป็นต้นไม้เดียวหรือห้าสิบต้น

5. **ใครเป็นเจ้าของมาตรฐานโครงสร้างของเรา และเกิดอะไรขึ้นจริงเมื่อโครงการหนึ่งไม่เข้ากับมันจริงๆ** ในระดับพอร์ตโฟลิโอ คุณค่าของโครงสร้างเกือบทั้งหมดมาจากความเหมือนกัน ความเสี่ยงจริงจึงคือมาตรฐานที่ไม่มีเจ้าของและเน่าเปื่อย และเส้นทางยกเว้นที่คลุมเครือจนทุกทีมคิดผังของตัวเองอย่างเงียบๆ ความตึงเครียดอยู่ระหว่างความเหมือนกันที่แข็งทื่อซึ่งไม่เหมาะกับโครงการที่ไม่ธรรมดา กับเสรีภาพที่ไม่มีการจัดการซึ่งทำให้ทุกอย่างกระจัดกระจาย คำตอบที่ดีคือค่าเริ่มต้นที่แข็งแรงพร้อมกระบวนการยกเว้นที่มีเอกสารและตรวจสอบได้ ซึ่งกำกับโดยเจ้าของที่มีชื่อและกำหนดเวอร์ชันเหมือนโค้ด นำหลักฐานมา มีเจ้าของที่รับผิดชอบเพียงคนเดียวหรือไม่ มีเอกสารมาตรฐานที่มีเวอร์ชันพร้อมบันทึกการเปลี่ยนแปลงหรือไม่ มีบันทึกข้อยกเว้นที่ให้ไปและเหตุผลหรือไม่ และจำนวนการเบี่ยงเบนที่ไม่มีเอกสารที่คุณพบได้ในโลกจริง ในองค์กรขนาดใหญ่และภาครัฐ ข้อยกเว้นที่ไม่มีใครบันทึกคือช่องว่างของการควบคุม จึงผูกแต่ละการเบี่ยงเบนกับเหตุผลที่เป็นลายลักษณ์อักษรและวันทบทวน และให้แน่ใจว่าสัญญาจัดซื้อที่บังคับผังนั้นระบุด้วยว่าใครอนุมัติการออกนอกผังได้

6. **README และไฟล์คอนฟิกูเรชันที่เช็กอินไว้ของเราทำให้ข้อตกลงมีผลจริง หรือเป็นแค่ของประดับ** README คือประตูหน้า และ `.editorconfig` ไฟล์ละเว้น และคอนฟิกูเรชัน linter ที่เช็กอินไว้คือสิ่งที่ทำให้ข้อตกลงบังคับตัวเอง แต่สิ่งเหล่านี้คือสิ่งแรกที่ล้าสมัยและสิ่งสุดท้ายที่ใครสังเกตจนกว่าผู้ตรวจสอบหรือผู้เข้าใหม่จะสร้างโครงการไม่ได้ ความตึงเครียดอยู่ระหว่าง README กระชับที่ทันสมัยอยู่เสมอกับ README ละเอียดที่เบี่ยงห่าง และระหว่างการไว้ใจให้คนจัดรูปแบบโค้ดถูกต้องกับการให้คอนฟิกูเรชันร่วมบังคับอัตโนมัติ นำตัวอย่างมา ดึงห้าที่เก็บโค้ดแล้วตรวจว่า README กี่ฉบับระบุจริงว่าโครงการคืออะไร สร้าง ทดสอบ และรันอย่างไร และใครเป็นเจ้าของ และกี่ที่เก็บโค้ดมีไฟล์คอนฟิกูเรชันร่วมแทนที่จะพึ่งนิสัยของแต่ละคน สำหรับองค์กรใหญ่หรือที่อยู่ภายใต้กฎระเบียบ ซึ่งผู้เชื่อมต่อ ผู้ทบทวนด้านความมั่นคงปลอดภัย และผู้ดูแลระยะยาวอ่าน README ก่อนสิ่งอื่นใด ให้มองประตูหน้าที่ขาดหรือล้าสมัยเป็นข้อบกพร่องที่มีเจ้าของ และตรวจการมีอยู่ของไฟล์คอนฟิกูเรชันโดยอัตโนมัติ เพื่อให้ความสอดคล้องไม่ขึ้นกับน้ำใจ

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ความเร็วชนะ จึงตกลงผังที่เรียบง่ายและแบนพอสำหรับที่เก็บโค้ดแรก (src, test, docs, scripts, README ที่มีเนื้อหา, `.editorconfig` และไฟล์ละเว้น) และบันทึกเป็นแม่แบบน้ำหนักเบาในบ่ายวันเดียวกัน สร้างบริการที่สองจากมัน เพื่อให้ทั้งสองที่เก็บโค้ดรู้สึกคุ้นเคยและผู้รับเหมาใหม่เริ่มงานได้ในไม่กี่ชั่วโมงแทนที่จะต้องแกะสโนว์เฟลก ต้านทานลำดับชั้นลึกและธรรมาภิบาลหนักๆ ที่คุณยังไม่ต้องการ ผลตอบแทนทั้งหมดตรงนี้คือผู้ก่อตั้งสองคนกับผู้รับเหมาหนึ่งคนใช้แผนที่เดียวกัน

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญด้านแพลตฟอร์มและงบจำกัด ให้ใช้ผังตามข้อตกลงที่ภาษาหรือเฟรมเวิร์กของคุณสมมติไว้อยู่แล้ว แทนการคิดขึ้นเอง เพื่อให้เครื่องมือสำเร็จรูปและพนักงานใหม่ทุกคนมาพร้อมความคุ้นเคยกับมัน ซื้อโครงเริ่มต้น (ตัวสร้างของเฟรมเวิร์กหรือแม่แบบ cookiecutter) แทนที่จะสร้างเอง และใช้แรงอันน้อยนิดไปกับการรักษา README ที่มีเนื้อหาให้ทันสมัย README นั้นคือประกันที่ถูกที่สุดที่คุณมีสำหรับวันที่คนเดียวที่รู้ผังย้ายไปที่อื่น

**องค์กรขนาดใหญ่.** ข้ามหลายทีมและที่เก็บโค้ดหลายร้อยแห่ง เป้าหมายคือความเหมือนกัน เผยแพร่มาตรฐานโครงสร้างที่มีเวอร์ชัน สร้างทุกบริการใหม่จากแม่แบบร่วม ตรวจจับการเบี่ยงห่างโดยอัตโนมัติ และอนุญาตการเบี่ยงเบนผ่านกระบวนการยกเว้นที่มีเอกสารเท่านั้น เพราะทุกที่เก็บโค้ดดูเหมือนกัน วิศวกรที่ถูกย้ายไปทีมใหม่จึงทำงานได้ภายในไม่กี่ชั่วโมง และเครื่องสแกนความมั่นคงปลอดภัยและการพึ่งพาทั่วพอร์ตโฟลิโอพบใบอนุญาต นโยบายความมั่นคงปลอดภัย และนิยามการสร้างในที่เดียวกันทุกครั้ง จัดงบการดูแลแม่แบบและการตรวจจับการเบี่ยงห่างอย่างชัดเจน เพราะการดูแลนั้นคือสิ่งที่ทำให้มาตรฐานมีความหมายในระดับใหญ่

**ภาครัฐ.** การจัดซื้อจัดจ้าง ความโปร่งใส และความรับผิดชอบระยะยาวกำหนดรูปผัง จึงบังคับโครงสร้างร่วมในมาตรฐานการส่งมอบที่ผูกผู้ขายทุกราย กำหนดให้มีโฟลเดอร์ `specification` ที่เชื่อมโค้ดกับความต้องการที่อนุมัติ ไฟล์ใบอนุญาตและนโยบายความมั่นคงปลอดภัยที่ราก และโฟลเดอร์ `deploy` ที่เก็บนิยามโครงสร้างพื้นฐานในรูปแบบโค้ด เพื่อให้ผู้ตรวจสอบหาชิ้นงานด้านการปฏิบัติตามกฎระเบียบได้ในแบบเดียวกันในทุกระบบ เพราะผู้รับเหมาจากผู้ขายต่างรายทุกคนใช้แผนที่เดียว การบำรุงรักษาหลังสัญญาสิ้นสุดจึงถูกลงมาก และสาธารณชนได้เส้นทางที่ปกป้องได้และตรวจสอบได้จากความต้องการไปสู่โค้ดที่ทำงานอยู่

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสามคนตกลงผังมาตรฐานที่เรียบง่ายสำหรับที่เก็บโค้ดแรก (src, test, docs, scripts, README ที่มีเนื้อหา, .editorconfig และไฟล์ละเว้น) และบันทึกเป็นแม่แบบน้ำหนักเบา เมื่อพวกเขาเปิดบริการที่สองหนึ่งเดือนต่อมา พวกเขาสร้างมันจากแม่แบบนั้น ทั้งสองที่เก็บโค้ดจึงรู้สึกคุ้นเคยอยู่แล้วและผู้รับเหมาใหม่เริ่มงานได้ในบ่ายเดียว พวกเขาต้านทานลำดับชั้นโฟลเดอร์ลึกที่ยังไม่ต้องการ รักษาต้นไม้ให้แบนพอจะสแกนได้ในพริบตา ต้นทุนคือการตั้งค่าหนึ่งบ่าย และมันช่วยพวกเขาจากความกระจัดกระจายแบบสโนว์เฟลกที่จะทำให้ทุกที่เก็บโค้ดในอนาคตกลายเป็นโครงการวิจัยเล็กๆ

**องค์กรขนาดใหญ่.** ผู้ค้าปลีกข้ามชาติรันบริการหลายร้อยตัวในหลายภาษา ทีมแพลตฟอร์มเผยแพร่มาตรฐานโครงสร้างที่เก็บโค้ดที่มีเวอร์ชันและชุดแม่แบบโครงการที่ทำให้มันเป็นจริง ทุกบริการใหม่ถูกสร้างจากแม่แบบ จึงมาพร้อมโฟลเดอร์ `src`, `test`, `docs`, `deploy` และ `scripts` มาตรฐาน README ที่มีเนื้อหา `.editorconfig` ไฟล์ละเว้น และสายพาน CI ที่ใช้งานได้ เพราะทุกที่เก็บโค้ดดูเหมือนกัน วิศวกรที่ถูกย้ายไปทีมใหม่ทำงานได้ภายในไม่กี่ชั่วโมง และเครื่องสแกนความมั่นคงปลอดภัยและการพึ่งพาทั่วองค์กรรันได้เหมือนกันเพราะพบไฟล์ในที่ที่คาดหวังเสมอ

**ภาครัฐ.** หน่วยงานระดับชาติที่ปรับปรุงระบบเดิมบังคับผังที่เก็บโค้ดร่วมเป็นส่วนหนึ่งของมาตรฐานการส่งมอบสำหรับผู้ขายทุกราย แต่ละที่เก็บโค้ดต้องมีโฟลเดอร์ `specification` ที่เชื่อมโค้ดกับความต้องการที่อนุมัติ README ที่มีเอกสาร ไฟล์ใบอนุญาตและนโยบายความมั่นคงปลอดภัยที่ราก และโฟลเดอร์ `deploy` ที่เก็บนิยามโครงสร้างพื้นฐานในรูปแบบโค้ด (บทที่ 8.2) เพราะผู้รับเหมาจากผู้ขายต่างรายทุกคนทำตามโครงสร้างเดียวกัน ผู้ตรวจสอบของหน่วยงานจึงหาชิ้นงานด้านการปฏิบัติตามกฎระเบียบได้ในแบบเดียวกันในทุกระบบ และการบำรุงรักษาระยะยาวหลังสัญญาสิ้นสุดมีต้นทุนต่ำกว่ามาก เพราะผู้ดูแลที่เข้ามารู้แผนที่อยู่แล้ว

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

ต้นทุนของการนำมาตรฐานโครงสร้างมาใช้ส่วนใหญ่เกิดครั้งเดียว คือการตกลงผัง การสร้างแม่แบบ และการบันทึกข้อตกลง ต้นทุนที่เกิดซ้ำต่ำ รวมอยู่ที่การดูแลแม่แบบและการกำกับดูแลข้อยกเว้น ต้นทุนของการ*ไม่มี*มาตรฐานเกิดซ้ำและทบต้น ทุกวิศวกรที่เปิดที่เก็บโค้ดที่ไม่คุ้นเคยจ่ายภาษีการนำทาง ทุกการเริ่มงานช้าลง และเครื่องมืออัตโนมัติต้องตั้งค่าทีละที่เก็บโค้ดเพราะไม่มีอะไรอยู่ในที่ที่คาดหวัง ทั่วองค์กรใหญ่ ความฝืดเล็กๆ เหล่านี้คูณกันเป็นการสูญเสียเวลาวิศวกรรมอย่างร้ายแรง

ผลตอบแทนปรากฏเป็นการเริ่มงานที่เร็วขึ้น การย้ายระหว่างทีมที่ถูกลง สัญญาณที่ชัดขึ้นจากเครื่องมือทั่วพอร์ตโฟลิโอ และในสภาพแวดล้อมที่อยู่ภายใต้กฎระเบียบ ต้นทุนการตรวจสอบและการบำรุงรักษาระยะยาวที่ต่ำลง เพราะชิ้นงานหาเจอได้เสมอ *ต้นทุนรวมตลอดอายุการใช้งาน* (TCO หมายถึงต้นทุนตลอดอายุของการสร้าง รัน และบำรุงรักษาระบบ) ลดลงมากที่สุดในระบบที่อยู่ยาว ซึ่งผู้ดูแลที่ได้ประโยชน์จากโครงสร้างที่คาดเดาได้มักไม่ใช่ผู้เขียนที่สร้างมัน ในการนำเสนอต่อผู้บริหาร ให้วางโครงสร้างเป็นมาตรฐานต้นทุนต่ำที่ให้ผลทวีคูณสูง ซึ่งปรับปรุงผลิตภาพของนักพัฒนาและความพร้อมต่อการตรวจสอบ และใส่ตัวเลขให้ต้นทุนของความไม่สอดคล้องในปัจจุบันโดยใช้ข้อมูลเวลาเริ่มงานและแรงที่เสียไปกับการตามหาสิ่งต่างๆ ในที่เก็บโค้ดที่ไม่คุ้นเคย

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **ที่เก็บโค้ดสโนว์เฟลก:** ทุกที่เก็บโค้ดจัดต่างกัน ทำให้แต่ละที่ต้องเรียนรู้ใหม่ตั้งแต่ต้น
- **README ที่ขาดหรือล้าสมัย:** ไม่มีประตูหน้า บังคับให้ผู้มาใหม่ต้องแกะรอยว่าจะสร้างและรันโครงการอย่างไร
- **โครงสร้างด้วยเอกสาร ไม่ใช่ด้วยแม่แบบ:** หน้าวิกิอธิบายผังมาตรฐาน แต่ไม่มีอะไรสร้างหรือบังคับมัน ความเป็นจริงจึงเบี่ยงห่าง
- **แม่แบบเบี่ยงห่าง:** ที่เก็บโค้ดที่สร้างจากแม่แบบแยกออกไปตามเวลา และการปรับปรุงแม่แบบไม่เคยไปถึงมัน
- **ลำดับชั้นที่ออกแบบเกินจำเป็น:** โฟลเดอร์ซ้อนลึกที่แทบว่างเปล่า เพิ่มพิธีรีตองโดยไม่ช่วยการนำทาง
- **ความสนใจปนกัน:** ซอร์ส การทดสอบ ผลลัพธ์การสร้าง และความลับ ปนกันโดยไม่มีการแยกที่ชัดเจน
- **คอมมิตผลลัพธ์การสร้างและชิ้นงานท้องถิ่น:** ไฟล์ที่สร้างขึ้นถูกเช็กอินเพราะไม่เคยตั้งกฎละเว้น ทำให้ประวัติและ diff สกปรก
- **การละเมิดชั้นที่ซ่อนอยู่ในโครงสร้างแบน:** ไม่มีขอบเขตทางกายภาพ วงวนของการพึ่งพาและการพึ่งพากันที่ไม่เหมาะสมจึงคืบคลานเข้ามาโดยไม่มีใครสังเกต

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** แต่ละที่เก็บโค้ดถูกจัดแบบเฉพาะกิจโดยผู้เขียน ตอบสนองสิ่งที่ขณะนั้นต้องการ ผังต่างกันมาก README ขาดหรือเชื่อถือไม่ได้ และผู้มาใหม่ต้องมีคนพาเดินดูทุกที่เก็บโค้ดด้วยมือ
- **ระดับ 2 พัฒนา:** มีข้อตกลงพื้นฐานอย่างไม่เป็นทางการและหลายที่เก็บโค้ดคล้ายกัน บางทีมมีผังเริ่มต้นของตัวเอง แต่ไม่มีมาตรฐานที่เป็นที่ยึดถือ ไม่มีโครงเริ่มต้นร่วม และโครงสร้างเบี่ยงห่างอย่างเห็นได้ชัดจากทีมหนึ่งไปอีกทีม
- **ระดับ 3 สร้างมาตรฐาน:** มาตรฐานโครงสร้างที่มีเอกสารและมีเวอร์ชันถูกบังคับใช้ทั่วองค์กร ที่เก็บโค้ดใหม่ถูกสร้างจากแม่แบบร่วมที่มีผังมาตรฐาน README ไฟล์คอนฟิกูเรชัน และ CI การเบี่ยงเบนผ่านกระบวนการยกเว้นที่มีเอกสาร แทนที่จะเกิดขึ้นอย่างเงียบๆ
- **ระดับ 4 บริหารจัดการ:** ความสอดคล้องกับมาตรฐานถูกวัดและควบคุมด้วยข้อมูล การตรวจอัตโนมัติรายงานว่าสัดส่วนของที่เก็บโค้ดที่ตรงกับผังเป็นเท่าไร ที่เก็บโค้ดที่ใช้แม่แบบเบี่ยงห่างไปแค่ไหน ความสมบูรณ์ของ README และการละเมิดทิศทางการพึ่งพา ทั้งหมดติดตามเทียบกับเบสไลน์ เวลาเริ่มงานและเวลานำทางถูกวัด ข้อยกเว้นถูกบันทึกและทบทวน และการเปลี่ยนแม่แบบได้รับอนุมัติตามหลักฐานแทนความเห็น
- **ระดับ 5 ประสานทั้งระบบ:** โครงสร้างได้รับการปรับปรุงต่อเนื่องและปรับตัวได้ การปรับปรุงแม่แบบแพร่ไปยังที่เก็บโค้ดที่มีอยู่โดยอัตโนมัติ ธรรมาภิบาลโครงสร้างผสานกับเครื่องมือด้านความมั่นคงปลอดภัย การปฏิบัติตามกฎระเบียบ และแพลตฟอร์ม และมาตรฐานพัฒนาอย่างตั้งใจเมื่อภาษา สถาปัตยกรรม และพอร์ตโฟลิโอเปลี่ยนไป รักษาความเหมือนกันให้สูงขณะที่องค์กรเปลี่ยนไปรอบๆ

## ประเด็นชวนคุย

- โฟลเดอร์ระดับบนสุดใดควรเป็นสากลจริงๆ ทั่วองค์กรของคุณ และใดควรเป็นทางเลือก
- คุณป้องกันไม่ให้ที่เก็บโค้ดที่สร้างจากแม่แบบเบี่ยงห่างออกไปตามเวลาได้อย่างไร
- เส้นแบ่งระหว่างลำดับชั้นเป็นชั้นที่มีประโยชน์กับพิธีรีตองของโฟลเดอร์ที่ออกแบบเกินจำเป็นอยู่ที่ไหน
- มาตรฐานโครงสร้างของคุณควรต่างกันอย่างไร (ถ้าต่าง) ระหว่างแนวทาง monorepo กับ multi-repo
- กระบวนการยกเว้นที่เหมาะสมสำหรับโครงการที่ความต้องการจริงไม่เข้ากับผังมาตรฐานคืออะไร
- โครงสร้างของคุณตรวจอัตโนมัติได้เท่าไร และส่วนใดยังพึ่งการทบทวนโดยมนุษย์
- ใครเป็นเจ้าของมาตรฐานโครงสร้างและแม่แบบ และการเปลี่ยนแปลงถูกเสนอและนำออกใช้อย่างไร

## ข้อสรุปสำคัญ

- จัดระเบียบทุกที่เก็บโค้ดเพื่อให้วิศวกรคนใดนำทางโค้ดเบสใดก็ได้ด้วยความคาดหมาย ตามหลักการแปลกใจน้อยที่สุด
- ใช้ผังระดับบนสุดที่สอดคล้องกัน (ซอร์ส การทดสอบ เอกสาร การสร้าง การนำไปใช้งาน สคริปต์ ตัวอย่าง ข้อกำหนด) และทำให้ README เป็นจุดเริ่มต้น
- เช็กอินคอนฟิกูเรชันตัวแก้ไขและเครื่องมือ (เช่น `.editorconfig`) เพื่อให้ข้อตกลงมีผลจริง ไม่ใช่แค่เขียนไว้
- บังคับโครงสร้างด้วยโครงเริ่มต้นและแม่แบบ เพื่อให้ที่เก็บโค้ดใหม่ถูกต้องโดยค่าเริ่มต้น
- ในระดับใหญ่ คุณค่าอยู่ที่ความเหมือนกัน กำกับดูแลมาตรฐาน จัดการการเบี่ยงห่าง และอนุญาตการเบี่ยงเบนผ่านข้อยกเว้นที่มีเอกสารเท่านั้น
