# 5.7 การพัฒนาแอปพลิเคชันมือถือ

## ภาพรวมและแรงจูงใจ

[การพัฒนาแอปพลิเคชันมือถือ](https://en.wikipedia.org/wiki/Mobile_app_development) (mobile application development) คือศาสตร์ของการสร้างซอฟต์แวร์สำหรับโทรศัพท์และแท็บเล็ต สำหรับหลายคน โทรศัพท์คือคอมพิวเตอร์เครื่องหลักหรือเครื่องเดียวที่มีอยู่ในปัจจุบัน ทำให้แอปมือถือเป็นประตูหน้าของบริการของคุณ และมักเป็นที่ที่ผู้ใช้ตัดสินองค์กรของคุณทั้งองค์กร

มือถือเป็นสภาพแวดล้อมทางวิศวกรรมที่ต่างออกไป ไม่ใช่เว็บหรือเดสก์ท็อปฉบับย่อส่วน อุปกรณ์อยู่ในกระเป๋า ใช้แบตเตอรี่ และเชื่อมต่อผ่านเครือข่ายที่ขาดๆ หายๆ หน้าจอเล็ก ระบบปฏิบัติการควบคุมว่าแอปของคุณทำอะไรได้บ้าง มีสองแพลตฟอร์มหลัก ([iOS](https://en.wikipedia.org/wiki/IOS) ของ Apple และ [Android](https://en.wikipedia.org/wiki/Android_%28operating_system%29) ของ Google) แต่ละแพลตฟอร์มมีภาษา กฎการออกแบบ และสโตร์ของตัวเอง คุณปล่อยอัปเดตเมื่อไรก็ได้ตามใจไม่ได้ เพราะสโตร์ต้องตรวจก่อน และผู้ใช้เป็นคนเลือกว่าจะติดตั้งเมื่อไร บทนี้ต่อยอดจากวิศวกรรมส่วนหน้า (บทที่ 5.6) พื้นฐาน UX (บทที่ 5.1) และการเข้าถึง (บทที่ 5.3) และพึ่งพาความมั่นคงปลอดภัยของแอปพลิเคชัน (บทที่ 4.2) กับ CI/CD และการส่งมอบ (บทที่ 8.1)

ความเกี่ยวข้องกับองค์กรขนาดใหญ่และภาครัฐสูงมาก องค์กรส่งมอบทั้งแอปสำหรับลูกค้าและแอปภายในสำหรับพนักงานของตนเอง ซึ่งมักบริหารผ่าน[การจัดการอุปกรณ์เคลื่อนที่](https://en.wikipedia.org/wiki/Mobile_device_management) (MDM: ซอฟต์แวร์กลางที่ตั้งค่าและรักษาความปลอดภัยให้อุปกรณ์ของบริษัท) รัฐบาลสร้างแอปสำหรับประชาชนด้านสวัสดิการ สุขภาพ การยืนยันตัวตน และการชำระเงิน และต้องให้บริการทุกคน รวมถึงผู้ที่ใช้อุปกรณ์เก่าและการเชื่อมต่อช้า ภายใต้กฎหมายด้านการเข้าถึง ทั้งสองบริบทถือว่ามือถือเป็นข้อผูกพันที่จริงจังและยาวนาน จึงควรปฏิบัติต่อมันด้วยความเข้มงวดเท่ากับระบบใช้งานจริงอื่นๆ

## หลักการสำคัญ

- ออกแบบเพื่ออุปกรณ์: หน้าจอเล็ก แบตเตอรี่ และเครือข่ายที่ขาดๆ หายๆ
- สมมติว่าการเชื่อมต่อไม่ต่อเนื่อง ทำงานแบบออฟไลน์ก่อน แล้วซิงก์เมื่อทำได้
- เคารพธรรมเนียมการออกแบบและการโต้ตอบของแต่ละแพลตฟอร์ม
- คุณไม่ได้ควบคุมเวลาปล่อยรุ่น สโตร์และผู้ใช้เป็นผู้ควบคุม
- ความหลากหลายของอุปกรณ์เป็นเรื่องปกติ รองรับอุปกรณ์และเวอร์ชัน OS ในช่วงที่ตรงกับความจริง
- เก็บข้อมูลบนอุปกรณ์อย่างปลอดภัย เพราะอุปกรณ์หายและถูกขโมยได้
- การเข้าถึงเป็นข้อกำหนด ไม่ใช่ขั้นตอนตกแต่งตอนท้าย
- เลือกแนวทางการสร้างให้เหมาะกับอายุขัยทั้งหมดของแอป ไม่ใช่แค่วันเปิดตัว

## ข้อแนะนำ

### เลือกแนวทางการสร้างอย่างตั้งใจ

มีสามแนวทางหลัก และแต่ละแบบเหมาะกับความต้องการต่างกัน

[การพัฒนาแบบเนทีฟ](https://en.wikipedia.org/wiki/Mobile_app_development) (native) หมายถึงการเขียนแยกสำหรับแต่ละแพลตฟอร์มด้วยเครื่องมือของแพลตฟอร์มนั้น คือ Swift สำหรับ iOS และ Kotlin สำหรับ Android คุณได้ประสิทธิภาพที่ดีที่สุด การเข้าถึงฟีเจอร์ของอุปกรณ์ได้เต็มที่ที่สุด และความรู้สึกแบบแพลตฟอร์มที่ซื่อตรงที่สุด โดยแลกกับการสร้างและดูแลสองโค้ดเบส

[เฟรมเวิร์กข้ามแพลตฟอร์ม](https://en.wikipedia.org/wiki/Cross-platform_software) (cross-platform) ให้โค้ดเบสเดียวรองรับทั้งสองแพลตฟอร์ม [React Native](https://en.wikipedia.org/wiki/React_Native) ใช้ JavaScript และเรนเดอร์คอมโพเนนต์เนทีฟจริง [Flutter](https://en.wikipedia.org/wiki/Flutter_%28software%29) ใช้ภาษา Dart และวาดวิดเจ็ตของตัวเอง แนวทางเหล่านี้ลดงานซ้ำซ้อนและช่วยให้ส่งมอบได้เร็วขึ้น แต่เพิ่มการพึ่งพาสุขภาพของเฟรมเวิร์ก และอาจตามฟีเจอร์ใหม่ล่าสุดของแพลตฟอร์มไม่ทัน

[เว็บแอปแบบก้าวหน้า](https://en.wikipedia.org/wiki/Progressive_web_app) (PWA: เว็บไซต์ที่ติดตั้งได้และทำงานแบบออฟไลน์ได้) ไม่ต้องผ่านสโตร์และอัปเดตได้ทันที แต่เข้าถึงฟีเจอร์ของอุปกรณ์บางอย่างได้จำกัด และมีตัวตนบนหน้าจอหลักน้อยกว่า

เลือกตามฟีเจอร์ของอุปกรณ์ที่ต้องใช้ ลักษณะประสิทธิภาพ ระยะเวลาการดูแล ทักษะที่จ้างได้ และการเข้าถึงที่ต้องการ แอปผู้บริโภคที่ต้องการประสิทธิภาพสูงอาจคุ้มกับเนทีฟ ส่วนแอปเนื้อหาและฟอร์มที่มีทีมเล็กอาจเหมาะกับข้ามแพลตฟอร์มหรือ PWA

### ทำตามแนวทางการออกแบบของแพลตฟอร์ม

แต่ละแพลตฟอร์มมีธรรมเนียมที่เผยแพร่ไว้อย่างละเอียด Apple มี[Human Interface Guidelines](https://en.wikipedia.org/wiki/Human_interface_guidelines) และ Google มี [Material Design](https://en.wikipedia.org/wiki/Material_Design) ครอบคลุมการนำทาง ท่าทางสัมผัส ตัวอักษร ระยะห่าง และพฤติกรรมของระบบ การทำตามทำให้แอปให้ความรู้สึกคุ้นเคย ซึ่งลดแรงที่ผู้ใช้ต้องใช้ในการเรียนรู้ การฝืนทำให้แอปรู้สึกแปลกและอึดอัด โค้ดเบสข้ามแพลตฟอร์มยังต้องเคารพธรรมเนียมเฉพาะแพลตฟอร์มในจุดที่ต่างกัน แทนที่จะบังคับหน้าตาของแพลตฟอร์มหนึ่งไปใส่อีกแพลตฟอร์มหนึ่ง

### ออกแบบให้รับข้อจำกัดของมือถือ

สร้างแบบออฟไลน์ก่อน ให้งานหลักทำได้โดยไม่มีการเชื่อมต่อ เก็บการเปลี่ยนแปลงไว้ในเครื่อง และซิงก์เมื่อเครือข่ายกลับมา จัดการความขัดแย้งอย่างรอบคอบเมื่อข้อมูลเดียวกันเปลี่ยนในสองที่ ประหยัดแบตเตอรี่และข้อมูล รวมการเรียกเครือข่ายเป็นชุด หลีกเลี่ยงการใช้ตำแหน่งหรือทำงานเบื้องหลังตลอดเวลา บีบอัดเพย์โหลด และเคารพการตั้งค่าประหยัดข้อมูลของผู้ใช้ วางแผนรับมือความหลากหลายของอุปกรณ์ ซึ่งกระจายตั้งแต่ขนาดหน้าจอ กำลังเครื่อง ไปจนถึงเวอร์ชัน OS เลือกช่วงที่รองรับจากข้อมูลการใช้งานจริง และทดสอบบนฮาร์ดแวร์ระดับธรรมดา ไม่ใช่แค่รุ่นเรือธง ออกแบบสำหรับหน้าจอเล็กด้วยลำดับชั้นที่ชัด พื้นที่สัมผัสขนาดใหญ่ และเนื้อหาที่ปรับตามขนาดและการวางแนวที่ต่างกัน

### วางแผนการเผยแพร่ การกำหนดเวอร์ชัน และการอัปเดต

การเผยแพร่ผ่าน [Apple App Store](https://en.wikipedia.org/wiki/App_Store_%28Apple%29) และ [Google Play](https://en.wikipedia.org/wiki/Google_Play) ซึ่งแต่ละแห่งมีขั้นตอนตรวจสอบและนโยบายที่อาจทำให้รุ่นล่าช้าหรือถูกปฏิเสธ ใส่เวลาตรวจสอบไว้ในตารางงาน และอ่านนโยบายแต่เนิ่นๆ เพราะผู้ใช้เลือกเองว่าจะอัปเดตเมื่อไร คุณจึงมีหลายเวอร์ชันอยู่ในสนามพร้อมกันเสมอ ทำให้แอปเข้ากันได้ย้อนหลังกับไคลเอนต์รุ่นเก่า และกำหนดเวอร์ชัน API (บทที่ 2.3) เพื่อให้แอปรุ่นเก่ายังทำงานได้ จัดช่องทางบังคับให้อัปเดตเมื่อจำเป็น เช่น หน้าต่างบังคับอัปเดตเมื่อเวอร์ชันนั้นไม่ปลอดภัยหรือไม่รองรับแล้ว และใช้อย่างประหยัด องค์กรยังแจกจ่ายแอปภายในผ่าน MDM หรือช่องทางส่วนตัวแทนสโตร์สาธารณะได้

### ใช้การแจ้งเตือนแบบพุชและดีปลิงก์อย่างระมัดระวัง

[การแจ้งเตือนแบบพุช](https://en.wikipedia.org/wiki/Push_technology) (push notification) ช่วยให้เข้าถึงผู้ใช้ได้เมื่อแอปปิดอยู่ ใช้เมื่อมีคุณค่าจริง เคารพความยินยอมของผู้ใช้และสิทธิ์ของแพลตฟอร์ม และหลีกเลี่ยงความรกรุงรัง เพราะผู้คนปิดการแจ้งเตือนของแอปที่ล้ำเส้น [ดีปลิงก์](https://en.wikipedia.org/wiki/Deep_linking) (deep link) พาผู้ใช้ตรงไปยังหน้าจอเฉพาะจากลิงก์หรือการแจ้งเตือน ตั้งค่าให้ลิงก์เปิดไปยังตำแหน่งที่ถูกต้องในแอป และถอยกลับไปที่เว็บอย่างนุ่มนวลเมื่อยังไม่ได้ติดตั้งแอป

### รักษาความปลอดภัยของแอปและข้อมูล

ถือว่าอุปกรณ์ไม่น่าไว้วางใจและอาจสูญหาย เก็บข้อมูลอ่อนไหวในที่เก็บที่ปลอดภัยของแพลตฟอร์ม ([iOS Keychain](https://en.wikipedia.org/wiki/Keychain_%28software%29) หรือ Android Keystore) อย่าเก็บในไฟล์ธรรมดา เสนอ[การยืนยันตัวตนด้วยชีวมิติ](https://en.wikipedia.org/wiki/Biometrics) (ลายนิ้วมือหรือใบหน้า) เพื่อปลดล็อกการกระทำที่อ่อนไหว โดยมีรหัสผ่านสำรอง พิจารณา[การตรึงใบรับรอง](https://en.wikipedia.org/wiki/Public_key_pinning) (certificate pinning: ตรวจว่าเซิร์ฟเวอร์ส่งใบรับรองที่คาดไว้) สำหรับการเชื่อมต่อที่มีมูลค่าสูง และวางแผนการหมุนเวียนใบรับรองเหล่านั้น เก็บข้อมูลบนอุปกรณ์ให้น้อยที่สุด ปกป้องความลับ และทำตามแนวทางที่กว้างกว่าในความมั่นคงปลอดภัยของแอปพลิเคชัน (บทที่ 4.2)

### สร้างสายงานทดสอบและส่งมอบที่ใช้ได้จริง

ทดสอบบนอุปกรณ์จริง ไม่ใช่แค่[อีมูเลเตอร์](https://en.wikipedia.org/wiki/Emulator)และซิมูเลเตอร์ เพราะฮาร์ดแวร์ เซนเซอร์ และประสิทธิภาพต่างกัน ใช้ห้องแล็บอุปกรณ์หรือฟาร์มอุปกรณ์บนคลาวด์เพื่อครอบคลุมรุ่นและเวอร์ชัน OS ที่เป็นตัวแทน ทำให้การบิลด์ ทดสอบ เซ็นลายมือชื่อ และส่งขึ้นสโตร์เป็นอัตโนมัติผ่าน[การรวมระบบและส่งมอบอย่างต่อเนื่อง](https://en.wikipedia.org/wiki/CI/CD) (บทที่ 8.1) รวมถึงการแจกจ่ายรุ่นเบต้าให้ผู้ทดสอบก่อนเผยแพร่สู่สาธารณะ การจัดการกุญแจเซ็นและข้อมูลรับรองของสโตร์อย่างปลอดภัยเป็นส่วนหนึ่งของสายงานนี้

### ทำให้การเข้าถึงเป็นข้อกำหนด

รองรับฟีเจอร์การเข้าถึงของแต่ละแพลตฟอร์ม ได้แก่ตัวอ่านหน้าจอ ([VoiceOver](https://en.wikipedia.org/wiki/VoiceOver) บน iOS และ [TalkBack](https://en.wikipedia.org/wiki/Google_TalkBack) บน Android) การปรับขนาดข้อความแบบไดนามิก ความเปรียบต่างของสีที่เพียงพอ และพื้นที่สัมผัสขนาดใหญ่ ใส่ป้ายกำกับให้ตัวควบคุม เพื่อให้เทคโนโลยีช่วยเหลืออธิบายได้ ทดสอบด้วยเครื่องมือช่วยเหลือจริง ไม่ใช่แค่การตรวจอัตโนมัติ โดยเฉพาะสำหรับภาครัฐ การเข้าถึงเป็นข้อบังคับทางกฎหมาย และรายละเอียดอยู่ในบทการเข้าถึง (บทที่ 5.3)

## ข้อดีข้อเสียและการแลกเปลี่ยน

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| เนทีฟ (Swift, Kotlin) | ประสิทธิภาพดีที่สุด เข้าถึงอุปกรณ์ได้เต็มที่ ให้ความรู้สึกแบบแพลตฟอร์มจริง | สองโค้ดเบส ต้นทุนสูงกว่า ต้องใช้คนมากกว่า |
| React Native | โค้ดเบส JavaScript เดียว คอมโพเนนต์เนทีฟจริง ปรับปรุงได้เร็ว | พึ่งพาเฟรมเวิร์ก ซับซ้อนที่ตัวเชื่อม ฟีเจอร์ตามไม่ทัน |
| Flutter | โค้ดเบสเดียว UI สม่ำเสมอ ประสิทธิภาพแรง | ทักษะ Dart พบน้อยกว่า ขนาดแอปใหญ่กว่า มีโมเดลวิดเจ็ตของตัวเอง |
| เว็บแอปแบบก้าวหน้า | ไม่ต้องผ่านสโตร์ อัปเดตทันที โค้ดเบสเว็บเดียว | ฟีเจอร์อุปกรณ์จำกัด มีตัวตนน้อยกว่า ติดข้อจำกัดของแพลตฟอร์ม |
| การบังคับอัปเดต | กำจัดเวอร์ชันเก่าที่ไม่ปลอดภัยได้เร็ว | ทำให้ผู้ใช้รำคาญถ้าใช้บ่อยเกินไป อาจขวางการเข้าใช้ |
| การตรึงใบรับรอง | ป้องกันการดักข้อมูลได้เข้มแข็ง | พังเมื่อหมุนเวียนใบรับรองโดยไม่ได้อัปเดตแอป |

ข้อแลกเปลี่ยนที่เกิดซ้ำๆ คือการเข้าถึงและความเร็วในการส่งมอบ เทียบกับความลึกและความซื่อตรง เนทีฟให้ประสบการณ์ที่สมบูรณ์และซื่อตรงที่สุด แต่มีต้นทุนการสร้างและดูแลสูงที่สุด แนวทางข้ามแพลตฟอร์มและ PWA ประหยัดแรงและขยายการเข้าถึง โดยแลกกับความรู้สึกแบบแพลตฟอร์มหรือการเข้าถึงอุปกรณ์บางส่วน สำหรับทีมเล็กที่ส่งมอบฟอร์มและเนื้อหา การใช้โค้ดเบสร่วมกันมักเป็นทางเลือกที่ฉลาด สำหรับแอปผู้บริโภคที่เรียกร้องสูง ความลึกของเนทีฟอาจคุ้มกับราคา ตัดสินใจโดยมองอายุขัยทั้งหมดของแอป ไม่ใช่แค่ตอนเปิดตัว

## คำถามที่ควรคุยกับทีม

1. **เราจะรองรับไคลเอนต์รุ่นเก่าในสนามนานแค่ไหน และ API ของเรากำหนดเวอร์ชันไว้เพื่อให้ไคลเอนต์เหล่านั้นยังใช้งานได้หรือไม่?** เพราะผู้ใช้เลือกเองว่าจะอัปเดตเมื่อไร คุณจึงมีแอปหลายเวอร์ชันติดตั้งอยู่พร้อมกันเสมอ และการเปลี่ยนแปลงฝั่งหลังบ้านที่สมมติว่าทุกคนเป็นรุ่นล่าสุดจะทำให้ไคลเอนต์รุ่นเก่าส่วนหางพัง ตัดสินใจช่วงเวลาที่รองรับย้อนหลัง กำหนดเวอร์ชัน API เพื่อให้แอปรุ่นเก่ายังทำงานได้ และเก็บช่องทางบังคับอัปเดตที่ใช้น้อยไว้สำหรับเวอร์ชันที่ไม่ปลอดภัยจริงๆ เรื่องนี้สำคัญเท่ากันทั้งแอปของประชาชนในภาครัฐและแอปของพนักงานองค์กร ที่ผู้ใช้อุปกรณ์เก่าอัปเกรดตามกำหนดของคุณไม่ได้หรือไม่ยอม ลองนำข้อมูลการกระจายเวอร์ชันปัจจุบันมาดู และถามว่าอะไรจะพังสำหรับไคลเอนต์รุ่นเก่าที่สุดที่ยังใช้งานอยู่จริง ถ้าคุณไม่รู้การกระจายนั้น ให้ติดตั้งการวัดก่อนปล่อยการเปลี่ยนแปลงที่ทำให้พังครั้งต่อไป

2. **เกณฑ์ของเราในการส่งการแจ้งเตือนแบบพุชคืออะไร และใครตัดสินว่าอะไรคุ้มที่จะรบกวนผู้ใช้?** การแจ้งเตือนแบบพุชเข้าถึงผู้คนเมื่อแอปปิดอยู่ ทำให้ทรงพลังและถูกใช้ผิดได้ง่าย และผู้ใช้ปิดการแจ้งเตือน (หรือลบแอป) ของผลิตภัณฑ์ที่ล้ำเส้น ตกลงกันว่าอะไรนับเป็นคุณค่าจริง ผู้ใช้ควบคุมความถี่และช่องทางได้อย่างไร และจะเคารพความยินยอมตามแพลตฟอร์มอย่างไรแทนการตื๊อขอสิทธิ์ หากไม่มีเกณฑ์ร่วม ทุกทีมที่มีตัวชี้วัดต้องทำให้ถึงก็จะหันไปใช้พุช และช่องทางทั้งหมดเสื่อมเป็นเสียงรบกวน ลองนำการแจ้งเตือนที่ส่งไปในเดือนที่แล้วมาดู แล้วถามว่าฉบับไหนที่ผู้ใช้จะขอบคุณคุณ ถ้าส่วนใหญ่เป็นเชิงโปรโมต ให้ขันนโยบายให้เข้มก่อนที่อัตราการปิดรับจะทำแทนคุณ

3. **สายงานส่งมอบมือถือของเราใช้ได้จริงหรือไม่ ครอบคลุมการเซ็น ฟาร์มอุปกรณ์ และการแจกจ่ายเบต้า หรือการปล่อยรุ่นเป็นการวิ่งวุ่นด้วยมือที่เครียด?** มือถือเพิ่มอันตรายที่เว็บไม่มี การตรวจของสโตร์อาจทำให้รุ่นล่าช้าหรือถูกปฏิเสธ กุญแจเซ็นและข้อมูลรับรองของสโตร์ต้องจัดการอย่างปลอดภัย และฮาร์ดแวร์กับเซนเซอร์ต่างกันมากพอที่อีมูเลเตอร์จะซ่อนปัญหาจริง การทำให้การบิลด์ ทดสอบ เซ็น และส่งขึ้นสโตร์เป็นอัตโนมัติผ่าน CI/CD พร้อมการแจกจ่ายเบต้าให้ผู้ทดสอบและฟาร์มอุปกรณ์บนคลาวด์ที่ครอบคลุมรุ่นที่ผู้ใช้ของคุณถืออยู่จริง คือสิ่งที่เปลี่ยนการปล่อยรุ่นจากวีรกรรมเป็นงานประจำ ตัดสินใจว่าใครเป็นเจ้าของสายงานและกุญแจเซ็น และจะใส่เวลาตรวจของสโตร์ไว้ในทุกแผนปล่อยรุ่นอย่างไร ลองเล่าเรื่องการปล่อยรุ่นล่าสุดแล้วนับขั้นตอนที่ทำด้วยมือ ทุกขั้นตอนคือจุดที่การปล่อยรุ่นที่เครียดอาจผิดพลาดเมื่อถูกเร่งกำหนดส่ง

4. **เราเลือกเนทีฟ ข้ามแพลตฟอร์ม หรือเว็บแอปแบบก้าวหน้าสำหรับอายุขัยทั้งหมดของผลิตภัณฑ์นี้ หรือเลือกเฉพาะวันเปิดตัว?** แนวทางการสร้างเป็นคันโยกที่ใหญ่ที่สุดต่อต้นทุนและความสามารถของแอปมือถือไปอีกหลายปี และการเลือกเพื่อส่งให้เร็วอาจดักคุณไว้ เนทีฟซื้อการเข้าถึงอุปกรณ์และความรู้สึกแบบแพลตฟอร์มที่สมบูรณ์ที่สุด ในราคาของสองโค้ดเบสและสองชุดทักษะ ขณะที่ข้ามแพลตฟอร์มและ PWA แชร์โค้ดได้แต่เพิ่มการพึ่งพาเฟรมเวิร์กหรือเสียการเข้าถึงฟีเจอร์อุปกรณ์บางอย่าง สำหรับทีมขนาดใหญ่ การตัดสินใจนี้กำหนดการจ้างงาน งบการดูแล และความเร็วที่จะนำ OS รุ่นประจำปีมาใช้ จึงควรมีเจ้าของที่ชัดเจน ไม่ใช่ค่าเริ่มต้นที่คนเขียนต้นแบบแรกกำหนดไว้ ลองนำฟีเจอร์อุปกรณ์ที่ต้องใช้ ลักษณะประสิทธิภาพ ระยะเวลาการดูแล และทักษะที่จ้างได้จริงมาพิจารณา และตรงไปตรงมาว่าฟีเจอร์แพลตฟอร์มใดที่คุณจะเสียไปภายใต้แต่ละตัวเลือก ในบริบทองค์กรและภาครัฐ ให้ชั่งว่าแอปนี้เป็นข้อผูกพันระยะยาวที่ต้องอยู่รอดผ่านการหมุนเวียนบุคลากรและการเปลี่ยนแปลงของแพลตฟอร์มทศวรรษหนึ่งหรือไม่ และบันทึกการตัดสินใจกับเหตุผล เพื่อไม่ให้ทีมในอนาคตต้องเดาว่าทำไมโค้ดเบสจึงเป็นแบบนี้

5. **ผู้ใช้จริงของเราต้องการช่วงอุปกรณ์และเวอร์ชัน OS ที่รองรับแค่ไหน และเราทดสอบบนฮาร์ดแวร์ที่พวกเขาถืออยู่จริง ไม่ใช่โทรศัพท์บนโต๊ะของเราหรือเปล่า?** ความหลากหลายของอุปกรณ์เป็นสภาพปกติของมือถือ ผู้ใช้กระจายตั้งแต่ขนาดหน้าจอ กำลังเครื่อง ไปจนถึงเวอร์ชัน OS และแอปที่ปรับจูนบนเครื่องเรือธงของทีมจะออกมาอืดหรือพังบนฮาร์ดแวร์ธรรมดาที่ผู้ฟังส่วนมากของคุณมี การกำหนดช่วงที่รองรับคือข้อแลกเปลี่ยนระหว่างการเข้าถึงกับแรงที่ต้องใช้ เพราะทุกรุ่นเก่าและเวอร์ชัน OS ที่คุณสัญญาว่ารองรับจะขยายเมทริกซ์การทดสอบและภาระการดูแล ช่วงนั้นจึงต้องมาจากข้อมูลการใช้งานจริง ไม่ใช่การสมมติ ลองนำการกระจายอุปกรณ์และเวอร์ชัน OS รุ่นที่ฟาร์มอุปกรณ์บนคลาวด์หรือห้องแล็บครอบคลุมอยู่ และประสิทธิภาพที่วัดได้บนฮาร์ดแวร์ระดับล่าง ไม่ใช่แค่ซิมูเลเตอร์ มาดูด้วยกัน สำหรับแอปของประชาชนในภาครัฐ เรื่องนี้แทบต่อรองไม่ได้ เพราะต้องให้บริการทุกคน รวมถึงผู้ที่ใช้อุปกรณ์เก่าและการเชื่อมต่อช้า ภายใต้ข้อผูกพันด้านการเข้าถึง และสำหรับกลุ่มอุปกรณ์ขององค์กร ควรทดสอบกับเครื่องแบบทนทานที่พนักงานถืออยู่จริง ไม่ใช่ตัวอย่างทั่วไป

6. **มีข้อมูลอ่อนไหวอะไรอยู่บนอุปกรณ์ และแต่ละชิ้นได้รับการปกป้องจากโทรศัพท์ที่หาย ถูกขโมย หรืออยู่ในมือคนอื่นหรือไม่?** อุปกรณ์มือถืออยู่ในกระเป๋าและหายหรือถูกขโมยได้ ข้อมูลหรือความลับใดที่เก็บในไฟล์ธรรมดาจึงห่างจากการรั่วไหลแค่โทรศัพท์เครื่องเดียวที่วางผิดที่ และรัศมีความเสียหายใหญ่ขึ้นตามจำนวนผู้ใช้ ข้อพิจารณาต่างๆ ดึงกันอยู่ การแคชข้อมูลบนอุปกรณ์คือสิ่งที่ทำให้ออฟไลน์ก่อนใช้ได้และทำให้แอปเร็ว แต่ข้อมูลที่แคชแต่ละชิ้นคือภาระที่ต้องอยู่ในที่เก็บที่ปลอดภัยของแพลตฟอร์ม (iOS Keychain หรือ Android Keystore) ต้องเก็บให้น้อยที่สุด และควรมีชีวมิติหรือรหัสผ่านเป็นด่าน ลองทำบัญชีรายการว่าแอปเก็บอะไรไว้ในเครื่องจริงๆ แต่ละชิ้นเก็บที่ใด อะไรปลดล็อกมัน และการเชื่อมต่อมูลค่าสูงใช้การตรึงใบรับรองพร้อมแผนหมุนเวียนที่ทำได้จริงหรือไม่ ในบริบทองค์กร ให้ผูกเรื่องนี้กับนโยบายการจัดการอุปกรณ์เคลื่อนที่และการลบข้อมูลระยะไกล และในภาครัฐ ให้ถือว่าข้อมูลส่วนบุคคลบนอุปกรณ์เป็นความเสี่ยงด้านความเป็นส่วนตัวและกฎหมายที่ต้องอธิบายได้ บันทึกไว้ และป้องกันตัวได้เมื่อถูกตรวจสอบ

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ด้วยทีมเล็กและเงินทุนที่เหลือน้อย แทบไม่มีปัญญาสร้างสองโค้ดเบสเนทีฟหรือจ้างสองชุดทักษะ เฟรมเวิร์กข้ามแพลตฟอร์มหรือแม้แต่ PWA ที่เข้าถึงทั้งสองสโตร์จากโค้ดเบสเดียวจึงมักชนะ ส่งมอบแบบออฟไลน์ก่อนสำหรับงานหลักเรื่องเดียวที่สำคัญ เก็บโทเค็นไว้ในที่เก็บที่ปลอดภัยแทนไฟล์ธรรมดา และใส่เวลาตรวจของสโตร์ไว้ในทุกรุ่น เพื่อไม่ให้การถูกปฏิเสธทำให้วันเปิดตัวพังทลาย ข้ามการบังคับอัปเดต การตรึงใบรับรอง และฟาร์มอุปกรณ์ไปก่อนจนกว่าการใช้งานจริงจะคุ้ม

**ธุรกิจขนาดเล็ก.** เมื่อไม่มีผู้เชี่ยวชาญมือถือโดยเฉพาะและงบจำกัด ให้เอียงไปทางซื้อมากกว่าสร้างอย่างมาก ไม่ว่าจะเป็นเครื่องมือสร้างแอปแบบไม่ต้องเขียนโค้ด แอปแบรนด์ขาวจากผู้ขายระบบขายหน้าร้านหรือระบบจองของคุณ หรือ PWA ที่ทำดีจากเว็บไซต์เดิม ซึ่งมักดีกว่าแอปสั่งทำที่คุณดูแลไม่ไหว หากจ้างทำแอป ให้ถือกุญแจเซ็นและบัญชีสโตร์ไว้เอง เพื่อไม่ให้ผู้รับจ้างยึดตัวตนของคุณเป็นตัวประกัน และยืนยันให้มีการเข้าถึงและการเก็บข้อมูลบนอุปกรณ์อย่างปลอดภัยในสัญญา จำกัดขอบเขตไว้ที่หนึ่งหรือสองงานที่ลูกค้าทำบนโทรศัพท์จริงๆ

**องค์กรขนาดใหญ่.** เมื่อขยายขนาด แอปเป็นข้อผูกพันระยะยาวข้ามหลายทีม จึงควรทำให้แนวทางการสร้าง รูปแบบที่เก็บที่ปลอดภัย สายงาน CI/CD และนโยบายการกำหนดเวอร์ชัน API เป็นมาตรฐาน แทนที่จะปล่อยให้แต่ละผลิตภัณฑ์คิดใหม่เอง แอปภายในสำหรับพนักงานมักผ่านการจัดการอุปกรณ์เคลื่อนที่สำหรับการติดตั้ง การตั้งค่า การลบข้อมูลระยะไกล และนโยบาย ขณะที่แอปลูกค้าต้องมีฟาร์มอุปกรณ์ที่ครอบคลุมการใช้งานจริง และการตรวจสอบด้านการเข้าถึงและความมั่นคงปลอดภัย กำกับดูแลกุญแจเซ็น ข้อมูลรับรองของสโตร์ และเวลาปล่อยรุ่นจากส่วนกลาง เพื่อไม่ให้การเปลี่ยนแปลงหลังบ้านที่ทำให้พังทิ้งไคลเอนต์รุ่นเก่าส่วนหางไว้กลางทาง

**ภาครัฐ.** กฎการจัดซื้อจัดจ้าง ความโปร่งใส และความรับผิดชอบต่อสาธารณะกำหนดทุกการเลือก คุณต้องให้บริการทุกคน รวมถึงผู้ที่ใช้อุปกรณ์เก่าและการเชื่อมต่อช้า การเข้าถึงจึงเป็นข้อบังคับทางกฎหมายที่ตรวจสอบด้วยเครื่องมือช่วยเหลือจริง และช่วงอุปกรณ์ที่รองรับกว้างแทบต่อรองไม่ได้ เลือกแนวทางและสัญญาที่หลีกเลี่ยงการผูกขาดกับผู้ขาย รักษาให้ข้อมูลย้ายได้ และให้สาธารณชนตรวจสอบได้ว่าแอปทำอะไรกับข้อมูลของพวกเขา และถือว่าข้อมูลส่วนบุคคลบนอุปกรณ์เป็นความเสี่ยงที่ต้องอธิบายและบันทึกเมื่อถูกตรวจสอบ

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปสามคนที่สร้างแอปติดตามนิสัยต้องเข้าถึงทั้ง iOS และ Android แต่ไม่มีปัญญาสร้างสองโค้ดเบสเนทีฟหรือจ้างสองชุดทักษะ พวกเขาเลือกเฟรมเวิร์กข้ามแพลตฟอร์มเพื่อให้ทีมเล็กทีมเดียวส่งขึ้นได้ทั้งสองสโตร์ และออกแบบแบบออฟไลน์ก่อนตั้งแต่ต้น เพื่อให้ผู้ใช้บันทึกนิสัยบนรถไฟใต้ดินที่ไม่มีสัญญาณแล้วซิงก์ทีหลังได้ พวกเขาเก็บโทเค็นล็อกอินไว้ในที่เก็บที่ปลอดภัยของแพลตฟอร์มแทนไฟล์ธรรมดา ใส่เวลาตรวจของสโตร์ไว้ในแผนปล่อยรุ่นทุกครั้ง และทดสอบบนโทรศัพท์รุ่นเก่าราคาถูกสองสามเครื่องควบคู่กับเครื่องของตัวเอง ซึ่งจับความอืดที่มิฉะนั้นอาจหลุดไปถึงผู้ใช้ได้

**องค์กรขนาดใหญ่.** บริษัทโลจิสติกส์แห่งหนึ่งสร้างแอปภายในสำหรับคนขับและพนักงานคลังสินค้า เพราะคลังสินค้าและเส้นทางส่งของมีสัญญาณไม่นิ่ง ทีมจึงเลือกการออกแบบแบบออฟไลน์ก่อน การสแกนและการอัปเดตสถานะบันทึกในเครื่องและซิงก์เมื่อการเชื่อมต่อกลับมา พวกเขาใช้เฟรมเวิร์กข้ามแพลตฟอร์มเพื่อให้ทีมเล็กดูแลโค้ดเบสเดียวสำหรับทั้งสองแพลตฟอร์ม แอปแจกจ่ายผ่านการจัดการอุปกรณ์เคลื่อนที่แทนสโตร์สาธารณะ เพื่อให้ฝ่ายไอทีควบคุมการติดตั้ง การตั้งค่า และนโยบายความมั่นคงปลอดภัยบนอุปกรณ์ของบริษัท ข้อมูลรับรองที่อ่อนไหวอยู่ในที่เก็บที่ปลอดภัยของแพลตฟอร์ม และชีวมิติปลดล็อกแอป ฟาร์มอุปกรณ์บนคลาวด์ทดสอบเครื่องแบบทนทานที่พนักงานถืออยู่จริงในหลายรุ่น

**ภาครัฐ.** หน่วยงานระดับชาติส่งมอบแอปสำหรับประชาชนด้านการยืนยันตัวตนและสวัสดิการ การเข้าถึงเป็นข้อกำหนดเด็ดขาดตั้งแต่วันแรก ได้แก่การรองรับตัวอ่านหน้าจอเต็มรูปแบบ การปรับขนาดข้อความแบบไดนามิก และความเปรียบต่างสูง ทดสอบด้วยเครื่องมือช่วยเหลือจริงเพื่อให้เป็นไปตามกฎหมาย เพราะประชาชนใช้อุปกรณ์หลากหลายมาก ทีมจึงรองรับรุ่นเก่าและการเชื่อมต่อช้าในช่วงกว้าง และทำให้งานหลักใช้ได้แบบออฟไลน์ ข้อมูลอ่อนไหวอยู่ในที่เก็บที่ปลอดภัยของอุปกรณ์ ชีวมิติปกป้องการเข้าถึง และการเชื่อมต่อมูลค่าสูงใช้การตรึงใบรับรองพร้อมกระบวนการหมุนเวียนที่วางแผนไว้ การกำหนดเวอร์ชัน API ทำให้แอปรุ่นเก่าที่ติดตั้งแล้วยังใช้งานได้ และมีช่องทางบังคับอัปเดตที่ใช้น้อยสำหรับการแก้ไขด้านความปลอดภัย เวลาตรวจของสโตร์ถูกใส่ไว้ในทุกแผนปล่อยรุ่น

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

มือถือคือที่ที่ผู้ใช้จำนวนมากพบกับบริการของคุณ แอปจึงส่งผลต่อการนำไปใช้ ความพึงพอใจ และการทำงานสำคัญให้สำเร็จขององค์กร แอปที่เร็ว เชื่อถือได้ และออกแบบดีเพิ่มการใช้งานและลดภาระซัพพอร์ต สำหรับองค์กร แอปมือถือภายในช่วยให้กำลังคนที่เคลื่อนที่ทำงานได้มากขึ้นอย่างวัดผลได้และลดงานเอกสาร สำหรับรัฐบาล แอปประชาชนที่ใช้ง่ายขยายการเข้าถึงและลดความต้องการด้านคอลเซ็นเตอร์และการมาติดต่อด้วยตนเอง

ด้านต้นทุนรวมตลอดอายุการใช้งาน (TCO) การเลือกแนวทางคือคันโยกที่ใหญ่ที่สุด เนทีฟหมายถึงการจ่ายสำหรับสองโค้ดเบสและสองชุดทักษะตลอดอายุของแอป ข้ามแพลตฟอร์มแลกบางส่วนของนั้นกับการพึ่งพาที่คุณต้องรักษาให้ทันสมัย นอกจากโค้ด ให้ตั้งงบสำหรับค่าธรรมเนียมสโตร์และรอบการตรวจ ห้องแล็บทดสอบอุปกรณ์หรือฟาร์มบนคลาวด์ การรองรับเวอร์ชัน OS ต่อเนื่องเมื่อแพลตฟอร์มปล่อยรุ่นทุกปี และงานด้านความมั่นคงปลอดภัยที่มือถือเรียกร้อง ต้นทุนของการลงทุนไม่พอปรากฏเป็นแอปแครชบนอุปกรณ์ที่ไม่ได้รองรับ เหตุการณ์ด้านความปลอดภัยจากข้อมูลบนอุปกรณ์ที่ไม่ได้รับการปกป้อง รุ่นที่ถูกปฏิเสธหรือล่าช้า และผู้ใช้ที่ทิ้งแอปที่ช้าหรืออึดอัด

เมื่อต้องเสนอผู้บริหาร ให้เชื่อมแอปเข้ากับผลลัพธ์ที่จับต้องได้ เช่น การทำงานสำเร็จ การรักษาผู้ใช้ ผลิตภาพของกำลังคน หรือต้นทุนซัพพอร์ตที่ลดลง ประเมินราคาการตัดสินใจเรื่องแนวทางตลอดอายุของแอป ไม่ใช่แค่รุ่นแรก และระบุความเสี่ยง (ความมั่นคงปลอดภัย กฎหมายการเข้าถึง การถูกสโตร์ปฏิเสธ) ที่แนวปฏิบัติมือถืออย่างจริงจังช่วยลดได้

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **มองมือถือเป็นเว็บไซต์ที่ย่อส่วน**: เพิกเฉยต่อการสัมผัส ท่าทาง และธรรมเนียมของแพลตฟอร์ม
- **สมมติว่าเครือข่ายสมบูรณ์แบบ**: ไม่มีการจัดการออฟไลน์ ทำให้แอปพังทันทีที่สัญญาณหาย
- **ทดสอบเฉพาะบนเรือธงรุ่นล่าสุด**: ซ่อนประสิทธิภาพแย่บนอุปกรณ์ที่ผู้ใช้จริงถืออยู่
- **เก็บความลับในไฟล์ธรรมดา**: ข้อมูลอ่อนไหวถูกเปิดเผยเมื่ออุปกรณ์หายหรือถูกขโมย
- **การแจ้งเตือนล้นเกิน**: พุชมากเกินไป ผู้ใช้จึงปิดเสียงหรือลบแอป
- **เมินเวลาตรวจของสโตร์**: แผนปล่อยรุ่นที่สมมติว่าเผยแพร่ได้ทันทีแล้วเลื่อนออกไป
- **ไม่มีช่องทางบังคับอัปเดต**: เวอร์ชันเก่าที่ไม่ปลอดภัยยังอยู่ต่อโดยไม่มีวิธีเลิกใช้
- **กินแบตเตอรี่และข้อมูล**: งานเบื้องหลังตลอดเวลาและการใช้เครือข่ายถี่เกินจนผู้ใช้สังเกตเห็น
- **การเข้าถึงเป็นเรื่องที่คิดทีหลัง**: กันผู้ใช้ออกไป และสำหรับภาครัฐคือฝ่าฝืนกฎหมาย
- **โค้ดเบสเดียวที่บังคับให้หน้าตาเหมือนกันทุกที่**: แอปที่รู้สึกแปลกบนทั้งสองแพลตฟอร์ม

## แบบจำลองความเป็นผู้ใหญ่

**ระดับ 1 เริ่มต้น.** มือถือเป็นแบบเฉพาะกิจและตั้งรับ แอปถูกสร้างเหมือนเว็บไซต์ ทดสอบบนโทรศัพท์ของทีมเอง และมักพังเมื่อออฟไลน์ แทบไม่มีการคิดเรื่องที่เก็บที่ปลอดภัย การเข้าถึง หรือตารางเวลาตรวจของสโตร์ การปล่อยรุ่นเป็นการวิ่งวุ่นด้วยมือที่เครียด และไม่มีใครเป็นเจ้าของแนวทางการสร้างหรือกุญแจเซ็น

**ระดับ 2 พัฒนา.** เริ่มมีแนวปฏิบัติพื้นฐาน แต่ไม่สม่ำเสมอข้ามทีมและผลิตภัณฑ์ เลือกแนวทางการสร้างสำหรับแอปหนึ่งๆ ทำตามพื้นฐานของแพลตฟอร์ม ทดสอบบนอุปกรณ์จริงไม่กี่เครื่อง และมีการจัดการออฟไลน์กับที่เก็บที่ปลอดภัยบ้าง การบิลด์เป็นอัตโนมัติบางส่วนและมีผู้ดูแลการส่งขึ้นสโตร์ แต่แอปของอีกทีมอาจยังทำสิ่งเหล่านี้ต่างออกไปหรือไม่ทำเลย

**ระดับ 3 สร้างมาตรฐาน.** แนวปฏิบัติที่ดีถูกบันทึกและบังคับใช้ทั้งองค์กร ออฟไลน์ก่อนเป็นค่าเริ่มต้น ช่วงอุปกรณ์ที่รองรับที่บันทึกไว้ถูกทดสอบบนห้องแล็บอุปกรณ์หรือฟาร์มบนคลาวด์ ทำตามแนวทางการออกแบบของแพลตฟอร์มและการเข้าถึงและตรวจสอบด้วยเครื่องมือช่วยเหลือจริง ที่เก็บที่ปลอดภัย ชีวมิติ และการกำหนดเวอร์ชัน API เป็นมาตรฐาน CI/CD ทำให้การบิลด์ ทดสอบ เซ็น และแจกจ่ายเบต้าเป็นอัตโนมัติ และวางแผนเวลาตรวจของสโตร์ไว้ในทุกรุ่น

**ระดับ 4 บริหารจัดการ.** คุณภาพมือถือถูกวัดและควบคุมเทียบกับเส้นฐาน การแครช ประสิทธิภาพการเริ่มแบบเย็นและการเรนเดอร์หน้าจอ การใช้แบตเตอรี่และข้อมูล และอัตราการทำงานให้สำเร็จ ถูกเก็บจากอุปกรณ์จริงอย่างต่อเนื่องและติดตามเทียบเป้าหมาย พร้อมการแยกตามรุ่นและเวอร์ชัน OS เพื่อให้การถดถอยบนฮาร์ดแวร์ระดับล่างถูกจับได้ ไม่ใช่ส่งออกไป การเข้าถึงและความมั่นคงปลอดภัยถูกตรวจสอบแทนที่จะสมมติ ติดตามอัตราการปิดรับการแจ้งเตือนและอัตราการยอมรับการอัปเดต และทบทวนช่วงที่รองรับกับแนวทางการสร้างบนหลักฐานนี้ การตัดสินใจว่าจะหยุดหรือแก้ไขรุ่นอิงตัวชี้วัด ไม่ใช่ความรู้สึกของแอปบนโทรศัพท์ของหัวหน้า

**ระดับ 5 ประสานทั้งระบบ.** มือถือได้รับการปรับปรุงอย่างต่อเนื่องและผนวกรวมทั่วองค์กร และปรับตัวเมื่อภูมิทัศน์ของอุปกรณ์เปลี่ยนไป การหมุนเวียนใบรับรอง ช่องทางบังคับอัปเดต และการย้อนรุ่นเป็นงานประจำ ช่วงที่รองรับและแนวทางการสร้างถูกปรับขอบเขตตามหลักฐานเมื่อแพลตฟอร์มปล่อยรุ่นทุกปี และผู้ใช้กับอุปกรณ์ทุกกลุ่มถูกถือเป็นเรื่องสำคัญอันดับแรก การวางแผนมือถือเชื่อมกับแนวปฏิบัติด้านความมั่นคงปลอดภัย การเข้าถึง API และการส่งมอบ ดังนั้นการเปลี่ยน OS ระดับอุปกรณ์ใหม่ หรือการเปลี่ยนนโยบาย จึงถูกรับเป็นงานประจำแทนเหตุฉุกเฉิน

## ประเด็นชวนคุย

- จะตัดสินอย่างไรระหว่างเนทีฟ ข้ามแพลตฟอร์ม และเว็บแอปแบบก้าวหน้าสำหรับผลิตภัณฑ์หนึ่งๆ
- ช่วงอุปกรณ์และเวอร์ชัน OS ที่รองรับแบบไหนเหมาะกับข้อมูลผู้ใช้จริงของคุณ และจะรักษาให้ทันสมัยได้อย่างไร
- แอปของคุณจำเป็นต้องออฟไลน์ก่อนที่ใดบ้าง และจะจัดการความขัดแย้งของการซิงก์อย่างไร
- เมื่อไรการบังคับอัปเดตจึงสมเหตุสมผล และจะหลีกเลี่ยงการขวางผู้ใช้อย่างไม่เป็นธรรมได้อย่างไร
- จะทดสอบบนอุปกรณ์จริงในขนาดที่สะท้อนผู้ใช้ของคุณได้อย่างไร
- มีข้อมูลอ่อนไหวอะไรอยู่บนอุปกรณ์ และแต่ละชิ้นได้รับการปกป้องอย่างไร
- จะเคารพธรรมเนียมของแต่ละแพลตฟอร์มจากโค้ดเบสร่วมได้อย่างไร

## ข้อสรุปสำคัญ

- เลือกแนวทางการสร้าง (เนทีฟ ข้ามแพลตฟอร์ม หรือ PWA) ให้เหมาะกับอายุขัยทั้งหมดของแอป
- ทำตามแนวทางการออกแบบของแพลตฟอร์มเพื่อให้แอปรู้สึกคุ้นเคยและลดแรงของผู้ใช้
- ออกแบบให้รับข้อจำกัดของมือถือ: ออฟไลน์ก่อน ประหยัดแบตเตอรี่และข้อมูล ความหลากหลายของอุปกรณ์ หน้าจอเล็ก
- คุณไม่ได้ควบคุมเวลาปล่อยรุ่น วางแผนสำหรับการตรวจของสโตร์ การกำหนดเวอร์ชัน และการบังคับอัปเดต
- ใช้การแจ้งเตือนแบบพุชและดีปลิงก์อย่างยั้งมือและด้วยความยินยอม
- ปกป้องข้อมูลบนอุปกรณ์ด้วยที่เก็บที่ปลอดภัย ชีวมิติ และการตรึงใบรับรองเมื่อสมควร
- ทดสอบบนอุปกรณ์จริงและทำให้สายงานมือถือเป็นอัตโนมัติผ่าน CI/CD
- ทำให้การเข้าถึงเป็นข้อกำหนด ซึ่งสำหรับภาครัฐเป็นข้อบังคับทางกฎหมาย
