# 2.5 การทบทวนโค้ด และ การทำงานร่วมกัน

## ภาพรวมและแรงจูงใจ

[การทบทวนโค้ด](https://en.wikipedia.org/wiki/Code_review) (code review) คือการให้คนอื่นที่ไม่ใช่ผู้เขียนตรวจการเปลี่ยนแปลงก่อนที่จะรวมเข้าสู่โค้ดหลัก เป็นกิจกรรมที่ให้ผลคุ้มค่าที่สุดอย่างหนึ่งทั้งด้านคุณภาพและการแบ่งปันความรู้ในองค์กรซอฟต์แวร์ และสำหรับทีมขนาดใหญ่ ยังเป็นกลไกหลักของการประสานงานและวัฒนธรรมด้วย การทบทวนช่วยจับข้อบกพร่อง กระจายความรู้เรื่องโค้ดเบส บังคับใช้มาตรฐาน และเป็นพื้นที่ให้วิศวกรสอนงานกัน แต่จะได้ผลก็ต่อเมื่อทำได้ดี ถ้าทำไม่ดี การทบทวนจะกลายเป็นคอขวด เป็นแหล่งของความขัดแย้ง หรือเป็นแค่การประทับตราให้ผ่านที่ให้ความมั่นใจลวง ๆ

สำหรับทีมขนาดใหญ่ การทบทวนคือจุดที่งานของแต่ละคนมาพบกับความเป็นเจ้าของร่วมกัน มักเป็นจุดสัมผัสหลักระหว่างวิศวกรที่ปกติทำงานแยกกัน บรรทัดฐานของการทบทวนจึงกำหนดว่าทั้งองค์กรจะทำงานร่วมกันอย่างไร การทบทวนช่วยกระจายความรู้ไม่ให้ส่วนใดของระบบมีคนเข้าใจอยู่คนเดียว ซึ่งลดความเสี่ยงเรื่อง [บัสแฟกเตอร์](https://en.wikipedia.org/wiki/Bus_factor) (bus factor) คืออันตรายที่เกิดเมื่อความรู้กระจุกอยู่กับคนจำนวนน้อยเกินไป ปัญหานี้เกิดบ่อยในระบบขนาดใหญ่ที่อยู่มานาน และการทบทวนยังสร้างร่องรอยการตรวจสอบว่าใครเปลี่ยนอะไรและใครอนุมัติ

ในบริบทองค์กรขนาดใหญ่และภาครัฐ การทบทวนมักมีมิติด้านการปฏิบัติตามข้อกำหนดด้วย [การแบ่งแยกหน้าที่](https://en.wikipedia.org/wiki/Separation_of_duties) (segregation of duties คือไม่มีใครคนเดียวควบคุมการเปลี่ยนแปลงที่ละเอียดอ่อนได้ทั้งหมด) การอนุมัติที่บังคับ และการสืบย้อนได้ มักเป็นมาตรการควบคุมที่กำหนดไว้ การเปลี่ยนแปลงที่แตะระบบอ่อนไหวอาจต้องให้บทบาทเฉพาะเป็นผู้ทบทวน และบันทึกการทบทวนจะกลายเป็นหลักฐานสำหรับการตรวจสอบ ความท้าทายของคุณคือทำให้เป็นไปตามมาตรการเหล่านี้ได้ โดยที่การทบทวนยังเร็วและสร้างสรรค์ ไม่กลายเป็นพิธีกรรม

## หลักการสำคัญ

- ทบทวนเพื่อทำให้การเปลี่ยนแปลงดีขึ้นและแบ่งปันความรู้ ไม่ใช่เพื่ออวดความเก่ง
- การเปลี่ยนแปลงขนาดเล็กได้รับการทบทวนที่ดีกว่า ดังนั้นให้ pull request (PR) มีจุดมุ่งหมายเดียวและมีขนาดพอเหมาะ
- ความล่าช้าในการทบทวนเป็นต้นทุนของทั้งทีม การตอบกลับที่รวดเร็วช่วยให้ทุกคนเดินหน้าได้
- ทำงานเชิงกลไก (สไตล์ การทดสอบ การสแกนความปลอดภัย) ให้เป็นอัตโนมัติ เพื่อให้คนทบทวนเรื่องการออกแบบและความถูกต้อง
- แยกปัญหาที่ขวางการรวมโค้ดออกจากข้อเสนอแนะและความชอบส่วนตัว และบอกให้ชัดว่าอันไหนเป็นอันไหน
- วิจารณ์โค้ด ไม่ใช่ตัวบุคคล บรรทัดฐานการให้ข้อเสนอแนะเป็นตัวกำหนดว่าการทบทวนจะสร้างความไว้วางใจหรือกัดกร่อนมัน
- ผู้เขียนมีหน้าที่ทำให้การเปลี่ยนแปลงของตนทบทวนได้ง่าย

## ข้อแนะนำ

### ทำ pull request ให้เล็กและอธิบายให้ดี

ให้แต่ละการเปลี่ยนแปลงมุ่งที่เรื่องเชิงตรรกะเรื่องเดียว และเล็กพอที่จะทบทวนได้อย่างละเอียด PR ขนาดใหญ่มักถูกทบทวนอย่างผิวเผิน เขียนคำอธิบายให้ชัดว่าเปลี่ยนอะไร ทำไม และตรวจสอบอย่างไร เพื่อให้ผู้ทบทวนมีบริบท แยกการปรับโครงสร้างโค้ดเชิงกลไกออกจากการเปลี่ยนพฤติกรรมเป็นคนละ PR เพื่อให้แต่ละอันคิดตามได้ง่าย คำอธิบายที่ดีคือสิ่งที่ผู้เขียนมีส่วนช่วยคุณภาพของการทบทวนได้มากที่สุดเพียงอย่างเดียว

### กำหนดมาตรฐานและเช็กลิสต์การทบทวน

ระบุให้ชัดว่าผู้ทบทวนควรมองหาอะไร ได้แก่ ความถูกต้อง ความเข้ากันได้กับการออกแบบ ความเพียงพอของการทดสอบ ผลกระทบด้านความปลอดภัย ความอ่านง่าย และการยึดตามมาตรฐาน เช็กลิสต์แบบเบา ๆ ช่วยให้การทบทวนสม่ำเสมอและไม่ปล่อยมิติสำคัญหลุดไป โดยไม่ทำให้การทบทวนกลายเป็นการไล่ติ๊กช่อง กำหนดด้วยว่าอะไรต้องผ่านการทบทวน ใครอนุมัติได้ และพื้นที่อ่อนไหวต้องได้รับอนุมัติจากบทบาทใดบ้าง

### กำหนดและติดตามบรรทัดฐานเรื่องความล่าช้าของการทบทวน

ตกลงเป้าหมายเวลาตอบกลับ เช่น ตอบภายในหนึ่งวันทำการ และทำให้การทบทวนเป็นส่วนสำคัญของวัน ไม่ใช่สิ่งที่ยัดไว้ท้ายสุด คิวทบทวนที่ยาวทำให้การส่งมอบชะงักและล่อให้วิศวกรรวบการเปลี่ยนแปลงเป็นก้อนใหญ่ ติดตามเวลาถึงการทบทวนครั้งแรก (time-to-first-review) และเวลาถึงการรวมโค้ด (time-to-merge) และมองความล่าช้าที่เกิดต่อเนื่องเป็นปัญหาของกระบวนการที่ต้องแก้ ไม่ใช่ความผิดของคนใดคนหนึ่ง

### ทำทุกอย่างที่เป็นเชิงกลไกให้อัตโนมัติ

รันการจัดรูปแบบโค้ด [การลินต์](https://en.wikipedia.org/wiki/Lint_(software)) (linting) การทดสอบ และการสแกนความปลอดภัยและไลบรารีที่พึ่งพา ใน[การบูรณาการแบบต่อเนื่อง](https://en.wikipedia.org/wiki/Continuous_integration) (CI) เพื่อไม่ให้ผู้ทบทวนต้องเสียความสนใจกับเรื่องเหล่านี้ เก็บการทบทวนโดยมนุษย์ไว้สำหรับสิ่งที่เครื่องตัดสินไม่ได้ เช่น การออกแบบถูกต้องหรือไม่ แนวทางเข้ากับระบบหรือไม่ การทดสอบมีความหมายจริงหรือไม่ และโค้ดนี้จะยังอ่านเข้าใจได้ในอนาคตหรือไม่

### ใช้การเขียนโปรแกรมเป็นคู่และเป็นกลุ่มเมื่อเหมาะสม

ใช้[การเขียนโปรแกรมเป็นคู่](https://en.wikipedia.org/wiki/Pair_programming) (pair programming คือวิศวกรสองคนเขียนโค้ดด้วยกันที่เครื่องเดียว) สำหรับงานซับซ้อนหรือเสี่ยงสูง การปฐมนิเทศ และการถ่ายทอดความรู้ มันคือการทบทวนต่อเนื่อง และมักทำให้ไม่ต้องมีขั้นตอนทบทวนแยกต่างหาก ใช้[การเขียนโปรแกรมแบบกลุ่ม](https://en.wikipedia.org/wiki/Mob_programming) (mob programming คือทั้งทีมทำงานชิ้นเดียวพร้อมกัน) สำหรับการตัดสินใจออกแบบที่สำคัญ หรือเพื่อกระจายความรู้เรื่องส่วนที่ยุ่งยากให้ทั้งทีม ให้มองสองแบบนี้เป็นตัวเสริมของการทบทวนแบบไม่พร้อมกัน เลือกตามบริบท ไม่ใช่สิ่งที่จะบังคับให้ใช้ทุกที่

### นำการทบทวนอัตโนมัติและการทบทวนด้วย AI มาใช้อย่างระมัดระวัง

ใช้เครื่องมือทบทวนอัตโนมัติและผู้ช่วย AI เพื่อจับปัญหาทั่วไป เสนอการปรับปรุง และลดภาระของผู้ทบทวน แต่ให้ถือผลลัพธ์ของมันเป็นข้อมูลประกอบ ไม่ใช่ผู้มีอำนาจตัดสิน AI ทำได้ดีกับปัญหาผิวหน้าและความสอดคล้อง แต่ไม่เก่งเรื่องการตัดสินการออกแบบเชิงลึกและบริบทของระบบ ให้มีมนุษย์รับผิดชอบทุกการอนุมัติ โดยเฉพาะการเปลี่ยนแปลงที่อ่อนไหวด้านความปลอดภัยและเกี่ยวข้องกับการปฏิบัติตามข้อกำหนด

### กำหนดบรรทัดฐานการให้ข้อเสนอแนะอย่างสร้างสรรค์

กำหนดบรรทัดฐานให้ข้อเสนอแนะเฉพาะเจาะจง ใจดี และมุ่งที่โค้ด สนับสนุนให้ผู้ทบทวนถามคำถามแทนการออกคำสั่ง อธิบายเหตุผลเบื้องหลังสิ่งที่ขอ และชมงานที่ดี ทำเครื่องหมายให้ชัดว่าข้อไหนขวางการรวมโค้ดและข้อไหนเป็นข้อเสนอแนะที่เลือกได้ (เช่น ใส่คำนำหน้าให้บันทึกที่ไม่ขวาง) บรรทัดฐานเหล่านี้ตัดสินว่าการทบทวนจะทำให้ทีมแข็งแรงขึ้นหรือสร้างความขุ่นเคือง

## ข้อดีข้อเสียและการแลกเปลี่ยน

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| การทบทวน PR แบบไม่พร้อมกัน | ยืดหยุ่น มีบันทึก ขยายข้ามเขตเวลาได้ | ล่าช้า สูญเสียความละเอียดอ่อน อาจรู้สึกเป็นปฏิปักษ์ |
| การเขียนโปรแกรมเป็นคู่ | ทบทวนต่อเนื่อง ถ่ายทอดความรู้เร็ว คุณภาพสูง | สองคนต่องานหนึ่งชิ้น เหนื่อย จัดตารางยากกว่า |
| การเขียนโปรแกรมแบบกลุ่ม | ทั้งทีมเข้าใจตรงกัน กระจายความรู้เชิงลึก | รวมแล้วแพง ไม่เหมาะกับงานประจำ |
| บังคับให้มีผู้ทบทวนหลายคน | ความมั่นใจสูง เป็นมิตรกับการปฏิบัติตามข้อกำหนด | ช้ากว่า ความรับผิดชอบกระจาย เกิดแรงกดดันที่คิว |
| การทบทวนด้วย AI | เร็ว ไม่เหนื่อยกับปัญหาทั่วไป ลดภาระ | พลาดบริบทของระบบ ทำให้มั่นใจเกินจริงถ้าเชื่อมากเกินไป |

ความตึงเครียดหลักคือความละเอียดรอบคอบเทียบกับความเร็ว การทบทวนที่ลึกกว่าจับได้มากกว่า แต่ทำให้การส่งมอบช้าลงและอาจทำให้ผู้เขียนหงุดหงิด การทบทวนที่เร็วกว่ารักษาจังหวะการทำงานไว้ได้ แต่เสี่ยงที่จะผิวเผิน ทางออกคือให้ความลึกของการทบทวนสอดคล้องกับความเสี่ยงของการเปลี่ยนแปลง การเปลี่ยนแปลงเล็กน้อยทบทวนแบบเบา การเปลี่ยนแปลงเสี่ยงสูงทบทวนอย่างลึก และทำงานเชิงกลไกให้อัตโนมัติ เพื่อให้แรงของคนไปรวมอยู่ในจุดที่สำคัญ

## คำถามที่ควรคุยกับทีม

1. **ขนาดเท่าไรถือว่าใหญ่เกินไปสำหรับหนึ่ง pull request และคุณแยกการปรับโครงสร้างโค้ดเชิงกลไกออกจากการเปลี่ยนพฤติกรรมหรือไม่?** บทนี้บอกตรง ๆ ว่า PR ขนาดใหญ่ถูกทบทวนอย่างผิวเผิน และผู้เขียนเป็นเจ้าของความสามารถในการทบทวนได้ และขอให้แยกการปรับโครงสร้างโค้ดออกจากการเปลี่ยนพฤติกรรม เพื่อให้แต่ละอันคิดตามได้ง่าย ในทีมขนาดใหญ่ PR ยักษ์แทบรับประกันได้ว่าจะถูกประทับตราผ่าน ซึ่งให้ความมั่นใจลวง ๆ ขณะที่ข้อบกพร่องจริงหลุดเข้าไป ให้นำหลักฐานมาคุย เช่น การกระจายขนาด PR ของคุณ และความลึกของการทบทวนที่ลดลงเมื่อ diff ใหญ่ขึ้น ตกลงบรรทัดฐานเรื่องขนาดที่ใช้ได้จริง และนิสัยที่จะส่งการปรับโครงสร้างล้วน ๆ แยกจากการเปลี่ยนตรรกะ เพื่อให้ผู้ทบทวนถือแต่ละการเปลี่ยนแปลงไว้ในหัวได้จริง วินัยข้อเดียวนี้ยกระดับคุณภาพของทุกการทบทวนที่ตามมา

2. **คุณแยกข้อคัดค้านที่ขวางการรวมโค้ดออกจากข้อเสนอแนะที่เลือกได้อย่างไร และมีการใช้แนวปฏิบัตินั้นจริงหรือไม่?** บทนี้ขอให้แยกปัญหาที่ขวางออกจากความชอบส่วนตัว และบอกให้ชัดว่าอะไรเป็นอะไร และชี้ว่าการขวางเพราะความชอบเป็นรูปแบบที่ไม่ควรทำซึ่งกัดกร่อนทีม ถ้าไม่มีข้อตกลงร่วมกัน ความเห็นเรื่องสไตล์ของผู้ทบทวนจะถูกอ่านเป็นการแก้ไขที่จำเป็นต้องทำ ซึ่งสร้างความขุ่นเคืองและทำให้การส่งมอบช้าลงทั้งทีม ให้นำตัวอย่างจากการทบทวนล่าสุดที่ความชอบส่วนตัวทำให้การรวมโค้ดสะดุดมาเป็นสัญญาณที่จับต้องได้ นำเครื่องหมายแบบเบา ๆ มาใช้ เช่น คำนำหน้าที่ระบุว่าบันทึกนั้นไม่ขวาง เพื่อให้ผู้เขียนรู้ทันทีว่าอะไรต้องแก้และอะไรเป็นแค่ข้อเสนอแนะ วิธีนี้ช่วยให้การทบทวนมุ่งที่ความถูกต้องและการออกแบบ ไม่ใช่รสนิยม

3. **ใครต้องอนุมัติการเปลี่ยนแปลงโค้ดที่อ่อนไหวด้านความปลอดภัยหรือเกี่ยวข้องกับการปฏิบัติตามข้อกำหนด และการส่งต่อนั้นบังคับใช้อย่างไร?** บทนี้อธิบายการอนุมัติตามบทบาท กฎความเป็นเจ้าของโค้ด และการแบ่งแยกหน้าที่ที่ไม่มีใครคนเดียวควบคุมการเปลี่ยนแปลงที่อ่อนไหวได้ทั้งหมด โดยบันทึกการอนุมัติไว้เป็นหลักฐานการตรวจสอบ ในองค์กรขนาดใหญ่และภาครัฐ สิ่งเหล่านี้เป็นมาตรการควบคุมที่จำเป็น ความเสี่ยงคือมันถูกข้ามไป หรือกลายเป็นคอขวดที่ทำให้การส่งมอบหยุดชะงัก ให้นำสัญญาณมาดู เช่น โมดูลไหนอ่อนไหว และกฎความเป็นเจ้าของปัจจุบันส่งการเปลี่ยนแปลงเหล่านั้นไปหาผู้อนุมัติที่ถูกต้องโดยอัตโนมัติหรือไม่ เขียนการส่งต่อนี้ไว้ในการตั้งค่าความเป็นเจ้าของโค้ด และจับคู่กับการตรวจอัตโนมัติและการเปลี่ยนแปลงขนาดเล็ก เพื่อให้เป็นไปตามมาตรการโดยไม่ต้องมีคิวที่มีคนคอยเฝ้า ตัดสินใจเรื่องนี้อย่างตั้งใจ แทนที่จะมาพบช่องโหว่ในตอนตรวจสอบ

4. **เป้าหมายความล่าช้าของการทบทวนที่คุณตกลงกันจริง ๆ คืออะไร คุณวัดและบังคับใช้หรือไม่ หรือเป็นแค่ความปรารถนา?** บทนี้มองความล่าช้าของการทบทวนเป็นต้นทุนของทั้งทีม และขอให้ติดตามเวลาถึงการทบทวนครั้งแรกและเวลาถึงการรวมโค้ด โดยมองความล่าช้าที่ต่อเนื่องเป็นปัญหาของกระบวนการ ไม่ใช่ความผิดของบุคคล ในทีมขนาดใหญ่ คิวทบทวนที่ไม่มีเจ้าของเก็บภาษีทุกคนอย่างเงียบ ๆ ผู้เขียนรวบการเปลี่ยนแปลงให้ใหญ่ขึ้นเพื่อเลี่ยงการรอ การเปลี่ยนแปลงเหล่านั้นก็ถูกทบทวนผิวเผินกว่าเดิม และระยะเวลานำของการส่งมอบก็ค่อย ๆ ยาวขึ้นโดยไม่มีใครเป็นต้นเหตุคนเดียว ข้อพิจารณาที่ขัดกันคือเป้าหมายความล่าช้าที่เข้มงวดอาจผลักให้ผู้ทบทวนอ่านผ่าน ๆ จึงต้องถ่วงดุลระหว่างความเร็วกับความลึก ไม่ใช่แลกกันแบบมองไม่เห็น ให้นำหลักฐานมาดู ได้แก่การกระจายของเวลาถึงการทบทวนครั้งแรกในปัจจุบัน ความแตกต่างตามทีมและขนาดการเปลี่ยนแปลง และจุดที่การทบทวนค้างนานที่สุด ในองค์กรขนาดใหญ่และภาครัฐ ให้ผูกเป้าหมายกับตัวชี้วัดการไหลของงานที่ผู้บริหารติดตามอยู่แล้ว เพราะมาตรการที่บังคับให้มีผู้ทบทวนหลายคนโดยไม่มีบรรทัดฐานเรื่องความล่าช้าจะกลายเป็นคอขวดที่ทำให้การส่งมอบหยุดนิ่ง และล่อให้คนหาทางเลี่ยงมาตรการนั้นไปเลย

5. **การเปลี่ยนแปลงประเภทใดที่คุณไว้ใจให้ใช้การทบทวนอัตโนมัติและการทบทวนด้วย AI และจุดไหนที่ต้องมีมนุษย์รับผิดชอบ?** บทนี้บอกให้ถือผลทบทวนจาก AI เป็นข้อมูลประกอบ ไม่ใช่ผู้มีอำนาจตัดสิน เก่งเรื่องปัญหาผิวหน้าและความสอดคล้อง อ่อนเรื่องการตัดสินการออกแบบเชิงลึกและบริบทของระบบ โดยมีมนุษย์รับผิดชอบทุกการอนุมัติ ถ้าไม่มีเส้นแบ่งที่ชัดเจน ทีมขนาดใหญ่จะค่อย ๆ เชื่อมากเกินไป จนความเห็นสีเขียวของบอทถูกอ่านว่าผ่านการทบทวนแล้ว และความเสี่ยงด้านการออกแบบและความปลอดภัยที่แท้จริงหลุดผ่านไปภายใต้ความมั่นใจลวง ๆ แรงดึงอีกด้านคือการทบทวนด้วย AI ช่วยลดภาระและจับข้อบกพร่องทั่วไปได้ไม่รู้เหนื่อยจริง การห้ามใช้จึงเสียประโยชน์ไปเปล่า ๆ ให้นำหลักฐานมาดู ว่าข้อเสนอแนะอัตโนมัติจับปัญหาจริงได้ที่ไหน สร้างสัญญาณรบกวนที่ไหน และการเปลี่ยนแปลงประเภทใด (อ่อนไหวด้านความปลอดภัย เกี่ยวข้องกับการปฏิบัติตามข้อกำหนด เชิงสถาปัตยกรรม) ที่คุณจะไม่มีวันให้เครื่องเซ็นอนุมัติคนเดียว สำหรับงานองค์กรขนาดใหญ่และภาครัฐ ให้ระบุว่าใครรับผิดชอบการอนุมัติเมื่อมีผู้ช่วย AI เข้ามาเกี่ยวข้อง เพราะผู้ตรวจสอบจะถามว่าใครทบทวนการเปลี่ยนแปลงนั้น และ "เครื่องมือทำ" ไม่ใช่คำตอบที่หน่วยกำกับดูแลยอมรับ

6. **ควรใช้การเขียนโปรแกรมเป็นคู่หรือเป็นกลุ่มแทนการทบทวนแบบไม่พร้อมกันที่ไหน และคุณใช้การทบทวนเพื่อลดความเสี่ยงบัสแฟกเตอร์อย่างตั้งใจได้อย่างไร?** บทนี้วางการเขียนโปรแกรมเป็นคู่และเป็นกลุ่มไว้เป็นการทบทวนต่อเนื่องที่เลือกตามบริบท และระบุว่าการทบทวนเป็นกลไกที่กระจายความรู้ไม่ให้ส่วนใดของระบบมีคนเข้าใจอยู่คนเดียว ถ้าปล่อยไว้โดยไม่ตั้งใจ ความรู้จะกระจุกตัว ผู้เชี่ยวชาญคนเดิมทบทวนทุกการเปลี่ยนแปลงของระบบย่อยหนึ่ง การทบทวนกลายเป็นการประทับตราเพราะไม่มีใครอื่นท้าทายได้ และความเสี่ยงบัสแฟกเตอร์สูงขึ้นตรงจุดที่ระบบสำคัญที่สุด ข้อพิจารณาที่ขัดกันคือต้นทุน เพราะการเขียนโปรแกรมแบบกลุ่มใช้เวลาของทั้งทีม และการเขียนเป็นคู่ผูกวิศวกรสองคน จึงบังคับใช้ทุกที่ไม่ได้ ให้นำหลักฐานมาดู ว่าโมดูลไหนมีผู้ทบทวนที่เชื่อถือได้เพียงคนเดียว การปฐมนิเทศติดขัดที่ไหน และพื้นที่ยุ่งยากส่วนใดจะได้ประโยชน์จากการนั่งทำด้วยกันสดแทนการเถียงกันในกระทู้ความเห็น ในองค์กรขนาดใหญ่หรือองค์กรสาธารณะ ให้มองการกระจายความรู้อย่างตั้งใจเป็นการบริหารความเสี่ยง เพราะระบบที่อยู่มานานและมีส่วนสำคัญพึ่งพาคนคนเดียวเป็นภาระด้านการดำเนินงานและความต่อเนื่อง ไม่ใช่แค่ความไม่สะดวกเรื่องกำลังคน

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** เมื่อมีวิศวกรสามสี่คน ให้การทบทวนเป็นแบบเบา ๆ คือให้เพื่อนร่วมทีมหนึ่งคนอนุมัติ pull request ขนาดเล็ก ให้ CI ตรวจเรื่องเชิงกลไก และไม่บังคับให้มีผู้ทบทวนคนที่สองที่จะทำให้การรวมโค้ดติดขัด เป้าหมายจริงมีเรื่องการปฏิบัติตามข้อกำหนดน้อยกว่าการทำให้มีคนเข้าใจแต่ละส่วนของระบบมากกว่าหนึ่งคน ดังนั้นให้จับคู่เขียนส่วนที่เสี่ยงและถือว่านั่นคือการปฐมนิเทศ อย่าสร้างระบบส่งต่อตามความเป็นเจ้าของโค้ดที่หนักเกินไปจนเดี๋ยวก็โตเกิน บรรทัดฐานร่วมเรื่องการเปลี่ยนแปลงเล็กที่อธิบายดีให้ประโยชน์ส่วนใหญ่ด้วยต้นทุนเกือบเป็นศูนย์

**ธุรกิจขนาดเล็ก.** คุณไม่น่าจะมีผู้เชี่ยวชาญด้านเครื่องมือทบทวน ดังนั้นให้พึ่งสิ่งที่แพลตฟอร์มโฮสติ้งของคุณ (เช่น บริการ Git ที่มีผู้ดูแลให้) มีมาให้ แทนที่จะสร้างระบบอัตโนมัติเอง ซื้อการเชื่อมต่อด้านลินต์ การทดสอบ และการสแกนความปลอดภัยแทนการดูแลเอง เพื่อให้วิศวกรจำนวนน้อยใช้เวลาทบทวนอันมีค่ากับการออกแบบและความถูกต้อง มีกฎง่าย ๆ ข้อเดียว คือทุกการเปลี่ยนแปลงต้องมีคนอื่นดูอีกหนึ่งคู่ และอย่าเพิ่มกระบวนการที่ไม่มีใครดูแล

**องค์กรขนาดใหญ่.** ความท้าทายคือความสม่ำเสมอข้ามหลายทีม ได้แก่ มาตรฐานร่วม กฎความเป็นเจ้าของโค้ดที่ส่งการเปลี่ยนแปลงอ่อนไหวไปหาผู้อนุมัติที่ถูกต้อง และการอนุมัติตามบทบาทที่บันทึกเป็นหลักฐานการตรวจสอบ ทำการตรวจเชิงกลไกให้เป็นอัตโนมัติทั้งองค์กร เพื่อให้การทบทวนโดยมนุษย์มุ่งที่การออกแบบ และติดตามความล่าช้าของการทบทวนเป็นตัวชี้วัดการไหลของงาน เพื่อไม่ให้มาตรการบังคับผู้ทบทวนหลายคนกลายเป็นคอขวดโดยไม่รู้ตัว ให้ความลึกของการทบทวนสอดคล้องกับความเสี่ยงของการเปลี่ยนแปลงด้วยนโยบายที่จดไว้ เพื่อให้การเปลี่ยนแปลงเล็กน้อยยังเร็ว ส่วนการเปลี่ยนแปลงเสี่ยงสูงได้รับการแบ่งแยกหน้าที่และการตรวจที่ลึกกว่า

**ภาครัฐ.** การควบคุมการเปลี่ยนแปลงมักเป็นข้อบังคับ ทุกการเปลี่ยนแปลงในระบบจริงต้องได้รับการทบทวนและอนุมัติโดยคนอื่นที่ไม่ใช่ผู้เขียน และเก็บบันทึกไว้เป็นหลักฐานการตรวจสอบเพื่อให้เป็นไปตามข้อกำหนดการแบ่งแยกหน้าที่ เน้นร่องรอยที่โปร่งใสและสืบย้อนได้ว่าใครเขียน ใครอนุมัติ และการตรวจใดผ่านบ้าง และลงทุนกับระบบอัตโนมัติและการเปลี่ยนแปลงเล็กที่ทำถี่ เพื่อไม่ให้มาตรการนี้ทำให้การส่งมอบหยุดนิ่ง เมื่อจัดซื้อเครื่องมือทบทวน ให้เรียกร้องบันทึกการตรวจสอบที่ส่งออกได้และหลีกเลี่ยงการผูกติดกับผู้ขาย เพราะหลักฐานต้องอยู่ได้นานกว่าผู้ขายรายใดรายหนึ่งและยืนหยัดต่อการตรวจสอบของสาธารณะได้

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปที่มีวิศวกรสี่คนทำให้ทุก pull request เล็กและขอให้เพื่อนร่วมทีมหนึ่งคนอนุมัติก่อนรวมโค้ด ไม่ใช่เพื่อการปฏิบัติตามข้อกำหนดนัก แต่เพื่อให้แน่ใจว่าไม่มีใครคนเดียวที่เป็นผู้เดียวที่เข้าใจส่วนหนึ่งของระบบ CI รันตัวจัดรูปแบบและการทดสอบ ดังนั้นเวลาทบทวนอันน้อยนิดของคนจึงไปอยู่กับการออกแบบและความถูกต้อง ไม่ใช่เรื่องการเว้นวรรค เมื่อทีมเจอส่วนที่ยุ่งยากของขั้นตอนการชำระเงิน สองคนในทีมจับคู่เขียนส่วนนั้นแทนการโต้ตอบด้วยความเห็นแบบไม่พร้อมกัน ซึ่งทำหน้าที่เป็นการปฐมนิเทศให้พนักงานใหม่ล่าสุดไปในตัว

**องค์กรขนาดใหญ่.** บริษัทซอฟต์แวร์ขนาดใหญ่กำหนดให้ทุกการเปลี่ยนแปลงต้องมีการทบทวนที่อนุมัติอย่างน้อยหนึ่งครั้ง และต้องมีการอนุมัติครั้งที่สองสำหรับการเปลี่ยนแปลงโมดูลที่อ่อนไหวด้านความปลอดภัย ซึ่งระบุด้วยกฎความเป็นเจ้าของโค้ด CI จัดการการตรวจสไตล์และการทดสอบทั้งหมด ผู้ทบทวนจึงมุ่งที่การออกแบบและความถูกต้อง ทีมติดตามเวลาถึงการทบทวนครั้งแรก และมองค่ามัธยฐานที่สูงขึ้นเป็นสัญญาณให้ปรับสมดุลภาระงาน วิศวกรใหม่ได้รับการปฐมนิเทศผ่านการเขียนเป็นคู่ ซึ่งทำให้ถึงจุดที่ลงมือทำงานได้เองเร็วขึ้น

**ภาครัฐ.** หน่วยงานระดับชาติที่อยู่ภายใต้ข้อกำหนดการควบคุมการเปลี่ยนแปลงที่เข้มงวด กำหนดให้ทุกการเปลี่ยนแปลงในระบบจริงต้องได้รับการทบทวนและอนุมัติโดยคนอื่นที่ไม่ใช่ผู้เขียน พร้อมบันทึกการอนุมัติไว้สำหรับการตรวจสอบ เพื่อไม่ให้มาตรการนี้กลายเป็นคอขวด หน่วยงานลงทุนกับการตรวจอัตโนมัติและการเปลี่ยนแปลงเล็กที่ทำถี่ และกำหนดบรรทัดฐานให้ตอบกลับการทบทวนภายในวันเดียวกัน ร่องรอยการทบทวนที่ครอบคลุมว่าใครเขียน ใครอนุมัติ และการตรวจใดผ่านบ้าง กลายเป็นส่วนหนึ่งของหลักฐานการปฏิบัติตามข้อกำหนดสำหรับแต่ละรุ่นที่ปล่อย ตอบข้อกำหนดการแบ่งแยกหน้าที่ได้โดยไม่ทำให้การส่งมอบหยุดนิ่ง

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

การทบทวนโค้ดให้ผลตอบแทนคืนมาสามสกุล ได้แก่ ข้อบกพร่องที่จับได้ก่อนขึ้นระบบจริง ความรู้ที่กระจายทั่วทีม และมาตรฐานที่ได้รับการรักษาโดยอัตโนมัติเมื่อเวลาผ่านไป การจับข้อบกพร่องตอนทบทวนถูกกว่าการจับตอนอยู่ในระบบจริงมาก และประโยชน์ด้านการแบ่งปันความรู้ช่วยลดความเสี่ยงเรื่องคนสำคัญ ซึ่งอาจทำให้องค์กรเสียหายหนักเมื่อมีคนลาออก การทบทวนยังเป็นกลไกส่งต่อวัฒนธรรมที่ทำให้ทีมที่กำลังโตยังเป็นหนึ่งเดียว

ต้นทุนของการทบทวนคือเวลาของวิศวกรและความล่าช้าบางส่วน ซึ่งจัดการได้ด้วยแนวปฏิบัติที่ดี ส่วนต้นทุนของการ*ไม่*ทบทวน หรือทบทวนไม่ดี ได้แก่ ข้อบกพร่องในระบบจริง ความรู้ที่ติดอยู่เป็นไซโล โค้ดที่ไม่สม่ำเสมอ และในบริบทที่มีการกำกับดูแล คือการตรวจสอบที่ไม่ผ่านและข้อค้นพบด้านการปฏิบัติตามข้อกำหนด การทบทวนที่หนักเกินไปก็มีต้นทุนจริงเช่นกัน คือคิวที่ยาว การรวบงานเป็นก้อนใหญ่ และวิศวกรที่หมดกำลังใจ เมื่อต้องการโน้มน้าวผู้บริหาร ให้เชื่อมแนวปฏิบัติการทบทวนเข้ากับอัตราความล้มเหลวของการเปลี่ยนแปลง ระยะเวลานำของการส่งมอบ และความเร็วในการปฐมนิเทศ และติดตามความล่าช้าของการทบทวนเป็นตัวชี้วัดการไหลของงานอย่างชัดเจน

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **การประทับตราให้ผ่าน:** การอนุมัติโดยไม่ได้ตรวจจริง ให้ความมั่นใจลวง ๆ และทำตามมาตรการแค่ตามตัวอักษร
- **PR ยักษ์:** หลายพันบรรทัดที่อ่านได้แค่ผ่าน ๆ รับประกันว่าการทบทวนจะผิวเผิน
- **การทบทวนที่จับผิดแต่เรื่องจุกจิก:** เน้นเรื่องปลีกย่อยจนพลาดการออกแบบและความถูกต้อง มักเกิดเพราะการตรวจเชิงกลไกไม่ได้ทำให้เป็นอัตโนมัติ
- **การทบทวนเป็นการกีดกัน:** ใช้การทบทวนเพื่อแสดงอำนาจเหนือหรือขวางคนอื่น ทำลายการทำงานร่วมกัน
- **คิวที่ช้า:** การทบทวนที่ค้างเป็นวัน ทำให้การส่งมอบชะงักและกระตุ้นให้รวบงานเป็นก้อน
- **เชื่อการทบทวนด้วย AI มากเกินไป:** ถือข้อเสนอแนะอัตโนมัติเป็นเรื่องตัดสินขาด และเลิกใช้วิจารณญาณของมนุษย์กับการเปลี่ยนแปลงที่เสี่ยง
- **ขวางเพราะความชอบส่วนตัว:** เสนอความเห็นเรื่องสไตล์ส่วนตัวเป็นสิ่งที่ต้องแก้ โดยไม่แยกจากข้อบกพร่องจริง

## แบบจำลองความเป็นผู้ใหญ่

- **ระดับ 1 เริ่มต้น:** การทบทวนเป็นแบบเฉพาะกิจและตั้งรับ มักถูกข้ามหรือทำไม่สม่ำเสมอ ความเห็นส่วนใหญ่เป็นเรื่องเชิงกลไก ยังไม่มีบรรทัดฐานการให้ข้อเสนอแนะ และร่องรอยการอนุมัติ (ถ้ามี) เกิดขึ้นโดยบังเอิญ ไม่ได้ตั้งใจ
- **ระดับ 2 พัฒนา:** มีแนวปฏิบัติการทบทวนพื้นฐาน แต่ต่างกันไปในแต่ละทีม บางที่บังคับให้ทบทวน บางที่ช้าหรือเป็นทางเลือก ระบบอัตโนมัติมีบางส่วน และขนาดกับคุณภาพของ pull request แกว่งมากโดยไม่มีความคาดหวังร่วมกัน
- **ระดับ 3 สร้างมาตรฐาน:** มาตรฐานถูกจดไว้และบังคับใช้ทั้งองค์กร PR เล็กที่มีจุดมุ่งหมายเดียว การจัดรูปแบบ ลินต์ การทดสอบ และการสแกนความปลอดภัยแบบอัตโนมัติใน CI เช็กลิสต์ที่ชัดเจน ข้อตกลงที่ชัดเจนเรื่องข้อที่ขวางกับข้อเสนอแนะ และกฎความเป็นเจ้าของโค้ดที่ส่งการเปลี่ยนแปลงอ่อนไหวไปหาผู้อนุมัติที่ถูกต้อง
- **ระดับ 4 บริหารจัดการ:** การทบทวนถูกวัดและควบคุมเทียบกับเกณฑ์อ้างอิง ติดตามเวลาถึงการทบทวนครั้งแรก เวลาถึงการรวมโค้ด ความลึกของการทบทวนเทียบกับความเสี่ยงของการเปลี่ยนแปลง อัตราข้อบกพร่องที่หลุดรอด และอัตราความล้มเหลวของการเปลี่ยนแปลง ความล่าช้าที่ต่อเนื่องถูกมองเป็นปัญหาของกระบวนการ และข้อมูลชี้ว่าควรปรับสมดุลภาระผู้ทบทวนตรงไหน และมาตรการใดทำให้การส่งมอบช้าลงโดยไม่เพิ่มความมั่นใจ
- **ระดับ 5 ประสานทั้งระบบ:** การทบทวนได้รับการปรับปรุงอย่างต่อเนื่องและบูรณาการทั่วองค์กร ความลึกปรับตามความเสี่ยงของการเปลี่ยนแปลง การเขียนเป็นคู่ เป็นกลุ่ม และการช่วยเหลือด้วย AI ถูกใช้อย่างตั้งใจโดยมีมนุษย์รับผิดชอบ การกระจายความรู้และความเสี่ยงบัสแฟกเตอร์ถูกบริหารอย่างจงใจ และการทบทวนช่วยยกระดับคุณภาพ การไหลของการส่งมอบ และการปฐมนิเทศได้อย่างวัดผลได้

- การเขียนเป็นคู่หรือเป็นกลุ่มดีกว่าการทบทวนแบบไม่พร้อมกันที่ตรงไหนในบริบทของคุณ?
- ควรไว้ใจการทบทวนด้วย AI แค่ไหน และกับการเปลี่ยนแปลงประเภทใด?
- คุณรักษาให้ข้อเสนอแนะในการทบทวนยังสร้างสรรค์ได้อย่างไรเมื่อทีมโตขึ้นและหลากหลายขึ้น?
- คุณทำตามข้อกำหนดการอนุมัติด้านการปฏิบัติตามข้อกำหนดโดยไม่สร้างคอขวดได้อย่างไร?

## ข้อสรุปสำคัญ

- ทำ pull request ให้เล็กและอธิบายให้ดี ผู้เขียนเป็นเจ้าของความสามารถในการทบทวนได้
- ทำงานเชิงกลไกให้เป็นอัตโนมัติ เพื่อให้คนทบทวนการออกแบบ ความถูกต้อง และการทดสอบ
- ติดตามและจัดการความล่าช้าของการทบทวนเป็นต้นทุนการไหลของงานของทั้งทีม
- ให้ความลึกของการทบทวนสอดคล้องกับความเสี่ยงของการเปลี่ยนแปลง และแยกปัญหาที่ขวางออกจากความชอบส่วนตัว
- ใช้การเขียนเป็นคู่ เป็นกลุ่ม และการช่วยเหลือด้วย AI เป็นตัวเสริมที่เหมาะกับบริบท โดยให้มนุษย์ยังรับผิดชอบ
