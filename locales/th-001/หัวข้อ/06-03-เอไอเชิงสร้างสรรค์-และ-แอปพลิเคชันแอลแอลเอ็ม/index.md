# 6.3 เอไอเชิงสร้างสรรค์และแอปพลิเคชันแอลแอลเอ็ม

## ภาพรวมและแรงจูงใจ

[เอไอเชิงสร้างสรรค์](https://en.wikipedia.org/wiki/Generative_artificial_intelligence) (generative AI) โดยเฉพาะ[โมเดลภาษาขนาดใหญ่](https://en.wikipedia.org/wiki/Large_language_model) (LLM) สามารถสร้างข้อความที่ลื่นไหล โค้ด บทสรุป และข้อมูลที่มีโครงสร้างจากคำสั่งภาษาธรรมชาติ ทำให้เป็นส่วนประกอบทรงพลังสำหรับผู้ช่วย การค้นหา การประมวลผลเอกสาร และระบบอัตโนมัติ แต่จุดแข็งเหล่านี้มาพร้อมโปรไฟล์ความเสี่ยงที่โดดเด่น LLM เป็นระบบเชิงความน่าจะเป็น มันสร้างข้อความเท็จด้วยความมั่นใจได้ ([ภาพหลอน](https://en.wikipedia.org/wiki/Hallucination_(artificial_intelligence)) หรือ hallucination) มันอ่อนไหวต่อวิธีที่คุณเขียนพรอมต์ และมันเปิดพื้นผิวการโจมตีใหม่ เช่น [การฉีดพรอมต์](https://en.wikipedia.org/wiki/Prompt_injection) (prompt injection คือการลักลอบใส่คำสั่งประสงค์ร้ายในอินพุตเพื่อยึดพฤติกรรมของโมเดล) ดังนั้นการสร้างแอปพลิเคชัน LLM ที่พึ่งพาได้จึงเกี่ยวกับตัวโมเดลน้อยกว่าวิศวกรรมที่อยู่รอบตัวมัน: วิธีส่งบริบท การอ้างอิงคำตอบกับความรู้ที่เชื่อถือได้ การจำกัดเอาต์พุต และการประเมินคุณภาพ

สำหรับทีมขนาดใหญ่ แอปพลิเคชัน LLM ต้องใช้รูปแบบใหม่ที่ต่างจากทั้งซอฟต์แวร์แบบดั้งเดิมและการเรียนรู้ของเครื่องแบบคลาสสิก มักไม่มีขั้นตอนการฝึก แต่พฤติกรรมถูกกำหนดด้วยพรอมต์ บริบทที่ค้นคืนมา นิยามเครื่องมือ และแนวกั้น (guardrails คือการตรวจสอบขณะทำงานที่จำกัดอินพุตและเอาต์พุตของโมเดล) ซึ่งย้ายแรงวิศวกรรมไปที่การจัดการบริบท คุณภาพการค้นคืน การประสานงาน และการประเมิน องค์กรที่นำ LLM มาใช้ในวงกว้างต้องมีรูปแบบร่วม เพื่อไม่ให้ทุกทีมต้องค้นพบความล้มเหลวแบบเดิมด้วยวิธีเจ็บปวด

องค์กรภาครัฐและที่มีกฎระเบียบเผชิญข้อเรียกร้องเพิ่ม LLM ที่แต่งการอ้างอิงนโยบายขึ้นเองหรือรั่วข้อมูลอ่อนไหวไม่ใช่แค่บั๊ก แต่อาจเป็นเหตุการณ์ทางกฎหมายหรือความปลอดภัย บริบทเหล่านี้ต้องมีการอ้างอิงกับแหล่งที่เชื่อถือได้ การตรวจสอบเอาต์พุตอย่างเข้มงวด การกำกับโดยมนุษย์สำหรับเอาต์พุตที่มีผลตามมา และบันทึกที่ชัดเจนว่าระบบถูกถามอะไรและให้อะไร เทคนิคในบทนี้ (การสร้างเสริมด้วยการค้นคืน แนวกั้น และการประเมินที่เข้มงวด) คือสิ่งที่ทำให้ LLM ปลอดภัยพอจะนำไปใช้ในบริบทที่เดิมพันสูง โมเดล Claude ของ Anthropic เป็นตัวเลือกชั้นนำหนึ่งในหลายผู้ให้บริการที่มีความสามารถ แนวปฏิบัติในที่นี้ใช้ได้ไม่ว่าคุณจะเลือกโมเดลใด

## หลักการสำคัญ

- ให้โมเดลอ้างอิงกับความรู้ที่เชื่อถือได้ แทนการพึ่งสิ่งที่มันจำไว้เอง
- มองพรอมต์และบริบทเป็นชิ้นงาน (artefact) ที่ผ่านการออกแบบและกำหนดเวอร์ชัน ไม่ใช่สตริงที่ใช้แล้วทิ้ง
- สมมุติว่าโมเดลอาจผิดหรือถูกชักจูงได้ ตรวจสอบเอาต์พุตและจำกัดการกระทำ
- ให้บริบทและเครื่องมือแก่โมเดลเท่าที่จำเป็นเท่านั้น เพื่อลดข้อผิดพลาดและพื้นผิวการโจมตี
- ประเมินอย่างต่อเนื่องด้วยชุดทดสอบออฟไลน์ ตัวชี้วัดออนไลน์ และวิจารณญาณของมนุษย์
- คงมนุษย์ไว้ในวงจรสำหรับเอาต์พุตที่มีผลตามมา
- ออกแบบโดยมองโมเดลเป็นส่วนประกอบที่ไม่น่าไว้วางใจภายในระบบที่น่าไว้วางใจ

## ข้อแนะนำ

### ออกแบบพรอมต์และจัดการบริบทอย่างตั้งใจ

มองพรอมต์เป็นโค้ด: เก็บใน version control ทบทวนการเปลี่ยนแปลง และทดสอบกับชุดตัวอย่าง จัดโครงสร้างพรอมต์ให้ชัด: บทบาทและงาน ข้อจำกัด ข้อกำหนดด้านรูปแบบ และตัวอย่างเมื่อมีประโยชน์ มองหน้าต่างบริบท (context window คือช่วงข้อความคงที่ที่โมเดลพิจารณาได้ในครั้งเดียว) เป็นทรัพยากรที่หายาก ใส่ข้อมูลที่เกี่ยวข้องที่สุด เรียงลำดับอย่างรอบคอบ และตัดสิ่งรบกวนออก เพราะบริบทที่ไม่เกี่ยวข้องหรือมากเกินไปทำให้คุณภาพตกและต้นทุนสูงขึ้น สำหรับแอปพลิเคชันหลายรอบสนทนา ให้จัดการสถานะการสนทนาอย่างชัดแจ้ง โดยสรุปหรือตัดประวัติเพื่อให้อยู่ในขีดจำกัดแต่เก็บสิ่งสำคัญไว้ เลือกคำสั่งที่ชัดเจนและตัวอย่างแบบ few-shot (การสาธิตที่ทำให้ดูไม่กี่ตัวอย่างในพรอมต์) แทนลูกเล่นซับซ้อนที่พังทันทีที่เปลี่ยนโมเดล

### อ้างอิงคำตอบด้วยการสร้างเสริมด้วยการค้นคืน (RAG)

สำหรับงานที่ใช้ความรู้มาก ให้ค้นคืนเอกสารที่เกี่ยวข้องจากคลังที่เชื่อถือได้และส่งให้โมเดลเป็นบริบท พร้อมสั่งให้ตอบจากเนื้อหานั้นเท่านั้นและอ้างอิงแหล่งที่มา RAG ทำให้ความรู้ทันสมัยโดยไม่ต้องฝึกใหม่ จำกัดคำตอบอยู่ในเนื้อหาที่ได้รับอนุมัติ และเปิดทางให้อ้างอิงและตรวจสอบได้ ลงทุนกับคุณภาพการค้นคืน: แบ่งเอกสารเป็นชิ้น (chunk) อย่างสมเหตุสมผล เลือก[เอ็มเบดดิง](https://en.wikipedia.org/wiki/Word_embedding) (embedding คือการแทนความหมายด้วยเวกเตอร์ตัวเลขที่วางความหมายคล้ายกันไว้ใกล้กัน) ที่เหมาะกับโดเมนของคุณ และตรวจว่าข้อความที่ค้นคืนมามีคำตอบอยู่จริงหรือไม่ เพราะคำตอบลื่นไหลที่สร้างบนข้อความผิดแย่กว่าไม่มีคำตอบ และเมื่อไม่พบสิ่งที่เกี่ยวข้อง ให้ระบบบอกตรง ๆ แทนที่จะแต่งเนื้อหา

### สร้างเอเจนต์และการใช้เครื่องมืออย่างยับยั้งชั่งใจ

LLM เรียกใช้เครื่องมือได้ (การค้นหา ฐานข้อมูล เครื่องคิดเลข API ภายใน) และประกอบเป็นเอเจนต์ที่วางแผนและลงมือหลายขั้นตอนได้ ซึ่งเพิ่มขีดความสามารถจริง แต่คูณความเสี่ยงด้วย: ทุกเครื่องมือคือช่องทางอีกทางหนึ่งที่โมเดลที่ผิดหรือถูกชักจูงจะสร้างความเสียหาย กำหนดเครื่องมือด้วยสคีมาที่แม่นยำ ตรวจสอบทุกอาร์กิวเมนต์ ใช้หลักสิทธิ์น้อยที่สุดเท่าที่จำเป็น และกำหนดให้ต้องยืนยันหรือได้รับอนุมัติจากมนุษย์สำหรับการกระทำที่มีผลตามมา เช่น การส่งข้อความหรือการโอนเงิน ทำให้วงวนของเอเจนต์มีขอบเขต สังเกตได้ และขัดจังหวะได้ เริ่มจากเครื่องมือจุดประสงค์เดียวที่ขอบเขตชัดก่อนจะไปถึงความอิสระแบบปลายเปิด

### เพิ่มแนวกั้นและตรวจสอบเอาต์พุต

ห่อโมเดลด้วยชั้นป้องกันหลายชั้น ขาเข้า: กรองและตรวจจับการฉีดพรอมต์ โดยเฉพาะเมื่อเนื้อหาที่ไม่น่าไว้วางใจ (หน้าเว็บ เอกสารของผู้ใช้) เข้าสู่บริบท ขาออก: ตรวจโครงสร้างเทียบกับสคีมา ตรวจข้อกล่าวอ้างเทียบกับแหล่งที่มา กรองเนื้อหาที่ไม่ปลอดภัยหรือไม่เป็นไปตามข้อกำหนด และปฏิเสธหรือลองใหม่เมื่อการตรวจสอบล้มเหลว สำหรับเอาต์พุตแบบมีโครงสร้าง ให้แยกวิเคราะห์และตรวจสอบ แทนที่จะเชื่อรูปแบบที่โมเดลให้มา อย่าปล่อยให้เอาต์พุตดิบของโมเดลกระตุ้นการกระทำที่ย้อนกลับไม่ได้โดยไม่ผ่านการตรวจสอบ มองการลดภาพหลอนเป็นคุณสมบัติของระบบที่ได้มาจากการอ้างอิงแหล่ง การอ้างอิงกำกับ การตรวจสอบ และการทบทวนโดยมนุษย์ ไม่ใช่สิ่งที่โมเดลจัดการได้เอง

### ประเมินแบบออฟไลน์ ออนไลน์ และด้วยมนุษย์

สร้างชุดประเมินที่ประกอบด้วยอินพุตตัวแทนพร้อมเอาต์พุตที่ทราบว่าถูกหรือให้คะแนนตามเกณฑ์ และรันทุกครั้งที่พรอมต์หรือโมเดลเปลี่ยน (การประเมินออฟไลน์) วัดพฤติกรรมจริงในระบบจริงด้วยตัวชี้วัด เช่น ความสำเร็จของงาน อัตราการส่งต่อ และข้อเสนอแนะจากผู้ใช้ (การประเมินออนไลน์) สำหรับคุณภาพเชิงอัตวิสัย ให้ใช้ผู้ทบทวนที่เป็นมนุษย์ และใช้การให้คะแนนด้วยโมเดลอย่างระมัดระวัง การประเมินคือตาข่ายนิรภัยที่ให้คุณเปลี่ยนพรอมต์และโมเดลได้อย่างมั่นใจ หากไม่มี คุณกำลังบินสุ่มสี่สุ่มห้า

## ข้อดีข้อเสียและการแลกเปลี่ยน

| ทางเลือก | ข้อดี | ข้อเสีย | เหมาะที่สุดเมื่อ |
|---|---|---|---|
| เขียนพรอมต์ล้วน | เรียบง่าย เร็ว เปลี่ยนถูก | การอ้างอิงจำกัด อาจเกิดภาพหลอน | งานกว้าง ๆ เดิมพันต่ำ |
| RAG | ทันสมัย อ้างอิงกับข้อมูลจริง อ้างอิงกำกับได้ | การค้นคืนทำให้ถูกต้องได้ยาก | งานที่ใช้ความรู้และข้อเท็จจริงมาก |
| เอเจนต์ที่ใช้เครื่องมือ | ทรงพลัง ลงมือทำได้ | พื้นผิวการโจมตีใหญ่ขึ้น ควบคุมยากขึ้น | ระบบอัตโนมัติที่ขอบเขตชัดพร้อมแนวกั้น |
| โมเดลที่ใหญ่และแกร่งกว่า | คุณภาพและการให้เหตุผลดีกว่า | ต้นทุนและความหน่วงสูงกว่า | งานซับซ้อนหรือเดิมพันสูง |
| โมเดลที่เล็กและถูกกว่า | เร็วและราคาถูก | อ่อนกว่าในงานยาก | ปริมาณมาก งานง่าย |

ความตึงเครียดหลักคือขีดความสามารถเทียบกับการควบคุมและต้นทุน ความอิสระที่มากขึ้นและโมเดลที่ใหญ่ขึ้นให้คุณค่ามากกว่า แต่ต้องการแนวกั้น การประเมิน และเงินมากกว่า การอ้างอิงผ่าน RAG ปรับปรุงความน่าเชื่อถือโดยแลกกับงานวิศวกรรมการค้นคืน ความสมดุลที่เหมาะขึ้นกับเดิมพัน: แอปพลิเคชันเดิมพันสูงเอนไปทางการอ้างอิง การตรวจสอบ และการกำกับโดยมนุษย์ แม้ต้องจ่ายมากกว่า

## คำถามที่ควรคุยกับทีม

1. **ฟีเจอร์ LLM ต้องผ่านเกณฑ์ความแม่นยำและการอ้างอิงระดับใดก่อนเจอสาธารณชน และใครเป็นผู้อนุมัติ?** คำตอบลื่นไหลที่อ้างแหล่งผิดหรือแต่งนโยบายขึ้นแย่กว่าไม่มีคำตอบ และในภาครัฐ การอ้างอิงที่แต่งขึ้นคือเหตุการณ์ทางกฎหมาย ไม่ใช่บั๊ก สำหรับทีมขนาดใหญ่ เกณฑ์ที่ชัดเจนช่วยไม่ให้แต่ละกลุ่มตั้งเกณฑ์ส่วนตัวตามความรู้สึก นำนิยามของคำว่า "อ้างอิงพอ" ของคุณมา: ข้อกล่าวอ้างทุกข้อต้องสืบย้อนไปยังแหล่งที่ค้นคืนและตรวจสอบแล้วหรือไม่ ระบบต้องปฏิเสธเมื่อการค้นคืนว่างเปล่าหรือไม่ และชุดประเมินเชิงเป็นปรปักษ์ของคุณครอบคลุมอะไรจริง ๆ สัญญาณที่ต้องดูคือตอนนี้มีใครส่งการแก้พรอมต์ถึงผู้ใช้โดยตรงโดยไม่รันการทดสอบการถดถอยได้หรือไม่ หากเดิมพันเป็นเรื่องกฎหมายหรือความปลอดภัย คำตอบควรส่งเอาต์พุตความเสี่ยงสูงสุดผ่านผู้ทบทวนที่มนุษย์ซึ่งมีอำนาจจริงก่อนปล่อย

2. **ฟีเจอร์ LLM ของเราตัวไหนที่จริง ๆ แล้วเป็นเอเจนต์แอบแฝง และเครื่องมือแต่ละตัวได้รับสิทธิ์น้อยที่สุดและมีด่านมนุษย์สำหรับการกระทำที่ย้อนกลับไม่ได้แล้วหรือยัง?** ฟีเจอร์ใดที่ให้โมเดลเรียกเครื่องมือหรือลงมือหลายขั้นตอนได้ ถือว่าข้ามเข้าเขตเอเจนต์แล้ว และทุกเครื่องมือคือช่องทางอีกทางที่โมเดลที่ผิดหรือถูกชักจูงจะสร้างความเสียหาย สำหรับองค์กรที่เชื่อม LLM เข้ากับ API ภายใน คำถามนี้เผยความเสี่ยงที่ป้ายว่า "ผู้ช่วยธรรมดา" ซ่อนไว้ นำรายการเครื่องมือทุกตัวที่โมเดลเรียกได้ การตรวจสอบอาร์กิวเมนต์ ขอบเขตสิทธิ์ และการกระทำใด (การส่งข้อความ การโอนเงิน การแก้ไขระเบียน) ที่ต้องยืนยัน คุยว่าวงวนของเอเจนต์มีขอบเขต สังเกตได้ และขัดจังหวะได้หรือไม่ คำตอบควรทำให้ขอบเขตแคบลงและเพิ่มด่านอนุมัติโดยมนุษย์ ทุกที่ที่การกระทำที่มีผลตามมาหรือย้อนกลับไม่ได้ยังเข้าถึงได้โดยไม่มีด่าน

3. **เราจะรู้ภายในหนึ่งวันได้อย่างไรว่าคุณภาพการค้นคืนตก ในเมื่อคำตอบมั่นใจที่สร้างบนข้อความผิดก็ดูปกติ?** RAG ทำให้คำตอบน่าเชื่อถือได้ก็ต่อเมื่อการค้นคืนนำข้อความที่มีคำตอบขึ้นมาจริง และการค้นคืนเสื่อมไปอย่างเงียบ ๆ เมื่อเอกสารเปลี่ยน ชิ้นข้อความล้าสมัย หรือเอ็มเบดดิงเบี่ยงจากโดเมนของคุณ เพราะโมเดลยังเขียนได้ลื่นไหลบนบริบทที่แย่ ผู้ใช้อาจไม่ร้องเรียนจนกว่าความเชื่อมั่นจะหายไปแล้ว นำตัวชี้วัดปัจจุบันของความหน่วงและการเรียกคืน (recall) ของการค้นคืน วิธีตรวจว่าข้อความที่ค้นคืนมามีคำตอบจริง และวิธีที่ความสดใหม่ของดัชนีตามทันการเปลี่ยนของเอกสาร สำหรับการใช้งานเดิมพันสูงหรือต่อสาธารณะ ให้คุยเรื่องการบันทึกแหล่งที่ค้นคืนเพื่อตรวจสอบ เพื่อสืบคำตอบที่แย่ไปถึงข้อความที่แย่ได้ หากคุณไม่มีการประเมินการค้นคืนเลย แปลว่าคุณกำลังอ้างอิงด้วยศรัทธา

4. **เราปฏิบัติต่อพรอมต์ บริบท และชุดประเมินเป็นชิ้นงานที่มีเวอร์ชันและผ่านการทบทวน หรือเป็นสตริงที่กระจายอยู่ในโน้ตบุ๊กและบันทึกแชต?** เมื่อพรอมต์กระจายข้ามทีมโดยไม่มีเวอร์ชันและซ้ำซ้อน การแก้ที่หนึ่งไม่เคยไปถึงที่อื่น และไม่มีใครทำซ้ำได้ว่าระบบถูกสั่งให้ทำอะไรเมื่อไตรมาสก่อน สำหรับทีมใหญ่ ทะเบียนพรอมต์ร่วมและชุดทดสอบการถดถอยที่รันทุกครั้งที่เปลี่ยนคือสิ่งที่ให้คุณสลับโมเดลหรือแก้คำสั่งได้โดยไม่ทำให้ฟีเจอร์ของอีกสองทีมพังอย่างเงียบ ๆ แรงดึงที่ขัดกันคือความเร็ว: วิศวกรทำซ้ำเร็วที่สุดเมื่อวางพรอมต์แล้วส่งเลย จึงควรตกลงว่าเส้นแบ่งอยู่ตรงไหนระหว่างการทดลองเร็ว ๆ กับสิ่งที่แตะผู้ใช้ นำข้อมูลว่าพรอมต์อยู่ที่ไหนตอนนี้ ชุดประเมินเป็นด่านคุมการเปลี่ยนแปลงหรือไม่ และคุณกำหนดเวอร์ชันของคลังที่ค้นคืนควบคู่กับพรอมต์อย่างไร ในบริบทองค์กรและภาครัฐ ให้เพิ่มข้อกำหนดด้านการตรวจสอบ: คุณอาจต้องแสดงว่าพรอมต์ใดและแหล่งใดสร้างเอาต์พุตหนึ่งเมื่อหลายเดือนก่อน และพรอมต์ที่ประกอบขึ้นใหม่ไม่ได้คือระเบียนที่ป้องกันตัวไม่ได้

5. **เมื่อปริมาณโตขึ้น เราจะควบคุมต้นทุนการอนุมานอย่างไรโดยไม่ทำให้คุณภาพตกอย่างเงียบ ๆ และใครเป็นเจ้าของการตัดสินใจเลือกโมเดล?** TCO ของฟีเจอร์ LLM ถูกครอบงำด้วยต้นทุนการอนุมานต่อการเรียก และต้นทุนที่ดูเล็กน้อยในโครงการนำร่องทบต้นเร็วในระดับระบบจริง ทำให้ทีมถูกล่อให้ลดไปใช้โมเดลที่อ่อนกว่าอย่างเงียบ ๆ แล้วหวังว่าไม่มีใครสังเกตเห็นคุณภาพที่ไหลลง สำหรับองค์กรใหญ่ การปล่อยให้แต่ละทีมเลือกโมเดลและเพดานต้นทุนตามความรู้สึกสร้างทั้งใบแจ้งหนี้ที่น่าตกใจและคุณภาพที่ไม่สม่ำเสมอ ข้อแลกเปลี่ยนที่แท้จริงคือขีดความสามารถเทียบกับต้นทุนและความหน่วง: โมเดลใหญ่ให้เหตุผลได้ดีกว่าในงานยาก โมเดลเล็กถูกและเร็วกว่าในงานง่าย และการแคช การจัดเส้นทาง และขอบเขตการค้นคืนล้วนขยับตัวเลขนี้ นำต้นทุนต่องานที่แก้เสร็จ คุณภาพตามระดับโมเดลบนชุดประเมินของคุณ และจุดที่พรอมต์หรือบริบทที่บวมกำลังทำให้ค่าโทเคนพอง ในการจัดงบองค์กรและภาครัฐ ให้ระบุว่าใครอนุมัติการเลือกโมเดลและเพดานการใช้จ่าย เพราะรายการต้นทุนที่ไม่มีเจ้าของคือรายการที่ไม่มีใครควบคุมเมื่อทราฟฟิกเพิ่มสามเท่า

6. **ข้อมูลอ่อนไหวอะไรเข้าถึงโมเดลได้ ข้อมูลนั้นไปไหนต่อ และเราพิสูจน์ได้ไหมว่ามันอยู่ในขอบเขต?** ทุกพรอมต์ เอกสารที่ค้นคืน และผลลัพธ์จากเครื่องมืออาจพาข้อมูลส่วนบุคคลหรือความลับเข้าสู่โมเดล และเมื่อใช้ผู้ให้บริการแบบโฮสต์ ออกนอกขอบเขตของคุณ และการรั่วตรงนี้คือเหตุการณ์ทางกฎหมายหรือความปลอดภัย ไม่ใช่ตั๋วแก้ข้อบกพร่อง สำหรับทีมใหญ่ที่เชื่อม LLM เข้ากับระบบภายใน ความเสี่ยงซ่อนอยู่ในงานวางท่อ: คลังที่ค้นคืนที่มีระเบียนที่ผู้ใช้บางคนไม่ควรเห็น หรือบันทึกที่เก็บอินพุตดิบ ความตึงเครียดคือขีดความสามารถเทียบกับการเปิดเผย เพราะการปกปิดข้อมูลและการจำกัดขอบเขตให้แคบอาจทำให้ฟีเจอร์ที่คุณพยายามสร้างทื่อลง นำแผนที่การไหลของข้อมูลที่เข้าสู่บริบท เงื่อนไขการเก็บรักษาและการฝึกของผู้ให้บริการ และวิธีที่คุณปกปิด จำกัดขอบเขต และบันทึกฟิลด์อ่อนไหว ในบริบทที่มีกฎระเบียบและภาครัฐ ให้ผูกเรื่องนี้กับกฎถิ่นที่อยู่ของข้อมูล (data residency) หน้าที่ในการเก็บรักษาระเบียน และข้อจำกัดตามสัญญาว่าผู้ขายใช้ข้อมูลของคุณได้อย่างไร เพราะการกำกับที่คุณแสดงหลักฐานไม่ได้คือการกำกับที่คุณไม่มี

## มุมมองตามประเภทองค์กร

**สตาร์ทอัป.** ส่งมอบฟีเจอร์ LLM แคบ ๆ หนึ่งอย่างที่แตะคุณค่าหลักของคุณ สร้างบนโมเดลที่โฮสต์ไว้พร้อมการค้นคืนจากเนื้อหาของคุณเอง และเก็บพรอมต์ใน git หลังอินเทอร์เฟซบาง ๆ เพื่อสลับผู้ให้บริการได้ รันไฟล์ประเมินเล็ก ๆ ของคำถามจริงก่อนทุกการเปลี่ยนแปลง กรองข้อความที่ผู้ใช้วางเพื่อลดการฉีดพรอมต์ และจำกัดค่าใช้จ่ายรายเดือนให้เด็ดขาด อย่าไปทางเอเจนต์และการโฮสต์เอง: วงวนเรียกเครื่องมือแบบไร้ขอบเขตที่คุณกำกับไม่ได้เป็นภาระ ไม่ใช่เดโม

**ธุรกิจขนาดเล็ก.** คุณน่าจะไม่มีผู้เชี่ยวชาญ ML จึงควรซื้อฟีเจอร์ LLM ที่ฝังอยู่ในเครื่องมือที่ใช้อยู่แล้ว แทนการจัดคนสร้างเอง มองความเสี่ยงเป็นคำถามตรง ๆ: คำตอบผิดที่ดูมั่นใจจะทำให้เสียลูกค้าตรงไหน และใครตรวจเอาต์พุตก่อนส่งออก เลือกผู้ขายที่แสดงแหล่งที่มา ให้คงมนุษย์ไว้ในวงจร และทำให้ปิด AI ได้ง่ายเมื่อมันทำงานผิดปกติ

**องค์กรขนาดใหญ่.** ปัญหาคือขนาดข้ามหลายทีม: เผยแพร่รูปแบบร่วมสำหรับ RAG แนวกั้น และสคีมาเครื่องมือ พร้อมเครื่องมือประเมินและทะเบียนพรอมต์กลาง เพื่อไม่ให้แต่ละกลุ่มค้นพบความล้มเหลวแบบเดิมซ้ำ จัดงบต้นทุนการอนุมานและการทบทวนโดยมนุษย์อย่างชัดแจ้ง ทำให้ชั้นอินเทอร์เฟซเป็นมาตรฐานเพื่อให้โมเดลเปลี่ยนได้ และกำกับดูแลเอเจนต์แบบรวมศูนย์ด้วยสิทธิ์น้อยที่สุด วงวนที่มีขอบเขต และบันทึกการตรวจสอบ บริหารฟีเจอร์ LLM เป็นพอร์ตโฟลิโอที่มีตัวชี้วัดและเกณฑ์ยุติ ไม่ใช่โครงการนำร่องที่กระจัดกระจาย

**ภาครัฐ.** ความโปร่งใส กฎการจัดซื้อจัดจ้าง และความรับผิดชอบกำหนดรูปทุกการเลือก อ้างอิงอย่างเข้มงวดกับแหล่งที่ได้รับอนุมัติพร้อมการอ้างอิงกำกับ ปฏิเสธเมื่อการค้นคืนว่างเปล่า และห้ามโมเดลระบุข้อกฎหมายที่อ้างอิงไม่ได้ ให้เจ้าหน้าที่ผู้รับผิดชอบทบทวนเอาต์พุตที่มีผลตามมา บันทึกอินพุตและแหล่งที่ค้นคืนเพื่อการตรวจสอบ รันชุดประเมินเชิงเป็นปรปักษ์ก่อนทุกการปล่อย และเรียกร้องการเปิดเผยข้อจำกัดของโมเดลและเงื่อนไขการจัดการข้อมูลไว้ในสัญญา

## ตัวอย่าง

**สตาร์ทอัป.** สตาร์ทอัปเครื่องมือนักพัฒนาสามคนเพิ่มตัวช่วยแชตบนเอกสารของตนเอง เพื่อให้ผู้ใช้เลิกส่งอีเมลถามเรื่องพื้นฐาน พวกเขาใช้ RAG เพื่อให้ทุกคำตอบอ้างหน้าเอกสารเฉพาะ สั่งโมเดลให้พูดว่า "ฉันไม่แน่ใจ นี่คือคนที่ควรถาม" เมื่อการค้นคืนว่างเปล่า และเก็บพรอมต์ไว้ใน git ก่อนทุกการเปลี่ยนแปลง พวกเขารันพรอมต์กับไฟล์เล็ก ๆ ของคำถามจริงจากผู้ใช้เพื่อจับการถดถอย และกรองข้อความที่ผู้ใช้วางเพื่อลดการฉีดพรอมต์ ตัวช่วยจัดการคำถามที่พบบ่อยและส่งที่เหลือเข้ากล่องจดหมายร่วมของผู้ก่อตั้งอย่างเงียบ ๆ

**องค์กรขนาดใหญ่.** บริษัทซอฟต์แวร์สร้างผู้ช่วยสนับสนุนภายในบนเอกสารผลิตภัณฑ์ บริษัทใช้ [RAG](https://en.wikipedia.org/wiki/Retrieval-augmented_generation) เพื่อให้คำตอบอ้างหน้าเอกสารเฉพาะ สั่งโมเดลให้พูดว่า "ไม่ทราบ" เมื่อการค้นคืนล้มเหลว และตรวจว่าทุกแหล่งที่อ้างมีอยู่จริง พรอมต์ถูกควบคุมเวอร์ชันและทดสอบกับชุดคำถามสนับสนุนจริงทุกครั้งที่เปลี่ยน ผู้ช่วยช่วยลดตั๋วงานประจำและส่งต่อกรณีที่มั่นใจต่ำให้เจ้าหน้าที่ที่เป็นมนุษย์ ขณะที่ตัวชี้วัดออนไลน์ติดตามอัตราการแก้ปัญหาและอัตราการแก้ไข

**ภาครัฐ.** หน่วยงานรัฐแห่งหนึ่งนำผู้ช่วย LLM มาใช้ช่วยเจ้าหน้าที่ร่างคำตอบต่อข้อซักถามของประชาชน การอ้างอิงเข้มงวด: โมเดลเรียบเรียงคำตอบได้จากแนวทางที่ได้รับอนุมัติพร้อมการอ้างอิงเท่านั้น และถูกห้ามไม่ให้ระบุนโยบายที่ไม่มีอยู่ในแหล่งที่ค้นคืน เจ้าหน้าที่ผู้รับผิดชอบทบทวนทุกร่างก่อนส่งออก การกรองอินพุตป้องกันการฉีดพรอมต์จากเอกสารที่ประชาชนยื่นมา เอาต์พุตถูกบันทึกเพื่อการตรวจสอบ และชุดประเมินของคำถามเชิงเป็นปรปักษ์และกรณีสุดขอบรันก่อนทุกการปล่อย เพื่อยืนยันว่าระบบปฏิเสธการคาดเดาในเรื่องข้อกฎหมาย

## เหตุผลทางธุรกิจ: แรงจูงใจ ผลตอบแทน (ROI) และต้นทุนรวม (TCO)

แอปพลิเคชัน LLM ให้ผลตอบแทนการลงทุน (ROI) ด้วยการทำงานที่ใช้ภาษามากให้เป็นอัตโนมัติ: ตอบคำถาม สรุปเอกสาร ร่างเนื้อหา และดึงโครงสร้างจากข้อความที่ไม่มีโครงสร้าง คุณค่าปรากฏเป็นตั๋วที่ลดลง การร่างที่เร็วขึ้น การทบทวนด้วยมือที่น้อยลง และความสามารถบริการตนเองใหม่ ๆ เพราะมักไม่มีขั้นตอนการฝึก เวลาถึงคุณค่าแรกจึงสั้น ซึ่งเป็นจุดดึงดูดสำคัญ

แต่ต้นทุนรวมตลอดอายุการใช้งาน (TCO) ถูกครอบงำด้วยต้นทุนการอนุมานต่อเนื่อง โครงสร้างพื้นฐานการค้นคืน ไปป์ไลน์การประเมิน ระบบแนวกั้น และการทบทวนโดยมนุษย์ ต้นทุนต่อการเรียกสะสมเร็วเมื่อขนาดใหญ่ และแอปพลิเคชันที่ไม่มีการเฝ้าติดตามอาจเบี่ยงไปสู่พฤติกรรมที่ไม่ปลอดภัยหรือแพง ต้นทุนของการไม่นำมาใช้คือการตามหลังด้านคุณภาพบริการและผลิตภาพของเจ้าหน้าที่ ต้นทุนของการนำมาใช้อย่างสะเพร่าคือเหตุการณ์ภาพหลอนต่อสาธารณะหรือข้อมูลรั่ว นำเสนอเหตุผลต่อผู้นำโดยจับคู่เป้าหมายผลิตภาพที่เป็นรูปธรรมกับแผนความปลอดภัยและการประเมินที่เป็นรูปธรรม และจัดงบให้แนวกั้นและการกำกับโดยมนุษย์ที่ทำให้คุณค่ายั่งยืน

## รูปแบบที่ไม่ควรทำและข้อควรระวัง

- **เชื่อเอาต์พุตที่ลื่นไหล** เข้าใจผิดว่าข้อความที่มั่นใจและเขียนดีคือข้อความที่ถูกต้อง
- **RAG โดยไม่ประเมินการค้นคืน** สมมุติว่าการค้นคืนใช้ได้ และไม่เคยตรวจว่ามันนำข้อความที่ถูกต้องขึ้นมาหรือไม่
- **มองไม่เห็นการฉีดพรอมต์** ป้อนเนื้อหาที่ไม่น่าไว้วางใจเข้าพรอมต์โดยไม่มีการป้องกัน
- **เอเจนต์ไร้ขอบเขต** ปล่อยให้เอเจนต์ทำการกระทำที่มีผลตามมาโดยไม่มีข้อจำกัดหรือการอนุมัติจากมนุษย์
- **ไม่มีเครื่องมือประเมิน** เปลี่ยนพรอมต์และโมเดลตามความรู้สึก โดยไม่มีการทดสอบการถดถอย
- **พรอมต์ล้นเกิน** พรอมต์กระจัดกระจาย ไม่มีเวอร์ชัน และซ้ำซ้อนข้ามทีม
- **อัตโนมัติเกินไป** ถอดมนุษย์ออกจากการตัดสินใจที่มีน้ำหนักทางกฎหมายหรือความปลอดภัย

## แบบจำลองความเป็นผู้ใหญ่

1. **ระดับ 1 เริ่มต้น** เขียนพรอมต์แบบเฉพาะกิจในโครงการที่แยกกัน ไม่มีการอ้างอิง แนวกั้น หรือการประเมิน พรอมต์อยู่ทุกที่ที่ใครสักคนวางไว้ และภาพหลอนถูกค้นพบในระบบจริง
2. **ระดับ 2 พัฒนา** บางทีมเพิ่ม RAG การกำหนดเวอร์ชันพรอมต์ การตรวจสอบเอาต์พุตพื้นฐาน และชุดประเมินด้วยมือขนาดเล็ก แต่แนวปฏิบัติต่างกันตามทีมและอาศัยผู้นำเฉพาะบุคคลมากกว่าความคาดหวังร่วม
3. **ระดับ 3 สร้างมาตรฐาน** รูปแบบที่มีเอกสารสำหรับ RAG แนวกั้น สคีมาเครื่องมือ และการกำหนดเวอร์ชันพรอมต์ถูกบังคับใช้ทั้งองค์กร การประเมินออฟไลน์อัตโนมัติรันทุกครั้งที่พรอมต์หรือโมเดลเปลี่ยน ขั้นตอนเดิมพันสูงมีตัวชี้วัดออนไลน์และการทบทวนโดยมนุษย์
4. **ระดับ 4 บริหารจัดการ** พอร์ตโฟลิโอถูกวัดเทียบกับค่าฐาน: การเรียกคืนของการค้นคืน อัตราภาพหลอนและการปฏิเสธ ความครอบคลุมของการป้องกันการฉีดพรอมต์ ต้นทุนและความหน่วงต่อการเรียก และอัตราการส่งต่อและการแก้ไข ถูกติดตามบนแดชบอร์ด ด่านการปล่อยและเกณฑ์ยุติทำงานตามหลักฐานแทนความเห็น และการรันการถดถอยบล็อกการเปลี่ยนแปลงใดที่ขยับตัวชี้วัดไปในทางที่แย่
5. **ระดับ 5 ประสานทั้งระบบ** การประเมินออฟไลน์และออนไลน์ต่อเนื่องผูกกับผลลัพธ์ทางธุรกิจ การป้องกันการฉีดพรอมต์ เอเจนต์ และการอ้างอิงถูกกำกับดูแลและสังเกตได้ องค์กรเลิกใช้ ปรับจูน และปรับขอบเขตฟีเจอร์ LLM เป็นกิจวัตร และสลับโมเดลเมื่อคุณภาพ ต้นทุน และความเสี่ยงเปลี่ยน

## ประเด็นชวนคุย

- คุณตัดสินอย่างไรว่าเอาต์พุตใดต้องผ่านการทบทวนโดยมนุษย์ก่อนใช้?
- มาตรฐานของ "อ้างอิงพอ" ของคุณคืออะไร ก่อนที่คำตอบจะแสดงให้ผู้ใช้เห็นได้?
- คุณป้องกันการฉีดพรอมต์อย่างไรเมื่อเนื้อหาที่ไม่น่าไว้วางใจต้องเข้าสู่บริบท?
- เมื่อไรที่เอเจนต์คุ้มกับความเสี่ยงที่เพิ่มขึ้น เทียบกับการออกแบบที่เรียบง่ายกว่าแบบเรียกครั้งเดียว?
- คุณประเมินคุณภาพเชิงอัตวิสัยในระดับใหญ่อย่างไรโดยไม่พึ่งการให้คะแนนด้วยโมเดลมากเกินไป?
- คุณรักษาพรอมต์ให้ดูแลง่ายและสอดคล้องกันข้ามหลายทีมอย่างไร?

## ข้อสรุปสำคัญ

- ความพึ่งพาได้มาจากวิศวกรรมรอบโมเดล: บริบท การอ้างอิง แนวกั้น และการประเมิน
- RAG อ้างอิงคำตอบกับแหล่งที่เชื่อถือได้และเปิดทางให้อ้างอิงกำกับและตรวจสอบได้
- มองโมเดลเป็นส่วนประกอบที่ไม่น่าไว้วางใจ ตรวจสอบเอาต์พุตและจำกัดการใช้เครื่องมือ
- ให้เอเจนต์มีสิทธิ์น้อยที่สุด วงวนที่มีขอบเขต และการอนุมัติจากมนุษย์สำหรับการกระทำที่มีผลตามมา
- ประเมินแบบออฟไลน์ ออนไลน์ และด้วยมนุษย์อย่างต่อเนื่อง นั่นคือสิ่งที่ทำให้การเปลี่ยนแปลงปลอดภัย
