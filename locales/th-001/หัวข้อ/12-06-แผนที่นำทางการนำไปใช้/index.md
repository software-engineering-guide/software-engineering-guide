# 12.6 แผนที่นำทางการนำไปใช้

ภาคผนวกนี้เป็นคู่มือเชิงปฏิบัติสำหรับการนำแนวปฏิบัติในหนังสือเล่มนี้ไปใช้ทีละขั้น
(*incrementally*) คำแนะนำที่สำคัญที่สุดของทั้งเล่ม ซึ่งย้ำไว้ในทุกบท คือ
**นำไปใช้ทีละน้อย อย่าเปลี่ยนทุกอย่างพร้อมกันในคราวเดียว (big-bang)**
การเปลี่ยนแปลงที่พยายามแก้ทุกอย่างพร้อมกันมักไม่เปลี่ยนอะไรได้อย่างยั่งยืน
เพราะทำให้ความเต็มใจของคนหมดแรง ท่วมทีมจนรับไม่ไหว และล้มพับเมื่อเจอวิกฤตครั้งแรก
ส่วนการเปลี่ยนแปลงที่เริ่มจากความเจ็บปวดจริง ส่งมอบชัยชนะที่มองเห็นได้ แล้วต่อยอดสะสมไปเรื่อย ๆ
สามารถขยับองค์กรที่มีคนหลายพันคนได้ภายในไม่กี่ปี

แผนที่นำทางนี้ให้หลักการของการนำไปใช้ ลำดับขั้นตามระดับความเป็นผู้ใหญ่ตั้งแต่ 90 วันแรกไปจนถึงสองปีขึ้นไป
กรอบการจัดลำดับความสำคัญพร้อมตัวอย่างที่คำนวณให้ดู ชัยชนะเร็วรายโดเมน
แนวทางพิเศษสำหรับองค์กรขนาดใหญ่และภาครัฐ วิธีวัดความสำเร็จ และรูปแบบความล้มเหลวที่ควรหลีกเลี่ยง

## หลักการของการนำไปใช้

หลักการเหล่านี้ใช้ได้ไม่ว่าองค์กรของคุณจะมีขนาดเท่าใด อยู่ในภาคส่วนใด หรือเริ่มต้นจากระดับความเป็นผู้ใหญ่แค่ไหน

- **เริ่มจากความเจ็บปวด ไม่ใช่จากกรอบงาน** หาสิ่งที่เจ็บที่สุด
  ไม่ว่าจะเป็นการปล่อยเวอร์ชันที่ช้า ระบบล่มบ่อย การตรวจสอบที่ไม่ผ่าน หรือคนลาออก แล้วแก้สิ่งนั้นก่อน
  ความเจ็บปวดสร้างความต้องการและแรงหนุนทางการเมืองที่คำสั่งจากเบื้องบนสร้างไม่ได้ ไม่มีใครต่อต้านสิ่งที่ช่วยให้โล่งใจ
- **ถนนลาดยางดีกว่าคำสั่งบังคับ** ทำให้วิธีที่แนะนำเป็นวิธีที่ *ง่ายที่สุด*
  เส้นทางทอง (golden path) ที่เร็วกว่า ปลอดภัยกว่า และมีเอกสารดีกว่า จะชนะใจคนได้ด้วยคุณค่าของมันเอง
  ส่วนนโยบายที่ช้ากว่าทางลัดก็จะถูกเลี่ยงอยู่ดี ลงทุนกับถนนลาดยางก่อนจะเลิกใช้ทางลูกรัง
- **วัดผลลัพธ์ ไม่ใช่กิจกรรม** ติดตามว่าการเปลี่ยนแปลงทำให้การส่งมอบ ความน่าเชื่อถือ
  ความปลอดภัย หรือผลลัพธ์ของผู้ใช้ดีขึ้นหรือไม่ ไม่ใช่นับว่ากี่ทีมเข้าอบรมหรือติ๊กช่องครบ
  ติดเครื่องมือวัดก่อนเปลี่ยน เพื่อพิสูจน์ผลได้
- **หาผู้สนับสนุนระดับผู้บริหาร และรักษาไว้ให้ได้** การเปลี่ยนแปลงที่ยั่งยืนต้องมีผู้บริหารที่รับผิดชอบ
  คอยปกป้องงบประมาณ ปลดล็อกอุปสรรค และยืนหยัดเมื่อการเปลี่ยนแปลงเริ่มอึดอัด
  การสนับสนุนไม่ใช่กิจกรรมตอนเปิดตัว แต่เป็นความสัมพันธ์ต่อเนื่องที่ต้องพิสูจน์ซ้ำด้วยผลงาน
- **อาสาสมัครก่อนผู้ถูกเกณฑ์** เริ่มกับทีมที่ *อยากเปลี่ยน* ความสำเร็จของพวกเขากลายเป็นเรื่องเล่าอ้างอิงที่ดึงคนส่วนใหญ่ที่ยังลังเลเข้ามา
  การบังคับผู้ที่ต่อต้านก่อนจะได้แต่การทำตามแบบจำใจและเรื่องเตือนใจ
- **ทำให้ย้อนกลับได้เท่าที่ทำได้** เลือกการเปลี่ยนแปลงที่ทดลองนำร่อง วัดผล และถอยกลับได้
  การตัดสินใจแบบ "ประตูสองทาง" ที่ย้อนกลับได้ควรเดินเร็ว ส่วนกระบวนการหนัก ๆ เก็บไว้ใช้กับเรื่องที่ย้อนกลับไม่ได้จริง ๆ
- **แสดงชัยชนะให้เร็วและบ่อย** ส่งมอบสิ่งที่มองเห็นได้ภายในไม่กี่สัปดาห์ ไม่ใช่หลายไตรมาส
  โมเมนตัมเป็นทรัพยากร ใช้ชัยชนะแรกเป็นทุนให้ชัยชนะถัดไป
- **เจอทีมในจุดที่เขายืนอยู่** เกณฑ์ความเป็นผู้ใหญ่เดียวที่ใช้กับทุกทีมเหมือนกันนั้นไม่เป็นธรรมและบั่นทอนกำลังใจ
  จัดลำดับตามความพร้อมและความเจ็บปวดของแต่ละทีม

## ลำดับขั้นตามระดับความเป็นผู้ใหญ่

ช่วงเวลาด้านล่างนี้สะสมต่อกัน แต่ละช่วงสร้างบนช่วงก่อนหน้า วันที่เป็นเพียงแนวทาง ไม่ใช่กำหนดตายตัว
องค์กรขนาดใหญ่หรือถูกกำกับดูแลเข้มงวดอาจใช้เวลานานกว่าในแต่ละช่วง รูปแบบ (*ทำให้นิ่ง แล้วทำให้เป็นมาตรฐาน
แล้วขยายขนาด แล้วรักษาให้ยั่งยืน*) ใช้ได้ไม่ว่าจะเดินเร็วหรือช้า

### 90 วันแรก: ทำให้นิ่งและพิสูจน์

เป้าหมาย: วางฐานเปรียบเทียบ เลือกปัญหาเรือธงหนึ่งหรือสองเรื่อง และส่งมอบชัยชนะแรกที่น่าเชื่อถือกับทีมที่เต็มใจ

- [ ] ระบุผู้บริหารผู้สนับสนุนที่รับผิดชอบ และกลุ่มแกนนำขนาดเล็ก
- [ ] วัดฐานของตัวชี้วัด DORA ทั้งสี่ (ความถี่ในการปล่อย ระยะเวลานำ อัตราการเปลี่ยนแปลงที่ล้มเหลว
      เวลาในการกู้คืน) แม้ตัวเลขจะยังหยาบ
- [ ] ประเมินแบบเบา ๆ เทียบกับแบบจำลองความเป็นผู้ใหญ่ในบทที่ 12.4 เพื่อหาช่องว่างที่ใหญ่ที่สุด
- [ ] เลือกทีมนำร่องหนึ่งหรือสองทีมที่ *อาสา* และมีความเจ็บปวดจริง
- [ ] แก้ปัญหาที่เห็นได้ชัดหนึ่งเรื่องให้จบตั้งแต่ต้นจนปลาย (เช่น ทำการปรับใช้ของทีมหนึ่งให้เป็นอัตโนมัติ
      หรือเพิ่ม SLO ให้บริการสำคัญหนึ่งตัว)
- [ ] ตั้งบันทึกการตัดสินใจร่วมกัน (ADR) และที่เผยแพร่ผลลัพธ์
- [ ] ตกลงวิธีวัดความสำเร็จ *ก่อน* จะเปลี่ยนอะไรทั้งสิ้น

### ภายใน 6 เดือน: ทำรูปแบบที่ชนะให้เป็นมาตรฐาน

เป้าหมาย: เปลี่ยนความสำเร็จของทีมนำร่องให้เป็นรูปแบบที่ทำซ้ำได้และมีเอกสาร แล้วเสนอเป็นถนนลาดยางให้ทีมกลุ่มถัดไป

- [ ] เผยแพร่เส้นทางทองจากทีมนำร่องเป็นแม่แบบ ไปป์ไลน์ และเอกสารที่นำกลับมาใช้ซ้ำได้
- [ ] ตั้งทีมแพลตฟอร์มหรือทีมสนับสนุน (แม้จะเป็นทีมเสมือน) เพื่อดูแลและช่วยเหลือถนนลาดยาง
- [ ] ขยายรูปแบบไปยังอีกสามถึงห้าทีม โดยเรียงตามผลกระทบและความพร้อม
- [ ] ใส่ด่านตรวจคุณภาพและความปลอดภัยอัตโนมัติ (linting การทดสอบ SAST/SCA)
      ในไปป์ไลน์กลางเป็นค่าเริ่มต้น ไม่ใช่ส่วนเสริม
- [ ] เริ่มทบทวนเหตุการณ์แบบไม่กล่าวโทษ (blameless) และเผยแพร่รายงานหลังเหตุการณ์ภายในองค์กร
- [ ] ตั้งเวทีธรรมาภิบาลแบบเบา (การทบทวนสถาปัตยกรรม การดูแลถนนลาดยาง) ที่ช่วยปลดล็อก ไม่ใช่เป็นด่านกั้น

### ภายใน 12 เดือน: ขยายทั่วทั้งองค์กร

เป้าหมาย: ทำให้ถนนลาดยางเป็นค่าเริ่มต้นสำหรับงานใหม่ส่วนใหญ่ และเริ่มเลิกแนวปฏิบัติเก่าที่แย่ที่สุด

- [ ] ขยายหน้าที่ของทีมแพลตฟอร์ม เผยแพร่แค็ตตาล็อกบริการและสกอร์การ์ด
- [ ] กำหนดเกณฑ์พื้นฐานทั่วองค์กร: SLO สำหรับบริการระดับ 1 มาตรการความปลอดภัยในทุกไปป์ไลน์
      การตรวจสอบการเข้าถึงได้ (accessibility) ในการสร้างส่วนหน้า
- [ ] ติดตามอัตราการนำไปใช้รายทีมและทำให้ข้อมูลมองเห็นได้
- [ ] เริ่มปรับปรุงระบบเดิมอย่างตั้งใจในระบบที่เสี่ยงที่สุด โดยใช้รูปแบบ strangler-fig และ branch-by-abstraction
- [ ] ผนวกการวัดผลเข้ากับการวางแผน: ทีมทบทวนแนวโน้ม DORA และความน่าเชื่อถือในจังหวะการทำงานปกติ
- [ ] ลงทุนกับการเสริมศักยภาพ (อบรมภายใน การสอนงาน ชุมชนนักปฏิบัติ)
      เพื่อให้ความสามารถแพร่เร็วกว่าคำสั่งบังคับ

### 2 ปีขึ้นไป: รักษาและปรับปรุงอย่างต่อเนื่อง

เป้าหมาย: แนวปฏิบัติกลายเป็น "วิธีที่เราทำงาน" ไม่ใช่โปรแกรม และองค์กรปรับปรุงมันเองได้โดยไม่ต้องมีแรงผลักจากส่วนกลาง

- [ ] ยุติโปรแกรมการเปลี่ยนแปลงในฐานะโครงการที่มีชื่อ ฝังงานของมันเข้ากับธรรมาภิบาลปกติและการดำเนินงานของแพลตฟอร์ม
- [ ] มองถนนลาดยางเป็นผลิตภัณฑ์ที่มีแผนงาน ผู้ใช้ และตัวชี้วัดความพึงพอใจของตัวเอง (แบบสำรวจประสบการณ์นักพัฒนา)
- [ ] จัดการหนี้ทางเทคนิคและการปรับปรุงระบบเป็นพอร์ตโฟลิโอที่ทำต่อเนื่อง ไม่ใช่การรณรงค์ครั้งเดียว
- [ ] ประเมินระดับความเป็นผู้ใหญ่ซ้ำเป็นระยะ และยกมาตรฐานขึ้นเมื่อพื้นฐานสูงขึ้น
- [ ] ป้องกันการถดถอย: รักษาการสนับสนุน วัดผลต่อเนื่อง และปรับแนวปฏิบัติให้ทันเทคโนโลยีและภัยคุกคามที่เปลี่ยนไป

## กรอบการจัดลำดับความสำคัญ

คุณจะมีสิ่งที่อยากปรับปรุงมากกว่าที่มีกำลังทำเสมอ
จัดลำดับด้วยแบบจำลองที่เรียบง่ายและอธิบายได้ แทนที่จะฟังเสียงที่ดังที่สุดในห้อง

ให้คะแนนแต่ละโครงการริเริ่มใน 3 มิติ

- **ผลกระทบ (1–5):** ช่วยปรับปรุงผลลัพธ์จริง (ความเร็วในการส่งมอบ ความน่าเชื่อถือ ความปลอดภัย ต้นทุน หรือคุณค่าต่อผู้ใช้)
  ได้มากเพียงใด และกับกี่ทีมหรือกี่ผู้ใช้
- **ความพยายาม (1–5):** ต้องใช้งาน การประสานงาน และการรบกวนมากแค่ไหนจึงจะส่งมอบได้
  (ยิ่งสูง = ยิ่งต้องใช้ความพยายามมาก)
- **น้ำหนักความเสี่ยง (0.5–2.0):** ตัวคูณสำหรับความเร่งด่วนและความเสี่ยงที่เปิดเผย
  ประเด็นความปลอดภัย การปฏิบัติตามกฎระเบียบ และความปลอดภัยของชีวิตมีน้ำหนักสูงกว่า ส่วนของที่มีก็ดีแต่ไม่จำเป็นมีน้อยกว่า

คะแนนจัดอันดับที่ใช้ได้ดีคือ

```
Priority = (Impact × Risk weight) ÷ Effort
```

จัดอันดับจากมากไปน้อย แล้วเรียงลำดับรายการบนสุด แต่ให้มี "ชัยชนะเร็ว" ที่ใช้ความพยายามน้อยอย่างน้อยหนึ่งเรื่องกำลังเดินอยู่เสมอเพื่อรักษาโมเมนตัม
และทบทวนคะแนนทุกไตรมาสเมื่อสถานการณ์เปลี่ยน

ในตัวอย่างนี้ งานไปป์ไลน์ความปลอดภัยขึ้นอันดับต้นเพราะน้ำหนักความเสี่ยงสูงและใช้ความพยายามไม่มาก
ส่วนการเปลี่ยนภาษาทั้งองค์กรตกไปท้ายสุดแม้จะมีคนกระตือรือร้น เพราะผลกระทบต่ำ ขณะที่ความพยายามและการรบกวนสูง
กรอบนี้ทำให้ข้อแลกเปลี่ยนดังกล่าวชัดเจนและคุยกันได้ ซึ่งเป็นคุณค่าที่แท้จริงของมัน

## ชัยชนะเร็วรายโดเมน

ทุกส่วนของหนังสือมีก้าวแรกที่ต้นทุนต่ำและให้สัญญาณชัด เริ่มที่นี่

| ส่วน | ชัยชนะเร็ว "เริ่มที่นี่" |
|---|---|
| **รากฐาน (วัฒนธรรม ทีม กระบวนการ)** | ใช้ ADR แบบเบาและจัดการย้อนมองแบบไม่กล่าวโทษหนึ่งครั้ง ทำให้การตัดสินใจและการเรียนรู้มองเห็นได้ |
| **งานฝีมือการเขียนโปรแกรม** | เปิดตัวจัดรูปแบบอัตโนมัติและ linter ใน CI เป็นค่าเริ่มต้นที่บังคับใช้ เพื่อให้สไตล์เลิกเป็นหัวข้อในการรีวิว |
| **สถาปัตยกรรม** | เขียนบันทึกการตัดสินใจด้านสถาปัตยกรรมหนึ่งหน้าและแผนภาพบริบท C4 สำหรับระบบที่สำคัญที่สุดของคุณ |
| **ความปลอดภัย** | เพิ่มการสแกนการพึ่งพา (SCA) และการสแกนความลับ (secret) ในไปป์ไลน์ เริ่มเปิดใช้กับ repo สำคัญหนึ่งตัวก่อน |
| **UX / การออกแบบ** | ทำการทดสอบการใช้งานแบบประหยัด 3 ครั้งกับ flow ที่มีผู้ใช้มากที่สุด แล้วแก้ปัญหาอันดับหนึ่งที่สังเกตเห็น |
| **AI / ML** | เขียนการตั้งโจทย์ปัญหาหนึ่งหน้าและตรวจความพร้อมของข้อมูลก่อนเริ่มงานโมเดลใด ๆ กำหนดว่าจะประเมินความสำเร็จอย่างไร |
| **ข้อมูล / การวิเคราะห์** | กำหนดตัวชี้วัด "North Star" ที่ตกลงร่วมกันหนึ่งตัวและแดชบอร์ดที่เชื่อถือได้หนึ่งอัน เลิกอันที่ขัดแย้งกัน |
| **DevOps / แพลตฟอร์ม** | พาหนึ่งทีมไปสู่ไปป์ไลน์ build-test-deploy อัตโนมัติเต็มรูปแบบ และบันทึกเป็นแม่แบบ |
| **การปฏิบัติการ / ความน่าเชื่อถือ** | กำหนด SLI และ SLO หนึ่งตัวสำหรับเส้นทางผู้ใช้ที่สำคัญที่สุด แจ้งเตือนจากอาการ ไม่ใช่จากสาเหตุ |
| **องค์กรขนาดใหญ่ / ภาครัฐ** | จับคู่มาตรการควบคุมปัจจุบันกับกรอบหนึ่งกรอบ (NIST CSF, ISO 27001 หรือ SOC 2) และทำหลักฐานของมาตรการหนึ่งข้อให้เป็นอัตโนมัติ |

## แนวทางพิเศษสำหรับองค์กรขนาดใหญ่

องค์กรใหญ่ที่ก่อตั้งมานานมีขนาด ทีมจำนวนมาก ระบบเดิมที่ลึก และภาระการจัดการการเปลี่ยนแปลงสูง
ปรับแผนที่นำทางให้เหมาะ

- **กระจายอำนาจ อย่ารวมทุกอย่างไว้ส่วนกลาง** ทีมกลางทีมเดียวให้บริการทีมผลิตภัณฑ์เป็นร้อยไม่ไหว
  ใช้ทีมแพลตฟอร์มจัดหาถนนลาดยาง และทีมสนับสนุนช่วยสอนงาน โดยให้ทีมผลิตภัณฑ์ยังเป็นเจ้าของงานของตน
  (ดู Team Topologies)
- **เคารพกฎของคอนเวย์ (Conway's Law)** สถาปัตยกรรมของคุณจะสะท้อนผังองค์กร
  ถ้าอยากได้บริการที่แยกจากกัน ก็ต้องมีทีมที่แยกจากกันและมีอำนาจตัดสินใจ จัดโครงสร้างใหม่อย่างตั้งใจ แทนที่จะฝืนทิศของเสี้ยนไม้
- **มองระบบเดิมเป็นพอร์ตโฟลิโอ** คุณปรับปรุงทุกอย่างไม่ได้ จัดอันดับระบบเดิมตามความเสี่ยงและคุณค่าทางธุรกิจ
  แล้วใช้การย้ายแบบ strangler-fig กับไม่กี่ระบบที่สำคัญ ส่วนที่เหลือให้หยุดนิ่งหรือยุติอย่างตั้งใจ
- **การจัดการการเปลี่ยนแปลงเป็นงานจริง** ในระดับขนาดใหญ่ การสื่อสาร การอบรม และการจัดแรงจูงใจให้สอดคล้องไม่ใช่ภาระส่วนเกิน
  แต่คือตัวการเปลี่ยนแปลงเอง จัดงบสำหรับการเสริมศักยภาพ ชุมชนนักปฏิบัติ และการเผยแพร่ภายในอย่างชัดเจน
- **ระวังปฏิกิริยาเคยชินกับคำสั่ง** องค์กรใหญ่มักออกบันทึกนโยบายเป็นค่าเริ่มต้น จงต้านไว้
  คำสั่งที่ไม่มีถนนลาดยางให้ผลแค่การติ๊กช่อง ส่วนถนนลาดยางที่ไม่มีคำสั่งให้การนำไปใช้ที่แท้จริง
- **จัดแรงจูงใจและงบประมาณให้สอดคล้อง** เปลี่ยนจากการให้งบเป็นโครงการไปเป็นทีมผลิตภัณฑ์ที่ยั่งยืน
  เพื่อให้การปรับปรุงอยู่รอดเกินวันสิ้นสุดโครงการ ให้รางวัลที่ผลลัพธ์ ไม่ใช่ปริมาณงาน

## แนวทางพิเศษสำหรับภาครัฐ

องค์กรภาครัฐมีรอบการจัดซื้อจัดจ้าง ด่านการปฏิบัติตามกฎระเบียบ การบริหารผู้รับจ้าง งบประมาณหลายปี
และภาระความโปร่งใสเพิ่มเข้ามา สิ่งเหล่านี้คือข้อมูลนำเข้าของการออกแบบ ไม่ใช่ข้ออ้าง

- **ออกแบบเผื่อ ATO ตั้งแต่วันแรก** ด่านการอนุมัติให้ดำเนินการ (authorisation to operate) และการเฝ้าระวังต่อเนื่อง
  (ตาม NIST RMF / 800-37) อาจกินเวลาส่วนใหญ่ของโครงการ ฝังมาตรการความปลอดภัยและการเก็บหลักฐานในไปป์ไลน์ตั้งแต่ต้น
  เพื่อให้การปฏิบัติตามกฎระเบียบเป็นไปอย่างต่อเนื่อง ไม่ใช่การเร่งรีบปลายทางที่ขวางงาน
- **จัดซื้อทีละน้อย** การจัดซื้อแบบ big-bang หลายปีทำให้ความล้มเหลวแบบ big-bang ที่หนังสือเล่มนี้เตือนกลายเป็นสถาบัน
  ควรเลือกการทำสัญญาแบบแยกเป็นโมดูล การให้รางวัลงานขนาดเล็กลง และขอบเขตงานที่อิงผลลัพธ์ซึ่งเปิดทางให้ทำซ้ำปรับปรุงได้
- **บริหารผู้ขายและผู้รวมระบบเป็นส่วนหนึ่งของทีม** งานวิศวกรรมภาครัฐจำนวนมากส่งมอบโดยผู้รับจ้าง
  เขียนถนนลาดยาง ด่านคุณภาพ และข้อกำหนดความโปร่งใสลงในสัญญา และให้แน่ใจว่าความรู้และโค้ดถ่ายโอนมายังรัฐ
  เพื่อหลีกเลี่ยงการผูกขาดผู้ขายและความเสี่ยงแบบ bus factor
- **วางแผนตามรอบงบประมาณ** งบประมาณรายปีและหลายปีจำกัดสิ่งที่คุณผูกพันได้
  จัดลำดับงานให้แต่ละงวดที่ได้รับงบส่งมอบคุณค่าได้ในตัวเอง และไม่ทิ้งคุณไว้กลางทางของการเปลี่ยนแปลงถ้างบเปลี่ยน
- **การเข้าถึงได้และภาษาที่เข้าใจง่ายเป็นข้อผูกพันทางกฎหมาย** Section 508, ADA, WCAG
  และข้อบังคับภาษาธรรมดาเป็นข้อกำหนด ไม่ใช่ส่วนเสริม ฝังการตรวจการเข้าถึงในไปป์ไลน์และการทบทวนเนื้อหาในขั้นตอนการทำงาน
- **ความโปร่งใสคือฟีเจอร์** FOIA คำสั่งโอเพนซอร์ส ("เงินสาธารณะ โค้ดสาธารณะ")
  และมาตรฐานบริการที่เผยแพร่ ทำให้งานของคุณถูกสาธารณชนตรวจสอบ ออกแบบรองรับไว้
  มีบันทึกที่ชัดเจน เปิดเผยเมื่อเหมาะสม และเผยแพร่ข้อมูลประสิทธิภาพอย่างตรงไปตรงมา
- **ตามรูปแบบภาครัฐที่พิสูจน์แล้ว** U.S. Digital Services Playbook, GOV.UK Service Standard และ USWDS
  บรรจุบทเรียนที่ได้มาอย่างยากลำบากไว้ นำมาใช้แทนการคิดใหม่ทั้งหมด

## การวัดความสำเร็จของการนำไปใช้

วัดทั้งตัวชี้วัดนำ (*leading*: สัญญาณเริ่มต้นว่าการเปลี่ยนแปลงเริ่มหยั่งราก) และตัวชี้วัดตาม (*lagging*: ผลลัพธ์ที่คุณสนใจในที่สุด)
ดูแนวโน้ม ไม่ใช่การอ่านค่าครั้งเดียว และอย่าปล่อยให้ตัวชี้วัดกลายเป็นเป้าหมายที่ถูกเล่นเกม

| ประเภท | ตัวชี้วัด | บอกอะไรคุณ |
|---|---|---|
| นำ | จำนวนทีมที่อยู่บนถนนลาดยาง | การนำไปใช้แพร่เร็วแค่ไหน |
| นำ | ความครอบคลุมของด่านในไปป์ไลน์ (การทดสอบ SAST a11y) | คุณภาพและความปลอดภัยฝังลึกเพียงใด |
| นำ | คะแนนแบบสำรวจประสบการณ์นักพัฒนา | ถนนลาดยางช่วยได้จริงหรือไม่ |
| นำ | เปอร์เซ็นต์ของการตัดสินใจที่บันทึกเป็น ADR | วัฒนธรรมการเขียนและการเรียนรู้เป็นของจริงหรือไม่ |
| ตาม | ความถี่ในการปล่อย (DORA) | ปริมาณงานที่ส่งมอบ |
| ตาม | ระยะเวลานำของการเปลี่ยนแปลง (DORA) | ความเร็วจาก commit ถึงการใช้งานจริง |
| ตาม | อัตราการเปลี่ยนแปลงที่ล้มเหลว (DORA) | คุณภาพของกระบวนการส่งมอบ |
| ตาม | เวลาในการกู้คืนบริการ (DORA) | ความยืดหยุ่นในการปฏิบัติการ |
| ตาม | แนวโน้มความถี่และความรุนแรงของเหตุการณ์ | ความน่าเชื่อถือที่ดีขึ้นตามเวลา |
| ตาม | ข้อค้นพบจากการตรวจสอบ / มาตรการควบคุมที่ล้มเหลว | สถานะการปฏิบัติตามกฎระเบียบ |
| ตาม | การคงอยู่และการลาออก | วัฒนธรรมกำลังดีขึ้นหรือไม่ |

ตัวชี้วัด DORA ทั้งสี่เป็นตัวชี้วัดผลลัพธ์ข้ามอุตสาหกรรมที่ผ่านการพิสูจน์มากที่สุดสำหรับการส่งมอบ
ให้ถือว่าการดีขึ้นพร้อมกันทั้งสี่ตัวเป็นสัญญาณหลัก และระวังอย่าปรับปรุงตัวหนึ่งโดยแลกกับอีกตัวหนึ่ง

## รูปแบบความล้มเหลวที่พบบ่อยและวิธีหลีกเลี่ยง

| รูปแบบความล้มเหลว | หน้าตาเป็นอย่างไร | วิธีหลีกเลี่ยง |
|---|---|---|
| **การเปิดตัวแบบ big-bang** | เปลี่ยนทุกอย่างให้ทุกคนพร้อมกัน โปรแกรมล้มทับน้ำหนักตัวเอง | เรียงลำดับตามความเจ็บปวดและความพร้อม นำร่อง พิสูจน์ แล้วจึงขยาย |
| **คำสั่งบังคับที่ไม่มีถนนลาดยาง** | นโยบายบังคับวิธีใหม่ แต่วิธีใหม่ช้ากว่า ทีมทำตามบนกระดาษแต่เลี่ยงในทางปฏิบัติ | สร้างทางที่ง่ายกว่าและดีกว่า *ก่อน* ให้การนำไปใช้เกิดจากคุณค่า |
| **คัดลอกกรอบงานแบบลัทธิบูชา (cargo-culting)** | ลอก SAFe โมเดล Spotify หรือโครงสร้างขององค์กรอื่นโดยไม่มีบริบทของเขา | เริ่มจากความเจ็บปวดและหลักการของตัวเอง ปรับให้เหมาะ ไม่ใช่ย้ายปลูก |
| **วัดกิจกรรม ไม่ใช่ผลลัพธ์** | ฉลองการอบรมที่เสร็จและช่องที่ติ๊ก ขณะที่การส่งมอบและความน่าเชื่อถือไม่ขยับ | ติดเครื่องมือวัดผลลัพธ์ (DORA เหตุการณ์ คุณค่าต่อผู้ใช้) ตั้งแต่ต้น |
| **การเปลี่ยนแปลงที่เริ่มจากเครื่องมือ** | ซื้อแพลตฟอร์มแล้วคาดว่าวัฒนธรรมจะตามมา | นำด้วยแนวปฏิบัติและถนนลาดยาง เครื่องมือรับใช้สิ่งเหล่านี้ ไม่ใช่กลับกัน |
| **สูญเสียผู้สนับสนุน** | ผู้บริหารผู้สนับสนุนย้ายออกหรือถอยห่าง โปรแกรมชะงัก | ฝังการเปลี่ยนแปลงในธรรมาภิบาลปกติ สร้างแนวร่วม ไม่ใช่จุดล้มเหลวจุดเดียว |
| **ตัวชี้วัดฉาบฉวยและการเล่นเกม** | ตัวเลขความครอบคลุมหรือ velocity สูงขึ้นขณะที่คุณภาพตก | ใช้ตัวชี้วัดเป็นสัญญาณพร้อมมาตรวัดถ่วงดุล ไม่ใช่เป้าหมายเดียว |
| **ต้มมหาสมุทรกับระบบเดิม** | พยายามปรับปรุงทุกอย่างแต่ส่งมอบอะไรไม่ได้เลย | จัดอันดับตามความเสี่ยงและคุณค่า รัดคอ (strangle) ไม่กี่ระบบสำคัญ แช่แข็งที่เหลือ |
| **ความเหนื่อยล้าจากการเปลี่ยนแปลง** | เปลี่ยนไม่รู้จบโดยไม่เห็นผล ทีมถอยห่าง | ส่งมอบชัยชนะเร็ว รักษาจังหวะที่ยั่งยืน ปล่อยให้โปรแกรมจบและกลายเป็นงานปกติ |
| **เมินผังองค์กร** | สถาปัตยกรรมใหม่ขัดกับโครงสร้างทีมที่มีอยู่ | ใช้ inverse Conway manoeuvre: จัดทีมให้ตรงกับสถาปัตยกรรมที่ต้องการ |

## เวอร์ชันที่สั้นที่สุดเท่าที่เป็นไปได้

ถ้าคุณจำอะไรไม่ได้เลยจากภาคผนวกนี้ ขอให้จำสิ่งนี้

1. หาความเจ็บปวดที่ใหญ่ที่สุด แล้วแก้กับทีมที่เต็มใจ
2. เปลี่ยนวิธีแก้นั้นให้เป็นถนนลาดยางที่ง่ายกว่าวิธีเดิมจริง ๆ
3. วัดผลลัพธ์ แสดงชัยชนะ และใช้มันเป็นทุนสำหรับก้าวถัดไป
4. ทำซ้ำ ขยายวงให้กว้างขึ้น จนถนนลาดยางกลายเป็นวิธีที่คุณทำงานตามปกติ
5. รักษาผู้สนับสนุน วัดผลต่อเนื่อง และอย่าเปลี่ยนทุกอย่างพร้อมกัน

ดู **บทที่ 12.4** สำหรับแบบจำลองความเป็นผู้ใหญ่ที่เป็นหลักยึดของการประเมิน
และ **บทที่ 12.2** สำหรับเช็กลิสต์การเปิดตัว การทบทวน และการตรวจสอบที่ทำให้แต่ละขั้นเกิดขึ้นได้จริง
